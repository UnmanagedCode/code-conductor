## Stack
- Node 24+ (native type-stripped TypeScript for `src/*.ts`, `node:test`, top-level await, `crypto.randomUUID`).
- `express` (REST + static) + `ws` (WebSocket).
- Vanilla HTML/CSS/JS in `public/`, no build step.
- `happy-dom` (dev-only) for DOM-backed rendering tests.
- No DB — projects in `<projectsRoot>/`, sessions in `~/.claude/projects/<encoded-cwd>/*.jsonl` (the jsonl root is overridable via `CLAUDE_PROJECTS_ROOT`).

## Component layout
- **server.ts** — Express + ws boot, mounts `/api` → `/mcp` → `/plugins` (reverse proxy) → static, binds `127.0.0.1:8787`. The WebSocketServer is `noServer: true` with a manual `server.on('upgrade')` dispatcher: `/ws` → wsHub, `/plugins/<id>/…` → plugin proxy raw-socket pipe, anything else destroyed. (With `noServer` the ws lib never attaches to the http server, so the old EADDRINUSE error-forwarding guard around `listenWithRetry` is gone — `tests/eaddrinuse-retry.test.mjs` covers the retry path.) Creates the plugin host and, after listen, feeds it the bound port + fires its adopt-on-boot init. Sets `process.title = 'code-conductor'` on entry so `pkill -f code-conductor` targets it precisely and `pkill -f server.ts` misses it. Launched via `conductor.sh` (`npm start`).
- **src/instances.ts** — Instance class, InstanceManager, capped event ring (`EventLog`: drop-oldest at `ORCH_EVENT_RING_CAP` (default in this module); `_seq` stamped at push and never renumbered; `trimmedBefore` = first retained `_seq`; trim snaps the surviving head to an outer `user_echo` turn boundary, falling back to the nearest **quiescent point** (`firstQuiescentAtOrAfter`, parser.ts) when no echo is in reach so the gap-case head still opens on whole blocks — plain cut only for a giant non-quiescent span; `snapshotTail()` serves the trailing window around `ORCH_SNAPSHOT_TAIL` (default in this module) events for WS subscribe, quiescent-snapped via `snapStartToQuiescent` — the snap moves the start EITHER way (forward, past an open block or a headless run, when the raw cut lands mid-block; back, to an earlier quiescent point, when the forward search finds nothing before the ring's end), so the served tail can be shorter OR longer than the cap and no inequality holds in general — backstopped by `lastQuiescentAtOrBefore` (parser.ts) when the forward snap would push past the ring's own end (the tail's only remaining content was sub-agent children with no reachable head), serving from the nearest quiescent cut rather than returning an empty tail; **retention is storage-only, decoupled from the live feed** — `push()` declines to retain the CLI's per-token floods (see the `thinking_tokens` entry in [protocol.md](protocol.md) for which models were observed emitting that one; prose streams one `text_delta` per token on every backend) so a single long turn can't overflow the ring and strand the archive mid-turn: `system/thinking_tokens` (a live-only last-value-wins counter, never persisted) is dropped from the ring entirely, and consecutive `thinking_delta` **or** `text_delta` of one `(msgId, blockIdx)` block fold into ONE slot — the same one-delta-per-block shape disk replay produces (`src/transcript.ts`), so ring + jsonl-archive reconstruct identically. The two kinds never fold into each other (`tail.kind === v.kind`), and `msgId` is per-message so a sub-agent block can never fold into an outer one; async sub-agents interleave their deltas with the outer turn's, breaking adjacency, so folding does not apply inside background-task regions. `context_usage` (the `message_delta`-sourced ctx reading — see [protocol.md](protocol.md)) is declined for the same storage-only reason: a re-subscribing client is seeded from the `lastContextUsage` field, and on the only backends that emit it every in-tail `message_start` carries `usage: null` and so cannot clobber that seed. The replay-path `message_start` (`replayed: true`, emitted by `loadHistory` to seed the ctx readout — see [protocol.md](protocol.md)) is declined too: it is synthetic, so it must not become history, and keeping it off the ring also keeps it from ever becoming the ring head (`message_start` is quiescent, so a trim could snap there and its non-`user_echo` head would read as mid-turn and mark a spurious `history_gap`). It also never advances `ring.nextSeq`, which `idleSubscriptions.ts` arms on as its "activity since arm" marker — defense-in-depth rather than a live hazard, since the event fires once inside `loadHistory` before any turn and so cannot land inside an arm→fire window. A declined event gets no `_seq`, so `_emitUi` still emits it seq-less and the LIVE per-token stream is untouched; the first delta of a block anchors the slot with its `_seq` so a later forward page dedups via the client's `seenSeq`. In-place `tail.text +=` is **append-only** — the slot is never shrunk, replaced, or renumbered — so a consumer holding a shallow snapshot across an `await` (`ringSnapshot` → `pageInstanceEvents`, `snapshotTail` → `wsHub`) can only observe a longer extension of the same `_seq`, never a torn or duplicated one. That, not synchronous serialization, is what makes it safe: `wsHub` subscribes the socket **before** calling `snapshotTail()` and awaits `reconstructActiveTasks` before sending, but the client clears before replaying a snapshot (`public/wsRouter.js`) so live frames emitted inside that window are discarded in favour of the grown slot, and on the paging path the client's `_seq` dedup drops an already-applied slot outright. The current counter isn't lost for a client joining mid-stream: `_emitUi` also keeps the latest count as O(1) `_liveThinkingTokens` state (set per `thinking_tokens`, cleared on `thinking_start`/`thinking_end`/`turn_end` so a finished block shows none), exposed via `inst.liveThinkingTokens` and re-attached by the WS subscribe path as a trailing seq-less `system/thinking_tokens` on the snapshot — so a fresh subscriber sees the coalesced partial thinking text (from the ring slot) AND the current count with no flicker. A block that has already CLOSED gets nothing re-attached, so a redacted one — which replays no text at all — would rebuild as a bare `thinking (redacted)`; `_emitUi` therefore stamps the final estimate onto the retained `thinking_redacted` slot as `estimatedTokens` before pushing it. Ring-resident only — the `thinking_tokens` entry in [protocol.md](protocol.md) enumerates the jsonl-backed rebuild paths that lose it), absolute `userIndex` stamping on outer user_echoes (the rewind/fork anchor — immune to trimming), control_request round-trip, mode validation. The **context-size** reading rides the same O(1)-state-on-the-snapshot pattern as `_liveThinkingTokens`, for the same "the ring is not a reliable carrier" reason: `_emitUi` latches every **usage-bearing** `message_start.usage` — or `context_usage.usage`, the fallback kind for a backend whose `message_start` is all-zero — as `_lastContextUsage` (a null-usage frame of either kind leaves it alone — see those two kind entries in [protocol.md](protocol.md) for why the parser produces them; exposed via `inst.lastContextUsage`, sent as the snapshot's `lastContextUsage` **field** — not an appended event, which would also reach `conversation.apply`). Only those two kinds feed the client's `UsageTracker`, and a turn whose final text block outruns the tail leaves the quiescent snap no cut except past the whole block, so every `message_start` lands below the window and a re-subscribe would otherwise rebuild an empty tracker (`ctx —` — the symptom on a backend that answers in one long block). Two deliberate differences from the thinking counter: it is **not** cleared at `turn_end` (the reading stays valid between turns, which is exactly when a reload would lose it), and its only reset is `_wipeForResume` (rewind/respawn) — a fork or a resume-after-restart needs none, since each builds a new Instance whose constructor starts it `null`, and a fork must leave the parent's value alone because that session continues. **Resume idempotency:** `create()` is a thin synchronous wrapper over `_doCreate()` that guards duplicate resumes of one sessionId — an already-live session (`i.proc`) throws 409 `already attached`, and a still-in-flight resume (tracked in `this._resuming`, keyed on the session's PUBLIC id when it is already in memory, so two callers naming one session by different forms still coalesce rather than racing two subprocesses onto one transcript) is **coalesced** (the second concurrent caller gets the same restored instance, one subprocess). The checks run in the wrapper's synchronous prefix (before any `await`), closing the window `_doCreate` opens between the guard and `spawn()` attaching `.proc`; the map entry is released when the create settles (success OR failure). This makes the restart anchor auto-resume racing the manifest restore — and manual stop+resume — safe regardless of caller. **Deferred steers** (`_pendingSteers`, `queueSteerAfterStop`/`_flushPendingSteers`/`steerPending`) park a message bound for a model that cannot take a mid-turn injection: the SOFT block-edge stop is armed (`interrupt()`, idempotent — N queued steers arm one abort and are delivered as one joined message) and the queue is flushed from the `turn_end` branch on a `queueMicrotask`, so the event reaches every subscriber — `IdleSubscriptionHub` reads `steerPending` synchronously — before `prompt()` flips the status back. The queue is drained before the send (exactly-once), rejected with a `system`/`stderr` annotation when `_setStatus` reaches a dead status, and any drain that starts no turn emits `system`/`steer_settled` so a wake deferred behind it is never stranded. Callers reach it through `promptOrQueueSteer(text, attachments?)` — which tests the one `needsPostStopSteer` predicate and never awaits the block edge — rather than testing the flag themselves; which route ran is deliberately not reported to any caller. Attachments ride along on `PendingSteer`. Routed-site inventory in [protocol.md](protocol.md).
- **src/idleSubscriptions.ts** — `IdleSubscriptionHub`, the idle-wake graph extracted from `InstanceManager` as a composed collaborator. **Wake-on-turn-end is a property of OWNERSHIP, not of a registration verb:** a conductor owns a target if it spawned it (`Instance.callerInstanceId`) or has ever dispatched to it (`noteDispatch`, called by every turn-starting MCP handler BEFORE the send), and `ownersOf(targetInstanceId)` is the union of the two minus self, filtered to live instances. Two maps, both **keyed by the stable instanceId** (the event stream carries it, and it survives an in-place `/clear`, so keying by instanceId needs no migration): `_owners` (`targetInstanceId → Map<callerInstanceId,{timeoutMs}>`, the durable dispatch edges plus each owner's preferred heartbeat window) and `subscribers` (`targetInstanceId → Map<callerInstanceId,{timerId,timeoutMs}>`, the ARMED wakes — so it is empty for every target that is not mid-turn). `onTurnStart(targetInstanceId)` arms one entry per live owner, driven by `InstanceManager`'s per-instance `'turn_start'` wiring off `Instance._setStatus`'s into-`turn` branch, so prompted and **unprompted** turns re-arm identically (the auto-approved-plan case) and the arm is synchronous inside `prompt()` — there is no registration window for a fast `turn_end` to fall into. `subs.has(caller)` makes it idempotent: a mid-turn steer on an already-armed pair delivers ONE wake. sessionId lives only at the boundary: `noteDispatch`/`setIdleTimeout` translate the MCP-supplied sessionIds to instanceIds on entry (via `liveForSession`), `deliver` translates the target instanceId back to its current sessionId for the wake stub, and the test-only `snapshot()` projects instanceIds back to sessionIds. Nothing is persisted and every map is purged on `remove()`, so there is nothing to "survive a restart." An armed wake is consumed by whichever of **three trigger paths** lands first — `turn_end`, the **idle task-drain settle** (`ORCH_IDLE_DRAIN_SETTLE_MS` — see the wake state machine below), or **rotation completion** (`_onRotationComplete`, for a rotation that comes up idle with no turn at all — i.e. a prune; a renewal declares `comesUpIdle:false` and is delivered by its reseed turn's `turn_end`) — plus two non-delivering clears: `purge` (instance removal) and `disarmSilently` (the `interrupt_turn({force:true})` path — CALLER-SCOPED: it clears only the interrupter's own entry, BEFORE the abort's own `turn_end`, so that turn wakes the interrupter not at all while every OTHER owner is woken there with the interrupted variant. Clearing the whole per-target map instead stranded every other owner with no stub and no heartbeat, on a wait nothing could end — and the interrupter need not even be an owner. `_owners` is left intact, so the next turn re-arms). Alongside them runs a **repeating heartbeat** (`_arm`'s `setInterval`, `.unref()`'d, window = the owner's `timeoutMs` else `DEFAULT_SUBSCRIBE_TIMEOUT_MS` via `ORCH_SUBSCRIBE_TIMEOUT_MS`): it delivers the `timedOut` "did NOT finish" stub and mutates **nothing**, so the pending turn-end wake is untouched and a hung worker keeps reporting. Its single exception is a target that is GONE FOR GOOD (`_goneForGood`) — no `turn_end` can ever follow, so that ping retires the entry rather than pinging forever. That is deliberately NOT just `!proc`, which is equally true across a prune/rewind/respawn's kill→relaunch gap: the check also requires that nothing is reviving it (`relaunching` / `rotationPending` / `_mutating` — `rotationPending` covers the whole rotation window, and reading `rotationInFlight` beside it was the same `_rotation` field spelled twice), because retiring inside that gap would drop an entry whose wake is still owed (the rotation's own completion, or the reseed turn's `turn_end`) and leave the owner with "did NOT finish" as its last word. `setIdleTimeout` records the window AND re-arms a running heartbeat (mid-turn is its only real use case). `onEvent` receives every instance event: `_onTurnEnd` **defers** delivery while the target's `activeAgentTaskCount > 0`, `taskNotificationPending`, or `rotationPending` (keeping the wake and its heartbeat armed), so a wake fires only once the worker's turn ends with no live background subagents and no context rotation in flight; `_onTaskEvent` covers the drain-at-idle-with-no-re-invocation case; a subagent that never finishes shows up as a repeating heartbeat. The rotation defer reads `Instance._rotation` (opened at `arm()` / at the top of `pruneSession`, closed by `endRotation`) rather than any controller state, so it holds regardless of listener registration order — the hub's listener is registered *before* the renew controller's, which is why a wake used to be spent on the **armed** `turn_end`, a turn early. Cross-instance lookups + `subscription_changed` emission route back through the manager. `InstanceManager` delegates the `noteDispatch`/`setIdleTimeout`/`disarmIdleSilently`/`isIdleCaller`/`ownedWakeTargetsOf`/… surface and exposes the live `_idleSubscribers` getter. `ownedWakeTargetsOf(callerInstanceId)` backs the `renew_session` mechanical state block (see `src/sessionRenew.ts`) and deliberately reports the OWNED set rather than the armed one: the armed set is empty whenever a target is idle, which would gut that block's "never orphan a worker" purpose precisely in the case it exists for. `noteRenewalDeclined(targetInstanceId, requestedBy)` records a one-sentence note in `_pendingDeclines`, keyed target→**caller** and only when that caller is actually waiting (`_isWaitingOn`: still armed, or armed at the turn_end being dispatched — `_justConsumed` now carries the caller set for exactly this). `_takeDecline` read-and-deletes one pair's note, and every path that ends a single caller's wait calls it — delivery before its first `await`, the dead-caller drop in `deliver()`, `disarmSilently`, and `purge`'s **caller-end** loop; `purge`'s **target end** drops that target's whole inner map in one `_pendingDeclines.delete` instead. `severForOverageStop(instanceId)` wraps `purge` for a session that is being STOPPED but is still alive: it additionally drops wakes already deferred behind other recipients that name this session as their target (which `purge` keeps, since a removed target still reports honestly) and returns every instance that lost a pending callback — the overage stop marks each. See the overage entry below. Either way a note reaches the conductor that asked, exactly once, and can never linger onto an unrelated wake. `deliver()` picks one of four stubs (`_plainStub`/`_buildFoldedStub`): a real `turn_end` to an already-idle caller **folds** the worker's recent output inline (reusing `buildRecentMessages` from `mcp/handlers.ts` + `flattenPayload` from `mcp/content.ts`, tagged with the `public/wakeCallback.js` marker for the collapsible UI bubble); the heartbeat and live mid-turn steering paths keep the plain pointer stub (a mid-turn wake is injected live into the caller's running turn), and so does the **interrupted** variant — a `turn_end` produced by a FORCE-abort (`Instance.turnForceAborted`) is never folded even to an idle caller, since the body separator is the client's "finished result" signal and partial aborted output must not read as one. That qualifier is READ by all three consuming paths (`_abortQualifier`) and cleared by neither: its lifetime is owned entirely by the two turn-start rules, so it stays true from the abort until the next turn begins. `onTurnStart` clears it when NO armed wake survived into the transition — armed means the wake is the aborted turn's own deferred one and the qualifier still describes it (the CLI resolves such a wake by opening exactly an unprompted re-invocation turn), while nothing armed means there is nothing left for it to describe, which is the only state a sole owner's own force-abort can leave behind. `prompt()` clears it in the case that check deliberately does not: a wake DID survive, but a new instruction supersedes the abort. Clearing at resolve time as well was removed for being indistinguishable from doing nothing — after any consuming path the target's `subscribers` entry is empty, so the next turn start necessarily sees no survivor and clears. A caller whose model declares `midTurnSteering:false` (`acceptsMidTurnSteering`) takes neither: its wake is **held** in `_deferredWakes` (caller-keyed) and flushed by `_flushDeferredWakes` at that caller's own next `turn_end` — or on `system`/`steer_settled` when a queued steer drains with no turn to end — re-deferring once more while `caller.steerPending`; a held wake whose target went busy again is marked stale (plain stub + `STALE_WAKE_NOTE`) rather than folded. `steerPending` is also a fourth `_onTurnEnd` defer reason on the TARGET side, for the same reason `rotationPending` is: the `turn_end` came from a block-edge stop, not from the worker finishing. See [protocol.md](protocol.md) and [models.md](models.md#mid-turn-steering-capability). No import cycle — nothing in `handlers.ts`'s import graph reaches back to `instances.ts`.
- **src/overageResume.ts** — `OverageResumeController`, the overage auto-resume timer machine extracted from `InstanceManager` as a composed collaborator. Owns the `instanceId → fireAtMs` (wall-clock epoch-ms **deadline**) map (**keyed by the stable instanceId**, so a due-tick resolves the Instance by a direct `byId.get(id)` rather than a scan) and `AUTO_RESUME_TEXT` (re-exported from `instances.ts` for back-compat); the per-Instance overage flags (`autoResumeAt`/`autoStoppedForOverage`/`_overageHandled`/`_overageResetsAt`) stay on the Instance. Firing is driven by a **single shared wall-clock sweep interval** (`ORCH_OVERAGE_RESUME_SWEEP_MS`, `unref()`'d — started on first arm, stopped when the map empties), **not** one `setTimeout` per session: each tick re-reads `Date.now()` and fires every deadline that is now due, so a deadline that lapsed while the process was suspended (Android Doze / Termux backgrounding freezes the libuv monotonic clock a `setTimeout` rides) fires on the first tick after wake. `resetsAt`-based scheduling, deadlines in-memory but persisted in the resume manifest (survive a graceful restart), never kills/respawns. **Usage-verified fire:** a due deadline does NOT resume on our clock alone — the tick does ONE coalesced `fetchUsage()` (`getAccountUsage`, injectable seam; its usage-cache cadence + backoff absorb the pressure — one fetch shared across all sessions due that cycle, guarded by `_ticking`) and only resumes when `usageOverThreshold(usage) === false` (five-hour util `< 100` and under any enabled threshold — the SAME evaluator the poll trip uses). Still-over → `_reschedule` to `max(resetsAt, now + ORCH_OVERAGE_RECHECK_MS)` (also pushes the manager's global `_overageResetsAt` forward so the lockout gate's future-resetsAt rail stays satisfied while parked), naturally polling at each recheck until the account clears — which is what kills the boundary re-trip (no resume turn is ever sent while still throttled). Can't-confirm (null/backoff/malformed) reschedules too, up to `FAIL_OPEN_AFTER` consecutive failures, then fails open and resumes so a persistently-down usage API can't park a session forever. `arm()` no longer dead-ends on a missing/past `resetsAt` — it schedules the first check at `now + recheck`; **`auto_resume_skipped`** now fires ONLY for the genuine "process gone" case in `run()`. `armRestored` (restart) re-inserts its persisted deadline as-is (keyed by the freshly-created Instance's new instanceId — the manifest persists the deadline by sessionId, and restore re-arms off the live restored `inst` after `create()`) and inherits the same usage-verified fire. `InstanceManager` delegates the `_armAutoResume`/`_cancelAutoResume`/… surface (also called from the temp-session exit branch so a disposed temp session never leaves an orphan deadline) and exposes the live `_autoResumeTimers` getter. **Message queueing:** while a session is auto-stopped-and-armed, a non-internal `Instance.prompt()` is intercepted **before** `emit('user_prompt')` and pushed onto `inst._overageQueue` (`{text, attachments, ts}`) with an `overage_message_queued` UI event — it does NOT resume or cancel. `run()` flushes on fire: it snapshot-empties the queue, calls `cancel(sid)` FIRST (clears `autoStoppedForOverage`/`autoResumeAt` so the follow-on resume send isn't re-queued — `cancel` is idempotent), emits an `auto_resume` system line, then sends ONE combined `internal:true` `prompt()` (`buildCombinedResumeText` = the kind's base preamble + numbered list, with all queued attachments concatenated) with `_overageResumeFiring` set around it. **The preamble selector is THREE-way**, owned by the single `overageResumeKind(inst)` mapping: `_overageWasStopped` → `AUTO_RESUME_TEXT` ("continue where you left off"); `_overageWasIdleParked` → `IDLE_PARKED_RESUME_TEXT` (the stop found it idle, so nothing of its own was interrupted); neither → `QUEUED_ONLY_RESUME_TEXT` (the softened line, non-empty queue only). Both conductor clauses ride all three. `cancel()` also clears `_overageQueue` (kill/remove/temp-exit/shutdown cleanup). `summary()` exposes `queuedCount` (rides every status emit → header/sidebar badges append `· N queued`). `fireNow()` is the sweep-internal + test seam and is also the primitive `InstanceManager.reevaluateOverageResumes()` drives (one `fireNow` per parked instanceId, snapshotting `timers.keys()` first since `fireNow` synchronously deletes its own entry) — called after a Settings → Account Apply that raises/disables the threshold, so a session parked under the OLD bar resolves against the new one immediately instead of waiting out its deadline. There is still **no** early-resume UI/button — this is a settings-save side effect, not a user-facing control.
- **src/usageWindowDomains.ts** — the backend-scoped **usage-window domain** seam that decides whether an instance is subject to the overage flow at all. A usage/rate-limit window is a provider concept: `usageDomainOfBackend(backend)` maps the identity `claude` backend to `'anthropic'` and every other registry backend to a domain named after itself, and `MONITORED_DOMAINS` (today just `{'anthropic'}`) names the domains with an active monitor. `InstanceManager` composes four helpers on top: `agentTreeRoot(inst)` (walks `callerInstanceId` **UPWARD** through `byId` to the tree's root; terminates on no-parent, a parent no longer live, or a cycle via a `seen` set, returning `inst` itself in every degenerate case), `agentTreeBackends(inst)` (cycle-safe **DOWNWARD** walk of `inst` + its conducted-worker descendants by `callerInstanceId` → `Set` of backend ids; in-process Agent-tool subagents share the parent CLI's launch-fixed backend so they add nothing), `usageWindowDomainsOf(inst)` (that same downward subtree, mapped to domains), and `_inUsageWindowFlow(inst)` — which evaluates `usageWindowDomainsOf(agentTreeRoot(inst))`, i.e. the **ROOT's** whole tree, because the unit of stopping is the tree (card 2026-0212). A root tree with no Claude agent → e.g. `{ollama}` → exempt; a root tree with any Claude agent → in-flow *for every member*, so a non-Claude conductor with Claude workers **and** a non-Claude worker under a Claude conductor are both in. Root resolution deliberately stays out of `agentTreeBackends`/`usageWindowDomainsOf`: they promise the argument's own subtree, and pushing it down would make `usageWindowDomainsOf(worker)` report its conductor's domains. **Stop vs trip:** `_handleOverageTrip` does NOT use `_inUsageWindowFlow` — it tests the emitting session's OWN backend (`isMonitoredDomain(usageDomainOfBackend(inst.backend))`), since only that backend says which account's window a `rate_limit_event` reports; it is strictly narrower, so it cannot admit a trip the root-scoped predicate would reject. Shipping a monitor for another backend's window later = add its domain to `MONITORED_DOMAINS`; no exemption logic changes.
- **src/usageOverageMonitor.ts** — `UsageOverageMonitor`, the server-side usage poller composed by `InstanceManager` as a second, equal-footing overage-trip source alongside the stream `rate_limit_event`. On an `ORCH_USAGE_POLL_MS` interval (`unref()`'d), `_tick()` is heavily gated (skip if `_overageActive`, threshold disabled, `getOnOverageAction()==='none'`, or nothing mid-turn — so it doesn't fetch needlessly), then calls `getAccountUsage()` (injectable as `fetchUsage` for tests; a throw or null is swallowed → no false-trip) and, when the **five-hour** window's `utilization` (a 0–100 percent) `>= overageThresholdPct`, calls `manager._handleOverageTrip(null, { resetsAt })` — the *same* seam the stream trip lands in. It writes no parallel stop logic and injects no prompts (routing's `internal:true` prompts are inherited), so dedup (`_overageActive`), conductor/conducted/plain routing, and resume all behave identically regardless of source. `start()`/`stop()` are idempotent; the server starts it after `listen()`, and both `shutdown()` and `shutdownForResumeSync()` stop it. The point: the stream event only reports near Anthropic's own ~90% mark, so a *low* threshold (e.g. 25%) is invisible to it — only the poll catches it. `parseResetEpochSecs` is exported from `instances.ts` and reused here to turn the bucket's ISO `resets_at` into epoch seconds. `forceTick()` is a thin public passthrough to `_tick()` — the same gates apply — used by the Settings → Account Apply handler (`src/routes.ts`) so a *lower* threshold that's already crossed trips a mid-turn session immediately instead of waiting up to `ORCH_USAGE_POLL_MS` for the next scheduled tick.
- **src/sessionLineage.ts** — the sidecar store that makes a session's identity permanent. `<store>/session-lineage.json`: `publicId → { current: <backingId>, segments: [{ id, reason, at }, …] }`, with the **backing → public reverse index built in memory at load and never persisted** (a second on-disk copy is a divergence surface). A session's **public id** is minted once from the first 8 hex chars of its first CLI `session_id` (`mintPublicId`, extending to `xxxxxxxx-xxxx` on collision, then to the full id with a `console.warn`); derive-check-extend-**and-write** is one operation under `withLock`, or two concurrent spawns mint the same id. The **collision universe is every key in BOTH indexes**, so a fresh public id can never shadow another session's segment. Follows `src/tempSessions.ts` verbatim otherwise: bulk load, atomic tmp+rename, `withLock` around every mutation, a module-level `serialize` chain, `loadStrict` inside mutations (so a failed read aborts rather than clobbering), missing file = empty with ENOENT the only legitimate empty base case.

  **BASE CASE, not a legacy branch:** absent row ⇒ public id == backing id. Every resolver returns its input unchanged for an unknown id, so pre-existing sessions work with **no migration and no backfill**, and nothing anywhere asks "is this a legacy id?". `migrations/` is untouched by this store.

  `reason: 'initial' | 'renew' | 'prune'` is load-bearing, not polish. Every segment's file survives on disk in both mechanisms, so segments are uniform for *identity* — but not for *content*: a `renew` segment is **disjoint** from its predecessor (full history is their concatenation) while a `prune` segment is a filtered **copy** that **overlaps** it (`src/sessionPrune.ts` writes a new file and leaves the original untouched) and must never be concatenated. `reason` alone carries that — do **not** add a second boolean that can disagree with it.

  API: `loadLineage` · `mintPublicId` (only caller: `Instance.launch()` on a fresh spawn) · `recordRotation(publicId, backingId, reason)` (appends + advances `current`; **creates the row lazily** for a previously row-less session by promoting its public id to an `initial` segment; idempotent on a retry) · `revertRotation` (drops the trailing segment iff it is the one named, and **deletes the row entirely** when that restores the base case — only caller: `pruneSession`'s rollback) · `resolveBacking` (public → `current`; a known **segment → itself**, deliberately, so clicking an archived row opens *that* transcript rather than silently redirecting to the newest) · `publicIdFor` · `segmentsFor` · `dropSegment`.

  **Read tolerance, not writes on reads.** A row can outlive the files it names (Claude prunes its own `~/.claude/projects` after ~30 days). `findSessionLocation` therefore resolves, probes, and on a miss walks the row's segments **newest-first**, returning the first that exists — read-only, because a write inside a hot read path races concurrent readers. The two places that *do* prune are the ones that know a file is gone for good: `deleteSessionForCwd` (the only jsonl-deleting path in the repo) and `Instance.loadHistory`'s ENOENT branch, both via `dropSegment`.

  **The path chokepoint.** `sessionFilePath(absCwd, backingId)` / `subAgentDirPath(absCwd, backingId)` in `src/projects.ts` are the only constructors of a transcript path, and both call `assertBackingId` — which THROWS when handed something shaped like a minted public id. It is an assertion, not a branch: nothing resolves differently by id length. `isMintedPublicId` (same regex, one source) lets a route that has already resolved and *still* sees that shape decline cleanly as an unknown session (null / false / 404) instead of turning a clean miss into a 500. `tests/session-lineage-chokepoint.test.mjs` fails the build on any other `.jsonl` path literal, with a small named exempt list and a vacuity guard.
- **src/sessionRenew.ts** — `SessionRenewController`, the managed session-renewal machine composed by `InstanceManager` (the `renew_session` MCP tool). Owns a `instanceId → {state:'requested'|'armed'|'clearing', opts, oldSid, timerId}` map. **Keyed by instanceId, not sessionId**, because renewal's whole job is to rotate the caller's sessionId out from under it — only the stable `byId` key survives. `arm(instanceId, {summary, followUp?})` (idempotent; re-arm refreshes opts, always carrying `followUp` forward) registers a pending renewal, and CONSUMES a `requested` entry for that instance if one is pending — folding its `followUp` in. `request(instanceId, {followUp, requestedBy})` registers the conductor-side ask (`requestedBy` is the asking conductor's sessionId, so the decline can be reported to IT and no other watcher) (see the `renew_session` targeted form in [protocol.md](protocol.md)); it overwrites another request but never a live `armed`/`clearing` renewal, and deliberately opens NO rotation window, so a decline rides the worker's ordinary `turn_end`. `dropRequest` un-registers one whose prompt never went out. `onEvent` acts on `turn_end` for a pending instance: `requested` → the entry is deleted and `manager.noteRenewalDeclined(id, requestedBy)` is called SYNCHRONOUSLY in that dispatch (the decline; the ordering that makes it reach the already-queued wake is documented on `noteRenewalDeclined` in `idleSubscriptions.ts`); `armed` → the caller's next `turn_end` drives `Instance.clearContext()` (a server-managed `/clear`, see protocol.md) and remembers the pre-clear sessionId → `clearing`; `clearing` → the first `turn_end` where `inst.backingSessionId` has rotated off the pre-clear id (i.e. `/clear`'s own turn_end, after its `system/init`) builds the mechanical state block (`buildStateBlock(manager, id)` — **at this point, not at arm time**, so it reflects current state) and injects `buildRenewSeed({...opts, stateBlock})` as the cleared session's first user turn (`prompt(..., {internal:true})`). The public `inst.sessionId` is pinned throughout — only the backing id moves.

  **The reseed waits on durability.** `system/init` corrects in-memory truth in its own tick and kicks the `recordRotation` write onto the instance's serialised `_lineageWrite` chain immediately — the earliest possible point, since the CLI has ALREADY written the new transcript by the time we see that line, making durable-before-first-use physically impossible. `_onClearingTurnEnd` then **awaits `inst.flushLineage()` before the reseed** (`flushLineage` rethrows the first failure since the last flush; the error is remembered rather than swallowed so a failed write cannot wedge later rotations). On rejection it emits a `system`/`renew_error` UI event naming the orphan risk and **still reseeds** — the clear already happened irreversibly and the summary is the only thing that can save the session. Failure-visible, not abort. The reseed's own failure gets the same event, replacing a `.catch(() => {})` that silently lost a cleared-context-with-no-summary. **Consequence for readers: "rotated" no longer implies "seeded"** — the reseed is dispatched one or more ticks after the rotation.

  **The rotation window.** `arm()` calls `inst.beginRotation('renew')` — mid-turn, when the tool is called, well before that turn ends — and every exit path closes it via `_clear(id, {ok})` → `inst.endRotation({ok, comesUpIdle: !ok})`. The window lives on the `Instance` (not in either controller) so `IdleSubscriptionHub`'s defer works regardless of listener registration order; `comesUpIdle` is `false` only on the success path, where a reseed turn follows by construction. Every abandonment — dead proc at either `turn_end`, a `clearContext` throw, the rotate watchdog, `purge()` — declares `comesUpIdle: true`, because no turn is coming at all and the completion event is then the only wake point a waiting conductor will ever get. Unlike the instanceId-keyed side structures, the **transcript-keyed** durable markers (`temp`/`conducted`/title/mode/backend) DO need carrying — they are looked up by FILENAME (`listSessionsForCwdWithCounts`), so the carry is a backing→backing move and reads `backingSessionId` at both ends: `clearing` calls `inst.carryMarkersAcrossRenewal(oldSid)` (fire-and-forget, best-effort) which marks the rotated id **first** (`markTemp`/`markConducted`/`setTitle` per the flags the instance carries — closing the window before the reseed `turn_end`'s incidental `_writeSessionMetadata` re-write, and carrying the title, which no `turn_end` path writes) then retires the abandoned old id **last** (`unmarkTemp` + `markArchived`, mirroring `_archiveTempSession` — conducted/title stay meaningful on the archived row); new-id-first ordering means a crash mid-way can't strand the new id unmarked while the old id is archived. No side-structure migration is needed — the idle-wake graph and overage timers are keyed by the stable instanceId, which `/clear` preserves. A `turn_end` that has NOT rotated (a mid-turn-queued user turn the CLI ran before `/clear` took effect) is ignored, so an intervening turn can't reseed into the wrong session. The `armed` state **defers** the clear while the caller has an overage-queued turn (`_overageQueue.length`), live subagents (`activeAgentTaskCount`), or an owed re-invocation (`taskNotificationPending`) — so queued/background work is never stranded by the rotation (mirrors the idle hub's defer gate). That gate only re-fires on a `turn_end`, so an armed renewal has a **second fire trigger** for the case no `turn_end` ever follows: a `system/task_updated`|`task_notification` that leaves the instance drained-idle fires the clear immediately (`_onArmedDrain` → the same `_fireClear` the turn_end path uses). Exactly those two subtypes, mirroring `IdleSubscriptionHub._onTaskEvent` — a broader "any event while idle" trigger would `/clear` before a test's next `send_prompt`, breaking the `go1 < /clear < seed` ordering — and no settle window, because the hub's exists to avoid waking one turn EARLY while the only risk here is a concurrently-opening turn, after which the queued `/clear` still reseeds correctly. A `.unref()`'d `ORCH_RENEW_CLEAR_TIMEOUT_MS` watchdog (default `CLEAR_ROTATE_TIMEOUT_MS` in `src/sessionRenew.ts`) abandons a renewal that never rotates rather than wedging the instance. `buildRenewSeed({summary, followUp?, stateBlock?})` composes the seed text, each part under its own fence: the self-authored summary, then the conductor's post-renewal `followUp` (a task, as against the summary's memory), then `stateBlock`, the mechanical state block. `buildRenewRequest({directive?})` composes the turn-A prompt a targeted request sends (ask → decline path → the summary call), and `RENEW_SUMMARY_TEMPLATE` is the ONE home for the summary structure, read from here by the `summary` argument description in `src/mcp/tools.ts` too. `buildStateBlock(manager, callerInstanceId)` enumerates `manager.liveOwnedBy(callerInstanceId)` (live instances the caller spawned, via the same `callerInstanceId` tracking the sub-agent panel uses — `{sessionId, project, worktree, status}`) and `manager.ownedWakeTargetsOf(callerInstanceId)` (every session the caller OWNS — spawn or dispatch — whose next turn will wake it) — framed as a safety net: it wins for **existence**, the self-authored summary wins for **intent**. `InstanceManager` delegates `armSessionRenew`/`requestSessionRenew`/`dropSessionRenewRequest`; `remove()` calls `_sessionRenew.purge(id)` (a `requested` entry holds no rotation window, so purging it closes nothing).
- **Overage trip detection + central routing** (in `src/instances.ts`) — the *decision* of what to do on an overage trip moved off the per-Instance handler (which can't reach the idle-wake graph) up to `InstanceManager`. Two sources reach `_handleOverageTrip`: the per-Instance stream path below, and the `UsageOverageMonitor` poll (above) — deduped by the global `_overageActive` one-shot so they never double-trip (whichever observes the crossing first wins). Flow: `Instance._isOverageTrip(data)` (hard `isUsingOverage` flag OR, when `getOverageThreshold().enabled`, `utilization >= pct/100` for any window) → `Instance` emits an `overage` signal (throttled per run by `_overageHandled`) → `InstanceManager._handleOverageTrip` holds a global one-shot `_overageActive`/`_overageResetsAt`/`_overageClearTimer`, returns early when `getOnOverageAction()==='none'`, else `_routeOverageStop` (**the stop SENDS NOTHING to anything** — the account is throttled, so a message into it is the burn the stop exists to prevent. Every session routing touches goes through the one `_directOverageStop`: mid-turn → soft-interrupt via `interrupt()`; already idle → the same notice + sever + arming, with `interrupt()` a no-op it returns from on `status !== 'turn'`. Pass 1 resolves in-control conductors (`_ownerConductor` = `byId.get(worker.callerInstanceId)`, in-control = mid-turn or `isIdleCaller`) and their `protectedWorkers`; Pass 2 stops each such conductor — the ONLY path an idle session reaches, since Pass 3 skips anything not `status === 'turn'`; Pass 3 stops every *other* mid-turn instance, protected workers included, in ONE branch (card `2026-0189`, done). The collapse is behaviour-identical for a `.conduct` orchestrator that is **not** itself a conducted worker — the ordinary case, where `unarmed` is false and it takes exactly the arming the deleted conductor branch gave it. It is NOT identical for a `.conduct` session spawned through MCP `spawn_instance`, which carries `conducted:true` + `callerInstanceId`: mid-turn under an in-control owner it is now treated as a protected worker (stopped un-armed, owner marked) where the old branch armed it. That is the intended reading of "protected worker" — its owner is the sole driver on resume — so the collapse is kept, not special-cased. `.conduct` has no routing special case left: a mid-turn orchestrator is soft-interrupted like anything else), and arms `_armOverageClear(resetsAt)`.

  **A conductor's workers are stopped un-armed, and its callbacks are dropped.** Pass 3 passes `armResume:false` for a `protectedWorker`, so it is interrupted and emits `auto_stop_overage` but sets no `autoStoppedForOverage` — no per-session resume timer, because the conductor is the sole driver on resume. Arming both would have the conductor's re-drive land mid-turn on a worker that just self-resumed, which is the mid-turn injection this path exists to avoid. **Severing the subscription graph has ONE owner.** `InstanceManager._severOverageWakes(inst)` wraps `IdleSubscriptionHub.severForOverageStop(inst.id)` + the mark loop, and has exactly TWO callers: `_directOverageStop` (the stop) and `_guardOverageTurnStart` (the turn-start lockout guard, below). It is called for every session the stop touches: an interrupted session's `turn_end` would otherwise wake its watcher with an `internal:true` prompt, which the overage queue intercept deliberately does **not** hold, so the watcher starts a fresh turn *inside* the lockout — the burn the stop exists to prevent. Keyed on the **idle-wake** graph, not on the conducted-SPAWN graph — a distinction that survives the graph becoming ownership-keyed, because ownership there is spawn OR dispatch: a conductor can be waiting on a session it never spawned, and keying on spawn alone left exactly that case armed. Both directions (the stopped session must wake nobody and nobody may wake it) plus wakes **already** deferred behind a mid-turn recipient — `purge()` deliberately keeps those, because a *removed* target still reports honestly through `deliver()`, but a stopped-and-alive one must not be reported at all. It returns every instance that lost a pending callback, including the stopped session itself, and each is **marked** `_overageDroppedCallbacks` — marked, not notified: the mark only reaches an instance that has a resume prompt of its own to carry it, which an un-armed worker or any session under plain `Stop` does not. An armed wake a stopped conductor holds on a target Pass 3 leaves running is covered by the same call (since card 2026-0212 root-scoped the predicate, the reachable case is a **non-owned** backend-exempt target — a standalone session with no `callerInstanceId` to walk up, held via `noteDispatch`; a *conducted* exempt worker is now in-flow and Pass 3 stops it); left armed, the heartbeat (`DEFAULT_SUBSCRIBE_TIMEOUT_MS`, well inside a five-hour window) would fire mid-lockout — repeatedly — delivering an `internal:true` wake the queue intercept does not hold. **Why the turn-start GUARD severs too:** `purge()` clears the dispatch edges but not spawn ownership — `ownersOf` re-adds the parent from `Instance.callerInstanceId` on every call — so a stopped, already-severed worker whose turn starts again re-arms its conductor's wake at `onTurnStart`; without a sever there, the guard's own interrupt produces a `turn_end` that delivers an `internal:true` wake stub, i.e. a message sent during the lockout. `purge()` itself is deliberately unchanged: a *removed* target must still report honestly through `deliver()`, which is exactly why `severForOverageStop` exists as the overage-specific wrapper.

  **The conductor resume prompt is composed from TWO independent flags, each gating its own clause** (`buildConductorResumePreamble`, `src/overageResume.ts`): `_overageDroppedCallbacks` (a callback was severed → re-check the sessions directly instead of waiting to be woken) and `_overageUnarmedWorkers` (set on the OWNER when Pass 3 stops a worker un-armed → those workers will not resume themselves, re-prompt them). Either can hold without the other — a conductor can lose a callback on a session it does not own, or own an un-armed worker while holding no subscription at all — so one selector for both would make the other clause assert something that did not happen. Neither clause describes *how* anything was stopped: the conductor does nothing differently for that, and it cannot be stated truthfully for a mixed set. Both clauses ride the queued-only preamble too (`appendConductorClauses`), since the human typing into a stopped conductor arms it queued-only and it would otherwise lose them. Both persist in the resume manifest alongside `overageWasStopped`, for the same reason — losing either delivers a resume prompt missing a fact the conductor must act on, and it then waits forever for a wake nothing will send. The manifest key `overageStoppedWorkers` is the **pre-rename spelling** of `_overageDroppedCallbacks` and is deliberately not renamed: a manifest written before the rename is read during exactly the restart it exists for.

  **A worker left un-armed also refuses queued sends.** `_overageStoppedUnarmed` is **assigned** (never latched) per trip on it — a later trip can find the worker un-protected, and a stale `true` would refuse every send to an ordinary session while the only thing that could clear it is the send it refuses. It is surfaced on the status frame — **ungated**, because `_clearOverage` clears the flag in the same loop that re-emits every summary, so the frame is already accurate (a second `gate.active` guard there would be redundant and unkillable). Two clears, neither redundant with the other: `_clearOverage` is global at window release, `OverageResumeController.cancel()` per-session and reachable while the window is still active. Pass 3's `= unarmed` assignment is *equivalent* to a conditional set, since `_handleOverageTrip` returns early on `_overageActive` and routing therefore runs once per window. It is read via `Instance.overageSendRefused` (the one test of the condition, ANDing the flag with the live window so the refusal lifts by itself at reset). The AND is **load-bearing, not defensive**: the gate also requires `_overageResumeMode` and `atMs > Date.now()`, so it is inactive under plain `Stop` — where Pass 3 still sets the flag but there is no queue to strand anything in — and during the `_armOverageClear` buffer between the window expiring and `_clearOverage` running by `Instance.prompt`'s overage intercept: queueing would strand the text forever (the queue is flushed only by a fired deadline, and `cancel()` discards it) and `_armResumeNow` must not arm one, since a self-resuming worker plus a re-driving conductor is the mid-turn injection this card closes. So the send throws instead (CONVENTIONS: fail loudly), `_armResumeNow` guards as a backstop, and `public/composer.js` stops offering the "Queue" affordance for such a session and says the conductor owns it. On the **MCP** surface the four sending tools turn it into a soft `OVERAGE_STOPPED_UNARMED` refusal (`overageUnarmedRefusal`) rather than a throw — this surface's convention, and a conductor just told to re-drive these workers hitting one early is a correctable mistake it should branch on; the WS path keeps the throw. The `auto_stop_overage` event carries **`armResume`**, not the routing mode, because `public/blocks.js` renders `resume:true` as "auto-resuming at ⟨time⟩" and an un-armed worker has no resume to name. **Global release is unified with the per-session rechecks:** the clear timer's callback is now `_maybeReleaseOverageLock` (a BACKSTOP for the never-armed case), which clears the global flag ONLY when nothing is parked (`_overageResume.timers.size === 0`) AND no live instance is still `autoStoppedForOverage` (a session whose interrupt is armed but which has not yet arrived at idle will arm imminently — closes the past-resetsAt backstop race). The resume controller calls `_maybeReleaseOverageLock` after every deadline-removing outcome (verified resume, fail-open resume, process-gone teardown), so the lockout lifts exactly when the last parked session resolves — the release and the resumes can't disagree because they're the same usage-verified sweep. `_clearOverage` (backstop fire, that release path, or manual takeover of an `autoStoppedForOverage` session via the `user_prompt` handler) releases the flag and resets every instance's `_overageHandled`. For `stop-resume`, a stopped conductor arms its own resume either way, but **by two different routes**: a MID-TURN one sets `autoStoppedForOverage` before the abort and its timer arms on the next status→idle transition, while an IDLE-PARKED one never transitions at all (it is neither prompted nor interrupted) and so is armed at routing time by `_armResumeNow(inst, resetsAt)` — the same controller entry point a queued-only session uses, and its only arming. `_directOverageStop` reads `midTurn = inst.status === 'turn'` BEFORE the interrupt to pick between them, and that same boolean sets the preamble selectors (`_overageWasStopped` vs `_overageWasIdleParked`). Its `protectedWorkers` are the one exception (`armResume:false`, above). Resume timing keys off the five-hour `resetsAt` (read camelCase epoch from the live event by `parseResetEpochSecs`), **not** the far-future `overageResetsAt`. **A prompt runs `_cancelAutoResume` iff it is NOT `internal`** — the flag is the whole test the `user_prompt` handler applies, so no site list here can go stale. `internal:true` senders today, as examples: the idle-wake wake stub, the renewal reseed (`sessionRenew.ts`), and the auto-resume's own send. Note that "server-authored" is NOT the same classification: two server-side sends go out **non-internal** and so do cancel a pending resume — the restart notify (`resumeRestart.ts`, harmless because `!e.overageStopped` excludes exactly the sessions that have a resume) and the auto-approved-plan approval (via `promptOrQueueSteer`, contrived to reach). A new server-side notification must therefore pass `internal:true` deliberately rather than inherit it from those precedents. The auto-resume's own fire is `internal:true` too and tears its deadline down by calling `cancel()` directly inside `run()`. **Turn-start lockout guard** (`_guardOverageTurnStart`, wired on the existing `turn_start` listener AFTER `_idleHub.onTurnStart` so the survived-a-wake / abort-qualifier bookkeeping is untouched): any turn that begins while `inst._overageGate().active` is soft-interrupted — wakes severed first, then `interrupt()` (never `force:true`) — and a server-side `system`/`soft_interrupted` carrying `data.text` names the lockout as the cause. The gate call is the single owner of every scope condition (active + resume-mode + future finite `resetsAt` + `_inUsageWindowFlow`), so plain `Stop`, an expired window and a **root**-exempt session all fall out of it. Root-exempt, not domain-exempt: a session on an unmonitored backend whose ROOT tree contains a `claude` agent (an ollama worker under a Claude conductor) is deliberately guarded — that guard is the backstop for the F1 wake-stub burn (card 2026-0212). The one exemption is `inst._overageResumeFiring`, set around the auto-resume's own send in `OverageResumeController.run` and cleared in the prompt's `.finally()` — **the flag is what exempts the turn in every interleaving**, not any ordering. Ordering only explains why the gate is still observably active at `turn_start` for an EMPTY-QUEUE resume: `prompt()`'s only `await` is its attachment loop, so with no attachments `_setStatus('turn')` → `turn_start` runs inside `run()`'s own frame, before `_resolveDue` calls `_maybeReleaseOverageLock()` at all. A resume carrying QUEUED ATTACHMENTS yields at each `await saveAttachment(...)` before `_setStatus('turn')`, and `run()` does not await its own prompt — so the release can interleave first and, with nothing else parked, the gate is already lifted by the time that turn starts. Parked count is not what guarantees passage; the flag is. A context rotation started during the lockout IS guarded (`clearContext` sets `turn` directly and its reseed is a real API-burning turn): accepted, bounded by `CLEAR_ROTATE_TIMEOUT_MS` + `signalRotationTurnLost`. **Domain-scoped exemption, resolved from the tree's ROOT:** every *routing* decision gates on `_inUsageWindowFlow(inst)` (see `usageWindowDomains.ts`), which asks the question of the **root's** whole tree, so a session is outside the flow only when that whole tree is purely in an unmonitored domain (no `claude`-backed agent anywhere in it): `_routeOverageStop` filters such instances out of `live` (never stopped or marked); the per-instance `_overageGate` returns `active:false` for them (so their sends never queue **and** `summary().overageActive` stays false → no overage badge); `_guardOverageTurnStart` inherits that through the gate; and `resumeRestart.ts` skips re-arming a restored deadline onto one (a no-op in practice — restored entries carry `callerInstanceId: null` and worker-group entries are skipped, so a restored instance is always its own root). Arming is thus unreachable for **root-exempt** instances without extra guards. A non-Claude worker under a Claude conductor is NOT root-exempt: routing handles it exactly as it would a Claude sibling in the same position — stopped and badged, then armed-and-queueing *or*, when it was **mid-turn at the trip** **and** its conductor is in control, stopped **un-armed**, which refuses sends rather than queueing them. Both conjuncts are load-bearing: Pass 1 adds to `protectedWorkers` regardless of the worker's status, but Pass 3 visits only `status === 'turn'` and is the only writer of `_overageStoppedUnarmed` whose value is **decided** rather than an unconditional reset to `false` — every other write is such a reset (the constructor, the respawn wipe, and the two clears named earlier in this paragraph), so the mark's *presence* is proof Pass 3 visited. A worker of an in-control conductor that had already gone idle is therefore skipped entirely — never stopped, never marked — and queues like any other in-flow session (an ordinary shape, not an edge: workers idle out before a window trips). Which case a session lands in follows from its position in the tree and its status at the trip, per Pass 1/Pass 3 above; membership is what root-scoping fixes, not the per-case verbs. What matters is that it never RUNS a turn inside the lockout — mid-turn ⇒ stopped by Pass 3; idle ⇒ any turn it starts is aborted by the turn-start guard, which fires off the same gate — and that is what makes its `turn_end` unable to deliver a wake stub into the throttled account mid-lockout (card 2026-0212). `_handleOverageTrip` is the one site that does **not** use this predicate — it tests the emitting session's own backend instead (see the `usageWindowDomains.ts` bullet above); the `null`-inst poll trip is account-global and unaffected by either.

What makes "some page carries it" hold at all is that backward pages **tile unconditionally**: every window is served (none is ever skipped — see the backstop note below), so each page's `nextBefore` is its own served start and the next page's end is this page's start. So: never silently dropped. It can still be emitted **twice** in one narrow case — when the snap lands a straddling page's start exactly *on* the seam, that page splices at offset 0 and the page below it splices at its own end. Known, much narrower than the pre-seam-anchoring double class it replaced, and deliberately not closed). The archive is loaded for two reasons, not one: the requested window's seq extent dips below `trimmedBefore`, **or** the tentative ring window holds a sub-agent child with no owning head inside the ring (`hasHeadlessChildIn`, parser.ts) — group heads are resolved over the whole loaded array, so such a child reads as headless and gets pushed out of the only page whose window covers it unless the (usually archive-side) head is loaded with it. Backward pages return an opaque `nextBefore` cursor that jumps the numeric gap between the two seq spaces. Rejected-window backstop: when the quiescent snap would reject a window outright (`start >= end` — the window's only content was sub-agent children with no reachable head), the page is instead served from `lastQuiescentAtOrBefore(rawStart)` (parser.ts) — the window's own pre-snap start, down-snapped to the nearest quiescent cut — rather than coming back empty; a backward page is empty **iff** the window itself is empty (`end === 0`), which is terminal (`hasMore` is already false there), so this is total: every non-empty window is served, on some page, exactly once. Headless children served this way ride along and park client-side (`Conversation.orphanChildEvents`) rather than rendering, which is strictly better than the events being dropped along with their whole merged component; window starts snap to **quiescent points** (`snapStartToQuiescent`, parser.ts: no open outer block, every `tool_use` resolved; outer `user_echo`/`turn_end` force-reset the scan; sub-agent events are scan-opaque — nested-block wholeness comes from the group-boundary resolver, which moves the cut EITHER way: an available head is dragged into the page with its whole group, while a child with no head at or before it in the loaded array has the cut pushed past it (unreachable by design rather than served orphaned); the archive→ring seam is passed as `resetIdx` so state is never scanned across missing events). - **src/sessionPrune.ts** — **Prune**: a mechanical, zero-token context compaction. `analyzeSessionForPrune({cwd,sessionId})` returns per-turn, per-category prunable-token counts; `pruneSessionToNewId({cwd,sessionId,cutTurnIndex|keepLatestTurns,pruneThinking,inputMode,mode})` writes a stubbed copy under a fresh `sessionId` (same atomic tmp→rename + `sessionId`-rewrite + `writeSessionMetadata` convention as `sessionEdit.ts`) and returns `{newSessionId, turnCount, cutTurnIndex, saved}`. **Cut range: `0…turnCount` inclusive** — `turnCount` is a full prune, newest turn included; only `turnCount+1` and above 400, and a zero-turn session is refused outright. The two cut arguments are **XOR** (supplying both, or neither, throws — no silent precedence): `keepLatestTurns` resolves to `Math.max(0, turnCount - keepLatestTurns)` **inside** the transform, which is the only point past `Instance.pruneSession`'s subprocess kill — a caller that pre-read the count via `analyzeSessionForPrune` could have a turn land in between and silently keep one turn too many. A user prompt's own text and every `text` block survive a full cut untouched (a pure-user-prompt line's `content` is a string, so it is not `touchable`), and the unresolved-`tool_use` thinking exemption is message-keyed and cut-independent, so an interrupted newest turn keeps its signed thinking. Both passes route every block through ONE `pruneBlock()` helper, so the dialog's savings preview cannot drift from what the transform does — which is also why the exempt-tool check (`isPruneExemptTool`, invariant 6 below) lives **inside** `pruneBlock` rather than in either caller's loop; `pruneBlock` returns the original block whenever the stub would be *larger*, so pruning never inflates the context. Turn boundaries come from `isPureUserPromptLine` (transcript.ts) — the same index space rewind/fork use — which is what makes the slider's turn-snapping structural rather than cosmetic: the cut can never land between a `tool_use` and its `tool_result`. `Instance.pruneSession()` (instances.ts) wraps it in the `rewindToUserMessage` skeleton (`_mutating` guard → idle-only → `kill` → transform → `_wipeForResume` → `launch({resume:newSid})`) and then reuses `carryMarkersAcrossRenewal(oldSid)` from the renewal path to carry temp/conducted/title/backend and archive the abandoned id. **Only the BACKING id rotates — the instanceId and the public `sessionId` are both preserved**, so the idle-wake graph, overage timers, the renew controller, every `?caller=<instanceId>` MCP handle and every id a conductor holds stay valid with no migration. The rotation is recorded as a `prune` segment BEFORE `launch()` (prune is server-minted, so it is the one rotation that can be durable before first use) and the fail-safe catch calls `revertRotation`, so a throw inside `launch()` can never leave a segment the process never ran. It sets a one-shot `_skipUsageSeed` consumed in `loadHistory`, because the jsonl's newest assistant `usage` still reports the PRE-prune size. On a mid-transform throw it fails **safe**: the subprocess is already dead by then, so the catch respawns against the ORIGINAL backing id (always possible — Prune only ever writes a new file) and rethrows the real cause, rather than leaving the instance wedged with no proc and no respawn. `Instance.prompt()` refuses with 409 while `_mutating` is set, closing the sliver between a caller's idle check and the kill in which a prompt would be written to stdin and its partial tail folded into the rewritten file — rewind gets the same protection for free, and `Instance.forkAtUserMessage()` (instances.ts, sitting alongside its two rewrite siblings) sets the same flag around `forkSessionAtUserMessage` — fork never kills its source subprocess, so `!this.proc` does not cover it at all; the flag is scoped to the READ, since once the copy is on disk a prompt to the source cannot affect it. Fork also refuses (409) when `_mutating` is already set, rather than reading a jsonl a concurrent rewind/prune is rewriting. The fork ROUTE (`routes.ts`) only parses `userMessageIndex` and spawns the `createArgs` the method hands back — every guard, the flag claim/release and the derivation of those respawn arguments belong to the instance, which is what all three of them are read off. Not a new failure class for callers, which already tolerate the `not running` throw from the same window. Unlike `renew_session` it never calls `prompt()` — a pruned session resumes **idle**.
  - **Harness-state invariants (derived by probing the real CLI — treat as spec).** The CLI rebuilds its read-before-edit cache (`readFileState`) by REPLAYING THE TRANSCRIPT on resume, reading `input.file_path` off every Read/Write/Edit `tool_use` and pairing it with the matching `tool_result`. So: **(1)** never rewrite a `tool_use.input` key set — only string *values* are edited and path keys are skipped at any depth; replacing an input with a marker object drops `file_path` and every later Edit fails with "File has not been read yet". **(2)** never touch `toolUseResult` — it is a disk-only sidecar (pruning it saves zero *context*) and its ABSENCE is the CLI's discriminator for "this is a human user turn". **(3)** `tool_result.content` stays a string **except for pruned Read/Write results, which use a block array deliberately**: the CLI only reconstructs a `readFileState` entry when `typeof content === "string"`, so the array form is what makes the read-before-edit guard RE-ARM once the file's content has left the context. Normalizing (3) back to a string would look like a cleanup and would silently re-break that guarantee — the model would be allowed to edit a file it can only "remember", reconstructing an `old_string` that may not match or may match the wrong occurrence. Switchable via `PRUNE_STUB_AS_BLOCKS` (default `true`). An Edit-seeded cache entry is out of reach either way: the CLI re-reads that path from DISK using only `input.file_path` and a non-error result. The reconstruction pass branches on exactly three tool names — **Read, Write, Edit** — so `SEEDING_TOOLS` is `{Read, Write}` (Edit's result content is irrelevant to it). `NotebookEdit` is a defined tool-name constant that the pass never references: a notebook result cannot seed the cache, and since nothing seeds it from a transcript, a notebook edit already needs a live Read after ANY resume — pruning neither causes nor worsens that. The guard is only *enforced* for a fixed model set (haiku-4-5, sonnet-4-5/4-0, opus ≤4-6, 3-x) — which is why `tests/prune.real.test.mjs` pins `claude-haiku-4-5`; on Opus 5 / Sonnet 5 it would pass vacuously. **(3a)** Truncate mode cuts with `sliceCodePoints`, which backs off one unit when the cut would land inside a surrogate pair — `slice` counts UTF-16 code units, and a lone high surrogate has no valid UTF-8 encoding, so a naive cut writes unencodable content into a jsonl whose whole contract is that it resumes cleanly. Minimal mode replaces whole values and is immune. **(4)** No entry and no block is ever removed, which is what keeps the `parentUuid` chain and the `tool_use`/`tool_result` pairing invariant safe with zero relinking. **(5)** Sidechain entries are never pruned and never counted in the estimate; the sibling sub-agent directory (`<encoded-cwd>/<sid>/subagents/`) is COPIED to the new sessionId, without which every sidechain silently vanishes from the pruned session's transcript view (`loadSubAgentTranscript` keys off the sessionId — `forkSessionAtUserMessage` has this same gap today). **(6)** Some tools are EXEMPT by name (`isPruneExemptTool`): their `tool_use` and the `tool_result` answering it are copied verbatim in every mode, at any cut. Two classes — **`AskUserQuestion`**, because the question card is rebuilt entirely from `input.questions` on replay (`transcript.ts`) and the answer is recovered by *string-matching* the question text and option labels against the following `user_echo` (`public/userQuestionAnswers.js` → `isUserQuestionAnswerText`/`parseUserQuestionAnswers`, driven from `public/conversation.js`), so squeezing either side leaves an unreadable question and silently drops the answer off the card; and **core conductor MCP calls** (`mcp__code-conductor__<tool>`), the orchestration record of what was spawned, approved, merged, filed. The MCP half is exempt by NAMESPACE so a core tool added later is exempt by default, minus a hardcoded two-entry denylist `PRUNABLE_CONDUCTOR_MCP_TOOLS` = {`project_read`, `project_bash`} whose results are bulk file/command output — precisely what Prune exists to shed. **Not configurable**: which class a tool falls in is a property of the tool, not a user preference. Matching the prefix alone is not enough: what remains after it must ALSO contain no further `__`, since a plugin-forwarded tool carries one (`mcp__code-conductor__code-kanban__file_task`, `mcp__code-conductor__acme-tools__run`) and stays prunable. The separator tested is `__` and not `_`, which keeps a core tool whose own name contains a single underscore (`spawn_instance`, `merge_worktree`) on the exempt side; testing for `__` rather than for the first-party `code-*` plugin naming habit is deliberate, so a third-party plugin id classifies the same way. An orphaned `tool_result` (no `tool_use` in context ⇒ no name) stays prunable. Thinking blocks keep their `signature` when their text is stubbed: an *unsigned* thinking block survives the CLI's own other-model strip pass (which only removes SIGNED blocks) and would then reach the API unsigned; a stale signature was measured to provoke no rejection, and the CLI has a strip-all-and-retry recovery path regardless.

- **src/sessionActivity.ts** — `lastActivityOf(path, stat)`: when a session transcript was last ACTUALLY active, as epoch ms. The ISO `timestamp` on the LAST timestamped record in the jsonl (last in file order, not newest by value — records are appended in real time, so the two differ only where interleaved sidechain records land a few ms out of order), found by a bounded 64 KB tail read; falls back to `stat.mtimeMs` when the tail holds no timestamped record. **Not mtime**, because the CLI appends untimestamped bookkeeping records (`last-prompt`, `mode`, `ai-title`) as its process exits — so a mass subprocess exit (a server drain/restart) stamps every live session's file within the same millisecond, collapsing distinct sessions into one indistinguishable minute days after they actually stopped. This is load-bearing on Termux: post-restart CPU throttle (~10–75×) can starve a live holder for many seconds mid-write, and the old-server/new-server overlap during a restart is the only window with cross-process contention; the previous 10 s age-based eviction reclaimed the live holder there, letting two writers run the read-modify-write concurrently and drop each other's entries (a lost update) — which silently un-archived a subset of sessions on every restart. A slow holder is now waited out via bounded retries (a truly wedged holder throws on acquire rather than corrupting), and release is **ownership-token-checked** so a process can't delete a successor's lock. `archivedSessions.ts` additionally guards against a **silent full-reset** under the host's frequent OOM/low-disk churn: it keeps a rolling `.bak` (refreshed under the lock only from a non-empty write that is a **superset** of the current backup — never a shrink — so a spurious empty/tiny base can't canonize over the last-good snapshot; consequently `.bak` may lag behind un-archives by design, the safe direction: a recovery from a stale `.bak` only re-archives a few since-unarchived ids, never loses data); a missing primary recovers from `.bak` (missing primary **and** `.bak` = legitimately empty); a corrupt primary is quarantined to `.corrupt-<pid>-<ts>` (under the lock, in the mutation path) and recovered from `.bak` rather than bricking archiving; and a drain-to-empty now writes `{"sessions":[]}` atomically **instead of unlinking**, so an absent primary unambiguously means external loss. Only a genuine unrecoverable I/O error (EACCES etc.) still aborts a mutation. `tempCleanup.ts` writes/sweeps `<store>/pending-temp-cleanup.json` to GC temp jsonl orphaned after exit; it and `resumeManifest.ts` write their sync-before-exit manifests via tmp-write + `renameSync` so an OOM mid-write can't leave a torn manifest.

- **src/groupedCommand.ts** — `runGroupedCommand({argv}|{shell}, {cwd, env?, timeoutMs?, cap?, onChunk?, killGraceMs?})` → `{code, stdout, stderr, output, timedOut, truncated, durationMs, spawnError}`, plus `killProcessGroup(pid, {graceMs, fallback})` and `GROUP_OUTPUT_CAP`. - **src/jsonStore.ts** — `createJsonStore({file, noun, empty, parse, toDoc, isEmpty, unlinkWhenEmpty?, loadLenient?, loadStrict?, afterWrite?})` → `{load, mutate}`. The one read-modify-write machine behind every `<store>/*.json` session sidecar. `mutate(fn)` = `serialize( withLock( fn(loadStrict(), write) ) )`: the **lock** is the correctness guard (O_EXCL, `storeLock.ts` — it excludes same-process callers too), the **chain** is a contention guard keeping same-process writers off the lockfile so a burst can't exhaust the bounded acquire retries, and the strict re-read **inside** the lock is what makes the base canonical. `load()` is lenient (any failure → empty + warn, for the query surface); `loadStrict()` throws on anything but ENOENT so a transient read error can't be laundered into "the store was empty" and written back as truth. Writes go through `writeFileAtomic` (`src/projects.ts`, documented above) and unlink when empty by default. The returned surface is deliberately just those two: `loadStrict` and `write` stay INTERNAL, reachable only through `mutate`, because a public bare `write()` would be an UNLOCKED atomic write on the very primitive that exists to guarantee the lock. The three optional hooks exist for `archivedSessions.ts` alone (`.bak` recovery, always-write-a-document, rolling-backup refresh inside the lock) — see that module. **Behaviour change on adoption:** `sessionTitles`/`sessionSummaries` previously did their in-mutation read with the LENIENT loader, so corrupt JSON degraded to an empty map that was then written back carrying only the new entry — silently discarding every other title/summary in the file. On `createJsonStore` they read via `loadStrict`, so corrupt JSON now throws and the mutation aborts with the file untouched. This is the intended fail-loudly direction and matches what the four already-hardened stores did on main; a class of silent data loss became a loud failure. Pinned by `tests/store-lock-lost-update.test.mjs` (the cross-process lost update) and `tests/store-lock.test.mjs` (the lock primitive, including that the lock is held until `fn`'s BODY settles — `return await fn()`, not `return fn()`).

- **src/plugins/** — the plugin subsystem ([features](features.md#plugins), [wire contracts](plugins.md)). **Trust stance: plugins are trusted own code** — same-origin iframes + supervised child processes with the conductor's privileges; there is no sandboxing. Modules:
  - **registry.ts** — `createPluginHost({instances})`, the single service layer shared by REST (`api.ts`), the reverse proxy and MCP forwarding. Owns discovery (scan `projectsRoot()` top-level dirs for manifests; a project whose main checkout has NO manifest file falls back to its worktree checkouts — first valid manifest in sorted-name order, via the store metadata with no git spawns — so a plugin-in-progress in an unmerged worktree can bootstrap (`manifestSource` marks the origin; enable then defaults `activeVersion` to that worktree; an invalid main manifest is never masked); duplicate id ⇒ first-alphabetical wins, rest `conflict`), lifecycle state (`stopped|starting|ready|crashed|failed` on top of `discovered/enabled⇄disabled` + `invalid|incompatible|conflict`), lazy `ensureStarted` (deduped in-flight start, exponential crash backoff and a crash-count threshold ⇒ `failed` (constants in `src/plugins/registry.ts`)), discovery-time CC-Dev workspace auto-assign (every rescan/boot places any unassigned discovered plugin project into CC-Dev, not just on enable — the conductor's own project gets the same placement via a separate one-time boot seed in `server.ts`, since it isn't a plugin), worktree-version activation (cwd resolved via `worktrees.ts` metadata; manifest re-read + id-checked from the active checkout every start), and **adopt-don't-drain**: children are detached process groups that survive the conductor's self-respawn — `init()` re-adopts a recorded pid that's alive+answering, else clears the record (the liveness predicate and the ready/adopted lifecycle mutation are here; the record pruning + its single write are the store's, see `store.ts` below). Health is passive (child exit events, proxy `reportUpstreamFailure`, on-demand `status()` probe) — no periodic poller (battery).   - **contributions.ts** — `createContributions({ensureInit, contributingEntries, resolveCwd})`, the composed collaborator owning everything enabled plugins contribute to the conductor beyond an HTTP backend: `conventions()`, `roles()`, `claudePluginDirs()`, BOTH caches (`fragmentBodyCache`, the memoized `conventions()` result) and the `registryGeneration` counter that invalidates the second — a counter whose only reader is that memo. The registry signals into it through `invalidate()` (drop bodies + bump) and `noteRegistryChange()` (bump only), and holds no cache of its own. `roles()` is deliberately **synchronous and init-free** (a role binding is inline in the manifest, and `appSettings.resolveRoleBackend` resolves it at spawn time; `server.ts` installs the provider before `init()`) — pinned by `tests/plugins-host-surface.test.mjs`. The `conventions()` accessor returns the contributions of enabled+`ok` plugins only (bodies read from the active checkout, cached in a single process-lifetime `fragmentBodyCache` keyed by absolute path) — each entry carries `body` (fragment, `''` when the convention is scaffold-only) and optional `scaffold` (resolved directive text). Two distinct failure modes, treated differently: a **vanished fragment/scaffold file** is skipped with a warning, same as always — the convention just contributes nothing, same as if it were never declared. A **failed cwd resolution** is transient infra (e.g. a worktree checkout not yet mounted), not "contributes nothing", so it additionally flags `.degraded` on **every** scope array the function returns — including ones left empty — because an empty-and-unflagged array is exactly what "this scope genuinely has no plugin contributions" looks like, and the one plugin that failed may have been the only would-be contributor to that scope; see `fragmentCatalog.ts`'s `CatalogList` and the `src/projectClaudeMd.ts` bullet below for what a reader does with that. The cache is dropped wholesale (the registry calls `contributions.invalidate()`) at the start of `rescanInternal()`, at the top of `doStart()`'s async body, right after `setActiveVersion()`'s `saveRegistry()`, and right after `enable()`'s `saveRegistry()` — every explicit "the checkout on disk moved, or a disabled plugin's fragments are about to matter again" gesture (rescan, start/restart, an active-version switch even on a stopped/backendless plugin, and enable — a fragment can be edited while its plugin sits disabled) — so neither a `git pull` into an already-loaded checkout nor an edit made while disabled keeps serving stale fragment text for the process lifetime. `conventions()` itself is **memoized**, because it is not a cheap read (it walks `contributingEntries()` and calls `resolveCwd()` per contributing plugin, and `resolveCwd` → `reconcileActiveVersion` does a dynamic `import('../worktrees.ts')` plus a store read for any worktree-pinned plugin — and `server.ts` wires **two** providers onto it, so one `GET /api/settings/conventions/conductor` was two full scans and a mutating plugin route fanned out through `regenerateAllProjectConventions` at two scans per project). The invalidation signal has **two parts, both load-bearing**: (1) a `registryGeneration` counter, owned here and bumped through `noteRegistryChange()` from `saveRegistry()` (which every mutation of `persisted.plugins` is immediately followed by — so the set is provably complete rather than hand-enumerated, and it is what catches `disable()`, which deliberately does *not* drop fragment bodies), inside `invalidate()` (so a stale fragment body can never survive in a cached result), and — again via `noteRegistryChange()` — immediately after `doStart()`'s `entry.manifest = result.manifest` reassignment (which happens ten lines *after* that function's own invalidate, so a concurrent read landing in between would otherwise be cached pre-reassignment); and (2) a per-call `existsSync` liveness re-check of the checkout dirs the cached scan actually read — both the discovered project dir and the resolved cwd. A checkout deleted from under a running server mutates no registry state, so the counter alone cannot see it, and serving a cached "still here" would silently disable the `.degraded` flag that `ensureProjectConventionsMd`'s never-blanks decline depends on; a vanished dir simply falls through to the real scan, which degrades exactly as it does uncached. The generation is snapshotted **before** the scan loop, because `reconcileActiveVersion` can `saveRegistry()` mid-computation when it self-heals a vanished worktree pin — the result is then tagged stale and recomputed once, and the idempotent self-heal does not bump again. **The returned object is shared by reference and must be treated as read-only**; both consumers are verified non-mutating (`fragmentCatalog.ts` reads `.degraded` then copies every entry via `raw.map(r => ({...r, builtin:false}))`; `server.ts`'s two providers only index `.project` / `.conductor`). No defensive shallow copy is made — the entry objects would still be shared, so it would buy the appearance of safety rather than safety. `server.ts` wires it to the projectConventions and conductorConventions providers. `conventions()` is **grouped by the required per-entry `scope`** (keyed by `SUPPORTED_CONVENTION_SCOPES` from manifest.ts; `project`/`conductor` today, `workspace` rejected at load); `server.ts` routes the `project` group to `projectConventions` and the `conductor` group to `conductorConventions`, so adding a scope is a one-line enum move + one provider wiring, not a redesign.
  - **store.ts** — `createPluginStore({onRegistryChange})`, the persistence collaborator: the two JSON files under `<orchStoreRoot()>/plugins/` — `registry.json` `{plugins:{<id>:{project, enabled, activeVersion}}}` and `runtime.json` `{<id>:{pid, pgid, port, startedAt, gitHead}}` (both shapes pinned by `tests/plugins-store-files.test.mjs`) — plus their load policy and the adopt pass's record pruning. A non-ENOENT load failure of either is **not** swallowed: the bad file is renamed to `<file>.corrupt` — a fixed name, so a prior backup is overwritten — and recorded on `notices()`, which the registry re-exports, `GET /api/plugins` returns and the Settings → Plugins status line renders; without that, the `{plugins:{}}` fallback silently resets every plugin's enabled state and pinned version with nothing anywhere saying so. A failed rename is itself non-fatal — the notice carries `backup: null`. Notices reset per `load()` pass, and `load()` reads registry.json before runtime.json. **Reads hand out shallow copies and every mutator writes** (`upsert`/`setEnabled`/`setActiveVersion` for registry.json; `recordStart`/`clearRuntime`/`clearRuntimeDetached`/`adopt` for runtime.json) — that is what the boundary buys: no code outside this module can change persisted state without going through a method that persists it. `onRegistryChange` fires from the single registry.json save path, BEFORE the write (a failed write still leaves the contributions cache invalidated), which is what makes the invalidation set provably complete rather than hand-enumerated. `adopt({isAdoptable})` is **inverted** rather than lifted whole: the store iterates only its own records, asks the injected predicate, clears the rejects in one write (only when something changed) and returns the adopted ids for the registry to mark ready — moving the whole pass here would have needed back-references to discovery and lifecycle. The file paths are functions, recomputed per call, so a `PROJECTS_ROOT` swap between test roots is picked up.

- **src/waitFor.ts** — `waitFor({initial, subscribe, timeoutMs, onTimeout})`: the one promise shape behind every LISTENER-driven wait. `initial()` is the already-satisfied fast path, checked before any listener is attached (returns `{value}` or `null`); `subscribe(settle, fail)` attaches whatever listeners it likes and returns an opaque teardown that detaches all of them — which is why the N-listener case needs no special support; `onTimeout()` picks the timeout's disposition by RETURN TYPE — an `Error` rejects, anything else resolves. The **source of truth travels with the project**: line 1 is a marker `<!-- cc:conventions <slug,…> -->` (built/parsed by `buildMarker`/`parseMarker`) so any cc instance regenerates the body from the file alone (survives move/rename/import into a store with no record of it). `composeProjectConventionsDoc(slugs, missing?)` = marker (all `slugs`, unchanged) + `composeProjectConventionsBlock` bodies for the resolvable slugs, with a visible in-body note (`` > Convention unavailable: `slug`[, `slug`…]. `` — `unresolvedNote`) naming any `missing` slug in place of its body. `ensureProjectConventionsMd(name,{log})` fetches the catalog (`getCatalog()`, returning a `CatalogList` — see `fragmentCatalog.ts`) and resolves each marker slug against it: **resolvable slugs recompose normally**; an **unresolvable** slug (custom convention absent here, disabled/absent plugin, retired seed) **stays in the marker** — so it recovers verbatim if it resolves again — but is named in the note instead of contributing a body. The write is **declined, leaving the committed file untouched (never blanked)**, in three cases: ≥1 slug is unresolvable AND the catalog is `degraded` (its `extraProvider` threw outright, or a plugin's own **cwd** resolution transiently failed — either way indistinguishable from "genuinely gone", so declining avoids mistaking a hiccup for a removal and stripping real text) → `{skipped:'catalog-degraded', missing}`; a slug is unresolvable, the catalog is NOT degraded, and nothing that does resolve carries a body → `{skipped:'unresolvable', missing}`; or every slug resolves but **none** of them carries a body (all scaffold-only, or a plugin update dropped a fragment while keeping the slug) → `{skipped:'no-body'}` (no `missing` — nothing is actually unresolvable). **Degradation only ever omits catalog entries — it never alters the body of one that's still present** — so a marker whose slugs all resolve regenerates normally even while the catalog is degraded elsewhere; the decline only protects a slug that's actually about to be dropped. Same never-blanks treatment for a missing file, a non-marker line-1 (grandfathered / hand-owned), or a *zero-slug* marker. Because only line 1 is ever parsed — the previous body (note included) is discarded wholesale before recomposition — the body is a **pure function of (marker slugs, catalog)**: repeated regeneration is byte-identical, the note cannot accumulate, and it vanishes cleanly (real text back, byte-identical) the moment the slug resolves again. **`ensureProjectConventionsMd` itself** (not the fan-out below) emits the five per-project log lines: `"CONVENTIONS.md left as-is for '<project>': catalog degraded, unresolvable <slugs>"` (catalog-degraded), `"CONVENTIONS.md left as-is for '<project>': unresolvable <slugs>"` (unresolvable), `"CONVENTIONS.md left as-is for '<project>': no selected convention carries a body"` (no-body), `"CONVENTIONS.md regenerated without unresolvable <slugs>: <path>"` (partial resolution), and `"CONVENTIONS.md regenerated: <path>"` (full resolution). **Boot ordering is a real constraint on this one call, and its violation is silent.** `regenerateAllProjectConventions` composes the PROJECT catalog — the one carrying an `extraProvider` — so it must run *after* `createServer()` has wired `setPluginConventionsProvider`. Unwired, that provider is a no-op stub returning `[]`, every plugin-namespaced slug lands in `missing` and is filtered out *before* compose, and each project's committed `CONVENTIONS.md` is rewritten with the plugin's real text replaced by the `> Convention unavailable:` note. Nothing throws and the boot log is clean. Pinned by `tests/boot-plugin-conventions-order.test.mjs` (a subprocess boot of the real `server.ts` — the only shape that can fail when the statement order moves). `ensureRootClaudeMd` is **not** what this protects: it composes the workspace catalog, which passes no `extraProvider` at all. `regenerateAllProjectConventions({log})` fans out over `listProjects()` (per-project try/catch) and owns exactly one line of its own — the only one signalling an actual fault rather than a designed decline — on a per-project exception: `"CONVENTIONS.md regenerate failed for '<project>': <message>"`. - **src/costTracking.ts** — per-turn cost persistence. `initCostTracking(instances)` subscribes to instance events and appends one JSONL row per `turn_end` to `<store>/costs.jsonl` (append-only). The `'event'` listener is synchronous and so cannot await the write: `appendCostRow` is itself **synchronous** — it snapshots the row (incl. `ts`, the live `inst`'s `project`/`model`/`sessionId`, and the resolved `costsPath()`) in the emit tick and hands the write to `writeCostRow` via a module-level promise chain (`serialize`, the same idiom as `tempSessions.ts`/`archivedSessions.ts`). It likewise omits the four token fields (`input_tokens`/`output_tokens`/`cache_creation_tokens`/`cache_read_tokens`) whenever `ev.usage` is null — the case for every turn on a substitution backend (its `result` frames carry no `usage`, and `message_start` is a non-summable context snapshot, so there is no per-turn token total; writing 0 would fabricate data). The gate is `usage`-presence (mirrors the client `UsageTracker`), so Anthropic rows — which always carry `usage` — are byte-identical, and a conditional spread keeps the fields in-position. `getCostSummary()` reads it back into the `{total_usd, row_count, by_project[], by_model[], daily_trend[]}` aggregate behind `GET /api/costs/summary`; it counts a row's tokens only when `'cost_usd' in r` (the Anthropic marker, robust to legacy non-Claude rows with stale 0s) and emits `tokens_known` per `by_model`/`by_project` entry (false ⇒ the `#costs` dashboard shows `—` instead of a bogus 0). `costsPath()` exposes the file path. Each `by_model[]` entry and each `by_project[]` entry (plus its nested `by_project[].by_model[]`) carries a `cache_misses` field — a plain count of that model's/project's rows with `cache_miss === true` — and a `sessions` field — the count of distinct `sessionId`s among that model's/project's rows (rows with `sessionId == null` excluded) — both folded into the same reduce loop that builds cost/token totals (no separate aggregation pass). Cache-miss detection is **cross-turn**, captured live in `src/instances.ts`, and catches *partial* (minority) evictions a stateless single-request rule cannot. Each turn is one or more API requests; `message_start` carries per-request cumulative usage and `cache_read` accumulates across a turn's tool-call iterations (there is no per-iteration array — `parser.ts` passes `result.usage` through verbatim). So the detector uses two points: `read_N` = this turn's **first**-request `cache_read` (`_turnFirstReqCacheRead`, pre-tool-call); `P` = the **previous** turn's **last**-request full prefix `cache_read + cache_creation` (`_prevTurnPrefix`), captured by overwriting `_turnLastReqPrefix` on every `message_start` and latching it at `turn_end`. **Miss ⇔ `read_N < P − max(1024, 1% of P)`** — this turn served less of the prefix than was cached at the end of last turn ⇒ eviction (full or partial); a warm continuation reads exactly `P` (drop 0, never flagged), the tolerance absorbs tokenization-boundary noise. **Turn 1** (`_prevTurnPrefix === null`) and any turn where `_prefixBaselineInvalid` is set fall back to the stateless `creation > read` rule, which still flags a genuinely cold prefix (cold start, expiry, resume, cold rewind). **Guards** against legitimate prefix shrink: compaction (`system`/`compacting` in `_handleStdoutLine`), model switch (`_trackModel`'s real-switch branch — cache is model-specific), and rewind/respawn (`_wipeForResume`) each set `_prefixBaselineInvalid`; the next turn's first request consumes it (forces the fallback, re-establishes `P` fresh) so the cross-turn rule never false-fires. **Known limitation:** a miss on a request *after* the first (e.g. a turn outliving the ~1h cache TTL) isn't caught — first-request-only. Per-turn capture (`_turnFirstReqCacheRead`/`Creation`/`_turnMissDetected`/`_turnLastReqPrefix`/`_turnEvicted`) resets in `_setStatus`'s into-`turn` branch and on (re)spawn; cross-turn state (`_prevTurnPrefix`, `_prefixBaselineInvalid`) intentionally persists across the turn boundary. Each `turn_end` is enriched with `cacheMiss`/`firstReqCacheRead`/`firstReqCacheCreation`/`firstReqEvicted` (`P − read_N` on the cross-turn path), persisted as `cache_miss`/`first_req_cache_read`/`first_req_cache_creation`/`first_req_evicted` (additive), and an informational `system`/`cache_miss` notice fires once per miss turn. The old read-time session-relative heuristic (`cache_creation_tokens >= max(50000, 4 × session median)`) was retired to a one-shot backfill, **migration 0014**, which stamps `cache_miss` on legacy rows; a row still carrying the old `cache_flush` key (a decisive verdict captured before the field was renamed) is renamed in place rather than recomputed, so historical rows are heuristic-or-renamed while new rows are decisive. Migration 0014 additionally stamps `cache_miss_heuristic: true` on any row whose verdict IT decided (neither key present, or a renamed `cache_flush` row lacking `first_req_cache_read` — an old-migration guess, not a live capture); presence is checked, not truthiness, since a decisive row can legitimately have `first_req_cache_read: 0`. `appendCostRow` never sets this field, so its absence always means "decisive."

## Conventions

Load-bearing rules this codebase follows — keep new work inside them so the project stays manageable as it grows.

1. **YAGNI — build for the requirement in front of you, not the one you imagine.** Implement only what a current, concrete caller or test needs; don't add speculative abstractions, config knobs, or extension points "for later" — they add surface area without a real user, and the eventual real requirement rarely matches the guess. If code stops being exercised by a real caller or test, delete it rather than keeping it "just in case" or "to trim later" — dead code rots silently and misleads the next reader into thinking it's load-bearing.
2. **Frontend: `installX({…})` modules; `app.js` is wiring-only.** Feature logic lives in a `public/` module exposing an `installX({…getters,…callbacks})` factory (or a class for a stateful widget). `app.js` only builds `state`/the DOM map, calls each `installX` once, holds the returned handles, and wires `wsRouter` last. Modules read live state through injected getters (`getActiveId: () => state.activeId`) — they never reach into globals. Don't grow `app.js` with feature logic; add a module and wire it.
3. **No god-modules — extract composed collaborators.** When a module takes on a second responsibility, lift it into a collaborator the owner *composes*, keeping the public surface stable via delegation. Cf. `InstanceManager` → `IdleSubscriptionHub` + `OverageResumeController`; `mcp/handlers.ts` → `diffPaging` + `messageReconstruction` + `content` + `textRender`/`readRenderers`; whisper/tts install → the `makeInstallRunner` factory; the convention scopes' catalog → `conventionSelection.ts`'s `createSelectionStore`.
4. **One service layer for REST + MCP — don't reimplement per surface.** Git / worktree / diff / session logic lives once in `src/worktrees.ts` (+ siblings) and is imported by **both** `src/routes.ts` and `src/mcp/handlers.ts` (shared: `isGitRepo`, `mergeWorktreeIntoParent`, `syncWorktree`, `getWorktree`, `getWorktreeMergeStatus`, `buildRebasePrompt`, `removeWorktree`, …). A new git/worktree op goes in the service layer and is called from both surfaces — never duplicated.
5. **Single-source-of-truth catalogs, shipped to the client — never client literals.** Curated catalogs (`modelVersions.ts`, `whisperModels.ts`, `ttsModels.ts`) own the authoritative list + allow-list + policy server-side; the client *fetches* them (`/api/settings/models` → `public/models.js`) instead of hardcoding the canonical set. (`public/models.js` keeps a `DEFAULT_VERSIONS` first-paint fallback — a fallback, not a second source of truth. `tests/models-fallback-drift.test.mjs` is what keeps that fallback honest: it asserts every one of its eight mirrors still equals the server value it mirrors, so a catalog change that forgets the client fails the suite instead of silently showing a stale default until the boot fetch lands.)
6. **Cross-surface magic strings get one owner module.** A canonical string shared across surfaces lives in a single module. Cf. `planApproval.ts` — the approve/reject prompts shared by the UI buttons, the server-side auto-approve, and the MCP `approve_plan`/`reject_plan` tools; `public/userQuestionAnswers.js` — the AskUserQuestion answer formatter shared by the UI question card and the MCP `answer_question` tool (a DOM-free module under `public/` that the server imports directly, avoiding a mirror); `public/wakeCallback.js` — the idle wake-stub marker (`WAKE_CALLBACK_MARKER`/`WAKE_BODY_SEP`) shared by the server (build) and the client (parse/render); `SOFT_INTERRUPT_MARKER` in `parser.ts`; `isTaskNotificationContent` and `isInterruptMarkerContent` in `parser.ts` — the CLI's re-injected `<task-notification>` tag and its post-abort `[Request interrupted by user]` line, both recognized by shape (no marker to inject, since the CLI produces the string) and checked at the same three sites as `SOFT_INTERRUPT_MARKER`. On the client the same rule covers the rate-limit vocabulary: the ordered bucket key list (`RL_BUCKET_KEYS`) and the long-form window label map (`RL_WINDOW_LABEL`) have exactly one home, `public/usage.js`, read by `accountUsage.js`'s fetch merge, `header.js`'s popover rows and `blocks.js`'s `rate_limit_event` lines. The order is load-bearing for both uses (which single window is most immediate, and the popover's row order), so a second list would let the chip and the popover disagree. The terse chip-only `RL_BUCKET_LABEL` stays private to `usage.js` — that long/terse split is deliberate, not drift. Likewise `el` (`dom.js`) and `apiFetch` (`http.js`) are the single owners of DOM construction and the fetch-error idiom.
7. **Test-only exports carry an explicit marker.** An export with no production caller that is kept for its tests opens its doc comment with `// Test-only export: no production caller.` followed by one line of *why it is kept rather than deleted with its tests*. Cf. `hasSessionBackend` (`sessionBackends.ts`), `snapStartToGroupBoundary` (`parser.ts`), `getSubstitutionBackends` (`appSettings.ts`), `isKnownVersion` (`modelVersions.ts`). Reset hooks (`_resetForTest`, `_resetCache`) are a distinct, self-naming category and need no marker. An export with **no** caller at all — production or test — is deleted, not marked.

## Instance lifecycle
```
create → spawning → idle ←─ turn ─→ turn_end ─┐
            ↓        ↓                          ↓
        load-hist  prompt                  exited / crashed
        fails                                   │
                                                ▼ respawn --resume <sid>
                                            (back to spawning)
```

On **resume**: `loadHistory(sessionId)` runs before flipping to `idle` — replays jsonl into UI events and emits a `system/history_replayed` divider. A history longer than the ring cap trims during the replay itself; the evicted prefix stays reachable via `GET /api/instances/:id/events`. On **turn end** or **mode change**: append `{"type":"last-prompt", …}` + `{"type":"permission-mode", …}` lines so `claude --resume`'s interactive picker can discover the session.

**`displayStatus` overlay (additive, not a 6th state).** The diagram above is the real `status` enum — untouched. A backgrounded `Agent` tool call's tool_result resolves immediately (`isAsync:true`), so `turn_end` (→ `idle`) can fire while the CLI's own `system/task_started`/`task_updated` task-tracking is still open for that call. `Instance._activeAgentTasks` (a `Map<task_id, tool_use_id>`) tracks this: incremented on `task_started` **unless** `task_type === 'local_bash'` (backgrounded/promoted Bash — a promoted long-lived command never emits a terminal event and would pin the count forever; unknown `task_type`s still count), decremented on a terminal `task_updated` (`patch.status` one of `completed|failed|cancelled|error` — an unrecognized status is treated as non-terminal on purpose, to avoid flipping back to idle early) or on `task_notification` (belt-and-suspenders). `summary().displayStatus` reads `'running'` instead of `'idle'` while the map is non-empty; every other `status` value passes through unchanged. Reset on (re)spawn. `Instance.activeAgentTaskCount` exposes the live map size. `IdleSubscriptionHub._onTurnEnd` **gates on TWO conditions**: a `turn_end` **defers** the idle wake (the armed wake and its heartbeat both stay armed) while **either** `activeAgentTaskCount > 0` (a subagent is still running) **or** `taskNotificationPending` is set — a `task_notification` fired *during* the turn now ending **and no top-level tool_result followed it**, which per the CLI's queue semantics means the notification is still queued and an unprompted **re-invocation turn** will deliver it. Both cleared, the wake fires — so a wake means "the worker AND all its subagents finished, and no re-invocation turn is still owed." `Instance._taskNotificationPending` (getter `taskNotificationPending`) mirrors the CLI's stdout-invisible message queue by event order: SET in the `task_notification` handler only when `status === 'turn'` (a completion while *idle* re-invokes immediately — that turn is its processing turn); CLEARED by any top-level (`parentToolUseId == null`) `tool_result` event — a sync-delivered task's own held-open result (fast Agent calls, long Bash promoted to a task, e.g. a full test run) or the outer tool round-trip the CLI attaches queued notifications to (batched flush) — by every idle→turn transition in `_setStatus` (the dequeued notification IS the new turn's input), and on (re)spawn. Nested (subagent-forwarded) tool_results never clear it. Every status-gated frontend control still keys off the real `status`; the cosmetic surfaces (sidebar dot, sub-agents strip, header chip) read `displayStatus`.

**Idle task-drain settle (the second wake path).** A background task can finish while its worker is ALREADY idle with **no re-invocation turn ever following** (verified trace: a subagent's nested Monitor completed after the subagent — the stream's last lines were `task_updated` + `task_notification`, no `turn_end` ever re-sampled the gate, and the wake orphaned into an endless heartbeat). `IdleSubscriptionHub._onTaskEvent` runs on every `task_updated`/`task_notification`: when a watched target is fully drained (`status === 'idle'`, `activeAgentTaskCount === 0`, `!taskNotificationPending`, `!idleWindowDirty`) it arms a **settle timer** (`ORCH_IDLE_DRAIN_SETTLE_MS`) recording the target's proc identity and `ring.nextSeq`; `_fireSettle` delivers the wake only if the subscription still exists, the SAME proc is live and still fully drained, and `ring.nextSeq` is **unchanged** — literally zero events since the arming task event. The trap this must not reintroduce is waking ONE TURN EARLY: an idle completion that DOES get a re-invocation turn announces it with CLI-local `system/init` + `system/status` writes within ms of the notification, while the `message_start` that flips `status` to `'turn'` waits on the API (seconds — no settle length can safely outwait it). Re-invocation evidence is therefore caught structurally on both sides of the drain event: **after the arm** by the frozen-seq check (init/status advance the ring before the timer fires → drop, the re-invocation's `turn_end` owns the wake), and **before the arm** by `Instance._idleWindowDirty` (getter `idleWindowDirty`) — SET when any non-task-lifecycle event (`TASK_LIFECYCLE_SUBTYPES` = task_started/updated/notification) is processed while `status === 'idle'`, CLEARED at `turn_end` and on (re)spawn — covering a task that drains *inside* another task's already-opening re-invocation window. Every failed re-check drops the settle silently (the wake and its heartbeat stay armed): the fail direction is always "wake later via turn_end", never "wake early" or "wake twice". The proc pin exists because respawn/rewind reuse the Instance AND its id but mint a new proc and reset the ring (`_wipeForResume`), making cross-run seq comparisons meaningless; history replay can't arm (it runs while `status === 'spawning'` and always trails a seq-advancing `history_replayed` event) and can't corrupt the dirty flag (replay bypasses `_handleStdoutLine`). `_justConsumed` stays turn_end-only — no worker `turn_notification` exists at settle-fire time. Accepted residuals: a CLI stalling longer than the settle between the notification and init writes (consecutive process-local writes, normally sub-ms — the window never scales with API latency) would wake one turn early; non-task noise in an idle window with no turn following leaves only the heartbeat, same as before this path existed.

## Playbooks

Four modules, layered so the policy is pure and the wiring is thin. The wire contract, the tool arguments and the known limitations are in [protocol.md → Playbooks](protocol.md#playbooks); this is the internal shape.

- **`src/playbooks.ts`** — definition catalog (built-in seeds + user overlay through the shared `fragmentCatalog.ts` factory), the load-time validator, and the **pure** policy decision `decide({toolName, args, projection, playbooks, isLive})` → `{ok, patchedArgs, move}` or `{ok:false, code, reason, legalMoves}`. `isLive: (sessionId) => boolean` is a **required** parameter, never defaulted — a default reading the projection would reintroduce the second liveness authority this shape exists to rule out — so every call site is a compile error away from being found. A bad definition is rejected **at load time**, not at spawn time. The governable-tool index resolves through a **memoized dynamic import** of `mcp/tools.ts` specifically so `handlers.ts → playbooks.ts` (which the read tools need) cannot close a cycle; `validatePlaybook` is pure and synchronous, taking that index as a parameter.
- **`src/playbookLedger.ts`** — the append-only JSONL log (`fs.appendFile`, **never** `writeFileAtomic` or a rewritten document — the `archive-store-corruption` failure was a rewritten JSON store wiping itself) and the in-memory **projection** folded from it. One `applyEvent` serves both the boot fold and each live append, so an incrementally-updated projection cannot diverge from one folded from the file. Event kinds: `spawn`, `transition`, `retire`, `refusal`, `enforcement`, `resume`. The projection carries **no liveness bit** — `retire` and `resume` are audit-only, folding to no state beyond the event itself — so `WorkerState` has nothing for a second reader to consult by mistake. `resume` still un-retires a worker **in place** in the sense that matters (nothing else about it changes): it is a distinct kind rather than a second `spawn` precisely because the `spawn` arm *replaces* the worker's state, which would reset `stageHistory` and empty `provenance` (see [protocol.md → Resuming a playbook-tracked worker](protocol.md#resuming-a-playbook-tracked-worker)). Run membership is **derived** — the connected component over `provenance` edges ∪ same-worker transitions, via union-find — so there are no run ids and no external entity to keep in sync. `stageHistory` is what makes a `needs` entry's provenance half answerable; its `liveness` half is answered from `InstanceManager.isSessionLive` (`src/instances.ts`), THE single liveness authority — `liveSessionsInStage(p, anchor, stage, isLive)` takes that oracle as a required parameter rather than reading a fold. The store path resolves through a **lazy** function so a `PROJECTS_ROOT` override is honoured per call.
- **`src/mcp/playbookGate.ts`** — the single enforcement point, composed by `buildMcpRouter` so `mcp/server.ts` stays transport. Owns the conductor predicate lookup, the enforcement-level read, `decide()`, the refusal payload, and **every** ledger write — exactly TWO writers: the `tools/call` checkpoint's commits, and the manager's `status` stream (below). A `refusal` row records every worker the call named — `sessionId`, plus `forwardSessionId` when the call carried a forward — since the `code` alone says which side was refused (one `subjects(args)` helper, shared with the `playbook_warn` payload). Under `warn` it also pushes a UI-only `system`/`playbook_warn` event onto the **calling conductor** (`_emitUi`, strictly after the append) — the ledger has no reader, so without it the mode that exists to warn a human warns nobody; the conductor *agent* is unaffected, since `_emitUi` never reaches the CLI. Appends are serialized through one chain (`append` reads the seq then awaits the write) and the ledger path is **pinned on first resolution**, because some appends are fire-and-forget and a deferred write must not land in a different store than the one it was decided against. The stream writer carries the two things no `tools/call` can report: `retire` when a subprocess exits (an audit record — capacity no longer reads it) and `enforcement` when the level changes — watching the stream rather than each toggle's call site means a spawn-time value, the WebSocket flip and a restart restore are all recorded without any of them knowing the ledger exists. The gate also exposes `isLive(sessionId) => instances.isSessionLive(sessionId)`, the SAME oracle every `decide()` call here uses, so a read surface (`playbook_state`, `describe_playbook`'s dry-run) answers from the identical source rather than re-deriving its own. A host reboot (or an orchestrator crash) needs no boot-time repair any more: capacity and `needs.liveness` both read `isSessionLive` directly, so a session this process's registry never heard of simply holds no slot — see [protocol.md → Playbooks](protocol.md#playbooks).
- **`src/playbookConvention.ts`** — the pure renderer `renderPlaybookConvention(pb)` behind the preferred-playbook convention (contract in [protocol.md → Playbooks](protocol.md#playbooks)). Pure and store-free so it is unit-testable against a definition object; composed by `conductorConventions.ts` (`getDefaultPlaybookSelection`/`setDefaultPlaybook`/`resolveDefaultPlaybookId`/`defaultPlaybookConvention`), which resolves the selected id through `loadPlaybooks()` rather than a second discovery layer. Authored `description` text is passed through **verbatim** — the definition is its one home, and a renderer that reflowed or truncated it would become a second.
- **`src/mcp/handlers.ts`** — the three read tools, reading the gate's one projection through `readProjection()`/`readHistory()` rather than folding a second. Both load on demand, and that load is read-only, which is what lets a read tool answer on an install with no ledger yet without materialising the file.

**Definitions are the authority on what the graph is; the projection is the authority on where workers are; the instance field is the authority on the enforcement level.** The persisted `defaultPlaybookEnforcement` (`conductorConventions.ts`) supplies only the level a conductor is **born** at, applied in `Manager._doCreate` before `launch()`; nothing writes back to it, so the runtime authority is never split. `projection.enforcement` is written for the audit trail and deliberately has **no reader** — `playbook_state` reports the calling conductor's live mode off its instance instead, which also means nothing can surface a non-conductor as a governed actor.

## Testing
All tests via `node tests/run.mjs` (programmatic node:test runner — Termux's glibc-runner wrapper hoists leading `--flags` into `NODE_OPTIONS` and refuses `--test`).

**TypeScript toolchain.** Server-side `src/*.ts` runs directly under Node 24's native type stripping — no emit, no `dist/`, no bundler — so converted files are limited to **erasable syntax** (`tsconfig.json`: `strict`, `erasableSyntaxOnly`, `verbatimModuleSyntax`, `allowImportingTsExtensions`, NodeNext ESM). Because stripping never type-checks, `npm run typecheck` (`tsc --noEmit`) is an **enforced gate**, not an optional script: it runs as `pretest`, before every `npm test` (including the mutation harness's `npm test` baseline/test commands). Converting a module renames it `.js` → `.ts` and every importer's specifier with it (Node resolves import specifiers literally — no extension fallback); a still-`.js` sibling is imported via a minimal hand-written `.d.ts` that declares only what the `.ts` consumer uses (`src/projects.d.ts` today). Round 1 converted `modelVersions`, `usageWindowDomains`, `storeLock`, `sessionBackends`.

Test **files run in parallel** (node:test `isolation:'process'` — one child process per file). The suite is isolation-safe: `bootServer` binds an ephemeral port (`listen(0)`) and `mkdtemp`s a unique home per server, so files never contend over ports or paths. Concurrency defaults to a cores-derived cap (see `resolveConcurrency` in `tests/run.mjs`). Override with `TEST_CONCURRENCY=<n>` (`1` = fully serial). Measured ~79 s serial → ~29 s at the default on an **8-core** device; on a **16-core** box, where the cap and the per-core term bind simultaneously, 67.3 s at the old cap of 4 → 37.7 s at the default. The 8-core figure is unaffected by that cap change — the expression yields 4 either way. Past ~37 s the suite is dominated by its slowest deadline-bound file, which is `tests/idle-wake-ownership.test.mjs` (**33.0 s** on a quiet 16-core box at `a23fbbb`, 2026-08-24, in a ~38.5 s suite) — card 2026-0211 owns that figure. `tests/hang-guard.test.mjs` used to be a near-second at 30.0 s; card 2026-0198 split it into five `tests/hang-guard-*.test.mjs` files, taking its slowest to **8.5 s** (see "Regression suite" below). Only the **head** of the verdict line's slowest-5 is stable: the 3rd–5th places (then `header-playbook-enforcement` 10.4 s, `server-restart` 9.2 s, `hang-guard-file-kill` 8.5 s) sit within ~2 s of several other files and re-order under ambient load, where `worktree-feature-branch`/`worktrees` displace them. `FILE_KILL_MS` in `tests/hangGuardConfig.mjs` owns the measurement and the trend.

**Port ownership.** Picking a port by binding it and freeing it leaves a window in which another file's `bootServer()` `listen(0)` is handed the same port — after which an HTTP readiness probe is answered by that stranger and a destructive `POST /api/admin/restart` kills *another test file's process* mid-run. Two rules:

1. **Hold the socket when you can.** `tests/eaddrinuse-retry.test.mjs` and `tests/plugins-supervisor.test.mjs` bind `listen(0)` and never release until the test says so, which also makes the collision deterministic rather than lucky. **`tests/server-restart.test.mjs` deliberately does not** — it keeps bind-then-free `getFreePort()`. Card **2026-0157** proposed converting it to hold-then-release; that was **measured and declined**, not deferred (16-core host, idle; 5 instrumented runs + forced-contention runs):
   - **Window A**, `getFreePort()` resolve → the child's banner: **241–278 ms** (median 268; spawn lag 0–2 ms, the rest is boot). Hold-then-release does **not** close it — the gate is the child's first `EADDRINUSE on port` stderr line, which `listenWithRetry` (`server.ts`) writes at the *start* of its 100 ms sleep, leaving a measured **111–114 ms** residual.
   - **Window B**, `scheduleRestart`'s `server.close()` (`src/restart.ts`, before the replacement spawns) → the replacement's banner: **254 ms**, and it is not test-side at all — a competing bind took the port on its **first attempt, 2 ms after** the parent's `restart: spawned replacement pid=` log. No test change narrows it. Tracked separately.
   - So the conversion narrows **window A — the larger of the two (median 268 ms vs B's 254) — by ~2.4×** (268 → 111–114 ms). **Two different ratios, do not conflate them:** the per-file aggregate falls only **~1.43×** (2 tests × each window: 536 + 508 = ~1044 ms → 224 + 508 = ~732 ms), because window B is untouched and carries 508 of the remaining 732 ms. That is **~0.022% → ~0.016% collision per suite run** (~261 ephemeral binds per run over ~30–60 s against 28232 free ports, `/proc/sys/net/ipv4/ip_local_port_range`) — that denominator is an **upper bound**: leaked fixture listeners held 12 of those ports on the measuring box (card 2026-0226). It does not move the rate. The kernel never hands out a port already in `LISTEN`, so an orphan holding *P* removes a candidate rather than causing an `EADDRINUSE`; 12 of 28232 shrinks the pool by 0.042%. The reason to decline is not that A is the smaller window — it is the larger — but that a production window **nearly as large** survives untouchable from a test while the machinery reads as "window closed". Declined on those numbers; do not re-open without new ones.
   - What makes ~0.022% acceptable is rule 2: forced contention on either window ends at `waitForBanner` rejecting (`child never printed listening banner #<n> for port <p>`), and in both forced runs the stranger received **zero** requests. The cost of a collision is this file timing out, never another file's process.
   - Dead alternative: spawning with `PORT=0` and reading the bound port back from the banner would close window A entirely, but `spawnReplacementAndExit` passes `env: process.env` (`src/restart.ts`), so the replacement inherits `PORT=0`, binds a *different* port, and destroys the same-port invariant.
2. **Never trust the port as identity.** Readiness on a spawned `server.ts` waits for that child's own stdout banner `code-conductor listening on http://<host>:<port>`, printed from the address it actually *bound* — never an HTTP probe a stranger answers just as happily. The rule lives once in **`tests/serverBanner.mjs`** (`waitForBanner(captured, port, {nth})`; the restart replacement inherits the same stdout, so its banner is occurrence #2) and is imported by every test that waits on a `server.ts` child. Additionally, never send a destructive request to a port whose owner you have not established: `server-restart.test.mjs` asserts the port is still `EADDRINUSE` immediately before each restart POST.

`tests/restart-port-identity.test.mjs` is the regression guard — a decoy `node:http` server answers the old probe while the real child cannot bind, and the test asserts that `waitForBanner` (the same import the restart tests use, which is what makes the guard cover them) rejects rather than reporting ready.

**Store isolation (`tests/safeStoreRoot.mjs`).** The sidecar stores resolve their on-disk root from `PROJECTS_ROOT`, falling back to a source-relative default (`src/../..`) that IS the real production `.code-conductor` when it's unset — so a test touching a store with `PROJECTS_ROOT` unset corrupts the live store. `run.mjs` pins the whole run to a throwaway temp root (`createSafeRoot()`) before any file forks — every child inherits it — and asserts via `assertStoreIsolated(orchStoreRoot())` that the store never resolves into the real workspace (aborting the run if it would). `bootServer` teardown restores `PROJECTS_ROOT`/`CLAUDE_PROJECTS_ROOT` to that safe root, never to unset, so out-of-window writes stay in the temp dir. `tests/store-isolation.test.mjs` is the regression guard.

**harness/playwright depth.** `harness/playwright/boot-orch.mjs`'s orchestrator cwd is derived from its own directory depth; `4c1a3da` added a level and left it one short, breaking every `bootOrch()` caller with an opaque `child server exited before binding`. The constants now live in `harness/playwright/paths.mjs` — node builtins only, so it imports cleanly without the sibling `code-playwright` clone — and `tests/harness-playwright-paths.test.mjs` is the ungated regression guard. `boot-orch.mjs` consumes the same exports behind a fail-loud `existsSync` precondition.

**Forcing a fire-and-forget sidecar write to land late.** A store write fired without `await` (e.g. `markSessionBackend` at `Instance.spawn()`) can race a test's post-spawn read. Sample-then-assert is flaky by construction; the deterministic pattern (`tests/backend-spawn.test.mjs`, describe `'a sidecar write that lands after the spawn response'`) pre-creates `<dataFile>.lock` with a live PID (this test process's own) *before* triggering the write: `storeLock.ts` reclaims a held lock only when the owner PID is dead, so the write provably cannot have landed while the lock stands — a hard mutual-exclusion barrier, not a timing delay. Assert the miss first (proves the forcing engaged), release the lock, then read through a `waitFor`-based helper (`settledSessionBackend` in `tests/helpers.mjs`) rather than sampling again.

**Never assert across a machine-speed window.** `SPAWN_SETTLE_MS = 400` (`src/plugins/supervisor.ts`) bounds how fast a crash must be **observed**, not how fast a child boots — the latter is a property of the host. Card **2026-0219**: `tests/plugins-supervisor.test.mjs`'s settle-window test squatted a port and required a real `bash -lc 'node server.mjs'` to fail `listen()` and be reaped inside that window. Measured spawn→exit for that child: **p50 42 ms idle (max 46, 0/12 over 400 ms)** vs **p50 ≈ 420 ms at load1 ≈ 75 (min 219, max 813)** — so it went red **7/9 runs at load1 73.8–77.5** and never once idle. The rule: make each branch reachable **only** by construction, never by margin.
- *Inside the window* → the `_spawn` seam (`createSupervisor`). A fake child emitting its stderr + `exit` on `process.nextTick` is settled before any timer can run, so `raceSettle`'s first 20 ms tick always observes it — true on an arbitrarily starved box. Never a real process.
- *Outside the window* → `_settleMs: 0`, which makes "the window expired first" the only reachable branch, again with no competing clock. That test also cross-checks node's **actual** bind-failure line against the string the fakes emit, so the fixture cannot drift out of sync with reality.
- The **event-driven retry** (retry on the child's exit event instead of a window) was **measured and declined**, not deferred — same treatment as card 2026-0157 above. The retry heuristic is anti-correlated with its own risk: `allocatePort()`'s TOCTOU window widens under exactly the load that stops a 400 ms window from catching the resulting crash. But retrying after `start()` returned means rewriting a record `registry.ts` has already persisted via `store.recordStart(id, rec)`, i.e. a record-rewrite path for a ~0.02 %-class event (the collision rate computed under "Port ownership" above). Do not re-open without new numbers.
- The **readiness-cancellation** half of that card is load-independent and pinned by a pair: a squatter that counts accepts and destroys each socket (so a probe cycle is countable and cannot leak), one test asserting accepts stop growing once the child is dead (`<= base + 1`, the one probe that can be in flight) and its **control** asserting they *do* grow over the same shared `PROBE_WINDOW` while the child lives (`> base + 1`). The two bounds are exact complements, so neither can pass vacuously.

**Second worked example of the same rule — a RATIO between two wall figures (card 2026-0222).** `tests/summary-attribution.test.mjs` compared per-file durations as `fast * 3 < medium` and `medium * 1.25 < slow`. A difference cancels the per-file spawn cost `C` to first order; a **ratio multiplies it**. `fast * 3 < medium` reduces to an absolute cap of `C < 600 ms` — not a spread tolerance — and `C` reaches ~770 ms at 72-way (above), so it went red **10/24 (42 %) at load1 72.8–74.4** on a completely correct reporter, while passing **30/30 at 24-way**. The construction that replaced it: **chain the fixtures' completions through a rendezvous** (`tests/fixtures/attribution/chain.mjs` — each waits for its predecessor's **process to exit**, spends its own designed increment, then publishes its own pid) and assert **differences against those increments** (`medium - fast >= 1200`, `slow - medium >= 900`, `sub - fast >= 550`). Because `reported_a - reported_b = (done_a - done_b) + (dequeue_b - dequeue_a)` and both terms are non-negative when `a` is listed before `b` in argv, every bound is a lower bound **no child-side cost** can violate. **State that claim precisely** — `done` is stamped in the runner's `test:complete` *handler*, so the identity also carries a parent-side delivery term, and one contiguous stall of the parent's event loop spanning both completions compresses the difference toward zero. The stall must be roughly the size of the increment it attacks (~600 / 850 / 1150 ms for the 550 / 900 / 1200 bounds); measured buffers over the floors are **+12…+53 ms quiet, +46…+539 ms at 72-way**. That branch is still margin-reachable and the test header says so — **the smallest increment, 550 ms, is what sets the breaking stall size, so do not shrink it without re-measuring.** It fails loud (red), never silently green, and the exposure is far smaller than the multiplied-`C` term it replaced. Two things are load-bearing and commented at their call sites: `TEST_CONCURRENCY=4` (fewer slots than chained fixtures deadlocks the chain, loudly) and the **descending** argv order `slow, medium, subsecond, fast`. Resolution claims get the same treatment — a `(0, 1000)` band on a difference was measured *outside* its own range (gap 1053 ms) on a correct reporter and is now a load-free lattice residue, `some(ms => ms % 100 !== 0)`. **Gate a rendezvous on the predecessor's process EXIT, not on its marker appearing** — a marker written at the end of a test body leaves that child's whole teardown+exit cost inside the difference, subtracting: measured at 72-way, marker-gating broke all three bounds (minima 1200/900/550 → **1050 / 811 / 460**, standalone red **13/24**, i.e. worse than the ratio it replaced), and the deficits tracked the *predecessor's* own reported figure monotonically. Exit-gating removes that term and makes the successor's exit cost a positive buffer: **24/24 green at load1 70.9–75.8**, minima **1312 / 953 / 596**.

**Third worked example — a fixed PRE-SIGNAL DELAY (card 2026-0228).** `tests/hang-guard-sweep.test.mjs`'s two interrupt legs (`SIGTERM …exits 143`, `SIGINT …exits 130`, landed by card 2026-0226) signalled the nested runner a fixed **1200 ms** after spawn (`runGuard(…, { signalAfterMs: 1200, signal })`) and then read the fixture's `silent-orphan: holder pid=<n>` line back out of the captured stream. That is a margin claim about a **host property** — the case's own header said the delay was "well clear of process start-up on a starved box" — because the whole nested boot chain (runner boot + `node:test` dispatch + fixture boot + two `--import` preloads + `spawn`) has to fit inside it. Measured spawn→marker: **759 / 952 / 1585 ms** (min/med/max, n=8) **at 72-way** vs **87–115 ms idle** — ~13× oversubscribed under load, ~10× under-subscribed quiet. Standalone `node tests/run.mjs tests/hang-guard-sweep.test.mjs` ×14 at load1 75.1–76.6 / load5 53.0–63.5 went red **6/14 runs (43 %) / 8/28 legs (29 %)** (SIGINT 5, SIGTERM 3), always on `the fixture never printed its holder pid` and never on a product assertion: on every red the runner still printed its interrupt banner, swept under the correct trigger label, and exited 130/143 with `signal === null`. **Test defect against a correct product — no `src/` and no `tests/run.mjs` change.**

The construction that replaced it: **`signalWhen`, a rendezvous on the fixture's own marker** (`runGuard`, `tests/hangGuardCase.mjs`) — one signal, sent synchronously in the same tick the captured stream first matches the regex, rather than after a duration. Five preconditions are *eliminated*, not widened. **E1** *the marker precedes the signal* (the assertion that failed): was a 1200 ms margin, now causal — the signal exists only because the line arrived. **E2** *the holder is alive when the sweep runs*: structural — the fixture writes the pid only after `spawn()` returned. **E3** *run.mjs's SIGINT/SIGTERM handlers are armed*: structural — registered at `tests/run.mjs:333`, before `run()` at `:364`, and only an already-dispatched file can emit the marker. **E4** *the holder-is-actually-dead poll executes*: it was silently skipped on every flake (`holderPidFrom` aborted first), so **coverage strictly increases**. **E5** *no armed timer outlives the case*: no timer exists — `bail` is now `runGuard`'s only one. `CC_TEST_DWELL_MS` stays at **4000**; nothing was widened. The firing pattern and the read-back are one `HOLDER_LINE` const in the test file (no `g` flag — a global regex carries `lastIndex` across `.test()` calls), so the signal cannot fire on a line the assertion then refuses.

**Residual (R1), stated rather than hidden:** the interrupt must still land mid-run, so one contiguous **>~4000 ms** stall of the *outer* test process's event loop — between the pipe becoming readable and the `data` handler running — would miss it. Measured fixture-write→parent-observation latency at 72-way: **1–52 ms (n≈88, median ~12)**, a ~330× buffer on a term that was never the failing one, and the failure direction is a loud red (`code=1`, `trigger: run end`), never a silent green. **No fallback timer or absolute cap was added, deliberately:** "wait N ms then signal anyway" *is* `signalAfterMs` renamed; the two bounds are different objects (1200 ms was a **lower** bound the green path had to clear, while a cap is an **upper** bound whose exceedance reds at *any* value, since the assertions fail either way); and the run is already bounded three times over — the fixture's 4000 ms dwell, then `CC_TEST_RUN_CAP_MS` 12 000, then `hardTimeoutMs` 20 000. **Negative control** (point `HOLDER_LINE` at a pattern the fixture never prints): **3/3 red in 4.9–5.6 s** on `no-holder-pid` plus the exit-code assertion, with **no hang** — the construct holds the authority rather than relocating it. Prototype at 72-way with all five leg assertions applied: **SIGTERM 0/20, SIGINT 0/20 red**, against 6/20 and 10/28 for the delay at the same load. Dead alternative: an **open-ended dwell** (`await new Promise(() => {})`, so only the interrupt can end the run) removes R1 and measured **0/8 red**, declined because it slows the *broken*-path failure from ~5 s to `FILE_KILL` 8000 ms and adds an env knob for no measured gain.

**This does not contradict 2026-0222's "gate a rendezvous on the predecessor's process EXIT, not on its marker appearing"** — that rule is scoped to **duration differences**, where marker-gating leaves the predecessor's teardown+exit cost inside the quantity under assertion. These legs assert no duration at all: only ordering, an exit status, and a liveness fact. And the rendezvous target here must be **alive** when the signal lands, so exit-gating would guarantee the interrupt arrived after the run was already over. Marker-gating is not the weaker choice here, it is the only admissible one.

**Negative assertions ("X did not happen") — barrier + `settle()`, never a fixed sleep.** `await new Promise(r => setTimeout(r, 200))` before asserting an absence is both flaky (too short on a starved box) and weak (vacuous on a fast one, because nothing forced the thing you are asserting the absence of to have had its chance). Instead: `waitFor` on an observable that is **causally downstream of the decision under test**, then `settle(turns = 3)` from `tests/helpers.mjs` (drains queued micro/macrotasks via `setImmediate`; load-independent). `settle()` is **not** a barrier on its own — it cannot wait for work that has not been scheduled yet, so a `settle()` with no barrier in front of it is exactly as vacuous as the sleep it replaced. Worked examples across `tests/idle-wake-ownership.test.mjs`: the barrier is the target's turn_end handler having run (`waitFor(() => target.status === 'idle')`), because that same handler both sets the status **and** makes the fire-or-defer decision — so a wrong delivery is already queued and `settle()` puts it in the ring where the assertion sees it.

**The overage usage seams default to a non-network tripwire, not the live fetcher (card 2026-0208).** `OverageResumeController.fetchUsage` and `UsageOverageMonitor.fetchUsage` default in production to the real `getAccountUsage`, so a fire-path test that forgets to inject makes a live `api.anthropic.com` request bounded by a 10 000 ms `AbortSignal` (`src/accountUsage.ts`) — racing the overage tests' own 10 000 ms `waitFor` budget, which is what made that card. So `tests/overage-action.test.mjs`, `tests/overage-turn-guard.test.mjs` and `tests/overage-backend-exempt.test.mjs` install `installUsageSeamTripwire(instances)` in `beforeEach` (both seams → one counting stub returning `null`, the existing "can't confirm" branch) and call `assertUsageSeamInjected(seam)` in `afterEach`, after `shutdown()`/`rmrf()`. Both live in **`tests/overageUsageSeam.mjs`**. A **throw** inside the stub would not work as the guard — both call sites swallow it into `usage = null` — hence count-then-assert. `null` rather than an under-the-bar payload is deliberate: an un-injected test must not silently *work*. When the assertion fires, inject what that test actually means (`setResumeUsage(UNDER)`/`(OVER)`, or `async () => null`); never relax the assertion. **Each of the three files also carries its own `HARNESS (2026-0208)` test calling `assertUsageSeamsInstalled(instances, seam)`** — the wiring pin has to live in the same file as the wiring, because each `beforeEach` is independently editable and a sibling's assertion cannot see this one reverted (mutation-proven: without it, reverting either of the other two files' `beforeEach` to the live default survives the whole suite green). That helper compares each seam against `state.fn` by **identity before invoking anything** — if the tripwire is absent the seam may be the real `getAccountUsage`, and calling it to find out would make the request the guard exists to prevent. How an un-injected test then fails depends on its `resetsAt`, because `_reschedule` parks at `max(resetsAt, now + recheck)`: a **future** `resetsAt` (these files' usual `nowSec() + 3600`) parks ~1 h out, so the fail-open counter stalls at 1 and the body burns its full 10 s `waitFor`; a **past** `resetsAt` (the fail-open tests' `nowSec() - 100`, chosen so the counter *can* climb) fails open and lets the body pass, leaving the call count as the only detector. Both regimes are offline and deterministic.

**A negative assertion needs a positive control, or it decays silently.** "No stub arrived" proves a timer was cleared only if a stub *would otherwise* have arrived. Pair the negative with an identical test that omits the cancelling step and asserts the event **does** land in the same window, and single-source the window constants so the pair cannot drift (`HEARTBEAT_MS` / the derived `OBSERVE_MS` in `tests/idle-wake-ownership.test.mjs`). Verified by mutation: with the production heartbeat patched never to fire, the negative goes **vacuously green** and only the control goes red. Where an assertion genuinely requires a real timer to fire, a wall-clock window is unavoidable without a fake clock (an `src/` change) — widen it for margin, keep the control, and if it still flakes change the assertion rather than the number.

**DOM-vs-null assertions (`tests/dom-assert.mjs`).** Never compare a DOM node against `null`/`undefined` with `assert.equal`/`strictEqual`/`deepEqual` — use `assertNull(node, label)` / `assertUndefined(node, label)`. On failure node serializes `err.actual` across the per-file child-process boundary, walking a live happy-dom element's circular `ownerDocument`/`Window` graph: the file stalls **33–120s** and then aborts, so **every later test in it silently never runs**. Supplying a message makes it *worse*, not better (3-arg measured slower than 2-arg at the same site — `err.actual` crosses the boundary regardless), so the rule is unconditional on arity. `deepStrictEqual` never terminates at all: it grows unboundedly until the OS kills it (`exit 137` on a smaller device; **27 GB RSS** on a 30 GB host, killed by hand at ~2 min before the kernel acted), and `--max-old-space-size` does **not** bound it — do not raise that flag to chase the symptom. Reproduce **only** under a hard address-space cap, which does bound it because it cuts below V8's own accounting: `( ulimit -v 2000000; node repro.mjs )` aborts in **0.9s** with `exit 134` (SIGABRT) and never passes 2 GB. Without it the process consumes the whole machine, not just its own test run. The helpers compare without handing the node to `assert` and throw an `AssertionError({message, stackStartFn})` carrying only a short `<tag#id.class>` summary, leaving `actual`/`expected` `undefined` — that is what keeps the cycle off the wire. Always pass a `label` naming the element and its source (`'copy button must not be inside <pre>'`): nothing enforces it (a missing one just yields `undefined — expected null, found …`), but it is the whole failure message.

**Enforcing the DOM-vs-null rule — two guards, non-overlapping ownership.** The 2026-0150 sweep fixed ~50 occurrences but nothing stopped re-accumulation, and only *failing* assertions stall, so a green suite hides the pattern. Both guards are needed; each module's header says why the other cannot be deleted as redundant.

- **`tests/dom-assert-scan.mjs` (+ `tests/dom-assert-guard.test.mjs`) OWNS the invariant** *no equal-family assertion in `tests/` is written against a DOM-valued expression.* It is the only guard that fails at authoring time on a site that currently **passes** — a latent site is invisible at runtime, which is exactly how the sweep's occurrences accumulated.
- **`tests/dom-assert-tripwire.mjs` GUARDS THE PATH, for one shape only:** *a DOM node compared against `null`/`undefined` by a positive equal-family assertion never reaches assert's serializer.* Preloaded into every per-file child via the `execArgv: ['--import', …]` option on `run({…})` in `tests/run.mjs`; it wraps only the positive family (`equal`/`strictEqual`/`deepEqual`/`deepStrictEqual` — `not*` can only fail when the operand is already nullish) and throws an `AssertionError` carrying just the `<tag#id.class>` summary. It covers DOM-ness the scan is structurally blind to. **Not covered, and still stalling 33–120 s:** a node compared against a non-nullish value (`assert.equal(node, 5)`, `assert.equal(el.parentElement, otherNode)`) and a node nested inside a compared structure. Tracked as card **2026-0163**; do not widen the tripwire, because intercepting any node operand breaks legitimate node-vs-node assertions that currently pass.

The shared predicate `isDomNode` and the `describeFound` formatter live in **`tests/domNode.mjs`, which must have ZERO imports**: `dom-assert.mjs` imports `node:assert/strict`, and instantiating assert's ESM namespace during the preload is what creates the hole below.

**The scan is comment-stripped and paren-balanced, not a line regex.** A line regex both over-matches prose (`tests/header-playbook-enforcement.test.mjs:165-169` names `assert.equal(node, null)` in English) and misses multi-line-formatted calls (`tests/notifications.test.mjs:200,208,213`). `stripNonCode` blanks comments, string bodies, template *text* (`${…}` stays live) and regex bodies; **line numbers stay valid because newlines are preserved**, not because the output is the same length. The argument splitter then walks a `()[]{}` stack. **No JS parser is available** — `typescript@7.0.2` is the Go-native `tsgo` shim (exports only `version`/`versionMajorMinor`), there is no acorn/babel/espree, and `CONVENTIONS.md` forbids adding one.

**Scan direction, and why there is no allow-list.** Enumerating every legitimate primitive-vs-null comparison in `tests/` is intractable — they take too many arbitrary shapes and share no primitive signal. The scanner instead keys on DOM-*producing* signals in **tail position** — so `root.querySelector('a').length` correctly does not match. Receiver scoping on the `DOC_PROPS` and `PICKS` signal sets is load-bearing, not decoration: an unscoped `.body` produced the only false positives measured (5, all HTTP response bodies), and an unscoped `.find` conflates `[...root.querySelectorAll('.x')].find(…)` with `list.body.find(…)`. There is deliberately **no escape hatch**: a genuine future false positive is fixed by narrowing a signal constant in one place, never by an inline ignore comment.

**Measured recall: 46 of the 50 pre-sweep sites, at zero false positives across every legitimate primitive-vs-null comparison in `tests/`** (unchanged after widening `isDocumentReceiver` to accept a `.document` tail and adding the destructuring arm). Exact counts drift as unrelated cards add nullish assertions, so they are not restated here — `tests/dom-assert-scan.mjs`'s header carries a MEASUREMENT RECORD with the numbers, the sha and the date; re-derive with `scanTestsDir('tests')`. The 4 residual occurrences are 3 distinct expressions — `conv.emptyNode`, `main.leadingAssistantWrap` (×2), `batch.leadingWrap` — whose DOM-ness lives in `public/` return values and is absent from the test syntax entirely. Two further shapes are **waived** known misses, named in the scanner's false-negative note: redundant parens around a whole call, and declare-empty-then-assign. **None of this is an oversight and must not be "fixed" with a name list**; the tripwire bounds them at runtime.

**The tripwire must use `createRequire(import.meta.url)('node:assert')`, never a static ESM import.** Measured: with `import assert from 'node:assert'` in the preload, a test file's `import { strictEqual } from 'node:assert'` **bypasses the patch** — the ESM namespace snapshot of the CJS named exports is taken when the preload instantiates it, before the patch lands. `createRequire` leaves the namespace uninstantiated, and all four styles (both modules × named/default) end up patched. Patch `assertObj.strict[k]` as well (`assert.strict` is `node:assert/strict`'s default export). Forward `arguments` (`orig.apply(this, arguments)`) — named parameters would turn `assert.equal(1)` into `assert.equal(1, undefined)` and lose `ERR_MISSING_ARGS`. If the preload itself throws, the child exits 1 before the body runs and `run.mjs`'s `test:fail` counter increments; it cannot silently no-op.

`tests/dom-assert-guard.test.mjs` holds T1–T11, each titled with the invariant it pins: tree-is-clean (T1), induced-violation recall across seven shapes (T2), comment/string immunity incl. the real prose comment (T3), `not*` never flagged (T4), historical-recall floor (T5), tripwire behaviour parity via two child processes over a 12-case table (T6), tripwire installed-and-fires via a node-*ish* plain object — never a live node, so an absent tripwire fails instantly instead of stalling (T7), `dom-assert.mjs` reads the shared predicate (T8), the predicate accepts a real happy-dom node (T9), all four import styles patched (T10), throwing-preload fails loudly (T11). **Cost:** scan ≈300 ms including its extra `node:test` child (~180 ms of blanking + matching over all of `tests/`); the tripwire's per-child cost is below the ±7 ms run-to-run noise floor; T6/T10/T11 add 4 child spawns ≈200 ms.

**ClaudeLauncher seam (in-process fake by default).** `Instance` never calls `child_process.spawn` directly — it spawns through an injected `ClaudeLauncher.launch({command,args,cwd,env})` (`src/claudeLauncher.ts`), threaded `createServer({claudeLauncher})` → `new InstanceManager({claudeLauncher})` → `Instance`. Production default is `RealClaudeLauncher` (a raw `child_process.spawn` — behavior byte-for-byte unchanged). `src/claudeLauncher.ts` also owns the two pure launch-resolution primitives — `resolveClaudeBin()` (splits `CLAUDE_BIN`, default `claude`, into `{command,prefixArgs}`; test injection via `CLAUDE_BIN="node fake.mjs"`) and `resolveBackendLaunch(backendRecord, model, claudeBin)` — so one-shot spawners that need no `Instance` (`health.ts`'s boot probe, `summarize.ts`'s summary generation, `claudeShellEnv.ts`'s bundle-gen) can import just these without pulling in the 2000+-line `instances.ts`. **Backend-agnostic spawn:** `resolveBackendLaunch` computes only command + prefix (plus the backend's `env`) from the **backend record**; every caller then appends the same claude args (including `--model <model>`) uniformly. A blank `template` returns the resolved claude bin's `{command,prefixArgs}` unchanged; otherwise the template is whitespace-split with `{model}` substituted **inside each token** (so `--model={model}` works too), token 0 becoming the command and the rest the prefix — e.g. the built-in `ollama` row yields `['launch','claude','--model',<model>,'--yes','--']` (the model also rides in the forwarded `--model` — a harmless no-op duplicate). Because templates are DATA, there is no per-command env shim: a test pointing a backend at a fake binary just registers a row whose template names it. The helper owns the **null-model invariant** — it throws whenever the template is non-blank and no model resolved (unconditional on the template shape; see the create-time guard below), rather than emit `--model undefined` — so `Instance.spawn()` wraps the call in a try/catch only to add its own `_setStatus('crashed')` side effect before rethrowing. A backend needing a non-default host sets it as an `env` pair on its registry row (e.g. `OLLAMA_HOST`) rather than through any dedicated plumbing. Only `model` + `backend` thread `create()→_doCreate→Instance ctor→spawn()`; both appear in `summary()` (so the resume manifest carries them) and survive an in-place `/clear` renewal. On resume, `backend` is recovered from the `session-backends.js` marker; `model` is recovered from that same marker's tagged value for substitution-backend sessions (the jsonl `message.model` is bare — tag dropped by the inner CLI — so a jsonl-only recovery would relaunch the unpullable tagless name), falling back to the jsonl (`readLastSessionModel`) for Claude sessions and legacy model-unknown entries. There is **no** spawn-time reachability preflight — a bad backend or model fails at launch, and a subprocess on a substitution backend that dies on its own emits a `system/launch_failed` event with captured stderr (`_handleExit`, gated by a `_killing` flag so a commanded kill isn't mislabeled). That event is therefore the only failure signal for a misconfigured backend. Two create-time guards still fire before any spawn: `422 BACKEND_MODEL_MISSING` when a substitution backend has no resolvable model (unconditional on the template shape — the model also rides in the forwarded claude args and drives the context-window env, so a template that omits `{model}` is no exception), and `422 BACKEND_GONE` when the named backend isn't in the registry, whether it came in explicitly or from the session sidecar. `Instance.spawn()` re-checks the record and refuses a null one, so a row removed under a live instance crashes it visibly instead of falling into resolveBackendLaunch's identity branch and launching the real `claude` with a foreign model id. A live "Change model" (`Instance.setModel(model, backend)`) is **blocked** (`409 BACKEND_LOCKED`) whenever either side is a non-`claude` backend, including substitution↔substitution (the running endpoint is fixed at launch), with a "kill and respawn" message; only Claude↔Claude live switches proceed. **`bootServer()` defaults to `InProcessClaudeLauncher`** (`tests/inProcessLauncher.mjs`): the fake-claude engine runs on the event loop against in-memory `PassThrough` streams — **zero OS subprocesses per instance**. This is the forget-proof default (an Android phantom-process-killer defense: the app UID is killed above ~32 processes), so a normally-written test forks nothing. The in-process handle is a `FakeChildProcess` (EventEmitter + 3 PassThrough + `pid=null`); it defers engine start to `setImmediate`, gates `'exit'` on the readable-side `'end'` of stdout/stderr (so a trailing `turn_end` is never delivered after `'exit'`), and maps `kill('SIGKILL')` → `exit(null,'SIGKILL')`, `kill('SIGTERM')`/`stdin.end()` → graceful `exit(0,null)`. `pid=null` makes the manager's OS-`process.kill` sync-shutdown paths (`shutdownTempSync`/`shutdownForResumeSync`) a safe skip.

The fake-claude **scenario engine** lives once in `tests/fake-claude-engine.mjs` (`runFakeClaude({argv,env,cwd,stdin,stdout,stderr,onReaderReady})`): silent until first stdin message, auto-acks `control_request`s, emits canned events from `env.FAKE_CLAUDE_SCENARIO`, matches `control_response`s so scenarios can branch on allow/deny. `env.FAKE_CLAUDE_ARGV_DUMP` / `FAKE_CLAUDE_ENV_DUMP` capture the launch argv / computed child env; `FAKE_CLAUDE_TRANSCRIPT` records stdin. It reads everything from its params (not `process.*`), so the same engine drives both the in-process launcher and the thin subprocess entrypoint `tests/fake-claude.mjs`. Config flows through `env` (bootServer sets `FAKE_CLAUDE_SCENARIO`), and for the in-process path `CLAUDE_BIN` is a **bare sentinel** (`claude`, no script path) so `resolveClaudeBin`'s `prefixArgs` stay empty and the argv the engine sees equals the real CLI flag set.

**`bootServer({claudeLauncher})`** injects a custom launcher (e.g. `tests/backend-spawn.test.mjs`'s `ControllableLauncher`, whose child stays alive until the test triggers a spontaneous `crash()` or a `kill()`) to exercise post-launch crash paths. A test needing a **substitution backend** that reaches a real fake binary registers a registry row whose `template` names it (`addBackend`) — templates are data, so that is the injection seam; there is no per-command env shim.

**`bootServer({realProcess:true})`** opts a test back into a real `node fake-claude.mjs` subprocess (`RealClaudeLauncher`) — needed only where a test uses a real `.pid` / OS `process.kill(pid)` / the SIGKILL+reap sync-shutdown path: the `instances.test.mjs` crash+respawn test, and the two `shutdownTempSync` tests (`archive-sessions.test.mjs`, `restart-temp-cleanup.test.mjs`). Each opts in per-test (booting its own dedicated realProcess server) so the rest of its file stays in-process. `shutdownForResumeSync` is graceful (`stdin.end()`), so `resume-after-restart.test.mjs` stays fully in-process.

**Process-count guardrail** (`tests/run.mjs`): samples the peak concurrent `fake-claude.mjs` subprocess count via `/proc/*/cmdline` (~100 ms) and fails the run if it exceeds a process-count budget `FAKE_CLAUDE_BUDGET` (`tests/run.mjs`) — catching a regression that flips the default back to subprocess or a new test that spawns real processes without `realProcess:true`. A clean default run peaks at ~2–3 (only the realProcess opt-in tests). Enforcement is skipped under `RUN_REAL_CLAUDE=1` and when `/proc` is unavailable. It reads `/proc` through `tests/procTree.mjs`, the suite's single `/proc` reader (one `snapshot()` per sampler tick answers every question the tick asks, so the answers cannot disagree mid-tick). (Use `/proc` reads only here — `pkill`/`lsof` misbehave on this host.)

### Suite hang guard

**The invariant: no test file may outlive its own report.** node:test emits a file's terminal `test:summary` **only when its child process exits**, so a file that finishes its tests but leaves the event loop open never reports and wedges `reporter.on('end')` in `tests/run.mjs` *forever*. That is not hypothetical: it cost review 2026-0183 code-mutant's entire 300 s external ceiling for one leaked handle.

**The `timeout` option is not a defence.** `run({timeout})` reaches each child as `--test-timeout`, a **per-test** deadline on the test body's promise. It cancels the *test*, never the *process*. Measured shapes that it does not touch at all: a test that **passes** while leaking a handle; a test that **fails** before its cleanup line; a CPU busy-loop (the timer cannot run); an orphan grandchild holding inherited stdio after the child exits cleanly.

**`--test-force-exit` is a trap — do not add it.** It makes leaking children exit, but `process.exit()` in the child **truncates its pending report to the parent pipe**. Two whole-suite scans with it on disagreed by 31 tests; one silently emitted *nothing* for `tests/mcp-conductor-view.test.mjs` (~38 tests) while still printing `fail 0` and **exit 0**. A silent green is worse than a hang.

Three layers, all reading their deadlines from `tests/hangGuardConfig.mjs` so a guard can never protect a private copy of a number. Every deadline is env-overridable **only** so the `tests/hang-guard-*.test.mjs` suite can drive the real code path at millisecond scale:

| constant | env override | role |
|---|---|---|
| `FILE_KILL_MS` | `CC_TEST_FILE_KILL_MS` | parent: SIGKILL a per-file child that outlives it. Must stay **above** the per-test `timeout` in `run.mjs` so it cannot pre-empt a test node would still cancel and report. |
| `LEAK_GRACE_MS` | `CC_TEST_LEAK_GRACE_MS` | child: time from root-`after()` entry to declaring the loop leaked. |
| `ORPHAN_SWEEP_MS` | `CC_TEST_ORPHAN_SWEEP_MS` | parent: grace between every discovered file being *settled* and declaring the report stream stalled. `end` normally follows the last summary within ~4 ms, so this is nearly all margin; applied once, from the last file to settle. |
| `RUN_CAP_MS` | `CC_TEST_RUN_CAP_MS` | parent: absolute run ceiling. **Last-resort backstop only** — it makes an unbounded hang finite; the per-file deadlines above are what produce a timely verdict and what must fit inside an external harness's ceiling. Measured: a full run under 24-way CPU starvation (load ~30) takes **~157–170 s**, so a 240 s cap would leave only ~1.4× margin and go red on a merely-loaded box; the default is sized ~3.5× the starved figure. **The plan's stated property "below code-mutant's 300 s so we, not it, produce the verdict" is therefore NOT true of this constant and must not be re-asserted** — `harness/mutation/config.json`'s `timeoutMs` is 300 s. It is benign because the per-file deadlines (90 / 15 / 5 s) and the stream-stall check are what actually terminate a wedged run, all well inside 300 s. |

- **Layer B — `tests/handleLeakGuard.mjs`** (child side), preloaded into every per-file child via `execArgv: ['--import', …]` alongside the DOM tripwire. A `--import` preload evaluates before the test body, so its root `after()` hook is registered — and therefore runs — **first**, ahead of the file's own `after(() => ctx.close())`. It does not check anything there; it arms an **unref'd** `LEAK_GRACE_MS` timer. Clean file → the loop drains, the process exits, the timer never fires, zero happy-path cost (which is exactly why arming it ahead of the file's own teardown does not race that teardown). Leaking file → the timer gets a turn, which **is** the criterion; it writes the diagnostic with `fs.writeSync(2, …)` (synchronous, so it cannot be truncated the way `process.exit` truncates an async pipe write) and exits 1, which the parent surfaces as a file-level `test:fail`. Cost of a leak becomes `LEAK_GRACE_MS` instead of infinity.
- **Layer A — `tests/run.mjs`**: (1) a **completeness ledger** — every discovered file must emit its own `test:summary` (the per-file event carries `data.file`; the single run-level summary has `file === undefined`, which is how they are told apart). Anything discovered but never reported is **named and counted as a failure**, which closes the truncation class above whatever its cause. (2) A **per-file kill watchdog** mapping live direct children to the test file named as the **last** element of their argv, SIGKILLing the whole tree past `FILE_KILL_MS`. (3) A **stream-stall check** plus a **leaked-process sweep** (see below) on **four** triggers — stream stall, run cap, **normal run end**, and **SIGINT/SIGTERM**. The last two are card 2026-0226: a leaked process only wedges the stream if it holds stdio inherited from the *runner*, and a plugin child holds pipes to the *test file's* child, so it wedged nothing and no trigger ever fired — measured, 21 orphans across 9 runs that all exited 0. (4) An **absolute run cap**. (5) An unconditional `hang-guard:` verdict line on green *and* red runs, carrying files-reported / killed / swept / stall / cap state and the slowest 5 files — the slowest figure is the standing evidence that `FILE_KILL_MS`'s margin is still real as the suite grows. Expect a **steep ranking with one culprit**, not a plateau; a flat top five means the metric regressed (see the next bullet). `FILE_KILL_MS` in `tests/hangGuardConfig.mjs` owns the measured figures, the margin trend across review rounds, and — the number that actually binds — the **broken-guard** cost; that comment is the reference, not this line, and the line also **says when `/proc` was unavailable**, because a blind watchdog reporting `0 killed` must not read as `clean`.
- **The verdict line's two events are different events, and the split is deliberate.** The **completeness ledger** is defined against `test:summary` (per-file carries `data.file`; the run-level one has `file === undefined`). The **per-file duration** comes from `test:complete`, filtered to the file-level test via `d.name === d.file`. They differ because per-file `test:summary` events are emitted in `files` order, so a file finishing ahead of an earlier-listed one has its summary **held** until that one reports — and a duration measured at summary time then charges it the earlier file's wall. Measured, same file, argv order swapped: `parser.test.mjs` reported 1172 ms vs 108 ms, and in the inflated case **ranked above** the file that actually spent the time. `test:complete` fires at real completion and is order-independent. It is preferred over `test:summary`'s own `duration_ms`, which is measured inside the child and so excludes spawn + import: dispatch→child-done keeps the figure comparable to `FILE_KILL_MS`, a process-lifetime deadline. Measured on a 16-core box at the default concurrency, `summary.duration_ms` runs **31–297 ms lower**, never higher, across 90 file observations — sampling **every 6th name of the sorted `tests/*.test.mjs` list (45 of 266 at the time), skipping the files that spawn nested runners of their own** — then two (`hang-guard`, `summary-attribution`), now six (the five `hang-guard-*` plus `summary-attribution`), so repeating this sample today skips six — in two runs (one idle, one under a concurrent mutation campaign) that agreed closely. **The range travels; the centre does not.** Median 219–234 ms / mean 179–181 ms describe *that* sample only: the excluded work *is* spawn + import, so the centre tracks the import weight of whichever files are picked — cheapest here ~31–35 ms, express+ws importers ~297 ms, and a lighter-weight subset of the suite medians near 87 ms. The earlier "consistently 25–50 ms" figure was ~5× low because it described only the cheapest files. `tests/summary-attribution.test.mjs` is the regression guard. It runs the real `tests/run.mjs` against fixtures under `tests/fixtures/attribution/` and asserts on the `hang-guard:` lines, covering three seams that fail against **different** wrong implementations — none is redundant. Test 1 overrides to **`TEST_CONCURRENCY=4`** (one slot per chained fixture — fewer deadlocks the chain, loudly); tests 2 and 3 keep the helper's default of 2:

| test | fixtures | fails against `test:summary` source | fails against last-**inner**-`test:complete` source | fails against a **whole-second** figure |
|---|---|---|---|---|
| charges each file its own wall | the four **chained** fixtures — `fast` 0 → `subsecond` +550 → `medium` +650 → `slow` +900 — argv **descending** (`slow, medium, subsecond, fast`), `slow` still **first** | yes — (1), (2) and (2b) all fire | no | yes — (5), unconditionally |
| a **killed** file keeps its figure and rank | `killed` (outlives `CC_TEST_FILE_KILL_MS=2000`), `fast` | yes — it emits no summary at all | yes — its one test never completes | no |
| post-test **teardown** is inside the figure | `teardown` (~1 ms test, ~900 ms root `after()`) | no | yes — reports ~29 ms instead of ~954 ms | no |

`subsecond` exists because its **+550 ms link is the smallest designed increment**, and therefore the resolution floor: assertion (2b) `sub - fast >= 550` is the only one that dies against a reporter which rounds away sub-second separations while preserving larger ones. Assertion (5) is `[slow, medium, sub, fast].some(ms => ms % 100 !== 0)` — a **lattice residue, carrying no load term at all**. It fires on any lattice whose quantum is a multiple of 100 ms (every figure becomes `≡ 0 (mod 100)`), which covers the whole-second, 500 ms and 100 ms cases — the last two being holes the superseded two-sided `0 < medium - subsecond < 1000` band provably let through. That band is **gone**: it was measured *outside* its own range (gap 1053 ms) on a **correct** reporter at load1 ~73, i.e. it was itself a machine-speed window. (4) `slow >= 2100` is a pure control — an absolute **lower** bound that load can only inflate. **Envelope, not totality:** a uniform rescale of every figure by a constant factor (e.g. ×1.5) passes every assertion here, violating no ordering, no designed separation and no resolution claim. A lattice whose quantum is **not** a multiple of 100 ms largely **escapes**: (5) fires only when *all four* figures happen to land on the 100 ms lattice, so a 50 ms quantum is caught with probability ~(1/2)^4 = **1 run in 16** — measured **0 kills in 16 runs**. State that as the escape it is; the residue's guarantee covers 100 ms-multiple quanta only.

Argv order and the concurrency are load-bearing: the ordering bug only fires for a file listed *after* one still running, and the **descending** argv order is what keeps the dequeue term non-negative. **NEVER A RATIO** — that is the defect card 2026-0222 removed: a ratio between two wall figures *multiplies* the per-file spawn+import cost instead of cancelling it (`fast * 3 < medium` reduces to an absolute cap of `C < 600 ms`), and it went red 10/24 at 72-way on a correct reporter. Every bound is now a **difference against a designed chain increment** (1200 / 900 / 550), plus the one absolute **lower**-bound control; the fixture sleeps are no longer solved as a pair against a shared `C` budget, because no bound carries a `C` term. The threshold algebra that lived in the test's header is **deleted** — do not restore it, and do not reintroduce a ratio. See the ratio worked example above for the construction and both campaigns' figures. It follows the same two rules as the hang-guard regression suite below — `*.fixture.mjs` naming and a **deleted `NODE_TEST_CONTEXT`** in the child env. Do not move the duration back onto the `test:summary` handler, and do not narrow it to the last inner `test:complete`.
- **Layer C is deliberately empty.** There is no periodic sweep of "files that leak"; the guard is structural, fires on any future leak with no per-file opt-in, and needs no rule for a test author to remember.

Three non-obvious mechanics, each of which cost a wrong first cut:

- **`killTree(process.pid)` kills the runner.** `tests/procTree.mjs` therefore exposes `killDescendants()` (never touches the root) and `killPids()` refuses `process.pid` and pid ≤ 1. At the run cap, use `killDescendants` — an earlier revision turned a reportable timeout into a bare `exit 137` with no verdict at all.
- **A leaked process keeps the report stream open. It is identified EXACTLY, by a run marker — do not re-introduce a heuristic.** A grandchild is reparented to init the instant its parent dies, so no `/proc` walk from the runner reaches it; and if its file completed inside one 100 ms sampler tick it was never recorded either (measured: a 33 ms file's orphan survived an entire run and leaked onto the box). FD-INODE MATCHING was tried and refuted — node spawns child stdio over *socketpairs*, whose two ends have **different inodes**, so our `/proc/<pid>/fd` link never equals the orphan's. That refutes inode **equality** only; peer resolution does exist via netlink `UNIX_DIAG_PEER` and is merely out of scope. The full note, with the measurement, lives at `sweepOrphans` in `tests/run.mjs` — read it there rather than trusting a summary. So the design splits the two concerns:
  - **Termination is guaranteed without identifying anything.** A file is *settled* once it has reported, been killed, or lost its child without reporting. Once every discovered file is settled and the stream *still* has not ended, it can teach us nothing further, so the runner **abandons the wait**, prints `STREAM STALLED`, and fails the run. This needs no `/proc` at all. The trigger is deliberately **not** "this file failed to report": the measured orphan shape is a file whose child exits *cleanly with every test passing*, so its summary arrives — a `reported`-gated check switches itself off in exactly the case it exists for, and the run then falls through to the absolute cap.
  - **Killing uses an exact identity, not a heuristic.** `tests/run.mjs` exports a run-unique **`CC_TEST_RUN_ID`** (an `mkdtemp` basename) before any child forks, so every descendant inherits it and `processesWithMarker()` finds it by reading `/proc/<pid>/environ`. That reflects the environment as of *exec*, so it survives `setsid`/`detached: true` (which escapes the process group), survives reparenting to init, needs nothing to have been sampled beforehand, and cannot match a stranger, a system daemon, a shell-pipeline sibling, or a *different concurrent run* of this suite. It replaced a process-group + `ppid == 1` + start-time heuristic, which was **unsafe**: a process group is a job boundary only under interactive job control, and under `sh -c`, CI, or an agent harness — how this runner is actually executed — the runner inherits its parent's group, so the group spans unrelated work. **`PROJECTS_ROOT` is not usable as the marker**: `bootServer` reassigns it per server to a path outside the run root, so a grandchild spawned mid-test would not carry it (measured). Two best-effort sources remain alongside it (live descendants; pids recorded per file), but the marker covers everything they miss. A **standalone** `node tests/foo.test.mjs` gets its marker from `markRun()` in `tests/safeStoreRoot.mjs` (`??=`, so an inherited one is never replaced — overwriting it would drop that child out of its own run's sweep); before card 2026-0226 a single-file run set none, the one mode in which a leaked process has no identity at all. **The run-end sweep runs before `removeSafeRoot`**, and that order is pinned rather than commented: `run.mjs` re-reads its own marker between the two, so moving the sweep past teardown (which is what leaves a live process with a `(deleted)` cwd) prints `RESIDUAL` and fails the run. The check **holds** the invariant rather than only reporting it — anything it finds already matched this run's marker, so it is reaped through the same `killPids` path before the root goes, and the run still goes red. **A `/proc` snapshot is not evidence of liveness**: each candidate is re-verified **live** via `hasMarker`, because `processesWithMarker`'s `readdirSync('/proc')` samples the pid list microseconds after the sweep's kills, so a pid early in a ~2700-pid walk is read inside its own death window — observed once at load 25 as a false `RESIDUAL` with `SWEPT` naming the same pid. `RESIDUAL_SETTLE_MS` (`tests/hangGuardConfig.mjs`) then caps how long a genuinely-signalled process is given to die. It owns the measured figures, the reason it is *not* the fix, and the reason it is a **measurement-informed choice rather than a guarantee** — no fixed bound covers a process held in D-state sleep or under swap/cgroup throttling. What makes that acceptable is the failure *direction*: exceeding it produces a visible red on an otherwise-clean run, never a silent leak, with `CC_TEST_RESIDUAL_SETTLE_MS` as the escape hatch. **SIGKILL of the runner is uncoverable by construction** — no in-process handler runs — which is the standing reason `tests/reapOrphans.mjs` exists.
  - **The stall check is gated on node having finished** (`nodeFinished`, set by node's single run-level `test:summary`, the one with `file === undefined`). Without that gate it false-positives on a healthy run with a **slow stdout consumer**: the ledger settles from source-stream events at push time, while the wait is on the composed reporter, whose `end` is deferred by backpressure from `reporter.pipe(process.stdout)`. Measured with ~4 MB of output and a paused reader — gate removed: `STREAM STALLED`, a SIGKILL sweep and **exit 1 at 1.8 s on a green run**; gate present: exit 0. `node tests/run.mjs | less` is enough to trigger it and raising `ORPHAN_SWEEP_MS` cannot help, since a pager pause is unbounded. The run-level summary is the exact discriminator: emitted at push time on a healthy run (~44 ms), **never** emitted in a genuine wedge (absent through 5 s). Note the volume threshold is real — at ~200 KB the runner still finishes in ~120 ms behind a paused reader, because the OS pipe plus libuv's queue absorb it and the closing `process.exit()` discards the rest, so a smaller fixture would pass against the broken code.
  - Measured outcomes, all previously running to the absolute cap or hanging forever: a sub-tick leak swept, run ends ~1.7 s; a **detached** leak swept (the marker reaches it), ~1.7 s; a live grandchild swept, ~3.2 s.
- **The run cap timer is deliberately REF'D** (and cleared in a `finally`, on both paths). An unref'd cap cannot fire once the loop has otherwise drained — the "all children gone but the stream never emitted `end`" case, where the runner would exit *naturally* with code 0 and skip the verdict. **Disclosed gap:** no test discriminates ref'd from unref'd. Making it unref'd leaves the whole suite green, because inducing that state requires the loop to drain while the stream is still pending, and every way of holding the stream open also holds a handle. `tests/hang-guard-run-cap.test.mjs` pins the cap's *observable* behaviour instead (it fires, fails the run, prints the verdict, bounds the wall time) with a child still alive — a state an unref'd timer would also fire in. Ref'd is kept because it costs nothing and the failure it guards is a silent green.
- **`LEAK_GRACE_MS` is the real per-file teardown deadline, not `FILE_KILL_MS`.** It is 6× tighter (15 s vs 90 s) and is armed at the *first* root `after()` hook — which, because a `--import` preload registers before the file's own hooks, is before the file's own teardown starts. A file whose teardown legitimately exceeds it is failed by Layer B as a leak and the 90 s figure never gets a say; under the ~2.7× starved slowdown a file with ~6 s of quiet-box teardown would cross it. If a file starts awaiting many child exits in teardown, raise `LEAK_GRACE_MS`, not `FILE_KILL_MS`.

**`process._getActiveHandles()` is a private Node API** (present through **v24.18.0**, the version all of this was measured against). Layer B uses it for the **diagnostic only** — never as the pass/fail criterion — and degrades to a clear "culprits UNAVAILABLE" note if it is ever absent, because a guard whose own failure mode is a crash would just be a new hang class. The culprit filter is `_getActiveHandles()` minus stdio, kept only where `hasRef()` is true; note `hasRef` lives on the internal `_handle`, not the JS wrapper. Ref-awareness is what makes it usable: a naive `process.getActiveResourcesInfo()` check flags **207 of 267** files (unref'd timers, in-flight `FSReqCallback`s).

**Two different probes, two different numbers — keep both, because collapsing them deletes the fact that would re-open the Layer C decision.** The plan measured **12 of 267** files holding a ref'd handle *at the moment of child exit*, and that number was the entire justification for planning a 12-file sweep. Layer B asks a different question: *is the loop still open `LEAK_GRACE_MS` after teardown began?* By that predicate **0 of 273** files leak at `a23fbbb` (2026-08-24). **The census lineage, because 268 + 4 ≠ 273 and the gap is real, not an error:** 267 at the at-exit probe → **268** when 2026-0190 landed (it added `hang-guard.test.mjs`) → **269** after an unrelated card added a file → **273** once card 2026-0198 split that one file into five. Anchor any re-count to a sha rather than to the arithmetic. Layer B is preloaded into every per-file child, so a green whole-suite run *is* this probe. A re-run of the plan's own at-exit probe now flags **1** (`static.test.mjs`, a `Socket`). Both results are true: a handle that is closing *during* teardown is real at the exit snapshot and never wedged anything. Layer B's is the operationally meaningful one, which is why the sweep was dropped — see "Layer C is deliberately empty" above.

**Two refuted mechanisms, recorded because the obvious intuition is wrong both times.** (1) **`_getActiveHandles()` does not report timers at all** in v24 — a ref'd `setTimeout` keeps the process alive while being completely invisible to it. Layer B still catches a leaked timer, but via *the loop still being open* (the grace timer firing), not via the handle list; so an empty culprit list plus a live loop is reported as **either** a leaked ref'd timer **or** teardown work still in flight — pending fs ops and awaited child exits are *requests*, not handles, so they are equally invisible, and "await the child's actual exit in teardown" is a pattern this very document recommends. The guard does not assert which; only the loop-still-open criterion is certain. (2) Consequently **Layer B cannot pin "an idle heartbeat was cleared"** — and `src/idleSubscriptions.ts` `.unref()`s that interval anyway, so an uncleared one holds nothing open. Do not "restore" a coupling between `tests/idle-wake-ownership.test.mjs`'s `timeoutMs` tests and the leak guard; see the honest-pinning comments at those sites.

**Writing a test so it cannot leak.** Release every fixture on the **fail** path too — `try/finally` or `afterEach`, never a cleanup line trailing the assertions (that is the exact 2026-0183 shape). For a happy-dom `Window`, `window.happyDOM.abort()`; for a spawned child, await its actual exit.

**Register the teardown AT SPAWN TIME, not after the helper returns** (card 2026-0226). A `try/finally` in the caller cannot cover a helper that spawns and *then* awaits readiness: the handle does not reach the caller until after the wait, so a timeout there leaks a child the `finally` never learns about. `startAndSettle` in `tests/plugins-supervisor.test.mjs` is the pattern — `t.after(...)` on the line after `sup.start(...)`, before anything that can throw.

**A teardown that signals needs a LICENCE, and identity is the only safe one.** Once teardown is unconditional it also runs for tests using a fake/injected `spawn`, whose stand-in children carry synthetic pids (`900001 + n`) — and `sup.stop` signals a process *group*, so an unguarded hook calls `process.kill(-900001, …)`. The hazard is the **wrap**, not any one census: `pid_max` here is 4194304 and allocation has long since passed the synthetic band, so a literal `900001` is a *real* pid — an unrelated live process sat at **1089935** while this was written (2026-08-25; the live ceiling moved 3.99M → 4.10M during that one card, which is why the figure is dated and the property is what you should rely on). So that group belongs to a stranger. Guard with **`hasMarker(pid, marker)`** (`tests/procTree.mjs`) — `processesWithMarker`'s identity asked about one pid, failing closed on a vanished or unreadable `environ` — never a caller-supplied "this one is fake" flag, which relocates kill authority to the caller instead of closing the class. Match by identity only: **never** by name, process group, ppid, or start time.

**A fixture's diagnostics reach `runGuard` on the runner's STDOUT — never on its stderr — including a raw `writeSync(2, …)`.** `node:test` captures the per-file child's stderr, relays it as a `test:stderr` event, and `tests/run.mjs`'s `spec` reporter writes it out through `reporter.pipe(process.stdout)` (`tests/run.mjs:432`). Choosing fd 2 over `console.log` in a fixture buys freedom from in-child reporter reformatting, **not** a different outer stream (measured 5/5 with `silent-orphan.fixture.mjs`). `runGuard` drains both pipes into one `out`, so a case that only *reads* the text is unaffected; anything that *hooks* a stream is not — which is why the interrupt legs' `signalWhen` rendezvous is called from both `data` handlers, a stderr-only hook having silently never fired (card 2026-0228).

**Why five files and not one** (card 2026-0198, splitting the former `tests/hang-guard.test.mjs`): each case's cost is its squeezed **deadline**, not work, so a single serial file was charged the *sum* of every case's deadline and five files are charged the *max*. `staleRunTargets(snap, rootExists)` is pure over its snapshot and its oracle. A pid is licensed iff
**all** hold: `snap.available` (a partial `/proc` read yields *nothing*, never everything); `pid > 1`
and not `process.pid`; its `environ` carries a both-ends-anchored `CC_TEST_RUN_ID` entry (`MARKER_RE`
in `tests/procTree.mjs` — one home for the anchoring); the captured id matches `RUN_ROOT_SHAPE`
(exported from `tests/safeStoreRoot.mjs`, not re-declared); and **`!rootExists(id)`** — the owning run
reached `removeSafeRoot`, so it is *provably* over. That last conjunct is what makes the tool safe to
run while a suite is in progress. `--id` swaps the oracle for `marker !== id`, so naming a run
narrows the list and a typo selects nothing. Kills go through `killPids`, which re-verifies each
pid's starttime identity immediately before signalling.

**`pkill -f 'node server.mjs'` is NOT safe as routine cleanup**, though it works as a one-off. A
*name* match hits the live children a running suite spawned — manufacturing failures that read as
real reds — and unrelated apps on a shared box. It is also what destroyed the `server.mjs` family's
evidence during card 2026-0226's inventory.

### Reproducing CPU starvation

Several deadlines and flake rates in this repo are quoted "under 24-way CPU starvation"
(`FILE_KILL_MS` in `tests/hangGuardConfig.mjs`; `tests/summary-attribution.test.mjs`,
`tests/renew-session.test.mjs`, `tests/idle-wake-ownership.test.mjs`). This is how that condition is
produced. Use the **self-limiting** form:

```bash
N=24; SECS=600          # 24 = the DEFAULT width; card 2026-0222's figures are at 72 — see below
for i in $(seq $N); do timeout --signal=KILL "$SECS" sh -c 'while :; do :; done' & done
trap 'kill $(jobs -p) 2>/dev/null' EXIT INT TERM
wait
```

- **`timeout --signal=KILL` is the load-bearing half.** The `trap` dies with the shell; `timeout`
  does not. A worker killed mid-campaign cannot leave 100%-CPU spinners behind, which a bare
  `trap`-only version does — and a leaked spinner is far more expensive than a leaked idle timer.
- **The agent shell here is zsh, where bare `kill $pids` silently leaks spinners.** When killing by
  hand rather than letting `timeout` do it, use `xargs` with an anchored `pgrep`.
- **`N` is a starvation WIDTH, not a core count.** `FILE_KILL_MS` (`tests/hangGuardConfig.mjs`)
  and the test comments above are quoted at **24-way**, which is why the example is 24;
  card 2026-0222's attribution figures are quoted at **72-way**. A run at a different `N` is a
  different measurement and must say which. (Do not confuse this with the *8-core* / *16-core* device figures elsewhere in this
  section: those are hardware, not induced load.)
- `SECS` bounds the whole campaign, and is what makes the recipe self-limiting.
- **A 24-way pass does not clear a load-correlated flake.** 24-way is the default width, not the
  top of the range a defect can live in.
  `tests/summary-attribution.test.mjs` was measured at `174c355` on a 16-core host: **0/30 red at
  24-way (load1 19.5–25.0)** and **10/24 red at 72-way (load1 72.8–74.4)**, with **0 orphans either
  side of every campaign**. Quote the width with the result, and when a card's own reproduction was
  at a wider N, verify at that N — not at 24.
- **The quantity that scales is per-file spawn+import cost `C`** (fork+exec+node boot+import, which
  `run.mjs`'s `done - dequeue` figure includes). Measured maxima: **`C` ≈ 320 ms at 24-way** vs
  **`C` ≈ 770 ms at 72-way** — ~2.4–3.2x. Any test bound that tolerates `C` must be re-checked
  against the 72-way envelope, not the 24-way one.

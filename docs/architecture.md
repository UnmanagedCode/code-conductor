## Stack
- Node 24+ (native type-stripped TypeScript for `src/*.ts`, `node:test`, top-level await, `crypto.randomUUID`).
- `express` (REST + static) + `ws` (WebSocket).
- The browser UI — `web/`: Vite + React + TypeScript + Tailwind v4 + shadcn/ui, served at `/` and built into `web/dist/` by the server at start when its sources changed, or staged into `web/dist.next` before a restart (`src/webBuild.ts`). The build tooling is a runtime dependency; Vitest, Testing Library and Playwright are dev-only. `shared/` holds the TypeScript modules it shares with the server and the node tests; nothing there is served.
- `happy-dom` (dev-only) for DOM-backed rendering tests, and the environment of the Vitest suites.
- No DB — **a project IS a record**: `<store>/projects/<name>/project.json` holds one `location`, and its tree may sit under `<projectsRoot>/`, nested in a container directory there, anywhere else on disk, or on a registered system. Sessions in `<configDir>/projects/<encoded-cwd>/*.jsonl` — `<configDir>` is `~/.claude` for a LOCAL place and the target's own cc-owned config dir for a remote-backed one (see `transcriptRoot` under [`src/projects.ts`](components/store.md#srcprojectsts)). The local jsonl root is overridable via `CLAUDE_PROJECTS_ROOT`.

## Conventions

Load-bearing rules this codebase follows — keep new work inside them so the project stays manageable as it grows.

1. **YAGNI — build for the requirement in front of you, not the one you imagine.** Implement only what a current, concrete caller or test needs; don't add speculative abstractions, config knobs, or extension points "for later" — they add surface area without a real user, and the eventual real requirement rarely matches the guess. If code stops being exercised by a real caller or test, delete it rather than keeping it "just in case" or "to trim later" — dead code rots silently and misleads the next reader into thinking it's load-bearing.
2. **Frontend: features in `web/src/features/<area>/`; `main.tsx`/`App.tsx` only mount.** UI feature logic lives in its area's directory under `web/src/features/<area>/` (DOM-free logic in the `@shared` modules, the transcript model in `web/src/conversation/`). `main.tsx` mounts `<App/>` and starts each feature once; `App.tsx` lays out and mounts. A feature opens another feature's dialog or view only through the `open*` APIs (`web/src/features/dialogs/api.ts`, `web/src/features/views/api.ts`) and otherwise imports only its store, action or component modules; `web/src/app/` imports no feature and reaches them through `web/src/app/events.ts`. Don't grow `main.tsx`/`App.tsx` with feature logic; put it in the feature and start it from there.
3. **No god-modules — extract composed collaborators.** When a module takes on a second responsibility, lift it into a collaborator the owner *composes*, keeping the public surface stable via delegation. Cf. `InstanceManager` → `IdleSubscriptionHub` + `OverageResumeController`; `mcp/handlers.ts` → `diffPaging` + `messageReconstruction` + `content` + `textRender`/`readRenderers`; whisper/tts install → the `makeInstallRunner` factory; the convention scopes' catalog → `conventionSelection.ts`'s `createSelectionStore`.
4. **One service layer for REST + MCP — don't reimplement per surface.** Git / worktree / diff / session logic lives once in `src/worktrees.ts` (+ siblings) and is imported by **both** the `src/routes/` routers and `src/mcp/handlers.ts` (shared: `isGitRepo`, `mergeWorktreeIntoParent`, `syncWorktree`, `getWorktree`, `resolveProjectCwd`, `getWorktreeMergeStatus`, `worktreeDirtyLines`, `removeWorktree`, …). A new git/worktree op goes in the service layer and is called from both surfaces — never duplicated.
5. **Single-source-of-truth catalogs, shipped to the client — never client literals.** Curated catalogs (`modelVersions.ts`, `whisperModels.ts`, `ttsModels.ts`) own the authoritative list + allow-list + policy server-side; the client *fetches* them (`/api/settings/models` → `shared/models.ts`) instead of hardcoding the canonical set. (`shared/models.ts` keeps a `DEFAULT_VERSIONS` first-paint fallback — a fallback, not a second source of truth. `tests/models-fallback-drift.test.mjs` is what keeps that fallback honest: it asserts every mirror the file lists still equals the server value it mirrors, so a catalog change that forgets the client fails the suite instead of silently showing a stale default until the boot fetch lands.)
6. **Cross-surface magic strings get one owner module.** A canonical string shared across surfaces lives in a single module. Cf. `shared/planApproval.ts` — the approve/reject prompts shared by the UI buttons, the server-side auto-approve, and the MCP `approve_plan`/`reject_plan` tools; `shared/userQuestionAnswers.ts` — the AskUserQuestion answer formatter shared by the UI question card and the MCP `answer_question` tool (a DOM-free module in `shared/` that the server imports directly, avoiding a mirror); `shared/wakeCallback.ts` — the idle wake-stub marker (`WAKE_CALLBACK_MARKER`/`WAKE_BODY_SEP`) shared by the server (build) and the client (parse/render); `SOFT_INTERRUPT_MARKER` in `parser.ts`; `isTaskNotificationContent` and `isInterruptMarkerContent` in `parser.ts` — the CLI's re-injected `<task-notification>` tag and its post-abort `[Request interrupted by user]` line, both recognized by shape (no marker to inject, since the CLI produces the string) and checked at the same three sites as `SOFT_INTERRUPT_MARKER`. On the client the same rule covers the rate-limit vocabulary: the ordered bucket key list (`RL_BUCKET_KEYS`) and the long-form window label map (`RL_WINDOW_LABEL`) have exactly one home, `shared/usage.ts`, read by the fetch merge in `web/src/app/accountUsage.ts`, the popover rows of `web/src/features/session/UsageChip.tsx` and the `rate_limit_event` lines of `systemLine` (`web/src/conversation/format.ts`). The order is load-bearing for both uses (which single window is most immediate, and the popover's row order), so a second list would let the chip and the popover disagree. The terse chip-only `RL_BUCKET_LABEL` stays private to `usage.ts` — that long/terse split is deliberate, not drift. Likewise `apiFetch` (`http.ts`) is the single owner of the fetch-error idiom.
7. **Test-only exports carry an explicit marker.** An export with no production caller that is kept for its tests opens its doc comment with `// Test-only export: no production caller.` followed by one line of *why it is kept rather than deleted with its tests*. Cf. `snapStartToGroupBoundary` (`parser.ts`), `isKnownVersion` (`modelVersions.ts`). Reset hooks (`_resetForTest`) are a distinct, self-naming category and need no marker. An export with **no** caller at all — production or test — is deleted, not marked.
8. **Project-scoped I/O goes through the project's `System` unless it is on the exception list below.** Anything that touches a project's tree — git, reading or writing a file in it, running a command in it — takes the handle `getProject`/`resolveProjectDir`/`resolveSystem` hands out (`src/systems/`). cc's OWN paths are the complement rather than exceptions: the store under `<projectsRoot>/.code-conductor/`, `~/.claude/**`, `<projectsRoot>/.plugins/` and the self-update checkout are local by definition and keep their direct calls. **Resolving a project is NOT project-scoped I/O** — it is one store read and touches no tree at all. **A worker's FUSE run directory is one of them** — it lives under the store, the mount scaffolding is the orchestrator's own, and `src/systems/fuse/` writes it with `node:fs` on purpose. A worker reads its project through the union at the project's real path on its system. 

   **Browsing an arbitrary path on a system before it is registered** (`src/dirListing.ts`) goes through `systemById(...)` → the System handle, the way `adoptProject` does — a use of the seam, not an exception-list entry.

   **The exception list — bare `fs`/`spawn` on a project path, sanctioned, with the reason each is sanctioned.** Adding to it is a design decision, not a shortcut; anything not on it is a leak.
   - **`src/plugins/supervisor.ts`'s backend spawn** (`_spawn('bash', ['-lc', manifest.backend.start], {cwd: <project dir>})`) — project-scoped and deliberately bare: plugin backends are **local-only**, because crossing needs remote process lifecycle plus a port forwarded back to cc. A remote-system project refuses the affordance instead.
   - **`Instance.launch`'s CLI spawn** (`instances.ts`, via the injected `ClaudeLauncher`) — cwd is the project tree, deliberately bare: the `claude` CLI always runs locally, whatever system the project lives on — a remote system cannot be assumed to host node or Claude credentials.
   - **The repo-tracked plugin surface's reads inside a project tree** — `readManifest` plus the declared-path `fs.access` checks beside it (`plugins/manifest.ts`: `<tree>/conductor.plugin.json` and the `conventions[].file` / `scaffold.file` it names), `worktreeManifestFallback` (`plugins/registry.ts`, which feeds a worktree's `worktreePath` into that), and `claudePluginDirs`' `fs.access` on `<cwd>/<rel>/.claude-plugin/plugin.json` (`plugins/contributions.ts`) — bare for the same reason as the backend spawn above: repo-tracked plugin contributions are **local-only**, and that member skips a non-`local` placement before it resolves anything. P4 owns their refusals. (`readFragment` in the same module is NOT on this list: a fragment body is read through the placement's `System` handle.)
   - **The Plugin Library's install-target paths** (`plugins/library.ts` — the installed-check `fs.stat`, the failed-clone `fs.rm` and the update precheck's `fs.stat`, all on `path.join(projectsRoot(), name)`) — cc-level, never per-project: the library only ever clones into the local projects root — the one marginal misreport being a library name colliding with a remote project's.
   - **`ensureConductProject`'s `fs.mkdir`** (`conduct.ts`) — `.conduct` is pinned to the local system unconditionally, so its dir is cc's own by invariant. The `CLAUDE.md` write beside it *does* take the resolved handle: that is the pin being used, not an inconsistency to tidy away.
   - **`listProjects`' enumeration of the projects root** (`projectRegistry.ts`) — the root is cc's own registry area, not a project tree. A remote project does not live in it; P4 adds remote records by unioning store-derived entries onto this local enumeration, so routing the `readdir` through a System would be the wrong fix.

   The rule is enforced for everything else by `tests/systems-seam.test.mjs`, which watches `fs.promises` and `node:child_process` while real operations run — against both an in-root and an adopted project — and fails on any call that reached a project tree without a `LocalSystem` frame beneath it. So a reintroduced direct call is a named failure, not a silent one that works until the project moves to another machine.

9. **Host-OS differences come from `Platform`, not `process.platform`.** Spawn options, shells, kills, command splitting, path-equality keys and feature capabilities go through the injected `Platform` (`src/platform/`); `process.platform` appears only in `src/platform/index.ts`. Enforced by `tests/platform-seam-guard.test.mjs`.
10. **No two paths, and no two module stems, may differ only by case.** A case-insensitive filesystem (NTFS, default APFS) cannot check out two paths that fold to the same name, and resolves an extensionless import to whichever case twin its resolver tries first — Vite tries `.ts` before `.tsx`, so `./Foo` can load `foo.ts` and the build fails `MISSING_EXPORT` on a case-insensitive filesystem only. Checked over tracked plus untracked-but-not-ignored files (`git ls-files --cached --others --exclude-standard`): `pathCollisions` — full paths of any extension and the directories they imply; `moduleStemCollisions` — files matching `MODULE_EXT` (the JS/TS module extensions and `.json`), compared by path minus that extension, test files included. Name a component after its export (`JsonTreeView.tsx`) rather than after a same-stem helper (`jsonTree.ts`). Enforced by `tests/case-collision-guard.test.mjs`.
11. **Dependency-free helpers live once, in `shared/basics.ts`.** It imports nothing; import the helpers it exports rather than writing a local copy. Enforced by `tests/basics-guard.test.mjs`. Its one exemption is `src/systems/referenceProvider.ts`'s `errMsg` (that file is flat-copied into a container with only its siblings).
12. **Server sources (`server.ts`, `src/`, `shared/`, `migrations/`) have no runtime import cycle.** Static, non-type imports only (`import type` and dynamic `import()` are not edges; `import { type X }` is). Enforced by `tests/import-cycles.test.mjs`; the scanner and the shrink-only `BASELINE` are in `tests/importCycles.mjs`. Break a cycle by moving the pure code both sides need into a leaf module.
13. **An export has a caller outside its module.** `node scripts/unused-exports.mjs` lists the `server.ts`/`src/`/`shared/` exports no other tracked file's code references, values and types counted separately; drop `export` from a value used only in its own module, delete one used nowhere. `tsconfig.json` sets `noUnusedLocals`/`noUnusedParameters` (as `web/tsconfig.json` does): prefix a deliberately unused parameter with `_`.
14. **Every env read in the server code `scripts/env-reads.mjs`'s `PRODUCTION` scope covers is registered in `ENV_VARS` (`src/env.ts`), with its kind.** `tests/env-registry.test.mjs` enforces it, and the scanner also fails an env access it cannot resolve. `bin/` launchers are outside that scope. The port default is `DEFAULT_PORT`.

## Instance lifecycle
```
create → spawning → idle ←─ turn ─→ turn_end ─┐
            ↓        ↓                          ↓
        load-hist  prompt                  exited / crashed
        fails                                   │
                                                ▼ respawn --resume <sid>
                                            (back to spawning)
```

**Terminal latch (`Instance.spawn` → `_procEnded`).** Every launch wires a **one-shot** latch on the child's `'exit'` **AND** `'close'`, whichever arrives first; it resolves `Instance._procEnded` and calls `_handleExit` exactly once. `kill()` awaits `_procEnded` — never a freshly-registered `proc.once('exit')` — and clears its SIGTERM/SIGKILL timers in a `finally`, keyed on no event at all. Two shapes force this:
- **A child whose spawn FAILED emits `'error'` then `'close'` and NEVER `'exit'`** (measured: +10 ms / +14 ms, both long before anything reaps it). Keying the terminal path on `'exit'` alone left `proc` assigned with `proc.pid === undefined` — and `proc != null` is the liveness oracle (`liveForSession`/`isSessionLive`), so `kill`, `remove`, `shutdown`, `respawn`, the resume manifest and every cross-module `.proc` read saw the corpse as alive; `kill()` and `InstanceManager.shutdown()` never returned.
- **A healthy child killed while a detached grandchild holds its stdout pipes emits `'exit'` and no `'close'`** (measured: `exit(null,'SIGKILL')` at +417 ms, no `close` in the following 2.6 s) — so `'close'` cannot be the primary key either, and the latch must be order-agnostic.

`'error'` is deliberately **not** in the latch: it also fires post-spawn (a failed `kill`), so it is not terminal and never nulls `proc`. The latch is the only thing that does. Because the flag is per-launch closure state, a stale launch's late event can never reach a newer launch's handler — no `this.proc !== launched` identity check is needed. Pinned by `tests/spawn-failure-teardown.test.mjs` (both a real `child_process` spawn against a nonexistent `CLAUDE_BIN` and an injected launcher, which is what makes the mid-kill race window reachable).

**Relaunch window (`Instance._beginRelaunch` → `_awaitRelaunchConfirmed` → `_endRelaunch`).** Shared by rewind, prune and the restart model switch; opened immediately before the kill, closed once the relaunch is confirmed or abandoned:
- **Open:** `_exitSuppressed` and `_relaunching` set. No exit inside it archives a normal session or records an exit cause, and the manager's exit drop (its per-instance `'status'` listener, which reads `_exitSuppressed`) cannot drop the instance on any status emit in the gap — the kill's exit, the attempt's crash, or `launch()`'s `_hydrateAwaitingUser`.
- **Confirm:** `_awaitRelaunchConfirmed` resolves once the relaunched CLI is idle and has outlived `_relaunchGraceMs` (`RELAUNCH_GRACE_MS`); it rejects `500 RELAUNCH_FAILED` with `_lastExitCause()` if the process ends first, or at `_relaunchIdleDeadlineMs` (`RELAUNCH_IDLE_DEADLINE_MS`). `_mutating` is held through it, so a prompt in the grace is refused 409.
- **Close:** `_endRelaunch` clears both flags, archives a normal session still suppressed with no process (`exit_archive`), and emits `'status'` — which lets the manager drop it.
- **Failure end state:** the caller's error surfaces; the attempt is killed (`kill()` also reclaims pre-spawn mount scaffolding); a normal session is archived and dropped, a persistent one stays registered `exited`/`crashed`. Prune first relaunches the unpruned original (also confirmed); rewind has no fail-safe (its truncation is the requested state). The model switch re-resumes on the old model and ends suppression at confirmation, holding `_relaunching` until it settles.
- Respawn (`InstanceManager.respawn`) sets `_relaunching` alone: no kill, and a normal target has already left `byId`.
- Pinned by `tests/relaunch-window.test.mjs`.

**A pristine exit is a removal (`Instance._retireOnExit`).** Every exit of a pristine instance that would archive a normal session — a reap, the header Terminate (`kill` frame), `DELETE /api/instances/:id`, a crash, `InstanceManager.shutdown()`, an abandoned relaunch — runs `_removePristineSession()` instead of `_archiveSession()`: it removes the transcript file and the sub-agent dir (normally neither exists), awaits `_lineageWrite`, then `dropSegment(backingSessionId)` with no `unlessLast`, which deletes the whole store record, a manual title included. The removal deletes no cost or event-log row. The resume-restart path (`_exitSuppressed`) removes nothing; see `src/pristine.ts` → Restart and boot.

**Spontaneous-exit cause (`Instance.lastExit` → `InstanceManager._exitCauses`).** `_handleExit` treats **any** exit with neither `_killing` nor `_exitSuppressed` set as the CLI ending on its own (`_exitSuppressed` spans a whole relaunch window, above, so a relaunched CLI dying inside one records no `lastExit` — its cause is the caller's `RELAUNCH_FAILED` error), on **every** backend and whatever the code — a clean exit included, since the CLI only ends unasked when something went wrong (`launch_failed` is the substitution-backend-only event, on the same gate narrowed to non-zero-or-signalled):
- **Server log.** One `console.warn`, written once the tail has settled (below): `instances: session <sessionId> (<project>[/<worktree>]) exited on its own: code=<c> signal=<s> — stderr: <tail | none>`, the tail's newlines rendered as ` ⏎ `.
- **`lastExit`** = `{code, signal, stderrTail}` (`ExitCause`, `src/instanceTypes.ts`), set **before** `_setStatus`. `stderrTail` is cut by `EXIT_STDERR_TAIL_LINES` then `EXIT_STDERR_TAIL_CHARS` (`src/instances.ts`). `spawn()` resets both `_stderr` and `lastExit`, so a tail belongs to one launch.
- **The tail settles at stderr EOF.** A real child can deliver `'exit'` before readline has read its last stderr line, so the tail cut at the latch is **provisional**: `spawn()` hands `_handleExit` a promise of this launch's own stderr (`launchStderr`, not `_stderr`, which the next `spawn()` resets) that resolves on readline's `'close'` or the stream's `'close'` (a destroyed stream emits no `'end'`), bounded by `EXIT_STDERR_SETTLE_MS` for a grandchild still holding the pipe. On settle the tail is recut **in place** — the `_exitCauses` entry is the same object — and the log line written.
- **Exception: `launch_failed` does not settle.** `_handleExit` cuts its `data.stderr` from `_stderr` at the latch, so for a wrapper that prints after its `'exit'` event, `launch_failed`'s `stderr` can be `null` while `lastExit.stderrTail` (and the refusal's `exit.stderrTail`) carries the line.
- **`_exitCauses`** (publicSessionId → `ExitCause`, insertion-ordered, capped at `EXIT_CAUSE_CAP`). `_handleExit` emits **`exit_cause`** (`lastExit`, or null for a commanded exit) on **every** exit, before `_setStatus`; the manager's per-instance listener records it or **deletes** the entry on null, and wakes the owners (`onTargetExit`, unless `relaunching`). Keyed on the exit path rather than the status transition because a spawn that never started was already marked `crashed` by its `'error'` handler, so no transition follows; emitted before `_setStatus` so it lands ahead of the exit drop, which is what lets the cause outlive a normal worker's `byId` entry and the wake reach owners before the purge clears their entries. A successful `create({resume})` deletes its public id's entry after `launch()` (guarded on `proc`, so a relaunch that already died keeps its own). Read through `exitCauseFor(sessionId)` — exact public id — by the MCP resolvers; wire shape in [protocol/mcp.md](protocol/mcp.md) → Worker resolution.
- Pinned by `tests/spawn-startup-crash.test.mjs` and `tests/idle-wake-exit.test.mjs`; the startup crash, the exit-before-stderr order and the never-started spawn are staged by `tests/controllableLauncher.mjs` (`crashNext`, `crashNext(…, {exitFirst:true})`, `failNext`).

On **resume**: `loadHistory(sessionId)` runs before flipping to `idle` — replays jsonl into UI events and emits a `system/history_replayed` divider. The replayed events fill the ring and the manager stream but are pull-only (no socket gets them as `event` frames); the live `history_replayed` is the subscribed client's cue to re-subscribe and take them as a snapshot tail plus lineage paging. A history longer than the ring cap trims during the replay itself; the evicted prefix stays reachable via `GET /api/instances/:id/events`. On **turn end** or **mode change**: append `{"type":"last-prompt", …}` + `{"type":"permission-mode", …}` lines so `claude --resume`'s interactive picker can discover the session.

**Resume reclaims the instances it supersedes (`InstanceManager._doCreateResolved`).**
A resume is guarded by `isSessionLive(publicId)` in `_doCreate` — not `liveForSession` — which **subsumes** the `liveForSession` + `_resumingPublicIds` pair it replaced and additionally refuses **409** inside a relaunch window (`rotationPending` / `_relaunching`: a prune's kill→relaunch, a rewind's, a respawn's, a restart model switch's, for its whole run), where a `proc`-only guard let a resume start a second CLI on one transcript.
Past that guard, every in-memory instance answering to the session is a superseded husk, so each is retired via `InstanceManager.remove(id)`.
The reclaim is the **last statement before `byId.set`**, not part of the guard: every refusal in `_doCreateResolved` — mode/thinking/effort validation, backend and worktree resolution, the mirror-geometry and hook/bash-rule checks, `FUSE_LAUNCHER_UNRESOLVED`, the resume pre-flight, `FUSE_BACKEND_UNRESOLVED` — runs above it and none is rolled back, so reclaiming earlier let a *refused* resume destroy the session's existing instance (`create({resume, thinking:'garbage'})` over a husk left the session with zero).
The span from `new Instance(…)` to `byId.set` is pure listener wiring, no await and no throw, so nothing between the reclaim and **registration** can fail.
That is the whole of the claim, and deliberately not a guarantee about the create as a whole: `launch()` runs **after** `byId.set` and carries its own refusals — `MIRROR_ADVERTISEMENT_CHANGED` (501) and `_assertRemoteMountable`'s `FUSE_REMOTE_UNREACHABLE` (502) / `FUSE_MIRROR_ROOT_ABSENT` (501).
Those ask the system **live, per spawn**, precisely because the create-time mirror read is memoised off the connection generation and so cannot see a box that stopped since.
Resuming a remote/FUSE session whose box is down therefore tears the husk down, registers the replacement, and only then refuses.
**Known, and deliberately not fixed:** deferring the reclaim past `launch()` would leave the husk and its replacement co-registered for the entire launch, reopening the `anyForSession` first-match window this reclaim exists to close.
A narrow error-path loss is the better side of that trade.
Post-condition: at most one `byId` entry answers to any public sessionId, which is what makes `anyForSession`'s first-match unambiguous.
Without it the husk stayed, `anyForSession` resolved **it** (insertion order), and its auto-resume deadline, idle-wake edges, renew arm, redirect connection and tmp root leaked — `remove()` is the one teardown that reclaims all five, and a stranded deadline holds the **global** overage lockout (`_maybeReleaseOverageLock` short-circuits while `_overageResume.timers` is non-empty).
Same rule `detachInstancesForSession` (`src/routes/projectSessions.ts`) applies at the REST layer, moved to the chokepoint, so the sidebar one-click resume gets it too: resuming a dead persistent session **replaces** its sidebar row instead of adding a second.
- **Safety, and its exact boundary.** `remove()` calls `kill()`, so the reclaim is sound only where nothing it reaches is live. At the guard that holds absolutely: `isSessionLive` false is a `.some()` over **every** answering instance, so all of them have `proc === null` and both relaunch flags clear, and `kill()` takes its already-settled early-out. But `await this.remove(staleId)` is a real event-loop window (a FUSE husk's `kill()` early-out still awaits `_fuse.teardown()`), so the question is what can make one live *during* it. Two of the three in-place revival paths are closed: a competing `create({resume})` is refused by the `_resumingPublicIds` claim, which is `isSessionLive`'s first line; and `InstanceManager.respawn` (`POST /api/instances/:id/respawn`, the UI Respawn button) now refuses **409** while that claim is held — synchronously, with no await between the check and its `_relaunching = true`, which also closes the reverse order through the guard. **The exception, stated rather than assumed:** `Instance.rewindToUserMessage`, `Instance.rewindAcrossRenewal` and `Instance.pruneSession`, reached from `POST /api/instances/:id/rewind` (either body form) and `/prune`, resolve by **instanceId** and require no live process, so a rewind/prune landing inside the reclaim window can still have its fresh process killed. `Instance` holds no back-reference to the manager, so neither can consult the claim from where it runs. Pre-existing and not narrowed by the reclaim — before it, the same interleaving produced a *double-spawn* on one transcript instead — but it is the one case in which this bullet's guarantee does not hold. Closing it wants `_mutating` folded into `isLiveOrComingUp`, which widens the authority the playbook gate reads and is not this card's to take.
- **Race — both actors, not just the deleting one.** A *deleter* can land in the `await` gap: the exit-drop status listener also does `byId.delete`, from the subprocess exit handler. That reaches the same post-condition, so the reclaim treats **404 as success** and propagates every other error. A *reviver* can land there too, which is the previous bullet: 404-as-success says nothing about it, because a revived husk is still **present** in `byId` — it is refused at the entry point instead, never absorbed here.

Covered by `tests/mcp-resume-reclaim.test.mjs`.

**`displayStatus` overlay (additive, not a 6th state).**
The diagram above is the real `status` enum — untouched.
A backgrounded `Agent` tool call's tool_result resolves immediately (`isAsync:true`), so `turn_end` (→ `idle`) can fire while the CLI's own `system/task_started`/`task_updated` task-tracking is still open for that call.
`Instance._activeAgentTasks` (a `Map<task_id, tool_use_id>`) tracks this: incremented on `task_started` **unless** `task_type === 'local_bash'` (backgrounded/promoted Bash — a promoted long-lived command never emits a terminal event and would pin the count forever; `mcp_task`, an auto-backgrounded MCP call, counts like `local_agent`; unknown `task_type`s still count), decremented on a terminal `task_updated` (`patch.status` one of `completed|failed|cancelled|error` — an unrecognized status is treated as non-terminal on purpose, to avoid flipping back to idle early) or on `task_notification` (belt-and-suspenders).
`summary().displayStatus` reads `'running'` instead of `'idle'` while the map is non-empty; every other `status` value passes through unchanged.
Reset on (re)spawn **and cleared in `_handleExit`** (a SIGKILLed CLI sends no terminal task frames), after `exit_cause` and before `_setStatus`, so the exit's status edge already carries zero tasks and the clear raises no task wake.
Node can fire `exit` before stdout drains, so the stdout reader passes `_handleStdoutLine(line, launchEnded)` its launch's exit latch: a `task_started` or `background_tasks_changed` read after it is still parsed and recorded but grows neither `_activeAgentTasks` nor `_backgroundJobs`.
`Instance.activeAgentTaskCount` exposes the live map size.
`IdleSubscriptionHub._onTurnEnd` **gates on TWO conditions**: a `turn_end` **defers** the idle wake (the armed wake and its heartbeat both stay armed) while **either** `activeAgentTaskCount > 0` (a subagent is still running) **or** `taskNotificationPending` is set — a `task_notification` fired *during* the turn now ending **and no top-level tool_result followed it**, which per the CLI's queue semantics means the notification is still queued and an unprompted **re-invocation turn** will deliver it.
Both cleared, the wake fires — so a wake means "the worker AND all its subagents finished, and no re-invocation turn is still owed."
`Instance._taskNotificationPending` (getter `taskNotificationPending`) mirrors the CLI's stdout-invisible message queue by event order: SET in the `task_notification` handler only when `status === 'turn'` (a completion while *idle* re-invokes immediately — that turn is its processing turn); CLEARED by any top-level (`parentToolUseId == null`) `tool_result` event — a sync-delivered task's own held-open result (fast Agent calls, long Bash promoted to a task, e.g. a full test run) or the outer tool round-trip the CLI attaches queued notifications to (batched flush) — by every idle→turn transition in `_setStatus` (the dequeued notification IS the new turn's input), and on (re)spawn.
Nested (subagent-forwarded) tool_results never clear it.

`Instance._queuedPromptPending` (getter `queuedPromptPending`) models the same queue for a PROMPT written into a running turn. The CLI folds such a message only at a top-level tool round-trip; with none before the turn ends it opens a new turn for it, so the turn's own `result` is followed by `system/init`, `system/status:requesting` and `message_start` before status returns to `turn`. A fold leaves no stdout frame (`--replay-user-messages` is not passed) and `result.queued_turn_count` carries no signal, so the flag is a model: SET by `prompt()` after the send when the instance was already in `turn`; CLEARED by any top-level `tool_result` (a fold), by every idle→turn transition in `_setStatus` (the queued turn started), on (re)spawn, and in `_handleExit` before the exit event is emitted. Measured over conductor session jsonls (wakes written into a running turn): every fold followed a top-level `tool_result` after the enqueue, and all but 2 of 106 queued-past-the-end wakes had none; the 2 exceptions were a second wake enqueued within about 200 ms of a `dequeue` that was starting a queued turn. Such a wake is not folded although a tool_result clears the flag — the hold releases early. A hold is never left stuck. Pinned against the CLI by `tests/mid-turn-queue-cli.real.test.mjs` (`RUN_CLI_CONTRACT=1`) and on fixtures derived from real captures by `tests/queued-prompt-pending.test.mjs` (`tests/fixtures/cli-queue/`). Every status-gated frontend control still keys off the real `status`; the cosmetic surfaces (sidebar dot, sub-agents strip, header chip) read `displayStatus`.

**Background Bash jobs (display + overage routing input).** `Instance._backgroundJobs` (`Map<task_id, {title, startedAt}>`, getter `backgroundJobs`, `summary().backgroundJobs`) is folded from each `system/background_tasks_changed` snapshot by `reconcileBackgroundJobs` (`src/backgroundJobs.ts`) and emits `status` on a membership change. Reset in `spawn()` with `_activeAgentTasks`; cleared in `_handleExit` before `_setStatus`, because a CLI killed outright sends no final snapshot. It never overlays `displayStatus` and is never read by `IdleSubscriptionHub.targetDefers`, `_waitsOnWork` or `isCaller` — a job never holds a wake. Its three readers: `IdleSubscriptionHub.deliver`, which renders the target's jobs into every non-heartbeat stub at build time (`backgroundJobsNote`), and `InstanceManager.list()`, which derives `waitingOnJob` per row with `jobWaiters` (a live instance with a job plus every live owner above it, via `ownersOf`), and `_routeOverageStop`, whose Pass 1 counts a job-waiting conductor as in control — both through `InstanceManager._jobWaiters()`. The client's `waitingOn(status, awaitingWake, waitingOnJob)` (`shared/needsYou.ts`) is the one precedence rule for the blue "waiting" state: idle only, a held wake wins. `background_tasks_changed` is outside `TASK_LIFECYCLE_SUBTYPES`, so an idle-time snapshot dirties the idle window like any other non-task event.

**Wake delivery gap (`_inFlight`, `_parked`).**
`IdleSubscriptionHub.deliver` sends on a microtask, after (for a folded stub) an async transcript read, so between a wake's consume and the CLI taking it in the conductor is idle with nothing armed.
`isCaller` — the predicate behind `awaitingWake`, the strip's "on a worker" state and `resumeRestart`'s resumable-work snapshot — therefore also counts wakes in `_inFlight` and wakes held in `_deferredWakes`.
`_inFlight` is incremented in `deliver` and released in its `finally` once `prompt()` has run and moved status off idle.
A send into a caller's RUNNING turn is not yet taken in: when the caller's `queuedPromptPending` is set after `prompt()` returns (read from the flag, not from the status at delivery time), the target id goes on `_parked` and the `_inFlight` count stays.
`_releaseParked` releases it when the flag has cleared — at the top of `onEvent` for every event of that caller (a top-level `tool_result` fold, the `system/exit` event) and in `onTurnStart` (the queued turn started) — or `purge` drops it.
A backstop bounds the hold: `_armParkBackstop` (called from the caller's `turn_end`) schedules a `PARKED_BACKSTOP_MS` timer per caller; if no release has cleared the parked entries when it fires, they are released through `_endInFlight` (so `subscription_changed` fires as for a normal release) and one stderr line on the caller says the backstop did it.
The timer is cancelled on turn start, release and `purge` (an exit releases first, which cancels it).
`PARKED_BACKSTOP_MS` is sized from wakes queued past a running conductor turn's end in conductor session jsonls: `dequeue` max 9.5 s and first reply of the queued turn p90 6.8 s. One flag covers every parked wake because the CLI folds all queued messages together: in the conductor session jsonls scanned, all 238 folds (runs of consecutive `remove` records at one tool round-trip) removed every message then pending, including 19 folds of 2 to 4 messages and none partial.
The scheduler (`_setTimer` / `_clearTimer`) is a field so tests fire the callback by hand.
`_endInFlight` emits `subscription_changed` when that leaves the caller with nothing armed, held or in flight; a heartbeat delivery counts too but emits nothing while the wake stays armed.
A delivery that throws against a caller that still has a process goes back on `_deferredWakes` with its note and options (before `finally` releases the count, so `isCaller` never dips) and is redelivered at the caller's next `turn_end` or `steer_settled`, or at `onPromptsUnblocked`; the stderr line says so.
A caller with no process drops the wake as before — its status is not `idle`, so it cannot read as finished.
After a refusal other than a rewrite, the wake therefore waits for that caller's next `turn_end`.
A caller whose `rewriteBlocksPrompts` is true (rewind, prune and the restart model switch hold `_mutating`) has the wake deferred up front rather than thrown at; `Instance._endMutation` ends each of those claims and emits `prompts_unblocked`, which `InstanceManager` wires to `onPromptsUnblocked` → `_flushDeferredWakes`.
A wake in flight TO a session also makes it `_waitsOnWork`, so that session's own owners stay held until the send has been taken in — or failed to a caller with no process, which releases them (`_releaseHeld`).
Without this the browser's attention tracker would see the conductor idle, un-waiting, with a counted turn end, and notify Finished on every worker hand-back.
Pinned by `tests/idle-wake-in-flight.test.mjs` (hub rig, backstop included), `tests/queued-prompt-pending.test.mjs` (real `Instance` stdout handler on fixtures plus `list()` end to end) and the `prompts_unblocked` cases in `tests/rewind.test.mjs`, `tests/prune-flow.test.mjs` and `tests/model-switch-restart.test.mjs`.
Not covered: the worker side of the same CLI rule — a conductor's mid-turn `send_prompt` that the CLI queues gives the worker a `turn_end` before its queued turn starts, and `targetDefers` does not read `queuedPromptPending`.

**Idle task-drain settle (the second wake path).**
A background task can finish while its worker is ALREADY idle with **no re-invocation turn ever following** (verified trace: a subagent's nested Monitor completed after the subagent — the stream's last lines were `task_updated` + `task_notification`, no `turn_end` ever re-sampled the gate, and the wake orphaned into an endless heartbeat).
`IdleSubscriptionHub._onTaskEvent` runs on every `task_updated`/`task_notification`: when a watched target is fully drained (`status === 'idle'`, `activeAgentTaskCount === 0`, `!taskNotificationPending`, `!idleWindowDirty`) it arms a **settle timer** (`ORCH_IDLE_DRAIN_SETTLE_MS`) recording the target's proc identity and `ring.nextSeq`; `_fireSettle` delivers the wake only if the subscription still exists, the SAME proc is live and still fully drained, and `ring.nextSeq` is **unchanged** — literally zero events since the arming task event.
The trap this must not reintroduce is waking ONE TURN EARLY: an idle completion that DOES get a re-invocation turn announces it with CLI-local `system/init` + `system/status` writes within ms of the notification, while the `message_start` that flips `status` to `'turn'` waits on the API (seconds — no settle length can safely outwait it).
Re-invocation evidence is therefore caught structurally on both sides of the drain event: **after the arm** by the frozen-seq check (init/status advance the ring before the timer fires → drop, the re-invocation's `turn_end` owns the wake), and **before the arm** by `Instance._idleWindowDirty` (getter `idleWindowDirty`) — SET when any non-task-lifecycle event (`TASK_LIFECYCLE_SUBTYPES` = task_started/updated/notification) is processed while `status === 'idle'`, CLEARED at `turn_end` and on (re)spawn — covering a task that drains *inside* another task's already-opening re-invocation window.
Every failed re-check drops the settle silently (the wake and its heartbeat stay armed): the fail direction is always "wake later via turn_end", never "wake early" or "wake twice".
The proc pin exists because respawn/rewind reuse the Instance AND its id but mint a new proc and reset the ring (`_wipeForResume`), making cross-run seq comparisons meaningless; history replay can't arm: the manager forwards `_emitUi`'s `replayed` flag on `'event'` and both hub registrations (`IdleSubscriptionHub`, `SessionRenewController`) skip replayed events — needed because `loadHistory`'s emit loop runs after an async transcript read and can land while the instance is already `idle` (a prompt sent while it was `spawning` whose turn ended first) — and it can't corrupt the dirty flag (replay bypasses `_handleStdoutLine`).
`_justConsumed` stays turn_end-only — it exists for `_isWaitingOn`, and a renewal expiry runs only in a turn_end dispatch.
Accepted residuals: a CLI stalling longer than the settle between the notification and init writes (consecutive process-local writes, normally sub-ms — the window never scales with API latency) would wake one turn early; non-task noise in an idle window with no turn following leaves only the heartbeat, same as before this path existed.
A **UI model switch** is now such noise: `system`/`model_changed` is retained, so a `setModel` landing inside the settle window advances `ring.nextSeq` and freezes the settle out.
The pre-arm `idleWindowDirty` guard cannot see it — that flag is set only in `_handleStdoutLine`'s loop, i.e. by subprocess stdout, and `setModel` emits through `_emitUi` directly.
Cost is bounded to **delay**: the subscription and its heartbeat stay armed, so the wake falls back to the heartbeat (`ORCH_SUBSCRIBE_TIMEOUT_MS`) or to the next `turn_end`, and `_fireSettle`'s contract — never early, never twice — is untouched.
Pinned by the characterization test named `characterization: a UI model switch inside the settle window delays the wake, never loses it` in `tests/idle-drain-settle.test.mjs`.
Rejected alternatives: declining the kind from the ring (kills the transcript notice on re-subscribe), emitting it seq-less on the `setModel` path only (asymmetric retention for one kind, and a re-subscribe loses the notice), and narrowing the freeze check by kind (it is deliberately event-shape agnostic, and weakening it to buy a human-timed race reopens the wake-one-turn-early bug).

**Ownership and awaitingUser.** The spawn-tree links and the sticky ask, on `summary()` (and so `GET /api/instances`, the `status` → `{t:'instances'}` broadcast, and `CONDUCTOR_VIEW_KEYS`). `summary()` reads none of them from a store — no migration.
- **Nudge-chain turns.** `Instance._turnNudgeChain` marks the current turn as part of an idle-renewal nudge chain (`src/idleRenewNudge.ts`). Every transition into `turn` resets it to false in `_setStatus`, so a CLI-initiated turn is always real; only three sends set it: `prompt(…, {idleNudge:true})`, `clearContext()` while the `_renewalNudgeChain` latch is set, and a `prompt()` whose text is a renew seed (`parseRenewSeed`) while the latch is set. Any other `prompt()` clears the latch, and a real prompt steered into a chain turn makes that turn real. The latch is copied from `_turnNudgeChain` at every `turn_end` while `renewalPending` (the turn that fires the `/clear`, and the `/clear`'s own), and `endRenewal()` clears it. At a chain turn's end, `liveTurnEnds`, `lastTurnError` and the unread `recordTurnEnd` write are skipped, and `_emitUi`'s live feed does not bump `liveAsks`; `lastResponseAt` still moves and `awaitingUser` is still reduced, so state is never suppressed. `lastTurnEndWasNudgeChain` (the flag snapshotted at the last `turn_end`) is what the controller reads. `_overageReportedUntilMs` / `overageReportedNow(now)` record the last live `rate_limit_event`'s `isUsingOverage` until its reset (unbounded when it names none), independent of the overage action, for the controller's overage skip.
- **Attention counters (`liveTurnEnds`, `lastTurnError`, `liveAsks`).** Live-only per-Instance fields on `summary()`, never hydrated and never reset (a reused Instance object keeps counting). `liveTurnEnds` / `lastTurnError` are set in the `turn_end` block of `_handleStdoutLine` BEFORE `_setStatus('idle')`, so the `status` emission that carries the idle flip already shows them; a turn a commanded stop interrupted (`_stopInterruptedTurn`) moves neither. `liveAsks` counts null→ask transitions in the `_emitUi` live feed only: hydration (`_hydrateAwaitingUser`) never counts, so a resume cannot fake a Waiting. The browser's tracker (`shared/attention.ts`) reads them; `turnEndSeq` cannot serve (written asynchronously, hydrated after launch).
- **Spawn-tree links (`rootSessionId`, `parentSessionId`).** `_doCreateResolved` resolves both ONCE, from the caller `spawnInstance` passes as `callerInstanceId`. `parentSessionId` is that caller's public sessionId. `rootSessionId` is the caller's own root when the caller is conducted, else the caller's sessionId (`rootSessionOf`). Resolving at create, rather than walking `callerInstanceId` on read as `agentTreeRoot` does, keeps a live grandchild attributed after an intermediate section lead has exited and left `byId`. `parentSessionId` then still names the exited lead, so a reader checks its liveness. By induction `rootSessionId` is a non-conducted session's id or null. `summary()` reports both only while `conducted && !isDeadStatus(status)`, and the exit `_setStatus` broadcast uncolours the row. A resume is a fresh create, so whichever conductor calls `spawn_instance({resume})` becomes both. A resume with no caller (UI/REST: sidebar row, notification, crash recovery) of a conducted session keeps the stored lineage instead: `parentSessionId` is the recorded `parent`, `rootSessionId` is `conductorSpawns.conductedLineage`'s `rootOf` chain, and `callerInstanceId` is the parent's live instance when `liveForSession(parent)` finds one (then the links equal a caller's). After a restart, conductors come back with no caller and re-form the links by re-resuming their workers; `adoptOwnedResume` (called from `spawnInstance` before `create()`) lets that `spawn_instance({resume})` take over a worker a user already resumed — conducted, recorded parent is the caller, no running owner — setting its `callerInstanceId`, `rootSessionId` and emitting `status`, and refuses nothing else. `parentSessionId` is also recorded as the session's `parent` (`markConducted`), which `conductorSpawns.rootOf` walks. `rootSessionId` is in memory only. Disk rows (`SessionRow`) carry neither.
- **awaitingUser (`awaitingUser` / `awaitingUserSource`).** The most recent ask with no REAL user message after it. A tool ask (`user_question`, or a `plan_request` not auto-approved) → `{kind, source:'tool'}` and always overwrites; a turn that ends `stop_reason:"end_turn"` with a final text that `isTextAsk` accepts (ends in `?` after trailing whitespace and markdown closers, or its last paragraph holds a word-bounded offer phrase — the list is `OFFER_PHRASE`) → `{question, 'text'}` only when nothing is pending; a real user turn → null. Never set on a conducted worker (`Instance._emitUi` feeds nothing when `conducted`).
- **The classifier (`classifyUserTurn`).** Its rules live in `isInjectedUserTurn` (`shared/promptOrigin.ts`), which the browser's sticky prompt header shares. Injected, i.e. leaves the ask alone: a `cliInjected` echo (skill content, compaction continuations, hook feedback — `isCliInjectedLine`, `src/parser.ts`); a leading `WAKE_CALLBACK_MARKER` (every wake stub and heartbeat); a leading `IDLE_NUDGE_MARKER` (the idle-renewal nudge); a renew reseed (`parseRenewSeed`); `RENEW_REQUEST_LEAD`; `FORWARD_FRAME_HEADER`; `RESTART_NOTICE_TRUNK` (both restart notices); `RESTART_ABORTED_LEAD`; an overage preamble WITHOUT the `QUEUED_SECTION_LEAD` section; `/clear` in both recorded shapes; `/effort ` and its `<command-name>` shape; `<local-command-stdout>`. Everything else is real — the composer, both answer cards, the rebase button, a queued overage resume, and `buildApprovePrompt` (so an auto-approved plan, never set live, also ends null on disk). **Limit:** an MCP send into a conductor or a hand-spawned session (`send_prompt`, `answer_question`, `approve_plan`, `reject_plan`) is byte-identical to the user's and reads as real; workers never carry the flag, so only a non-worker driven over MCP can be cleared early.
- **Live feed.** `LiveAskFacts` takes tool asks from both arms — the streamed `user_question`/`plan_request` and the reconciled `assistant_message` envelope, which the CLI sends first — once per `toolUseId`; the envelope arm reads `Instance._planAutoApproves()`, the same rule the plan_request auto-approve gate reads. The final text is the last text block of the turn's last message, from either arm. Buffers reset on every transition into `turn` and at `turn_end`.
- **Hydrate + replay.** `Instance.launch()` derives the pre-launch state on every non-fresh launch that passes its pre-spawn refusal checks (every resume, respawn, rewind, prune relaunch, resume-after-restart) from `chainEndingAt(this._segments, resume ?? this.backingSessionId)` — the newest segment scanned last, never twice. `loadHistory` then replays through `_emitUi(ev, {replayed:true, pullOnly})` (`pullOnly` whenever a `history_replayed` follows; wsHub withholds only `pullOnly` events from the sockets — the ctx-seed `message_start` is `replayed` and still goes out live), which the feed ignores: a replayed real `user_echo` would otherwise clear the hydrated ask, and replay carries no end-of-turn to restore it. A per-event tag, not a time window, so live stdout interleaving with the replay still feeds. The transcript scan owns everything before launch, the live feed everything after.
- **Disk scan (`deriveAwaitingUser`).** Segments newest→oldest, each scanned backward in `CHUNK_BYTES` chunks, stopping at the first decisive fact (tool ask or real user turn) — the summary algebra (`const(v)` / `inherit(c)`, `c` the oldest text ask) is what makes the backward stop and the segment composition exact. Every line goes through `replayPersistedLine` in isolation, so the scan sees what a replay does (queued_command prompts, task-notification drops, the mid-turn note, the sidechain skip, the `cliInjected` stamp). The end of a turn is read off the raw line: `isSidechain` lines are dropped first, a run of `assistant` records sharing `message.id` is one message, and only the run's FINAL record's `stop_reason` counts (earlier per-block records carry absent, null or duplicated values depending on backend); `end_turn` yields one endTurn fact carrying the run's last text block. Non-conversational lines (attachments other than `queued_command`, snapshots, markers) break no run. **Memo:** process-lifetime, keyed by absolute path: unchanged `dev/ino/ctime/mtime/size` → hit; same inode grown → scan from `scannedTo` (the start of the trailing assistant message — never taken as finished whatever its newest record's `stop_reason`, since a later record of the same `message.id` may extend it — else the end of the last complete line) and compose over the memoised prefix; anything else → full rescan. An incremental read therefore always equals a full scan of the same bytes. **Cost bound:** `listSessionsForCwdWithCounts` derives only `!conducted && !archived` rows (every exited conductor is normal and so archived); `sessionRowForCwd` (`describe_session`'s retired branch) also derives an archived row — never a conducted one. The segment chain comes from the already-loaded `Lineage` (`liveSegmentIdsOf`), never a per-row store read.
- **Named residual.** Live evaluates the text ask at `turn_end`, disk at each `end_turn` message; they differ only if the CLI continued a turn past an `end_turn` message without a `result` — not observed.
- **Prompt authorship (`user_echo.author`).** A conducted worker's prompt records who wrote it — `human` (the WS `prompt` frame, the rebase-prompt route) or `conductor` (the MCP sends, the targeted renewal request, a followUp-carrying reseed) — as a trailing marker block (`src/promptAuthor.ts`; site list in [protocol/subprocess.md](protocol/subprocess.md) → the `user` row). Gated on `Instance.conducted` inside `Instance.prompt`, which `_doCreateResolved` re-acquires on resume, so a resumed worker keeps writing markers. The block is persisted by the CLI with the line, so a retired or restarted worker's transcript still says who wrote each prompt; an unmarked line (a server- or CLI-injected prompt, a non-conducted session's) is **unknown** — nothing falls back to `promptOrigin` or text shape, and no migration exists because cc owns no changed format. A parked steer keeps its author (`PendingSteer.author`), as does an overage-queued send (its `_overageQueue` entry); a coalesced delivery takes `combineAuthors`. The idle hub collects the human ones per target (`_humanPrompts`, under [`src/idleSubscriptions.ts`](components/instances.md#srcidlesubscriptionsts)) for the owner's wake notice and the send-time field. **Known limit:** a hand-spawned session a conductor later dispatches to is not conducted, so it gets no marker and its owner gets no human notice.
- Pinned by `tests/awaiting-user.test.mjs` (classifier drift gate over every builder's output, reducer, algebra, live dedupe), `tests/awaiting-user-agreement.test.mjs` (live feed == transcript scan over `tests/fixtures/awaiting-user/`), `tests/awaiting-user-transcript.test.mjs` (scan, memo, row cost bound), `tests/awaiting-user-live.test.mjs` and `tests/session-ownership-live.test.mjs`.

│   │       │                                 #   anything here at boot is dead by construction.

│       │                                 #   control socket below (a local fake remote, no transport)
│   │       ├── fusectl/                      #   fusectl, namespace-local — NOT /sys/fs/fuse/connections
│   │       ├── pins.txt                      #   the tier table, generated by tierTable.ts
│   │       ├── intent.json                   #   written by cc BEFORE spawn: a crash before the handshake is recoverable

A project is a RECORD. Nothing under the projects root is listed because it is there — which is what lets the root hold container directories, cc's own dotfolders and a worktree area without any of them surfacing as a project, and what lets a project's tree live anywhere else instead. A record cc cannot parse still lists, with an empty path and a `degraded` reason.

Orchestrator state stays in the central store; the only cc-written file inside a project tree is every project's tracked, app-regenerated `CONVENTIONS.md` (`src/projectClaudeMd.ts`) — imported by its `CLAUDE.md` and committed with the project (its line-1 marker is the self-describing source of truth). That holds for an adopted target too, git repo or not: it is written at adopt time, on every sweep and by an **Edit conventions…** save (on any project), landing in the user's own tree — as an uncommitted change where that tree is a repo. Creation also makes the tree a git repo (`git init`, when git can) and commits what it scaffolded — that `.git/` is git's own, not cc-written state. Adoption commits nothing. No per-project `.gitignore` plumbing.

## Migrations
`migrations/` holds idempotent migration scripts run automatically on boot (entrypoint `migrations/index.mjs`).
The most recent, `0043-persistent-sessions`, rewrites `sessions.json` and its `.bak` from `temp` on normal segments to `persistent` on persistent ones (an archived segment is persistent iff its record's current segment is live and was not temp) behind an in-file `version: 2` marker, after copying both to `<store>/migrated-backup-0043/` once; converts the `temp` field of `pending-resume.json` / `running-sessions.json` entries to `persistent`; and renames `pending-temp-cleanup.json` to `pending-archive.json`.
Before it, `0042-remove-mcp-client-dir` moves a leftover `<store>/mcp-client/` (the retired generated clients) to `<store>/migrated-backup-0042-<ms>/mcp-client/`; absent → a no-op.
Before it, `0041-event-log`, converts `<store>/playbook-ledger.jsonl` into `<store>/events.jsonl` row for row in file order (mapping in its header) and moves the old file to `<store>/migrated-backup-0041/`; an `events.jsonl` byte-identical to its conversion (a crash before the move-aside) completes the move.
A `playbook-ledger.jsonl` that reappears once `events.jsonl` and the backup both exist — an old server's late writes during the upgrade restart — is moved, unconverted, to `migrated-backup-0041/playbook-ledger.straggler-<ms>.jsonl` and boot continues — unless it converts to any `bind`, `move` or `config` row, which aborts boot for a hand resolution, as does an `events.jsonl` that differs from the conversion with no backup yet.
Before it, `0040-plugin-autostart-flag` adds `autoStart: false` to every `plugins/registry.json` record lacking a boolean one; a corrupt registry is left to its loader.
Before it, `0039-unified-session-store` merges the per-session files into `<store>/sessions.json` keyed by public id and moves them to `<store>/migrated-backup-0039/`; its own header is authoritative (merge rules, known limits).
Before it, `0038-rename-wiki-plugin-id` re-keys the wiki plugin's id `code-karpathy-wiki` → `code-wiki` in `plugins/registry.json`, `plugins/runtime.json`, the conventions `disabled` lists, `settings.json` `models.roleBackend`/`roleEffort` and each registered local project's line-1 `CONVENTIONS.md` marker.
It defers (writes nothing) until the plugin's main-checkout `conductor.plugin.json` declares `code-wiki`, and the old registry key, removed last, is its done-flag; its own header is authoritative.
Before it, `0037-project-location-records` gives every project a stored `location` and moves what the old layout implied — local worktree checkouts under `<root>/.worktrees/<project>/<key>`, Library plugin installs under `<root>/.plugins/<name>` — with a two-class error taxonomy, a ledger for what it could not move, a fixed-path snapshot and a completion marker; its own header is authoritative.
Before it, `0036-temp-cleanup-manifest-place` clears the placement of any pending-temp-cleanup entry written while the manifest persisted a bare `cwd`: the sweep now needs `{ system, remoteId, cwd }` to name a subagent directory, and a placement cannot be invented — guessing one could delete a different remote's. The sweep's existing placeless branch degrades to bookkeeping only, so the loss is at most one orphaned subagent directory per temp session in flight across the upgrade.
Each self-checks "already applied?" and is a fast no-op in steady state; a script that throws **aborts the boot**.
See [`migrations/migrations.md`](../migrations/migrations.md) for the listing and conventions for adding new ones.

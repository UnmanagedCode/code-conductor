# Features: the UI, projects and workspaces

## The UI
- **Serving** — the React UI (`web/`) is served at `/`, built into `web/dist` at server start when its inputs changed (see [components/web.md](../components/web.md#srcwebbuildts) → `src/webBuild.ts`). Until the server's first build exists, `/` shows a self-refreshing "Building the interface…" page. A rebuild, or a failed one, keeps the previous build serving; a failure with no build in place shows its error instead, and the API stays up. In the rare case that a failed swap cannot put the previous build back either, none is left and the error shows.
- **PWA and service worker** — the manifest (`web/public/manifest.webmanifest`) has `start_url` and `scope` `./` and no `id`, so the app's identity is `/`: an installed app keeps that identity and updates in place. The service worker (`web/public/sw.js`) is registered as `/sw.js` with scope `/` at boot, notification permission or not (`registerServiceWorker` in `web/src/features/notifications/notifications.ts`) — one registration at the root, which a browser that already holds it updates in place. A click on one of its notifications with no open tab opens `/#session=<sid>`. The manifest `<link>` in `web/index.html` carries `crossorigin="use-credentials"`: Chrome otherwise fetches the manifest with credentials omitted, so a host that gates every request (a code-hub share's cookie/Basic gate) answers it 401 and the app is not installable. Installing needs a secure context (HTTPS or loopback).
- **Logo** — one drawing, rendered by `web/src/components/logo/Logo.tsx` from `logoArt.ts` beside it; its knockout gaps are transparent (SVG masks), so the surface behind shows through on any background.
  - **Sidebar header** — the logo tile (`LogoTile`) and the outlined wordmark in place of the title text; the `<h1>` (or the app switcher's trigger) keeps a visually hidden "Code Conductor", so it still reads as that.
  - **Landing and empty chat** — the mark (`LogoMark`): its `_` cursor blinks while the WebSocket is open and holds still, visible, while connecting or reconnecting (`LiveMark` in `web/src/features/session/SessionView.tsx`). Under `prefers-reduced-motion` it never animates.
  - **Static elsewhere** — Settings → About shows the lockup (`LogoLockup`: mark + wordmark, as its heading), the app switcher's Conductor entry the 16px favicon art with its white terminal face (`LogoSmall`); neither animates.
  - **Favicons** — `favicon-16.png` and `favicon-32.png` (light palette) plus `favicon-16-dark.png` and `favicon-32-dark.png` (dark palette, white baton), transparent background; `index.html` links each with its `sizes` and a `prefers-color-scheme` media query, so the browser picks the set by the OS theme and the size by device pixels. The PWA icons (`icon.svg`, `icon-*.png`, `apple-touch-icon.png`) draw the mark on the manifest's background colour. All are generated: see [components/web.md](../components/web.md#web) → `web/public/`.
- **Settings layout** — the Settings column is the session width (see **Session width** below); the no-overflow sweep includes the floor, Full and a Wide column. The Settings section nav stays reachable at every sidebar width: beside the content when the Settings column has room, as section pills above it otherwise. **No Settings section** overflows its column at any sidebar width: two-column forms and catalogs follow the Settings column's width, not the viewport's, and long ids, names and links wrap. In **Settings → Models** every tier and role select is captioned with a word its accessible name contains, and every control stays clear of its neighbours.
- **Toasts** — results and refusals (a Sync's outcome, a failed restore) show as toasts at the top, below the view's top bar at every width, so a toast never covers a top-bar control. Each is announced through the polite **Notifications** live region (Alt+T moves focus into it), stays while the pointer rests on it or after Alt+T has moved focus into it (a toast reached by Tab keeps its timer), and is dismissed by its **Close toast** button or a swipe; otherwise it leaves on its own. Tab moves through a toast (the toast, then **Close toast**) and on in page order. Closing a toast that holds focus returns focus to where it came from, and leaving a toast visited with Alt+T returns focus to where Alt+T was pressed.

## Projects & workspaces
- **Project list** — STORE-DERIVED: the sidebar shows one row per record under `<store>/projects/`, and nothing else. A directory under `<projectsRoot>/` is not a project until it is registered, which is what lets the root hold container directories with projects nested inside them at any depth. A record cc cannot parse still lists, with an empty path and a `degraded` reason — invisible would also mean undeletable. `+ New project` creates a dir, `git init`s it (when git cannot make a repo — git missing, or the init fails — the project is created as a non-git project and the create-confirmation pane shows why; worktrees need `git init` plus a commit first), seeds `CLAUDE.md` containing exactly `@CONVENTIONS.md` — the import of the regenerated in-project conventions file that carries both workspace and project conventions (see **Conventions** in [settings.md](settings.md#settings-page-and-app-controls)), written whether or not any project convention was picked — then commits both files, so the project is worktree-ready with no first commit needed. The commit uses the repo's configured `user.name`/`user.email`, substituting `code-conductor <code-conductor@invalid>` per field only where one is unset (`-c` on that one command; nothing is written to any git config). A global `core.excludesFile` cannot drop a scaffolded file from it (creation force-adds exactly what it wrote). A commit that cannot be made — a refusing hook, a broken signing key, or a git that resolves the new directory to some other repository — is a `console.warn` and leaves the project created with an unborn HEAD; creation never fails over it, and never commits into a repo it did not just create. Nothing has to be filtered out of the list: a worktree checkout, a container directory and cc's own dotfolders all lack records. The list also carries every project placed on a **system** (see **Projects on a system** below).
- **The list follows API changes** — a project, workspace or worktree created, changed or removed after the page loaded shows without a reload, whoever made the change: the UI, REST, or a conductor's MCP project, workspace and worktree tools. A created or adopted project gains its row, a deleted one loses it, a workspace assignment, rename or removal regroups the list, and a worktree appears or goes under its project. The UI re-reads the list on the server's `{t:'projects'}` hint ([protocol](../protocol/websocket.md) → WebSocket protocol) and drops a re-read that answers after a newer one has landed (`refreshProjects` in `web/src/app/controller.ts`).
- **Project row menu** — each project row, in both lenses, ends in one **⋮** (`ProjectMenu` in `web/src/features/sidebar/ProjectMenu.tsx`, on the shell every sidebar row menu shares — `RowMenu` in `web/src/features/sidebar/RowMenu.tsx`, whose items are its children), holding, in order, **New session**, **Edit conventions…**, the enabled plugins' project-scope `menuItems` (a plugin with one such item is a flat entry with its icon and a muted trailing plugin tag, all behind one separator; a plugin with more keeps a separator-led group, its label over its buttons, after them; a click opens that plugin's frontend with the project in its query, in the dock when one shows, else full view — [plugins/manifest.md](../plugins/manifest.md) → `menuItems`), a separator, then **Delete…**. New session opens the same spawn dialog the worktree menu's **New session in this worktree** opens, without a worktree preset. On a row whose project cannot be resolved (`systemUnreachable`, a malformed record included), New session and Edit conventions… are **disabled with the reason** as their tooltip; Edit conventions… is also disabled, with the read error, when the project's `CONVENTIONS.md` could not be read. Delete… is always enabled. A **warning dot** on the ⋮ (`data-conventions-attention`, `conventionsNotice` in `web/src/features/sidebar/conventionsNotice.ts`) flags a project whose selection is **unset** — never chosen ("No project conventions chosen yet.") — or names a slug the catalog **no longer has** ("Selected conventions no longer available: …"); a project that **chose no project conventions** is not flagged; the notice is the ⋮'s tooltip and accessible description, the ⋮ then stays visible without hover, and the Edit conventions… item carries a dot too. In the Conductors lens the ⋮ shows on a project the project list holds; a chip project missing from that list renders its name alone, with no ⋮ and no system pill.
- **Worktree row menu** — each worktree row ends in one **⋮** (`WorktreeMenu` in `web/src/features/sidebar/WorktreeMenu.tsx`), holding **New session in this worktree** (the spawn dialog preset to the worktree), the enabled plugins' worktree-scope `menuItems` (flat entries and groups as in the project menu, opened as in the project menu, with the project and the worktree in the page's query), a separator, then **Remove worktree…** (destructive: the confirm, then a force-remove confirm on a 409, via `removeWorktree` in `web/src/app/sessionActions.ts`). On a project whose system cannot be reached (`systemUnreachable`), New session in this worktree is **disabled with the reason** as its tooltip; Remove worktree… is always enabled. The ⋮ is hover-revealed on a pointer device and always visible on touch. The row itself carries `≡` Commit history, the name, the ahead/behind pill, 🔒 and `← base`. In the Conductors lens the ⋮ shows on a worktree the project lists; a worktree known only from a live worker's instance has none.
- **Delete project** — **⋮ → Delete…** per row opens the confirm dialog (`DeleteProjectDialog` in `web/src/features/dialogs/ProjectDialogs.tsx`): a typed-name confirm plus an **off-by-default** "also delete the project directory" checkbox, naming the literal path it would remove. **DELETE MEANS DEREGISTER**: the record goes and the tree stays unless that box is ticked, and the box is **absent** for a project on a system — cc removes its record of a tree on another machine, never the tree (`deleteDirectory:true` there is refused **400**). One behaviour for every project, whichever way it was registered. For a project on a system the confirm dialog reads **Unregister** and names what it leaves in place on the system.
  - The cascade kills instances, then removes every worktree **with the ordinary guards** — a worktree that is dirty, dirty-unknown or depended-on **refuses the whole delete 409**, and nothing is force-removed under the user. A checkout that is not there, or whose parent is no longer a repo, has no uncommitted work to lose: its registration is dropped rather than refused, so a project whose tree vanished out-of-band is still deletable.
  - cc's own area for the project always goes: `<store>/projects/<name>/` and `<projectsRoot>/.worktrees/<name>/`. Session jsonls are left intact, but WHERE differs: a local project's stay at `<configDir>/projects/<encoded>/` and remain resumable by the standalone CLI, while a system-placed project's stay under that target's own cc-owned transcript root (`<store>/claude-config/<dirName>/.claude/projects/`), which the standalone CLI does not read — re-registering the project at the same placement is what reaches them again. Response: `{ok, project, killedInstances, system, remoteId, path, directoryDeleted}`.
- **Adopted projects** — a directory that already exists anywhere on disk becomes a project — a git repo or not — without being copied or moved. Sidebar ≡ → **+ Add project**, MCP `adopt_project({name, path, system?, remoteId?})`, or `POST /api/projects/external`. **Nesting under the projects root is legal**: a container directory there can hold projects at any depth, and only the ones adopted are projects.
  - **Layout** — the record at `<store>/projects/<name>/project.json` carries `location: {kind:'local', path}` and IS the registration. Nothing else is written outside the store.
  - **The Adopt dialog** (`AdoptProjectDialog` in `web/src/features/dialogs/ProjectDialogs.tsx`) — opened from the sidebar ≡ overflow panel. **Name** + **System** + **Directory**, plus a list of suggested directories from `GET /api/projects/suggestions`. The list is an **input helper for the Directory field**: clicking a row fills Directory (and Name, from `suggestedName`), and Submit always POSTs whatever is in the field — so adopting a path from anywhere on disk is the *same* action, typed rather than clicked, not a second flow.
    - **Where the tree lives** — the **System** picker offers the built-in **This machine** (the default) plus every registry row with a provider command, and choosing one reveals an optional **Remote** (the target's name; blank for the provider's default) — a dropdown when that system's provider lists its configured targets, free text otherwise, exactly as `+ New project` does (see **The Remote field** under **Projects on a system**).
      Directory then means a path on that machine, so **changing the machine empties Directory** — a path on one machine is not a path on another, whether it was typed or clicked out of the list — and the suggestion list is **hidden** with its note retargeted to *Type an absolute path on remote 'r' of system 's'.*, because the scan is of cc's own disk.
      The Directory field itself **completes directories on whichever machine is chosen** (`web/src/features/dialogs/PathInput.tsx`, `GET /api/fs/dirs`): after a short pause it lists the subdirectories of the text up to the last `/`, filtered by what follows it, and typing within a directory already listed makes no new request.
      **Tab** completes the first item (or the arrow-selected one), **Enter** completes the arrow-selected one (with none selected it submits as usual), a click completes the row, **↑/↓** move the selection, and **Esc** closes the list before it would close the dialog.
      Dot-directories are offered only once the typed name starts with a `.`.
      A symlink cc could not confirm is a directory is shown **muted** (it may be a file).
      If the system cannot be listed the reason appears under the field (a refusal about the path is remembered for that directory; a momentary one — timeout, lost transport, unreachable system — is retried on the next keystroke there) — the field stays editable and Submit still works — and a directory with more entries than the cap says so.
      Changing the system or the remote discards what was listed.
      A Windows-style path gets no completion.
      A **relative path on a system is refused in the dialog**, before any request; a relative path with no system is left to the server, so a local adopt surfaces the server's own refusals, and a local adopt posts only `{name, path}`.
      If the registry cannot be read the dialog **says so**, naming the server's reason, else its status, else the unreachable server (*Could not read the systems registry (HTTP 503) — only this machine is offered*) and still offers this machine — a registry that answers with only the local row says nothing, so "cc could not ask" and "nothing is registered" are distinguishable.
    - **What the scan offers** (`src/projectSuggestions.ts`): unregistered directories under the projects root, `SUGGEST_MAX_DEPTH` levels deep, `.git`-bearing ones ranked first then `relPath` ascending. Five rules, each derived from a refusal `adopt_project` would otherwise answer: **dot-prefixed directories are skipped** (which is what keeps the store, `.worktrees`, `.plugins` and `.conduct` out — there is no second exclusion list); a **registered project is skipped AND not descended into**; the walk **stops descending at a `.git`-bearing directory** (every descendant is `TARGET_INSIDE_REPO`); **symlinked entries are neither offered nor followed**; and breadth is bounded by `SUGGEST_MAX_DIRS`, with `truncated` and `unreadable` surfaced in the dialog's scan note so an absent directory is not read as "cc looked and it is not adoptable". No `git` is run — a `.git` stat answers both the ranking and the stop-descend rule.
    - **A stale record** (`PROJECT_EXISTS_STALE`) swaps the dialog to a second pane naming the path the record still points at and the three `discards` counts, with **Relocate** / **Replace** re-sending the same target as `onStaleRecord`. A `PROJECT_PLACEMENT_IN_USE` refusal of a Relocate is rendered **on that pane**, so Replace stays one click away.
    - **Refusal wording** — every `reason` is shown to the user and a bare `code` never is. Two are reworded, because the server's remedy clause is written for an API caller: `TRANSCRIPT_DIR_COLLISION`'s "Pick another name." becomes "Pick a different directory…" (the transcript directory is keyed on the cwd, which the project name never enters, so renaming cannot help on the adopt path), and `PROJECT_PLACEMENT_IN_USE`'s "pass `onStaleRecord:'replace'`" becomes "choose Replace below". Each replacement is keyed on a byte-exact tail of the server's sentence and **replaces** that clause rather than stacking a second remedy; a sentence that no longer matches renders verbatim.
  - **A corrupt record does not strand its directory.** A `project.json` that cannot be parsed lists as a degraded row with an empty `path` — which names no directory, so it suppresses nothing in the scan and nothing in the transcript-key guard (`registeredPlaces` skips it for the same reason). Its tree is therefore **offered as a candidate, and adopting it under a free name succeeds**: that is the recovery, not a hazard. The degraded row stays listed and stays deletable (`getProjectForDelete` tolerates a record it cannot read), and re-using the corrupt *name* is refused `PROJECT_EXISTS` naming that repair.
  - **Paths are REALPATHS.** `resolveProjectDir` / `getProject` (`src/projects.ts`) hand back the target's realpath, never a symlink, and `list_projects` / `GET /api/projects` report that. Load-bearing: the Claude CLI encodes its `<configDir>/projects/<encoded-cwd>/` session dir from `getcwd()` (always the realpath) and walks `CLAUDE.md` upward along the realpath, with no env lever — a logical-path project would strand every resume. `<configDir>` is `~/.claude` for a local place and the target's own cc-owned config directory for a remote one; the cwd half is what this bullet is about, and it is the same either way.
  - **Refusals** (returned as `{ok:false, code, reason}`, never an error):
    `INVALID_NAME` (bad charset, or dot-leading — reserved for orchestrator-managed projects, which is what stops an adopted project shadowing `.conduct`), `INVALID_TARGET_PATH` (not a non-empty absolute path), `TARGET_NOT_FOUND`, `TARGET_NOT_A_DIRECTORY`, `TARGET_ALREADY_MANAGED` (already registered under another name, or the target CONTAINS the projects root), `TARGET_IS_CC_STATE` (inside `<store>`, `<projectsRoot>/.worktrees/` or `<projectsRoot>/.plugins/`), `TARGET_INSIDE_REPO` (a *subdirectory* of a git repository — `reason` names the toplevel it found), `TARGET_NO_WORK_TREE` (a bare repository, or a repo's own `.git`), `TARGET_DUBIOUS_OWNERSHIP` (git refused the repository because a different user owns it — `reason` carries the `safe.directory` fix), `PROJECT_EXISTS` (the name is held by a project whose path still resolves), **`PROJECT_EXISTS_STALE`** (the name is held by a record whose path no longer exists — carries `heldPath` and `discards:{attachments,debug,worktrees}`; re-call with `onStaleRecord:'relocate'` to repoint that record and keep its stored state, or `'replace'` to discard the state and register afresh; a `relocate` of a project **on a system** is itself refused `PROJECT_PLACEMENT_IN_USE` while it has registered worktrees — a remote worktree derives its path from its parent's and its checkout does not move, so the two would diverge permanently), **`PROJECT_EXISTS_UNRESOLVABLE`** (the name is held and cc could not ask whether it still resolves, so it cannot tell a moved project from a machine that is merely down — relocation is not offered), `INVALID_STALE_ACTION`, **`TRANSCRIPT_DIR_COLLISION`** (the transcript directory the project would use is already held — see **Two places cannot share one transcript directory** below;
    `reason` names the holder), `SYSTEM_UNREACHABLE` (the named system could not be resolved, or stopped answering mid-probe — this also carries `SYSTEM_NO_REMOTES` / `REMOTE_NOT_FOUND`), `INVALID_REMOTE_ID` (unusable, or given without a `system`).
    Every check runs before the record is written, so a refused adopt leaves nothing behind.
  - **cc writes into the adopted directory, at adopt time.** `<target>/CONVENTIONS.md` is created/overwritten with the composed document (app-owned, no sentinel), and `<target>/CLAUDE.md` gains an `@CONVENTIONS.md` line — prepended, every existing byte kept below it; already present ⇒ no write at all. That is the only channel the workspace conventions have, so it is unconditional and not skippable; **in a git target both land as uncommitted changes in the user's repo.** Recomposition is a pure function of the selections, so repeat sweeps are byte-identical and a git target is dirtied exactly once.
  - **Undoing an adopt** — take both writes back: delete `CONVENTIONS.md`, and remove the `@CONVENTIONS.md` line from `CLAUDE.md`, or delete `CLAUDE.md` if adopt created it (it creates one when absent). In a git target, `git checkout --` the paths adopt overwrote and `rm` the ones it created; name only pre-existing paths, since a pathspec matching nothing in HEAD aborts the checkout and restores neither. In a non-git target it is the deletion and the line removal by hand. Deleting only `CONVENTIONS.md` leaves a dangling import.
  - **Worktrees live in cc's own area** — `<projectsRoot>/.worktrees/<project>/<key>`, wherever the project's tree is: cc owns that directory, and the user's parent directory is not cc's to scatter checkouts in. They never surface as projects — nothing without a record does.
  - **A vanished target still LISTS** — resolution is a record read, so a project whose tree was unmounted, moved or deleted keeps its row (its git facts go unknown) and stays deletable. Re-adopting the name at the new path answers `PROJECT_EXISTS_STALE` with the two repairs.
- **Projects on a system** — a project's tree, git repo and shell commands can live on a registered **system** (Settings → Systems) instead of on the machine cc runs on. A third placement: neither in-root nor adopted.
  - **A system is an endpoint; a TARGET is what it serves.** One registered system can serve many targets — one `docker exec` provider talks to the daemon on behalf of every container — so ten containers are one Settings row and one provider process, not ten of each. Which target a project is on is chosen **per project**, by its `remoteId`, and all three of `(system, remoteId, path)` together identify a tree: the same path on two targets of one system is two different projects. **Absence of `remoteId` means the provider's own default target**, exactly as absence of `system` means cc's own machine.
  - **Creating one** — `+ New project` offers a **System** picker (the built-in **This machine**, the default, plus every user row that has a provider command — a row with none is skipped, since a project on it could never be opened) and, when one is chosen, an optional **Remote** (the target's name — a container name, a hostname, a VM id; left blank for the provider's default; see **The Remote field** below) followed by the absolute **path on that system** (required: cc has no default location on another machine) (which **completes directories** on that system, on the chosen target, exactly as the Adopt dialog's Directory field does). The `mkdir`, `git init` (where git is available) and seed files all happen there; under the projects root there is no tree and no directory — only the `<store>/projects/<name>/` record, which IS the registration, exactly as for a local project. Adopting an existing tree on a system is the same **System** + **Remote** pair in the Adopt dialog (≡ → **+ Add project**), `adopt_project({name, path, system, remoteId})`, or `POST /api/projects/external` — every check (realpath, directory, enclosing-repo + work-tree) runs on that target.
  - **The Remote field** (New project and Add project alike; in New project it sits above the path, which completes against the target it names) — choosing a non-local system asks `GET /api/systems/:id/remotes` which targets that system's provider is configured for; choosing **This machine** asks nothing.
    - **The provider lists them** → a **dropdown**: an unsubmittable *— choose a remote —* placeholder, one option per listed `remoteId` in the provider's order, and **Other…**, which reveals the free-text field for a target it did not list. A target already typed before the list arrived stays selected under Other…. A list with no targets still shows the dropdown (placeholder + Other… only) with the note *System 's' lists no configured remotes right now — choose Other… to type one.* Submitting with the placeholder, or with Other… left blank, is **refused in the dialog**, before any request — leaving the field blank for the provider's default is a free-text affordance only.
    - **The provider does not list them** (it does not advertise remote listing) → the **free-text field**, as before, with nothing said.
    - **The enumeration failed** (the system is unreachable, the provider answered an error, or its list was invalid) → the free-text field, with the note *Could not list the remotes of system 's' (<reason>) — type one.* — never an empty dropdown.
    - A listed id is one the provider is **configured** for, not necessarily reachable; a typed one is verified at create/adopt time either way. Every choice of a system asks afresh, and an answer for a system no longer chosen is dropped; reopening a dialog resets the field to free text, empty, with no note.
  - **Changing the target** — `set_project_remote({project, remoteId})` / `PUT /api/projects/:name/remote`, or the **Change target** dialog behind a remote project's **system pill** in the sidebar (the pill reads `<system>/<target>`; it is a control only when the system is reachable, since the change verifies the new target there before persisting). On the provider's default target it reads the bare system id, and its tooltip says where the tree, repo and commands live. `remoteId:null` (or `""`) clears it back to the provider's default; **omitting the field is refused**, not read as a clear. It is **refused 409 `PROJECT_PLACEMENT_IN_USE`** while the project has live sessions or registered worktrees, and the refusal **names whichever of the two is blocking** (the parts are `Boolean`-filtered, so a project blocked only by worktrees is not told about sessions) while the 409 BODY always carries both `instances` and `worktrees` arrays — kill the sessions and delete the worktrees first; nothing is discarded for you. A permitted change leaves no cc-owned copy of the old target behind — there is none to leave, so the clobber a stale local root once made possible is unreachable rather than cleaned up.
  - **`remoteId` is not a slug** — container names, hostnames and VM ids legitimately carry `_` and `.`. It must be non-empty after trimming, at most `REMOTE_ID_MAX` characters (`src/systems/protocol.ts`), and free of whitespace and control characters. A `remoteId` with no `system` is a 400: cc's own machine is one machine.
  - **Layout** — the record IS the registration: `<store>/projects/<name>/project.json` carries `location: {kind:'remote', system, remoteId, path}`. No directory. Names stay globally unique, and the same path on two different targets is two different projects.
  - **Worktrees** — created **on the system**, at that system's `worktreesDir` when Settings → Systems sets one, else `<dirname(project path)>/.worktrees/<project>/<key>`: cc owns no area on another machine, so the default sits beside the tree that is already there. Same `<root>/<project>/<key>` shape as the local layout — no per-kind exception.
  - **What works** — worker sessions (below), the project list and its git facts, worktrees, diff, status, merge, sync, the **in-tree** `post-worktree-create.sh` and `post-worktree-merge.sh` hooks, conventions materialisation, and every `project_*` tool.
  - **What does not** — `project_bash` runs in a plain login shell there (claude's own restored shell bundle is a file on cc's machine). A **store-sourced** `post-worktree-create.sh` or `post-worktree-merge.sh` is skipped with `STORE_HOOK_LOCAL_ONLY` in its own report (a skipped merge hook still leaves the merge landed, `ok: true`) — it lives under cc's store, and putting a cc-owned file on the system is a later phase; the in-tree hook works. Plugin **backends** and repo-tracked **`claudePlugin` dirs** stay local-only — see [plugins/manifest.md](../plugins/manifest.md).
- **Worker sessions on a system** — spawning works exactly as on a local project; what changes is where the worker's tools land. The `claude` CLI always runs on cc's machine (a system cannot be assumed to host node or Claude credentials), so cc puts it inside a **chroot onto a union filesystem** whose root is the system's, and redirects `Bash` to run there.
  - **Where the worker works** — the CLI's working directory **is the project's own path on its system**. cc owns no local session root: nothing is pulled ahead of a spawn, and a file has ONE spelling whichever tool names it. Its CLI is pointed at that remote's own config directory (below), so the transcript directory it derives from that cwd cannot be another machine's. What makes the cwd itself possible is the **FUSE-union chroot** ([components/fuse.md](../components/fuse.md#srcsystemsfuse)), which is **mandatory** for a worker on a system — a host that cannot mount it refuses the spawn rather than running the worker somewhere wrong: the filesystem decides which bytes appear at a path, so `Read`/`Write`/`Edit` need no translation — they are hooked only to REFUSE a path the union does not serve to that session.
  - **Each remote gets its own CLI config directory.** The Claude CLI names its transcript directory `<configDir>/projects/<encodeCwd(cwd)>`, and a remote-backed worker's cwd is the remote's own path spelling — so `/root/app3` on two boxes would be one directory. cc gives every `(system, remoteId)` a config directory of its own at `<store>/claude-config/<dirName>/.claude/` and launches the worker with `CLAUDE_CONFIG_DIR` pointing at it, so the root differs per machine. `encodeCwd` is unchanged; only the root it joins to moved. **A local project is untouched** — same directory as before, byte for byte.
    - The directory is a **symlink farm** over the host's real config dir: every top-level entry is linked, so settings, plugins, skills and history stay shared and are edited in one place. These are not linked — `projects/` (the isolation itself), `.claude.json` (its lock is not realpath-resolved, so sharing it loses writes, and its `projects` map is cwd-keyed and would leak allowed tools and trust acceptances between remotes), `.credentials.json` (reached through `CLAUDE_SECURESTORAGE_CONFIG_DIR` instead) and `backups/` (its contents are `.claude.json` backups and nothing else, so sharing it lets one config's churn evict another's last backup, and makes the CLI's missing-config recovery offer a foreign config for restore). The farm is rebuilt before every spawn, so an entry the CLI adds in a later version starts being shared; a real file cc did not create, at a name cc links, is left alone and reported once.
    - **Plan mode** writes to the worker's own `<configDir>/plans`, which is a link to the host's `~/.claude/plans` — so plan files still accumulate in one place, and a worker cannot name another remote's config directory through a file tool.
  - **Two places cannot share one transcript directory.** Creating or adopting a project, or creating a worktree, whose **transcript directory** is already held is refused **409 `TRANSCRIPT_DIR_COLLISION`**, naming the holder and saying whether the two are literally one directory or merely encode alike (`_` and `.` both become `-`). The comparison is on the whole directory, so what it now refuses is what genuinely IS one directory: **two places on one target** at one path, and **two local places** whose cwds encode alike. Two systems at one absolute path, two targets of one system, and a remote plus a local project at one path are all registrable. A session that ran on a system is still **locatable by `sessionId` alone**, and its transcript is READ from cc's own disk, so an unreachable system refuses a spawn but never a read.
  - **How wide the remote tier is, is the provider's to say.** A provider may advertise a **mirror root** and an **exclude list** per target (`describeRemote`, [systems-protocol.md](../systems-protocol.md)). Advertise nothing — the default, and every provider that predates the frame — and the answer is the **narrowest** one: the project's own path. Advertise a root **above** the project and that wider slice is served from the system too, so a worker can reach a file outside the project tree at its real path. The advertisement is read **once, at create, and pinned for the session**. A provider that answers differently on a later connection generation makes the next relaunch refuse **501 `MIRROR_ADVERTISEMENT_CHANGED`**, naming both geometries: a session cannot continue at a shape it did not start under, and there is no local image left to rebuild at a new one. Refused at spawn: **501 `MIRROR_ROOT_EXCLUDES_PROJECT`**, **501 `MIRROR_EXCLUDE_COVERS_PROJECT`**, **502 `MIRROR_ADVERTISEMENT_INVALID`**. An exclude *outside* the mirror root is inert and reported on the session's event stream, never a refusal.
  - **`Bash` runs on the system** — **one fresh shell per command**, exactly as locally: each local `Bash` call gets a brand-new shell and the CLI resets the working directory to the project root (measured on CLI 2.1.258), and a redirected one behaves the same way.
    So nothing carries between two commands — not `cd`, not `export`, not a shell function, and not between agents in either direction.
    **A command that ends somewhere else is told so**, on stderr after its output: cc names where it ended and where the next command will start, because a `cd` that silently vanished is worse than one that is announced.
    Commands that did not move the working directory are told nothing, matching a local session's silence.
    **Output streams as it arrives**, not at exit: a long build or test run is visible while it is still running, and a backgrounded command's output accumulates in its task file as it goes rather than appearing at exit. stdout and stderr stay on their own descriptors, and the exit code is still the command's own.
    A command that dies without finishing still delivers what it printed first.
    **Commands run concurrently** — nothing takes a turn, so two agents' commands, or a session's own, overlap freely.
    **A command's own `timeout` does not cut it short**, exactly as locally, where a foreground Bash past its `timeout` is handed to you as a background task and keeps running — a redirected one is handed over the same way.
    That it then **keeps running on the system** follows from cc never being told to stop it, and has not been observed directly — treat it as the expected behaviour rather than a verified one. cc is not even told the number and needs it for nothing.
    What does bound it is cc's per-command ceiling, set just over the built-in Bash tool's **documented** maximum so it never cuts short a command that tool would still be waiting for — a `timeout` above that documented maximum is untested territory, and `ORCH_SHELL_COMMAND_TIMEOUT_MS` is the knob that raises cc's ceiling back above it.
    - **Output is fenced at 8 MiB per command.** Past it the command is killed and the call fails, naming the limit — cc accumulates a command's output in its own memory while it runs, and a truncated success would be read as the command's real output.
    - **Interrupting cancels that call and nothing else.** A call cancelled before it crosses never runs on the system at all; one already running is stopped there, through its own command's kill signal — so a concurrent command is untouched. Ending the session stops every command it still has running, rather than leaving them to finish on a machine nobody is reading.
    - **A backgrounded job returns immediately and outlives its command, as it does locally**, and the command still reports its own exit code and its own output. Every shape behaves the same way — `cmd &`, `cmd & disown`, `setsid cmd &`, and `nohup cmd &` **with or without** an output redirect — so there is no form to prefer and nothing to work around. (`nohup` alone diverts a TTY, not a pipe, so the redirect is the half that could matter — and here it does not.) **Measured on cc's reference provider** — same-host and across a real container boundary, in both capability configurations; a third-party provider is not covered by that measurement. Before the fix a job holding the command's stdout open kept the provider from ever reporting the command's exit, and a command that exited 0 reached the worker as a failure with an empty stdout, minutes late; cc now settles a redirected command on **its own framing sentinel**, which is where the output ends by construction.
  - **The CLI's own output files stay on cc's machine, and `Read` reaches them.** A backgrounded or timed-out `Bash` command's `.output` (under the session's tmp dir) and an oversized tool result saved to its `tool-results/` dir are written on cc's host — a subagent's land in the same places, under its parent session. `Read` opens them (for `tool-results/`, only the session's own, and only `Read`); a `Bash` command that names one is refused before it runs, with a reason pointing at `Read` with `offset`/`limit`, because on the system that path is a different file or none. The match is on the command's literal text, so a path reached through a variable, `~`, a glob or a `cd` is not caught.
  - **`Glob` and `Grep` are unavailable — removed from the registry AND refused by name**, and the second guard is not a leftover: a marked CLI's `Grep` spawns an **unmarked** `rg`, which the union routes as a stranger, so it would search the wrong side and return silently wrong results rather than failing. A search also cannot be redirected the way `Bash` can — a tool result can be annotated but never replaced. Re-enabling them needs mark inheritance, which is measured closed. The refusal names `find`/`grep` through `Bash`, which runs on the system. The cost is coverage confidence, not correctness.
  - **The worker is told**, in two sentences at the top of the project's `CONVENTIONS.md`: where the tree is, that `Bash` runs there, and that **the same path names the file for every tool** — the CLI is chrooted at the system path, so there is no second, local spelling of it. It deliberately makes no claim about *where* such a path can appear: both earlier wordings of this sentence made one and both were falsified, one by telling the worker to read at a local path and never at the system path — which would now forbid the only path that works. It says nothing about shells or where a command starts: that is delivered at the point of use, by the notice on the one command whose `cd` was discarded.
  - **Refused before it starts** — **501 `REDIRECT_HOOKS_DISABLED`** when any scanned settings file sets `"disableAllHooks": true`.
    That switch turns the whole redirect off: the worker's commands would run on the orchestrator's machine while every result claimed the system, and no edit would reach it — and because it leaves `permissions.*` working, nothing else would fail loudly.
    **501 `BASH_RULES_NOT_ENFORCEABLE`** when a `Bash(…)` pattern rule appears in `permissions.deny`/`ask`.
    Both scan the same files: the project's own `.claude/settings*.json` **read through its `System` handle** (they live on the system; there is no local copy), `~/.claude/settings.json`, and `/etc/claude-code/managed-settings.json`.
    Redirection rewrites every command into one forwarder invocation, so the CLI — which matches rules against the rewritten command — could no longer tell two commands apart and the rule would apply to nothing. cc does not reimplement the matcher; it names the rules and their files and declines.
    **501 `WORKER_SESSIONS_NEED_A_SHELL`** when cc cannot run a command on the system at all.
    **501 `FUSE_LAUNCHER_UNRESOLVED`** when the `claude` CLI does not resolve to an absolute path on cc's own machine — that path is the union's marking event and the CLI's only host pin, so a session started without one would mark no caller and pin no launcher; the message names `CLAUDE_BIN` as it was set and the repair.
    (A session whose launcher runs the CLI **inside cc's own process** has no chroot and no marking event, and is exempt.)
    **501 `FUSE_BACKEND_UNRESOLVED`** when the session's **backend** launch command — the template's first token — does not resolve on cc's own PATH; the message names the backend, the token it tried and the template.
    It is refused **for attribution, not for pin correctness**: that command runs unmarked inside the chroot and needs no host pin, but an unresolvable one fails the launch inside `setpriv`, deep in the chroot, naming nothing.
    Same in-process exemption.
    Three more come from the mirror advertisement — **501 `MIRROR_ROOT_EXCLUDES_PROJECT`**, **501 `MIRROR_EXCLUDE_COVERS_PROJECT`**, **502 `MIRROR_ADVERTISEMENT_INVALID`** — described under **How wide the remote tier is** above, plus **501 `MIRROR_ADVERTISEMENT_CHANGED`** on a relaunch after the provider moved it.
    Two more are asked **LIVE at every launch**, because a machine that stopped after cc connected is invisible to every memoised answer — and for a union-mounted worker "discovered at first use" means inside its own chroot, with every project path answering -EIO and nothing there to say why: **502 `FUSE_REMOTE_UNREACHABLE`** (the system did not answer a live check; it names the remote, the system and the far side's own reason) and **501 `FUSE_MIRROR_ROOT_ABSENT`** (the system is up and the advertised mirror root does not exist on it — every file tool in the session would be refused as outside it).
    Both run before the mount is prepared, so a refused spawn creates nothing.
    All of these refuse the SESSION and nothing else: the project keeps its row and every `project_*` tool still works, because none of them consults the mirror.
  - **When the project cannot be resolved** — an unregistered system, one with no provider command, one that is down, or a record naming a system with no `systemPath`: the project **keeps its row** in every listing, carrying `systemUnreachable` with the reason; its git facts are absent rather than invented. The sidebar row shows a red **system pill** with the refusal in its tooltip and disables the ⋮ items that would fail, with the reason; Delete… stays, and works — unregistering never reaches the system, at any layer, so a project on a system that is down (or one whose record is malformed) is never stranded holding its system row at 409. Its worktree **registrations still list** — they are cc's own records and need no system — with their divergence unknown rather than invented. Addressed-by-name calls refuse: `SYSTEM_NOT_REGISTERED` (501), `SYSTEM_NO_PROVIDER` (501), `SYSTEM_UNREACHABLE` (502), **`SYSTEM_NO_REMOTES`** (501 — the record names a target but the provider does not serve named targets; drop the target or upgrade the provider) and **`REMOTE_NOT_FOUND`** (502 — it does serve targets, but not this one: the container is gone, or the name is a typo). The two new codes are raised at creation and at every resolution, so a bad target is refused before anything is written and again on every later use. A system that dies MID-operation refuses the same way rather than reporting a git answer, and `merge_worktree` adds `mayHaveCompleted` when the transport dropped after `git merge` was issued — cc cannot know whether it landed.
  - **When git refuses the repository (dubious ownership)** — the uid cc runs git as does not own the repo, so git refuses every command in it. The row **keeps its system** (the system answered; the pill stays healthy, the ⋮ items stay enabled) and shows an amber **`dubious ownership`** pill whose tooltip is git's refusal with the fix — `git config --global --add safe.directory <path>`, run as that user on that system. Its git facts are absent (no commit log, no ahead/behind), never reported as "not a git repo"; `list_projects` prints `! git refused <message>`, `project_status` prints it and still lists FILES. Worktree create and the commit log refuse **403 `GIT_DUBIOUS_OWNERSHIP`**, and so does **deleting the project while it has a registered worktree whose checkout still exists** — `checkoutIsProtectable` cannot ask git whether that worktree's parent is still a repo — so trusting the repo is the only way out inside cc (deleting the worktree refuses too, with or without `force`); a registration whose checkout is gone is dropped and the delete proceeds; adopting such a repo refuses `TARGET_DUBIOUS_OWNERSHIP`. cc never sets `safe.directory` itself.
- **Workspaces** — the sidebar `≡` menu hosts **New workspace**; nest projects under collapsible headers (`web/src/features/sidebar/ProjectsList.tsx`), one workspace per project, empty workspaces persist. Edit (rename / re-pick members / delete) via the ✎ button on each header. Each workspace header is a full-width band (`bg-sidebar-accent`, a top and a bottom rule) holding the caret, a layers icon, the uppercase name, the count and ✎; it is sticky at the top of the sidebar's scrolling body (`[data-sidebar-body]`) while its projects scroll by, until its section ends and the next band takes its place. Project rows under it start at the project list's left edge, with no indent and no caret: the folder comes first, about under the band's caret. The main checkout's sessions sit in a collapsible `Sessions (N)` group (open by default, in-memory state) beside the `Worktrees (N)` group, both on a rail. Unassigned projects follow under an `Other projects` band of the same kind (folders icon; no caret, count or ✎; drawn only when a workspace precedes it), its rows at the same edge; with no workspaces the list is flat, with no band. A selected row revealed by scrolling upward stops clear of the band (a scroll margin on the selected row inside a banded list). Workspaces default-collapsed; expand state persists in `localStorage` (`code-conductor:workspaces-expanded`). Stored server-side at `<store>/projects/<name>/project.json`; the workspace set is the union of `<store>/workspaces.json` and any referenced names. Workspace names use the same `^[a-zA-Z0-9._-]+$` charset as project names, capped at 40 chars and barred from starting with `.` (`^[a-zA-Z0-9_-][a-zA-Z0-9._-]{0,39}$`), so a name stays safe as a path segment.
- **Resizable sidebar** — desktop layout only (Tailwind's `md` breakpoint and up). A drag handle on the sidebar's right edge (`useResizableWidth` in `web/src/lib/useResizableWidth.ts`, shared with the plugin dock) resizes the column live, clamped to `SIDEBAR_MIN_WIDTH`–`SIDEBAR_MAX_WIDTH` around a `SIDEBAR_DEFAULT_WIDTH` default (all in `web/src/features/sidebar/derive.ts`); a double-click on the handle, or Enter on it, restores the default. The handle is a focusable WAI-ARIA window splitter (`role="separator"`, **Resize sidebar**): ArrowRight / ArrowLeft widen / narrow by `RESIZE_KEY_STEP` (same file), and `aria-valuenow` / `aria-valuemin` / `aria-valuemax` read the width and its limits. While a drag is in progress `body[data-resizing]` (also set by the session width handles) turns pointer events off on every iframe, a safeguard for engines where the handle's pointer capture does not retarget over one; a cancelled drag (`pointercancel`) commits nothing. Persisted in `localStorage` (`SIDEBAR_WIDTH_STORAGE_KEY`, `code-conductor:sidebar-width`) on release and on every key that moves it. Below the breakpoint the sidebar is a slide-in drawer instead, with no handle; the drawer's close `×` is the last of the sidebar header's controls, after ⚙ (`AppSidebar` in `web/src/features/sidebar/AppSidebar.tsx`), on their line and ending on the content column's right edge.
- **Session width** — desktop layout only (`md` and up); below it the column is already narrower than any setting, so it has no effect and the phone drawer has no control and no handles. It sizes the transcript, the sticky pin, the task and workers panels and the composer together, and the Settings page and the Costs, Commits and Review full-page views.
  - **Full-page views:** Settings, Costs, Commits and Review follow the setting only: they have no handles, and they change live (the footer toggle stays reachable while they are open). They keep no gutter: the cap is the plain px, or none under Full. Each view's breakpoints read its column (`@container` on the width box), so Settings' nav becomes pills above the section on a narrow column and Costs' totals tiles follow the column. Plugin views fill the pane — the setting does not resize the pane — while their pages in the full view follow it through the bridge's `--cc-session-width`; a page docked in the side pane always fills the pane (see **Plugin session width** under Plugins).
  - **Toggle:** an icon button in the sidebar footer, beside the theme toggle (`SessionWidthControl` in `web/src/features/sidebar/`), switches Full ↔ Resizable. The label and tooltip read `Session width: Full` or `Session width: Resizable, <N> px`; the icon is `MoveHorizontalIcon` under Full, `UnfoldHorizontalIcon` under Resizable. Full makes the column fill the area and never touches the stored width; Resizable returns to it. It is an ordinary button, the keyboard path to the setting.
  - **Handles:** under Resizable, thin strips sit on both edges of the column, spanning the transcript's top to the bottom of `main` (`SessionWidthHandles` in `web/src/features/session/`). They are pointer-only: `aria-hidden`, not focusable, no keyboard resizing. They look and behave like the sidebar and dock dividers (`RESIZE_HANDLE_CLASS` and `setResizing` in `web/src/lib/useResizableWidth.ts`: `col-resize`, hover tint, pointer capture, and `body[data-resizing]` while dragging). Dragging one edge mirrors the other at twice the pointer distance, so the column stays centred. The column follows live on all three boxes; the setting is written once on release, and `pointercancel` commits nothing. A double-click on either handle resets to `SESSION_WIDTH_DEFAULT`. Hidden under Full.
  - **Snap:** during a drag only, a width within `SESSION_WIDTH_SNAP_RADIUS` of a `SESSION_WIDTH_SNAPS` point (Normal, Wide) lands on it, before the room limit applies.
  - **Bounds:** the floor is `SESSION_WIDTH_MIN`; there is no fixed maximum. A drag stops at the room (the transcript scroller's client width, the basis every box's `100%` resolves against) less `SESSION_WIDTH_GUTTER` per side (`sessionWidthCeiling` in `web/src/app/sessionWidthScale.ts`), which keeps the handles clear of the dock divider, the sidebar handle and the transcript scrollbar. On desktop the rendered cap is `min(<width>px, 100% - 2 * gutter)`; below `md` it is the plain px. Dragging to the limit stores the shown px, not a marker. A stored width wider than the current window renders clamped and stays stored: rendering never writes, a click without movement writes nothing, and a drag starts from the shown width.
  - **Storage:** one global setting per browser, `localStorage['code-conductor:session-column']` = `{"width":<px>,"full":<bool>}`; a width below the floor reads as the floor. The store reads only `code-conductor:session-column`; a missing, unparseable or wrong-shaped value reads as Resizable at Normal. `data-session-width` on each column box is `full` or the width in px: the setting, not the rendered or live width.
  - **Plugin pages:** in the full view, follow the committed setting through the bridge's `--cc-session-width` ([plugin-ui.md](../plugin-ui.md)); a handle drag updates them on release. A page docked in the side pane (split or rail) gets `none` and fills the pane.

- **Git status pill** —
  - **Project rows**: amber `↑N ↓M` against the currently-checked-out branch's *configured upstream* (e.g. `origin/<branch>`), using cached refs only (no `git fetch`). No pill when in sync / detached / upstream-less.

# Features: worktrees, diffs and history

## Worktrees
- **Isolated environments** — "Run in isolated git worktree" checkbox in the new-instance dialog runs `git worktree add <projectsRoot>/.worktrees/<project>/<short-id> -b code-conductor/<short-id> <currentSha>` and spawns the agent with `cwd` set to the worktree. ONE layout for every local project, wherever its tree lives; a project on a system puts its worktrees there instead — see **Projects on a system** in [projects.md](projects.md#projects--workspaces).) The orchestrator captures `{baseBranch, baseSha, branch}` at creation so you can spawn off any branch and land back later. Worktrees survive instance death — re-spawn into the same worktree from the sidebar. The checkbox is disabled with the reason in its hint when the project is not a git repo **or** is a repo with no commits yet (`unbornHead`); the sidebar flags the same state with a `no commits` pill on the project row.
- **Named worktrees** — MCP `create_worktree` / `spawn_instance({createWorktree:true})` accept `name`, slugified (lowercase, non-alphanumerics → `-`, trimmed, capped at `SLUG_MAX_LEN` in `src/worktrees.ts`) into `code-conductor/<slug>` in place of the random 6-hex id. **The store key, the `worktreeName` and the directory basename are ONE string** — the slug — so nothing parses a name out of a path and nothing aliases one spelling to another. A name with no usable characters is refused **400**; a slug whose branch `code-conductor/<slug>` already exists is refused **409**; so is one whose working directory is already held by another place, on any system (**`TRANSCRIPT_DIR_COLLISION`**), checked before any git state is touched — a SEPARATE 409 from the branch pre-check below, on a different subject. That branch-ref check covers both of ITS collision cases — a still-registered worktree (whose branch git won't let you delete while it is checked out) and a worktree that was deleted but left its branch behind — and its value is the clean 409 in place of the 500 `git worktree add` would otherwise raise. Worth setting for a worktree others will be based on, whose branch is read in `git log` long after it was created. There is one spelling per worktree, so every worktree-addressing input takes the slug exactly as it is reported (see [protocol/mcp.md → Input params](../protocol/mcp.md#mcp-tool-protocol)). No GUI affordance — the browser checkbox still creates hash-named worktrees.
- **Two-step rebase-back** (**Sync** is in the session header and the commits view; **Merge** is in the commits view only — see Commit history):
  - **Sync** — already in sync → no-op; purely behind & clean → server-side `git merge --ff-only <baseBranch>`; diverged & clean → orchestrator attempts `git rebase --rebase-merges <baseBranch>` directly (`rebased` on success) and on conflict aborts cleanly and returns `rebase-conflict`; behind-but-dirty → `commit-required`. **Sync never prompts an agent.** Those last two are `ok:true` results carrying `branch`/`baseBranch`/`baseSha`/`ahead`/`behind` plus a rendered `rebasePrompt` — two briefs (commit-then-rebase, or rebase-by-hand from a clean tree), both telling the agent to run the same `--rebase-merges` command, to consult the user via `AskUserQuestion` on non-trivial conflicts, and to reply `REBASE_DONE`. Neither brief claims an earlier rebase attempt: a dispatch can arrive after the worktree's state has moved, so the conflict brief asserts only the standing invariant (the orchestrator aborts a failed rebase, never leaves one half-applied) and tells the agent to verify with `git status` — and to say so if the branch turns out to need nothing. Dispatch is the caller's own explicit step: the conductor `send_prompt`s the text to whichever worker should do the work; the GUI confirms, naming the session (from the commits view: a live session on the viewed worktree; with none, the user is told no agent is running), then `POST /api/instances/:id/rebase-prompt`. **`--rebase-merges` is load-bearing** on every path: a branch that other worktrees merged into carries their merge commits, and a bare `git rebase` flattens them silently, looking like a clean sync.
  - **Merge** — `git merge --no-ff --no-edit <worktreeBranch>` on the parent. A successful merge records the landing in server memory (read by the **Landing renewal nudge**, Conduct mode). Always produces a merge commit (default msg `Merge branch 'code-conductor/<id>'`) so each contribution stays visible in `git log --graph` and is revertible as one commit. Refuses inline (not as a 500) if the user has locked the worktree (checked first — see **Lock**), the worktree is behind the parent, the parent is on a different branch than `baseBranch`, or the parent tree is dirty. On success, also fast-forwards the worktree's own branch up to the new merge commit (best-effort — reported as `worktreeFastForwarded: true/false`) so a kept worktree lands at `ahead:0/behind:0` instead of looking one commit behind.
- **Delete** — refused if there's a live instance, uncommitted work, or another worktree based on this one, with a `force=1` override. MCP `delete_worktree` also refuses a locked worktree, and `force` does not override that (see **Lock**).
- **Lock** — the user can lock a worktree so it is not merged by mistake, by them or by an agent: e.g. a long-lived worktree backing a merge request, or a feature worktree aggregating task worktrees. A **🔒 Lock** toggle sits beside Sync and Merge in the worktree's commit history view (≡); it is the only way to **clear** the lock, and the only way to set it on an existing worktree; an agent can set it only when creating one (`create_worktree({lock:true})`), and deliberately **no MCP tool** clears it. Stored server-side as `locked: true` in the worktree's `worktree.json` (`PUT /api/projects/:name/worktrees/:wt/lock`, [protocol/rest-instances.md](../protocol/rest-instances.md)).
  - **Refuses** merging the worktree into its base on every merge path (the commits view's Merge, REST, MCP `merge_worktree`) with `WORKTREE_LOCKED`, checked before every other merge refusal; and **an agent deleting it** — MCP `delete_worktree` refuses `WORKTREE_LOCKED` ahead of every other delete refusal, **even with `force:true`**. The refusal tells an agent that only the user can unlock it, and that a worker on it is retired by killing the worker and leaving the worktree.
  - **Does not affect** Sync, a child worktree merging **into** the locked one (the lock is read off the worktree being merged, never the target), or the user's own deletes (the sidebar worktree menu's **Remove worktree…** and the project-delete cascade). Deleting a worktree deletes its lock; a worktree re-created under the same name starts unlocked unless its creation asks for the lock (`create_worktree({lock:true})`).
  - **UI:** while locked, Merge is disabled with a tooltip saying why, the toggle reads `🔒 Locked` (pressed), and the worktree's sidebar row carries a 🔒 marker, refreshed through the `{t:'projects'}` hint like the merge pill. Agents see a trailing `locked` cell on the worktree's row in `list_projects` / `list_worktrees`.
  - **Known limit:** the lock guards cc's own tools against mistakes; it is not a sandbox. An agent can still run `git merge`, `git worktree remove` or `rm` through `project_bash` / `system_bash`, overwrite or move files with `system_transfer`, or call the REST API directly.
- **Feature branches (a worktree based on another worktree)** — `create_worktree` / `spawn_instance({createWorktree:true})` accept `baseWorktree: "<worktree name>"`. The new worktree takes `baseBranch`/`baseSha` from **that worktree's HEAD** and its `parentPath` points at that worktree's checkout, so it syncs against and merges into the base worktree instead of the project root. That yields nested history — `main ← merge ← merge ← … ← commits`, one level per link in the chain — lets a multi-stage feature be tested integrated without landing partial work on `main`, and gives a whole feature one reviewable diff.
  - **"Feature" is a position in the graph, not a type.** A worktree others are based on is a feature; a worktree with a `baseWorktree` is a task. The only stored field is `baseWorktree` (`WorktreeMeta`, `src/worktrees.ts`) — absent means based on the project root. `parentProject` stays the **root project name** either way. There are no `*_feature` tools: the existing sync/merge/delete tools do the work.
  - **Chains nest to any depth.** A `baseWorktree` may itself have a `baseWorktree`. Cycles are impossible by construction rather than by check: `baseWorktree` has one write site (`createWorktree`, at creation, naming a record that already exists), so creation order is a topological order and there is no re-parenting API. The `WORKTREE_HAS_DEPENDENTS` *predicate* stays direct-only and is depth-independent — a grandchild cannot exist without its parent record, so the direct child always blocks first — while the *list* it hands back walks the subtree (below). The cost of depth is the freeze: a non-leaf can neither sync nor merge for the union of its descendants' lifetimes.
  - **`WORKTREE_HAS_DEPENDENTS`** — `sync_worktree`, `merge_worktree`, and `delete_worktree` all refuse, listing the blocking worktree names in `reason` and in `dependents[]`, while any worktree record descends from this one. The list is **transitive and deepest-first** — the order they must be deleted in — so the first refusal names the real blocker rather than a child whose own delete then refuses. Every sync path rewrites this branch, which is the base the children were created from; a delete removes that branch outright. The predicate is over **worktree records, not live instances**: killing a child's worker is not enough, the worktree must be deleted. A surviving child whose base was rewritten or deleted under it is genuinely broken, so this is deliberate. The refusal is unconditional on ahead/behind, and on `merge_worktree` it is checked **before** `WORKTREE_BEHIND` — merging needs a prior sync that would also refuse, so this names the real blocker on the first call. Only the lock (`WORKTREE_LOCKED`, see **Lock**) is checked earlier, on merge and on MCP delete: a locked feature always has children, and this refusal would otherwise send the caller off to delete them first.
  - **`force` overrides it on delete, and strands the subtree.** `delete_worktree({force:true})` / `?force=1` deletes that worktree's branch anyway, so each surviving **direct child**'s `baseBranch` ref disappears and its next sync fails loudly with "base branch may have been deleted or renamed". Anything deeper keeps an intact base ref but is rootless — its chain no longer reaches the project. Legitimate when abandoning a whole feature including its children; otherwise delete the subtree first. (The project-delete cascade sweeps with `force`, so it is unaffected.) `force` never overrides the lock on MCP `delete_worktree`.
  - **It applies to the worktree being synced/merged/deleted, never to the one being merged INTO.** Merging task `A` into feature `F` succeeds while `F` still has task `B` based on it: a `--no-ff` merge onto `F` appends to `F`'s history rather than rewriting it. (Were it otherwise, no feature with two children could ever take a merge.) A task's own delete is likewise unaffected by having a base.
  - **Two disciplines, both valid — pick per feature; nothing here prescribes one.** *Serialized*: land child → delete child worktree → sync feature → spawn next child → … → sync → merge feature. The feature tracks `main` continuously. *Concurrent*: several children at once; the feature's base is frozen for that window (its sync is refused), so all `main`-integration risk lands at the end.
  - **Known shortcoming: a task's merge sha is ephemeral.** Each sync of a base rewrites that base's history, so a merge commit into it is renewed every time. Only the **root-most** worktree's landing commit on `main` is durable — don't cite an intermediate merge sha as a stable reference.
  - **Every non-leaf worktree is a merge target, so it must be kept clean.** `PARENT_DIRTY` is evaluated against it and has **no override** (`allowDirty` covers only the *merging* worktree's own tree), so untracked build artifacts there — e.g. from `post-worktree-create.sh` or `post-worktree-merge.sh` — will refuse every task merge into it.
  - A derived worktree's `post-worktree-create.sh` is resolved from **its base's checkout** (in-tree lookup uses `parentPath`), not the project root — same repo, and a base that edited the hook correctly passes the new one down. `CC_PARENT_PATH` likewise points at the base's checkout.
  - `list_projects` and `list_worktrees` both show the relation as `base <branch>@<sha>` and mark a derived row `← <baseWorktree>` — its own direct base, so a chain is read by joining rows. There is no GUI tree view — the sidebar renders every worktree as a flat sibling row.
- **Post-worktree-create hook** — a `post-worktree-create.sh` script (need not be committed — read from disk, not the new worktree) is resolved from two locations in priority order: **in-tree** `<parent>/.code-conductor/post-worktree-create.sh` first, else the **central store** `<root>/.code-conductor/projects/<name>/post-worktree-create.sh`. When found, the orchestrator runs it automatically with `cwd` in the new worktree, after the worktree directory, branch, and metadata are written. Use case: symlink `node_modules`, copy `.env`, run `npm ci`, etc. The script receives env vars `CC_WORKTREE_PATH`, `CC_PROJECT_NAME`, `CC_BRANCH`, `CC_BASE_BRANCH`, `CC_PARENT_PATH`. Non-fatal: a failure warns but does not roll back the worktree. Output is capped to a tail bound (`HOOK_OUTPUT_CAP`); timeout via `ORCH_POST_WORKTREE_TIMEOUT_MS` (see `src/worktrees.ts`). Kill-switch: `ORCH_DISABLE_POST_WORKTREE_HOOK=1`. Result is reported in the spawn/worktree-create response as `postWorktreeCreate: { ran, source, exitCode, durationMs, output, truncated?, timedOut? }` (`source` is `'in-tree'` or `'store'`). The spawn dialog stays open with a one-line `Worktree hook:` summary and only **Done** left whenever the hook ran (expandable output when it printed any, expanded on failure), was skipped (`disabled` as a neutral line, `STORE_HOOK_LOCAL_ONLY` as a warning line), or errored without running (warning, output expanded); it closes as usual when no hook was found. Agent guide: `code-conductor:worktree-hooks`.
- **Post-worktree-merge hook** — a `post-worktree-merge.sh` script, resolved like the create hook: **in-tree** `<target>/.code-conductor/post-worktree-merge.sh` first, else the **central store** `<root>/.code-conductor/projects/<name>/post-worktree-merge.sh`. Runs after a merge has landed (REST merge, the commits view's Merge, MCP `merge_worktree`), never for a refused merge.
  - **Read from the target after the merge**, so a branch that edits the in-tree hook runs its own version. `cwd` is the **merge target** — the project root, or the feature checkout when a task merges into its base.
  - **Env vars:** the create hook's vars (`CC_WORKTREE_PATH`, `CC_PROJECT_NAME`, `CC_BRANCH`, `CC_BASE_BRANCH`, `CC_PARENT_PATH` = the target) plus `CC_PRE_MERGE_SHA` (the target's HEAD before the merge — what the merge gates measured) and `CC_POST_MERGE_SHA` (the merge commit, = `newSha`). A target on cc's own machine also gets `CC_SERVER_NODE` (the node binary running cc), and, when it is the running server's own checkout, `CC_SERVER_BOOT_SHA` (the commit the server booted from) or `CC_SERVER_BOOT_UNKNOWN` (why it cannot vouch for one: tracked changes outside `web/` at boot, an unborn HEAD, or its own web build running now). What the merge brought in: `git diff --name-only "$CC_PRE_MERGE_SHA" "$CC_POST_MERGE_SHA" -- web/`.
  - **Non-fatal:** a non-zero exit, a timeout, an error or a skip never changes the merge's `ok` — the merge has landed either way. Reported as `postWorktreeMerge`, shaped like `postWorktreeCreate` ([protocol/rest-instances.md](../protocol/rest-instances.md)).
  - **Blocking, serialised per project:** the merge response waits for the hook, and two merges into one project run their hooks one at a time. The timeout bounds the hook's own run, not its wait in the queue, so N merges queued behind each other can block up to N × the timeout.
  - **Timeout and kill switch are its own:** `ORCH_POST_WORKTREE_MERGE_TIMEOUT_MS` (default in `src/worktrees.ts`), `ORCH_DISABLE_POST_WORKTREE_MERGE_HOOK=1`. The create hook's pair does not touch it, nor its pair the create hook. A merge is bounded by the server's HTTP request timeout ([environment.md](../environment.md)), which covers REST and MCP alike (`/mcp` is on the same server): a timeout raised past it drops the REST and the MCP `merge_worktree` response while the merge has still landed.
  - **A merge hook must leave the target clean.** Write only gitignored output: every merge target is checked for `PARENT_DIRTY` with no override, so a hook that leaves files behind refuses the next merge into it. Neither hook is chmod-ed: it runs as `bash <script>`, so an in-tree hook committed without its exec bit is run as committed and its mode is left alone.
  - **UI:** the "Merged into parent" toast names the hook's result when it ran or was skipped; a non-zero exit, a timeout, an error or a `STORE_HOOK_LOCAL_ONLY` skip adds a warning toast (`Post-merge hook failed` / `Post-merge hook not run`) carrying the label and the output's tail (`web/src/app/hookResult.ts`). The Merge button stays busy while the hook runs.

## Diff / review & commit history
- **Worktree diff/review** — **Review changes** in a worktree's commit history header opens a full-page, mobile-friendly diff browser (`ReviewView` in `web/src/features/views/ReviewView.tsx`). Fetches a per-file **summary** (no hunks, never truncated — a `--numstat`/`--name-status` pass) from `GET /api/projects/:name/worktrees/:wt/diff` (`<baseBranch>...HEAD`) and renders a collapsible card per file (`FileCard`: status letter, `±` counts). A file's hunks are fetched lazily via `?path=<file>` only when its card is expanded, and cached on the card so collapsing/re-expanding doesn't refetch; an expanded card shows a brief loading state, then the hunks in the chosen layout (below). Failure states per file: a retryable load error, a note for a binary file (no fetch at all) or an oversized file (`adds+dels > FILE_DIFF_LINE_GUARD`; the server sends no hunks), and a truncation note if that one file's raw diff still exceeds `DIFF_BYTE_CAP` (both constants in `src/gitDiff.ts`). Because the summary has no size cap, a change touching any number of files always lists every one, with exact totals.
  - **Unified / Split** — the header's **Split view** toggle (`aria-pressed`) applies to every diff the view opens (worktree, commit, uncommitted). The choice persists per browser in `localStorage` `code-conductor:diff-mode` (`DIFF_MODE_STORAGE_KEY`, `'unified'|'split'`, in `web/src/features/views/diffMode.ts`); a fresh profile, a garbage value or unavailable storage means unified.
    - Unified keeps the hunks in a horizontally scrolling box.
    - Split puts the old file on the left and the new file on the right (`DiffHunks.tsx`); old/new line numbers come from the hunk header (`splitRows` in `shared/diffSplit.ts`). A run of deletions pairs row by row with the run of additions that follows it, blank cells filling the shorter side. Hunk headers span both columns; long lines wrap within their half and the rows stay aligned.
    - Below the `md` breakpoint (`WIDE_QUERY`) there is no toggle and diffs render unified; the stored choice is kept, so widening the window brings split back.
    - The binary, oversized and truncated notes and the rename title are the same in both layouts. `\ No newline at end of file` is shown in neither: the server drops it.
- **Commit history** — `≡` button on every git-repo project row opens a full-page scrollable commit list (`CommitsView` in `web/src/features/views/CommitsView.tsx`) of the project's **current branch (HEAD)**: short sha, subject, author, relative date, newest first — and **topologically ordered** (`--topo-order`), which the rail below depends on: a parent never precedes its child, so no lane is ever routed at an already-drawn commit.
  Backed by the commits endpoint (bounded limit, default in `src/worktrees.ts`; header shows `(showing latest N)` when truncated).
  Tapping a commit opens the **same diff renderer** showing just that commit's change (`GET /api/projects/:name/commits/:sha/diff`, via `git show`); the diff layers over the list and `← Back` returns to it.
  Merge commits (parents.length ≥ 2) show the **first-parent aggregate** — the full diff the merged branch brought onto mainline (`git show --first-parent`), not git's default combined/conflict-only diff — and every file in that aggregate is listed regardless of the change's total size.
  A **branch/merge graph rail** (git-log --graph style) is drawn to the **left** of each row: colored lanes, a dot per commit, diagonals where branches fork and merges converge.
  Topology is computed client-side in `computeGraph()` (`web/src/features/views/graph.ts`) from each commit's `parents` (SHAs from `%P`); lanes use stable column indices so pass-through lines stay aligned.
  Each rail is a fixed-height SVG "node band" (dot + diagonals) plus full-height CSS filler lines, so it aligns with variable-height (wrapping) rows without measurement.
  Parents older than the cap / on unfetched branches simply trail off the bottom; a lane aimed at a commit already drawn ABOVE it terminates instead (it could never converge).
  Every row is badged ahead/already-merged from its **own** `ahead` flag (never from its position — the ahead set is not a contiguous prefix; see [protocol/rest-instances.md](../protocol/rest-instances.md)).
  A divider row labelled `↓ already in <base>`, bound to the section below it, sits above the first already-merged commit — but **only when every row below it is also already merged**, since that is what its label claims.
  Where the ahead rows are interleaved (a branch that merged its base back in), the badges carry the answer alone and no divider is drawn.
  A soft lane cap (`MAX_LANES`, `web/src/features/views/graph.ts`); extras clamp to the last column, logged to console.
  The **same view opens from a worktree row's branch icon** (the row's only commit-history control), addressed as the pair `(project, worktree)` — the sidebar row hands both to `openCommits` (`web/src/features/views/api.ts`), and every URL the view builds (list, commit diff, working-tree diff, and the `<prefix>/diff` its own Review changes hands `openReview`) hangs off the worktree-scoped prefix.
  That pair is what makes the view work for a project **on a system**: the worktree's tree sits beside its parent's on that machine, so nothing under cc's projects root names it.
  The header titles the worktree, not the parent.
  **Review changes**, **Sync** and **Merge** buttons sit in the view header when it shows a worktree's history, and are absent for a project's own tree.
  Review changes opens the worktree's `base...HEAD` review (see **Worktree diff/review**) and is never disabled.
  Sync and Merge act on the **viewed worktree**, not the active session, through `POST /api/projects/:name/worktrees/:wt/sync` / `…/merge`, with their confirm and alerts; the list re-fetches after an ok result.
  **Lock** toggles the worktree's lock (see **Lock** under Worktrees) with no confirm, through `PUT …/worktrees/:wt/lock`; its state comes from the `/commits` payload's `locked`, so it stays disabled until that payload lands.
  Sync, Merge and Lock are all disabled while any one of them is in flight; Review changes stays enabled.
  A blocked sync's rebase prompt goes (after the usual confirm) to a live session on that worktree, else the user is told no agent is running there.
  Reachable from the branch icon on any worktree row, in the project tree and the Conductors tree.

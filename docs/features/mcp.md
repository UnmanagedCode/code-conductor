# Features: the MCP interface and core skills

## MCP interface
Mounted at `POST /mcp` (Streamable HTTP, JSON-RPC 2.0); tools exposed as `mcp__code-conductor__*`. Auto-registered on every spawn via `--mcp-config`, as `/mcp/<sessionId>?format=text` — the session's own id in the path is its caller identity, and the text format is the agent view (opt out with `ORCH_DISABLE_MCP_AUTOREGISTER=1`). No auth — localhost-only.

**For applications.** The same tools answer scripts and plugins: JSON by default (`structuredContent` against each tool's `outputSchema`), a REST alias (`POST /mcp[/<sessionId>]/tools/<name>`, `GET /mcp/tools`), and `CONDUCTOR_MCP_URL` in a plugin backend's env (anonymous). Contract, error channels, ceilings and samples: [mcp-applications.md](../mcp-applications.md).

**Code mode.** `run_code` (`{code, description?, timeoutMs?}`) runs a JavaScript async function body in a child process whose `cc` object calls any tool as the calling session — `cc.<tool>(args)`, `cc.<plugin_ns>.<tool>(args)`, `cc.call(name, args)` — and calls into cc's tools go through the same gate as a direct call (a plugin name only a program can call runs inside the program instead), so a conductor chains or aggregates many calls and reads only the digest. `cc.describe_tools()` (in-script only) looks tools up, with TypeScript signatures; a literal call to an unknown tool refuses the whole program before it runs; a long call streams progress to a client that accepts it and can be cancelled. The contract, limits, plan-mode behavior and samples: [code-mode.md](../code-mode.md).

**Contract conventions (clean, no legacy aliases).**
The worker handle is always `sessionId` (stable across respawn / `--resume` / restart, **and** across a `renew_session` or a prune — it is a permanent public id, never the CLI's rotating one); the per-process `instanceId` is internal and **never** appears on, nor is accepted by, the conductor-facing surface (a legacy `{id}` hard-fails; the REST/browser path keeps `id`).
Every worker-addressing tool accepts three forms — the public id, an unambiguous **prefix** of it, or **any** of the session's backing/segment ids (permanently, so ids already written into wiki pages and old cards keep resolving) — resolved at the MCP boundary; exact matches always win, an ambiguous prefix soft-refuses `{ok:false, code:'SESSION_AMBIGUOUS', matches:[…]}` (see [protocol/mcp.md → MCP tool protocol](../protocol/mcp.md#mcp-tool-protocol)).
**`describe_session` is the one scoped exception to the third form**: it takes the handle (or a prefix of it) only, and a backing/segment id soft-refuses `SESSION_NOT_A_HANDLE` naming the handle that owns it, so a conductor never holds a `~/.claude` UUID — see [protocol/mcp.md → Public vs backing id](../protocol/mcp.md#mcp-tool-protocol).
Worktree is always `worktree`, and takes the one registered name.
Worker resolution is **strict-live + soft-erroring** — `{ok:false, code:'SESSION_NOT_LIVE'|'SESSION_UNKNOWN', reason}`, and **never** brings a worker back: reviving a stopped session is `spawn_instance({resume})`, an explicit call, never a side effect of addressing one — except for the three call sites that read a session's bytes rather than drive it (`get_transcript`, `get_recent_messages`, `send_prompt`'s `forward` source), which fall back to the on-disk transcript so a retired worker stays readable and forwardable.
`describe_session` is a further exception in the same direction, and not a fourth byte-reader: it describes a **retired** session from its on-disk session **row** rather than refusing `SESSION_NOT_LIVE`.
The row is built by `sessionRowForCwd` on the same per-file builder as the listing (`listSessionsForCwdWithCounts`), from that session's own transcript(s) only — a head read for the first prompt, a tail read for last-activity and an awaiting-user scan of each candidate transcript (the session's current segment and, for a legacy full-UUID record, its own file), never a sibling transcript or a directory listing. It does touch the transcript, but it serves that row and never the session's **content**, and it never resolves through `getInstOrDisk`, which is the line the three byte-readers sit on.
It falls back to `SESSION_NOT_LIVE` only when the orchestrator still holds the session in memory but nothing on disk describes it.
Inputs are schema-validated (unknown properties rejected); text-payload tools (`project_read`, `project_diff` diff mode, `project_bash`, `system_bash`, `get_recent_messages`) append raw un-escaped body blocks after the `content[0]` metadata; the five recon read tools, `describe_playbook` and `enumerate_remotes` instead return a plain-text rendering as their whole result (no JSON); `ok:false`+`code` for soft refusals, prose+`statusCode` for errors — all of that is the **text format** (`?format=text`) every worker reads; the JSON format is [mcp-applications.md](../mcp-applications.md).
Full wire contract: [protocol/mcp.md → MCP tool protocol](../protocol/mcp.md#mcp-tool-protocol).

- **Audience:** workers (conducted or hand-spawned, i.e. any non-`.conduct` session) are offered only the `all`-audience core tools; the spawn, drive, land and registry tools are conductor-only (`audience` on each registry entry; [protocol/mcp.md → MCP tool protocol](../protocol/mcp.md#mcp-tool-protocol)).
- **Read:**
  - `list_projects`, `list_worktrees` — **text-rendered** in the text format (see [protocol/mcp-results.md → Rendered read results](../protocol/mcp-results.md#rendered-read-results)). A worktree the user has locked carries a trailing `locked` cell on its row. `list_projects` counts a project's live workers (`live N`) but does not name them — that is `list_sessions`' job; every row has the same shape whatever kind of project it is — the listed `path` is the tree's real path, and the only extra line a row can carry about itself is `! unreadable project record`.
  - `list_workspaces` — bare listing.
  - `enumerate_remotes` — **text-rendered**; which `remoteId`s registered Systems' providers are configured to route to. Args `system?` (one registry id; omit for every registered System, `local` included). Needs the `remoteSystems` platform capability. One block per System, in registry order: `<id> · <label>`, then one of three states, never collapsed — `enumerable — N remotes` with one id per line (`no configured remotes right now` for an empty list), `not enumerable — <reason>` (`local`, decided by id and never asked, or a provider that does not advertise remote listing — its Remote is named by hand), or `enumeration failed [<code>] — <reason>` (an unknown id, a row with no provider command, an unreachable provider, an error answer, the timeout, or a list cc will not believe). A failure is reported per System and never as an empty list; one failing System does not hide the others. Each call asks the provider afresh — nothing is memoised. A listed id is configured, not necessarily reachable. Unlike a plugin tool that lists one provider's own records, it asks every System through cc's provider protocol and returns only the `remoteId`s a project's Remote field takes. Same caller as `GET /api/systems/:id/remotes`. Sample:
    ```
    SYSTEMS (4)

    local · This machine
      not enumerable — cc's own machine has no named remotes

    prod-box · Prod box
      enumerable — 2 remotes
        ctr-a
        ctr-b

    plain · Plain
      not enumerable — system 'plain' does not advertise remoteListing — a remote is named by hand

    lab · Lab
      enumeration failed [SYSTEM_NO_PROVIDER] — remote enumeration of system 'lab' is registered on system 'lab', which has no provider command — give it one in Settings → Systems
    ```
  - `list_sessions` — **text-rendered**; the single session-listing entrypoint (live workers *and* resumable stopped sessions). Args `project?` (omit = everything; **covers the project's worktrees**, validated — an unknown name soft-refuses `PROJECT_UNKNOWN`), `worktree?` (narrows; requires `project`, else soft-refuses `PROJECT_REQUIRED`), `includeArchived?` (default false). Output groups by directory — each project's main checkout first, then its worktrees — with a per-group `live N · inactive N · archived N` header carrying the branch. A worktree group also shows `↑N ↓N vs base` (commits vs the base branch it merges into); a main checkout shows no divergence — its equivalent is vs the remote upstream, a different question, reported by `list_projects` instead. Live rows lead their group marked `LIVE`, carrying displayStatus, activeAgentTasks and backgroundJobs (`jobs N`, plus one `job "<title>" — running <duration>` line per running background Bash job); inactive rows are one line each (sessionId, last-activity, playbook/stage, flags, title), newest first. Archived collapses to a per-group `+N archived` line unless `includeArchived:true`. The `resumes-hot` flag marks a session whose resume comes up in `bypassPermissions`. `owner <sessionId>` (live workers) and `awaiting-user <kind>` / `awaiting-user-via <source>` (live and inactive rows) flag the root conductor and an unanswered ask; archived rows are not derived here. Every live row carries a `context <used> / <window> (<pct>%)` line in raw tokens (`—` for an unknown figure) — see [protocol/mcp-results.md → Rendered read results](../protocol/mcp-results.md#rendered-read-results).
  - `describe_session` — **text-rendered**; one session's row addressed by its handle, live or retired, plus the project and worktree that own it. A live session renders the same `LIVE` worker block `list_sessions` prints; a retired one renders the same single session line, which carries no mode/effort/model because there is no process to read them off; its `awaiting-user` flag is derived even when the session is archived. `sessionId` takes the **handle only** — a backing/segment id soft-refuses `SESSION_NOT_A_HANDLE` naming the handle that owns it — and `SESSION_UNLOCATABLE` says the transcript exists but no registered project or worktree owns its directory.
  - `get_transcript` — disk-backed ring-first event stream (forward-paged via `fromSeq`, inclusive); also serves a **retired** session wholly from its transcript (`source`, `status:"exited"`). A page stops short of `limit` rather than exceed one MCP result (`hasMore`/`nextFrom` continue), and an event too large for any page arrives as an `omitted:true` stub with its size. A conducted worker's `user_echo` carries `author` (`human`/`conductor`); absent means unknown. A live worker that renewed reads its current context only: evicted pre-renew events surface as one `history_gap` at the front of a walk from `fromSeq: 0` (or of a default call that reaches that far), never on an incremental poll.
  - `get_recent_messages` — multi-block (text + narration + tool_use + thinking; narration by default as a `--- narration ---` body section, thinking only with `includeThinking`), default-call bonding, disk-backed ring-first; also serves a **retired** session wholly from its transcript. Tool inputs come back as a per-argument descriptor (pointers verbatim, oversized arguments marked) unless `includeToolCalls:true`. A result over one MCP result's budget is cut shorter, then the oldest messages dropped (a plan/questions message last), every cut flagged (`planTruncated`, `questionsTruncated`, `omittedForBudget` + `hint`, `blocksOmitted`). `promptedBy:"human"` marks a message whose turn the human prompted directly.
  - `project_status` — **text-rendered**; dirty-state output capped.
  - `project_read` — path-traversal guarded, multi-block (metadata + body). `maxBytes` defaults to and is capped at the most one result carries; a cut line-range read ends on a whole line named by `endLine`, so `offset: endLine + 1` continues — a single line longer than the cap is cut mid-line with a marker and `lineTruncated:true`.
  - `project_diff` — unified diff, summary mode, line-index pagination; every page fits one MCP result (an over-long line is cut, `lineTruncated`), summary mode pages `files` by index with whole-set `totals`, and the side lists are capped with `<list>Truncated` + `<list>Total`.
  - `list_project_conventions` — `{conventions, incomplete?}`; hasScaffold flag per convention. `incomplete` appears **only** while the convention catalog is degraded — cc could not read a plugin's conventions and cannot tell those apart from conventions that are genuinely absent. It is phrased conditionally on the loss, because the flag fans out to every convention scope and can fire where this scope lost nothing: whatever *is* missing from the listing cannot appear in the line-1 `CONVENTIONS.md` marker of a project created from it, and no regeneration adds it back.
  - `list_conductor_conventions` — `{conventions, incomplete?}`; conductor convention catalog. Same degrade field, with the opposite consequence: nothing here is committed, since the role doc is recomposed from the catalog on every spawn.
- **Shell** (read-only inspection only): `project_bash` — run a shell command inside a project/worktree cwd, in the exact shell environment claude's own built-in Bash tool uses (the `rg`/`find`/`grep` shims and shell functions/aliases from a captured shell snapshot, generated once per (`claude` version, shell) via a throwaway one-shot `-p` run — spawned through the **Fast capability tier**'s bound backend (Settings → Models) — plain `claude -p` on the identity `claude` row, or that row's command template followed by the claude args (the built-in `ollama` row happens to end in `--`, but a template need not — e.g. `ollama launch claude --model <tag> --yes -- -p ...`) — honoring that tier's model either way (no Anthropic default fallback) — cached under `<store>/shell-env/` as `bundle-<version>-<bash|zsh>.sh` (the cache key is the real `claude --version`, independent of the Fast tier's backend), and memoized in-memory for the life of the daemon process — at most one `claude --version` spawn per restart; see `src/claudeShellEnv.ts` + the shared `resolveBackendLaunch()` in `src/claudeLauncher.ts`).
  The bundle records which shell (bash or zsh) actually produced it, and `project_bash` spawns that same shell to source it — a zsh-flavored capture (e.g. oh-my-zsh completion internals) is only ever re-sourced by zsh, never by bash.
  Mirrors `project`/`worktree` for cwd scoping plus the meaningful subset of the built-in Bash tool's schema: `command` (required), `description` (shown in the transcript bubble in place of the command; never read server-side), `timeout` (ms; the default is in the `project_bash` schema, the clamp is `clampBashTimeoutMs`).
  **multi-block** — metadata `{project, worktree, cwd, exitCode, durationMs, truncated?, timedOut?, descendantsMaySurvive?, outputMayBeIncomplete?, error?}` + a raw body block carrying the combined stdout+stderr output in arrival order; a non-zero `exitCode` is a normal result, not a tool error; (`project_bash` only) `outputMayBeIncomplete:true` means a background process the command started held the output open after it exited, so later output is missing (the body ends with a marker saying so; on POSIX the process is also stopped unless it detached, on Windows it keeps running); `truncated:true` means retained output was capped at the bash output cap (`BASH_OUTPUT_CAP`) but the command still ran to completion (drain-and-discard, not kill-on-cap); on `timeout` (the only hard kill) the whole process group is killed, `exitCode` is `null`, `timedOut:true`.
  Replaces the former `grep`/`glob` tools — use `rg`/`grep`/`find` through this tool for search.
- **Shell on a system** (read-only inspection only): `system_bash` — run a shell command on a REGISTERED SYSTEM addressed directly, with **no project in play**, so a box can be inspected before anything is placed on it.
  Args `system` (a system registry id — `local` refuses `SYSTEM_IS_LOCAL` (400), since that is cc's own machine and the caller has its own Bash tool for it), `remoteId?` (one of that system's named targets; omit, `null` or `""` all mean the provider's own default target), `command` (required), `cwd?` (absolute path on that system; omit or `null` for `/`), `description?` (shown in the transcript bubble in place of the command; never read server-side — the same property `project_bash` takes) and `timeout?` (ms; the default is in the `system_bash` schema, the clamp is `clampBashTimeoutMs`).
  That `/` default is the one path [systems-protocol.md](../systems-protocol.md) §7 requires every conforming provider to accept; a relative `cwd` refuses `CWD_NOT_ABSOLUTE` (400) before the system is resolved.
  `list_projects` names a project's placement (`system <id>` / `remoteId <target>`) only when it is on a **non-local** system — `local` and a null `remoteId` are the deviation defaults and print nothing; `enumerate_remotes` lists every registered System and the `remoteId`s it is configured for, where its provider can say.
  The command runs in a **plain login shell** on that system — the captured `claude` shell-env bundle is a file on cc's own machine and is never sourced here.
  Resolution is `systemById`, so the same named refusals a project on that system would get reach the caller unflattened: `SYSTEM_NOT_REGISTERED` (501), `SYSTEM_NO_PROVIDER` (501), `SYSTEM_UNREACHABLE` (502), plus `SYSTEM_NO_REMOTES` (501) and `REMOTE_NOT_FOUND` (502) when a `remoteId` is named.
  **multi-block** — metadata `{system, remoteId, cwd, exitCode, durationMs, truncated?, timedOut?, descendantsMaySurvive?, error?}` + a raw body block carrying the combined stdout+stderr output in arrival order; the truncation, timeout and `descendantsMaySurvive` semantics are `project_bash`'s, computed by the one shared helper.
- **Transfer between systems:** `system_transfer` — copy ONE regular file from one System to another, or move it with `move:true`. Engine: `transferFile` in `src/systems/transfer.ts`; handler: `systemTransfer` in `src/mcp/handlers.ts`. Hidden with the other system tools when the host lacks `remoteSystems`.
  - **Args:** `from` / `to` (required) are each `{system, remoteId?, path}` — `system` a registry id, **`local` (cc's own machine) accepted on either side**; `remoteId` normalised as in `system_bash` (omit, `null` or `""` = the provider's default target; a non-empty one on `local` refuses `SYSTEM_NO_REMOTES`); `path` absolute on that system, no trailing `/`, no NUL, used **verbatim** (no lexical normalisation — the far side's kernel resolves it). Unknown endpoint keys are refused. `overwrite?` (default `false`), `move?` (default `false`).
  - **Result:** compact JSON `{from: {system, remoteId, path}, to: {…}, bytes, mode, moved}` — bare data, no `ok`; `remoteId` is the normalised target; `mode` is the octal string of the bits written (e.g. `"0755"`).
  - **Bytes:** verbatim (binary-safe), up to `MAX_FILE_BYTES` (`src/systems/protocol.ts`, inclusive); the whole file is buffered in cc's heap.
  - **Mode:** the source's `0o777` bits are applied to the destination exactly, unmasked by any umask; setuid/setgid/sticky are dropped and ownership is not carried.
  - **Symlinks:** a source symlink is followed for its bytes; a move removes **the link only**, never its target. The write is always atomic (temp file + rename, parents created), so a destination symlink is **replaced**, never written through.
  - **Refused before anything is written:** every code below except `DEST_UNVERIFIED`, `SOURCE_NOT_REMOVED`, a move's `SOURCE_CHANGED`, and a `WRITE_FAILED` whose `errno` is a transport failure (e.g. `ETRANSPORT`), which may have landed (see Known limits) — so a refusal without `written` does not by itself mean nothing was written. A special-file source is never opened.
  - **Move ordering:** the source is unlinked only after the write is acknowledged, the destination re-checked (a file of the written size) and the source re-checked (same size and mtime). A refusal from there on carries `written:true`, and a retry needs `overwrite:true`.
  - **Store guard:** on `system:"local"`, a destination — or a move's source — inside cc's store (`orchStoreRoot()`) refuses `PATH_IN_CC_STORE`; copying out of it is allowed. An accident guard, not a sandbox: the check is lexical, so a symlinked alias gets past it.
  - **Refusal codes** — every refusal is `{ok:false, code, reason, side?, errno?, written?}`; `side` (`from`/`to`) is set on the handler's codes, `errno` (e.g. `EACCES`, `ETRANSPORT`) on a System failure, `written:true` when the destination holds the file and the source was kept:
    - `ENDPOINT_INVALID` — `from`/`to` is malformed (not an object, unknown key, empty or non-string `system`, non-string `remoteId`, path not absolute, ending in `/`, or containing a NUL). Checked before either system is resolved.
    - `PATH_IN_CC_STORE` — a destination, or a move's source, inside cc's store on `local`.
    - `SYSTEM_NOT_REGISTERED`, `SYSTEM_NO_PROVIDER`, `SYSTEM_UNREACHABLE`, `REMOTE_NOT_FOUND` — `systemById`'s refusals, with the meanings they have for `system_bash`, returned rather than thrown.
    - `SYSTEM_NO_REMOTES` — the system serves no named targets; also a non-empty `remoteId` on `local`.
    - `SOURCE_NOT_FOUND` — no entry at the source path (absent, a dangling symlink, or a non-directory component on the way), or it disappeared before the read.
    - `NOT_A_FILE` — the source, after following links, is a directory or a special file; the reason names the kind.
    - `EFBIG` — the source is above `MAX_FILE_BYTES`, or a System refused the payload as too large.
    - `SAME_FILE` — `from` and `to` name one directory entry on one endpoint (realpath'd parent + leaf).
    - `DEST_EXISTS` — something is at the destination and `overwrite` is not set.
    - `DEST_NOT_A_FILE` — `overwrite` is set but the destination is a directory or a special file.
    - `SOURCE_CHANGED` — the read returned a different length than the stat (nothing written), or during a move the source's size or mtime changed after the write (`written:true`, source kept).
    - `READ_FAILED` — any other coded failure stat'ing, resolving or reading the source; carries `errno`. Nothing is written.
    - `WRITE_FAILED` — any other coded failure inspecting or writing the destination; carries `errno`. The source is kept.
    - `DEST_UNVERIFIED` — move only: after the write the destination is not a regular file of the written size, or cannot be re-checked. `written:true`, source kept.
    - `SOURCE_NOT_REMOVED` — move only: unlinking the source failed (an already-absent source counts as removed). `written:true`.
  - **Known limits:** the `DEST_EXISTS` check runs before the atomic rename, so a destination created concurrently in between is replaced. A copy of a file growing during the read gets its first stat'd bytes (a move refuses `SOURCE_CHANGED`). A source swapped for a fifo between the stat and the read can block the read indefinitely, because the type check runs on the stat. A transport failure during the write leaves the destination's state unknown — a retry without `overwrite` may answer `DEST_EXISTS` — and a crashed remote write can leave a uniquely named temp file beside the destination. Two registry ids reaching one machine are not detected as one endpoint, so `SAME_FILE` cannot fire across them: a move from one spelling onto the other with `overwrite` writes the file over itself, and only the size+mtime re-check stands between that and unlinking the file it just wrote — on a filesystem with coarse mtimes the re-check passes and the only copy is lost.
- **Create:** `adopt_project` (`{name, path, system?, remoteId?}` — register an EXISTING out-of-root directory as a project in place, or one on a target of a registered system; returns JSON, refusals as `{ok:false, code, reason}` — see **Out-of-root projects** above for the codes and for what cc writes into the target). `create_project` (`{name, conventions?:[slug,…], noProjectConventions?, system?, remoteId?, systemPath?}` — the new dir is `git init`-ed and the scaffold committed when git is available, so it can take a worktree straight away — otherwise it is a non-git project and the result carries `gitSkipped` (the reason) while still being created and seeded; optional `conventions` appends each picked convention's CLAUDE.md fragment inline (call `list_project_conventions`; 400 on unknown slug); `noProjectConventions: true` records a deliberate choice of no project conventions instead (400 `CONVENTIONS_NONE_WITH_SLUGS` beside a non-empty `conventions`), and omitting both records the choice as unset; any picked convention with `hasScaffold:true` also contributes its one-time setup directive, composed in selection order into one framed block **returned** as the result's `scaffold` field (empty/omitted when none) — nothing persisted, the conductor folds it into the first worker's brief).
- **Placement:** `set_project_remote` (`{project, remoteId}` — change which TARGET of its system a project is on, or clear it with `null`/`""`; refuses `PROJECT_PLACEMENT_IN_USE` (409, naming the live sessions and registered worktrees), `SYSTEM_NO_REMOTES` (501) and `REMOTE_NOT_FOUND` (502), all before anything is written; refuses a project on `local`). Twin of `PUT /api/projects/:name/remote` — both call the one helper, so both inherit the same guard.
- **Workspaces:** `create_workspace` (`{name}` — register), `delete_workspace` (`{name}` — removes registry entry + clears member assignments), `rename_workspace` (`{oldName, newName}` — atomic), `set_project_workspace` (`{project, workspace}` — assign or clear with `null`/`""`; refuses `.conduct`; auto-registers a new workspace name).
- **Spawn/drive:** `spawn_instance` (`createWorktree:true` makes a fresh worktree off HEAD; `worktree:"<name>"` (a non-empty string) attaches to an existing one; optional `backend` picks among the backends serving a model id ([models.md](../models.md#custom-models)); optional `title` names the worker's session with the same schema as `set_session_title` (`TITLE_SCHEMA` — refused `ARGS_INVALID`, not truncated, including a value a playbook stage pins), written once the session is minted so it survives an early exit, and retitling the session when combined with `resume`; a stage `pin` on `title` is dropped on a resume.
  A successful spawn (fresh or `resume`) whose caller (`/mcp/<sessionId>`) names a live session that is untitled and not in `plan` mode gets `SELF_TITLE_NUDGE` (`src/mcp/handlers.ts`) as a **PostToolUse hook block** on that call, not a result field — the same channel as the **Landing renewal nudge**; the result is the conductor view alone.
  Its text names the calling session, not the worker it started, as the one to title.
  It is not an injected turn.
  Nothing is persisted, so it stops once the caller is titled.
  Refusals, titled callers, plan-mode callers and anonymous callers never get it, nor does a spawn inside `run_code`, and the worker's `title` argument does not count as titling the caller.
  **The user does not see the nudge text in the tool result** — it reaches the model only.
  MCP-path spawns are always normal (archived on subprocess exit — transcript retained and resumable, just out of the default session list) with **no MCP knob for it**; mode still stays `plan` — `InstanceManager.create()` is policy-light and never couples persistence to mode, so conducted workers plan before acting; an explicit `mode` still wins.
  The UI's **Persistent session** checkbox and `POST /api/instances/:id/persist` are the human's affordances), `send_prompt` (`{sessionId, …}`; a mid-turn send to a worker whose model declares **no mid-turn steering** stops that turn at a block boundary — finished text and completed tool work are kept — and arrives as a fresh turn instead, told that its turn was cut off; same tool, same result shape.
  `approve_plan` / `reject_plan` / `answer_question` and the UI's composer and card surfaces take the same route, and no result field says which one ran; [protocol/subprocess.md](../protocol/subprocess.md#subprocess-protocol)'s `user` row is the authoritative routed-site list; **you are woken when its turn ends** — see below; optional `forward:{sessionId}` injects another worker's recent output into the prompt server-side — the same default `get_recent_messages` selection, framed as context-only, with the conductor's own `text` placed last, and rendered in the target's view as the forwarded-output bubble (see Live conversation → Forwarded worker output); an empty/tool-only source soft-refuses `NOTHING_TO_FORWARD` before any prompt is sent), `set_idle_timeout` (`{sessionId, timeoutSeconds}`; adjusts the HEARTBEAT window on one owned session and re-arms a running heartbeat — `armed:true` means a wake from the target was pending — with the default as its ceiling, so it can only shorten.
  The wake itself needs no tool: when an owned target hits `turn_end` (unless the wake is held — see **Wake on turn end** below) the orchestrator injects a stub user prompt into the *owner* via `Instance.prompt()`, naming the worker by sessionId; **folded wake** — on an ordinary `turn_end` delivered to an already-idle caller the stub **folds the worker's recent output inline** (the SAME content a default `get_recent_messages({sessionId})` call returns — bonded prose + plan/questions — via the shared `buildRecentMessages` builder + `flattenPayload`), so the conductor needs no follow-up call; the folded stub is tagged with a `[[cc:wake-callback]]` marker (`shared/wakeCallback.ts`) that the conductor UI renders as a **collapsible wake-callback bubble** (worker id + a one-line summary always visible — "finished its turn" for this folded variant; the other variants say plainly that it did NOT finish — with the folded payload collapsed by default; expanding it renders the payload, whose first line (the compact-JSON metadata block of the `get_recent_messages` result) shows as its own metadata line and never as markdown, with the rest rendered as markdown and its framing lines as plain paragraphs — `raw`/`md` toggle and a `copy` yielding the exact folded payload including the metadata line, never the summary) marked as system-injected by an orchestrator badge; caller identity is read from the `/mcp/<caller sessionId>` path baked into the per-worker MCP URL at spawn time (after the sessionId is minted); **carve-outs** — the heartbeat stub, the mid-turn-deferred stub and the force-abort **interrupted** stub all keep a plain "call `get_recent_messages` to inspect" pointer (no fold), while still being tagged with the marker (via `markPlainStub`, body-less) so they render as the **same wake bubble** — badge + summary line only, no expandable body or caret.
  On the interrupted one the carve-out is deliberate rather than incidental: a force-abort's output is PARTIAL, and the body separator is the client's "this is the finished result" signal, so folding it would invite the conductor to act on exactly what the abort was meant to stop it acting on.
  It reaches every owner except whoever called for the abort (that one is silenced), and the UI's stop button — same `Instance.interrupt` chokepoint — has no interrupter, so there every owner gets it; the idle-wake graph is keyed internally by the stable instanceId (the caller's public sessionId is translated at the dispatch boundary); the heartbeat repeats every window with a clearly-labelled "did NOT finish" stub while the target is mid-turn or holding the wake — **without consuming the pending wake** — so a hung worker is never misread as finished, and keeps saying so for as long as it can still finish.
  It does NOT ping forever: a target that is gone for good (subprocess dead with no prune/rewind/respawn reviving it) gets one final ping and then the heartbeat retires, because no `turn_end` can follow and an unbounded series would be a false report rather than a warning.
  Silence after a "did NOT finish" ping therefore means the worker died, not that the wake was lost; a conductor whose own model declares **no mid-turn steering** (Settings → Models) never receives a wake into its running turn — the wake is **held** and delivered at that conductor's own next `turn_end`, folded, or marked "no longer idle" if the worker has since started another turn), `set_mode`, `interrupt_turn` (default arms a deferred abort that fires at the next output boundary — returns `interrupting:true` meaning armed, not stopped; optional `force:true` ⇒ abort now), `kill_instance`.
- **Self-title:** `set_session_title` (`{title}` — names the CALLING session: the target is always the caller identity in the `/mcp/<sessionId>` path, and there is no `sessionId` argument, so passing one is refused as an unexpected argument. `title` must contain a non-whitespace character and is capped at `MAX_TITLE_LEN` by the schema's `maxLength` (refused, not truncated); clearing stays a UI-only action. Writes the same custom title as **Rename session**, so it shows in the sidebar, the header chip and `list_sessions`/`describe_session`, and survives restart, resume and renewal. Returns `{sessionId, title}`; no caller identity throws `caller identity missing`.) The always-on conductor core tells a conductor to name itself once its task is clear, and an untitled caller's `spawn_instance` is followed by `SELF_TITLE_NUDGE` as a PostToolUse hook block (see **Spawn/drive**).
- **Session renewal / prune:** `renew_session` (`{sessionId?, summary?, directive?, followUp?}`) — an agent renews its OWN session (sheds context about landed jobs — dead weight taxing every future turn — at a lifecycle seam, not because context is "full").
  Caller identity comes from the `/mcp/<sessionId>` path (the caller's public sessionId, pinned for its life — so it always targets the calling session, works only for a code-conductor-managed instance, and **stays valid across repeated renewal**); it hands off a self-authored `summary`, structured under the exact `## <heading>` titles `RENEW_SUMMARY_SECTIONS` (`shared/renewSeed.ts`) names, and code-conductor drives a **server-managed `/clear`** at the caller's next `turn_end`, rotating the CLI's context in place (**same OS process/pid**, old jsonl preserved) and reseeding the cleared session with the summary plus a **server-generated mechanical state block** as its first user turn (the UI renders that reseed as the renewal-reseed bubble — see User messages, above).
  **The session's `sessionId` does not change** — only the CLI's internal backing id rotates, and the rotation is recorded as a `renew` segment in the session's lineage (see [components/instances.md](../components/instances.md#srcsessionrenewts)), so every id a conductor, a kanban card or a wiki page holds stays valid.
  `summary()` reports `rotationReason`/`lastRotatedAt`/`segmentCount` so a conductor can still tell a freshly-renewed worker from a stalled one.
  Nothing is carried: `conducted`, the custom title, the recorded mode and the backend live on the session's public-id record, which the rotation never touches, and the new transcript's segment inherits `persistent`.
  The abandoned pre-clear transcript is **auto-archived** (its jsonl stays resumable but moves to the archived section), so a later resume/`spawn_instance({resume})` of the renewed session keeps its persistent/conducted/title state.
  The state block (built at reseed time, not arm time, so it reflects current — not stale — state) enumerates the live instances the caller spawned (`InstanceManager.liveOwnedBy`, via the same `callerInstanceId` ownership tracking the sub-agent panel uses) and the caller's own owned wake targets (spawn or dispatch, whether or not one is armed right now) — a safety net so a worker a degraded summary omitted is never orphaned: the mechanical list wins for **existence**, the self-authored summary wins for **intent**.
  The bare form is deferred to the caller's `turn_end` (not fired inline) so the tool call's own turn finishes first, and returns `{ok:true, willClearAtTurnEnd:true}`.
  **A conductor can also REQUEST a renewal** — `renew_session({sessionId, directive?, followUp?})` prompts that worker to renew itself and returns immediately (the request's own turn wakes the caller) (`{requested:true, …}`).
  The worker authors its own summary via its ordinary self-call, so the conductor never writes another session's working memory: `directive` is a PRE-directive (what to be sure to capture), `followUp` a POST-directive (its next job, fenced into the reseed under its own marker, so one call replaces renew-then-send_prompt).
  The request lives exactly one turn and **cannot be forced**: a worker that ends its turn without calling `renew_session` has DECLINED — it may be mid-rebase or holding state only it can land — and that expiry is reported as a note prefixed into the conductor's wake stub.
  Mixing the two forms' arguments (a `summary` with a `sessionId`, a `directive` without one, or targeting yourself) soft-refuses `INVALID_RENEW_FORM`; a target that is not free — mid-turn, or idle but owing a re-invocation turn, running subagents, or overage-parked — soft-refuses `SESSION_BUSY`, because a request needs a turn of its own.
  The decline note reaches the conductor that asked and no other, exactly once.
  Because it declares a `sessionId` it is a governable tool: a playbook stage may deny the request, while the bare form and the worker's own self-call are never gated.
  Empty summary soft-refuses `INVALID_SUMMARY`; a renewal armed while a prune is rotating the same session soft-refuses `SESSION_ROTATING` (and vice versa — the two mechanisms are mutually exclusive, because a prune makes `prompt()` 409 and the reseed is a `prompt()`).
  The clear is deferred further past an overage-queued turn or live subagents so queued/background work is never stranded by the rotation.
  Mechanism in `src/sessionRenew.ts` (`SessionRenewController`, keyed by the stable instanceId; no side-structure migration needed since the idle-wake graph and overage timers are instanceId-keyed too).
  A default-on conductor convention, `context-renewal` (`conventions/conductor/context-renewal.md`), says when to renew or prune; preparing a renewal is in `renew_session`'s description; a conductor's own landing trigger is the **Landing renewal nudge** (Conduct mode).
  **`prune_session`** (`{sessionId, keepLatestTurns?, pruneThinking?, inputMode?}`) is the other half of that convention and the MCP face of the Prune feature above: it rewrites the target worker's transcript with old tool outputs, oversized tool inputs and thinking replaced by size stubs, then respawns that worker against the pruned copy — no LLM pass, no summary, no turn spent, and the worker comes back **idle** with nothing seeded.
  Handler defaults (the schema's `default` is documentation only): `keepLatestTurns: 1`, `pruneThinking: true`, `inputMode: 'truncate'`.
  `keepLatestTurns: 0` prunes every turn including the newest; a value larger than the session has clamps to "prune nothing".
  Returns `{ok:true, sessionId, keptTurns, prunedTurns, saved:{thinking,toolInputs,toolOutputs}, contextTokensBefore}` — `saved` is the calibrated estimate (see Prune → Savings estimate) and `contextTokensBefore` is the worker's real ctx reading taken just before the prune (`null` when it held none), so a conductor can weigh one against the other; the SAME public `sessionId` it was given (only the backing id rotates), and deliberately **no** `oldSessionId`/`newSessionId`, which are internal backing ids.
  `keptTurns`/`prunedTurns` are what make a clamped `keepLatestTurns` legible.
  Soft refusals: `SESSION_UNKNOWN` / `SESSION_NOT_LIVE` (strict-live, like every worker-addressing tool), `SESSION_BUSY` mid-turn (routing to `interrupt_turn`), `SESSION_ROTATING` when a renewal or another prune already holds the target, and `INVALID_PRUNE_TARGET` when the `sessionId` is the caller's own (a prune respawns its target, so it would kill the calling process mid-call — `renew_session({summary})` is the self-directed form).
  Because it declares a `sessionId` it is prefix-resolvable and playbook-governable like the rest.
  Renew vs prune: renew at a **job seam**, when a summary is all that needs to survive; prune **inside** a job, when the worker must keep its recent working state and only its older payloads are dead weight.
- **Wake on turn end is a property of ownership.**
  A conductor OWNS a target if it spawned it (`callerInstanceId`) or has ever dispatched to it — `send_prompt`, `approve_plan`, `reject_plan`, `answer_question`, and the targeted `renew_session` each record the edge (from the `/mcp/<sessionId>` caller path) **before** the send.
  Arming happens in `Instance._setStatus`'s into-`turn` branch, so every transition into a turn re-arms one wake per live owner: prompted and **unprompted** turns alike, which is what covers an auto-approved plan rolling into implementation with no conductor call behind it.
  There is no `subscribe` parameter, no result field, and no opt-out; `idleTimeoutSeconds` (whole seconds, `minimum:1`, floored at both ends against `ORCH_SUBSCRIBE_TIMEOUT_MS` via `DEFAULT_SUBSCRIBE_TIMEOUT_SECONDS`) only shortens the heartbeat window.
  A failed ownership record never fails the send.
  One armed wake per owner→target pair, so a mid-turn steer on top of a dispatch still delivers exactly ONE wake.
  **A wake is held while the target still waits on work of its own.**
  At a turn end (or idle-drain settle, or prune) where the target is still waiting — a wake on its way to it, or a wake it is owed by a session that is busy, has live subagents, has not yet delivered that wake for any reason besides its own hold (e.g. a background-task drain whose report was dropped), or is itself waiting — the owner's wake and its heartbeat stay armed; the owner is woken at the first such point where the target is not waiting.
  Always woken through a hold: a turn that asked a question (`AskUserQuestion`) or put a plan up for approval (`ExitPlanMode`, not auto-approved), a force-aborted turn (INTERRUPTED), and the target's CLI exiting (EXITED) — except an exit inside a relaunch window: a commanded relaunch's (rewind, respawn, prune), and a restart model switch's for its whole run, including a crash after the switch was confirmed but before it settled.
  That crash is recorded (`describe_session`, the next `send_prompt`'s `SESSION_NOT_LIVE` with the exit) but delivers no EXITED wake; the owner learns of it on its next engagement or from the heartbeat's "did NOT finish" stub.
  A wait that ends without a turn releases the held wake once, with the target's folded output: the session it waited on removed (`kill_instance` or delete — so removing a grandchild releases the grandparent), a wake to it refused, or a disarm.
  Two sessions that own each other (a worker that `send_prompt`s its owner) do not hold each other: a session waiting only back on the one being decided does not count.
  The owner reads `awaitingWake` throughout, and a dispatch to a session it is already armed on restarts that heartbeat window.
  **A background Bash job is not held for:** a target that ends its turn with a `run_in_background` Bash job still running wakes its owners at that turn end, and the stub's always-visible summary (the wake bubble's summary line, rendered one job per line) lists each job — title (its description, else its command, truncated) and how long it has run — and says the worker is re-invoked when each job exits, which is the turn that wakes the owner again.
  Heartbeat stubs carry no job list.
  Cleared by `turn_end` / the idle task-drain settle / rotation completion / the worker's CLI exiting on its own mid-turn (all of which deliver — the last an **EXITED** stub pointing at `describe_session`, at once rather than at the next heartbeat), by `kill_instance` (which delivers nothing), and by `interrupt_turn({force:true})`, which clears the INTERRUPTER's own entry **before** the abort's own `turn_end` so that turn wakes it not at all — the conductor caused it.
  Every OTHER owner is still woken there and told the turn was **interrupted**, not finished (a fourth wake-stub variant, never folded — see [protocol/mcp.md](../protocol/mcp.md#mcp-tool-protocol)); silencing an owner that did not ask for the abort would strand a wait nothing else can end, and a target can have several owners.
  The UI's stop button goes through the same `Instance.interrupt` chokepoint, so it produces the same interrupted stub — with no interrupter, every owner gets it.
  A SOFT `interrupt_turn` deliberately leaves it armed: its boundary wait is unbounded, so the continuing heartbeat is the escalation signal.
- **Human prompts into a conducted worker are reported to its conductor.** Anything the human sends a conducted worker from the web UI — the composer, the plan Approve/Reject card, the question card, the rebase button — is recorded as the human's, and everything a conductor sends as the conductor's, in the worker's own transcript (so it survives a retire or restart; [protocol/subprocess.md](../protocol/subprocess.md#subprocess-protocol) → the `user` row). The worker's model does receive the literal marker block, but nothing explains it to the worker, and the UI does not show it. When a turn the human prompted (or steered) ends, the owner's wake **opens with a notice** that the human prompted the worker directly, quoting their message(s) — every finished, interrupted and exited variant, never the heartbeat; a conductor-started turn's wake is unchanged. A conductor send (`send_prompt`, `approve_plan`, `reject_plan`, `answer_question`) into a worker the human has prompted since the conductor's last wake returns a `humanPrompts` field quoting them, so a send that joins a human's turn is visible at once; the wake still follows. No separate wake is sent when the human prompts. **Known limits:** a hand-spawned session a conductor later dispatches to is not conducted, so it gets neither; a transcript with no marker reads as author unknown.
- **Plan handling (Conduct-mode verbs):** `approve_plan` (`{sessionId, feedback?}` — flips to bypassPermissions + sends canonical approval prompt), `reject_plan` (`{sessionId, feedback?}` — stays in plan mode, asks for refinement). Both share the same approval/rejection text as the UI's Approve & Implement / Reject buttons via `shared/planApproval.ts`. `approve_plan`/`reject_plan` record ownership like every turn-starting call (see above).
- **Question handling:** `answer_question` (`{sessionId, answers}`) — structured answer to a worker's `AskUserQuestion`, mirroring the UI question card. `answers` aligns by index to the worker's pending questions (re-derived from the ring, same source as `get_recent_messages`); each entry is `{option}` / `{options:[…]}` / `{text}` / `{}` with an optional `note`. Delivers text **byte-identical** to a UI submit — both call the DOM-free formatter in `shared/userQuestionAnswers.ts`. Soft-refuses `{ok:false, code}` with `NO_PENDING_QUESTION` / `ANSWER_COUNT_MISMATCH` / `INVALID_OPTION` / `NOT_MULTISELECT` / `NOTE_WITHOUT_OPTION` / `EMPTY_ANSWER`. A `note` is accepted only beside a pick (`option` or a non-empty `options`): beside `text`, alone, or on `options:[]` it is refused with `NOTE_WITHOUT_OPTION` + `questionIndex` (fold it into `text`). `options:[]` counts as no pick, the same as `{}`. An `option`/`options` label matches **byte-exact** — a dropped ` (Recommended)` suffix is refused — and `INVALID_OPTION` carries `offered` (the question's labels verbatim) beside `invalid`, with the same labels quoted in `reason`. Records ownership like every turn-starting call (see above).
- **Playbooks:** `list_playbooks`, `describe_playbook` (`{id}` — **text-rendered** on success; its `PLAYBOOK_UNKNOWN` refusal stays JSON), `playbook_state` (`{sessionId?}` — omit it for every run at once). All three are read-only and never create the event log they read. `spawn_instance` gains `playbook`/`stage`/`provenance` and `send_prompt` gains `stage`/`provenance`; under `enforce` a run-root `spawn_instance` is refused unless it names `playbook` + `stage` — but a `spawn_instance({resume})` of a playbook-tracked session is not a run root and inherits both from the session record. `list_sessions` rows carry `playbook`/`stage` (`null` when the session is not playbook-tracked). See [protocol/playbooks.md → Playbooks](../protocol/playbooks.md#playbooks).
- **Worktrees:** `create_worktree` (`{project, baseWorktree?, name?, lock?}` — see Feature branches above, and **Lock**), `delete_worktree` (success is `{project, worktree}`; a conductor caller whose landed work it removed gets the **Landing renewal nudge** as a PostToolUse hook block when that setting is on; soft-refuses `{ok:false, reason, code:'WORKTREE_ATTACHED'|'WORKTREE_DIRTY'|'WORKTREE_HAS_DEPENDENTS'}` unless `force:true`, and `WORKTREE_LOCKED` — checked first — even with `force:true`), `sync_worktree` (`{project, worktree}`; `action: already-in-sync|fast-forwarded|rebased|commit-required|rebase-conflict` — the last two are `ok:true` and carry a rendered `rebasePrompt`; it never prompts a worker), `merge_worktree` (`{project, worktree}`; fast-forwards the worktree's own branch onto the new merge commit; refusals carry a `code`: `WORKTREE_LOCKED`/`WORKTREE_BEHIND`/`BASE_BRANCH_MISMATCH`/`PARENT_MID_MERGE`/`PARENT_DIRTY`/`PARENT_STATUS_UNKNOWN`/`WORKTREE_DIRTY`/`WORKTREE_STATUS_UNKNOWN`/`NOTHING_TO_MERGE`/`MERGE_FAILED`/`SYSTEM_UNREACHABLE` — `WORKTREE_DIRTY` here is the worktree's own tree, not the parent's, and is overridable via `allowDirty:true`). `sync_worktree`, `merge_worktree`, and `delete_worktree` all refuse `WORKTREE_HAS_DEPENDENTS` (with `dependents[]`) — see Feature branches above. No tool clears the lock (`WORKTREE_LOCKED`), deliberately — only the user can, from the commits view — and only `create_worktree({lock:true})` sets it, at creation.

## Core skills
- **What** — Claude Code skills cc itself ships, loaded into every session it spawns. They live in cc's built-in Claude Code plugin root, `claude-plugin/` at the repo root (`CORE_CLAUDE_PLUGIN_ROOT`, `src/coreClaudePlugin.ts`), passed as the first `--plugin-dir` ([protocol/subprocess.md](../protocol/subprocess.md#subprocess-protocol)).
- **Namespace** — a core skill appears as `code-conductor:<skill>`. The prefix is the `name` in `claude-plugin/.claude-plugin/plugin.json`; nothing in code repeats it.
- **Adding one** — create `claude-plugin/skills/<name>/SKILL.md` with `name` and `description` frontmatter. The description loads into every session's system prompt, so keep it to one tight line. A dir without `SKILL.md` is not a skill.
- **Shipped** — `code-conductor:scripting` (`claude-plugin/skills/scripting/SKILL.md`): scripting cc tool calls through `run_code` ([code-mode.md](../code-mode.md)). Its sample is run by `tests/core-skill-scripting.test.mjs`. `code-conductor:worktree-hooks` (`claude-plugin/skills/worktree-hooks/SKILL.md`): where to put a worktree hook (tracked in-tree, untracked and excluded, or cc's store), how it runs, how to read its result, and recipes. Its labelled `bash <label>` samples are run by `tests/core-skill-worktree-hooks.test.mjs`, which requires the exact label set.
- **Delivery** — every session cc spawns: workers and the conductor, interactive and MCP-spawned, including workers whose project is on a remote system (the root is in cc's own checkout, so it is local, and it is on the remote worker's readable-path list). The list is frozen per session at create, so a skill added by an update reaches sessions created or resumed afterwards, not a bare respawn. One-shot calls (summaries, `askSession`) load no plugin roots.
- **Broken install** — if `claude-plugin/.claude-plugin/plugin.json` is missing, cc logs a `console.warn` naming the path and launches the session without the root; a failure resolving plugin roots never drops it.
- **Name collision (unhandled)** — an enabled plugin whose `claudePlugin` root declares `code-conductor` as its plugin.json `name` is passed through alongside the built-in root; how the CLI resolves two same-named roots is unmeasured.
- **Tests** — `tests/plugin-skills-launch.test.mjs` (fake CLI scenario `tests/fixtures/scenario-plugin-skills.json`); `tests/core-skill-scripting.test.mjs`; `tests/core-skill-worktree-hooks.test.mjs`.
- **Convention skills** — a convention can move its long procedure into a skill so it costs nothing in the system prompt until invoked: a `<!-- cc:skill <description> -->` line in its fragment file (`<!-- cc:skill:<name> … -->` in a scope's `core.md`) splits the inline rule above from the skill body below. The skill is delivered only where the inline part is — same toggle, same enabled+`ok` plugin, same scope (a worker's project skills follow its `CONVENTIONS.md` marker) — and refreshed on every launch. A Settings-authored custom convention takes the same marker line in its body (the editor previews the split and refuses a malformed marker on save). Namespaces: `cc-conductor`, `cc-workspace`, `cc-project` for built-ins and cores, `cc-custom-<scope>` for a custom convention's, `cc-<scope>-<plugin-id>` for a plugin's, so the inline part can point at it by name (e.g. "invoke `cc-conductor:<name>`"). Delivered to remote-backed sessions too. Grammar, lifecycle and layout: [components/playbooks.md → Convention skill parts](../components/playbooks.md#convention-skill-parts).

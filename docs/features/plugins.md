# Features: plugins

## Plugins
- **What a plugin is** — any project (in-root, or an **adopted** out-of-root directory) with a `conductor.plugin.json` at its root (schema: [docs/plugins/manifest.md](../plugins/manifest.md)). Each capability is one manifest key past the identity block — `KNOWN_TOP_KEYS` (`src/plugins/manifest.ts`) minus `id`/`name`/`version`/`pluginApi`, so a key added there is a capability unless it joins the identity block: a supervised backend process, an embedded frontend, MCP tools forwarded through the conductor's MCP server, **conventions** (entries joining the Conventions catalog as `<plugin-id>/<slug>`, each `project`- or `conductor`-scoped — see **Convention scope** below — and carrying a CLAUDE.md fragment and/or a one-time scaffold directive), **roles** (named model-bindings joining the role list as `<plugin-id>/<slug>`, resolvable by `spawn_instance`, user-rebindable in Settings → Models → Roles — the manifest binding is the default; a user override takes precedence at spawn), **row-menu buttons** (`menuItems`, need a frontend), **run_code members** (`runCode`: named members of the plugin's namespace, described like tools and backed by one ES module, that a `run_code` program calls as `cc.<ns>.<name>(args)` — [plugins/manifest.md → `runCode`](../plugins/manifest.md)), and **Claude Code skills** (a `claudePlugin` root contributed as a session-local `--plugin-dir` at every claude launch — interactive sessions and MCP-spawned workers alike). The contribution-only kinds need **no backend** — a manifest declaring no `backend` (`hasBackend`, `src/plugins/row.ts`) validates, enables, and never starts a process. Discovery scans the projects root at boot and on **↻ Rescan**; duplicate ids resolve first-alphabetical-project-wins (the rest show `conflict`).
- **Conventions & scaffolds** — an enabled plugin's `conventions` join the new-project dialog + `list_project_conventions` (namespaced `<plugin-id>/<slug>`).
  A convention carries a CLAUDE.md **fragment** (`file`, written into the project's regenerated `CONVENTIONS.md` at creation — regeneration drops the slug's text and names it in the file once the plugin is disabled/uninstalled, and it returns verbatim on re-enable; see the **Project** convention bullet in [settings.md](settings.md#settings-page-and-app-controls) and [components/web.md](../components/web.md#srcprojectclaudemdts) for the full behavior) and/or a **scaffold** facet (`scaffold:{text|file}`, a one-time setup directive; a custom project convention takes one in Settings too); at least one of the two is required.
  A convention flagged `hasScaffold` carries its scaffold invisibly in the dialog (no tag); when picked at creation its directive is composed (in selection order across all picked scaffold-bearing conventions) into one framed block **returned** by `create_project`/`POST /api/projects` under a `scaffold` field — nothing persisted, no spawn coupling.
  The conductor folds it into the first worker's brief; the UI displays it read-only in the create confirmation (v1), where a `gitSkipped` reason is shown too (the pane opens for either).
  A **scaffold-only** convention contributes nothing to `CONVENTIONS.md` but still emits its directive.
  A scaffold-bearing convention added later through **⋮ → Edit conventions…** gets its fragment, but its scaffold is not run.
  Only enabled+`ok` plugins contribute; a stale/missing fragment or scaffold `file` makes the plugin `invalid` at load.
  Since fragment and scaffold now live on one entry, author a scaffold-bearing convention to **degrade gracefully** if the scaffold step wasn't run (e.g. "if a project-local harness wrapper exists, use it; otherwise see the shared harness to create one").
  Updating a plugin's checkout (rescan, restart, an active-version switch, or Plugin Library **Update**) now reaches every referencing project's `CONVENTIONS.md` on that same request — no orchestrator restart needed (see limitations in [plugins/rest.md](../plugins/rest.md#rest--apiplugins)).
- **Convention scope** — every plugin convention declares a required `scope`. **`project`** and **`conductor`** are accepted today; `workspace` is **planned** and rejected at manifest load with a "not yet supported" error. A **`conductor`-scope** convention joins the Conductor-conventions catalog above (Settings → Conventions → Conductor) as its own checkbox, namespaced `<plugin-id>/<slug>`; it is **on by default while the plugin is enabled** (composed into the conductor's system prompt), unless the user has explicitly unchecked it (a remembered off-switch). Unlike a project convention it leaves no tracked in-tree artefact, so disabling the plugin (or unchecking its convention) simply drops it from the next conductor spawn's composed prompt — there is no marker keeping it named. The scaffold facet has no scope of its own — it's inherently project-scoped (it runs at project creation); a scaffold facet on a `conductor`-scope entry is simply never read (nothing outside project creation consumes it). ⚠️ A **`conductor`-scope** convention edits the orchestrator's **own** rules (the conductor role-prompt conventions that govern how it delegates/reviews/merges across all projects) — a powerful, trust-loaded capability (consistent with "plugins are trusted code", but far beyond a per-project convention); it requires the same explicit user opt-in as any other conductor convention, precisely because of that trust jump.
- **Trust stance (loud)** — plugins are **trusted own code**. Their frontends are same-origin iframes: plugin JS can call every conductor API the UI can. Enabling a plugin is equivalent to running its code with your conductor's privileges.
- **App switcher** — a dropdown (**Switch app**) that replaces a title once an enabled plugin contributes a frontend (zero plugins ⇒ every title stays a plain `<h1>`). It is the only plugin selector: it picks the plugin on screen. Rendered by `AppSwitcher` (`web/src/features/views/AppSwitcher.tsx`) from `GET /api/plugins`; each plugin entry shows the plugin's `frontend.icon`, else a plug; a plugin whose keep-alive frame is resident reads `<navLabel> (running)` (text, not colour).
  - **Where:** one switcher at a time, in the slot `switcherSlot` (`web/src/features/views/dockLayout.ts`) names for the plugin column's mode and the breakpoint. While the column shows a plugin at **split** or **full** width (desktop and phone, a split too narrow to fit included) it is the column bar's title, labelled with the plugin's name, and the sidebar and the phone drawer read a static `Code Conductor`. Otherwise it is the sidebar's switcher on desktop, the drawer's below `md`: on Conductor or under a covering view (Settings, Costs, Commits, Review) it reads `Code Conductor` with Conductor checked; in the **rail** (desktop only; its bar is hidden behind the strip) it reads the docked plugin, checked.
  - **An unlisted plugin's full view** (the route names a plugin the catalog no longer lists while others are listed): the bar's switcher reads the route's plugin id, with Conductor checked (**Checked entry**).
  - **Checked entry:** the menu's one checked radio item is the plugin on screen (`shownApp` in `web/src/features/views/dockLayout.ts`): the full view's plugin, or on desktop the plugin in split beside the session; otherwise Conductor, including while the route names a plugin the switcher no longer lists, or while Settings, Costs, Commits or Review covers a split.
  - **A pick from Conductor** opens the remembered mode (`mode` in **Plugin dock** below; default the full view). Below `md` a pick always opens the full view.
  - **A pick over a covering view** (Settings, Costs, Commits or Review) on desktop with split remembered closes that view onto the active session's anchor — whatever history holds beneath it, a plugin's full view included — and shows the picked plugin in split beside the session; with full remembered it opens the plugin's full view.
  - **A pick from a plugin** (from the bar's switcher) keeps the current mode: in full it opens the next plugin's full view and **replaces** the history entry (`openPlugin` in `web/src/features/views/api.ts`), so a plugin visit costs one entry however many switches it holds; in split it swaps the plugin beside the session (at its root) with no route or history change. Picking the shown plugin again, or Conductor from Conductor, changes nothing.
  - **Conductor** hides the plugin column completely, from split or full, and restores the active session's anchor (never `history.back()` — a deep link has no usable back entry). Picking Conductor while the route still names a plugin the switcher no longer lists leaves that plugin's view.
- **Plugin view** — `#plugin/<id>/<subpath>` shows the plugin's frontend in a full-page iframe: the **full** mode of the plugin column (`PluginView` in `web/src/features/views/PluginView.tsx`; on desktop the column is also the dock, see **Plugin dock**), with frames owned by `pluginFrames` in `web/src/features/views/plugins.ts`; src `/plugins/<id>/<subpath>` through the reverse proxy).
  Switching to an enabled-but-stopped plugin **auto-starts it behind a "Starting …" overlay** (REST status→start before the iframe loads, a bounded readiness window (`READY_TIMEOUT_MS`, `src/plugins/supervisor.ts`)); a start failure shows the error + crash tail with a **Retry** button instead of raw proxy JSON in the frame.
  A subpath change from outside the frame (a transcript link, the address bar; [plugin-ui.md](../plugin-ui.md) → Deep links) steers the open page there without reloading it, including back to a subpath after the page has moved itself.
  A plugin visit costs exactly **one** history entry (the bridge patches `pushState`→`replaceState` inside the iframe, and a switch to another plugin replaces the entry), so hardware **Back always lands on the conductor** and never on a split.
  The view has a bar (`<header>`, `--header-height`) above the frame: below `md` the `≡` **Open sidebar** button plus the plugin's switcher name (`appLabel` in `plugins.ts`, or the route's plugin id when the catalog has no row for it); on desktop, when its split could show, the **Dock to side** toggle, then the name (**Plugin dock** → The toggle).
  The name fills the bar and is the app switcher while one plugin or more is listed (**App switcher** → Where), else a plain heading.
  The bar's far-right control is `dockLayout`'s `dismiss`: **Collapse plugin dock** where a rail can show beside the session (desktop, a plugin the switcher lists; **Plugin dock** → Collapse), else **Close plugin** (below `md`, or a plugin the switcher does not list), which is the switcher's **Conductor** pick (`exitToConductor` in `web/src/features/views/AppSwitcher.tsx`): it returns to Conductor, so a keep-alive page keeps running hidden and no plugin is stopped.
  **Escape** collapses where Collapse shows, and only while focus is inside the plugin column or on the page body, never while a menu, Select or dialog is open; where Close shows it leaves the view from anywhere on the page.
  Back and a session pick leave the view too.
  Keys pressed inside the plugin's own page never reach cc (the bridge forwards none), so Escape there does nothing.
  The frame and the start overlay sit below the bar, so its controls stay reachable while a plugin starts or fails.
  The sidebar stays live (`/ws` events keep flowing) while a plugin is open, and, like every full-page view, the plugin view closes when another opens or a session is selected (the switcher returns to Conductor).
  Leaving the hash space, or switching to another plugin, ends the plugin's page (the shared iframe is removed or reloaded, freeing memory) — unless the plugin's manifest sets `frontend.keepAlive`: then its page keeps running hidden (a call, a stream, an open microphone) and is revealed without a reload on return, and the app switcher labels it `(running)` until it is evicted by Stop, Disable, a rescan that drops it, or a Restart, Update or version switch made from Settings → Plugins in this tab (a backend crash keeps it) ([plugins/manifest.md](../plugins/manifest.md) → Frontend keep-alive).
  Limitation: multi-page (non-SPA) plugins still pollute joint history.
- **Plugin session awareness** — a plugin docked beside a session (or open full-screen) can follow the session the user views, switch to a live session, and prompt one as if typed into its composer, through the optional `window.ccBridge` ([plugin-ui.md](../plugin-ui.md) → Session awareness).
- **Plugin theme** — a plugin page that loads the bridge and `/pluginTheme.css` ([plugin-ui.md](../plugin-ui.md)) shows cc's light/dark theme before its first paint and follows every change live: the sidebar theme toggle, and the OS theme while cc's theme is "system". A hidden keep-alive page follows too. cc's palette and the Geist fonts come from cc, so the page's colours are the host's own.
- **Plugin session width** — the same page also gets cc's committed session-column width as `--cc-session-width` (`<n>px`, or `none` under Full) in the full view; a page docked in the side pane (split or rail) gets `none`. Before first paint and live, through docking and expanding, hidden pages included (a hidden page keeps the value of where it was last shown) ([plugin-ui.md](../plugin-ui.md) → Follow the session width).
- **Plugin dock** — desktop only (`md` and up): the plugin column right of the session, whose width is its mode (`dockLayout` in `web/src/features/views/dockLayout.ts`). The app switcher alone selects what it shows.
  - **hidden** — nothing selected (Conductor): the session has the whole row and the column holds no control.
  - **split** — the selected plugin beside the transcript.
  - **rail** — the split collapsed to a `DOCK_RAIL_WIDTH` strip at the viewport edge holding **Expand plugin dock** and the plugin's name (vertical). The plugin's section stays mounted and live at its split width behind the strip (clipped, `inert`, hidden from assistive tech), so its page never reloads, resizes or loses its scroll position. The switcher moves back to the sidebar and still checks the plugin (re-picking it does nothing), Escape does nothing, and the rail shows instead of the forced-full cover in a window too narrow for a split (a rail always fits; Expand there shows the forced-full split).
  - **full** — the plugin fills the row: the plugin view above, or a split too narrow to fit (**Narrow windows**).
  - **The toggle** — the column's mode control, a button in its header strip (above the plugin's page, never over it), the bar's first control, left of the switcher (the plugin's name; **Plugin view**): **Expand to full view** in split, which remembers `mode: 'full'` and opens the full view at the docked page's route; **Dock to side** in the full view, which remembers `mode: 'split'` and docks the plugin at the page's current route, back beside the session. It is offered only when its target layout can show: none below `md`, for a plugin the switcher does not list, or when no split fits.
  - **Collapse** — **Collapse plugin dock**, the bar's last control, right of the switcher, in split and in the full pane (the forced-full split, and the full view of a listed plugin on desktop), parks the plugin as the rail beside the session, and the switcher's **Conductor** closes it. From the full view (`collapseFullView` in `dock.ts`) it docks the page at its route collapsed and leaves the view without reloading the page, and the remembered mode stays as it was. Escape in the full pane is a keyboard Collapse (**Plugin view**). The collapse is cleared by every close of the split (Conductor pick, a session pick over a forced-full split) and by entering the full view, and a pick of another plugin docks expanded, so the full view and a new pick always show expanded and **Dock to side** docks expanded. A keyboard activation (not a mouse click) of Collapse, or Escape, moves focus to the rail's Expand, and of Expand to the bar's Collapse, in the forced-full split too.
  - **The remembered mode** (`mode`, default `'full'`) is what a pick from Conductor opens. Only the toggle writes it; Conductor, Collapse (also from the full view), Escape and session picks keep it. A pick from the switcher opens the full view on `'full'` only while no plugin shows beside the session; with one in split or the rail it swaps in split.
  - **Full and split never coexist:** entering the full view (a pick, Expand, a link while no split shows, the address bar, Forward) clears the split selection, so leaving the full view by any exit but Collapse (and Escape, which collapses where Collapse shows) lands on Conductor.
  - **The handle** on the column's left edge in split (`role="separator"`, **Resize plugin dock**, the same `useResizableWidth` as the sidebar, `edge: 'left'`) only resizes: a drag is clamped to `DOCK_PANEL_MIN_WIDTH`–the room that leaves the transcript `DOCK_TRANSCRIPT_MIN_WIDTH` (`maxPanel`), with no snap to another mode, and its release commits the clamped width. Double-click or Enter resets it to `DOCK_PANEL_DEFAULT_WIDTH` (the stored width is removed). ArrowLeft / ArrowRight widen / narrow by `RESIZE_KEY_STEP`; a key a limit stops writes nothing. `aria-valuemin` is `DOCK_PANEL_MIN_WIDTH` and `aria-valuemax` the transcript limit. Before the main row's first measurement the handle's ceiling is the window's (`maxPanel(window.innerWidth)`), so `aria-valuemax` and every committed width are finite, while the layout already counts a split as fitting.
  - **Links:** while the dock shows a plugin beside the session (split, rail, or a split too narrow to fit), a plugin link shows its target in the dock at its subpath instead of entering the full view. That covers a transcript or markdown click, and two links in a plugin page the bridge catches (`openLink`, [plugins/runtime.md](../plugins/runtime.md) → Bridge protocol): a plain click on any `http://cc.internal/` link whatever its `target`, and a `target="_top"` / `_parent` link to cc's page with a `#plugin/` hash. A modified or middle click on a `cc.internal` link in a plugin page stays the browser's and reaches the dead host (limitation). A link to another plugin switches the dock to it; a link to the docked plugin steers its frame without a reload; a rail expands. The link changes no route and pushes no history entry. A plugin the switcher does not list opens the full view. The address bar, Forward, deep links, modified and middle clicks, a window below `md`, and a covering view (Settings, Costs, Commits, Review) behave as without a dock.
  - **History:** links shown in the dock push no entry. Expand pushes one entry; Dock to side steps back (or writes the session's anchor from an entry the app did not push); split picks, swaps and resizes push none, and the docked page's own navigation never reaches the URL (it is mirrored into the dock's saved subpath). Escape in split does nothing, and a session pick in split swaps the session beside the plugin, which keeps its frame.
  - **Where:** beside the session view only; Settings, Costs, Commits and Review hide the column (opening one is leaving the plugin: plain frames end, keep-alive frames hide) and the switcher reads Conductor. Leaving one (Back, Escape) shows what is beneath it: the session with the split again, or a plugin's full view, whose entering had already ended the split. A pick from the switcher closes the covering view (**App switcher** → A pick over a covering view).
  - **Narrow windows:** a stored width wider than the room shows clamped to it, and the stored width stays the preference. When not even `DOCK_PANEL_MIN_WIDTH` fits (`canSplit` false: a narrow desktop, or a wide sidebar), the split shows full-screen over the session: the route stays the session's, nothing is written, and there is no toggle. Escape collapses it to the rail (a rail always fits; no history entry is stepped, the split stays selected and remembered), and Expand covers the session again; a user's session pick (not the first-connect restore after a reload) closes it: the switcher reads Conductor, the split stays remembered, and no history entry is stepped. A later pick reopens it (full-screen again while the window stays too narrow); widening while it shows restores split at the stored width.
  - **Persisted** per browser in `localStorage`: `code-conductor:plugin-dock` (`DOCK_STORAGE_KEY`, `{id, subpath, mode}`) and `code-conductor:plugin-dock-width` (`DOCK_WIDTH_STORAGE_KEY`), and `code-conductor:plugin-dock-collapsed` (`DOCK_COLLAPSED_STORAGE_KEY`, `'true'`/`'false'`, global per browser like the width), all in `web/src/features/views/dock.ts`. Any other stored shape (such as `{id, subpath, open}`) reads as nothing selected with the full view remembered. A reload restores what was on screen: the split at its plugin, route and width, or the full view from its URL.
  - **Toasts** sit below `--header-height` at every width, so none covers the strip's toggle; on desktop their right offset is `TOAST_EDGE_GAP` (`web/src/ui/toastLayout.ts`, `App.tsx`).
  - **Below `md`** there is no split, no handle, no rail, no Collapse and no toggle: the plugin view is the full-page view, whatever the stored dock says, and its bar ends in **Close plugin**.
- **Settings → Plugins** — management group (`PluginsSection` in `web/src/features/settings/PluginsSection.tsx`): per-plugin state badge (`discovered / disabled / enabled / stopped / starting / ready / crashed / failed / invalid / conflict / incompatible`), contribution badges (`N project conventions`, `N roles`, `N playbooks`, `Project scaffold: N` with a per-scaffold name/description preview), immediate Enable/Disable/Start/Stop buttons, an **Auto-start** switch (enabled, local, backend-bearing plugins only — beside Start/Stop; saved through the same one-action-at-a-time flow and read back from the reloaded row; it only marks the plugin to start when cc next boots, unless it is already running — see [plugins/runtime.md](../plugins/runtime.md#auto-start)), crash-output expander, ↻ Rescan, and an **active version** dropdown (main + the project's worktrees). A ready row shows `running <version> @ <sha7>`, ` · update available` when stale, + port. A **backendless (contributions-only)** enabled plugin shows state `enabled` and only a Disable button (no Start/Stop/version — it has no process). One action runs at a time: the clicked control shows a spinner and a pending label (e.g. `Restarting…`, from `PENDING_LABEL` in `PluginsSection.tsx`; a version switch shows it beside its select). Every other plugin control, including the Library's, is disabled until the action's request and the list reload that follows it land. Start, Restart and a version switch answer only once the backend is ready (or has failed), so the spinner spans the real startup. A failure shows `<action> failed: <error>` on the Installed card's status line and re-enables the controls.
- **Restart on stale code** — a running plugin whose active checkout's HEAD has moved past the sha it was started at (a commit landed while it was running) is flagged `stale` and gets a **Restart** button next to Stop (stop + start in place, `POST /api/plugins/:id/restart`, 409 if not running). No button while stopped, backendless, or already at the started-at sha; a non-git checkout is never stale. Plugin Library **Update** does this restart itself (see below) — the manual Restart button stays for a plugin whose code moved by some other means (e.g. a hand-run `git pull`).
  - **Restart all** — beside **Rescan** in the Installed card's header (`restartAll` in `web/src/features/settings/PluginsSection.tsx`; the per-row condition is `canRestart` in `pluginLogic.ts`):
    - Shown only while N > 0 or a run is in progress (hidden, not disabled); label `Restart all (N)`, N being the rows showing a per-row **Restart**.
    - Runs the same `POST /api/plugins/:id/restart` for each, one at a time, in list order over the rows as of the click; progress `Restarting i/n…` on the button and `Restarting <id> (i/n)…` on the line.
    - Continues past failures; reloads the list once at the end and announces one `restart` change naming the restarted plugins; summary `Restarted X of N plugins — <id> failed: <error>` (error-toned when anything failed or the reload failed).
    - Disabled while any plugin action runs; during its run every other plugin control, **Update all** included, is locked.
- **Plugin Library** — below the installed-plugins list, a catalog of *installable* plugins (git repo URLs) with an **Install** button that clones the repo into the projects root (`GET`/`POST /api/plugins/library[...]`, `src/plugins/library.ts`).
  Install clones then **enables the freshly-discovered plugin by default** (so its conventions go active immediately); enabling is start-neutral (backends start lazily on first use), so nothing launches at install time, and an invalid/conflicting manifest is left disabled.
  Once cloned, the project surfaces in the list above through the normal discovery/rescan flow, same as any other plugin project.
  A set of built-in library entries is present even with no library dir (hidden when `settings.json` sets `plugins.builtinLibrary: false`) — overlaid by drop-in manifests dropped into `<orchStoreRoot()>/plugins/library/*.json` and any configured `plugins.libraryDirs` (one JSON object per file: `{id, name, description?, repo, postClone?, postPull?}`; a later layer's entry with the same `id` overrides; malformed/incomplete files, and files whose `repo` is refused, are skipped with the reason in the Library status line, never fatal).
  **Local / offline catalogs** — a `repo` may be a `file:///` URL or a `catalog:<path>` relative to its JSON, naming a bare repo or a git bundle, so a mounted volume of mirrored repos installs and updates with no network; rules in [plugins/rest.md](../plugins/rest.md#local--offline-catalogs).
  An entry whose derived project name is registered as a project (the record, not a directory on disk) shows "installed as `<name>`"; an **Update** button only appears when the checkout is actually **behind its origin** — `list()` runs a bounded (8s), best-effort `git fetch` per installed entry before comparing (reusing `getProjectUpstreamStatus`, `src/worktrees.ts`), so a fetch timeout/no-remote/detached-HEAD/non-repo just hides Update rather than crashing the list; an up-to-date entry shows "installed as `<name>` · up to date" instead.
  The target project name is derived from the resolved clone URL's last path segment (`.git` or `.bundle` suffix stripped); `repo` is always a URL — `http:`/`https:`/`git:`/`file:`/`catalog:`; a bare path is refused with a message naming both local forms.
  A failed/timed-out clone shows the error + clone-output tail (reusing the crash-tail `<details>` styling) and cleans up any partial directory so the same install can be retried.
- **Plugin Library — live install/update output** — Install/Update stream their progress as NDJSON (`streamNdjsonAction`, `src/ndjsonAction.ts`), so the clicked row shows its button disabled + relabeled (`Installing…`/`Updating…`) and a small live output box (`LogBox`) filling in with clone/pull/hook stdout+stderr as it runs, instead of only a result appearing after the fact. On failure the row's live output stays visible and the button re-enables; on success the whole library list re-renders (dropping the live box, re-evaluating Update availability).
- **Plugin Library — Update all** — an **Update all** button is the Plugin Library card's header action (`updateAll` in `web/src/features/settings/PluginsSection.tsx`):
  - **Second surface:** Settings → About's **Version** card shows the same action as **Update plugins (N)**, hidden when N is 0 and no run is in progress. Both surfaces read the count, progress label, lock and action from `useUpdateAllPlugins` (same file), so a run started on either shows on both.
  - **Label / enablement:** `Update all (N)`, where N is the entries currently showing a per-row **Update** (`installed && updateAvailable`); disabled when N is 0 and while a run is in progress (a reload mid-run — reopening Settings or a switch between Settings sections — re-arms neither it nor any row's Install/Update, and both, with every plugin action, stay locked through the run's closing reload). It is also disabled while a row's own Install/Update or any other plugin action runs.
  - **Runs** the same `POST /api/plugins/library/:id/update` for each of those entries **one at a time** — each update rescans, restarts backends and regenerates referencing projects' `CONVENTIONS.md`, and the server has no lock against a concurrent one. Each row streams into its own live output box; the button reads `Updating i/n…` and the status line `Updating <name> (i/n)…`.
  - **A failed update does not stop the run.** At the end the list reloads once; the status line reads `Updated X of N plugins`, followed by each failure (`<name> failed: <error>`) and each soft warning (the single-Update wording). Their output tails are collected into the Library output box, each under a `── <name> ──` header.
  - Every other plugin action (Rescan, Enable/Start/…, Install, a row's Update) is disabled during the run.
- **Plugin Library — postClone/postPull + Update** — an entry may declare `postClone`/`postPull` shell commands (run via `bash -lc`, cwd = the project directory, e.g. `code-playwright`'s `bash install.sh`) that install the plugin's own dependencies.
  `postClone` runs once, right after a successful install (clone + rescan); **Update** (when shown — see above) runs `git pull --ff-only` → rescan → `postPull` → **auto-restarts the plugin's own backend if it's currently running** (a stopped plugin is left stopped — it'll pick up the pulled code lazily on its next start) → regenerates every project referencing one of its conventions. cc's own regenerated `CONVENTIONS.md`/`CLAUDE.md` in the plugin checkout never block the pull: they are discarded first and regenerated after, even when the pull fails.
  `CONVENTIONS.md`'s body counts as cc's (it is rewritten on every regeneration anyway); only its line-1 selection marker, when it differs from what cc derives from HEAD, is a hand edit.
  A hand-edited `CLAUDE.md` (any byte off cc's prepend), a changed selection marker, and any other local change are kept, and a failed update names them.
  **If a backend is actually running and `postPull` fails, the auto-restart is skipped entirely rather than attempted** (checked in that order — a plugin with nothing running reports the same "nothing to restart" either way, never a skip) — a broken `postPull` leaves the checkout half-built, and restarting into it would trade a healthy backend serving old code for a crash-looping one serving no code at all; the running backend is left exactly as it was, still serving the pre-update code, until the user fixes the dependency and retries Update (or trusts the checkout enough to hit **Restart** by hand).
  A failed `git clone`/`git pull` is a hard failure (error + tail shown, and a failed clone is rolled back); a failed `postClone`/`postPull`/auto-restart, by contrast, is a **soft warning** — the clone/pull already succeeded and the project is already discoverable, so the entry still shows as installed, just with a warning + output tail (a failed post-hook wins the status line over a failed or skipped restart, since it's the likelier root cause of both, and the message is extended to say the backend was left on the old code).
  The documented way to retry a failed `postClone` is hitting **Update** (which reruns `postPull` — `code-playwright` sets both to the identical command); a failed (or skipped) auto-restart can be retried with the manual **Restart** button.
  Running a library entry's declared command is a trusted-code-execution surface (bounded timeout, output always surfaced), consistent with the plugin system's overall "plugins are trusted own code" stance.
- **Lifecycle & lazy start** — enabling records the plugin. Any discovered plugin project (enabled or not, valid or not) with no workspace is auto-assigned to the **CC-Dev** workspace on every rescan/boot — enable, install, and manual rescan all trigger this via the same discovery pass, and a project already assigned elsewhere is never moved. The conductor's own project gets the same CC-Dev placement via a one-time boot seed, since it isn't a plugin. Enabled-but-stopped costs zero RAM: the first proxy request or MCP tool call starts the child and waits through the readiness window (`READY_TIMEOUT_MS` in `src/plugins/supervisor.ts`). Children are detached process groups that **survive conductor restarts** (adopted on boot when still alive+answering). Health is passive (exit events, proxy errors, on-demand probes) — on Android, Doze may kill a child at any time; the next request 503s with the crash tail, then lazy-restarts after a short backoff. a crash-count threshold within a rolling window ⇒ `failed` (see `src/plugins/registry.ts`; manual Start/Enable to recover).
- **Worktree-version activation** — the version dropdown switches which checkout the child runs from (`main` or any of the project's worktrees, resolved via the worktree store). The manifest is re-read from the active checkout on every start and must keep the same id (else 400, previous state kept). Caveat: worktrees don't share `node_modules` — a missing-deps start failure surfaces in the crash tail; the per-project `post-worktree-create.sh` hook can `npm install` automatically.
- **Plugin MCP tools** — manifest-declared tools appear inside the existing conductor MCP server as `<plugin-id>__<tool>` (client-visible `mcp__code-conductor__<plugin-id>__<tool>`). Visibility: every session is offered every enabled plugin's tools unless a tool declares an `audience` — then conductor sessions (`.conduct`, section leads included) or worker sessions only, the rest hidden and refused `TOOL_UNAVAILABLE_TO_CALLER`; an anonymous caller sees everything, and audience is not access control ([details](../plugins/tools.md#tool-audience)). The manifest `mcp.scope` field is accepted for compatibility with shipped manifests but dropped at load — nothing reads it. A disabled plugin's tools are simply unknown. Calls lazy-start the plugin and forward over HTTP with a per-manifest timeout. Note: workers snapshot the tool list at spawn — mid-session enable/disable reaches only new sessions.

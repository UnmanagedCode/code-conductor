# Features: settings and app controls

## Settings page and app controls

- **Settings page** — the sidebar header's ⚙ opens a full-page view, hash-routed at `#settings` (survives reload; closing restores the previously-active session anchor).
  An unsaved add or edit form in **Models** (a custom model, and the new-role name), **Backends** or **Systems** keeps its typed values, and the row it edits, across a section switch and leaving Settings; it clears on a successful save, on **Cancel**, when the edited row is removed, or on a page reload.
  A **Conventions** block's add or edit form keeps its typed values and the convention it edits the same way, and also across collapsing its block; it clears on a successful save, on **Cancel**, or on a page reload.
  A refusal on a block's status line (such as `Delete failed: …`) likewise stays across collapsing the block and a section switch, until that block's next delete, successful save or failed toggle, a plugin change (including one made while the block or the Conventions section was not shown), reopening Settings, or a page reload replaces it; a successful toggle or a refused save leaves it in place.
  Each Conventions block stays expanded or collapsed as you left it until a page reload.
  **Plugins** keeps its lists, both status lines, the library's install/update output and each entry's live log across a section switch.
  An install, update, Update all, Restart all or plugin action still running then keeps its progress line and lands its outcome in the section shown, and only one plugin action runs at a time across those switches.
  Reopening Settings while a plugin action is running keeps that action's progress line and live log; while none is running it replaces a finished action's message on either status line and drops the live logs, as every reload after a plugin action does.
  The install/update output stays until the next install, update or Update all starts.
  Exactly one full-page view (Settings, commits, review, costs, plugin) shows at a time: opening one — or selecting a session — closes whichever other is showing, and the URL names the view now open (review over the commit list is the one layering).
  A view opened from another replaces it, and **Back** (the view's Back, Escape or the browser's Back) returns to the view it replaced: review → commit history → wherever the history was opened from.
  Back from a view the app did not open itself (a deep link or an address-bar hash) goes to the active session, so Back never leaves the app.
  `SettingsView` in `web/src/features/settings/SettingsView.tsx`, one module per section beside it (+ `shared/models.ts` client cache/resolver, through `web/src/app/models.ts`).
  Groups:
  - **Models** — one row per capability tier (**Frontier → Powerful → Balanced → Fast**) with a registry-driven **backend select** + a **model select scoped to that backend** + a **default-effort select**, a per-tier **enable checkbox** and **default radio**; a **Custom models** fieldset (label + backend + model id + **required** context tokens (accepts `200k` / `1m` shorthand, decimal) + an **Accepts mid-turn steering** checkbox, ticked by default — untick it for a model that errors on or silently swallows a message sent into a running turn, and such a send instead stops the turn at a block boundary, keeping finished work, and arrives as a fresh turn; the list badges only the opt-out; each row has **Edit** — the same form with backend + model id locked — beside **Remove**); and a **Roles** fieldset (built-in / user-custom / plugin-owned, each bound to a tier or a concrete backend+model, each with its own default effort — `Inherit (<level>)` follows the bound tier). Every mutation is one `POST /api/settings/models/prefs`-family call returning the full refreshed state, effective immediately, no restart. Panel walkthrough + the binding data model: [models.md](../models.md).
    - **Override compact window for the Conduct session** — opt-in toggle + a slider over the bounded compact-window range (`COMPACT_K_MIN`…`COMPACT_K_MAX`, `src/appSettings.ts`) (persisted as `models.conductorCompactWindowEnabled` + `models.conductorCompactWindowK`) that sets `CLAUDE_CODE_AUTO_COMPACT_WINDOW` (raw tokens = sliderK × 1000) on the `.conduct` child env — applies to the orchestrator session only, **not** its MCP workers; seeded at boot from the orchestrator's own `CLAUDE_CODE_AUTO_COMPACT_WINDOW`.
    - **Idle renewal nudge** card (`ConductorIdleNudgeCard`): opt-in switch + a **Nudge after** minutes slider whose bounds come from the payload (`IDLE_NUDGE_MIN_MINUTES`…`IDLE_NUDGE_MAX_MINUTES`, default and clamp in `src/appSettings.ts`); persisted as `models.conductorIdleNudgeEnabled` + `models.conductorIdleNudgeMinutes`; a save applies to idle stretches already running. Behaviour: Conduct mode → **Idle renewal nudge**.
    - **Landing renewal nudge** card (`LandingRenewNudgeCard`): switch only, placed beside the Idle renewal nudge card; persisted as `models.landingRenewNudgeEnabled` (absent → on). Read at each delete, so a save applies at once. Behaviour: Conduct mode → **Landing renewal nudge**.
    - **Debug capture** card (`DebugDefaultCard` in `web/src/features/settings/models/ModelsSection.tsx`, own `spawn` namespace — not the models payload): a checkbox gating whether a spawn call that omits `debug` defaults to debug mode (`GET/POST /api/settings/spawn[/prefs]`, `spawn.debugByDefault` in `settings.json`; see **Debug mode** in [session-actions.md](session-actions.md#spawn-options)). An explicit `debug` on the spawn call always wins. The Debug capture, Task tools and MCP auto-background cards share failure handling: a failed load or save shows a persistent inline warning, a save reverts to the last saved value, and one `console.warn` is logged per failure streak.
    - **Task tools** card (`TaskToolsCard`, same file; `GET/POST /api/settings/spawn[/prefs]`, `spawn.taskTools` in `settings.json`): off by default. On, every session launch (spawn, resume, respawn; workers, the conductor, remote-system workers) carries `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`, which opts the CLI into `TaskCreate`/`TaskGet`/`TaskList`/`TaskUpdate` on any model. Never applied to cc's one-shot summariser or shell-env probe. Takes effect at a session's next launch; a running session keeps the tools it started with. Off sets nothing and strips nothing, so the CLI's own model-gated default and any host-exported value stand.
    - **MCP auto-background** card (`AutoBackgroundCard`, same file; `GET/POST /api/settings/spawn[/prefs]`, `spawn.autoBackground` + `spawn.autoBackgroundMs` in `settings.json`): a switch plus a **Background after** slider. Off by default; the threshold defaults to `AUTO_BACKGROUND_DEFAULT_MS` and is bounded by `AUTO_BACKGROUND_MIN_MS` / `AUTO_BACKGROUND_MAX_MS` (`src/appSettings.ts`; the slider reads the bounds from the GET). The slider is disabled while the switch is off. On, every **worker** launch (spawn, resume, respawn; conducted and human-launched; local and remote-system) carries `CLAUDE_AUTO_BACKGROUND_TASKS=1` and `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS=<threshold>`: an MCP call that runs past the threshold moves to the background, the worker's turn ends, and the CLI starts its own turn when the call finishes; the owner's wake waits for that turn. The conductor never gets either var: `Instance.spawn` owns both on every session launch and strips a host-exported or backend-pair value, on or off. cc does not apply the setting to its auxiliary one-shots (summariser, shell-env probe, auth/update checks); those inherit cc's own environment, so a host export of either var still reaches them. Takes effect at a session's next launch. Known limitations (all measured against Claude Code 2.1.316):
      - A steer sent while a backgrounded task is pending runs at once but gets no wake of its own; its reply arrives folded into the single wake after the task completes.
      - A commanded kill wakes nobody about the stopped task.
      - The EXITED stub says "mid-turn" when the worker was idle with a background task.
      - The flag also force-backgrounds an Agent call made with `run_in_background:false` at 120 s; the CLI fixes that threshold, and the slider moves only the MCP one.
      - Bash is unaffected: it backgrounds at its own 120 s timeout with or without the flag.
  - **Conventions** — one consolidated Settings section with three collapsible blocks, **Workspace**, **Conductor** and **Project**; Workspace starts expanded, Conductor and Project collapsed. All three are built on the shared fragment-catalog (`src/fragmentCatalog.ts`) and rendered by one reusable widget (`ConventionsPanel` in `web/src/features/settings/ConventionsSection.tsx`): an always-on **core** row (read-only "always on" badge), then each built-in convention (read-only, `built-in` badge) and custom convention (Edit / Delete) with — for the toggleable scopes — a per-convention enable checkbox, plus a `+ Add custom …` form (slug / name / description / body; the Project block adds a **Scaffold** field). A body holding a `<!-- cc:skill <description> -->` line previews, below the field, the part that stays in the system prompt and the skill (`cc-custom-<scope>:<slug>`) that loads on demand, or the parser error; a row badges `skill` and `scaffolds`, and shows a stored marker that does not parse as an error line. Edit loads the body as stored, skill part included.
    - **Conductor** — what the 🎼 Conduct orchestrator's composed role prompt contains (written to `.conduct/CONVENTIONS.md` and delivered as a CLAUDE.md `@`-import — see [components/store.md](../components/store.md#srcconductts) → `src/conduct.ts`).
      Core (role, hard boundary, dispatch-and-wake, your own plan mode — its procedure is the skill `cc-conductor:plan-mode` — MCP toolbelt, safety, talking to the user) + the toggleable built-in conductor conventions (`conventions/conductor/*.md`; see `src/conductorConventions.ts`) + custom conventions.
      **Global** selection (the conductor is a singleton) at `<store>/conventions/conductor.json` (`{disabled, rules}`), default all-on.
      Bodies in `conventions/conductor/core.md` + `conventions/conductor/<slug>.md`; toggling/editing takes effect for the **next-spawned / next-context-refresh** conductor (the doc is recomposed and rewritten to that file on every spawn/resume).
      `GET/PUT/POST/DELETE /api/settings/conventions/conductor[...]` + read-only MCP `list_conductor_conventions`.
      Enabled **plugins** may contribute additional conductor conventions (slugs namespaced `<plugin-id>/<slug>`) — they join the same catalog with a `plugin: <id>` badge (provenance only, no master toggle; each convention is its own checkbox).
      A plugin's conductor conventions are **on by default whenever the plugin is enabled** — the only per-convention state persisted is the user's explicit off-switches, in the same `disabled` deny-list the seeds and customs use.
      The effective set derives from the live catalog (enabled plugins only), so disabling a plugin drops its conventions automatically, a plugin **update** that adds a convention turns it on with no toggle (a removed one drops out), and unchecking one is remembered across disable→re-enable.
      The same block carries a **Preferred playbook** picker (`#dp-select`, `ConductorPlaybookPrefs` in `web/src/features/settings/ConventionsSection.tsx`, fed from the same GET): the selected playbook's stages, per-stage intent, `spawn_instance` pins and transitions are **generated from its definition** into the role prompt, so a conductor knows its shape and its move at each stage without a tool call; the other enforcement facts a refusal volunteers (the rest of `tools`, `needs`, spawnability) are left out — see [protocol/playbooks.md → Playbooks](../protocol/playbooks.md#playbooks).
      Three states: left at *Unset* (nothing ever chosen) it injects the built-in `DEFAULT_PLAYBOOK_ID` playbook, *None* injects nothing, or pick one by id.
      A plugin-contributed playbook is labelled `(plugin <id>)`.
      A stored choice that is no longer loaded (its plugin disabled, its overlay file deleted) stays selected as a disabled `<id> — not loaded` row, with the reason in the status line, and applies again once it loads.
      A successful pick blanks that status line and a refused one shows the server's reason until the block next reloads, and every reload re-selects the stored playbook and enforcement level.
      Global, stored as the tri-state `defaultPlaybook` in the same `<store>/conventions/conductor.json`; the section rides the **Playbooks** convention toggle.
      Editing a **built-in** `playbooks/*.json` shows up on the next compose, like a user-overlay playbook or the selection itself — no orchestrator restart.
      Beside it, a **Playbook enforcement** picker (`#dpe-select`, same component, same GET) sets the level newly spawned conductors start at — `defaultPlaybookEnforcement`, a sibling key in the same `<store>/conventions/conductor.json`, **`enforce` when unset** (`DEFAULT_PLAYBOOK_ENFORCEMENT`) — a fresh install refuses illegal moves until someone picks `warn`.
      Read live at spawn (no restart); a running conductor keeps its level, and **⋮ → Enforce Playbooks** overrides one session without writing back here.
    - **Workspace** — the "applies to every project" conventions. Core (`conventions/workspace/core.md`: intro + the delivery contract) + the toggleable built-in workspace conventions (`conventions/workspace/*.md`; see `src/workspaceConventions.ts`) + custom conventions, bodies in `conventions/workspace/<slug>.md`. **Global** selection at `<store>/conventions/workspace.json` (`{disabled, rules}`), default all-on so a fresh install reproduces the prior bundled canonical byte-for-byte. The composed text has **no file of its own**: it is folded into every project's app-owned in-tree `CONVENTIONS.md` (above that project's own conventions) by `src/projectClaudeMd.ts`, and prepended to the conductor role doc in `.conduct/CONVENTIONS.md` by `src/conduct.ts`. Every mutation (and boot) fans out via `regenerateAllProjectConventions()`, so a toggle rewrites every project's file. Because the selection is installation-wide it deliberately does **not** travel with a project — only the project-scope marker does. `GET/PUT/POST/DELETE /api/settings/conventions/workspace[...]`.
    - **Project** — optional convention sections selectable per project at creation, and afterwards from the row's **⋮ → Edit conventions…** (`EditConventionsDialog`, `web/src/features/dialogs/EditConventionsDialog.tsx`; `PUT /api/projects/:name/conventions`, [protocol/rest.md](../protocol/rest.md)).
      In the edit dialog only the conventions list scrolls, with the header and **Save**/**Cancel** always in view, on a short viewport too.
      It pre-checks the recorded selection; a recorded slug the catalog lacks is listed **checked** under **Unavailable**, by slug, and kept on save unless unchecked — a slug the catalog lacks can be kept, never added.
      Above the list (outside its scroll), **This project uses no project conventions** records a deliberate choice of none: ticking it unticks every convention, **Unavailable** ones included (still listed, so one can be re-ticked), and saving it drops them from the marker; ticking any convention clears it.
      It opens ticked for a project that chose none.
      Saving with nothing ticked and that choice off records **unset**, which stays flagged.
      The **New project** dialog offers the same choice above its checklist, with the same mutual clearing; creating with nothing ticked and the choice off records **unset**.
      Newly picking a convention with a scaffold facet shows a note that its setup step only runs at creation and is **not run** by the edit.
      Saving rewrites `CONVENTIONS.md` (and adds the `CLAUDE.md` import if missing) in the project's tree, on its system for a project on one, and leaves it as an **uncommitted change**.
      A dialog whose selection changed underneath it is refused **409**; keeping an unresolvable slug while the catalog is degraded is refused **503 `CONVENTIONS_CATALOG_DEGRADED`** with the file untouched (the freeze rule below) — unchecking that slug lets the save through. built-in project-convention seeds (`conventions/project/*.md`; see `src/projectConventions.ts`) + custom; bodies in `conventions/project/<slug>.md`, custom persisted at `<store>/conventions/project.json`.
      **No global toggle** (no core row, no checkboxes) — the new-project dialog shows checkboxes; the selected bodies are written under a `# Project conventions` heading in the regenerated in-project **`CONVENTIONS.md`** (imported by the project's `CLAUDE.md` via `@CONVENTIONS.md`, an import re-ensured on every regeneration), below the workspace block and under a line-1 marker `<!-- cc:conventions <slug,…> -->` that records the project selection as the self-describing, in-tree source of truth.
      Unlike the old inline snapshot, this file is **app-owned and regenerated** (on boot + after any project custom-convention edit, and by the Edit conventions… save) so a project picks up improved convention text over time.
      If a selected slug no longer resolves locally (imported into another cc instance, a since-removed custom convention, a disabled/uninstalled plugin), regeneration still refreshes the project's **other, resolvable** conventions; the missing slug stays selected — recorded verbatim in the marker so its text returns automatically once it resolves again — and the file shows a one-line note naming it in place of its body.
      Regeneration declines to write in exactly **one** case, leaving the file as committed: an unresolvable slug's absence can't yet be confirmed (a transient plugin-host hiccup, not the slug being gone) — that freeze covers the whole file, workspace block included, until the next regenerate.
      See [components/web.md](../components/web.md#srcprojectclaudemdts) for the full contract.
      Every other project is written, **including** one with no `CONVENTIONS.md` at all, a non-marker first line, or a zero-slug marker: all three mean an **unset** selection (never chosen), the old body is discarded, and the file comes out carrying the workspace block.
      A project that **chose none** carries the `<!-- cc:conventions :none -->` marker; it regenerates to that marker plus the workspace block alone and, having no slug to drop, is never frozen.
      Enabled **plugins** may contribute additional conventions (slugs namespaced `<plugin-id>/<slug>`) — they join the same catalog and dialog under a plain per-plugin heading (provenance only, no master toggle; each convention is its own checkbox); the committed body survives the plugin being disabled/uninstalled (regeneration drops the slug's text and names it in the file; it returns verbatim on re-enable).
      A plugin convention may also carry an optional **scaffold** facet (a one-time setup directive — a plugin's, or a custom project convention's from its Scaffold field; built-in seeds are fragment-only), invisible in the dialog; picking it returns the composed directive as `create_project`'s `scaffold` field (see Plugins → Conventions & scaffolds).
      A scaffold-only convention contributes nothing to `CONVENTIONS.md` but still emits its directive.
      `GET/POST/PUT/DELETE /api/settings/conventions/project[...]` + read-only MCP `list_project_conventions` (carries `hasScaffold`).
  - **Backends** — the user-managed **launch-template registry** (`BackendsSection` in `web/src/features/settings/BackendsSection.tsx`): one card per row showing label, id, template (blank shows `claude`), its injected env pairs, and the custom models bound to it. The two built-ins (`claude`, `ollama`) carry a **built in** badge, show their template and env read-only, and have no Remove. One shared add/edit form (id + label + template + an env textarea, one `KEY=VALUE` per line) — for user rows only. Removing a row is **refused (409)** while any custom model still references it (bound model ids surfaced in the status line) *or* while any session is still on it (session ids surfaced) — an exited session still counts, so archive or delete it rather than just killing it. Full contract: [models.md](../models.md).
  - **Systems** — the **system registry** (`SystemsSection` in `web/src/features/settings/SystemsSection.tsx`): the execution environments a project's tree — its git repo, its files, and the commands run in it — can live on. One card per row showing label and id. **This machine** (`local`) carries a **built in** badge and has neither an Edit nor a Remove control: it is where every project lives unless its record names another. One shared add/edit form (id + label + **provider command**) for user rows; the id is the identity and is locked while editing. The provider command is what cc runs to reach the system, typed as a command line and sent as argv — **saving one connects to it first**, and a system that does not answer is refused with the provider's own error shown on the form rather than saved. A row shows its command, or says it has none: such a row is a name only, and a project on it cannot be reached. **One system may serve many named targets** (one provider, ten containers), so a user row lists each referencing project with its target — `name (remoteId)`, or the bare name for a project on the provider's default. Removing it is **refused (409)** while any of them still does — the message names them the same way, so the status line says what to move first.
  - **Account** — two blocks: **Claude login** (which Anthropic account cc's `claude` CLI is signed in to, and signing it in from the browser) and **overage protection** (guards that account from paid-credit spend).
    - **Claude login** (`ClaudeLogin` in `web/src/features/settings/ClaudeLogin.tsx`, server `src/claudeAuthStatus.ts` + `src/claudeLogin.ts`; endpoints in [protocol/rest-settings.md](../protocol/rest-settings.md) → `/api/claude-auth/*`) — reloaded on every Settings open.
      - **State** — what `claude auth status --json` reports, for the same binary and credential store worker spawns use (`CLAUDE_BIN`, `CLAUDE_CONFIG_DIR` as cc's env has them): **Signed in** · email · organisation · plan · "Claude subscription"; **Using an API key** (its source, e.g. `ANTHROPIC_API_KEY`, with a note that cc's environment sets it and a login here won't change it); another method by its raw name; or **Not signed in**. Null identity fields are skipped. A `Credentials: <configDirectory>` line names the store. A status that cannot be read shows the error, never "Not signed in".
      - **Signed in = credentials present, not validated** — the CLI's status is local-only; an expired token whose refresh fails still reads signed in.
      - **Log in / Re-log in** — runs `claude auth login` (subscription login; no Console/API-billing option) on the server. The panel shows **▶ Open the sign-in page** (new tab) plus the same URL in a read-only field to copy to another device, then a code field: after signing in, the callback page shows a code — paste it and **Submit** (Enter works). A malformed code shows the CLI's complaint and waits for another; a rejected one fails the flow with the CLI's error. **Cancel** kills it. Starting while another tab's flow runs is refused; the refusal stays on screen and that flow is shown, so it can be followed or cancelled here.
      - **One flow at a time, server-side** — a second start is refused; any tab sees the flow and a reopened Settings resumes it. It times out after `LOGIN_TIMEOUT_MS` (`src/claudeLogin.ts`), failing with `Login timed out after 10m` at the default. Success re-reads the status and switches the header's usage chip to the new account at once: the server drops its cached usage (a fetch begun with the old token can no longer land), and the tab that saw the success drops its last-good usage and rate-limit buckets and refetches. Other open tabs pick up the new account's usage at their next poll. The status itself is cached for a few seconds, and dropped when a login starts or succeeds.
      - **Re-login replaces credentials in place.** A cancelled, failed or timed-out login leaves the existing credentials untouched (the CLI writes only on success). New sessions use the new login; running sessions aren't restarted and may keep the previous login until they are.
      - **Usage follows the credential store.** The usage chip reads the token from the `.credentials.json` the login CLI writes (same directory, with or without `CLAUDE_CONFIG_DIR`). Where the CLI keeps tokens in the OS keychain (macOS) the chip has no token and stays hidden; a re-login does not change that.
      - **Running workers and overage state.** A worker still on the previous token can keep reporting that account's rate limits into the header. Overage stops and the global lockout are not cleared by a re-login: they belong to live sessions that may still be on the old token.
      - **Windows / macOS:** `BROWSER=true` (no browser on the server host) is verified on Linux only; elsewhere the CLI may also open a browser on the host.
      - No logout button: it would sign out every running worker.
    - **Overage protection** — these prefs **ride in the shared `/api/settings/models` payload** (`onOverage`, `overageThreshold`) and save via the same `POST /api/settings/models/prefs` — there is no separate overage endpoint; the client reuses that payload and keeps its dirty-edit guard (below) across page switches.
      - **Action on overage** — `Off` / `Stop` / `Stop & resume` (persisted `models.onOverage`, default `none`).
        `Stop`/`Stop & resume` **arm a deferred interrupt** on the turn (idle-but-alive, never killed/respawned) — a conductor's workers are stopped too, and an *idle* conductor awaiting a wake — or whose worker has a background job running — is stopped with **no message sent** — its resume is armed immediately instead (see [components/instances.md → Overage trip detection + central routing](../components/instances.md#overage-trip-detection--central-routing)); `Stop & resume` also arms an **in-memory** resume deadline (~5 s after the window resets, drives the auto-resume badge; survives orchestrator restart via the resume manifest) fired by a **wall-clock sweep** (not a per-session `setTimeout`) so it survives the process being suspended (Android Doze / Termux backgrounding) and fires on the first tick after wake.
        **Nothing is sent to any session during a `Stop & resume` pause** — including a turn that starts anyway (a background re-invocation, a self-triggered turn): it is stopped, and the transcript shows `⏸ Turn interrupted: the overage lockout is still active …` so the cut is never silent.
        Trip detection + conductor-aware routing live in [components/instances.md](../components/instances.md#overage-trip-detection--central-routing) → overage.
        The action buttons, the threshold enable checkbox, and the threshold slider (below) are staged locally and committed together — see **Apply**, below.
        **Non-Claude exemption:** a usage window is an Anthropic-account concept, so a session whose **root** agent tree touches **no monitored usage-window domain** (i.e. no `claude`-backed agent anywhere in it) is left entirely out of this flow — never auto-stopped, never queued behind the lockout, never armed for auto-resume, and it shows no overage badge.
        **The unit of stopping is the tree, and it is resolved from the tree's ROOT, not from the session:** a tree with **any** Claude agent stays in *as a whole*, so both a non-Claude conductor with Claude workers **and** a non-Claude worker under a Claude conductor are in the flow, handled exactly as a Claude session in that same position would be — stopped and badged, then either armed-and-queueing or, for a worker that was **mid-turn when the window tripped** **and** whose conductor is in control, stopped **un-armed** (which *refuses* sends instead of queueing them, per **Global stop-and-queue lockout** below).
        Both conjuncts are needed: in-control alone is not enough, since a worker that had already gone idle is not stopped at all and queues like any other in-flow session.
        Which case a given session lands in follows from its position in the tree and what it was doing when the window tripped, not from its backend; what root-scoping fixes is membership.
        Only a whole root tree that touches no monitored domain is exempt.
        **Trip detection is scoped differently — per session, by its own backend:** a non-Claude session's own `rate_limit_event` reports its own endpoint's window, so it never trips the monitored flow even when its tree is in-flow.
        This is backend-scoped by *usage-window domain* (`src/usageWindowDomains.ts`), where `claude` maps to the monitored `anthropic` domain and every other backend to its own unmonitored one — not hardcoded per provider, so monitoring another backend's window is a one-line addition.
        - **Global stop-and-queue lockout** — under `Stop & resume`, while the window is active **every** session queues its sends, not just the one stopped mid-turn: an idle/existing chat and a **brand-new chat started during the window** both queue (each queued-only session **arms its resume deadline immediately**, since there's no mid-turn→idle transition to arm on).
          Typing does **not** resume a session inside the still-throttled window: each message is **queued** and delivered as **one combined prompt** (reset text + numbered list + all queued attachments) when the deadline fires.
          This is a **hard lockout — no override, no early-resume button** (resume happens only on the deadline; internally `fireNow()` stays as the sweep/test seam).
          **Safety rail:** global queueing engages only when there's a valid *future* reset time with an armed clear timer — a missing/past reset means sends flow normally (never a permanent lockout).
          Plain `Stop` never queues (no flush path).
          **One session does not queue:** a worker the stop left **un-armed** (its conductor is the sole driver) *refuses* sends instead — the MCP tools soft-refuse `OVERAGE_STOPPED_UNARMED`, the WS path fails the send, its composer **disables Send** rather than relabelling it, and its banner reads "Stopped for account overage — your conductor resumes this worker.
          Messages can't be queued here."
          Queueing it would strand the text: the queue flushes only on a resume deadline it deliberately does not have.
          A **queued-only** session (idle/new, never stopped mid-work) resumes with a **softened preamble** ("Delivering the messages you queued while paused") instead of "continue where you left off".
          The composer stays usable but shows a **"Paused until &lt;time&gt; — messages are queued"** banner (keyed on the global `overageActive` signal, so it shows before the first message is even typed) and its send button reads **"Queue"**; queued messages render as muted **ghost bubbles** ("queued" chip + clock) that collapse (dim) into the delivered turn on fire, marked by a `Window reset — delivered N queued` system line.
          Each delivered ghost stays where it was queued, dimmed, with its text.
          The auto-resume badge reads `resumes at <time>` in the header chip and, compact, `⏸ <time>` on the session's needs-you strip entry, whose tooltip leads with the full wording; the queued count shows as `· N queued` in the header and a leading `N · ` on the entry (`N · ⏸ <time>`).

- **Two-tier interrupt** — ⏸ Interrupt is a **deferred** stop by default: it **arms** an abort that fires at the next output boundary — when nothing is mid-stream and every dispatched tool has returned its result — so the block being written and any finished tool work are preserved, and the model is never asked to acknowledge anything (no extra round-trip). Armed with nothing in flight, it fires at once. Repeating ⏸ while armed does nothing. While armed, the header status chip reads **stopping…** and the bottom turn-indicator label switches to **Stopping…** with an inline **⏹ Interrupt now** button — the explicit escalation to an **immediate** abort that severs the turn and discards in-progress work. The split is driven by a transient `interrupting` flag on the `status`/`snapshot` WS frames; it auto-clears when the turn ends. Either tier leaves the CLI's `[Request interrupted by user]` marker line, which renders as the **⏸ Turn interrupted** system annotation rather than a user bubble, and is never counted as a real user prompt (so rewind/fork indices stay correct) — live it is dropped while the post-abort drain window (below) is open, which the abort itself opens, so it typically surfaces on replay/resume where that turn's `drain_abort` line is not there to say the same thing. Omitting `force` (WS `interrupt`, MCP `interrupt_turn`) is always the deferred tier.
  - **Post-abort drain window** — after an abort the CLI's internal stdin queue is not cleared: any messages written mid-turn (a prompt sent while busy) remain queued, and the CLI will dequeue them and start spurious new turns. The orchestrator opens a **drain window** (`POST_ABORT_DRAIN_WINDOW_MS`, default 3 s) after every abort — forced, or an armed ⏸ firing. The moment a spurious turn announces itself (via `system/init` on the event channel, ~39 ms after the abort and ~3.7 s before the first API round-trip), the orchestrator fires an immediate `control_request interrupt` to sever it — each spurious drain resets the window deadline (sliding window) so a queue of N messages is fully drained. Each drained turn shows a `drain_abort` system annotation ("⏹ Drained queued turn after interrupt") in the conversation. The window closes automatically when it elapses with no new turn-start. Calling `prompt()` (any explicit new-turn path) closes the window immediately so intentional follow-up prompts are never intercepted. A safety cap `POST_ABORT_DRAIN_MAX` (`src/instances.ts`) bounds the number of drains per window.

  - Normal sessions are carried over by every Restart and Shut down, never archived by one; a normal session orphaned by a crash and not restored stays listed until archived by hand. Internals (drain grace, stagger, three-group split, the exit-archive suppression, the running record, the orphan reap): [components/restart.md](../components/restart.md#srcresumerestartts) → `resumeRestart.ts`, `runningRecord.ts`, `pendingContinue.ts`, `resumeBoot.ts`.

- **A merge into cc's own main checkout updates the web UI** — cc's `.code-conductor/post-worktree-merge.sh` (`src/webPostMerge.ts`) compares the merge with the commit the serving server booted from, which that server measures at boot and passes to a hook merging into its own checkout as `CC_SERVER_BOOT_SHA` (`src/bootCommit.ts`).
  Every change since boot is under `web/`, `docs/`, `tests/` or `shared/`, or is the root `README.md`, and is a file the running server's imports do not reach (from `server.ts` and `src/`, transitively, as of the boot commit — `src/serverImports.ts`): the new build is swapped into `web/dist` and is live on the next page load.
  Anything else changed since boot — a `docs/`, `tests/`, `shared/`, `web/` or `README.md` file the server's imports reach, `src/`, `server.ts`, the root `package.json` / `tsconfig.json`, `migrations/` / `bin/` / `playbooks/` / `conventions/`, any other path, or any `docs/` / `tests/` / `shared/` path or `README.md` when the boot commit has an import the hook cannot resolve — or no boot commit (the server's checkout had tracked changes outside `web/` at boot, its own web build is running, or the merge went into another checkout): the build is staged in `web/dist.next`, so the next restart adopts it without building.
  The hook line names the path that forced the stage, with its import chain when the server imports it (e.g. `src/server.ts → shared/http.ts → shared/wire.ts`).
  Nothing the UI build reads changed, or the target is a linked worktree: nothing happens.
  **A swap only goes live if the tree is still the merge's own when the build is done** — HEAD still the merge commit, the build's inputs unchanged while it ran, and no uncommitted edits to them.
  Otherwise (a later merge landed, or someone edited the inputs) nothing is swapped, `web/dist` stays as it was, the hook says `swap skipped — the tree moved` and exits 0, and the later merge's own hook decides afresh.
  The server's boot build is guarded the same way against the HEAD it booted at (even when it cannot vouch for that commit, e.g. tracked changes outside `web/`): a merge landing while it builds leaves the previous build serving until the next start, except where Known limits says it is unguarded.
  The script runs the node cc runs on (`CC_SERVER_NODE`), so it needs `node` on the hook shell's PATH only when run without cc.
  Known limits:
  - two servers serving one checkout share its `web/dist`, and each vouches only for its own backend: a swap one server decides is served by the other too;
  - the boot build is unguarded, so a merge landing while it builds can go live in front of the boot backend, for a FIRST-ever build (no `web/dist` yet — an old-but-present UI beats none), and for a boot with no readable HEAD — unborn, unreadable, or not a git checkout (nothing to measure against);
  - the hook runs in its own process beside the server, so it and a restart's preparation can both work on `web/dist.next`, and a restarted server's boot build can start while a hook's swap is still running. The hook removes only a stage stamped with other sources than the ones it just made current, and renames it aside before deleting it; a stage of the current sources is left alone. The worst outcome is a rebuild at the next boot, never a missing or partial `web/dist`.

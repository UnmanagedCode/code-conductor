# Features: conduct and headless modes

## Conduct mode
- **`🎼 Conduct` button** at the top of the sidebar, full width in both lenses (`+ New project`, `+ Add project` and `+ New workspace` are in the `≡` menu of the Projects lens's filter row — see **Sidebar lenses**). Tap → no dialog: spawns a **normal**, **pristine** Claude session in the `.conduct` project in code mode (bypassPermissions) — listed nowhere until its first prompt (see **Pristine conductor** under Sessions & instances) — sending `role:'conductor'` and no `model`/`backend`/`effort` — the server resolves the **Conductor role**'s current binding (Settings → Models → Roles) and its default effort, falling back to the default spawn tier if the role's binding has gone dead. The conductor is opened as soon as the spawn answers; the project and instance lists refresh behind it. A failed spawn surfaces as a toast; a failed background refresh is only logged.
- **`.conduct` project** created at boot and by any conductor create (the server ensures it before resolving the project). Lives at `<projectsRoot>/.conduct/`, holding two app-owned files: a generated `CONVENTIONS.md` — the conductor's role prompt, composed from the always-on core (`conventions/conductor/core.md`) + enabled toggleable conventions (`conventions/conductor/*.md`) + custom conventions, rewritten before **every** conductor spawn/resume (see **Settings → Conventions → Conductor** above) — and a `CLAUDE.md` carrying an `@CONVENTIONS.md` import line, created if absent and otherwise left with every existing user line intact. Delivery is the messages stream rather than an appended system prompt because a translation proxy in front of a non-Anthropic backend can drop the CLI's extra `system` block. Workspace conventions reach the conductor through this same file: `materializeCurrentConduct()` prepends the composed workspace text above the role doc. The dir is filtered out of `listProjects()` by the existing dot-prefix rule, so it never appears in the Projects lens; its sessions are the Conductors lens (see **Sidebar lenses**). Reserved name: `POST /api/projects {name:".conduct"}`, `DELETE /api/projects/.conduct`, and `PUT /api/projects/.conduct/workspace` all return 400.
- **Workflow** (full details in the composed conductor role prompt — source: `conventions/conductor/core.md` + `conventions/conductor/*.md`): conductor uses MCP to `spawn_instance({mode:'plan', createWorktree:true})`, reviews via `get_recent_messages` / `project_diff`, lands via `approve_plan` → `sync_worktree({project, worktree})` → `merge_worktree({project, worktree})` → `kill_instance` + `delete_worktree`.
- **Playbooks** — declarative, enforceable workflow graphs, so a conductor's flow is checked by the server instead of only described in its prompt.
  A playbook is a graph of **stages** a worker is bound to; illegal moves are refused at the MCP boundary and every governed call is appended to the **event log** (`<store>/events.jsonl` — governed calls, every session's start/resume/exit, conductor and worker turns, wakes and enforcement changes; format: [event-log.md](../event-log.md)), which makes the current state inspectable and the history backtrackable.
  The built-ins ship in-repo (`playbooks/*.json`): `solo` (one worker plans, implements and refines; separate reviewers), `relay` (a planner that can never implement, handing off to a fresh implementer), `forge` (relay plus two mandatory critic passes over the plan — a rival plan, then a defect audit — that an implementer cannot be spawned ahead of), `freeform` (the unconstrained escape hatch — a fan-out, a one-off command, or a worker that lands code) and `section-lead` (the lead conductor spawns one or more section leads, each conducting its own scope — one level deep).
  **Author your own** as a JSON file under `<projectsRoot>/.code-conductor/playbooks/` — it is picked up without a restart, and `list_playbooks`' `errors` tells you why one failed to load.
  Enabled **plugins** can ship playbooks too, listed as `<plugin-id>/<slug>` with a `plugin` field; disabling the plugin leaves its bound workers refused (the reason names the plugin) until it is re-enabled, which restores them untouched — see [plugins/manifest.md](../plugins/manifest.md).
  Enforcement is per conductor session, starting at the **Playbook enforcement** level set in **Settings → Conventions → Conductor** (beside the Preferred-playbook picker; **`enforce` out of the box**, applied to the next conductor spawned).
  **⋮ → Enforce Playbooks** (below Prune, shown for `.conduct` sessions only) overrides that level **for the current session only** — it never changes the setting — toggling between the two levels — on refuses illegal moves; off allows the call but records the refusal in the event log **and** drops an amber ⚠ warning bubble into the conductor's own transcript naming the tool, the refusal code, the reason, and the target worker when the refused call named one, so a would-be refusal is visible as it happens instead of only in the log.
  When the server cannot write the event log (it no longer holds the projects root — e.g. mid-restart handover), the rows are dropped and an amber **Event log not recording** bubble lands in the affected conductor's transcript, naming the reason.
  Under `enforce`, a spawn that starts a new run must name a `playbook` and a `stage`; the refusal names every playbook and where each can be entered (under `warn` the same spawn is warned about and proceeds untracked).
  A stage can also restrict its **worker's own** tool calls with `workerTools` — a map of tool-name patterns to allow/deny, covering built-in and MCP tools and the worker's subagents, checked on every call so a stage move or a definition edit applies at once; under `warn` a denied call proceeds with the same warning bubble.
  It names tools, not effects, so it is not a sandbox (`Bash` can still write files).
  Conductor-facing surface: `list_playbooks`, `describe_playbook`, `playbook_state` (which reports where a run is and what each next move would do).
  Contract, refusal codes and known limitations: [protocol/playbooks.md → Playbooks](../protocol/playbooks.md#playbooks); internals: [components/playbooks.md → Playbooks](../components/playbooks.md#playbooks).
- **Read nudge** — a conductor reading its way through a project gets one short in-band reminder, and the user sees it too. A conductor-only `PreToolUse` hook counts the conductor's own `project_read` / `project_bash` calls since its last `spawn_instance` / `send_prompt`; when that run reaches 8, and again at 16, the call carries an `additionalContext` reminder naming the count and pointing at the role doc's "does this read change a gate decision I own?" rule. The call itself always runs: nothing is denied, rewritten or permission-checked differently (plan mode included).
  - **What resets the run:** a `spawn_instance` / `send_prompt` (so a later run of 8 in the same turn nudges again), and the end of the turn — turn end, crash, exit or respawn. A message steered into a running turn does **not** reset it. `project_diff` neither counts nor resets; calls made inside a subagent are ignored.
  - **What the user sees:** an amber `read_nudge` system line in the conductor's transcript, reading exactly what the model was given. It survives reload, restart and scroll-back, because it is rebuilt from the session transcript.
  - Thresholds, wording and tool lists: `src/conductorReadNudge.ts`; wire detail: [protocol/ws-events.md](../protocol/ws-events.md) → `system`/`read_nudge`.
- **Idle renewal nudge** (opt-in, **Settings → Models → Idle renewal nudge**) — shortly before an idle conductor's prompt cache expires (`PROMPT_CACHE_TTL_MINUTES`, `shared/idleRenewNudge.ts`), cc injects one turn asking it whether to `renew_session` while the cache is still warm, so the user's next message lands on a small fresh context instead of paying a full cache write on a large one. Controller: `IdleRenewNudgeController` (`src/idleRenewNudge.ts`); text: `buildIdleRenewNudge`.
  - **Who:** top-level conductors only (`isTopLevelConductor`: a `.conduct` session that is not `conducted`). Workers, section leads and hand-driven sessions are never nudged.
  - **When:** an idle stretch starts at a **real** turn's end; at the configured minutes into it, a wall-clock sweep (`IDLE_NUDGE_SWEEP_MS`) sends the nudge **once**. A nudge-chain turn (the nudge, and the `/clear` + reseed of a renewal it caused) never starts a stretch, so the stretch stays spent until the next real turn ends.
  - **Skipped for the whole stretch:** overage (the manager's overage window, a stopped/auto-resume-armed session, a queued overage message, or the last `rate_limit_event` reporting `isUsingOverage` — tracked even under `onOverage: 'none'`), and a stretch already past `PROMPT_CACHE_TTL_MINUTES` (device sleep, a late enable, a lowered threshold): the cache is already cold.
  - **Retried at the next sweep:** a conductor mid-turn, pristine, mid-rotation/renewal/relaunch/rewrite, with a parked steer, live subagents or an owed task notification; and every nudge during a resume-restart drain (`suspendWakes`).
  - **What the conductor is told:** renew only if the context carries history the next exchange will not need, end the turn right after `renew_session`; if it was waiting on the user, copy the question verbatim into the summary and re-ask it after the reseed, not in the nudge turn; otherwise end the turn with no tool calls and no text.
  - **What the user sees:** a closed ⏰ fold titled with the nudge's summary line (the instruction inside), labelled `⏰ Idle-renewal nudge` wherever a session is named by its first prompt. Nudge-chain turns bump no attention counter — no unread, no Waiting/Finished notification — while `awaitingUser` is still tracked, so a conductor that was waiting still shows as waiting after a nudge-driven renewal and re-ask.
  - **Restart:** stretches are in memory only and every resumed session is a new instance with none, so a cc restart sends no burst of nudges; a resumed conductor's stretch starts at its next real turn's end.
- **Landing renewal nudge** (on by default, **Settings → Models → Landing renewal nudge**, `landingRenewNudge` in the models prefs) — an MCP `delete_worktree` by a **conductor** (a `.conduct` session — top-level conductors and section leads; `isConductorInstance`) of a worktree whose work landed gets `LANDING_RENEW_NUDGE` (`src/mcp/handlers.ts`) as a **PostToolUse hook block** on that call: the handler queues it under the call's toolUseId once the removal succeeded, and the conductor's PostToolUse hook hands it to the model inside the tool result (`src/toolResultNudges.ts`; [protocol/subprocess.md](../protocol/subprocess.md#subprocess-protocol)). The result stays `{project, worktree}`. It states the conductor's landing renewal trigger in full — renew only when more work follows in the session, otherwise skip, leaving a session that ends on the landing to the **Idle renewal nudge** when that is enabled — because `renew_session`'s schema may not be loaded; the `context-renewal` convention carries no landing trigger. It is not an injected turn: no turn starts and no attention counter moves. **The user does not see the nudge text in the tool result** — it reaches the model only; the UI shows no line for it. A refused delete, a call inside `run_code`, and any caller [protocol/subprocess.md](../protocol/subprocess.md#subprocess-protocol) lists as getting no tool-result nudge never get it.
  - **Landed** = a recorded successful merge of that worktree (`recordWorktreeLanding`, `src/worktreeLandings.ts`; any surface — see **Merge**) **and** no commits ahead of its base (`worktreeWorkLanded`, read before the branch is deleted). A merge refused for any reason records nothing. The record is held in server memory only, keyed to that specific worktree and cleared when it is removed by any cc path (including wiping its project's store), so a restart between merge and delete means no nudge and a same-name successor never inherits a landing.
  - **Nudged:** a child merged into its feature worktree then deleted; a worktree merged from the UI then deleted by the conductor; a worktree kept after its merge (a worker reused across merges) and deleted with nothing committed after the merge; a `force` delete (uncommitted changes were never part of the landing).
  - **Never nudged:** worktrees never merged, including zero-commit ones (`NOTHING_TO_MERGE`) and abandoned or prover/child worktrees removed mid-review; a worktree with commits added after its landing; work landed outside cc's merge (a hand-run `git merge`, push or cherry-pick, or commits made straight on the base branch); a landing check that cannot run (base branch gone, system unreachable) — the delete itself is unaffected; the REST delete behind the web UI; an anonymous MCP call (no `/mcp/<sessionId>` caller).
  - Setting off: `delete_worktree` makes no extra git call and its result is unchanged. The landing is recorded on every successful merge regardless of the setting.
- **Awaiting-wake dot** — a session's sidebar status dot renders **blue** (`Dot` in `web/src/features/sidebar/rows.tsx`) while it is idle *and* an armed wake on a session it owns is pending, with the tooltip `idle — waiting on a worker`; the waiting-on-you ring composes with it (ring over the blue fill). Armed-wake-pending is wider than "its worker is mid-turn": the wake is held — and the dot stays lit — through a deferred `turn_end` (live subagent / unconsumed task notification, target already idle) a dropped idle-drain settle, and a hold (its section lead ended a turn still waiting on workers of its own — see **Wake on turn end** in [mcp.md](mcp.md#mcp-interface)), which is precisely when a conductor most needs not to read as done. It is the only thing on the row distinguishing "idle because I am waiting on a worker" from "idle because I am done". Fed by the `awaitingWake` field on the instance summary (`web/src/features/sidebar/derive.ts` → `instanceAwaitingWake`), which is CALLER-side. It stays lit across a heartbeat, because a heartbeat reports without consuming the wake — a conductor whose worker is hung does not read as finished. The same blue dot is also lit, with the tooltip `idle — waiting on a background job`, while a background Bash job (`run_in_background:true`) still runs on the session or on any live session it owns, transitively — the `waitingOnJob` field `GET /api/instances` adds per row (`instanceWaitingOnJob`). Display only: the job never holds a wake. A pending wake wins the tooltip.
- **Sub-agent panel** — while viewing a session that has spawned workers via `spawn_instance`, a collapsible **Workers** panel (open by default, headed by the worker count) appears below the task panel, listing each of them.
  Each row shows a label (custom title → readable first prompt, cut at 60 characters → `project · id8`) plus a status icon keyed off `displayStatus` (not raw `status`): a spinner for `turn` or `running` (a worker whose turn ended but still has a backgrounded subagent working spins like an actively-turning one, not like an idle one), a dotted circle for idle, a check for exited, a cross for crashed, a plain circle otherwise (spawning).
  An idle section lead that is itself waiting on a wake (`awaitingWake` — it waits on workers of its own, so this session's wake from it is held) also spins, titled `on a worker`; an idle worker with a background Bash job still running on it or below it (`waitingOnJob`) spins titled `on a job`.
  A worker bound to a playbook also carries a small `<playbook-id> · <stage>` label (e.g. `forge · plan-rival`; one name when the stage is named as its playbook) at the right end of its row; a worker with no binding gets no label element at all, not a hidden one.
  Status and binding updates both arrive via the existing `instances` hint → `refreshInstances()` path (the same mechanism that drives sidebar live dots; the hint also fires on every playbook `spawn`/`transition`, not just a status flip).
  Tap any row, including its playbook label, to navigate directly to that worker's conversation view.
  A session with no workers shows no panel.
  Implemented in `SubagentPanel` (`web/src/features/session/SessionPanels.tsx`); backed by the `callerInstanceId` field on `Instance` (set when `spawn_instance` is called as `/mcp/<conductor sessionId>` — the sessionId is resolved back to the conductor's live `instanceId` so `callerInstanceId` stays an instanceId for the panel's `i.callerInstanceId === inst.id` filter).
  The worker's own view links back to its owner through the header owner chip and Alt+↑.

  **Unknown owner.** A live conducted worker has `rootSessionId: null` (and `parentSessionId: null`) (the `unknown` owner above: neutral chip, no accent, no send check) when it (1) was resumed from a stored session through the UI — a sidebar session-row click, Settings → Archived, or a `#session=` anchor / notification click / Back or Forward onto an unlisted session, including an anchor restore after a restart that runs before its conductor re-spawns it; or (2) was spawned through MCP `spawn_instance` anonymously (no `/mcp/<sessionId>` caller). The header **Resume**, a conductor's `spawn_instance({resume})` after a restart and crash recovery keep the owner. A normal worker that exits leaves the list; a persistent one stays listed `exited`/`crashed` with a null owner and a disabled composer.

## Headless mode
Run one conductor session with no browser and no person attached: `node server.ts --prompt <text>` boots cc as usual, runs one **New conductor** session until it and everything it owns are done, prints one JSON object on stdout and exits. Modules: `src/headless/` ([components/headless.md](../components/headless.md#headless-mode) → Headless mode); the JSON and exit codes: [protocol/headless.md](../protocol/headless.md) → Headless run result; docker: [docker/README.md](../../docker/README.md) → Headless runs.

**Flags** (`src/headless/args.ts`). Any one of the three anywhere in argv makes the run headless; an argv with none of them boots the ordinary server and ignores the rest.

| Flag | Value |
|---|---|
| `--prompt <text>` / `--prompt=<text>` | The prompt, verbatim. |
| `--prompt-file <path>` / `--prompt-file=<path>` | Read the prompt from a file; `-` reads all of stdin. |
| `--mode code\|plan` / `--mode=…` | Default `code`. `plan` starts the root in plan mode with **Auto-approve plan** on. |

**Usage errors** — a `usage_error` object and a synopsis on stderr, before anything boots (no projects-root lock, no migrations): both prompt flags; neither (a `--mode` alone); a flag repeated; a flag with no value (`--prompt` last, or `--prompt=`); a `--mode` other than `code`/`plan`; any other argument once a headless flag is present; an unreadable `--prompt-file`; a prompt that is empty once trimmed.

**What runs.**
- Boot is the ordinary one minus the web build and the dependency sync (as `CC_SKIP_WEB_BUILD=1 CC_SKIP_DEPS_SYNC=1`), so a headless run never writes into a checkout another server may be running from. The web UI serves whatever `web/dist` already holds, and answers for the whole run: stderr names it (`headless: UI at http://<addr>:<port>`, one line per non-internal IPv4 for a wildcard `HOST` — in a container that is its own IP).
- The projects-root lock applies: a root another server holds is refused (`root_held`), naming the holder.
- The root is spawned with the same body New conductor posts (`shared/newConductor.ts`: a pristine normal session in `.conduct` on the Conductor role, `bypassPermissions` in code mode), plus `autoApprovePlan` in plan mode — for the root only; its workers and section leads never get it.
- The root's first prompt is a short headless fragment (`HEADLESS_FRAGMENT`, `src/headless/fragment.ts`) followed by a blank line and your prompt. The fragment tells the root that nobody will answer, to decide instead of asking and state each assumption, that its workers' plans and questions are its own to decide, and that its last message is the run's output.
- **Asks, the root's only.** A root **AskUserQuestion** gets one canned answer per ask (`HEADLESS_QUESTION_ANSWER`: decide yourself, state the assumption, continue). A root **ExitPlanMode** plan that Auto-approve did not take (code mode, or after the root left plan mode) is approved as the UI's Approve does. A text ask (a final message ending in `?` or an offer) is neither answered nor waited on — it is the result. Workers and section leads route their asks to their owners exactly as in the UI.
- **Restart is refused** — `POST /api/admin/restart` answers `409 RESTART_DISABLED_HEADLESS`, so Settings → About's restart and self-update's follow-up restart fail; nothing replaces the process.

**When it ends.**

| Ends when | `reason` |
|---|---|
| The root and every session in its tree (everything it owns transitively, and every worker spawned under it at any depth, even one whose section lead is gone) stay idle for the idle-drain settle window (`IDLE_DRAIN_SETTLE_MS`, `src/idleSubscriptions.ts`; env `ORCH_IDLE_DRAIN_SETTLE_MS`) with no turn still coming — see below | `completed` |
| …the same, but the root's last turn ended in an error | `conductor_error` (the text is still reported) |
| The root exits or crashes first, or its spawn or first prompt fails | `conductor_error` |
| `SIGINT` / `SIGTERM`: the root's turn is force-interrupted (bounded by `INTERRUPT_WAIT_MS`, `src/headless/runner.ts`), then the run ends. A second signal ends it at once | `signal` |

Anything else that fails still writes the one object: `signal` once a signal arrived, else `conductor_error` once the run started, else `boot_failed`. Each reason's exit code: [protocol/headless.md](../protocol/headless.md) → Headless run result.

"Nothing still coming" means: the root has ended at least one turn and holds no tool ask; and neither it nor any session it owns is mid-turn, waiting on a wake (armed, held, in flight or deferred), deferring one (a live background agent, a pending task notification, a rotation, a parked steer) or running a background Bash job. So "spawn a worker and end the turn" is not completion: the root's wake on that worker keeps it waiting, and a section lead idle on its own worker holds the root's wake the same way. An exited or crashed worker does not block — its exit is a wake to its owner.

**State is left as is.** The exit tears nothing down: no session cleanup, no worktree removal; normal sessions, worktrees and transcripts stay as a normal cc death leaves them, and the next server on that root boots over them as after any crash. Plugin backends are detached and nothing calls `stopAll`, so outside docker they keep running after the run — the next boot on that root adopts them; kill them yourself if you throw the root away. In docker, `--rm` takes them down with the container.

**Limits.**
- A context renewal or compaction of the root may drop the first-turn fragment; the canned answer and the plan approval still hold.
- The result's `costUsd` counts claude-backend turns only (as `costs.jsonl` does), and is null when the cost read fails.
- A projects root shared with a running server is refused, not shared; give each run a root of its own ([components/headless.md](../components/headless.md#provisioning-a-projects-root) → Provisioning a projects root). Two runs on two roots may share one `$HOME`.

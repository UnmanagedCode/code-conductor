# Protocol: WebSocket event payloads

## WebSocket event payloads

**UI event kinds (`ev.kind`)** — each carries `parentToolUseId` (or `null`); non-null routes into a nested sub-Conversation. Declared once as the `UiEvent` union in `shared/uiEvent.ts`, which the server and the web client both type against; the bullets carry the semantics.

- `message_start` — one per agent-loop LLM call.
  **Live shape** `{msgId, usage, model}`; `usage` is that single call's prompt size (`input_tokens + cache_read_input_tokens + cache_creation_input_tokens`) and is the only **live-frame** feed for the ctx readout apart from `context_usage` below (`turn_end.usage` is a per-turn SUM across every call in the turn — using it is the `ctx 743%` bug; see `shared/usage.ts`).
  `usage` may be **`null`**: the parser drops any block whose `input_tokens + cache_read_input_tokens + cache_creation_input_tokens` is 0, because some substitution backends' gateways report an all-zero block on every `message_start` and put the real numbers only on the final `result` and in the jsonl — latched verbatim that renders a false `ctx 0% · 0/200k`.
  The **event still fires** (it also carries the turn-boundary model reading and the idle→turn flip for a turn we didn't initiate), and both latches (`Instance._lastContextUsage`, `UsageTracker.lastUsage`) skip a null block, so a good reading — including the replayed jsonl seed below — survives.
  A present-but-zero-sum block additionally **arms the `context_usage` fallback** for that message (next bullet), so the reading arrives from `message_delta.usage` instead of staying unknown; a usage-bearing block **disarms** it.
  `loadPersistedTranscript` (`src/transcript.ts`) floors the replay path over the same three fields; a zero-start backend's persisted assistant lines carry that call's real usage (not the zero start), so the replay seed below is a real reading on such a backend too (`tests/fixtures/nonclaude-openrouter.transcript.jsonl`, pinned by `openrouter replay: a resumed zero-start session seeds a real ctx reading`).
  An **absent** `usage` still suppresses the event entirely (fixture accommodation) and leaves the arming flag untouched.
  **Replay shape** `{msgId, usage, replayed: true}`, emitted once by `loadHistory` from the newest non-`<synthetic>` assistant line's `message.usage` so a resumed session's ctx chip is populated before its first live turn (the jsonl carries no `message_start`; it also carries no `type:"result"` line, so the summed value is structurally unreachable from replay).
  The replayed one is **seq-less and never retained** — `EventLog.push` declines it, so it reaches the live feed only and never appears in a snapshot `events[]`.
  That keeps it off the ring head (where it could fake a `history_gap` at the archive seam) and out of `ring.nextSeq` (which `idleSubscriptions.ts` arms on).
  `model` is deliberately **omitted** on the replay shape so `UsageTracker` keeps falling back to the instance's tagged model for the window denominator — the jsonl reports the model bare (`glm-5.2`, not `glm-5.2:cloud`).
  The conversation model renders nothing for it in either shape (a no-op `case` in `ConversationModel.renderEvent`).
- `context_usage` `{msgId, usage}` — the **fallback** ctx reading, emitted from `stream_event`/`message_delta` (event-level `usage`, not `delta.usage`) and **only** while armed by that message's zero-sum `message_start` (previous bullet). Same three-field floor: an absent or all-zero-sum block emits nothing. The parser stays armed across a message's deltas, so **last non-zero wins** at the latch. Both latches read it exactly as they read a usage-bearing `message_start` — one whole `usage` object, no per-field merge — and `startController` (`web/src/app/controller.ts`, its `HEADER_EVENTS` set) refreshes the header chip on it. Deliberately **not** a second `message_start` shape: that would feed the delta's cache numbers into `Instance`'s cross-turn cache-miss bookkeeping and fake an eviction on the following turn. Carries **no `model`**, so the window denominator keeps resolving from the instance's tagged model. **Seq-less and never retained** (`EventLog.push` declines it) — a re-subscribing client is seeded from the snapshot's `lastContextUsage` field, and on such a backend every in-tail `message_start` carries `usage: null` and so cannot clobber that seed. The conversation model renders nothing for it (a no-op `case` in `ConversationModel.renderEvent`). Arming resets on `Parser.reset()` (reached from `_wipeForResume`), and a fork/resume starts a new `Parser`.
- `call_usage` `{msgId, outputTokens, thinkingTokens, inputTokens, cacheReadTokens, cacheCreationTokens, promptTokens, growthTokens}` — one top-level API call's figures, **live only**.
  The parser emits it for every `stream_event`/`message_delta` whose event-level `usage.output_tokens` is a number (after the `context_usage` above when that fires), with `outputTokens` = that number, `thinkingTokens` = `usage.output_tokens_details.thinking_tokens` (null when absent), and `inputTokens` / `cacheReadTokens` / `cacheCreationTokens` = that usage's `input_tokens` / `cache_read_input_tokens` / `cache_creation_input_tokens` — each **null when the key is absent** (or not a finite number), which is a different fact from a sent `0`; they feed the cache estimate (`turn_end.cacheEstimate`): `message_delta` is the only exact source of a call's output — the `assistant` envelope repeats `message_start`'s placeholder.
  `Instance._emitUi` stamps the rest (`CallUsageTracker`, `src/callUsage.ts`): `promptTokens` = this call's prompt (from its `message_start`, else its `context_usage`; the tracker is keyed by `msgId`, so a call whose `message_start` the parser suppressed for carrying no `usage` gets null rather than the previous call's figures), `growthTokens` = `promptTokens` minus the context reading from before this call — the previous measured call's prompt, so that call's output plus everything appended since (tool results, the user message, injected context, hook output), not per-tool attribution.
  Either is null when unknown; `growthTokens` is null on a fresh session's first call and on the first call after a top-level compaction, `/clear` rotation, model switch or prune; which rewinds and respawns re-seed the reading, giving their next call a baseline, is under `turn_end.contextTokens` below.
  It can be negative (CLI context edits).
  A call interrupted before its `message_delta` gets no event, but its reading still becomes the next call's baseline; when that reading differs from the one before it, its turn's `contextGrowthTokens` is null.
  **No `blockIdx`**, so it is quiescence-neutral.
  **Retained** in the ring (a re-subscribe keeps the lines) and listed in `RING_ONLY_KINDS` (`src/eventArchive.ts`) — it has a `msgId` but no correlation key, so the archive head scan must skip it.
  **Never replayed**: archive pages and resumed history carry none.
  Subagent calls emit no `stream_event` frames, so none is ever a subagent's. `UsageTracker`, the context latch and the cache-miss bookkeeping never read it; on a non-Claude session `Instance` feeds it to the cache estimate (`src/cacheEstimate.ts`).
  Always emitted; rendered as a `div.call-usage` line that is shown only while the session's **Show mid-turn statistics** box is ticked (see [features.md](../features.md)).
  The turn's sum is stamped on `turn_end` as `contextGrowthTokens`.
- `text_delta` / `text_end` — streaming text deltas.
- `thinking_start` / `thinking_delta` / `thinking_end` / `thinking_redacted` — thinking-block lifecycle; `redacted` renders as a non-expandable `thinking (redacted)` line. `thinking_redacted` carries optional `estimatedTokens` (number) — the final `thinking_tokens` estimate, stamped at emit by `Instance._emitUi`; present only when counter frames ran during the block, and renders as `thinking (redacted, ~N tokens)`.
  - **Narration.** `thinking_delta` carries `narration: true` on **every** delta of a narration block: a thinking block **with text** whose immediately preceding content block in the same assistant message is thinking with **empty** text (redacted). One predicate, `isNarration` (`src/narration.ts`), classifies it on all three surfaces — the live parser (`src/parser.ts`, decided at the block's first non-empty delta), transcript replay (`replayPersistedLine`, `src/transcript.ts`, adjacency carried across lines by the per-msgId `blockCursor`) and `get_recent_messages`' reconstruction (`src/mcp/messageReconstruction.ts`: the envelopes, by `assistant_message.blockIdx` adjacency, so a block whose predecessor's envelope is not in the ring is not narration, and an envelope without a finite `blockIdx` gets no verdict; when they yield none, the flagged deltas). Nothing else is read: no signature, token estimate, model or backend, and the CLI's own envelope field `narration_block_indexes` is ignored (it is absent from the persisted transcript). The block's `thinking_start` / `thinking_end` carry no flag. **Relies on Claude's current block ordering** — a narration block without a redacted predecessor reads as ordinary thinking. **Top-level only:** sub-agent turns (`parentToolUseId` set) are never classified, live or on replay. The ring's coalesced slot keeps the flag (it is the block's first delta).
- `tool_use_start` / `tool_use_input_delta` / `tool_use` — tool-call lifecycle.
- `tool_result` — tool-result block: `toolUseId`, `content`, `isError`, `finishedAt`, plus `yielded: true` present only when `content` exactly equals `AWAITING_INPUT_MESSAGE` or one of its earlier wordings in `EARLIER_AWAITING_INPUT_MESSAGES` (both `src/settings.ts`; the earlier wordings appear in persisted transcripts) — the orchestrator's own `can_use_tool` deny of an interactive tool. `isError` stays `true` on it. Set in `consolidateUserContent`, so live frames, replay and history pages all carry it. The UI renders it as `↪ handed to user` and leaves it out of the action-group error count. **Live only:** a foreground Agent's result also carries `agentTokens` (the envelope's `tool_use_result.totalTokens`) and `agentToolUses` (`totalToolUseCount`, or null), stamped by `Parser._handleUser` when the envelope produced exactly one `tool_result`. `totalTokens` is the **subagent's context when it finished** — its last call's prompt plus output — not the tokens it consumed, and a separate window from this session's. A backgrounded Agent (`status:"async_launched"`) carries no totals and gets neither field; replay never stamps them (it builds user events through `consolidateUserContent`), although the jsonl's `toolUseResult` has the totals.
- `user_echo` — outer user-prompt echo. Optionally `author: "human"|"conductor"` — only on a conducted worker's prompt, read from the line's author marker block (see the `user` row above), identically live and on replay; absent means **unknown** (an unmarked line, a server- or CLI-injected prompt, or a non-conducted session), never inferred from the text. Carries `userIndex`, the instance's **live** echo ordinal (absolute, 0-based; the rewind/fork anchor, immune to ring trimming). Without a live rotation it equals the position among pure user-prompt lines of the backing jsonl. It runs on across a live rotation: archive-served echoes of the current segment are restamped into the same live space (`buildArchive`), or carry **no** `userIndex` when the offset cannot be measured, and rewind/fork translate it back to a file position; optionally `skillLoad: {skill}` (see Skill-load correlation below); `cliInjected: true` when the line it came from is CLI-injected (`isSynthetic` on stdout, `isMeta` / `isVisibleInTranscriptOnly` in a jsonl — `isCliInjectedLine`, `src/parser.ts`), whether or not a pending skill load matched it — set identically live and on replay; `compactSummary: true` on the CLI's compaction summary (`stampCompactSummary`, `src/parser.ts`) — live: the first `isSynthetic` user frame directly after a `compact_boundary`, whatever its content shape (an auto-compaction sends an array of text blocks, a manual one a string), disarmed by any other user frame or a `result`; jsonl: the line's `isCompactSummary` (a string on both captures; an array-content line is not stamped). The summary stays a counted `user_echo` with its `userIndex`, so rewind/fork ordinals are unaffected by compaction.
- `compaction` — `{trigger:'auto'|'manual'|null, preTokens, postTokens, durationMs}` (each a number or `null`), the CLI's `compact_boundary`. Built by `compactionEvent` (`src/parser.ts`) from the stdout frame's `compact_metadata` (snake_case) and from the jsonl line's `compactMetadata` (camelCase) alike, so live and replay carry the same event. It is a top-level kind, not a `system` subtype: replay emits `system` for `soft_interrupted`, `read_nudge` and `task_notification` only (`neverPersisted`, `src/eventArchive.ts`). No `correlationKey`. **A top-level one clears the server's context reading** (`Instance._dropContextReading`, from `_emitUi` — live and replay alike; a parent-tagged one is a subagent compacting its own window and clears nothing): `summary().contextTokens` and the next `turn_end.contextTokens` read `null` until the next usage-bearing `message_start`. `loadPersistedTranscript` likewise discards a pre-boundary assistant usage, so a resume seeds nothing until a post-boundary call exists (a sidechain boundary resets nothing). The header chip is **not** cleared (see [features.md](../features.md)).
- `system` — subtypes incl. `init`, `history_replayed` (live: the replayed history is now in the ring and was withheld from the socket — the client re-sends `subscribe` for the active session and takes it as a `snapshot`; inside a snapshot or a lineage page it is only a divider), plus `thinking_tokens`, `cache_miss`, `model_changed`, `model_switch_failed`, `auto_resume`, `auto_resume_skipped`, `launch_failed`, `playbook_warn`, `read_nudge`, `task_notification` (sub-mechanisms below).
- `hook` — hook lifecycle.
- `turn_end` — turn boundary; carries timing + cache-miss + context fields (below).
- `turn_boundary` `{toolUseId, status}` — **replay only**: an unprompted turn starts here, the one the CLI runs to deliver a background task's notification. Built by `turnBoundaryFromDelivery` (`src/taskNotification.ts`) at `replayPersistedLine`'s `type:"user"` branch from the delivered `<task-notification>` user line (the line carrying `turnOrigin:"task_notification"`, the first line of that turn): its first `<tool-use-id>` and `<status>`, each null when absent. The jsonl keeps no `turn_end`, so without it replay runs that turn into the previous one. Never a `user_echo`, never counted toward `userIndex` (`isPureUserPromptLine` still excludes the line). A mid-turn delivery (a `queued_command` attachment) and the `queue-operation` lines emit none. Live never emits it: the previous turn ended with its own `turn_end`. Correlation key `tb <toolUseId> <status>` (`src/eventArchive.ts`); not in `RING_ONLY_KINDS`. `QuiescenceScan` force-resets on it as on an outer `user_echo`/`turn_end`. The client ends the assistant bubble on it (no row).
- `assistant_message` — reconciled assistant message (`msgId`, `message`), one per CLI envelope. `blockIdx` is the message-level index of `message.content[0]`: the parser counts the content blocks of every envelope of the message so far, per agent (`parentToolUseId`), so a message sent as one envelope per block reads 0, 1, 2… and the index survives a ring that has dropped an earlier envelope. `get_recent_messages`' reconciled pass reads narration adjacency off it (see `thinking_delta`).
- `control_response` — the CLI's ACK to a conductor `control_request` (`set_permission_mode` / `set_model` / `interrupt`), resolved against the pending-request map; hidden from UI.
- `user_question` — `toolUseId`, `questions[]`. The outer `user_echo` that answers it carries `questionAnswer: {toolUseId, questions}` (the client locks the card named by `toolUseId` and renders the answer bubble from it), stamped by `QuestionAnswerCorrelator` (`src/questionAnswerStamp.ts`) in `Instance._emitUi` (live) and `loadPersistedTranscript` (disk). Pairing rule: the last pending outer `user_question` plus `isUserQuestionAnswerText`; a match consumes the slot, a non-matching echo leaves it armed, and `cliInjected` / `skillLoad` echoes are never stamped. Sub-agent questions are not tracked. Scope is one transcript segment: a pending question is dropped at a segment rotation (`system/init` with a new session id, which covers `/clear` and renew) and on `_wipeForResume`, matching `loadPersistedTranscript`'s one correlator per segment file, so live and replay stamp the same echoes. UI-only: never sent to the CLI.
- `plan_request` — `toolUseId`, `plan`, `planPath`, optional `autoApproved`. `planPath` is the path `input.planFilePath`/`input.planPath` named, else the session's last `.claude/plans/*.md` `Write` (either path separator, returned unchanged; the fragment is home-agnostic on purpose: a remote-backed worker's plans dir is its own config dir's, `<store>/claude-config/<dirName>/.claude/plans/`, whose last component is `.claude` for exactly this reason) — attached alongside an inline `plan` **only** when that write happened in the same turn (an unverified path silently resolves to another run's plan), and unconditionally when the input carried no plan text, in which case the file's contents also become `plan`. One tracker (`src/planFile.ts`) drives both the live stream and jsonl replay, so a reload/respawn reproduces the same `planPath`, and a live `ExitPlanMode` after a resume binds a plan file written earlier in the current transcript segment (the live tracker is seeded from that segment's replay). A segment rotation (`/clear`, renew) or a prune that drops the `Write` is outside that recovery: the plan_request then carries no `planPath` and no file-derived `plan`.
- `overage_message_queued` — `data:{text, attachmentCount, ts, queuedCount}`; rendered as a muted ghost bubble; **no** `user_echo`/turn is sent.
- `raw` — passthrough.
- `segment_seam` — `{segmentId}`, **seq-less, UI-only**: a context renewal between two backing segments, labelled with the NEWER one (the segment whose content follows it). Injected by the server's presentation layer only — the WS snapshot/forwarder (`insertRingSeamDividers`, `src/eventArchive.ts`) and the lineage route (`src/lineagePager.ts`); never retained, never in `/events` or any MCP read. Renders the "Context renewed" divider (`renderSegmentSeam` in `web/src/conversation/model.ts`, drawn by `DividerView` in `web/src/conversation/items.tsx`), a merge barrier and the provenance boundary for rewind/fork. Its `segmentId` is the key the divider's controls send as `{boundary}` to `/rewind` and `/fork`.

**`system` sub-mechanisms:**

- `status` — the conversation view reads two frames: `data.status:"compacting"` (opens the running compaction bubble) and `data.status:null` with `data.compact_result:"failed"` (+ `data.compact_error`; marks it failed). Failure is live-only, since nothing is persisted. Every other `status` is hidden.

- `thinking_tokens` — `data:{estimated_tokens, estimated_tokens_delta}`, a live-only last-value-wins counter driving the thinking-block summary, emitted by the Claude CLI as a per-token progress estimate (one per `thinking_delta` token). Observed on `claude-opus-4-8`, `claude-sonnet-5`, `claude-fable-5` (all with redacted thinking — no content deltas) and `claude-haiku-4-5` (alongside **plaintext** deltas), so it is a progress signal, **not** a redaction marker; `claude-sonnet-4-6` and `claude-opus-4-7` were observed emitting none. Whether workers on a non-Claude backend emit it is unverified (no capture on disk). Both streams flood live per-token, but the ring keeps `thinking_tokens` out entirely and coalesces `thinking_delta` — and, identically, `text_delta` — to one slot per `(msgId, blockIdx)` block, so folded/counter frames arrive **seq-less** on the live feed (the client renders seq-less events unconditionally). Persistence of the count across a re-subscribe depends on the block shape:
  - **Open block** — latest count held as O(1) server state (`inst.liveThinkingTokens`), re-attached to a fresh subscriber's snapshot (see the `snapshot` row above).
  - **Closed block with text** — nothing to carry; the coalesced `thinking_delta` replays and the summary finalizes to `thinking (N chars)`.
  - **Closed redacted block** — no text replays, so the final estimate is stamped onto the retained `thinking_redacted` slot as `estimatedTokens`.
  - **Known limitation** — ring-resident only. Paths that rebuild from jsonl (resume, respawn, rewind, server-restart manifest restore, paging above `trimmedBefore`) show the bare `thinking (redacted)`: the CLI persists no counter frames to its session jsonl.
- `auto_resume` — `data:{count}`; marks the overage resume firing ("Window reset · delivered N queued").
- `auto_resume_skipped` — `data:{reason}`; fires ONLY for the genuine "session no longer running" case — a missing/past `resetsAt` no longer dead-ends; it schedules a usage recheck instead (see the usage-verified fire in [components/instances.md](../components/instances.md#srcoverageresumets)).
- `cache_miss` — `data:{cacheRead, cacheCreation}`, plus `prevPrefix` + `evicted` on the cross-turn path; an informational once-per-turn notice fired on a detected cache miss (rendered as a system line, `systemLine` in `web/src/conversation/format.ts`, no action). Detection is **cross-turn**: a miss when this turn's first-request `cache_read` (`read_N`) is below the previous turn's last-request prefix `P` (`cache_read + cache_creation`), i.e. `read_N < P − tolerance` (tolerance defined in the cache-miss detector, `src/instances.ts`) — catches full AND partial evictions. Turn 1 (no prior `P`) and the turn after a compaction (the `compaction` event), model switch (`_trackModel`), or rewind/prune/respawn (`_wipeForResume`) — each sets `_prefixBaselineInvalid`, consumed next turn — fall back to the stateless `creation > read` rule (still flags cold start / expiry / resume / cold rewind). Not flagged: warm continuations (read == `P`) or content-addressed hits. A mid-turn eviction (past the first request) is not caught (first-request-only).
- `model_changed` — `data:{from, to}`, both canonical model ids (the `claude` catalog's launch tag included, e.g. `claude-sonnet-4-6[1m]`). Announces a mid-session model switch. **Two emit sites, one helper:** `Instance._announceModelSwitch` (`src/instances.ts`), called from `_trackModel`'s real-switch branch (the CLI switched interactively — `system/init` or `message_start` starts reporting a different *canonical* id — a dated snapshot spelling of the same catalog version is not one) and from `setModel` (the UI **Change model** picker, reached over the WS `model` frame). Only a Claude→Claude switch is live: every other pair — any switch on a substitution session, and Claude onto another backend — is a restart and emits the divider below instead (and `_trackModel` returns early on a substitution backend). Both sites also rewrite the session record (`Instance._recordBackend`), so a cold resume before the next turn comes back on the new model. Re-selecting the running model emits nothing — the guard compares CANONICAL forms, so a bare id that canonicalizes to the running tagged model is a non-change. `_trackModel`'s silent-adopt branch (a resume whose model could not be recovered) also emits nothing: that is discovery, not a switch. Notices form a **contiguous chain** — each `from` is the model the previous notice's `to` left the session on — because `setModel` reads `from` AFTER its control round-trip, inside which a CLI-reported switch (a turn started during the round-trip, or the CLI's own `/model`) can land and be announced by `_trackModel` first; reading it before would skip a step or repeat one.
  - **Both context-usage latches drop on it** — `Instance._lastContextUsage` (server, in the helper) and `UsageTracker.lastUsage` (client, in `shared/usage.ts`'s `apply`). A switch moves the window denominator without changing what the reading measured, so a retained reading would render the old model's used tokens against the new model's window; the chip reads `ctx —` until the next usage-bearing `message_start`/`context_usage`, which then renders against the new window — or, when the new model's window is unknown, the previous known one (see [models.md](../models.md), live-switch carry-over). The client drop is `lastUsage = null` only — never `reset()`, which would also blank the `cum.*` session totals a switch does not invalidate. `_trackModel` runs BEFORE the per-event `_emitUi` in `_handleStdoutLine`'s loop, so a switch frame that also carries usage re-latches its own reading in the same line and no `ctx —` flash is rendered; the emitted order is `model_changed` then `message_start`, and the client applies them in that order too.
  - **Retained** (unlike `context_usage`): `EventLog.push` accepts it, so it carries a `_seq`, survives a re-subscribe as a transcript notice, and advances `ring.nextSeq` — which is what lets a `setModel`-originated one freeze out a pending idle-drain settle (bounded in [components/instances.md](../components/instances.md#srcidlesubscriptionsts) → the idle task-drain settle). `startController` (`web/src/app/controller.ts`, its `HEADER_SYSTEM` set) refreshes the header chip on it.
- **Restart switch dividers** — `model_changed` with `data:{from, to, restart:true, switchId}` (confirmed); `model_switch_failed` with `data:{from, to, error, switchId}` (failed; rendered `Switch to <to> failed · still on <from>`, warn-styled, `error` as the tooltip) or `data:{from, to, cancelled:true, switchId}` (a Terminate landed mid-switch; rendered neutral as `Switch to <to> cancelled · session stopped`, no tooltip, no failure chip). A switch that crossed backends adds `fromBackend` + `toBackend` (backend ids) to all three, and every model in the rendered text gains ` on <backend>` — e.g. `Model changed: <from> on <fromBackend> → <to> on <toBackend> (session restarted)`; a same-backend switch carries neither key. Both come from `modelSwitchEvent` (`src/transcript.ts`), one per ledger entry on the session record (`modelSwitches`, [models.md](../models.md)).
  - **Durable.** Every transcript read splices them back at their anchor through `loadPersistedTranscript` — ring replay, archive paging, `get_transcript` (live and disk), lineage scroll-back. The spliced copy carries `replayed:true`; `shared/usage.ts` does not drop the ctx reading on a replayed one (the snapshot seed already measures any later turns). `neverPersisted` treats an event carrying a `switchId` as persisted and `correlationKey` keys it `msw <switchId>`; an identity `model_changed` (no `switchId`) stays ring-only. The message readers (`get_recent_messages`, `forward`) ignore them.
  - **Emitted live** once: the success divider after the confirmation (it drops both ctx latches like any switch) — even when recording it in the ledger fails (logged; the divider then does not survive a replay); the cancelled divider straight into the ring (nothing is relaunched), once the attempt's own replay has finished; the failure divider only through the re-resume's replay, or — when that relaunch is `--session-id` — through the null-anchored seed.
- `playbook_warn` — `data:{tool, code, reason, sessionId?}`; the only UI signal for a **warn-mode** playbook refusal, emitted by `src/mcp/playbookGate.ts` on the **calling conductor's** instance (it made the call; `sessionId` — the refused call's target worker — is absent when the call named none, e.g. `spawn_instance`). Emitted strictly **after** the refused `call` row is appended to the event log, and only under `warn` — under `enforce` the refusal goes back to the caller, which needs no bubble. **UI-only** — `_emitUi` reaches the event ring and the WebSocket feed, never the CLI's stdin, so the conductor agent still sees the call succeed and enforcement semantics are unchanged. Ring-resident (survives a re-subscribe, lost on restart or eviction); the event-log row is the durable record. Rendered as an amber system line (`data-tone="warn"`, `SystemLineView` in `web/src/conversation/items.tsx`).
- `event_log_blocked` — `data:{reason}`; the event log refused a write because this server is not the projects root's sole writer (`RootLock.writerCheck`, [event-log.md → The writer](../event-log.md#the-writer)). Emitted once per blocked episode, on the live conductor the first dropped row names (its actor, else its subject) — none when neither is a live conductor. **UI-only**, like `playbook_warn`; rendered as an amber system line.
- `read_nudge` — `toolUseId`, `data:{count, tool, text}`; the conductor read nudge, built by `readNudgeEvent` (`src/conductorReadNudge.ts`) on both paths.
  - **Live:** emitted on the **conductor's** instance by `HookBroker` (via `onReadNudge`) after it has answered the hook whose `additionalContext` carried `text`; `toolUseId` is the envelope's `tool_use_id`.
  - **Replay:** rebuilt from the session jsonl's `type:"attachment"` line with `attachment.type:"hook_additional_context"`, which the CLI writes between the `tool_use` line and its `tool_result` line: `hookEvent:"PreToolUse"`, `hookName:"PreToolUse:<tool>"` naming `project_read` or `project_bash`, `toolUseID` (= the envelope's `tool_use_id`), and `content` — an array of strings, one of which matches `parseReadNudgeText`. Any other `hook_additional_context` attachment (a user's own hook, a redirect note) replays nothing.
  - **Survives** browser reload, server restart, ring eviction and archive scroll-back. It correlates across the archive/ring seam by `toolUseId` (`correlationKey` → `rn <toolUseId>`) and is not skipped by `neverPersisted`.
  - **Rendered** as an amber system line (`data-tone="warn"`, `SystemLineView` in `web/src/conversation/items.tsx`) whose detail is `data.text` verbatim. It is not a run-ender, so it leaves the open action group open.
- `task_notification` — `toolUseId`, `data:{task_id, status, output_file, name, exitCode, summary, notified}`; a task's end, built by `taskNotificationEvent` (`src/taskNotification.ts`) on both paths. `data.task_id` keeps the wire name (`Instance`'s task tracking reads it). Every live frame becomes one, rendered or not.
  - **`notified`** — the one rendering flag, read by `shouldRenderSystem` and by `neverPersisted`/`correlationKey`. `true` iff the task was started in the background and `status` is `completed` or `failed`. Not notified: a foreground task (a foreground Agent's frame carries a non-empty `output_file` too, so `output_file` is not evidence), and any stop.
  - **Stops are hidden on both paths, by design.** A TaskStop'd task streams `status:"stopped"` with `summary` = its bare description and leaves no jsonl enqueue; a task cut short by the session ending (SIGTERM) streams `stopped` with `output_file:""` and persists an enqueue saying `killed` / `Background command "X" was stopped`. Live hides `stopped`; replay drops `killed` and `stopped` enqueues. The stop is either visible as the TaskStop call or was never delivered to the model.
  - **Live:** `Parser._handleSystem`, from the `system/task_notification` frame (`taskNotificationFromFrame`) plus the same task's `task_started`, which `TaskStarts` records per `Parser` (reset with it). `name` = `task_started.description` (for a Bash with no description the CLI puts the command text there); `exitCode` = `sentenceExitCode(summary)`, null for an Agent; `summary` = the frame's (an Agent's is its result text). A frame whose `task_started` this parser never saw is not notified. `Parser.reset` runs only at a process boundary (launch, `_wipeForResume`), and a background task dies with its process.
  - **Replay:** from the jsonl's `{type:"queue-operation", operation:"enqueue", content}` line whose `content` starts with `<task-notification>` (`isTaskNotificationEnqueue`, `taskNotificationFromEnqueue`). The CLI writes it when the task ends, in the slot the live frame took; the delivery lines (a `<task-notification>` `type:"user"` line or a `queued_command` attachment with a string `prompt`) are written when the model next takes input, so neither replays the notification. The `type:"user"` delivery line replays a `turn_boundary` (it starts the unprompted turn that delivers the notification); the `queued_command` attachment (a mid-turn delivery) replays nothing, as do `dequeue`/`remove` lines and every other enqueue. Required: exactly one `<task-id>`, a `<tool-use-id>` and a `<status>` of `completed`/`failed` — which excludes Monitor stream events (`<summary>Monitor event: …</summary><event>…</event>`) and the resume-time `No completion record was found for N background agents…` line (several `<task-id>`s). Tag text is entity-escaped (`&lt;`, `&gt;`, `&amp;`; unescaped with `&amp;` last). `name`/`exitCode` from the unescaped `<summary>` sentence; `summary` = `<result>` when present (an Agent), else the sentence; `notified: true` — only background tasks are enqueued. Replay has no `task_started`, so the enqueue alone decides: a notification hidden live for want of its `task_started` still renders after a reload.
  - **Sentences** (`SENTENCE_RE`, `EXIT_CODE_RE`): `Background command "X" completed (exit code N)` (optionally `N: No matches found`), `… failed with exit code N`, `… was stopped`; `Agent "X" finished`, `Agent "X" failed: <reason>`; `Monitor "X" stream ended`, `… script failed (exit N)`, `… ended without producing output (exit N)`. `status` never comes from the sentence.
  - **Survives** browser reload, server restart, ring eviction and archive scroll-back. A notified one correlates across the seam by `tn <toolUseId> <status>` (a background Agent may notify more than once per tool use; the pair is unique within a session); a non-notified one is skipped by `neverPersisted`.
  - **Rendered** as a folded `<details data-subtype="task_notification">` (`SystemLineView`, `web/src/conversation/items.tsx`; `data-tone="warn"`, amber, when `status` is `failed`): the line is `name · status · exit N` (`taskNotificationHeadline`, `web/src/conversation/format.ts`) (no exit part when `exitCode` is null), the fold holds `summary` and `output: <output_file>`. Exception: an Agent's notification whose card (the `tool_use` with the same `toolUseId`) is in view and holds the report renders as the headline alone, a plain `div` with the same `data-subtype`, `data-tone` and `[data-headline]` and no fold (`SystemNode.inCard`, `web/src/conversation/model.ts`). "Holds the report" means the sub-agent transcript's last text block, trimmed, equals `summary`. Otherwise the fold stays: no card in view, no sub-agent transcript (its `subagents/agent-<agentId>.jsonl` absent on replay), a transcript with no text, or its last text differs, which is the usual case for a failed Agent, whose `summary` is the CLI's `Agent "X" failed: <reason>` sentence rather than a result. A failed Agent whose `<result>` matches its card goes headline-only like any other. Placement (`isTurnTailNotice`, `turnEndSlot`): a notified notification that is among the trailing root items when the `turn_end` arrives renders below that turn's `turn_end` row; content that streams into the same bubble after the notification still lands above the row, since it joins the bubble, not the root list. Not a run-ender.
  - **Known limitation — the correlation key assumes live and persisted `status` agree** for a rendered notification. They can disagree: C9 (SIGTERM) streams `stopped` and persists `killed`. That is harmless today only because neither status renders. If a rendered pair ever disagreed, its ring head would miss the archive and abandon to the echo fallback (a gap marker), and a twin served from below that cut could render the task twice.
  - **Replay never reaches the wake hubs.** `Instance._emitUi` forwards its `replayed` flag on the manager's `'event'` (`{id, ev, replayed, pullOnly}`; `pullOnly` keeps the event off every socket in `src/wsHub.ts`), and the `IdleSubscriptionHub`/`SessionRenewController` registrations skip replayed events — so a reload replaying `task_notification`s neither arms an idle-drain settle nor fires an armed renewal.
- `launch_failed` — `data:{code, signal, stderr}`; fires when a subprocess on a **substitution backend** (any backend but the identity `claude` row) terminates on its own (nonzero/signalled exit, not a commanded kill) — emitted right after the bare `exit` event. **Where the reason lives depends on the sub-case:**
  - **The wrapper ran and died** (daemon down, cloud-auth 401): `stderr` is the captured stderr, so the real reason is visible instead of an unexplained exit.
  - **The wrapper NEVER STARTED** (wrapper binary missing): no process ever wrote anything, so `stderr` is `null` and `code` is `-2`; the reason (`spawn <cmd> ENOENT`) is on the **preceding `spawn_error` event's `message`**. A failed spawn emits no `exit` at the OS level — this pair exists at all because `Instance` latches its terminal path on `'close'` as well (see [architecture.md](../architecture.md) → Instance lifecycle → terminal latch).

  This is the only failure signal for a bad backend, since there is no spawn-time preflight. Never emitted for the `claude` backend or clean/commanded exits. **Known gap — no frontend consumer:** it reaches WS subscribers and the event ring, but is not a subtype `shouldRenderSystem` (`web/src/conversation/model.ts`) shows, so nothing renders it; what a user actually sees on either sub-case is the co-emitted `exit` and `spawn_error` rows.

**`turn_end` additional fields:** carries `cacheMiss` (bool) + `firstReqCacheRead`/`firstReqCacheCreation` (the deciding first-request usage) + `firstReqEvicted` (`P − read_N` on the cross-turn path, else 0), persisted to `costs.jsonl` as `cache_miss`/`first_req_cache_read`/`first_req_cache_creation`/`first_req_evicted`.
It also carries `durationMs` (turn walltime incl. tool exec, from the SDK result's `duration_ms` — genuinely per-turn), `durationApiMs` (the SDK's raw `duration_api_ms`, a cumulative session total kept for reference), and `durationApiMsDelta` (the per-turn LLM/inference time, derived as a delta against the prior turn — mirrors `cost`/`costDelta`).
`duration_ms` is persisted as `duration_ms`; `durationApiMsDelta` is persisted as `duration_api_ms` (so aggregates sum true per-turn LLM time).
Both are null on legacy rows written before capture; rows written before the delta fix carry the old cumulative `duration_api_ms` and are left as-is.
`costs.jsonl` rows additionally carry `parentSessionId` — the spawning conductor's current sessionId, resolved from the worker's ephemeral `callerInstanceId` when the `turn_end` is observed, not when the (queued) write runs (null for UI/HTTP-created sessions) — which drives the per-session worker-tree rollup.
**`cacheEstimate`** `{inputTokens, cacheReadTokens} | null` — non-Claude sessions only (absent on `claude`): the turn's `usage.input_tokens` re-split into uncached input + an estimated cache read by `src/cacheEstimate.ts` (`inputTokens + cacheReadTokens === usage.input_tokens`); null when no call of the turn was estimated (every call reported a cache read, or the backend has reported one before), when `usage` is null, or when `usage.cache_read_input_tokens > 0`.
`costs.jsonl` writes it into `input_tokens` / `cache_read_tokens` and adds `cache_estimated: true` (additive, after `first_req_evicted`; absent on every other row); `UsageTracker` sums it into `cum.inputTokens` / `cum.cacheRead` and sets `cum.cacheEstimated`.

**`turn_end` context fields** (stamped by `Instance._handleStdoutLine`; ring and live feed only — `costTracking` copies its fields one by one and persists none of them; `turn_end` is ring-only, so archive-served pages have no turn-end line at all):

| Field | Value |
|---|---|
| `contextTokens` | `contextReading(Instance._lastContextUsage)` (`src/sessionPrune.ts`) — the **latest top-level API call's prompt** (`input_tokens + cache_read_input_tokens + cache_creation_input_tokens`). Excludes that call's output, so between turns it reads one reply short. Subagent calls never feed it. `null` when nothing has measured the context since the last clear (`_dropContextReading`: top-level compaction, `/clear` rotation, model switch, rewind/respawn). A rewind or respawn re-seeds it from the replayed transcript (`loadHistory`), except a rewind to the first user message, which relaunches as a fresh session with nothing to replay; a prune skips that seed. |
| `contextWindowTokens` | `Instance.contextWindowTokens` at the turn's end — the window the reading was measured against, or `null` when unknown. |

When non-null it equals the sum of the turn's `call_usage.growthTokens` (raw values). `null` when that baseline is null (a fresh session's first turn, or the first after a top-level compaction, `/clear` rotation, model switch or prune; which rewinds and respawns re-seed the reading is under `contextTokens`), when a clear lands mid-turn, on the first turn after a `POST /api/instances/:id/respawn` of a process that died with a call already open in the turn (the respawn reuses the instance, and its reset leaves that turn open), when no call in the turn stamped a growth (no usage-bearing call; a `/compact` turn), and whenever the two figures differ — e.g. a call cut off before its `message_delta` that moved the reading. Can be negative (CLI context edits). Subagent calls never feed it. |

**Skill-load correlation (`attachSkillLoad`, `src/parser.ts`).** A `Skill` tool call's SKILL.md content is injected back by the CLI as a separate `user` message. The parser tags the resulting `user_echo` with `skillLoad: {skill}` only when it can correlate that message with a queue of pending `{toolUseId, skill}` entries (`pendingSkillLoads`) pushed when a `Skill` tool_use is seen; an uncorrelated injection renders as an ordinary `user_echo`.

*Two surfaces, two marker names, two correlation strengths* — normalized in one place (`skillInjectionMarker`), because the replay path testing the stdout field name is exactly what shipped the "skill bubble only renders live" bug:

| surface | "CLI-injected" marker | identity link | correlation |
|---|---|---|---|
| stream-json **stdout** envelope | `isSynthetic: true` (CLI builds it as `isMeta \|\| isVisibleInTranscriptOnly`) | none — never carries `sourceToolUseID` | FIFO order (the CLI's synchronous `tool_use` → `tool_result` → injection ordering) |
| persisted **jsonl** line | `isMeta: true` (also `isVisibleInTranscriptOnly` for compaction lines) | `sourceToolUseID` — the id of the originating `Skill` tool_use | exact id match only |

Match order in `attachSkillLoad(events, sourceLine, pendingSkillLoads)`: (1) `sourceToolUseID` names a pending entry → splice it out (consuming it) and tag; (2) `sourceToolUseID` names nothing pending → the entry is gone or was never made (expired by an intervening real turn, dropped by an erroring `tool_result`, or its `Skill` tool_use sits outside the replayed range — every `sourceToolUseID` line in the persisted corpus names a `Skill` tool_use, so this is never "an injection for a different tool"), claim nothing and consume nothing; (3) jsonl-marked with **no** `sourceToolUseID` → a compaction continuation or hook feedback, never a skill load (no FIFO fallback on this surface — every real jsonl skill injection carries the id, so a fallback could only mis-stamp); (4) stdout-marked → FIFO `shift`; (5) unmarked → a real user turn, expire the queue.

**`_handleAssistant` is the single registration point** for pending entries on the live path. Measured over the 11 stdout captures on disk (12,226 lines, 6 model ids): 353 `tool_use` ids appeared on both the `assistant` envelope and the streaming frames — envelope first in **353/353** — and **0** appeared on the streaming frames alone. **Nothing arrives streaming-only**, so registering at the envelope loses nothing; registering in the `content_block_stop` branch as well would only double-register, because the envelope lands first and the entry is still pending when the stop frame arrives, and the duplicate goes on to mislabel the next injection. A trimmed live capture of one such turn is committed as `tests/fixtures/scenario-live-skill-load.json`.

**Sub-agent `tool_use`s are deliberately not registered live.** The CLI forwards sub-agent turns as envelopes tagged with `parent_tool_use_id` and no `stream_event` frames. No injection was ever observed to follow one: the *one* captured sub-agent `Skill` call ran `tool_use` → `tool_result` → `system` with no injection. ⚠️ That is **n=1 and rests on a capture since deleted** — it is no longer re-derivable from anything on disk, unlike every other number on this page, and no surviving capture contains a sub-agent turn at all, so nothing corroborates it either way. An entry registered for a sub-agent could never be consumed by its own injection, and — its `tool_result` not being an error, so the error-drop never fires — would sit at the queue head and claim the next *top-level* injection. Not registering is therefore the conservative reading: it forgoes folding we have no evidence is possible rather than risking a mislabel. A sub-agent `Skill` still folds on **replay**, where the persisted jsonl does record the injection (`loadSubAgentTranscript`, pinned against `tests/fixtures/real-skill-load-subagent.jsonl`).

`src/transcript.ts`'s replay path threads the same queue (alongside the existing `blockCursor`) through `replayPersistedLine`, for both `loadPersistedTranscript` and `loadSubAgentTranscript`, so live and replayed sessions tag identically. Replay always parses a session's jsonl in one complete pass from line 0 (never a partial/windowed range), and the queue is a fresh local array per call, so a `Skill` tool_use and its content injection are always correlated within the same pass regardless of how the resulting events are later paged.

Where only FIFO order is available, an entry could be orphaned (skill errored, or its turn was interrupted before the injection arrived) and survive to mislabel a later, unrelated injected message, so entries are bounded (`expireSkillLoads`): an erroring `tool_result` for its `toolUseId` drops it immediately, and any genuine (unmarked) `user_echo` — a real prompt, including the `queued_command` replay branch and `Instance.prompt()`'s direct live emission — clears the whole queue, since the synchronous ordering guarantee is broken once a new real turn begins. The id-matching surface is not exposed to that risk.

The client (`renderUserEcho` in `web/src/conversation/model.ts`, drawn in `web/src/conversation/items.tsx`) renders a `skillLoad`-tagged echo as a collapsed fold (`data-fold="skill"`) — the title names the invoked skill (`Loading skill: <name>`), the body holds the raw SKILL.md text — instead of the plain-text bubble a normal echo gets.

**Agent-tool (subagent) task events.** The CLI emits `system` events with these subtypes:

| Subtype | Payload | Notes |
|---|---|---|
| `task_started` | `{task_id, tool_use_id, description, is_backgrounded, subagent_type, task_type, prompt}` | fired the instant an `Agent` tool_use dispatches (foreground or backgrounded) |
| `task_progress` | `{task_id, tool_use_id, usage:{total_tokens,tool_uses,duration_ms}, last_tool_name}` | periodic ticks while it runs |
| `task_updated` | `{task_id, patch:{status, end_time}}` | on a state transition; `status` one of `completed\|failed\|cancelled\|error` for a terminal one |
| `task_notification` | `{task_id, tool_use_id, status, output_file, summary, usage}` | the human/model-facing "it's done" ping — the same event a `<task-notification>` block wraps when injected back into a worker's own conversation; rendered for a background task (`system`/`task_notification` above) |

None carry `parent_tool_use_id`, so they land as top-level `system` events like `turn_end`.
`shouldRenderSystem` (`web/src/conversation/model.ts`) hides `task_progress`/`task_started`/`task_updated` from the chat feed; `task_notification` renders iff `data.notified`.
That re-injected `<task-notification>` block is itself persisted as a `type:"user"` jsonl line — `isTaskNotificationContent` (`src/parser.ts`) recognizes it by tag shape.
Two sites filter it as they filter `SOFT_INTERRUPT_MARKER` (`parser._handleUser`, which emits nothing for it, and `transcript.isPureUserPromptLine`, which does not count it), and the replay site (`transcript.replayPersistedLine`) turns it into a `turn_boundary` marker, never a `user_echo`.
So it never becomes a user bubble or shifts a rewind/fork index; replay marks it because the line starts the unprompted turn that delivers the notification.
Server-side, `Instance` tracks in-flight ones in `_activeAgentTasks` (see `displayStatus` below).
Task events fire for more than explicit `run_in_background` calls: background is the Agent tool's default, and long-running foreground Bash gets promoted to a task (every promoted Bash observed ran ≥3.5 s — a full test run always does).
A foreground Bash that exceeds its `timeout` is killed at the timeout and emits no task frames (CLI 2.1.286: `timeout: 3000` on an 8 s command gives tool_result `Exit code 143` / `Command timed out after 3s`), and a short foreground Bash emits no task frames.
`task_started.task_type` discriminates the kinds: `local_agent` (Agent-tool subagents), `mcp_task` (an auto-backgrounded MCP call, see **Auto-background**) and `local_bash` (backgrounded/promoted Bash).
Only non-`local_bash` tasks enter `_activeAgentTasks` — a promoted long-lived command (a started server) never emits a terminal task event, so counting it would pin `displayStatus:'running'` and defer the idle wake and session renewal indefinitely, leaving only a repeating heartbeat.
Delivery has two shapes: a **slow** task's tool_result resolves immediately with an "Async agent launched" ack (`isAsync:true`), so `turn_end` can fire while `task_updated` is still pending; a **fast/blocking** task holds the tool_result open and delivers the full output right after its mid-turn `task_notification`, always before `turn_end`.

**Overage queue intercept (`Instance.prompt`).** A **non-internal** `prompt()` is **queued** (`{text, attachments, ts}` onto `_overageQueue`), emits `overage_message_queued`, and returns **before** `user_prompt` — so it neither resumes the session nor cancels the pending resume — when **either** intercept path fires:

| Path | Condition |
|---|---|
| (a) per-session | the session was stopped mid-turn and is armed: `autoStoppedForOverage && autoResumeAt` |
| (b) global gate | the GLOBAL gate is active: `inst._overageGate() → {active, resetsAt}`, where `active` is true iff `_overageActive && _overageResumeMode` (i.e. `stop-resume`, not plain `stop`) **and** `_overageResetsAt` is a valid **FUTURE** epoch-secs instant **and** `_inUsageWindowFlow(inst)` — the ROOT-scoped usage-window predicate (`src/usageWindowDomains.ts`), so a session whose whole root tree touches no monitored domain reports `active:false` and its sends flow normally, while a **non-Claude worker under a Claude conductor is in-flow**: it queues and shows the overage badge like any Claude sibling in that position. The one exception needs **both** conjuncts: a worker that was **mid-turn when the window tripped** **and** whose conductor is in control is stopped **un-armed**, and an un-armed session *refuses* instead of queueing (`OVERAGE_STOPPED_UNARMED` on the MCP surface, below). In-control alone is not enough — Pass 3 visits only mid-turn instances, so a worker that had already gone idle is never stopped or marked and queues like any other in-flow session |
| internal carve-out | every `internal:true` prompt **falls through** and bypasses both intercept paths — the idle-wake stub, the renewal reseed, and the auto-resume's own send (which first clears the flags via `cancel`) |

That future-`resetsAt` check is the **safety rail**: a queued send bypasses the manual-resume clear, so a missing/past/NaN reset must mean `active:false` (sends flow normally) or every session would lock out permanently.
Path (b) makes it a **global lockout**: idle/existing and brand-new sessions queue too.
A queued-only session (no `autoResumeAt` yet) emits an internal **`overage_queued`** (`{resetsAt}`) that the manager (`_armResumeNow`) turns into an immediate resume deadline via the controller — it can't wait for a mid-turn→idle transition.
`_armResumeNow` has two more callers for the same reason: `_directOverageStop` on an already-idle session, which is never prompted and so never transitions at all; and `_armSeveredCaller`, for the idle driver of a caller whose wake the overage sever cut (the caller, or its immediate live conductor) when no stop reached that driver — armed idle-parked (`_overageWasIdleParked`), see [components/instances.md](../components/instances.md#overage-trip-detection--central-routing) → Overage trip detection + central routing.
The one choke point covers the WS `prompt`, MCP `send_prompt`, and any REST path.
On fire, `OverageResumeController.run` delivers all queued messages as **one combined** `prompt({internal:true})` (preamble + numbered list + concatenated attachments); an empty queue is the unchanged single resume.
The preamble is **three-way**, selected by `overageResumeKind(inst)`: stopped mid-work (`_overageWasStopped`) → "…continue where you left off"; idle-parked (`_overageWasIdleParked`, the stop found it idle) → "You were idle when the overage stop fired…"; neither → the softened queued-only "Delivering the messages you queued while paused".
`summary().queuedCount` carries the depth; `summary().overageActive` + `overageResetsAt` (read from the gate) let the client paint the paused state before the first message is typed.
`_clearOverage` (window reset) clears `_overageResumeMode` and emits a fresh `status` for every instance so paused banners drop everywhere.

**`summary().displayStatus` / `activeAgentTasks`.**
Additive, display-only fields alongside `status` — `activeAgentTasks` is the count of in-flight Agent-tool tasks (`_activeAgentTasks`, keyed by `task_id`; `task_type:'local_bash'` tasks are excluded at `task_started`, unknown `task_type`s counted; cleared when the CLI exits, since a killed CLI sends no terminal task frames); `displayStatus` is `'running'` when `status === 'idle'` and `activeAgentTasks > 0`, else identical to `status` — background Bash jobs (`backgroundJobs`, below) never overlay it.
Never repurposes the `status` enum itself, so nothing that gates on the literal 5 `status` values (composer, kill/resume buttons) is affected.
`IdleSubscriptionHub._onTurnEnd` **does** read the count (via `Instance.activeAgentTaskCount`): a `turn_end` while `activeAgentTasks > 0` **defers** the idle wake until the follow-up `turn_end` after the last subagent finishes.
It **also** defers on `Instance.taskNotificationPending` — set when a `task_notification` fires *mid-turn*, cleared by any top-level `tool_result` that follows it within the turn (the task's own sync-delivered result, or the outer tool round-trip the CLI attaches queued notifications to).
Still set at `turn_end` therefore means the notification is genuinely queued and an unprompted **re-invocation turn** will deliver it; the wake waits for that turn's `turn_end`.
A notification consumed in-turn wakes at the same `turn_end` — parked (AskUserQuestion/ExitPlanMode) or not.
So the dispatch-and-wake callback fires only when the worker AND its subagents are done and no re-invocation turn is owed (a never-finishing subagent — or a CLI that never flushes its queue — shows up as a repeating heartbeat instead).
Every summary-based surface carries the fields — `GET /api/instances` plus every MCP tool that returns a worker summary through `toConductorView()` (`src/mcp/handlers.ts`).
`displayStatus:'running'` (not just raw `idle`) means "still busy"; `status:'idle'` alone doesn't prove a backgrounded subagent has finished.

**`summary().pristine` / `title` / `displayLabel`.** `pristine` is true from a `pristine: true` create (`POST /api/instances`) until the instance's first prompt from any sender, and is never persisted. `title` is the session's own title, else the draft title a pristine conductor was listed under (`Instance.draftTitle`: the leave's text with whitespace runs collapsed to one space, normalized and capped like any title), else null; the first prompt drops the draft title. The REST summary surfaces carry `pristine` (`GET /api/instances`, `POST /api/instances`, `GET /api/sessions/:sid/pristine`); `CONDUCTOR_VIEW_KEYS` does not. `displayLabel` is `sessionLabel` (`shared/promptPreview.ts`) over the synthetic row the sidebar builds from a live instance (`sessionFromInstance`, `shared/conductors.ts`): the trimmed `title` (the draft title included), else `promptPreview(firstPrompt)` (a server- or CLI-written first prompt named by `readablePrompt`, cut to 80 chars, whitespace collapsed), else `(new session)` — never the sessionId prefix, since the row is synthetic. Derived on every `summary()` and never persisted. Every REST summary surface carries it (`GET /api/instances`, `POST /api/instances`, `GET /api/sessions/:sid/pristine`, and the summary `POST /api/instances/:id/respawn`, `/fork`, `/prune` and `/persist` return); `CONDUCTOR_VIEW_KEYS` does not. **Where it differs from the sidebar:** `displayLabel` reads `Instance.firstPrompt` (captured by the first prompt, or read back from the transcript at a resume, and rewritten by no rotation or rewind), while the sidebar's row for a persistent session reads the first prompt of the session's **current segment's** transcript once that file is on disk (`readFirstPrompt`, `src/projects.ts`). For an untitled session the two differ whenever that file's first prompt is not the one `Instance.firstPrompt` holds:
- **A rotation** (`renew_session`, prune): the new segment opens with the renew seed or the `/clear` head, so the sidebar reads `Context renewed`.
- **A rewind to the first prompt**: the truncated file holds no conversation record, so the session relaunches on a fresh segment (`_relaunchSegment`) and the sidebar reads the next prompt sent once that segment's file is written.
- **A first prompt (or a record before it) that does not end within `FIRST_RECORD_CAP`**: `readFirstPrompt` returns null, so the sidebar reads the sessionId prefix.

**Background Bash jobs.** A `Bash` call with `run_in_background:true` that is still running after the worker's turn ended; the CLI re-invokes the worker when it exits. Source: the CLI's `system/background_tasks_changed` frame — a **level-triggered snapshot** of every live background task, emitted whenever that set changes:

```json
{"type":"system","subtype":"background_tasks_changed","tasks":[{"task_id":"bqcf1i5kw","task_type":"local_bash","description":"sleep probe"}]}
```

Observed on CLI 2.1.286 (fixture: `tests/fixtures/bg-bash-jobs.stdout.jsonl`):

| Case | Frames, in order |
|---|---|
| bg Bash starts | snapshot [the job] → `task_started` {`task_type:'local_bash'`, `is_backgrounded:true`} → tool_result `Command running in background with ID: …` |
| job exits (worker idle) | snapshot [] → `task_updated` {`status:'completed'`} → `task_notification` {`status:'completed'`} → unprompted re-invocation turn |
| `TaskStop` | snapshot [] → `task_updated` {`status:'killed'`} → `task_notification` {`status:'stopped'`} |
| interrupt (`control_request` interrupt) | nothing — the job keeps running |
| stdin EOF (graceful CLI exit) | snapshot [] → `task_updated` killed → `task_notification` stopped → exit |
| CLI SIGKILLed | no frame; the job's process survives as an orphan |
| no `description` | snapshot / `task_started` `description` = the full command, untruncated |
| Agent + Bash | one snapshot lists both (`local_agent` + `local_bash`); an Agent's completion drops only it |
| a subagent's own bg Bash | listed (`task_started.owned_by_subagent:true`); outlives the Agent task, re-invokes the subagent on exit |
| a subagent's foreground Bash | `task_started` `is_backgrounded:false`, never in a snapshot |
| `Monitor` (observed on CLI 2.1.302) | listed in the snapshot and `task_started` {`task_type:'local_bash'`, `is_backgrounded:true`}, keyed by the Monitor's `tool_use_id`, like a bg Bash; ends with `task_notification` summary `Monitor "X" stream ended` — so it is tracked as a background job |

- **Tracking.** `Instance._backgroundJobs` (task_id → `{title, startedAt}`), folded by `reconcileBackgroundJobs` (`src/backgroundJobs.ts`) from each snapshot's `local_bash` entries only. `title` = `trunc(description, JOB_TITLE_MAX)` (whitespace collapsed); `startedAt` = cc's clock (epoch ms) when the id first appears; a non-array `tasks` is ignored. Emits `status` only when membership changes. Reset in `spawn()`; cleared in `_handleExit` **before** the exit's own status change (a SIGKILLed CLI sends no empty snapshot).
- **`summary().backgroundJobs`** — `[{title, startedAt}]`, in every summary surface, including the MCP conductor view (`CONDUCTOR_VIEW_KEYS`). Display-only: never read by `IdleSubscriptionHub` holding (`targetDefers`, `_waitsOnWork`) or `isCaller`.
- **`waitingOnJob`** — `InstanceManager.list()` only (so `GET /api/instances`, never an MCP row): true for a live instance with a job and for every live owner above one (spawn ∪ dispatch, `IdleSubscriptionHub.ownersOf`; a dead owner stops the climb) — `jobWaiters` in `src/backgroundJobs.ts`. Independent of `awaitingWake`.

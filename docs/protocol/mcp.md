# Protocol: MCP tools — addressing and sessions

## MCP tool protocol

Mounted at `POST /mcp` and `POST /mcp/<sessionId>` (Streamable HTTP, JSON-RPC 2.0). Tools are listed in [features/mcp.md → MCP interface](../features/mcp.md#mcp-interface). This section specifies the wire contract — a **clean break** with no backwards-compatibility aliases.

**Streaming and cancellation.** A single, non-batch `tools/call` whose `Accept` includes `text/event-stream` may answer as an SSE stream of `notifications/progress` (only when the request carried `params._meta.progressToken`) ending in the JSON-RPC response; `notifications/cancelled {requestId}` from the same session, or a closed connection, aborts an in-flight call; `GET /mcp` stays `405`. The `--mcp-config` entry cc writes carries a per-server `timeout` (`CC_MCP_SERVER_TIMEOUT_MS`). The run channel `run_code`'s child uses is internal; its routes are in [code-mode.md → The run channel](../code-mode.md#the-run-channel-internal). All in [code-mode.md](../code-mode.md).

**Tool audience.** Every core tool declares an `audience` on its registry entry (`src/mcp/tools.ts`): `conductor` iff it spawns, drives, lands or retires a session, or mutates the project/workspace registry; `all` otherwise. A worker (any non-`.conduct` session, hand-spawned included) is not offered the `conductor` tools and a call is refused `TOOL_UNAVAILABLE_TO_CALLER` before the playbook gate, exactly as for plugin tools. The predicate, caller kinds and channels are in [plugins/tools.md → Tool audience](../plugins/tools.md#tool-audience).

**Scope: the text format.** The URL contract (caller identity in the path, `?format=json|text`), the JSON format (the default: `structuredContent` against each tool's `outputSchema`), its error channels and ceilings, and the REST alias are specified in [mcp-applications.md](../mcp-applications.md). Everything below describes the **text format** (`?format=text`) — the agent view every worker's `--mcp-config` names — unless it says otherwise; the call core (validation, prefix resolution, playbook policy, handler) is the same in both.

**Input params.**
The worker handle is always `sessionId` (the stable session id; the per-process `instanceId` is internal and never accepted — a legacy `{id}` arg hard-fails as unknown).
Every worker-addressing tool takes `{sessionId}` — the class is exactly the tools whose `inputSchema` declares it, the same predicate `governableToolNames()` computes the governable set from, and deliberately not re-listed here (see [Playbooks](playbooks.md#playbooks)).
`renew_session` is the one where it is **optional**, and that is the whole distinction (with it: ask that worker to renew itself; without it: renew your own session).
`merge_worktree` and `sync_worktree` are **not** in that list — they address a worktree, not a worker: `{project, worktree, allowDirty?}` and `{project, worktree}`.
`spawn_instance`'s `resume` already takes a sessionId.
Worktree is always `worktree` (never `worktreeName`), and there is **ONE spelling per worktree**: the store key, the `worktreeName` and the directory basename are one string — the slug or the 6-hex id.
Every worktree-addressing input — MCP args and the REST `:wt` path segment alike — takes that string exactly, and anything else is a **404** whose message lists the project's worktrees by exact name (or says it has none) — `unknownWorktreeMessage`/`requireWorktree` in `src/worktrees.ts`; nothing parses a name out of a path and nothing aliases one spelling to another.
An empty `worktree` (or `baseWorktree`) is refused by the schema (`minLength: 1`) on every MCP tool, before any handler runs.
`spawn_instance` takes `createWorktree:true` (fresh worktree off HEAD) and/or `worktree:"<name>"` (attach existing) — the old `worktree: boolean|string` overload is removed.
`create_worktree` and `spawn_instance` both also take `baseWorktree` (base the new worktree on another worktree of the project — see [Feature branches](../features/worktrees.md#worktrees)) and `name` (slugified into the new worktree's branch + dir); on `spawn_instance` both require `createWorktree:true` and are refused **400** otherwise rather than ignored — `name` names the worktree, never the session.
`createWorktree:true` alongside `resume` is likewise refused **400 `RESUME_TAKES_NO_WORKTREE`** (`_doCreateResolved`, `src/instances.ts`), before the worktree is created: a new worktree is a new cwd, and the transcript dir is keyed on that path, so it can hold none of the resumed session's history.
An explicit `worktree:"<name>"` alongside `resume` skips the project/worktree recovery below, so it is checked rather than trusted: a name that is not where `findSessionLocation` places the session is refused **400 `RESUME_WORKTREE_MISMATCH`**, naming where it actually ran.
Comparison is on the resolved record's `worktreeName`; naming the session's own worktree stays legal, and a session that cannot be placed is left to the pre-flight.
`spawn_instance` and `send_prompt` additionally take the playbook-policy arguments in [Playbooks](playbooks.md#playbooks).
`send_prompt` also takes `forward:{sessionId}` (see `send_prompt({forward})` below) — the one **nested** worker handle on this surface, since every other worker reference above is a top-level `sessionId`.

**Prefix resolution (MCP boundary).**
Before strict-live resolution, the MCP dispatch layer (`src/mcp/server.ts`) resolves the incoming `sessionId` arg of any tool that declares one through `InstanceManager.resolveSessionRef` — so a caller may pass an **unambiguous prefix** (e.g. first 8 chars) in place of the full UUID.
It is the single, uniform chokepoint (covers `describe_session` too, and `send_prompt`'s nested `forward.sessionId`) and is **non-destructive**: an exact full-id match always wins (even if it is also a prefix of another id) and passes through unchanged; a prefix that matches exactly one id is rewritten to that full id; no match is left untouched (so the strict-live paths below still produce `SESSION_NOT_LIVE`/`SESSION_UNKNOWN`/on-disk lookups).
A prefix that matches **more than one** id (or a prefix shorter than `SESSION_PREFIX_MIN` (see `src/instances.ts`) that matches any) soft-refuses `{ok:false, code:'SESSION_AMBIGUOUS', sessionId, reason, matches:[<public ids>]}` (`isError:false`) — the ids **whole**, never sliced: a public id is 8 chars only until a mint-time collision extends it (`PUBLIC_ID_LEN_EXTENDED`, `src/sessionLineage.ts`), and two extended ids share their first 8, so truncating would print the same candidate twice.
The resolution **universe** is, for every in-memory instance (live **and** exited in `byId`), its **public id plus every backing id it has run under** — broader than live-only, so a prefix unique among live workers but shared with an exited in-memory session is ambiguous rather than mis-resolved; historical disk-only sessions are out of scope (address them by their full id — and on `describe_session` that means the full **handle**, since a full backing/segment id soft-refuses `SESSION_NOT_A_HANDLE` there; see [Public vs backing id](#mcp-tool-protocol) below).
Resolution at **those three** sites is entirely in-memory, so it stays synchronous.
**`resume`** (spawn_instance) is the fourth site: same chokepoint, same decision, but **async** and over a wider universe — `InstanceManager.resolveResumeRef` overlays the **lineage store** (`src/sessionLineage.ts`) onto `byId` and decides the **union** in one pass, at a cost of one JSON read per `spawn_instance({resume})`.
It has to be wider: the ordinary resume target is not in `byId` at all — a conductor worker is normal, so its exit evicts it, and `src/resumeRestart.ts` skips `group:'worker'` on boot, so after an orchestrator restart a conducted worker is never re-entered.
Deciding the union (rather than consulting the store only on a memory miss) is what makes a prefix unique in memory but shared with a cold session `SESSION_AMBIGUOUS` instead of a confident wrong answer.
It also differs in what it **rewrites**.
It answers TWO ids: the public id (which the policy gate needs — its projection is keyed by it) travels beside the argument as `resumeHandle`, while `args.resume` is rewritten **only for a prefix**.
An exact **segment** id is left verbatim, because `resolveBacking` returns a named segment as itself and `current` only for a public id — so normalising a segment to its handle would silently redirect the resume to the session's newest transcript.
A prefix names no particular segment, so the handle is the only reading available (and `create()` cannot resolve a prefix itself).

**Public vs backing id.** A session has one **public id**, fixed for life: the first 8 hex chars of its first CLI `session_id`, minted through a collision-checked store (`src/sessionLineage.ts`). That is the only id that crosses an API / MCP / WS / UI boundary, and it is what `sessionId` means everywhere on this surface. The CLI's own `session_id` **rotates** on every `/clear` (managed or typed) and on every prune; that rotating value is the **backing id**, confined to process launch (`--session-id`/`--resume`) and transcript resolution (the `${backingId}.jsonl` transcript, the subagent dir). It reaches no caller: it is absent from `Instance.summary()` and from `CONDUCTOR_VIEW_KEYS`, and that absence is the enforcement. A session with **no record** in `<store>/sessions.json`, or only a single-`initial` one — never rotated and never minted — has public id == backing id; that is the store's base case, not a legacy branch.

Three input forms are accepted, all resolving to the same session: (1) the public id; (2) an unambiguous **prefix** of it; (3) **any full backing/segment id, permanently** — not transitionally. Form 3 is a **guarantee**, so the full UUIDs already written into wiki pages, resume manifests and old kanban cards keep resolving; do not "clean it up". Naming a segment directly opens **that** segment rather than redirecting to the newest, so an archived transcript stays individually addressable.

**One scoped exception: `describe_session`.** Form 3 stands **as a resolution guarantee** — it is not repealed, and it still holds for internal callers and for every other `sessionId` argument on the surface. `describe_session` is a conductor-facing *inspector* whose contract is deliberately narrower: it takes the **handle only**, and a backing/segment id soft-refuses `{ok:false, code:'SESSION_NOT_A_HANDLE', handle, reason}` naming the handle that owns it (the refusal echoes that handle, never the id passed in, so the tool emits no backing id at all). The principle is about what the **conductor sees and uses**: it must never hold a `~/.claude` UUID. Read a scoped narrowing here, not an inconsistency to tidy away. The check is **`publicIdFor(input) !== input`** (`src/sessionLineage.ts`) and must **never** be a length or shape test: a session with no lineage row has public id == backing id (the base case above), so a full 36-char UUID may be the only handle it has — `publicIdFor` accepts it, and refuses only an id the store knows to be *someone else's* segment. The refusal cannot fire for a session still in `byId`, because [prefix resolution](#mcp-tool-protocol) at the dispatch chokepoint rewrites an exact segment match to that session's public id before the handler runs; it fires for segment ids whose session is no longer in memory.

| Input | Verdict |
|---|---|
| Exact match on a public id, or on any segment id | **Resolves** (exact always wins, even when it is also a prefix of something else) |
| Prefix shared by two segments of the **same** session | **Resolves** — the answer set is of sessions, not of candidate strings |
| Prefix spanning a session's public id and one of its own segments | **Resolves** |
| A session's public id that is also a prefix of a **different** session's segment | **Resolves to the exact match** (public ids are claimed before segments) |
| Prefix shared by two **different** sessions (by public id or by segment) | **`SESSION_AMBIGUOUS`** — the input genuinely names two sessions |
| No match | `null` — the strict-live / disk-probe paths below still run |

`matches` on a `SESSION_AMBIGUOUS` refusal carries **public ids only**.

**Worker resolution (strict-live for addressing, disk-backed for reads).** `sessionId` (post prefix-resolution) resolves to its single *running* (proc-attached) instance. If the session is known but has no running process → `{ok:false, code:'SESSION_NOT_LIVE', sessionId, reason}` (resume via `spawn_instance({resume:sessionId})` — except a session whose worktree no longer lists (the listing `requireWorktree` reads), whose `reason` says it cannot be resumed and that its output is still readable through `get_recent_messages` / `get_transcript`); if no such session anywhere → `{ok:false, code:'SESSION_UNKNOWN', sessionId, reason}`. Both are normal results (`isError:false`), matching the soft-refusal convention. The resolver **never auto-respawns** — a dead session is a refusal, not a resurrection.

**A worker whose CLI exited on its own.** Any exit that no kill was commanded for — non-zero, signalled, a clean code 0, or a spawn that never started (`code` `-2`, reason on the `spawn_error` event); at startup before any prompt, or mid-turn — records an exit cause against the session's public id (`InstanceManager.exitCauseFor`, `src/instances.ts`). Every `SESSION_NOT_LIVE` about that session then carries it:

| Field | Value |
|---|---|
| `exit.code` | the CLI's exit code, `null` when signalled |
| `exit.signal` | the signal name, `null` when it exited with a code |
| `exit.stderrTail` | the end of **that launch's** stderr up to its EOF (waited for at most `EXIT_STDERR_SETTLE_MS`), bounded by `EXIT_STDERR_TAIL_LINES` / `EXIT_STDERR_TAIL_CHARS` (`src/instances.ts`); `null` when it wrote none |

The `system/launch_failed` event's `stderr` does **not** wait for EOF: `Instance._handleExit` cuts it at the exit event, so for a wrapper that prints after exiting it can be `null` while `exit.stderrTail` carries the line.

- The cause makes the session **known**: a normal worker leaves `byId` on exit and one that died before its first prompt has no transcript, yet it answers `SESSION_NOT_LIVE` with `exit`, never `SESSION_UNKNOWN`. This holds on the addressing tools, on the read tools (`getInstOrDisk`, after the transcript and orphan probes miss) and on `describe_session`.
- `reason` leads with the code/signal and the last stderr line, then advises: a transcript exists and its worktree still lists → `spawn_instance({resume})`; otherwise → spawn a fresh worker (with no transcript a resume would refuse `SESSION_UNKNOWN`; for a worktree that no longer lists see [Worker resolution](#mcp-tool-protocol)).
- `describe_session` on a retired session with a cause adds one `exited code <c> signal <s> — <last stderr line>` line under its location.
- Cleared by the session's next commanded exit and by a successful `create({resume})`. In memory only, capped (`EXIT_CAUSE_CAP`), and lost on a server restart.
- Not a cause: a commanded kill (`kill_instance`, ⏹, project delete, shutdown, rewind), or an exit under the resume-restart drain.
- `spawn_instance`'s own result is unchanged: it returns once the CLI is forked, and the CLI writes nothing before its first prompt, so a startup crash surfaces on the next call.

Every tool that **addresses** a worker (drives it, changes it, reaps it) resolves this way. The exception is the three call sites that need a session's **bytes** rather than its subprocess — `get_transcript`, `get_recent_messages`, and `send_prompt`'s `forward` **source**, which performs the same read — and they resolve through the sibling `getInstOrDisk`: live instance → **on-disk transcript** → refusal. So a retired worker stays readable and forwardable without being resurrected; see [Disk-backed reads](mcp-results.md#disk-backed-reads-ring-first-fallback-on-demand) for the mechanics and the two refusals that survive it. `kill_instance` is live-only (it cannot reap an already-exited persistent instance by sessionId — accepted under strict-live). `forward.sessionId` resolves **independently** of the target `sessionId`, with its own `FORWARD_SESSION_NOT_LIVE`/`FORWARD_SESSION_UNKNOWN` codes (see `send_prompt({forward})` below) — so a two-session call always says which side to fix.

**Resume pre-flight (`spawn_instance({resume})`).**
Before constructing an Instance or spawning `claude --resume`, `InstanceManager._doCreate` verifies the resume id has a **resumable conversation** at the resolved cwd (`hasResumableConversation` in `src/transcript.ts`: the `${sessionId}.jsonl` exists **and** holds ≥1 `user`/`assistant` record — mirroring the CLI's own "No conversation found" criterion, so a marker-only crash stub of `last-prompt`/`permission-mode` lines does **not** qualify).
If it doesn't, `spawn_instance` soft-refuses `{ok:false, code:'SESSION_UNKNOWN', sessionId, reason}` (`isError:false`) instead of spawning a subprocess that would exit 1 and crash-loop.
The `reason` names **the cwd it probed** (carried off the thrown error as a `cwd` property) — a refusal that omitted it read as a bad id when the real fault was the wrong place — while `sessionId` echoes **the caller's own input, untouched** — a prefix the transport already resolved to the handle, or an exact id verbatim, which for a named segment is a segment id rather than the handle.
That is an echo, not a leak (the caller already held it); what the refusal never surfaces is the backing id `create()` has internally rebound `resume` to by that point, which for a handle or a prefix would be an id the caller never had.
On a project on a **system** the resolved cwd is the project's own path there, so there is one candidate and no scan — and the probe resolves that cwd against **that remote's own transcript root** (`transcriptRoot`, `src/projects.ts`), so two boxes at one absolute path are probed separately rather than answering for each other.
This guards the case a caller pins `project`+`worktree` (which bypasses the `findSessionLocation` "project required" net — whose 400 on a resume names `list_sessions` as the place to find the session's project and worktree; a net that catches a session on a **system** too: its transcript is located from the project's path on that machine, which is where the CLI ran, so the bare `{resume}` form recovers project and worktree there as well) with a mistyped/bogus resume id.
Because the refusal fires before any Instance is registered in `byId`, the refusal is **idempotent**: repeating the same `spawn_instance({resume})` returns `SESSION_UNKNOWN` again, with no phantom crashed instance for the retry to resolve through.

**Resume liveness guard + reclaim (`spawn_instance({resume})`, and every other resume).**
The pre-flight above sits beside a liveness guard: `_doCreate` refuses **409** when `InstanceManager.isSessionLive(publicId)` — the same authority governance reads, **not** `liveForSession`.
Two consequences on this surface.
(1) A resume issued **during a relaunch window** — a prune's kill→relaunch (`rotationPending`), a rewind's, a respawn's or a restart model switch's for its whole run (`_relaunching`) — now 409s instead of starting a second `claude --resume` on one transcript; a `proc`-only guard read those as gone.
(2) A resume over a **settled** in-memory instance for that session **retires** it (`InstanceManager.remove`) rather than registering a second one, so at most one `byId` entry ever answers to a public sessionId — but only on the way to **success**: the retire is the last statement before registration, so a resume refused by any check above it (`SESSION_UNKNOWN` pre-flight, `BACKEND_GONE`, an invalid `mode`/`thinking`/`effort`, a worktree or mirror-geometry refusal) leaves the session's existing instance exactly as it found it.
The refusals that fire from `launch()` are **below** it and so do not get that protection — `MIRROR_ADVERTISEMENT_CHANGED`, `FUSE_REMOTE_UNREACHABLE`, `FUSE_MIRROR_ROOT_ABSENT` (see the REST table above): those land after the retire and after the replacement registers.
Known and deliberately unfixed; rationale in [architecture.md → Instance lifecycle](../architecture.md#instance-lifecycle).
(3) While a resume is in flight for a session, `POST /api/instances/:id/respawn` on one of that session's instances refuses **409** — the two would otherwise race over the same Instance.
`isSessionLive` is a `.some()` over **every** instance answering to the session, not `anyForSession`'s first match — an exited instance ordered ahead of a live one used to shadow it, which is what made `playbook_state`'s `live:` field untrustworthy.
Mechanics and invariants: [architecture.md → Instance lifecycle](../architecture.md#instance-lifecycle).

**Tool-result nudges** (`src/toolResultNudges.ts`). A short reminder a handler hands the **calling** session alongside one result, delivered as that call's PostToolUse `additionalContext` (hook entry 3 under **Subprocess protocol**) — never as a result field:

| Constant | Tool | Queued when |
|---|---|---|
| `SELF_TITLE_NUDGE` | `spawn_instance` | the spawn (fresh or `resume`) succeeded and the caller is live, untitled and not in `plan` mode |
| `LANDING_RENEW_NUDGE` | `delete_worktree` | the **Landing renewal nudge** setting is on, the caller is a conductor (`isConductorInstance`), the work landed (checked before removal), and the removal succeeded |

- **Correlation.** On a JSON-RPC `tools/call` the server reads `params._meta["claudecode/toolUseId"]` (`TOOL_USE_ID_META_KEY`, `toolUseIdOf` — a non-empty string, else none) into the handler ctx as `toolUseId`. The CLI sends the same value as the PostToolUse envelope's `tool_use_id`, so parallel calls and subagent calls each get exactly their own call's nudge (pinned against the real CLI by `tests/tool-result-nudge-cli.real.test.mjs`).
- **Store.** The handler queues the text on the caller's live Instance (`queueToolNudge` → `PendingToolNudges`, keyed by toolUseId; the same text under one id is kept once) before it returns; the CLI posts PostToolUse only after it has the result. The hook's `take` is one-shot. Every pending entry is cleared at each exit from `turn` (`Instance._setStatus`).
- **Refusals queue nothing.** The result shape is the same with or without a nudge.
- **The user does not see it.** The text reaches the model inside the tool result; the UI renders no line for it, and cc's transcript replay ignores the CLI's `hook_additional_context` attachment for PostToolUse.
- **Callers that get no tool-result nudge:**
  - a call inside `run_code` — the program's calls arrive over the REST alias, which reads no `_meta` (ctx `toolUseId: null`);
  - any other REST-alias call;
  - a non-CLI client calling `/mcp/<sid>` for a live session without the `_meta` key;
  - a session with no hook URL (`serverPort` unset — tests only);
  - a backend template that runs `claude` where `127.0.0.1` is unreachable — every cc hook already fails there.

**Emitted handles.**
Returns never carry an `instanceId`: `toConductorView()` projects every summary through an **explicit allowlist** (`CONDUCTOR_VIEW_KEYS`, `src/mcp/handlers.ts`) before it reaches any conductor-facing return — every `toConductorView()` call site in `src/mcp/handlers.ts`, including `list_sessions`, which then renders it as text — and inline returns emit `sessionId` instead of `id`.
What it withholds is the **complement**: every key `summary()` emits (`src/instances.ts`) that the list does not name — pinned as a set by `tests/mcp-conductor-view.test.mjs`, so a field added to `summary()` reaches no conductor until someone names it in `CONDUCTOR_VIEW_KEYS`.
Today that is the per-process handles `id` + `callerInstanceId`, `debugDir` (the `debug` boolean is the signal), the UI-only `autoApprovePlan`, `playbookEnforcement` (the gate reads the CALLING conductor's level and never its target's, so a worker's copy is the inert default), `interrupting` / `overageStoppedUnarmed`, each of which the caller either already knows or is told where it would act (the `OVERAGE_STOPPED_UNARMED` refusal), and the turn marks `turnEndSeq` / `viewedSeq` (the human's unread state — UI-only, like `POST /api/sessions/:sid/viewed`), and the notification counters `liveTurnEnds` / `lastTurnError` / `liveAsks` (UI-only), and the restart model switch's `modelSwitch` / `modelSwitchFailure` (UI-only — a switch is started from the UI, and `send_prompt` names one in flight as `SESSION_SWITCHING_MODEL`), and `pristine` (the browser's presence state for New conductor — UI-only; no MCP payload carries a hidden pristine conductor, see `summary().pristine`), and `displayLabel` (the sidebar's label, for plugins — `list_sessions` / `describe_session` render their own from `title` and `firstPrompt`).
While one is in flight the projected `model` and `backend` are its `from` and `fromBackend` — the pair the session is still confirmed on — although `summary()` may already name the target.
`backingSessionId` is withheld one level earlier — `summary()` never emits it at all — and that absence is what keeps a rotating id off this surface.
It publishes `lastRotatedAt` / `rotationReason` / `segmentCount`: pinning the public id makes a rotation invisible, which removes the only tell a conductor had that one happened, so a renewed or pruned worker would otherwise be indistinguishable from one that had gone quiet.
Deliberately rotation-generic rather than `lastRenewedAt` — prune rotates too.
It publishes `rootSessionId` / `parentSessionId` / `awaitingUser` / `awaitingUserSource` — what a conductor-first view groups and sorts by.
`rootSessionId` is the public sessionId of the root of a **live** conducted worker's spawn chain.
`parentSessionId` is that of its immediate spawner or resumer, and it keeps naming that session after it exits.
Both are `null` on a hand-spawned session, on a conducted one spawned anonymously, and on any dead instance.
`awaitingUser` (`'question'` \| `'plan'` \| `null`) is the sticky ask with no real user message since, and `awaitingUserSource` (`'tool'` \| `'text'` \| `null`, null iff `awaitingUser` is) says whether an `AskUserQuestion`/`ExitPlanMode` or a turn-end text ask set it.
Always null on a conducted worker.
Semantics, classifier and limits: [architecture.md](../architecture.md) → "Ownership and awaitingUser".
`list_sessions` alone adds the keys in `LIST_ONLY_KEYS` (`src/mcp/handlers.ts`), attached on top of the projection by `listSessions`'s own `view()` closure rather than supplied by `summary()`: `awaitingWake` comes from `InstanceManager.list()` (`src/instances.ts`) — **caller-side**: true while an ARMED WAKE on a session this instance owns is pending, so it is what distinguishes "idle because I am waiting" from "idle because I am done".
Armed-wake-pending, **not** "a session it owns is mid-turn": the two diverge in the states the wake is deliberately held through — a deferred `turn_end` (a live subagent or an unconsumed task notification, with the target already back to `idle`) and a dropped idle-drain settle.
It also stays true across a heartbeat, which reports without consuming, and from a wake's consume until the CLI has taken the wake in — including a wake written into this instance's own running turn that the CLI queues past that turn's end.
`playbook`/`stage` come from the read-only playbook projection.
The `list_sessions` outputSchema (`src/mcp/outputSchemas.ts`) is built from the allowlist by `keyed`, which throws on drift; the same test pins it, so an allowlisted key without a schema fails too.
The per-worker MCP URL names the caller in its path, `/mcp/<sessionId>?format=text`: the session's own **public sessionId** (baked into `--mcp-config` at spawn, `Instance.spawn`).
The public id is pinned for the session's life — a `/clear`, a renewal or a prune moves only the backing id, and a restart-resume pins the same public id again — so the baked URL never goes stale.
The `/mcp` boundary (`src/mcp/server.ts`) resolves it per request via `InstanceManager.liveCallerForPublicId(id)`, which accepts only the EXACT public id of a session with a live process, so every downstream handler receives a live sessionId as `callerId`.
Anything else — an unknown id, a prefix, a backing/segment id, an instanceId, a killed session — is refused `CALLER_UNKNOWN` before dispatch, never served anonymously; an anonymous `/mcp` yields `callerId=null`, and a caller-dependent tool then refuses with `caller identity missing` ([mcp-applications.md → URL contract](../mcp-applications.md#url-contract)).
The instanceId never leaves the server as an identity: the two sites that surface the caller (the `renew_session` return, the plugin `caller.sessionId` envelope) emit the resolved sessionId.
For `spawn_instance` the resolved caller instance is stored as `callerInstanceId` (internal/REST only).
Internally the idle-wake graph (`_idleSubscribers`, plus the ownership edges behind it) and overage timers (`_autoResumeTimers`) are keyed by the **stable instanceId**; sessionId is translated to instanceId at the dispatch boundary (`noteDispatch`/`setIdleTimeout`) and back for delivery — so an in-place `/clear` rotation needs no re-keying.

**Session renewal (`renew_session`).**
TWO FORMS, one tool; a call that mixes their arguments is refused `INVALID_RENEW_FORM`.
**Bare** (`{summary}`): renew the CALLER, named by the `/mcp/<sessionId>` path (an anonymous call throws; an unknown caller is refused `CALLER_UNKNOWN` before dispatch).
A session can renew **repeatedly** — its public id is pinned, so the same URL names it before and after every rotation.
It arms a managed `/clear` on the caller (see [Subprocess protocol → Managed `/clear`](subprocess.md#subprocess-protocol)); `SessionRenewController`, the idle-wake graph and the overage timers are keyed by the caller's `instanceId`, which a rotation keeps — so the rotation strands nothing and needs no migration.
**Targeted** (`{sessionId, directive?, followUp?}`): *request* that worker renew itself.
The server prompts it (a normal, non-`internal` prompt carrying `directive` — what to be sure to capture — plus the summary template), records the caller's ownership before prompting — unconditionally, since a request whose outcome the conductor never hears is useless — and returns immediately with bare data (`{requested:true, sessionId, note}`, no `ok`).
**The target must be FREE:** a request needs a turn of its own, so a target that is mid-turn — or idle but owing a re-invocation turn, or with live subagents, or with its sends parked in the overage queue (`renewalDeferredBy`, the same predicate `SessionRenewController` defers the `/clear` on) — soft-refuses `SESSION_BUSY`, carrying `status` plus `busy` naming which of those it is.
Registering against a turn the worker did not open for it would expire the request as a decline the worker never saw and spend the conductor's armed wake on unrelated work; an overage-parked prompt would open no turn at all, so the conductor would be told a healthy worker "did NOT finish" on every heartbeat instead.
**The worker's own bare self-call is the only channel a summary is ever authored on, and the conductor cannot force it:** the request is held for exactly ONE turn — the worker's own `renew_session({summary})` consumes it (folding `followUp` into the reseed under its own fence, distinct from the summary section), and the worker's `turn_end` expires it.
That expiry **is** the decline, recorded server-side at the moment it happens and reported on the wake of the conductor that ASKED — the note is keyed to that requester, so a second conductor watching the same worker is never told about a request it did not make, and the note dies with the wait it was recorded for (delivered once, or dropped on a silent disarm/purge/a dead caller) rather than surfacing on a later, unrelated wake.
A request deliberately opens **no** rotation window, so a decline rides the worker's ordinary, undeferred `turn_end`.
`renew_session` declares a `sessionId`, so it is **governable** like any other targeted tool and a stage may deny it (see [Playbooks](playbooks.md#playbooks)); the bare form names no worker, so it is never subject to a stage's `tools`, and neither is the worker's own self-call (`tools` applies to conductor callers only; the worker's own call is subject to its stage's `workerTools`).
**Interlock:** soft-refuses `{ok:false, code:'SESSION_ROTATING'}` when a prune is already rotating the subject (or a rewind/prune holds `_mutating` — `rewriteBlocksPrompts`; a fork does not refuse), because a prune makes `prompt()` 409 and the renewal's reseed **is** a `prompt()` — interleaving them would clear the context and then lose the summary.
On the targeted form the same check reads the TARGET and also refuses while it has a renewal already pending (`renewalPending`), so a request can never clobber one.
Re-arming a renewal over its own pending one stays idempotent.
The reseeded prompt also carries a server-generated mechanical state block — see [features/mcp.md → Session renewal](../features/mcp.md#mcp-interface) and [components/instances.md](../components/instances.md#srcsessionrenewts).

**Idle wake-stub text (`IdleSubscriptionHub.deliver`).** The variants below, each injected as an `internal:true` `user_echo` into the caller. **Every variant carries the `[[cc:wake-callback]]` marker** (defined in `shared/wakeCallback.ts`, imported by both `src/idleSubscriptions.ts` and `web/src/conversation/model.ts`), so every one renders as the wake-callback UI bubble with a bell icon (`data-variant="wake"`, `web/src/conversation/items.tsx`); only **Folded** additionally carries the `[[cc:wake-body]]` separator + payload. The markers survive persist/replay in the CLI jsonl and are stripped from display, not from the prompt the model reads. A declined `renew_session` request prefixes a one-sentence note into the **summary** of whichever variant is delivered (`buildWakeStub`'s `note`, `_plainStub`'s `note` — wording in `declineNote`, `src/idleSubscriptions.ts`), so it lands in the always-visible line; it is not a variant of its own. The presence of `[[cc:wake-body]]` is the "is it folded" signal — the client renders a collapsible fold (`data-fold="wake"`) when a body is present, else a body-less summary line (`data-wake-plain`, no caret). Every variant except **Timeout** appends a **jobs block** to its summary when the target still has background Bash jobs at build time (`backgroundJobsNote`, `src/backgroundJobs.ts`): `\nBackground jobs still running:` + one `- "<title>" — running <duration>` line per job + `Worker \`<sid>\` is re-invoked when each job exits, and you will be woken again after that turn.` The wake itself is not held for a job.
- **Folded** (real `turn_end` delivered to an already-idle caller): `[[cc:wake-callback]]<summary>[[cc:wake-body]]<payload>` (via `buildWakeStub`). The summary names the worker + says it finished; `<payload>` is `flattenPayload(meta, bodies)` — the compact-JSON metadata block + each raw body block joined by blank lines, i.e. **byte-identical to the content a default `get_recent_messages({sessionId})` call returns** (via the shared `buildRecentMessages` builder in `handlers.ts`, so the fold never drifts from the tool), narration segment included. `send_prompt({forward})` (below) renders a **third**, separate view over the same underlying selection (`selectRecentMessages`) — deliberately **not** byte-identical to this fold, since it is worker-facing rather than conductor-facing: no `sessionId`/`msgId`/char-count telemetry, bare `--- message i/n ---` boundaries, and the guiding text placed last inside a fixed frame.
- **Plain** (`turn_end` but caller was **mid-turn** at delivery, so the send is deferred to when it goes idle): `[[cc:wake-callback]]` + the unchanged `Worker \`<sid>\` finished its turn. Call get_recent_messages(...) to inspect the result.` pointer (via `markPlainStub`, body-less) — decided synchronously at delivery time, so the deferral keeps the plain stub even though the caller is idle by the time it actually fires.
- **Timeout** (heartbeat): `[[cc:wake-callback]]` + the unchanged `... did NOT finish — timed out after <duration> ...` pointer, where `<duration>` is `humanizeDuration(window)` (`src/duration.ts` — compact `30m` / `1m30s` / `<1s`, never ms) (via `markPlainStub`, body-less). Repeats every window while the target is mid-turn or holding the wake (below) and consumes nothing — one interval across every turn of a hold, restarted by a dispatch to the target — so a **Folded**, **Plain** or **Interrupted** variant still follows at the real `turn_end`.
- **Interrupted** (the `turn_end` a FORCE-abort produced — `Instance.turnForceAborted`, set at the one chokepoint both doors go through, so the MCP `interrupt_turn({force:true})` and the UI's stop button behave identically; **every** consuming path reports it — `turn_end`, the idle task-drain settle, and rotation completion alike, since which one resolves an abort's wake is an accident of what the worker was doing. A consuming path only READS the flag (`_abortQualifier`); it neither consumes nor clears it, so `turnForceAborted` legitimately stays true after a wake is delivered, until the next turn start. Adding a consuming path means adding the read and nothing else — clearing has its own home, [components/instances.md](../components/instances.md#srcidlesubscriptionsts)): `[[cc:wake-callback]]` + a `... was INTERRUPTED — ... did NOT finish and whatever it produced is PARTIAL ...` pointer (via `markPlainStub`, body-less). **Deliberately never folded**, even to an idle recipient: the presence of `[[cc:wake-body]]` is the client's "this is the finished result" signal, so folding partial aborted output in would invite the conductor to act on exactly what the abort was meant to stop it acting on. Delivered to every owner EXCEPT the one that called for the abort, whose own entry was silently disarmed first (`disarmSilently`, caller-scoped) — a target can have several owners, and telling the others a killed turn "finished" is the misreport this variant exists to prevent, while silencing them would strand a wait nothing else can end. The UI door has no interrupter, so there every owner takes this path.
- **Exited** (the target's CLI exited **on its own** mid-turn — `IdleSubscriptionHub.onTargetExit`, called from the manager's `exit_cause` listener when the exit carries a cause and the instance is not `relaunching`; see [Worker resolution](#mcp-tool-protocol) for what counts): `[[cc:wake-callback]]` + `Worker \`<sid>\` EXITED on its own mid-turn (exit code <n> | signal <sig>; a clean `exit code 0` included) — it is no longer running. \`mcp__code-conductor__describe_session({sessionId:"<sid>"})\` shows the cause.` (via `markPlainStub`, body-less, never folded). Delivered **at once** to every armed owner, consuming each entry and clearing its heartbeat — before a normal target's purge, which would otherwise clear them silently. **Never contains `did NOT finish`**: that phrase is the heartbeat's "still running". A held wake (below) names the sessionId carried on the wake, not the target's `byId` entry, which a normal target no longer has by delivery time. A **commanded** kill is not this path: a normal target's entries go with its purge, a persistent target's with the heartbeat's gone-for-good retirement.
All of them keep `internal:true` semantics (bypass the overage queue intercept, never cancel a pending auto-resume) — including **Interrupted**, which is the abort path, i.e. exactly where not cancelling a pending auto-resume matters.

**The human notice.** When the human prompted the target directly since its owners' last wake (a `user_echo` with `author:"human"`, so a conducted worker only), every turn-ending variant — **Folded**, **Plain**, **Interrupted**, **Exited**, and a held wake's stale form — opens its summary with a notice, before any decline or stale note (`buildWakeStub`'s and `_plainStub`'s `humanNote`; text from `humanPromptsNote`, `src/promptAuthor.ts`): `The user prompted this worker directly since your last wake — not your brief. Treat their words as the user's instruction to it; don't re-steer over them without checking with the user. Their message(s), oldest first:`, then the prompts with every line prefixed `> ` and prompts separated by a bare `>` line — so quoted text cannot forge `[[cc:wake-body]]`. At most `HUMAN_PROMPT_QUOTE_MAX_COUNT` (the most recent) are quoted, each cut at `HUMAN_PROMPT_QUOTE_MAX_CHARS` code points with `… [+N chars — get_transcript has it in full]`; older ones are counted on a leading `(K earlier user message(s) not shown — get_transcript has them)` line. **Timeout** never carries it. A wake about a turn with no human prompt is byte-identical to the variants above. The list is kept in `IdleSubscriptionHub._humanPrompts` (lifetime in [components/instances.md](../components/instances.md#srcidlesubscriptionsts) → `src/idleSubscriptions.ts`), so a wake held or deferred across several turns reports every human prompt since the last delivered one.

**When no stub is sent: the hold.** A target that reaches idle (`turn_end`, idle task-drain settle, prune) while still waiting on work of its own sends its owners nothing; their entries and heartbeats stay armed (`IdleSubscriptionHub._holds` — rule and pass-throughs in [features/mcp.md](../features/mcp.md) → *Wake on turn end*, mechanism in [components/instances.md](../components/instances.md#srcidlesubscriptionsts) → `src/idleSubscriptions.ts`). The stub eventually sent is the one the deciding path would have sent: **Folded**/**Plain** at a qualifying turn end or release, **Interrupted** for a force-aborted turn, **Exited** for an exit. A release (`_releaseHeld`) sends the **Folded** stub to an idle owner. Nothing at all is sent once the resume-restart drain has called `suspendWakes()`.

**Held wakes and stopped turns (models that can't take a mid-turn injection).** Two extra rules, both keyed on `Instance.acceptsMidTurnSteering` / `steerPending` (see [models.md](../models.md#mid-turn-steering-capability)):
- **Recipient side.** A wake for a conductor that is mid-turn on such a model is **held** in `IdleSubscriptionHub._deferredWakes` (keyed by caller instanceId) and delivered at that conductor's own next `turn_end` — never a block-edge stop: an idle report is not urgent, and aborting a conductor would sever its in-flight orchestration. Held-then-delivered means the recipient is idle at delivery, so it gets the **Folded** variant — unless the turn it reports was force-aborted, in which case **Interrupted**, which is never folded regardless of recipient state. It re-defers once more while a steer is parked on the recipient (`steerPending`), and flushes on the `system`/`steer_settled` event when a steer drains with no turn to end (failed or overage-queued delivery) — the strand a `turn_end`-only trigger would leave. A held wake whose **worker went busy again** is delivered with the plain stub plus a leading "no longer idle" note (`STALE_WAKE_NOTE`, `src/idleSubscriptions.ts` — after any decline note, before the summary) rather than dropped or folded.
- **Target side.** `steerPending` joins `activeAgentTaskCount` / `taskNotificationPending` / `rotationPending` in `_onTurnEnd`'s defer gate: the `turn_end` an armed block-edge stop produces means the worker was **cut off** to deliver a steer, not that it finished, so the wake stays armed for the steered turn's real `turn_end`.

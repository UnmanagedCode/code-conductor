# Protocol: MCP tools — results and refusals

## MCP tool results and refusals

<a name="mcp-input-validation"></a>
**Input validation (`validateArgs`).** Beyond type/enum/required, the server enforces the declared `pattern`, `minLength`/`maxLength`, `minimum`/`maximum`, and array `items.type`. **Unknown properties are rejected** (not silently dropped): `unexpected argument '<k>' — not a recognized parameter for <tool>. Allowed: <keys>`. Validation failures return `isError:true` with the message as a single text block. A core tool's `project` argument always addresses an existing project, so a malformed non-empty one (most often a path) is refused before the handler with `invalid project name "<arg>" — pass the project's NAME as list_projects prints it (^[a-zA-Z0-9._-]+$), not its path` (`validateProjectRef`, `src/projects.ts`), as a thrown-error envelope (`BAD_REQUEST`, 400); REST project creation keeps `validateName`'s neutral regex refusal. Schemas also declare `default`s mirroring handler defaults (documentation; handlers still apply them).

<a name="mcp-result-format"></a>
<a name="mcp-result-budget"></a>
**Result budget (text format).**
Every tool result's summed `content[].text` is bounded by `MCP_RESULT_CHAR_BUDGET` (`src/mcp/content.ts`): the Claude Code harness caps an MCP result at `MAX_MCP_OUTPUT_TOKENS` (default 25,000 tokens), accepts one whose chars/4 estimate is at most half that without counting, and rejects a larger over-limit one outright — so the budget is the largest result every harness default accepts.
`MCP_BODY_BUDGET` is the byte budget for a raw body beside a small metadata block (`BASH_OUTPUT_CAP`, `project_read`'s `maxBytes`).
The paged tools (`project_read`, `project_diff`, `get_transcript`, `get_recent_messages`, the bash tools) fit themselves and flag every cut.
**The response boundary.**
Every `tools/call` response passes one bound, `boundToolCall` (`src/mcp/server.ts`), whichever branch built it, keyed by how the call ended: (1) a **handler result** over budget is withheld, never cut — a core tool's becomes `boundResult`'s logged soft refusal `{ok:false, code:"RESULT_OVER_BUDGET", tool, chars, budget, completed, reason}`, where `completed` is true unless the tool is annotated `readOnlyHint` (the call already took effect; do not re-run it blindly), and a read tool that trips it is a cc defect — narrow the call; a plugin bridge tool's own result is outside cc's budget and passes as it is.
(2) A **refusal** (unknown tool, `validateArgs`, `SESSION_AMBIGUOUS`, a playbook-gate refusal) or a **thrown error** carries its meaning in its code, and what overflows is an echoed caller string: every string in it — each string value of a JSON block, keys and short fields like `ok`/`code`/`statusCode` untouched, or a plain block whole — is cut by `capEcho` to its head and a tail of at most 64 chars (a quarter of the cap, below 256) around an in-band `… [cut: N chars] …` marker (so an error's `(HTTP 404)` suffix survives), the cap halving from `MCP_RESULT_CHAR_BUDGET / 8` until the content fits, and the cut is logged; should even the smallest cap not fit, it becomes `RESULT_OVER_BUDGET`.
Every JSON-RPC error message (`method not found: <method>`, an internal error) is capped the same way in `rpcError`, its JSON-RPC `code` intact.
The boundary runs after the playbook gate's commit, so the event log is unaffected.

**Result format (text format).** `content[0]` is a **compact** JSON block (no pretty-print) for every tool except the seven that render plain text instead (see [Rendered read results](#rendered-read-results)). Pure-metadata tools emit just that one block. **Text-payload tools** append separate raw, **un-escaped** text blocks in `content[1..]`:

- `project_read` — **content[0] metadata:** `{path, size, truncated, encoding, lineCount, lineCountExact, lineTruncated?, startLine?, endLine?}` — `maxBytes` defaults to and is bounded by `MCP_BODY_BUDGET` (larger is refused by the schema, never clamped); a binary body is cut to ¾ of it so the base64 fits; a line-param read the cap cuts ends on a whole line, reports `startLine`/`endLine` (even with `lineNumbers` alone), and `endLine` is the last line served, so `offset: endLine + 1` continues with nothing lost — only a single line longer than the cap is cut mid-line, with an in-band `… [line cut: N bytes]` marker (N = the line's bytes; only when the marker fits within `maxBytes`, which the body never exceeds), `lineTruncated:true` and `startLine`/`endLine` — also on a read with no line params, whose byte cut is otherwise a plain prefix (`lineCountExact:false`); no offset reaches the rest of that line, so the description routes it to `project_bash` — **content[1..] bodies:** one block: utf8 file text, or base64 (binary)
- `project_diff` (diff mode) — **content[0] metadata:** `{project, worktree, baseRef, head:<sha>, contextLines, offset, truncated, nextOffset, totalLines, totalBytes, hasUncommittedChanges, untracked, untrackedTruncated?, untrackedTotal?, ahead, lineTruncated?, includedFiles?, includedFilesTruncated?, includedFilesTotal?, omittedFiles?, omittedFilesTruncated?, omittedFilesTotal?}` — a page is as many whole lines as fit what one result has left after the metadata at its widest; a single line longer than that is cut with an in-band `… [line cut: N bytes]` marker and `lineTruncated:true`. `untracked`, `includedFiles` and `omittedFiles` are each capped (`capPathList`, `src/mcp/diffPaging.ts`) and flagged `<list>Truncated` + `<list>Total` — **content[1..] bodies:** one block: raw unified diff, always including a `@@@ uncommitted working tree changes (git diff HEAD) @@@`-separated section when uncommitted changes exist (empty string when no diff and no uncommitted changes)
- `project_diff` (summary mode) — **content[0] metadata:** single JSON block `{project, worktree, baseRef, head:<sha>, summary:true, ahead, totals, offset, truncated, nextOffset, files[], uncommitted:{totals, files, untracked, filesTruncated?, filesTotal?, untrackedTruncated?, untrackedTotal?}}`. `totals` always cover the whole change set; `files` is paged by `offset` (a 0-based index into `files` in this mode) with the same `truncated`/`nextOffset` pair as diff mode; every page carries `uncommitted`, whose two lists are capped and flagged like diff mode's. When the uncommitted diff could not be READ, `uncommitted` is `{unknown:true, reason}` instead — absent counts, never zeroed ones, since a zero here reads as "nothing will land if you merge right now". The committed half throws on the same failure. — **content[1..] bodies:** —
- `get_recent_messages` — **content[0] metadata:** `{sessionId, messages:[{index, msgId, hasToolUse, textChars, textTruncated, promptedBy?, narrationChars?, narrationTruncated?, hasPlan?, planTruncated?, planPath?, questionCount?, questionsTruncated?, blocks?, blocksOmitted?}], source:"ring"|"disk", omittedToolOnly, omittedForBudget?, retained:{firstSeq,lastSeq,trimmed}, hint?}` — `promptedBy:"human"` is present only when the latest outer prompt before the message (a `user_echo` that is not `cliInjected`/`skillLoad`/`compactSummary`) carries `author:"human"`; any other prompt resets it, and no other value is emitted, so absent means conductor-sent or unknown (`humanPromptedIds`, `src/mcp/messageReconstruction.ts`; ring and disk alike). `narrationChars` / `narrationTruncated` are present only on a message carrying narration (see `thinking_delta` above); over the result budget, text, narration (`narrationTruncated`), plan (`planTruncated`), the rendered questions (`questionsTruncated`), tool inputs and thinking are re-capped shorter (halving from `MSG_TEXT_CAP / 2` to `TOOL_ARG_VALUE_CAP`), then the oldest messages are dropped, a plan/questions message last (`omittedForBudget` + `hint`), then the one remaining message's trailing blocks (`blocksOmitted`); `textChars` keeps the full size.
  MCP only: `send_prompt({forward})` and the idle-wake fold keep the plain selection and caps — **content[1..] bodies:** one body block **per message**, block k+1 ↔ messages[k]: prose plus a `--- narration ---` section (the message's narration blocks, each trimmed, joined by a blank line; returned by default, never in `blocks[]`, and not gated by `includeThinking`, whose `blocks[]` lists only the other thinking) and a `--- plan ---`/`--- questions ---` fenced section when the turn produced one (the plan header is `--- plan · saved to <path> ---` when the message carries a `planPath`; a message whose plan is a path with no readable text is that header alone) (order-faithful to when those blocks occurred — never empty for a plan/question-only turn); the questions section numbers each question by its position in the tool input, and a malformed entry keeps its number — a non-object question renders empty, a non-array `options` as none, a non-object option is dropped (`normalizeQuestions`, `shared/userQuestionAnswers.ts`, which `answer_question` reads the same way, so its `answers` align to this numbering) — UNLESS >1 message is returned, in which case every body is prefixed with `--- message i/N · msgId · textChars chars ---`

<a name="rendered-read-results"></a>
**Unanswerable reads.** A git command that did not answer is never rendered as a positive fact about the tree: `project_status` prints `DIRTY (unknown — git status did not answer)` instead of `DIRTY (0)`, `project_diff`'s summary carries `uncommitted:{unknown, reason}` instead of zeroed totals, and the commit-log payload carries `hasUncommitted: undefined` + `uncommittedUnknown:true` instead of `false` (and refuses **502** on a `git log` that did not answer, which it tells apart from a legitimately empty history via `hasUnbornHead`). Every one of those is a command that **RAN and answered non-zero**, and the realistic trigger is `runGit`'s own 16 MB output fence — which fires on exactly the tree least safe to describe as clean. A command that **never ran or never answered** takes a different route out: `runGit` throws a system refusal (502 `GIT_DID_NOT_RUN` / 504 `GIT_TIMED_OUT`), so none of these degraded renderings appear for it — the read fails by name instead. So does a command git **refused on ownership** (403 `GIT_DUBIOUS_OWNERSHIP`, message carrying the `safe.directory` fix), except on `project_status`, which prints `! git refused <message>` in place of branch/HEAD and still lists FILES.

**Rendered read results (text format).** Seven tools — the five recon read tools (`list_projects`, `list_worktrees`, `list_sessions`, `describe_session`, `project_status`) plus `describe_playbook` and `enumerate_remotes` — return a **plain-text rendering as their entire result**: one `content[0]` text block, no metadata block, **no JSON at all** (a `JSON.parse` of it throws). `describe_playbook` is text on its **success path only**; its `PLAYBOOK_UNKNOWN` refusal is a JSON `{ok:false, code}` like every other soft refusal, so branch on `code` before reading the text. Handlers opt in via `textResult(text)` (`src/mcp/content.ts`) — Symbol-tagged like `textPayload` rather than sniffing `typeof result === 'string'`, which would reshape any plugin returning a string through the bridge's `result` passthrough. Transport branch in `src/mcp/server.ts`; renderers in `src/mcp/readRenderers.ts` over the primitives in `src/mcp/textRender.ts`.

In text format there is **no structured channel** beside the text — no MCP `structuredContent`, no `outputSchema` (those are the JSON format's, [mcp-applications.md](../mcp-applications.md)) — so the text is the whole contract: **every fact a conductor acts on is in it.** Two ways a field gets there: rendered unconditionally, or declared in a `DeviantSpec[]` with a default and surfaced only when the value leaves it (`overageActive`, `archived`, `isGitRepo:false`, `unbornHead:true`, `degraded` on a `list_projects` block — `! unreadable project record <reason>`, the one thing a project row says about ITSELF, since every kind of project renders alike — `system`/`remoteId` on a `list_projects` block, which default to `local`/`null` and so print only for a project whose record names another system, and `remoteId` only for one that also names a target on it, `systemUnreachable` — `! system unreachable <reason>`, which leads the block because it is why the git facts under it are absent rather than measured, `gitRefusal` — `! git refused <message>` right after it, the same absence on a reachable system whose git refused the repository on ownership, `dirtyTruncated`, …), which keeps the common case short without hiding live state. A worktree row on `list_projects` and `list_worktrees` ends in a trailing `locked` cell when the user has locked that worktree, and carries nothing extra otherwise — never in the name cell, which is the `worktree` argument exactly as printed.

The LIVE worker block (`list_sessions`, and `describe_session`'s LIVE branch, which reuses it) always carries a `context` line after the `mode … model` line: `context <contextTokens> / <contextWindowTokens> (<pct>%)` in raw tokens, `—` for an unknown figure, and no percentage unless both are known (`context — / 1000000`, `context 84213 / —`). Inactive rows and the RETIRED branch have no process and no such line. Its first line carries `jobs <N>` (the count of `backgroundJobs`) after `agents <N>`, and one `job "<title>" — running <duration>` line per running background Bash job follows it (`jobLine`, `src/backgroundJobs.ts`); none when there are no jobs.

Fields deliberately **dropped** rather than hidden — not rendered and not reachable anywhere, each because it is redundant on screen or not actionable: `list_projects` `worktrees[].parentProject`/`.parentPath` (identical to the project header above them; `list_worktrees` renders `parentProject` in its own header, and drops `parentPath` for a different reason — it is not row-invariant once a worktree can be based on another, and is derivable either way: the project path for a root-based worktree, the base worktree's own `worktreePath` line for a derived one) and `worktrees[].sessions.{archivedCount,lastActivity}` (`list_sessions({project, worktree})` has it); `sessions.handCount` and `worktrees[].sessions.handCount` (a sidebar filter input; `list_sessions` carries each row's `conducted`); `list_sessions` `pid`, `createdAt`, and on an inactive row every runtime field plus `size`; and `firstPrompt` wherever a `title` exists. A session's recorded `mode` is not a field either — the one off-process mode fact is the `resumes-hot` DEVIANT flag. Full rationale in the header comment of `src/mcp/readRenderers.ts`.

**The recon split.** `list_projects` answers "what projects/worktrees exist and what is their git state"; `list_sessions` is the complete answer to "what sessions exist, live or resumable, and where". So `list_projects` prints `live N` as a **count only** — the payload carries no sessionIds at all (`liveCount`, from `InstanceManager.liveCountForProject`). That count and the live/inactive split in `list_sessions` both read one predicate, `isDeadStatus` (`src/instanceStatus.ts`), so the two tools cannot report a different fleet; `tests/mcp-instance-exits.test.mjs` pins the agreement — including for a **persistent exited instance**, which `byId` retains indefinitely (respawn resumes it) and which must therefore count as dead, not live. The REST `GET /api/projects` keeps its own `sessionIds` array (`src/routes/projects.ts`) — the sidebar consumes it, and it is a separate contract.

Two session counts on a `list_projects` block mean different things and are *both* intended to: `live N` counts in-memory workers, while `sessions N` counts non-archived transcript files on disk (`summarizeSessions`, `src/projects.ts`) — exactly what `list_sessions({project, worktree})` would list, which is why it keeps that name. A worktree with no worker can therefore read `sessions 2`. The MCP handler and the REST route pass that helper **different arguments on purpose**: REST passes `instances.normalSessionIdsForPlace(...)` so the GUI can render live normal sessions as their own nodes, while MCP passes nothing — excluding them would show `sessions 0` on a worktree with two running workers. So the same worktree legitimately shows a lower count in the GUI than in the MCP text.

`list_sessions` groups by the directory the sessions live in — each project's **main checkout first**, then its worktrees.
The main checkout is the one group that always exists, so the top of the output stays put as worktrees come and go.
Within a group, live workers lead (marked `LIVE`): `byId` rows failing `isDeadStatus`.
Inactive rows are that group's persisted sessions with no process, read from `listSessionsForCwd` (`src/projects.ts`) — the same function behind `GET /projects/:name/sessions`, so there is one definition of "which sessions exist and which are archived", not two.
The live sessionIds are passed as `excludeSessionIds`, so live and inactive are disjoint and a dead-but-retained `byId` instance reappears as an inactive row off its own transcript.
An inactive row is a `SessionRow`: it has no `status`/`effort`/`model`, so it renders as ONE table line (`sessionId  lastActivity  playbook/stage  flags  title`) rather than a worker block padded with `—`; the two shapes are unmistakable at a glance.
Its flags column carries `awaiting-user <kind>,awaiting-user-via <source>` when the transcript ends on an unanswered ask; a live block's `flags` line carries `owner <sessionId>` and the same pair.
**Archived** sessions are counted in every group header and collapse to a `+N archived` line; `includeArchived:true` lists them inline.
They stay off the default listing because archiving is the deliberate act of taking a session off the list — but the count is always visible, so an archived session is never silently invisible.
Each group header carries its branch.
A **worktree** group also carries its divergence, rendered `↑N ↓N vs base` — commits vs the base branch it will merge back into (`getWorktreeMergeStatus`, the same helper `list_projects` uses), which is what decides whether resuming into it lands somewhere useful.
A **main checkout** group carries no divergence: its equivalent number would be vs the remote upstream, a different question that renders `? ?` on any project without one, and it cost three git subprocesses per project to say nothing.
The `vs base` label is load-bearing — it is what makes the main checkout's silence read as "a different question was asked" rather than "not computed".
`list_projects` still reports upstream status for a project.

**Cost.**
`list_sessions` is disk- and git-bound.
Measured 2026-08-09, **before** the lineage bulk load and per-row lineage projection landed (2026-08-12) — so read the figures below as the comparative ratio they were taken for, not as today's absolute ms.
On a 24-project install with 6 worktrees (31 candidate cwds, 25 non-empty), old and new **interleaved in one process** (median of 21 — measuring them in separate runs drifts by 2× on filesystem-cache state alone, so interleaving is the only comparison worth quoting): **~76 ms filtered to one project / ~353 ms unfiltered**, against **~33 ms / ~258 ms** for the same scan without the grouping headers.
The added cost is git: one call per rendered group header, on top of the one `git worktree list` per project the scan already did.
The filtered ratio is the worse one (~2.3× vs ~1.4×) because with only a handful of cwds the git calls dominate.
Per cwd the disk work is one `readdir`, one `stat` per transcript, one read of the session store `listSessionsForCwdWithCounts` loads up front (`src/projects.ts` → `loadSessions`, a `stat` when the store's cache is warm; once per cwd, never per session) and a `readFirstPrompt` open per LISTED transcript (one `FIRST_PROMPT_READ` read, more — up to `FIRST_RECORD_CAP`, `src/projects.ts` — only when the first record does not end in it) — **not an exhaustive list**: the memoized 64 KB tail read behind `lastActivity` is per listed transcript too, and is described where `lastActivity` is, below.
Three things keep it from compounding: `listSessionsForCwdWithCounts` returns the rows and the archived count from **one** walk — pairing `listSessionsForCwd` with `summarizeSessions` instead costs a second `readdir`, a second `stat` of every transcript and a second archived-set load for a number the first walk already has; archived rows are counted before the `includeArchived` filter but their first prompt is read only when they are actually listed, so a project where archived outnumbers active 25:1 pays no per-transcript cost for its `+N archived` line; and a wholly empty group is dropped before its git call in an unfiltered listing.
`includeArchived:true` opts back into the full per-transcript read (~404 ms unfiltered).
The `project` filter narrows the scan *before* it happens (only that project's cwds are visited), so passing it is the mitigation; the tool description says so.
There is no cache — a stale session list would be worse than a slow one.

`list_sessions` takes an optional `project` filter — which now covers **the project AND its worktrees**; reaching a worktree's sessions no longer requires naming it — plus an optional `worktree` to narrow to one (without `project` it soft-refuses `{ok:false, code:'PROJECT_REQUIRED'}`), and `includeArchived`.
Groups sort by project, then main-checkout-before-worktrees, then worktree name.
Live rows within a group sort by project, worktree name, `createdAt`, `sessionId` (`compareInstanceRows`, `src/mcp/handlers.ts`); inactive rows sort by `lastActivity` descending instead — a stopped session has no `createdAt` on this surface, so recency comes off its transcript.
**Not the transcript's mtime**: the CLI appends untimestamped bookkeeping records (`last-prompt`, `mode`, `ai-title`) as its process exits, so a mass subprocess exit stamps every live session's file within the same millisecond, hours or days after those sessions actually stopped.
`lastActivity` is the ISO `timestamp` on the LAST timestamped record INSIDE the jsonl (last in file order, not newest by value — they differ only where interleaved sidechain records land a few ms out of order), read from a bounded 64 KB tail and memoized per file (`src/sessionActivity.ts`); it falls back to mtime only when the tail holds no timestamped record.
Unsorted `byId` Map order was creation order: deterministic between calls, but it interleaves projects and does not survive a restart.
The filter is **validated**: a malformed non-empty name (a path, most often) never reaches the handler — it is refused 400 `BAD_REQUEST` before dispatch runs it (see [Input validation](#mcp-input-validation)) — while an unknown well-formed name, or `''`, soft-refuses `{ok:false, code:'PROJECT_UNKNOWN'}` via `getProject` rather than rendering as an empty fleet — one of two cases where this tool returns JSON instead of text.
`.conduct` is legal by NAME rather than by a directory probe (the dir is created lazily at first conductor spawn), and the **unfiltered** scope appends it too — `listProjects` skips dotdirs, so without that a conductor hunting its own prior session to resume would see every project's stopped sessions and none of its own.
A *valid* project with nothing in it still renders normally, and the heading echoes the filter (`SESSIONS (live 0 · inactive 0 · archived 0)  project foo`) so that emptiness is not read as an idle fleet.

A **hidden** pristine conductor (see `summary().pristine`) is in neither `list_sessions` nor `describe_session`'s live branch, which both read `InstanceManager.listVisible()`; with no transcript it has no disk row either, so neither tool renders it as a session. Once prompted, or listed under a draft, it is a live row like any other.

`list_sessions` and `describe_session`'s **live** branch are the two of the five whose payload keys are a runtime-enumerable, code-owned list (`CONDUCTOR_VIEW_KEYS` + `LIST_ONLY_KEYS`, `src/mcp/handlers.ts`) — the same list, since both project through the one `conductorRowView` — so they are bound to their rendering directly: `tests/mcp-text-render.test.mjs` → *"list_sessions renders every allowlisted field"* feeds a unique sentinel per key and requires each to appear, with a small, non-empty, explicitly-named exempt set for the drops above. It is fail-by-default — a new allowlist key must be rendered or classified. The doc-drift gate in `tests/mcp-conductor-view.test.mjs` binds the allowlist to the `list_sessions` outputSchema only; both are needed, since a field can pass that gate and still never be emitted. The sentinel fill runs through `renderSession`'s live branch as well as `renderSessions`, so a new allowlist key must be rendered on **both** surfaces or classified. `describe_session`'s **retired** branch is a `SessionRow` instead, so it falls in with the erased-type tools below. The other three tools' payload shapes are TypeScript types erased at runtime, so the same technique does not apply to them; their renderings are pinned by exact-output tests instead, which catch a field that stops rendering but not one added upstream and never rendered.

Handles stay full-length (sessionIds, absolute paths, branch names, `project_status`'s HEAD sha); a `baseSha` is shortened to 12 as informational context.

**`get_recent_messages` default-call bonding.** `count` defaults to 1 and is clamped to a bounded range (see the `get_recent_messages` schema). On the **default** call only (`count` omitted — not `count:1`), when the last message is plain prose the selection is bonded back to the turn's plan/questions message and spans from it through the end of that turn — so a split turn whose trailing prose spans two or more messages surfaces the plan/question together with all of it, without the caller needing an explicit `count`. A message counts as plan-bearing for this purpose when it has plan text **or** a `planPath`, so a plan that is only a path still bonds its trailing prose. The walk-back is **scoped to the current turn** (via the ring's `turn_end` seqs — a plan from an earlier turn is never pulled in), and a message that already carries its own plan/questions is returned alone. Narration counts as prose here and as text for the default filter: a message carrying only narration (e.g. redacted thinking, narration, a tool call) is returned rather than counted in `omittedToolOnly`. Any explicit `count` is literal (`slice(-count)`), bonding never applies.

**`get_recent_messages` `hint`.** Present only when the result could not fill the request or was cut, and never a bare ambiguous result (`buildRecentMessages`, `src/mcp/handlers.ts`):
- **Fewer text messages than asked, some tool-only:** names how many recent assistant messages carried only tool calls and points at `includeToolCalls:true` / `get_transcript` — worded for a live session (the agent is active) or a retired one (it stopped mid-work).
- **No text messages at all:** retired → nothing further will arrive; live with the ring trimmed and the transcript unavailable on disk → try `get_transcript`; otherwise → none have arrived yet.
- **Older messages dropped for the result budget** (`omittedForBudget`): names the count and points at a smaller `count` or `get_transcript`, ahead of any hint above.

**`get_recent_messages` tool-input descriptor.** `blocks[].input` is a **per-argument
descriptor** by default. Each top-level argument whose size is at most `TOOL_ARG_VALUE_CAP`
(`src/mcp/messageReconstruction.ts`) is emitted verbatim — strings gate on raw utf8 bytes,
everything else on its JSON encoding — and a larger one is replaced by a marker naming its type
and size: `[omitted: string, <bytes> bytes]`, `[omitted: array, <n> items, <bytes> bytes of
JSON]`, `[omitted: object, <n> keys, <bytes> bytes of JSON]`. A block with any omitted argument
carries `inputTruncated:true` while `input` stays a structured object. The rule does **not**
recurse: a node is kept whole or replaced whole, which is what bounds an array of many small
elements (its own JSON blows the cap, so it collapses to one marker) at the cost of a nested
small value inside an oversized container. `includeToolCalls:true` emits the whole input instead,
capped as one unit at `MSG_TEXT_CAP` with `inputTruncated` meaning "cut mid-JSON" — that cap
applies on **both** paths, so it remains the structural ceiling. This is why a 15 KB `Write`
argument no longer rides into a conductor's context on a default read or an idle-wake
wake fold (`src/idleSubscriptions.ts` calls `buildRecentMessages` with no flags and inherits the
default); `send_prompt({forward})` never carried `blocks[]` at all.

**`send_prompt({forward})`.**
`forward:{sessionId}` injects another worker's recent output into this prompt, composed server-side so the text never passes through the conductor's own context.
The payload is the **same default selection** the bonding paragraph above describes (as if calling `get_recent_messages({sessionId: forward.sessionId})` with no `count`) — not re-derived, not summarised — rendered through the third, worker-facing view named above: bare `--- message i/n ---` boundaries (no `msgId`/char counts), no `sessionId`/`source`/`retained`/`omittedToolOnly` telemetry (the source `sessionId` is a **handle**, so leaking it into another worker's prompt is a hazard, not just noise: while the source lives it addresses it — a forwarded worker could `send_prompt`/`spawn_instance` itself — and once retired it still **reads** it, since the read tools serve a retired session from disk.
Retirement narrows the hazard; it does not end it), full plan bodies inline, and the conductor's own `text` placed **last**, once, after a fixed `--- FORWARDED WORKER OUTPUT (verbatim · context only) ---` / `--- END FORWARDED WORKER OUTPUT ---` frame that marks the payload as reference material and tells the receiving worker not to execute, answer, or reply to anything inside it.
The frame layout (header, footer, bare boundaries, `\n\n` joins) is owned by `shared/forwardFrame.ts`, which the conversation view also parses to render the forwarded-output bubble — no wire marker.
A message's `--- narration ---` segment rides along, capped at `MSG_TEXT_CAP` like the prose.
Each message's prose is still capped at `MSG_TEXT_CAP` (`src/mcp/messageReconstruction.ts`); where the cap bites, an in-frame marker says so and names the plan file as a recovery route when the message carries a `planPath` (plan bodies themselves are never capped).
`forward.sessionId` is prefix- and disk-backed-resolved **independently** of the target `sessionId` (own `FORWARD_`-prefixed codes — see refusals below), so a two-session call always says which side to fix.
A **retired** source is forwarded from its transcript, so the source need not be live — but it does need its **full** sessionId, since prefix resolution is in-memory only (see [Prefix resolution](mcp.md#mcp-tool-protocol)).
What governs the source is therefore policy, not liveness: it is a **policy subject**, not merely a resolution target, and under playbook enforcement is checked for `get_recent_messages` against its own stage (`FORWARD_DENIED_IN_STAGE` — see [Playbooks](playbooks.md#playbooks)), which `decideTargeted` resolves from the playbook projection and so applies to a retired worker exactly as to a live one.
An empty or tool-only selection soft-refuses `NOTHING_TO_FORWARD` before any prompt is sent — no turn starts, no wake arms, and (the gate records an `ok:false` result as a `failed` call, with no `move`) no transition is recorded even when the call also carried a legal `stage`.
On success the result gains `forwarded:<int>` (the forwarded message count); everything else about `send_prompt`'s result shape, wake semantics, and mid-turn steering is unchanged — a mid-turn forward takes exactly the same route as an unforwarded mid-turn send, with the steer note preceding the frame: delivered live on an ordinary model, and on one declaring `midTurnSteering:false` routed through the block-edge stop with `POST_STOP_STEER_NOTE` instead (the deferred branch keys on the composed text, so the frame rides along either way).

**`humanPrompts` (send-time).** `send_prompt` (forwarded or not), `approve_plan`, `reject_plan` and `answer_question` add `humanPrompts:[<string>]` to their success result when the target's pending wake holds human prompts — the human prompted it directly since its owners' last wake, so the send joins or follows a turn they started. Read with `InstanceManager.pendingHumanPrompts(target, caller)` just before the send — a peek: the wake still carries the notice — covering both the target's pending prompts and those already taken into a wake held for the mid-turn calling conductor (a non-steerable model, see Idle wake), quoted as the notice quotes them (cut, the most recent `HUMAN_PROMPT_QUOTE_MAX_COUNT`, oldest first, led by a `(K earlier …)` entry when older ones were dropped; `quoteHumanPrompts`, `src/promptAuthor.ts`) but without the `> ` prefixes. The key is **absent** when there are none. `renew_session` never carries it: its targeted form refuses a live target.

**Platform capabilities.** A tool that needs a capability the host platform lacks is omitted from `tools/list` and answers `unknown tool` when called: `system_bash`, `system_transfer`, `set_project_remote` and `enumerate_remotes` need `remoteSystems`. `create_project` / `adopt_project` with a non-local `system` refuse `SYSTEMS_UNAVAILABLE` (an error / a soft refusal, respectively) when it is off.

**Annotations.** `tools/list` entries carry `annotations`: `readOnlyHint` (all `list_*`, `describe_*`, `project_read`, `project_status`, `get_*`, `enumerate_remotes`), `destructiveHint` (`kill_instance`, `delete_worktree`, `merge_worktree`, `prune_session`, `system_transfer`), `idempotentHint` (`set_mode`, `set_project_workspace`, `set_project_remote`, `set_idle_timeout`, `set_session_title`, `create_workspace`, `delete_workspace`, `rename_workspace`, `kill_instance`).

**`ok` / refusals.**
`ok` is reserved for **soft refusals** only.
Acknowledgement tools (`kill_instance`, `set_idle_timeout`, `set_session_title`, `approve_plan`/`reject_plan`, `answer_question` success, the workspace tools, `set_project_workspace`, `set_project_remote`, `delete_worktree` success) return bare data with **no `ok`** — `send_prompt` left this list once `forward` gave it a refusal path: an ordinary send (forwarded or not) still returns bare data, but a refused `forward` returns `{ok:false, code, reason}` like any other soft refusal.
Expected business refusals return `{ok:false, reason, code}` and are **not thrown**, with stable codes: `WORKTREE_LOCKED` (`delete_worktree` and `merge_worktree` — the user has locked the worktree.
Checked **first** on both, and `force:true` does **not** override it on `delete_worktree`; only the user can unlock it, from the UI); `WORKTREE_ATTACHED`, `WORKTREE_DIRTY`, `WORKTREE_DIRTY_UNKNOWN`, `WORKTREE_HAS_DEPENDENTS` (`delete_worktree` — `WORKTREE_DIRTY_UNKNOWN` is a dirty check that **ran and failed**.
A failed check must never read as a passed one: falling through to `git worktree remove --force` deletes a worktree whose dirtiness was never measured.
`force:true` overrides both.
A check that **never ran or never answered** does not produce this code: the precheck's `worktreeDirtyLines` is unguarded, so `runGit`'s throw escapes the soft-refusal vocabulary as 502 `GIT_DID_NOT_RUN` / 504 `GIT_TIMED_OUT`, and `force:true` does not override it — measured, the forced path fails 504 at `git worktree remove --force` too);
`SESSION_NOT_LIVE` / `SESSION_UNKNOWN` (every worker-**addressing** tool, from strict-live resolution — **not** the read tools, which serve a retired session from disk; on those two `SESSION_NOT_LIVE` carries its second meaning instead: the transcript exists, under some transcript root cc knows about, but sits in an encoded-cwd directory no registered project or worktree owns, so it cannot be read — re-register that worktree);
`SESSION_UNKNOWN` also from **`spawn_instance({resume})`** when the resume id has no resumable conversation on disk (resume pre-flight in [mcp.md](mcp.md#mcp-tool-protocol));
`MODEL_AMBIGUOUS` (`spawn_instance`, when a specific model id is configured on more than one backend and no `backend` picks one; carries `model` + `backends:[<id>]`; rule in [models.md](../models.md#custom-models));
`SESSION_AMBIGUOUS` (any worker-addressing tool, when a sessionId **prefix** matches >1 in-memory session or is shorter than `SESSION_PREFIX_MIN`; carries `matches:[<8-char ids>]`; on `send_prompt` the ambiguous side can be either the target `sessionId` or `forward.sessionId`, and `reason` names which);
`SESSION_SWITCHING_MODEL` (`send_prompt`, checked before strict-live resolution, for the whole of a restart model switch — its process-less gap would otherwise read `SESSION_NOT_LIVE` with resume advice, and its grace window would deliver the prompt to a model not yet confirmed; carries `from`, `to`, `fromBackend`, `toBackend`, and `reason` names each model's backend when they differ; no prompt is sent);
`NOTHING_TO_FORWARD`, `FORWARD_SESSION_NOT_LIVE`, `FORWARD_SESSION_UNKNOWN` (`send_prompt({forward})` — the forward source resolves independently of the target.
`FORWARD_SESSION_NOT_LIVE` narrowed when forward gained its disk path: a non-live source is ordinarily forwarded from its transcript, so this now means the transcript could not be **reached** (the orphaned-transcript case above), not merely that the process is gone — a retired source with a readable transcript forwards, and one with nothing readable refuses `NOTHING_TO_FORWARD`; these carry `forwardSessionId`, never a bare `sessionId`, whenever a source id was resolvable — the malformed-argument case of `FORWARD_SESSION_UNKNOWN` (`forward` carried no usable `sessionId`) carries neither, since there is no id to name — see `send_prompt({forward})` above); a **fourth** `FORWARD_` code comes from the playbook gate rather than the handler — `FORWARD_DENIED_IN_STAGE`, when the source's stage denies the read (see [Playbooks](playbooks.md#playbooks)); `NO_PENDING_QUESTION`, `ANSWER_COUNT_MISMATCH`, `INVALID_OPTION`, `NOT_MULTISELECT`, `NOTE_WITHOUT_OPTION`, `EMPTY_ANSWER` (`answer_question`); `RESULT_OVER_BUDGET` (any core tool, from the [result-budget backstop](#mcp-result-budget) rather than the handler); `OVERAGE_STOPPED_UNARMED` (`send_prompt`, `approve_plan`, `reject_plan`, `answer_question` — the target is a worker the overage auto-stop left **un-armed**, so its conductor is the sole driver and a send to it can be neither delivered (the account is still throttled) nor queued (the queue flushes only on a resume deadline it deliberately does not have).
Shape `{ok:false, code, sessionId, reason}`; lifts by itself when the window resets, since the predicate `Instance.overageSendRefused` gates on the live overage window.
The **WS** `prompt` frame diverges deliberately: it keeps `Instance.prompt`'s throw, surfacing as `ack ok:false` and a failed send in the composer, which is the right shape for a human — see [components/instances.md](../components/instances.md#overage-trip-detection--central-routing) → overage); `WORKTREE_BEHIND`, `BASE_BRANCH_MISMATCH`, `PARENT_MID_MERGE`, `PARENT_DIRTY`, `PARENT_STATUS_UNKNOWN`, `WORKTREE_DIRTY`, `WORKTREE_STATUS_UNKNOWN`, `NOTHING_TO_MERGE`, `MERGE_FAILED`, `SYSTEM_UNREACHABLE` (`merge_worktree`, after `WORKTREE_LOCKED` above.
`SYSTEM_UNREACHABLE` covers the System failing at any point, not only at entry — the WHOLE body is converted, because a transport failure mid-merge otherwise arrived as a git-shaped answer and was reported as `MERGE_FAILED` carrying a transport cause.
It carries **`mayHaveCompleted: true`** when the transport dropped *after* `git merge` was issued: the orphaned merge was observed completing on the far side after cc had already reported failure, so `git merge` is **not** individually atomic and a refusal implying "nothing happened" would be wrong — check the parent before retrying.
`PARENT_MID_MERGE` is the state that leaves behind (`MERGE_HEAD` set), reported separately because `PARENT_DIRTY`'s repair — commit or stash — does not apply to it.
`PARENT_STATUS_UNKNOWN` and `WORKTREE_STATUS_UNKNOWN` are a `git status` that did not answer, on the parent and on the worktree's own tree: an unread tree is neither clean nor dirty, and the guard refuses instead of skipping itself.
`allowDirty:true` overrides the worktree one, as it does `WORKTREE_DIRTY`.
All returned rather than thrown, because every blocker here is a code the caller renders and a throw would surface as a 500 with nothing to act on — same `WORKTREE_DIRTY` meaning as `delete_worktree`'s (the worktree's own tree, not `PARENT_DIRTY`'s parent repo), overridable here via `allowDirty:true`);
`WORKTREE_HAS_DEPENDENTS` (`sync_worktree`, `merge_worktree`, **and** `delete_worktree`; carries `dependents:[<worktree names>]`, and on `delete_worktree` is overridable via `force:true` — see [Feature branches](../features/worktrees.md#worktrees));
`INVALID_SUMMARY` (`renew_session`, empty summary);
`INVALID_RENEW_FORM` (`renew_session`, any illegal combination of its two forms' arguments — `summary` with a `sessionId`, `directive`/`followUp` without one, or a `sessionId` naming the caller itself;
`reason` names which);
`SESSION_BUSY` (`renew_session` targeted form, when the target is not free; carries `status` + `busy`);
`INVALID_PRUNE_TARGET` (`prune_session`, when the `sessionId` names the caller itself — a prune respawns its target, so self-pruning would kill the calling process mid-call;
`reason` routes to `renew_session`);
`SESSION_BUSY` also from `prune_session` when the target is mid-turn (`reason` names `interrupt_turn`);
`SESSION_ROTATING` (`renew_session`, when a prune or another mutation already holds the caller — or, on the targeted form, the target — and `prune_session`, when any rotation already holds its target — see [Session renewal](mcp.md#mcp-tool-protocol); the REST prune path raises the same code as a 409);
`system_transfer` (shape `{ok:false, code, reason, side?, errno?, written?}`):
`ENDPOINT_INVALID`, `PATH_IN_CC_STORE`, `systemById`'s `SYSTEM_NOT_REGISTERED` / `SYSTEM_NO_PROVIDER` / `SYSTEM_UNREACHABLE` / `SYSTEM_NO_REMOTES` / `REMOTE_NOT_FOUND` returned rather than thrown, then from the engine `SOURCE_NOT_FOUND`, `NOT_A_FILE`, `EFBIG`, `SAME_FILE`, `DEST_EXISTS`, `DEST_NOT_A_FILE`, `SOURCE_CHANGED`, `READ_FAILED`, `WRITE_FAILED`, `DEST_UNVERIFIED`, `SOURCE_NOT_REMOVED` — every code's and field's meaning is defined once, in [features/mcp.md](../features/mcp.md#mcp-interface) → Transfer between systems → Refusal codes.
The only constant `ok:true` is `merge_worktree`/`sync_worktree` success (shape shared with the REST land endpoints).

**Errors.** True faults are caught and returned `isError:true` as a prose block — `<message> (HTTP <statusCode>)` when the handler set a `statusCode` — followed by a structured `{error, code, statusCode}` block, plus a plugin refusal's `details` object when it sent one ([docs/plugins.md](../plugins.md#typed-plugin-tools-both-formats) → 6). `code` is the thrown error's own `code` when it carries one (e.g. `PROJECT_UNKNOWN`, `WORKTREE_UNKNOWN`), else derived from `statusCode` (`400→BAD_REQUEST`, `404→NOT_FOUND`, `409→CONFLICT`, `500→INTERNAL`). Example sources: `project_read` 404, invalid `baseRef` 400. The envelope is bounded by the [result budget](#mcp-result-budget) like every other response — its prose can echo an argument and carries the message twice — see the response boundary there. (`describe_session` is not one — every way it can fail to answer is a soft refusal.)

**Conventions listings carry their own incompleteness.**
`list_project_conventions` and `list_conductor_conventions` return **`{conventions:[…], incomplete?:string}`** — an object, not the bare array.
`incomplete` is **present only when the convention catalog is degraded** (`CatalogList.degraded` — an `extraProvider` throw, a transient plugin **placement** failure, or a latched **discovery scan** that could not reach an enabled plugin's project; see [components/store.md](../components/store.md#srcfragmentcatalogts) → `src/fragmentCatalog.ts` and [plugins.md](../plugins.md) → *Discovery rules*), so its **presence is the signal** and a healthy result is exactly the old array under one key.
It carries a **prose sentence, one per surface**, and neither names the missing slug or plugin — the flag carries no cause and the failed plugin's declared slugs are not on the channel these handlers read.
The object shape is required, not cosmetic: `degraded` is the array's own property, which neither `.map()` nor the dispatcher's `JSON.stringify(result)` carries.
The project-scope sentence names the **committed** consequence, phrased conditionally on the loss because the flag fans out to every scope and can fire where nothing was lost: whatever is missing from the listing cannot appear in the line-1 `CONVENTIONS.md` marker of a project created from it, and no later regeneration adds it back.
The conductor-scope one names the contrast — nothing there is committed, since the role doc is recomposed from the catalog on every spawn.
`create_project` is not refused during a degrade; **on success only** it logs one server-side `createProject:` line naming the project, and that line — not the listing sentence — is where the lost **`scaffold`** directive is reported: a scaffold-bearing convention that dropped out of the listing cannot be picked, so no directive is emitted for it and nothing reissues one.
The REST twins `GET /api/settings/conventions/{project,conductor}` deliberately do **not** carry the flag.

<a name="disk-backed-reads-ring-first-fallback-on-demand"></a>
**Disk-backed reads (ring-first, fallback-on-demand).** "Disk-backed" covers two distinct cases, and both apply to `get_transcript` and `get_recent_messages`:

1. **A live instance whose ring evicted the range** — the in-memory event ring is a fixed-cap (`DEFAULT_RING_CAP`, `src/instances.ts`) drop-oldest cache, and eviction is **invisible** to these tools (per-tool mechanics below).
2. **A retired session with no instance at all** — killing a normal worker *archives* its session (`Instance._archiveSession`) and drops it from `byId`, but **retains the `.jsonl`**, so the whole read is served from the transcript with no ring involved.
   `getInstOrDisk` (`src/mcp/handlers.ts`) finds it via the instance record if one survives, else by probing registered projects/worktrees and then the place the session's record names (`findSessionLocation`) — so a worker stays readable after `delete_worktree` removed its worktree.
   `source` reports `"disk"` on both tools, `get_transcript` reports `status:"exited"` (a session with no process is accurately dead; no `"not-live"` member was invented), and `trimmedBefore` is `0` / `retained` is `{firstSeq:0, lastSeq:-1, trimmed:false}` — honest, since nothing is retained in memory.
   Two consequences worth planning around: a retired session needs its **full** sessionId (the prefix universe at [Prefix resolution](mcp.md#mcp-tool-protocol) is in-memory only), and a retired page carries only the event kinds the CLI **persisted**: no `turn_end`, no status/system events, nothing stream-only.
   That is also why turn bonding on the disk side partitions turns at outer `user_echo` events rather than `turn_end` — the same partition, from the boundary that *is* persisted (`src/transcript.ts`).
   A conductor must not poll a retired session for a completion event; `hasMore:false` is the end of it.
   If the transcript exists but sits under an encoded-cwd directory no registered project or worktree owns and no session record names (a session recorded before every spawn wrote its place), it cannot be read at all (`encodeCwd` is one-way, so the directory name cannot be reversed into a `cwd`) and both tools refuse `SESSION_NOT_LIVE` naming that cause — deliberately not `SESSION_UNKNOWN`, so *retired* stays distinguishable from *never existed*.
   That scan (`findOrphanedTranscript`) sweeps the local transcript root **and every registered remote's**, because there is no single root any more; left local-only it would answer `SESSION_UNKNOWN` for every remote session where this more informative refusal is owed.
   It is also what an **upgraded** install's stranded pre-per-remote-config-dir transcripts land on: the place IS registered, its root moved, so the refusal names the cause slightly imprecisely and is still the more useful of the two.
   A retired session on a project on a **system** is NOT that case: `findSessionLocation` derives the cwd from the project's registered path, so the read is served from cc's own disk and **needs no data from the box** — an unreachable system does not refuse a read, only a spawn.
   It is not free of the box either: locating the session walks each project's worktree store through its system, so a **wedged** provider stalls the read rather than refusing it and a **down** one changes which worktree places exist — see `findSessionLocation` (`src/projects.ts`) for that contract.

Per-tool mechanics:
- `get_transcript({sessionId, fromSeq, limit})` pages via `pageInstanceEvents` — or, for a retired session, `pagePersistedEvents` (both `src/eventArchive.ts`, sharing one windowing core) — and is always **single-segment**: an older segment id of a live session answers with the live pager, and only the web UI walks earlier segments ([Lineage scrollback](rest-instances.md#lineage-scrollback)).
  It translates at the boundary since the two surfaces deliberately differ: `fromSeq` is **inclusive** (events with `_seq >= fromSeq`, oldest-first — `fromSeq: 0` reaches the very first event), unlike the REST `after=` cursor above, which stays exclusive.
  Served from the ring; when the requested range dips below `trimmedBefore` (an evicted range) the on-disk session transcript is loaded and reconciled with the ring by `_seq` at a turn-aligned seam (no gap/dup).
  The response adds `{source, hasMore, nextFrom}` — `source` is `"ring"` vs `"disk"`, mirroring `get_recent_messages`, and tells a conductor it is reading history rather than a live stream; poll again with `fromSeq = nextFrom` (always the last served `_seq + 1`, so a caught-up re-poll returns nothing rather than re-serving the boundary event).
  `limit` is bounded with a fixed default.
  A page also stops short of `limit` when the next event would push the result past the [result budget](#mcp-result-budget): `hasMore` is then true and `nextFrom` continues from the last kept event, in both the `fromSeq` and newest-page modes; an event too large for any page arrives as a stub `{_seq, kind, omitted:true, chars}`, so the cursor still passes it.
  Replaces the old `truncated` field.
  Caveat: a single turn larger than the ring cap leaves a mid-turn `_seq` gap (covered by `get_recent_messages`) — but neither reasoning nor prose length triggers it any more, since the ring coalesces the per-token `thinking_delta`/`thinking_tokens`/`text_delta` floods to `O(blocks)` (see the `EventLog` retention note in [components/instances.md](../components/instances.md#srcinstancests), and the `thinking_tokens` entry above for provenance); only a turn with thousands of tool round-trips can still reach it.
  **Cursor consequence of that coalescing:** an open block occupies ONE slot whose `_seq` is stamped at its first fragment while its text keeps growing in place, and `nextFrom` is always the last served `_seq + 1` — so once served, an in-flight block is never re-served and incremental polling does **not** show it grow.
  Use `get_recent_messages` for in-flight prose (it reconstructs by `blockIdx` off the live ring, so it re-reads the growing slot on every call).
  Re-serving the slot at its unchanged `_seq` is deliberately NOT done: the client dedups by `_seq` (`ConversationModel.apply`, `web/src/conversation/model.ts`) and would silently drop it.
  - **A forward read proves nothing about the UI's view.** Only backward pages snap (`snapStartToQuiescent`, via `pageInstanceEvents`); `fromSeq` pages forward, and the web UI pages backward through `/lineage-events`. Reproduce a UI history symptom with the UI's own `before=` requests.
  - A transcript missing its opening `user_echo` is ring eviction, not a missing emission: replay synthesizes it (`replayPersistedLine` → `consolidateUserContent`), and live emits it in `Instance.prompt()`.
- `get_recent_messages` is ring-first; only when the retained tail can't satisfy the requested recent **text** messages (and the ring was trimmed) does it read the on-disk transcript and merge by `msgId` (ring entry wins; bounded by `DISK_REPLAY_TAIL_CAP` (`src/mcp/messageReconstruction.ts`)). `source` reports `"ring"` vs `"disk"`. A genuinely missing transcript degrades to ring-only + a `hint`; never crashes — note that an exited **normal** session is not that case, since its jsonl is retained rather than deleted. On a **defaulted** call (no `count` passed) the ring must satisfy `n+1` text messages, not `n`, since the default path may bond in one preceding plan/question message (see below) — this raises the bar for staying ring-only before falling back to disk.

Note: the REST endpoints above keep their own `worktreeName` field — they are a separate contract from the MCP tools and were not renamed.

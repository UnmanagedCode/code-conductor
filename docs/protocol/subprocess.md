# Protocol: the Claude CLI subprocess

## Subprocess protocol
```bash
claude -p \
  --input-format=stream-json --output-format=stream-json \
  --verbose --include-partial-messages --include-hook-events \
  --exclude-dynamic-system-prompt-sections \
  --allow-dangerously-skip-permissions \
  --permission-prompt-tool stdio \
  --permission-mode <plan|bypassPermissions> --effort <effort> --thinking <thinking> \
  --settings '{"hooks":{"PreToolUse":[…]}}' \
  --mcp-config '{"mcpServers":{"code-conductor":{"type":"http","url":"http://127.0.0.1:<port>/mcp/<sessionId>?format=text"}}}' \
  --plugin-dir <cc>/claude-plugin [--plugin-dir <root> …] \
  [--model <name>] \
  --session-id <fresh-uuid> | --resume <existing-uuid>
```

The `--mcp-config` URL names the session's own public id in the path (the caller identity — [mcp-applications.md → URL contract](../mcp-applications.md#url-contract)) and asks for the text view. The line is omitted when `ORCH_DISABLE_MCP_AUTOREGISTER=1` (no MCP toolbelt auto-registered into the spawned process).

`--plugin-dir` is **repeatable** (session-local Claude Code plugin roots — skills et al.). The first is always cc's built-in root (`CORE_CLAUDE_PLUGIN_ROOT`, `src/coreClaudePlugin.ts`; see [features/mcp.md → Core skills](../features/mcp.md#core-skills)), then one per enabled cc plugin whose manifest declares `claudePlugin`. Each `<root>` is a resolved+validated abs dir (a dir directly containing `.claude-plugin/plugin.json`); a root lacking that file is warned + dropped — the built-in one included — and the session still launches. Only a broken install omits the built-in one. See [plugins/manifest.md](../plugins/manifest.md#manifest--conductorpluginjson-at-the-plugin-project-root) → `claudePlugin`.

**Substitution backends (the launch template).**
Spawning is backend-agnostic: `Instance.spawn` computes only the command + argv prefix from the session's **backend record**, then appends the **same** claude args (including `--model <model>`) for every backend.
A backend's `template` is the command that replaces `claude`, with `{model}` substituted in (blank template ⇒ run `claude` directly); `resolveBackendLaunch` in `src/claudeLauncher.ts` is the single substitution point, and the backend's configured `env` pairs ride along with it.
Backends are user-managed data — see [models.md](../models.md).
For the built-in `ollama` row the template is `ollama launch claude --model {model} --yes --`, so the full argv is `ollama launch claude --model <tag> --yes -- <all the args above, including --model <tag>>`.
`ollama launch` sets the Anthropic-compatible endpoint + auth internally and re-injects `--model` into the child; the forwarded `--model <tag>` is a matching **no-op duplicate** (verified harmless).
`--yes` bypasses the interactive agent-capability confirmation (which would fail a piped spawn).
Everything after `--` (stream-json stdin/stdout, `--mcp-config`, `--settings` hook, `--session-id`) is forwarded unchanged — the worker registers, streams, and drives MCP + hooks exactly like a bare-`claude` spawn.
Any non-blank template refuses to launch without a resolved model (`422 BACKEND_MODEL_MISSING` at create time, and the same refusal inside `resolveBackendLaunch`) — **unconditional on the template shape**, so a template that never names `{model}` is no exception: the model still rides in the forwarded claude args and drives the context-window env below.
A backend id that isn't in the registry is likewise refused `422 BACKEND_GONE` rather than falling back to `claude` (see [models.md](../models.md#missing-backends-are-refused-never-downgraded)).
There is **no** reachability preflight: a bad backend or model fails at spawn and surfaces as `launch_failed`.
**Task tools.**
When `spawn.taskTools` is on (Settings → Models → Task tools), `Instance.spawn` sets `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` on the child env for every launch; it is cc-managed (wins over a same-named backend pair) and unset when the setting is off — cc neither writes nor strips it then.
The argv is identical either way.
The env var is used instead of `--tools`/`--allowedTools`: naming a task tool in either also opts the CLI in, but `--tools` restricts the base tool set and `--allowedTools` adds permission allow-rules (measured against CLI 2.1.312).
`CLAUDE_CODE_ENABLE_TASKS` is left alone so the CLI keeps the `Task*` variant that the task panel tracks.
Remote-system workers carry the var through the FUSE launch wrapper unchanged; the CLI's own task-store writes inside a remote worker's chroot are unmeasured.
**Auto-background.**
`Instance.spawn` owns `CLAUDE_AUTO_BACKGROUND_TASKS` and `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS` on every session launch, after the backend pairs are applied: it deletes both (dropping a value inherited from cc's own env or set by a backend pair), then, when `spawn.autoBackground` is on (Settings → Models → MCP auto-background) and the session is not the conductor (`isConductorInstance`), sets `CLAUDE_AUTO_BACKGROUND_TASKS=1` and `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS=<spawn.autoBackgroundMs>`.
Read at each launch.
The CLI ignores the threshold without the flag.
Remote-system workers carry both through the FUSE launch wrapper unchanged.
A backgrounded MCP call emits `system/background_tasks_changed` → `system/task_started` with `task_type:"mcp_task"` → a `tool_result` notice that the call moved to the background → the turn's `result`; on completion `task_updated` → `task_notification` → `background_tasks_changed`, then a self-started turn (`system/init` → `message_start` → … → `result`).
See the task frames below; an `mcp_task` is counted in `_activeAgentTasks` like `local_agent` (measured against CLI 2.1.316).

For a spawn on any **non-`claude`** backend, both `CLAUDE_CODE_AUTO_COMPACT_WINDOW` and `CLAUDE_CODE_MAX_CONTEXT_TOKENS` are set on the child env to the session's resolved `contextWindowTokens` (raw tokens; resolved once at create by `resolveContextWindowTokens` in `src/appSettings.ts`, which matches the custom-model row or curated catalog on the **exact** model id); unset when the window is unknown. These two are **cc-managed** — implicit to every substitution backend, never applied to plain `claude`, never exposed in the Backends UI, and applied *after* the backend's own `env` so they win over a same-named pair. Both are needed: the CLI clamps the effective compact trigger to `Math.min(modelWindow, AUTO_COMPACT_WINDOW)`, and its internal per-model table defaults any unrecognized model (every non-Claude id) to a 200k assumed window, which silently caps `AUTO_COMPACT_WINDOW` back down — `MAX_CONTEXT_TOKENS` overrides that assumed window directly for non-Claude models, so the CLI actually auto-compacts at the real limit instead of ~200k. The `.conduct` orchestrator's opt-in compact-window override still wins when both apply (it only overrides `AUTO_COMPACT_WINDOW`, which remains the binding minimum).

**Session identity env.** `Instance.spawn` sets the variables below on the child env of every session launch, so a hook, a stdio MCP server, a subagent or a local `Bash` inside the session can tell which cc session it belongs to. They are cc-managed: assigned after the backend's env pairs (beside `CC_PROJECTS_ROOT`), so neither a backend pair nor a host value wins.

| Var | Value |
|---|---|
| `CC_SESSION_ID` | the session's **public** `sessionId`: the handle `describe_session`, `list_sessions` and `/mcp/<sessionId>` take |
| `CC_SESSION_KIND` | `conductor` or `worker`, from `sessionKindOf` (`src/conduct.ts`): the same word the MCP tool audience gates on (`callerKindOf`, `src/mcp/server.ts`). `conductor` iff the session is in `.conduct`, so a section lead reads `conductor`. To tell a section lead from a top-level conductor, read `live.conducted`, `live.parentSessionId` or `live.rootSessionId` from `describe_session` |
| `CONDUCTOR_URL` | cc's base URL, `http://127.0.0.1:<port>` (`InstanceManager.conductorUrl()`): the same name and value plugin backends get. **Unset** (an inherited value deleted) when the manager has no bound port |

- **Lifetime.** One value per session. It is the same at fresh spawn, `--resume`, respawn, crash respawn, prune / rewind / model-switch relaunch and restart-resume: each goes through `launch()` → `spawn()` with the public id already pinned. An in-process `/clear` or renew keeps the process, and so the env; the public id does not rotate. A fork is a new session with its own id.
- **Not the hook input's `session_id`.** That, and the CLI's own `CLAUDE_CODE_SESSION_ID`, are the **backing** id, which rotates on `/clear`, renew and prune.
- **Remote (System) sessions** carry them: the FUSE launch wrapper passes the env through, and hooks and MCP servers run where the CLI runs, on cc's host inside the chroot. A remote session's **forwarded `Bash`** runs on the system without cc's env and does not see them.
- **Where they never reach.** An outer cc session's values (cc itself running inside a cc session) are removed:
  - `cliEnvBase` (`src/cliEnv.ts`) strips them, so the one-shot CLIs (`sessionOneShot`, `claudeShellEnv`, auth, `claude update`) get none and a session gets only its own.
  - The plugin supervisor's `spawnChild` strips them from a plugin backend, which serves many sessions and learns its caller from the forwarded `caller.sessionId`. It gets `CONDUCTOR_URL` only from the registry.
  - Host terminals, `project_bash` and worktree hooks are not session processes: they inherit cc's own env unchanged.
- **Resolving the rest** (project, worktree, playbook, stage): `POST $CONDUCTOR_URL/mcp/tools/describe_session`. Recipe: [mcp-applications.md → Resolve your own session](../mcp-applications.md#resolve-your-own-session).

**Interactive tools under CLI ≥ 2.1.x — `--permission-prompt-tool stdio`.** Headless stream-json (`-p`) sessions are non-interactive (`isNonInteractiveSession=true`); the CLI serves a coordinator/agent tool profile and **strips the interactive plan/question tools** unless the client presents as a permission consumer. Passing **`--permission-prompt-tool stdio`** does exactly that: the CLI routes those tools' permission prompts to us as `can_use_tool` control_requests over the stream-json channel (verified: it re-adds the three tools to `system/init` `tools[]` and they become callable). It is **additive** to `--allow-dangerously-skip-permissions` (normal tools stay auto-allowed and never reach `can_use_tool`; only the interactive tools do). Kill-switch: `ORCH_DISABLE_STDIO_PERMISSIONS=1` reverts to the fail-closed behavior (tools stripped).

The orchestrator answers `can_use_tool` in `Instance._handleStdoutLine`: for `ExitPlanMode`/`EnterPlanMode`/`AskUserQuestion` it replies `control_response {behavior:"deny", message:<AWAITING_INPUT_MESSAGE>}`; any other tool (rare) is allowed.
The deny releases the tool call — the `plan_request`/`user_question` card is emitted from the tool-use, so the drive-forward path needs nothing more from it — but it **does not reliably end the turn**: the model gets an `is_error` tool_result (tagged `yielded` — see UI event kinds) and wraps up only if the CLI has nothing queued behind it.
A message already sitting in the CLI's stdin (typically a wake callback from a finished worker) is injected right after the deny and the **same turn keeps running**.
So the reply is still fire-and-forget rather than held open — holding it for an *in-turn* answer would suppress `turn_end` entirely and deadlock a conductor's wake — but `turn_end` may be arbitrarily far off, and every answer path (`approve_plan`/`reject_plan`/`answer_question` and the UI cards alike) therefore sends **unconditionally**, picking up `MID_TURN_NOTE` when it lands mid-turn — or, on a model declaring `midTurnSteering:false`, parking behind a block-edge stop and picking up `POST_STOP_STEER_NOTE` instead (routed-site inventory in the `user` row below; the result shape does not say which route ran).
`approve_plan`/`reject_plan` are unchanged (setMode + approval prompt); `answer_question` delivers the worker a structured AskUserQuestion answer that is **byte-identical** to a UI question-card submit — both call the one DOM-free formatter in `shared/userQuestionAnswers.ts` (imported by the question card in `web/src/conversation/cards.tsx` and server-side by `src/mcp/handlers.ts`).
The flag alone exposes and makes the tools callable — **no `initialize`/`supportedDialogKinds` handshake is sent** (probe-verified unnecessary), and the CLI never issues `request_user_dialog` in this configuration (permission flows via `can_use_tool`).

`--allow-dangerously-skip-permissions` is **always** passed at spawn — even for `plan`-mode instances — because without it the CLI rejects any later runtime `set_permission_mode bypassPermissions` (i.e. the plan-approve flow). The flag only *permits* the switch; it doesn't activate bypass on its own.

`PreToolUse` hooks via inline `--settings` JSON (the old static `command` deny on **AskUserQuestion|ExitPlanMode** is **removed** — those tools are now gated at the `can_use_tool` layer, see above):
1. **Edit|Write|NotebookEdit|Bash** — `http` hook → `POST /api/instances/<id>/hook-callback`, a CLI-side hook timeout (`HOOK_HTTP_TIMEOUT_S`); the broker allows every local call, and a redirected session's calls follow the redirect policy.
2. **Conductor only** (`buildSettingsJSON({conductor:true})`, passed when `isConductorInstance`) — a second entry, appended after the first, on `READ_NUDGE_MATCHER` (`src/conductorReadNudge.ts`): the `mcp__code-conductor__` `project_read`, `project_bash`, `spawn_instance` and `send_prompt` tools, same URL and timeout. The matcher is an **anchored regex** (`^(…)$`): the CLI tests any matcher outside `^[a-zA-Z0-9_|]+$` as `new RegExp(m).test(toolName)`, so an unanchored alternation would also fire on any tool whose name contains one of these. Its answer **never carries a `permissionDecision`** (response table below). A worker's settings are entries 1, 3 and 4.
3. **Every session**, `PostToolUse` — one entry on `TOOL_RESULT_NUDGE_MATCHER` (`src/toolResultNudges.ts`): the `mcp__code-conductor__` `spawn_instance` and `delete_worktree` tools, same URL and timeout, anchored like entry 2. Any live session can call them, so it is not conductor-only. It delivers the **tool-result nudges** (`SELF_TITLE_NUDGE`, `LANDING_RENEW_NUDGE`; see **Tool-result nudges** under MCP in [mcp.md](mcp.md#mcp-tool-protocol)).
4. **Every session**, `PreToolUse`, **appended last** — the **worker-tools** entry: matcher `WORKER_TOOLS_MATCHER` (`"*"`, every tool: built-in, `mcp__…`, and a subagent's calls), URL = the hook-callback URL plus `?policy=worker-tools` (`WORKER_TOOLS_POLICY`, `src/settings.ts`), same timeout. The route answers it **before and instead of** the broker, from `PlaybookGate.checkWorkerTool` — `deny` or `{}`, **never `allow`** — enforcing the bound worker's stage `workerTools` ([Worker tools](playbooks.md#worker-tools-workertools)). On every session because launch cannot know whether, or to which stage, a session will be bound (a fresh spawn's `bind` is written after its process is up). Every other entry keeps its index and value. The CLI runs matching hooks in parallel and folds their answers strictest-wins (`deny` > `ask` > `allow`), so a deny here blocks a call a sibling entry allowed, and `{}` leaves the siblings' aggregate unchanged.

**A session on a non-`local` system** (`src/settings.ts` → `buildSettingsJSON({redirect:true})`) widens that JSON — it never narrows it, so a local session's settings are exactly the above:

| Addition | Why |
|---|---|
| `PreToolUse` matcher gains **`Glob\|Grep\|Read`** | `Read` is hooked: its bytes need no fetching (the union puts them there), but a file tool aimed at a path the union does not serve to this session must meet cc's own refusal rather than an `-ENOENT` a model reads as "absent" (`classifyForTool`, `src/systems/fuse/tierTable.ts`). It is hooked to REFUSE, with ONE allow on top of the tier table: `Read` (only) of a path within the session's own `tool-results/` dirs (`<CLAUDE_CONFIG_DIR>/projects/<encodeCwd(cwd)>/<backingId>/tool-results/`, for every backing id in the session's live segments, `Instance._segments`), where the CLI saves an oversized tool result. **A SECOND, STATEFUL SURFACE IS CONSULTED AFTER** — and only after — `classifyForTool` has already ALLOWED: the session's per-path fault record (`ControlServer.faultAt`), whose two refusals name a path this session wrote and could not land (`diverged`, which refuses every file tool but `Read`) or a file above the protocol cap (`over-cap`, which refuses `Read` too). **The ordering is a ruling**: a surface consulted ahead of the tier gate is a bypass route by construction whatever it returns today, and it costs nothing because a fault can only exist for a project-tier path. These denials carry **no `ToolDenyClass`** — that set stays four. Every key of `FILE_TOOLS` (`src/systems/toolRedirect.ts`) is in this matcher, and a test fails if a fifth is declared without being added. `Glob`/`Grep` are hooked as a second guard on the denial below. |
| `PostToolUse` on **Edit\|Write\|NotebookEdit\|Bash** → the same URL, a second entry after the tool-result nudge one | **LIVE.** `SessionRedirect.postToolUse` reports a reconcile that refused AFTER the tool already returned success: cc's `READY` on a `FETCH` means it has taken ownership of the push, not that the push landed, and the push itself is answered to `close(2)` from the daemon's `flush`. For a `FILE_TOOLS` path it **awaits `ControlServer.settle(path)`** — the in-flight frame for that exact path — and then returns `divergedRefusal`/`overCapRefusal` (`src/systems/fuse/faultRefusals.ts`) as `additionalContext`, which is the only channel that can put a post-return failure in front of the worker in band, or `null`. The await is the criterion, not a precaution: a `release` backstop, or a frame queued behind another for the same path, can land after the tool returns, and a hook that read the record without waiting would report a racing state. **`Read` is deliberately absent from this matcher** and present in the `PreToolUse` one — a read-only open pushes nothing, so it has no reconcile to report. |
| `permissions.deny: ["Glob","Grep"]` | Neither can be redirected: a marked CLI's `Grep` spawns an UNMARKED `rg`, which the union routes as a stranger, so it would search the wrong side and return silently wrong results rather than failing. Not `--disallowedTools`, which is variadic and swallows the following prompt argument. **Measured (claude 2.1.250, cc's exact flags): a headless session carries neither tool anyway and `ToolSearch` cannot surface them, so this currently removes nothing** — it is a guard against a tool profile that is undocumented and has already moved once, alongside the by-name refusal in `src/systems/toolRedirect.ts`. |

**`agent_id` is read for one thing only: excluding subagent calls from the read-nudge run.** The tool-result nudges ignore it: they are keyed by `tool_use_id`, so a subagent's call gets its own call's nudge. The CLI puts it on a **subagent's** `PreToolUse` payload and omits it on the main agent's; a conductor read-nudge call carrying it is answered `{}` and neither counts nor resets the run. The worker-tools check ignores it: a subagent runs in the worker's CLI process under the worker's settings, so its calls arrive on the worker's URL and are the worker's calls. It plays no part in the redirect: one `exec` per command, so no command's state reaches any later command and there are no per-agent shells to keep apart — it is absent from the forwarder argv and the `bash-forward` body. `tests/systems-cli-contract.real.test.mjs` pins the payload shape.

**Inbound** (orchestrator → CLI stdin):

- `user` — **Payload:** text or `[{type:"text", text:"..."}, …]` blocks; attachments use `` Attached file: `<path>` `` (the path may use either separator) — **Notes:** A `user` written while a turn is running is **delivered mid-turn and interleaved into the live turn** (steering) — not queued until `turn_end`; the CLI persists it as a `type:"attachment"` `queued_command` line (array `prompt`), not a `type:"user"` line. **Unless the session's model declares `midTurnSteering:false`** (`Instance.acceptsMidTurnSteering`, resolved per model — see [models.md](../models.md#mid-turn-steering-capability)): such a model errors on or silently swallows the injection, so every site that can inject into a running turn routes through `Instance.queueSteerAfterStop` instead — arm the SOFT block-edge stop, then send the text as a **fresh turn** at the following `turn_end`, prefixed with `POST_STOP_STEER_NOTE` (`MID_TURN_NOTE` plus a clause saying the turn was stopped mid-work) in place of the usual `MID_TURN_NOTE`. Queued steers coalesce into one message (one stop, one `user` line, original order); a turn that ends on its own before the boundary delivers by the same path with nothing written to the CLI; the process dying first is annotated into the session's own transcript as a `system`/`stderr` line — `promptOrQueueSteer` (the only production caller) swallows the rejection, so nothing propagates back to the caller.
  `send_prompt` returns without waiting for the block edge.<br><br>**The routed sites.** The `{status:'turn'} × {acceptsMidTurnSteering:false}` test has one home, `Instance.needsPostStopSteer`, and one shared sender, `Instance.promptOrQueueSteer(text, attachments?)`. **Which route ran is not on the RESULT SHAPE** — on both routes the send is pending until the answering turn, so a caller has nothing to branch on, and reporting it would leak the delivery mechanism into the contract. The routes *are* transcript-distinguishable (`prompt()` emits `user_echo` synchronously; a parked steer only at the block edge), which is why `send_prompt`'s description tells a conductor that a send it cannot yet see has **not** failed — the rule covers the gap rather than the result field. Deliberately not `async`, and the live branch returns `prompt()`'s **own** promise: callers must be able to act in the same microtask the send completes in, because the idle wake ARMS inside `prompt()` → `_setStatus('turn')`, so a caller resuming a tick later could not observe the turn it just started. The parked branch resolves immediately — never at the block edge. - `control_request` — **Payload:** `set_permission_mode` / `set_model` / `interrupt`
- `control_response` — **Payload:** our reply to the CLI's `can_use_tool`

**Two-tier interrupt.** Both tiers send the same `control_request` `subtype:interrupt`; they differ in **when**. FORCED (`force:true`) sends it immediately (discards in-progress work). SOFT (default) **arms** it: `interrupting:true` broadcasts at once, nothing is written to the CLI, and the abort fires at the first **quiescent point** — no outer text/thinking/tool_use block mid-stream (each opened block has had its `content_block_stop`) and every outer `tool_use` has received its top-level `tool_result`. Armed in a gap ⇒ fires synchronously inside the `interrupt()` call. No steering message is injected on either tier, so a soft stop costs no extra model round-trip. The SOFT tier is reused verbatim by the no-mid-turn-steering delivery path above (`await inst.interrupt()`, no arguments): because the fire predicate holds while any outer `tool_use` lacks its `tool_result`, the stop never leaves a dangling `tool_use` and the next turn's request is well-formed.

The fire predicate (`Instance._atInterruptBoundary`) is `pendingTools.size === 0 && (openBlocks.size === 0 || boundarySeq > armSeq)`. Tool spans are strict — only a matching `tool_result` or a turn boundary discharges one. Display blocks have **two** discharge paths: their own close event, and **progression** — the appearance of a different `${msgId}:${blockIdx}` key, which marks the previous block stale and bumps `QuiescenceScan.boundarySeq`. Progression exists because a substitution gateway can withhold a close entirely (a `content_block_start` with no `content_block.type`, or a `type` of `"output_text"`: the block opens on its first `text_delta` and its `content_block_stop` emits nothing), which pre-fix latched the arm for the whole turn and cleared it silently at `turn_end`. `interrupt()` snapshots `boundarySeq` into `_interruptArmSeq` at arm time, so the second clause reads "a boundary has been crossed **since you armed**" — the retiring event is the same event that opens the next block, so an empty-state reading can never see it. On a well-formed stream the close is its own event, so this reduces to today's behaviour exactly; on a withheld-close stream the abort lands **one block late** instead of never. Progression reads only events carrying BOTH a `msgId` and a numeric `blockIdx`: `system`, `tool_result` and a bare `assistant_message` name no block and retire nothing.

Residuals the soft tier still cannot discharge: **R1** an arm in the turn's FINAL block on such a gateway, **R2** a gateway that frames the whole turn as one block, **D** a proxy that renames tool ids between the streamed block and the `tool_result`, and a genuinely wedged tool. R1/R2 still reach idle at `turn_end`, so the automatic callers get their stop either way; D and a wedged tool are covered by the deadline backstop below.

The predicate is one `QuiescenceScan` (`src/parser.ts`, the same class the snapshot/paging snap uses) fed from `Instance._emitUi`, evaluated in `_maybeFireArmedInterrupt` after the event reaches subscribers.
The two consumers ask different questions of it — paging asks "is state empty AT index i", the abort asks "has a boundary been crossed since the arm" — so progression MARKS a stale block rather than deleting it: a never-closed block is unfinished permanently, and paging must keep counting it or a cut would end a page on a dangling block.
Quiescent cut indices are therefore identical by construction.
Consequences of that scan: sub-agent events (`parent_tool_use_id != null`) are ignored, and a backgrounded Agent/Bash whose `tool_result` already resolved (`isAsync`) does not hold the fire.
A genuinely wedged tool is what FORCED is for.
No timer and no max-defer knob on the MANUAL doors (⏸ / `interrupt_turn`) — a human and a conductor both already have ⏹.
The three AUTOMATIC callers (`_directOverageStop`, `_guardOverageTurnStart`, `drainToManifest`) pass an opt-in `{ deadlineMs }` (`softInterruptDeadlineMs()`, default 120 s, env seam `ORCH_SOFT_INTERRUPT_DEADLINE_MS`): on expiry the arm escalates to FORCED and emits a `system`/`stderr` line naming the held block keys and unreturned `toolUseId`s. It fires only for a turn that never ends — R1/R2 end by themselves — and never after `_interruptFired` (an ACKed-but-not-honoured stop is a different defect).
The fire gates on `_interruptArmed`, **not** on the `interrupting` flag the WS frames carry.
`_interruptFired` suppresses any further `control_request` from the moment one goes out, and exactly two things clear it: a rejection, and the exit from `turn`.
An **ACK is not one of them** — the flag stays true for the rest of a turn whose stop landed, which is what lets the deadline above tell an undelivered stop from an ACKed-but-unhonoured one.
Not one per arm, though: repeated soft is a no-op and a FORCED escalation while armed sets the flag so no second fire lands at the boundary, but either tier rolls it back when its own `control_request` rejects, so an arm that survives a failed escalation goes on to fire at the next boundary.
All three flags clear on any exit from `turn` in `_setStatus` — which runs *before* `turn_end` is emitted, so a turn that ends first sends nothing and no arm leaks into the next turn.
A fire also opens the drain window (below).
A failed/timed-out `control_request` on the SOFT fire emits a `system`/`stderr` line and clears **all three** flags — the abort never landed, so the same turn stays re-armable by a second soft call.
The FORCED tier's rule is narrower: it clears `_interruptFired` on **every** rejection mode (timeout included) and emits nothing, and it leaves `interrupting`/`_interruptArmed` untouched because it never set them — a bare force leaves both `false`, an escalation leaves both `true` and therefore keeps the ⏹ lever on screen.
`_turnForceAborted` alone keeps its `timedOut`-keyed pessimism: on an unknown outcome both of its readers prefer assuming the abort landed — the wake report (`Instance.turnForceAborted` below) and `resumeRestart`'s drain-escalation loop, which skips a second force for an instance already forced once — while `_interruptFired` prefers letting another stop through.
Both tiers gated by `if (status !== 'turn') return`.

The CLI then writes its own `[Request interrupted by user]` / `[Request interrupted by user for tool use]` line as a plain `type:"user"` message. `isInterruptMarkerContent` (`src/parser.ts`) recognizes it (anchored, lone text block) and it is filtered at the same three sites as `SOFT_INTERRUPT_MARKER` (`parser._handleUser`, `transcript.replayPersistedLine`, `transcript.isPureUserPromptLine`), so live and on replay it renders as a bare `system`/`soft_interrupted` annotation, never a user bubble, and never shifts `_userEchoCount`/the rewind-fork index. While a drain window is open the annotation is dropped entirely (`_handleStdoutLine`) — that turn already annotates as `drain_abort`. Nothing persists a prompt index, so old sessions simply stop counting the marker; there is no migration.

The CLI's **local-command caveat** — the `type:"user"` line it writes directly before a local slash command's `<command-name>` line (`/clear`, `/effort`, `/model`, …) — is filtered at the same three sites and produces nothing at all. `isLocalCommandCaveatLine` (`src/parser.ts`) requires the CLI's own mark (`isCliInjectedLine`: `isMeta` in a jsonl, `isSynthetic` on stdout) **and** string content that is only `<local-command-caveat>…</local-command-caveat>`, so a user prompt that merely mentions the tag keeps counting. The `<command-name>` line after it stays a prompt line, so one live command echo (`Instance.setEffort`, or a command typed through `prompt()`) maps to one counted file line.

`system`/`soft_interrupted` also has a **server-side** emitter: `InstanceManager._guardOverageTurnStart` emits it with `data.text` (the overage lockout reason) before stopping a turn that started during the pause, which the conversation renders as `Turn interrupted: <text>` (`systemLine`, `web/src/conversation/format.ts`). The parser-generated one stays payload-free, so the CLI's own marker for that same abort produces a second, bare `⏸ Turn interrupted` line right after it — accepted, not suppressed.

`SOFT_INTERRUPT_MARKER` is **read-only**: nothing writes it any more. The two sites that did — the resume-restart drain and the overage conductor stop, via `Instance.windDown()` — are plain aborts now (a steer a model may silently drop cannot be load-bearing), and `windDown` is deleted. Historical jsonls still carry the marker, so its VALUE must not change and every recognition site stays live.

**Managed `/clear` (session renewal).** `Instance.clearContext()` writes a `type:'user'` message whose sole content is the text `/clear` on the same stdin path a normal prompt uses (via `_sendRaw`, but bypassing `prompt()`'s user_echo + overage-queue intercept — it is a server-internal control send). The CLI rotates its sessionId to a fresh UUID **in place** — same OS process/pid, old `<sid>.jsonl` preserved, a new `<newId>.jsonl` created — and emits a `system/init` carrying the new `session_id` (which `Instance`'s system/init handler folds into `this.backingSessionId` — **not** `this.sessionId`, which is pinned for the session's life; it also appends a `renew` segment to the session's lineage row, see [components/instances.md](../components/instances.md#srcsessionrenewts)) plus a `result` (turn_end). Nothing is carried: the session's facts (title, mode, backend, `conducted`) are keyed by its public id in `<store>/sessions.json`. The rotation write kicked by that `system/init` gives the new segment the old one's `persistent` flag and **archives** the old segment, so the preserved old `<sid>.jsonl` surfaces in the archived section rather than as a stale live row — and a `/clear` the user types gets the same write, with no renewal armed. Driven by `SessionRenewController` off the `renew_session` MCP tool — see [MCP tool protocol](mcp.md#mcp-tool-protocol) and [components/instances.md](../components/instances.md#srcsessionrenewts).

**Post-abort drain window.** The CLI's stdin queue is not cleared by an abort. Any `user` message written before it (a prompt sent mid-turn) remains queued; after the abort the CLI dequeues them and starts a spurious new turn for each. After every abort — forced, or an armed soft one firing — the orchestrator opens a drain window (`POST_ABORT_DRAIN_WINDOW_MS`, default 3 s) and watches for `system/init` events on the event channel (`Instance._openDrainWindow`). The `system/init` event arrives ~39 ms after the abort and ~3.7 s before any API round-trip, so the drain fires an immediate `control_request subtype:interrupt` to sever the spurious turn at zero token cost. Each drain resets the window deadline (sliding window). Calling `prompt()` closes the window so intentional follow-up prompts proceed normally — **before and after** its own send: the prompt's `user_echo` is itself a quiescence reset, so a stop armed earlier in that turn fires right there and opens a window that would otherwise sever the turn this prompt is starting. The drain emits a `system/drain_abort` event (kind `'system'`, subtype `'drain_abort'`, data `{count}`) visible in the conversation as "⏹ Drained queued turn after interrupt".

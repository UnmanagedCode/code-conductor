# Testing: the suite hang guard

The per-file watchdog, the process sweep, and how to reproduce CPU starvation.

## Suite hang guard

**The invariant: no test file may outlive its own report.** node:test emits a file's terminal `test:summary` **only when its child process exits**, so a file that finishes its tests but leaves the event loop open never reports and wedges `reporter.on('end')` in `tests/run.mjs` *forever*. That is not hypothetical: it has cost code-mutant's entire 300 s external ceiling for one leaked handle.

**The `timeout` option is not a defence.** `run({timeout})` reaches each child as `--test-timeout`, a **per-test** deadline on the test body's promise. It cancels the *test*, never the *process*. Measured shapes that it does not touch at all: a test that **passes** while leaking a handle; a test that **fails** before its cleanup line; a CPU busy-loop (the timer cannot run); an orphan grandchild holding inherited stdio after the child exits cleanly.

**`--test-force-exit` is a trap — do not add it.** It makes leaking children exit, but `process.exit()` in the child **truncates its pending report to the parent pipe**. Two whole-suite scans with it on disagreed by 31 tests; one silently emitted *nothing* for `tests/mcp-conductor-view.test.mjs` (~38 tests) while still printing `fail 0` and **exit 0**. A silent green is worse than a hang.

Three layers, all reading their deadlines from `tests/hangGuardConfig.mjs` so a guard can never protect a private copy of a number. Every deadline is env-overridable **only** so the `tests/hang-guard-*.test.mjs` suite can drive the real code path at millisecond scale:

| constant | env override | role |
|---|---|---|
| `FILE_KILL_MS` | `CC_TEST_FILE_KILL_MS` | parent: SIGKILL a per-file child that outlives it. Must stay **above** the per-test `timeout` in `run.mjs` so it cannot pre-empt a test node would still cancel and report. |
| `LEAK_GRACE_MS` | `CC_TEST_LEAK_GRACE_MS` | child: time from root-`after()` entry to declaring the loop leaked. |
| `ORPHAN_SWEEP_MS` | `CC_TEST_ORPHAN_SWEEP_MS` | parent: grace between every discovered file being *settled* and declaring the report stream stalled. `end` normally follows the last summary within ~4 ms, so this is nearly all margin; applied once, from the last file to settle. |
| `RUN_CAP_MS` | `CC_TEST_RUN_CAP_MS` | parent: absolute run ceiling. **Last-resort backstop only** — it makes an unbounded hang finite; the per-file deadlines above are what produce a timely verdict and what must fit inside an external harness's ceiling. Measured: a full run under 24-way CPU starvation (load ~30) takes **~157–170 s**, so a 240 s cap would leave only ~1.4× margin and go red on a merely-loaded box; the default is sized ~3.5× the starved figure. **The plan's stated property "below code-mutant's 300 s so we, not it, produce the verdict" is therefore NOT true of this constant and must not be re-asserted** — `harness/mutation/config.json`'s `timeoutMs` is 300 s. It is benign because the per-file deadlines (90 / 15 / 5 s) and the stream-stall check are what actually terminate a wedged run, all well inside 300 s. |

- **Layer B — `tests/handleLeakGuard.mjs`** (child side), preloaded into every per-file child via `execArgv: ['--import', …]` alongside the DOM tripwire. A `--import` preload evaluates before the test body, so its root `after()` hook is registered — and therefore runs — **first**, ahead of the file's own `after(() => ctx.close())`. It does not check anything there; it arms an **unref'd** `LEAK_GRACE_MS` timer. Clean file → the loop drains, the process exits, the timer never fires, zero happy-path cost (which is exactly why arming it ahead of the file's own teardown does not race that teardown). Leaking file → the timer gets a turn, which **is** the criterion; it writes the diagnostic with `fs.writeSync(2, …)` (synchronous, so it cannot be truncated the way `process.exit` truncates an async pipe write) and exits 1, which the parent surfaces as a file-level `test:fail`. Cost of a leak becomes `LEAK_GRACE_MS` instead of infinity.
- **Layer A — `tests/run.mjs`**: (1) a **completeness ledger** — every discovered file must emit its own `test:summary` (the per-file event carries `data.file`; the single run-level summary has `file === undefined`, which is how they are told apart). Anything discovered but never reported is **named and counted as a failure**, which closes the truncation class above whatever its cause. (2) A **per-file kill watchdog** mapping live direct children to the test file named as the **last** element of their argv, SIGKILLing the whole tree past `FILE_KILL_MS`. (3) A **stream-stall check** plus a **leaked-process sweep** (see below) on **four** triggers — stream stall, run cap, **normal run end**, and **SIGINT/SIGTERM**. The last two are: a leaked process only wedges the stream if it holds stdio inherited from the *runner*, and a plugin child holds pipes to the *test file's* child, so it wedged nothing and no trigger ever fired — measured, 21 orphans across 9 runs that all exited 0. (4) An **absolute run cap**. (5) An unconditional `hang-guard:` verdict line on green *and* red runs, carrying files-reported / killed / swept / stall / cap state and the slowest 5 files — the slowest figure is the standing evidence that `FILE_KILL_MS`'s margin is still real as the suite grows. Expect a **steep ranking with one culprit**, not a plateau; a flat top five means the metric regressed (see the next bullet). `FILE_KILL_MS` in `tests/hangGuardConfig.mjs` owns the measured figures, the margin trend across review rounds, and — the number that actually binds — the **broken-guard** cost; that comment is the reference, not this line, and the line also **says when `/proc` was unavailable**, because a blind watchdog reporting `0 killed` must not read as `clean`.
- **The verdict line's two events are different events, and the split is deliberate.**
  The **completeness ledger** is defined against `test:summary` (per-file carries `data.file`; the run-level one has `file === undefined`).
  The **per-file duration** comes from `test:complete`, filtered to the file-level test via `d.name === d.file`.
  They differ because per-file `test:summary` events are emitted in `files` order, so a file finishing ahead of an earlier-listed one has its summary **held** until that one reports — and a duration measured at summary time then charges it the earlier file's wall.
  Measured, same file, argv order swapped: `parser.test.mjs` reported 1172 ms vs 108 ms, and in the inflated case **ranked above** the file that actually spent the time.
  `test:complete` fires at real completion and is order-independent.
  It is preferred over `test:summary`'s own `duration_ms`, which is measured inside the child and so excludes spawn + import: dispatch→child-done keeps the figure comparable to `FILE_KILL_MS`, a process-lifetime deadline.
  Measured on a 16-core box at the default concurrency, `summary.duration_ms` runs **31–297 ms lower**, never higher, across 90 file observations — sampling **every 6th name of the sorted `tests/*.test.mjs` list (45 of 266 at the time), skipping the files that spawn nested runners of their own** — then two (`hang-guard`, `summary-attribution`), now six (the five `hang-guard-*` plus `summary-attribution`), so repeating this sample today skips six — in two runs (one idle, one under a concurrent mutation campaign) that agreed closely.
  **The range travels; the centre does not.**
  Median 219–234 ms / mean 179–181 ms describe *that* sample only: the excluded work *is* spawn + import, so the centre tracks the import weight of whichever files are picked — cheapest here ~31–35 ms, express+ws importers ~297 ms, and a lighter-weight subset of the suite medians near 87 ms.
  The earlier "consistently 25–50 ms" figure was ~5× low because it described only the cheapest files.
  `tests/summary-attribution.test.mjs` is the regression guard.
  It runs the real `tests/run.mjs` against fixtures under `tests/fixtures/attribution/` and asserts on the `hang-guard:` lines, covering three seams that fail against **different** wrong implementations — none is redundant.
  Test 1 overrides to **`TEST_CONCURRENCY=4`** (one slot per chained fixture — fewer deadlocks the chain, loudly); tests 2 and 3 keep the helper's default of 2:

| test | fixtures | fails against `test:summary` source | fails against last-**inner**-`test:complete` source | fails against a **whole-second** figure |
|---|---|---|---|---|
| charges each file its own wall | the four **chained** fixtures — `fast` 0 → `subsecond` +550 → `medium` +650 → `slow` +900 — argv **descending** (`slow, medium, subsecond, fast`), `slow` still **first** | yes — (1), (2) and (2b) all fire | no | yes — (5), unconditionally |
| a **killed** file keeps its figure and rank | `killed` (outlives `CC_TEST_FILE_KILL_MS=2000`), `fast` | yes — it emits no summary at all | yes — its one test never completes | no |
| post-test **teardown** is inside the figure | `teardown` (~1 ms test, ~900 ms root `after()`) | no | yes — reports ~29 ms instead of ~954 ms | no |

`subsecond` exists because its **+550 ms link is the smallest designed increment**, and therefore the resolution floor: assertion (2b) `sub - fast >= 550` is the only one that dies against a reporter which rounds away sub-second separations while preserving larger ones. Assertion (5) is `[slow, medium, sub, fast].some(ms => ms % 100 !== 0)` — a **lattice residue, carrying no load term at all**. It fires on any lattice whose quantum is a multiple of 100 ms (every figure becomes `≡ 0 (mod 100)`), which covers the whole-second, 500 ms and 100 ms cases — the last two being holes the superseded two-sided `0 < medium - subsecond < 1000` band provably let through. That band is **gone**: it was measured *outside* its own range (gap 1053 ms) on a **correct** reporter at load1 ~73, i.e. it was itself a machine-speed window. (4) `slow >= 2100` is a pure control — an absolute **lower** bound that load can only inflate. **Envelope, not totality:** a uniform rescale of every figure by a constant factor (e.g. ×1.5) passes every assertion here, violating no ordering, no designed separation and no resolution claim. A lattice whose quantum is **not** a multiple of 100 ms largely **escapes**: (5) fires only when *all four* figures happen to land on the 100 ms lattice, so a 50 ms quantum is caught with probability ~(1/2)^4 = **1 run in 16** — measured **0 kills in 16 runs**. State that as the escape it is; the residue's guarantee covers 100 ms-multiple quanta only.

Argv order and the concurrency are load-bearing: the ordering bug only fires for a file listed *after* one still running, and the **descending** argv order is what keeps the dequeue term non-negative. **NEVER A RATIO**, and that is the defect to avoid: a ratio between two wall figures *multiplies* the per-file spawn+import cost instead of cancelling it (`fast * 3 < medium` reduces to an absolute cap of `C < 600 ms`), and it went red 10/24 at 72-way on a correct reporter. Every bound is now a **difference against a designed chain increment** (1200 / 900 / 550), plus the one absolute **lower**-bound control; the fixture sleeps are no longer solved as a pair against a shared `C` budget, because no bound carries a `C` term. The threshold algebra that lived in the test's header is **deleted** — do not restore it, and do not reintroduce a ratio. See the ratio worked example in [testing.md](testing.md) for the construction and both campaigns' figures. It follows the same two rules as the hang-guard regression suite below — `*.fixture.mjs` naming and a **deleted `NODE_TEST_CONTEXT`** in the child env. Do not move the duration back onto the `test:summary` handler, and do not narrow it to the last inner `test:complete`.
- **Layer C is deliberately empty.** There is no periodic sweep of "files that leak"; the guard is structural, fires on any future leak with no per-file opt-in, and needs no rule for a test author to remember.

Three non-obvious mechanics:

- **`killTree(process.pid)` kills the runner.** `tests/procTree.mjs` therefore exposes `killDescendants()` (never touches the root) and `killPids()` refuses `process.pid` and pid ≤ 1. At the run cap, use `killDescendants` — an earlier revision turned a reportable timeout into a bare `exit 137` with no verdict at all.
- **A leaked process keeps the report stream open. It is identified EXACTLY, by a run marker — do not re-introduce a heuristic.** A grandchild is reparented to init the instant its parent dies, so no `/proc` walk from the runner reaches it; and if its file completed inside one 100 ms sampler tick it was never recorded either (measured: a 33 ms file's orphan survived an entire run and leaked onto the box). FD-INODE MATCHING was tried and refuted — node spawns child stdio over *socketpairs*, whose two ends have **different inodes**, so our `/proc/<pid>/fd` link never equals the orphan's. That refutes inode **equality** only; peer resolution does exist via netlink `UNIX_DIAG_PEER` and is merely out of scope. The full note, with the measurement, lives at `sweepOrphans` in `tests/run.mjs` — read it there rather than trusting a summary. So the design splits the two concerns:
  - **Termination is guaranteed without identifying anything.** A file is *settled* once it has reported, been killed, or lost its child without reporting. Once every discovered file is settled and the stream *still* has not ended, it can teach us nothing further, so the runner **abandons the wait**, prints `STREAM STALLED`, and fails the run. This needs no `/proc` at all. The trigger is deliberately **not** "this file failed to report": the measured orphan shape is a file whose child exits *cleanly with every test passing*, so its summary arrives — a `reported`-gated check switches itself off in exactly the case it exists for, and the run then falls through to the absolute cap.
  - **Killing uses an exact identity, not a heuristic.**
    `tests/run.mjs` exports a run-unique **`CC_TEST_RUN_ID`** (an `mkdtemp` basename) before any child forks, so every descendant inherits it and `processesWithMarker()` finds it by reading `/proc/<pid>/environ`.
    That reflects the environment as of *exec*, so it survives `setsid`/`detached: true` (which escapes the process group), survives reparenting to init, needs nothing to have been sampled beforehand, and cannot match a stranger, a system daemon, a shell-pipeline sibling, or a *different concurrent run* of this suite.
    It replaced a process-group + `ppid == 1` + start-time heuristic, which was **unsafe**: a process group is a job boundary only under interactive job control, and under `sh -c`, CI, or an agent harness — how this runner is actually executed — the runner inherits its parent's group, so the group spans unrelated work.
    **`PROJECTS_ROOT` is not usable as the marker**: `bootServer` reassigns it per server to a path outside the run root, so a grandchild spawned mid-test would not carry it (measured).
    Two best-effort sources remain alongside it (live descendants; pids recorded per file), but the marker covers everything they miss.
    A **standalone** `node tests/foo.test.mjs` gets its marker from `markRun()` in `tests/safeStoreRoot.mjs` (`??=`, so an inherited one is never replaced — overwriting it would drop that child out of its own run's sweep); without it a single-file run sets none, which is the one mode in which a leaked process has no identity at all.
    **The run-end sweep runs before `removeSafeRoot`**, and that order is pinned rather than commented: `run.mjs` re-reads its own marker between the two, so moving the sweep past teardown (which is what leaves a live process with a `(deleted)` cwd) prints `RESIDUAL` and fails the run.
    The check **holds** the invariant rather than only reporting it — anything it finds already matched this run's marker, so it is reaped through the same `killPids` path before the root goes, and the run still goes red.
    **A `/proc` snapshot is not evidence of liveness**: each candidate is re-verified **live** via `hasMarker`, because `processesWithMarker`'s `readdirSync('/proc')` samples the pid list microseconds after the sweep's kills, so a pid early in a ~2700-pid walk is read inside its own death window — observed once at load 25 as a false `RESIDUAL` with `SWEPT` naming the same pid.
    `RESIDUAL_SETTLE_MS` (`tests/hangGuardConfig.mjs`) then caps how long a genuinely-signalled process is given to die.
    It owns the measured figures, the reason it is *not* the fix, and the reason it is a **measurement-informed choice rather than a guarantee** — no fixed bound covers a process held in D-state sleep or under swap/cgroup throttling.
    What makes that acceptable is the failure *direction*: exceeding it produces a visible red on an otherwise-clean run, never a silent leak, with `CC_TEST_RESIDUAL_SETTLE_MS` as the escape hatch.
    **SIGKILL of the runner is uncoverable by construction** — no in-process handler runs — which is the standing reason `tests/reapOrphans.mjs` exists.
  - **The stall check is gated on node having finished** (`nodeFinished`, set by node's single run-level `test:summary`, the one with `file === undefined`). Without that gate it false-positives on a healthy run with a **slow stdout consumer**: the ledger settles from source-stream events at push time, while the wait is on the composed reporter, whose `end` is deferred by backpressure from `reporter.pipe(process.stdout)`. Measured with ~4 MB of output and a paused reader — gate removed: `STREAM STALLED`, a SIGKILL sweep and **exit 1 at 1.8 s on a green run**; gate present: exit 0. `node tests/run.mjs | less` is enough to trigger it and raising `ORPHAN_SWEEP_MS` cannot help, since a pager pause is unbounded. The run-level summary is the exact discriminator: emitted at push time on a healthy run (~44 ms), **never** emitted in a genuine wedge (absent through 5 s). Note the volume threshold is real — at ~200 KB the runner still finishes in ~120 ms behind a paused reader, because the OS pipe plus libuv's queue absorb it and the closing `process.exit()` discards the rest, so a smaller fixture would pass against the broken code.
  - Measured outcomes, against what the sweep exists to prevent — a leaked process holding the report stream open until the absolute cap (`RUN_CAP_MS`, `tests/hangGuardConfig.mjs`) fires: a sub-tick leak swept, run ends ~1.7 s; a **detached** leak swept (the marker reaches it), ~1.7 s; a live grandchild swept, ~3.2 s.
- **The run cap timer is deliberately REF'D** (and cleared in a `finally`, on both paths). An unref'd cap cannot fire once the loop has otherwise drained — the "all children gone but the stream never emitted `end`" case, where the runner would exit *naturally* with code 0 and skip the verdict. **Disclosed gap:** no test discriminates ref'd from unref'd. Making it unref'd leaves the whole suite green, because inducing that state requires the loop to drain while the stream is still pending, and every way of holding the stream open also holds a handle. `tests/hang-guard-run-cap.test.mjs` pins the cap's *observable* behaviour instead (it fires, fails the run, prints the verdict, bounds the wall time) with a child still alive — a state an unref'd timer would also fire in. Ref'd is kept because it costs nothing and the failure it guards is a silent green.
- **`LEAK_GRACE_MS` is the real per-file teardown deadline, not `FILE_KILL_MS`.** It is 6× tighter (15 s vs 90 s) and is armed at the *first* root `after()` hook — which, because a `--import` preload registers before the file's own hooks, is before the file's own teardown starts. A file whose teardown legitimately exceeds it is failed by Layer B as a leak and the 90 s figure never gets a say; under the ~2.7× starved slowdown a file with ~6 s of quiet-box teardown would cross it. If a file starts awaiting many child exits in teardown, raise `LEAK_GRACE_MS`, not `FILE_KILL_MS`.

**`process._getActiveHandles()` is a private Node API** (present through **v24.18.0**, the version all of this was measured against). Layer B uses it for the **diagnostic only** — never as the pass/fail criterion — and degrades to a clear "culprits UNAVAILABLE" note if it is ever absent, because a guard whose own failure mode is a crash would just be a new hang class. The culprit filter is `_getActiveHandles()` minus stdio, kept only where `hasRef()` is true; note `hasRef` lives on the internal `_handle`, not the JS wrapper. Ref-awareness is what makes it usable: a naive `process.getActiveResourcesInfo()` check flags **207 of 267** files (unref'd timers, in-flight `FSReqCallback`s).

**Two different probes, two different numbers — keep both, because collapsing them deletes the fact that would re-open the Layer C decision.** The plan measured **12 of 267** files holding a ref'd handle *at the moment of child exit*, and that number was the entire justification for planning a 12-file sweep. Layer B asks a different question: *is the loop still open `LEAK_GRACE_MS` after teardown began?* By that predicate **0 of 273** files leak, measured 2026-08-24. **The census lineage, because 268 + 4 ≠ 273 and the gap is real, not an error:** 267 at the at-exit probe → **268** when the hang-guard test file was added → **269** after an unrelated change added a file → **273** once that one file was split into the five `tests/hang-guard-*.test.mjs`. Anchor any re-count to a dated re-run and the named changes above, not to the arithmetic. Layer B is preloaded into every per-file child, so a green whole-suite run *is* this probe. A re-run of the plan's own at-exit probe now flags **1** (a `Socket`). Both results are true: a handle that is closing *during* teardown is real at the exit snapshot and never wedged anything. Layer B's is the operationally meaningful one, which is why the sweep was dropped — see "Layer C is deliberately empty" above.

**Two refuted mechanisms, recorded because the obvious intuition is wrong both times.** (1) **`_getActiveHandles()` does not report timers at all** in v24 — a ref'd `setTimeout` keeps the process alive while being completely invisible to it. Layer B still catches a leaked timer, but via *the loop still being open* (the grace timer firing), not via the handle list; so an empty culprit list plus a live loop is reported as **either** a leaked ref'd timer **or** teardown work still in flight — pending fs ops and awaited child exits are *requests*, not handles, so they are equally invisible, and "await the child's actual exit in teardown" is a pattern this very document recommends. The guard does not assert which; only the loop-still-open criterion is certain. (2) Consequently **Layer B cannot pin "an idle heartbeat was cleared"** — and `src/idleSubscriptions.ts` `.unref()`s that interval anyway, so an uncleared one holds nothing open. Do not "restore" a coupling between `tests/idle-wake-interval.test.mjs`'s `timeoutMs` tests and the leak guard; see the honest-pinning comments at those sites.

**Writing a test so it cannot leak.** Release every fixture on the **fail** path too — `try/finally` or `afterEach`, never a cleanup line trailing the assertions (that is the exact leaked-timer shape). For a happy-dom `Window`, `window.happyDOM.abort()`; for a spawned child, await its actual exit.

**Register the teardown AT SPAWN TIME, not after the helper returns**. A `try/finally` in the caller cannot cover a helper that spawns and *then* awaits readiness: the handle does not reach the caller until after the wait, so a timeout there leaks a child the `finally` never learns about. `startAndSettle` in `tests/plugins-supervisor.test.mjs` is the pattern — `t.after(...)` on the line after `sup.start(...)`, before anything that can throw.

**A teardown that signals needs a LICENCE, and identity is the only safe one.** Once teardown is unconditional it also runs for tests using a fake/injected `spawn`, whose stand-in children carry synthetic pids (`900001 + n`) — and `sup.stop` signals a process *group*, so an unguarded hook calls `process.kill(-900001, …)`. The hazard is the **wrap**, not any one census: `pid_max` here is 4194304 and allocation has long since passed the synthetic band, so a literal `900001` is a *real* pid — an unrelated live process sat at **1089935** while this was written (2026-08-25; the live ceiling moved 3.99M → 4.10M over that interval, which is why the figure is dated and the property is what you should rely on). So that group belongs to a stranger. Guard with **`hasMarker(pid, marker)`** (`tests/procTree.mjs`) — `processesWithMarker`'s identity asked about one pid, failing closed on a vanished or unreadable `environ` — never a caller-supplied "this one is fake" flag, which relocates kill authority to the caller instead of closing the class. Match by identity only: **never** by name, process group, ppid, or start time.

**Regression suite:** five files — `tests/hang-guard-file-kill.test.mjs`, `-run-cap`, `-layer-b`, `-sweep`, `-stall` — over a shared harness in `tests/hangGuardCase.mjs` (`RUNNER`, `fixture()`, the squeezed deadlines, `FAST`, `redactTotals()`, `runGuard()`; not named `*.test.mjs`, so `discover()` ignores it). Each runs the **real** `tests/run.mjs` as a subprocess against `tests/fixtures/hang/*.fixture.mjs`, with the deadlines squeezed via the `CC_TEST_*` overrides. `runGuard(name | name[], env, opts)` takes one fixture or several for one inner run, and **always pins `CC_TEST_VERBOSE` in the child env** — `'0'` unless `verbose: true` — so an exported `CC_TEST_VERBOSE=1` cannot flip a case asserting the quiet reporter's output. Two kinds of case need `verbose: true`, because the quiet reporter holds a passing file's output back: the slow-consumer case in `tests/hang-guard-run-cap.test.mjs` (its backpressure is `chatty.fixture.mjs`'s volume reaching stdout) and both interrupt legs in `tests/hang-guard-sweep.test.mjs` (their `signalWhen` rendezvous needs `HOLDER_LINE` while the file still dwells). `runGuard` refuses `signalWhen` without `verbose` by throwing (`…which the quiet reporter holds back for a passing file — pass verbose: true`), pinned by `runGuard refuses signalWhen without verbose`.

**A fixture's diagnostics reach `runGuard` on the runner's STDOUT — never on its stderr — including a raw `writeSync(2, …)`.**
`node:test` captures the per-file child's stderr, relays it as a `test:stderr` event, and `tests/run.mjs`'s `spec` reporter writes it out through `reporter.pipe(process.stdout)` in `tests/run.mjs`.
Choosing fd 2 over `console.log` in a fixture buys freedom from in-child reporter reformatting, **not** a different outer stream (measured 5/5 with `silent-orphan.fixture.mjs`).
Whether it arrives *at all* is the quiet reporter's call: under `verbose`, for a failing file, or inside a `quiet-reporter:` dump (see Testing → "`tests/run.mjs` is quiet by default").
`runGuard` drains both pipes into one `out`, so a case that only *reads* the text is unaffected; anything that *hooks* a stream is not — which is why the interrupt legs' `signalWhen` rendezvous is called from both `data` handlers, a stderr-only hook having silently never fired.
The **stderr** call is consequently unexercised today — deleting it alone leaves the suite green — and is deliberately kept rather than pruned as dead code, because `run.mjs`'s *own* `hang-guard:` output is split across both handlers and **the writer call is what decides which**.
Its `console.error` diagnostics land on the stderr handler (the SIGINT/SIGTERM banners, `SWEPT` under every trigger, `STREAM STALLED`, `NO REPORT`), so a case rendezvousing on one of those needs that call and nothing else; its `console.log` diagnostics land on the stdout handler instead — the verdict line (grep `tests/run.mjs` for `files reported,`), the `/proc` WARNING (`WARNING — /proc was unavailable`), `slowest files` (`slowest files (limit`).
**The rule now has a standing test:** `the discarded-stdout shape carries stderr diagnostics and drops stdout ones` in `tests/hang-guard-run-cap.test.mjs` runs that file's `discardStdout` shape against `detached-orphan` and asserts `STREAM STALLED` and `SWEPT` *arrive* while the `console.log` verdict line does not — the non-vacuity pin for the slow-consumer case below it, which asserts the ABSENCE of the same two patterns (shared `STALL`/`SWEPT` consts) against a stderr-only accumulator.
What moving a writer to `console.log` destroys is diagnostic honesty plus the narrow "printed but not punished" discrimination, **not** detection: that case still reds on its `code === 0` assertion, since `run.mjs` does `failed++` on both `streamStalled` and `sweptOrphans > 0`.
"Capture stdout instead of discarding it" was measured and refused — with the 4000 ms pause in place and no discard the accumulator is *still* empty, because a failing run's `close` fires at ~1.8 s before the consumer ever resumes.
Check the writer for the pattern you are matching rather than assuming a stream: `writeSync` appears nowhere in `run.mjs`, and assuming stderr is the original silent-no-signal failure.

**Why five files and not one**: each case's cost is its squeezed **deadline**, not work, so a single serial file was charged the *sum* of every case's deadline and five files are charged the *max*. Measured before → after: **30 183 ms → 8 493 ms quiet**, **35 299 ms → 9 369 ms starved**; with a guard deliberately regressed, **47 408 ms → 24 720 ms** worst file (1.90x → 3.64x against `FILE_KILL_MS`). Files rather than in-file concurrency, because `FILE_KILL_MS` is a *per-file process* deadline: a truncating SIGKILL now costs one file's diagnostics instead of all sixteen cases', which is the property the suite exists for. Concurrent nested runners cannot cross-kill because each `tests/run.mjs` overwrites `CC_TEST_RUN_ID` with its own `mkdtemp` basename before any fork and `processesWithMarker` anchors on a **NUL-terminated** needle — verified live: six distinct markers across simultaneously-running nested runners, and serial-vs-concurrent per-case outcomes identical over three rounds. Fixtures are named `*.fixture.mjs` so `discover()` (which globs `*.test.mjs`) never picks them up in a normal run — several hang by design — while an explicit argv path still runs them. **`NODE_TEST_CONTEXT` must be deleted from the child env**: a nested `run()` that sees it prints `run() is being called recursively within a test file` and silently runs *nothing*. Verified against the **pre-fix tree — before the five-file split landed** (2026-08-20): `leak-on-pass`, `leak-on-fail`, `busyloop` and `orphan-grandchild` all hang **forever** pre-fix, and `exit-before-report` exits **0** silently; only the `clean` control passes both ways.

**Reaping what the sweeps cannot (`tests/reapOrphans.mjs`).** A run SIGKILLed outright runs no
handler, so its children survive; and orphans predating the run-id marker are a fixed historical
residue. This is the one-off tool for both. **Not wired into `npm test`** — reaping is implicitly
destructive and nothing new accumulates once the sweeps are in place.

```
node tests/reapOrphans.mjs --dry-run                # print pid / marker / cmdline, kill nothing
node tests/reapOrphans.mjs                          # reap
node tests/reapOrphans.mjs --id cc-testrun-XXXXXX   # a SIGKILLed run, whose root still exists
```

`staleRunTargets(snap, rootExists)` is pure over its snapshot and its oracle. A pid is licensed iff
**all** hold: `snap.available` (a partial `/proc` read yields *nothing*, never everything); `pid > 1`
and not `process.pid`; its `environ` carries a both-ends-anchored `CC_TEST_RUN_ID` entry (`MARKER_RE`
in `tests/procTree.mjs` — one home for the anchoring); the captured id matches `RUN_ROOT_SHAPE`
(exported from `tests/safeStoreRoot.mjs`, not re-declared); and **`!rootExists(id)`** — the owning run
reached `removeSafeRoot`, so it is *provably* over. That last conjunct is what makes the tool safe to
run while a suite is in progress. `--id` swaps the oracle for `marker !== id`, so naming a run
narrows the list and a typo selects nothing. Kills go through `killPids`, which re-verifies each
pid's starttime identity immediately before signalling.

**`pkill -f 'node server.mjs'` is NOT safe as routine cleanup**, though it works as a one-off. A
*name* match hits the live children a running suite spawned — manufacturing failures that read as
real reds — and unrelated apps on a shared box. It is also what destroyed the `server.mjs` family's
evidence.

Stale `/tmp/cc-testrun-*` **directories** are closed by teardown, not by a reaper. `createSafeRoot()`
records every root it mints in a private set in `tests/safeStoreRoot.mjs`; `removeSafeRoot()` removes
one on `tests/run.mjs`'s normal completion path, and a `process.on('exit')` backstop removes whatever
is still registered on every other exit (`process.exit(128+signo)` from the signal handler, the
store-isolation `exit(1)`, an uncaught throw, or a standalone file run that never had a removal at
all). The ownership rule: **mint ⇒ own ⇒ remove at exit; inherit ⇒ never remove** — registration
lives in `createSafeRoot()`, not `ensureSafeStoreEnv()`, so a root taken from the inherited branch
can never enter the set, and a test file under `run.mjs` can never delete the whole run's store from
under its siblings. The property — a standalone run of any test file, and a full suite run, each leave
no `/tmp/cc-testrun-*` root behind — is pinned by tests in `tests/safeStoreRoot.test.mjs`, which also
pin the inherited-root case, the deletion gate, and the backstop edges below. The gate
(`_forTesting.validateRootForDeletion`) is a second check on a path already drawn from the set, never
a selector: it refuses a symlink *pointing at* a valid run root, which `assertSafeTestRunRoot` alone
would realpath into acceptance; it refuses a temp dir of the wrong shape; and because `lstat` runs
before the shape gate it reports an already-removed root as `ENOENT` — the one error class the
backstop can read as "already gone" — which the backstop then consumes silently rather than reporting
a cleanup failure for work the normal path already did. The ordering inside `removeSafeRoot` is
likewise pinned: the registry entry is dropped only after `rmrf` resolves, so a removal that FAILS
leaves the root registered for the backstop to retry. Reversed, the registry empties while the root is
still on disk and the backstop's emptiness guard returns early — a silent leak. The test induces that
failure with a `chmod` (a deterministic `EACCES`, not a class `fs.rm` retries) and so is uid-dependent:
it skips as root, where a `chmod` would not constrain removal, rather than passing vacuously.

**No directory reaper exists, and one cannot be made safe.** The oracle it would need does not exist:
`/proc/<pid>/environ` is the environment *as of exec*, and `tests/run.mjs` sets `CC_TEST_RUN_ID` after
its own exec — so the process that **owns** a run root is invisible to `processesWithMarker`, and only
its children carry the marker. A reaper keyed on "no live process carries this marker ⇒ orphaned" —
the dual of `staleRunTargets`' licence — would therefore delete a **live** run's root during any
moment no marked child happens to be running. The only other available oracle is mtime age — the
name-plus-age heuristic this suite deliberately does not carry. So `reapOrphans.mjs` stays
process-only. SIGKILL remains uncovered (no in-process handler runs), which leaks a throwaway
directory only.

## Reproducing CPU starvation

Several deadlines and flake rates in this repo are quoted "under 24-way CPU starvation"
(`FILE_KILL_MS` in `tests/hangGuardConfig.mjs`; `tests/summary-attribution.test.mjs`,
`tests/renew-session.test.mjs`, the `tests/idle-wake-*.test.mjs` family). This is how that condition is
produced. Use the **self-limiting** form:

```bash
N=24; SECS=600          # 24 = the DEFAULT width; the attribution figures are at 72 — see below
for i in $(seq $N); do timeout --signal=KILL "$SECS" sh -c 'while :; do :; done' & done
trap 'kill $(jobs -p) 2>/dev/null' EXIT INT TERM
wait
```

- **`timeout --signal=KILL` is the load-bearing half.** The `trap` dies with the shell; `timeout`
  does not. A worker killed mid-campaign cannot leave 100%-CPU spinners behind, which a bare
  `trap`-only version does — and a leaked spinner is far more expensive than a leaked idle timer.
- **The agent shell here is zsh, where bare `kill $pids` silently leaks spinners.** When killing by
  hand rather than letting `timeout` do it, use `xargs` with an anchored `pgrep`.
- **`N` is a starvation WIDTH, not a core count.** `FILE_KILL_MS` (`tests/hangGuardConfig.mjs`)
  and the test comments above are quoted at **24-way**, which is why the example is 24;
  `tests/summary-attribution.test.mjs`'s figures are quoted at **72-way**. A run at a different `N` is a
  different measurement and must say which. (Do not confuse this with the *8-core* / *16-core* device figures elsewhere in this
  section: those are hardware, not induced load.)
- `SECS` bounds the whole campaign, and is what makes the recipe self-limiting.
- **A 24-way pass does not clear a load-correlated flake.** 24-way is the default width, not the
  top of the range a defect can live in.
  `tests/summary-attribution.test.mjs` was measured **2026-08-26** on a 16-core host (dated to the
  day, not pinned to a build): **0/30 red at 24-way (load1 19.5–25.0)** and **10/24 red at 72-way
  (load1 72.8–74.4)**, with **0 orphans either side of every campaign**. Quote the width with the
  result, and when a reported reproduction was at a wider N, verify at that N — not at 24.
- **The quantity that scales is per-file spawn+import cost `C`** (fork+exec+node boot+import, which
  `run.mjs`'s `done - dequeue` figure includes). Measured maxima: **`C` ≈ 320 ms at 24-way** vs
  **`C` ≈ 770 ms at 72-way** — ~2.4–3.2x. Any test bound that tolerates `C` must be re-checked
  against the 72-way envelope, not the 24-way one.

## Plugin system

Building a plugin's UI (the host contract, security advisories, an optional reference setup): [docs/plugin-ui.md](plugin-ui.md).

### Manifest — `conductor.plugin.json` at the plugin project root

```jsonc
{
  "id": "code-hub",             // REQUIRED ^[a-z][a-z0-9-]*$ ≤40 chars, unique across all projects
  "name": "Code Hub",           // REQUIRED display name
  "version": "0.3.0",           // REQUIRED informational
  "pluginApi": 1,               // REQUIRED int; conductor supports [1], anything else ⇒ state "incompatible"
  "backend": {                  // OPTIONAL (manifest-only/library plugins omit)
    "start": "npm start",       // bash -lc, cwd = active checkout, $PORT injected
    "healthPath": "/api/health",// optional readiness probe + on-demand liveness probe
    "readyWhen": "listening"    // optional stdout/stderr regex (precedence: readyWhen → healthPath → TCP)
  },
  "frontend": {                 // OPTIONAL, requires backend
    "path": "/",                // default "/"
    "navLabel": "Hub",          // default = name
    "keepAlive": false          // default false; true ⇒ the page keeps running after the user leaves the view — see "Frontend keep-alive"
  },
  "mcp": {                      // OPTIONAL, requires backend
    "endpoint": "/api/mcp",     // single POST endpoint on the child
    "scope": "project",         // TOLERATED AND DROPPED — accepted only because code-hub's shipped
                                //   manifest declares it; the value is read nowhere, not normalized,
                                //   and not enum-checked. Tools are always globally visible.
    "timeoutMs": 30000,         // per-call cap, clamped to `MCP_TIMEOUT_CAP` (`src/plugins/manifest.ts`)
    "tools": [{ "name": "...", "description": "...", "inputSchema": { "type": "object", ... } }]
  },
  "conventions": [              // OPTIONAL, NO backend required — project conventions
    { "slug": "visual-verification",           // ^[a-z][a-z0-9-]*$ ≤40, unique in this array
      "name": "Visual UX verification",        // REQUIRED
      "description": "verify UX via the harness", // REQUIRED
      "scope": "project",                      // REQUIRED enum — "project" or "conductor" accepted ("workspace" planned; see below)
      "file": "conventions/visual-verification.md", // OPTIONAL CLAUDE.md fragment: relative .md path, no leading '/' or '..'
      "scaffold": {             // OPTIONAL facet (plugin-only) — a one-time project-setup directive
        "file": "scaffold/harness.md" }        // EXACTLY ONE of "text" | "file" (same path rules as conventions.file)
      // "scaffold": { "text": "Build a project-local harness wrapper ..." }  // inline form
      // At least one of "file" | "scaffold" is REQUIRED.
    }
  ],
  "roles": [                    // OPTIONAL, NO backend required — plugin-owned roles
    { "slug": "release-captain",             // ^[a-z][a-z0-9-]*$ ≤40, unique in this array
      "name": "Release Captain",             // REQUIRED display label
      "binding": { "kind": "tier", "tier": "powerful" } }  // REQUIRED: {kind:'tier',tier} | {backend:'claude',model}
                                             //   (legacy {kind:'claude',model} still accepted)
  ],
  "playbooks": [                // OPTIONAL, NO backend required — playbook graphs
    { "slug": "release",                     // ^[a-z][a-z0-9-]*$ ≤40, unique in this array; MUST equal the body's own `id`
      "file": "playbooks/release.json" }     // REQUIRED: relative .json path, no leading '/' or '..'
                                             //   (no name/description here — the body owns them)
  ],
  "claudePlugin": "claude"      // OPTIONAL string, NO backend required — Claude Code plugin root
                                // (relative path, no leading '/' or '..'; "." = the cc plugin root itself)
}
```

`conventions` is an **active pluginApi:1 capability** (an additive extension of v1, not a version bump — an existing manifest without it stays valid). It works with **no backend**, so a contributions-only plugin is `{id,name,version,pluginApi,conventions}`: it validates, enables, contributes, and is **never started** (its Settings row shows only Disable + contribution badges; `POST .../start` refuses 400). Entries join the project **Conventions** catalog namespaced `<plugin-id>/<slug>` (visible in the new-project dialog + `list_project_conventions`). Each entry carries a CLAUDE.md **`file`** fragment (applied inline to a project's CLAUDE.md at creation — the applied copy survives plugin disable/uninstall) and/or a **`scaffold`** facet (a one-time setup directive via exactly one of `text` | `file`; **plugin-only** — builtin/custom conventions are fragment-only); **at least one of `file`/`scaffold` is required**. A scaffold-bearing entry surfaces `hasScaffold:true` in `list_project_conventions`. Bodies for `file` refs (fragment and scaffold) are resolved against the active checkout; a **missing/stale `file` at manifest load makes the plugin `invalid`** (fail loud). Only **enabled + `ok`** plugins contribute — a disabled/crashed plugin never surfaces its conventions.

**`roles` (active pluginApi:1 capability, no backend).** A plugin can contribute **roles** — a role is a *named model-binding indirection* (parity with the built-in roles in `ROLES`: it carries only a `slug`, a display `name`, and a `binding`, **no** persona/system-prompt). Each entry's `binding` is a tier reference `{kind:"tier",tier}` (a known capability tier) or `{backend:"claude",model}` (a known Claude version id) — it may name **only** the identity `claude` backend, since every other registry row is user-local (its rows and models exist only in that user's settings). **Back-compat:** the pre-registry shape `{kind:"claude",model}` is still **accepted and translated** to `{backend:"claude",model}` on read, so an existing manifest needs no edit; `{kind:"<anything else>",model}` is refused exactly as before. See [models.md](models.md). Entries join the merged role list namespaced **`<plugin-id>/<slug>`** and are resolvable anywhere built-in roles are: MCP `spawn_instance`'s `model` arg, and **user-rebindable** in **Settings → Models → Roles** (a "via `<plugin>`" badge; the manifest binding is the **default** — a per-role **override** is persisted under `models.roleBackend` keyed by the namespaced id and takes precedence at spawn, beating the manifest binding; re-selecting the manifest's tier/model in the picker reverts it). Roles are **not deletable** (plugin-manifest-controlled). The manifest binding is **live-derived from enabled + `ok` plugins** (never persisted) via `pluginHost.roles()` — a **synchronous** accessor, unlike `conventions()`, because a binding has no fragment file to resolve — so **disabling or removing the plugin drops its roles automatically** (no purge — a stored override is retained and re-applies on re-enable, and an override to a since-removed model silently falls back to the manifest binding at spawn). A binding that names a since-removed tier/model makes the plugin `invalid` at manifest load (fail loud). Additive, no migration: an existing manifest without `roles` stays valid.

**`playbooks` (active pluginApi:1 capability, no backend).** A plugin can contribute **playbook graphs** — the same stage-graph definitions as the built-ins and the `<store>/playbooks/` overlay ([protocol.md](protocol.md#playbooks)), governed by the same gate, ledger and read tools.
- **Shape:** `playbooks: [{slug, file}]` and nothing else per entry (`unknown key 'playbooks[i].x'` otherwise). `slug` is a slug, unique in the array (`duplicate playbook slug 'x'` → `invalid`). `file` follows the convention-`file` path rules with a **`.json`** extension (`'playbooks[i].file' must end with '.json'`).
- **Id:** listed as **`<plugin-id>/<slug>`** (`list_playbooks` entries carry `plugin: "<plugin-id>"`). The body's own `id` must equal the **bare** slug — a mismatch is rejected as `id '<x>' does not match its manifest slug '<slug>'`.
- **The `/` invariant:** built-in and overlay ids are slugs, which cannot contain `/`, so a plugin playbook can never collide with (or be shadowed by) one, and plugin ids are unique across plugins (registry `conflict` state). The same `/` is how an id is attributed to its plugin once that plugin is gone (`pluginIdOfPlaybook`, `src/playbooks.ts`).
- **Read at manifest load**, through the project's System, and held on the manifest (`readManifest`, `src/plugins/manifest.ts`). A missing file makes the plugin **`invalid`** (`playbooks '<slug>' file '<file>' not found`; any other read failure → `… unreadable: <msg>`).
- **Graph validated by the shared loader** (`loadPlaybooks`, `src/playbooks.ts`), not at manifest load: bad JSON or a bad graph rejects **only that playbook**, reported in `list_playbooks` → `errors` keyed by the namespaced id; the plugin stays `ok` and its other contributions keep working. A throwing plugin host costs only plugin playbooks, reported as one `{id:"plugins"}` error.
- **Freshness equals roles':** a body refreshes only when the plugin's held manifest is replaced. **Rescan**, **Library Update** and a server restart re-read the *discovered* checkout (the main clone, or the worktree fallback when main has no manifest). A **backend start** (`doStart`) re-reads the *active version's* checkout. **An active-version switch re-reads nothing on its own**: `setActiveVersion` validates the target manifest and discards it, so it refreshes only when it restarts a backend that was `ready`/`starting`. A stopped, crashed or failed backend, or a backendless plugin, keeps its bodies until the next Rescan or start. **Enable does not re-read.**
- **Live-derived from enabled + `ok` plugins** via `pluginHost.playbooks()` — **async, and awaits discovery**, so a governed call or resume at boot cannot see an empty set.
- **Disable/removal drops the playbook** under the existing drift rule: a worker bound to it is refused `PLAYBOOK_UNKNOWN` (governed calls under `enforce`; `warn` proceeds) and on `spawn_instance({resume})`; the targeted `playbook_state` meets the same refusal under `enforce`, and elsewhere (under `warn`, or for an ungoverned caller) reports `playbookMissing` with a `reason`. Every such reason names the owning plugin and, without asserting a cause it cannot see, routes the reader to `list_playbooks` → `errors`: a `plugins` entry means the plugin host is unavailable, an entry under the playbook's id means an invalid body, and with neither the plugin is disabled (re-enable restores it), removed, no longer declares it, or its manifest is invalid as a whole — e.g. a playbook file deleted before a Rescan, or a bad role binding; the plugin stays enabled but `invalid`, the errors are on its Settings → Plugins row (`GET /api/plugins` → `errors`), and enable refuses 409 until it is fixed (`missingPlaybookCause`, `src/playbooks.ts`). The ledger binding is untouched, so **re-enabling restores governance on the same session with no repair**. Disable is never blocked.
- **Preferred playbook:** a plugin playbook can be chosen in Settings → Conventions → Conductor only while loaded; the choice is **retained through a disable** and applies again on re-enable (`defaultPlaybookMissing` in the Settings payload meanwhile).
- **Model pins:** a stage `pin` naming a role is resolved only at spawn. Pinning the plugin's own role works; pinning another plugin's role while that plugin is disabled leaves the playbook listed, and the spawn fails with `spawn_instance`'s `unknown model '<role>'` error.
- The conductor's role doc lists plugin playbooks from its next spawn/resume (Known limitations → "Already-running sessions are not reached"); the MCP tools see them on the next call.
- **Authoring overlay playbooks from a plugin** (a GUI editor) is a different path from contributing them: see [Authoring playbooks from a plugin](#authoring-playbooks-from-a-plugin).

**`claudePlugin` (active pluginApi:1 capability, no backend).** OPTIONAL string — a path **relative to the cc plugin root** pointing at a **Claude Code plugin root** (a dir directly containing `.claude-plugin/plugin.json`; skills resolve at `<root>/skills/<name>/SKILL.md`). `"claude"`, `"adapters/x"`, or `"."` (the cc plugin root itself) — the author picks the dir. **Shape-validated at manifest load** (relative, no leading `/`, no `..`, not absolute; a bad shape marks the plugin `invalid`). At **every** claude launch — interactive sessions and MCP-spawned workers alike — each **enabled + `ok`** plugin declaring `claudePlugin` contributes one repeatable **`--plugin-dir <resolved-root>`** flag (session-local; `src/instances.ts` `Instance.spawn()`, resolved via `pluginHost.claudePluginDirs()`). **Existence is validated at launch/resolve time, not load:** if `{resolved}/.claude-plugin/plugin.json` is missing/unreadable the flag is **dropped with a loud `console.warn`** (never silently, and the session still launches) — it does **not** invalidate the plugin. Absent field → no flag. **A plugin whose PROJECT is on a non-`local` system contributes no flag at all** (`PLUGIN_DIR_LOCAL_ONLY`): `--plugin-dir` takes an absolute LOCAL directory, and passing the remote path through would load whatever sits at that path on cc's own machine into every session. Additive, no migration. Resolved+frozen per session at create (mirrors the MCP-config wiring), so a plugin enabled mid-session is picked up on the next spawn, not a bare respawn. Kept a **string** for now; the single accessor `claudePluginPaths(manifest)` (`src/plugins/manifest.ts`) makes widening to `string | string[]` a non-breaking change.

**Frontend keep-alive (`frontend.keepAlive`).** OPTIONAL boolean, default `false`; any other type (`"true"`, `1`, `null`) pushes `'frontend.keepAlive' must be a boolean` and marks the plugin `invalid`. It rides the row as **`frontendKeepAlive`** (a store-only row, whose manifest is `null`, reads `false`); `pluginFrames` (`web/src/features/views/plugins.ts`) reads it off the `GET /api/plugins/:id/status` it already makes before every first load.

- **Without it** the plugin loads into the one shared frame (`iframe[data-plugin-frame="shared"]`): leaving the view or switching to a keep-alive plugin removes the frame, and switching to another plain plugin replaces it with a fresh one; either way the page ends.
- **With it** the plugin gets its **own resident frame** (`iframe[data-plugin-frame="resident"][data-plugin-id=<id>]`), created on first show — an unvisited keep-alive plugin costs nothing. Every exit (hash leaving `#plugin/`, a Settings / session / other-view supersede, the switcher's Conductor entry, and on desktop opening a non-session view while a plugin is docked in split) only hides it with the section; a switch to another plugin hides it too. It is never moved in the DOM, which would reload it.
- **Re-entry** reveals the same page: no `POST /start`, no `src` change. At subpath `/` — what the switcher writes — or at the frame's own tracked route, the frame keeps its route, no `navigate` is posted, and the hash is `replaceState`d to `#plugin/<id><its route>` (in the desktop dock's split, the dock's saved subpath takes that route instead and the URL stays on the session); only a subpath that is neither is sent as a bridge `navigate`. A hidden frame's `route` messages update its tracked route but never the URL.
- **Eviction** (the frame is removed, ending its page — media tracks, sockets, timers) happens in two cases:
  - the row stops passing `keepsResident` in `web/src/features/views/plugins.ts`: disabled, keep-alive dropped, a state outside its allowlist (`stopped`, `invalid`, …), or the status route answering 404. Checked in the background on every re-entry (the reveal never waits on it) and by `reconcile()` after every Settings → Plugins action (`PluginView.tsx` on `pluginsChangedSignal`). Only a 404 evicts on a failed read: a network error, a 5xx, or a 200 whose body does not parse keeps the frame.
  - a Settings → Plugins action in this tab put new code under the plugin — one of `EVICTING_ACTIONS` in `web/src/features/views/plugins.ts`: **Restart**, **Update** (every plugin in the updated project) and a **version switch**. `web/src/features/settings/PluginsSection.tsx` reports the action as `notifyPluginsChanged({action, ids})` (`web/src/features/settings/pluginsSignal.ts`), which `web/src/features/views/PluginView.tsx` passes to `reconcile(change)` unchanged.

  After `reconcile()` evicts a frame, the plugin loads the plain way (auto-start, error overlay + Retry) at once only when the frame was on screen and the eviction is the second case: the view reloads in place at the subpath the frame was on. A frame evicted for its row (the first case) is not started again, even on screen; the next entry loads it. The re-entry check runs as the user enters, so it loads the plugin the plain way at once.
- **Kept:** a backend crash and the lazy restart the page's own proxied requests trigger leave the page up — it must cope with its backend coming back (compliance checklist).
- **Visible in the host UI:** the app switcher labels a plugin whose frame is resident `<navLabel> (running)` (`RESIDENT_SUFFIX` in `web/src/features/views/plugins.ts`, appended by `web/src/features/views/AppSwitcher.tsx`), from first show until eviction.
- **Measured** by `keepAliveFlow` in `web/e2e/plugin-host.shared.ts`, run on the desktop and phone projects by `web/e2e/plugin-host.spec.ts` and on the android project by `web/e2e/plugin-host.android.spec.ts` (Chromium with Playwright's default launch flags plus `--use-fake-device-for-media-stream` and `--use-fake-ui-for-media-stream`; one visible top-level tab). With the plugin view hidden and taking no space, behind Settings and behind Conductor, a hidden keep-alive page's timers, WebSocket messages and microphone (track `live`, `AudioContext` `running` with its clock advancing, non-zero samples) are polled until they have moved on; each return shows the same page load; the switcher marks the plugin while resident; and a plugin without `keepAlive` reloads on the same round trip. Playwright's default flags include `--disable-background-timer-throttling`, `--disable-renderer-backgrounding` and `--disable-backgrounding-occluded-windows`, so the measurement says nothing about Chrome's default throttling policy. Not measured: a backgrounded tab (the whole page hidden) and mobile Chrome.
- **Security.** The capability is not widened: a plugin frontend is a same-origin, unsandboxed iframe that can already script `window.parent`, and code it plants there already outlives the frame's removal. What is widened, for opted-in plugins only, is how long a page runs **openly** after the user leaves — including a **microphone left open with no plugin UI on screen**; the switcher label and the browser's own recording indicator are the cues. Accepted under the operator-installed, trusted-plugin stance.
- **Limitations.**
  - Nothing pushes plugin state to the browser, so a Stop / Disable / Rescan made from another tab or over REST reaches a hidden frame only at its next re-entry or the next Settings → Plugins action in this tab. A Restart, Update or version switch made anywhere but this tab's Settings → Plugins does not evict at all: its row reads like a lazy restart's.
  - Uninstalling (deleting the plugin's project) evicts only after the next Rescan, since the row does not change until then.
  - A cc server restart keeps the frames: plugin backends run detached, and the restart re-adopts a live, answering one as `ready` (`adoptRunning` in `src/plugins/registry.ts`). A child that cannot be adopted comes back `stopped`, which evicts its frame at the next check. A page reload — the self-update path included — drops every frame.
  - No count cap beyond the opt-in set: at most one frame per enabled keep-alive plugin shown in this tab. A leaking page is cleared by Stop, Disable or a reload.

**Convention `scope` (required, explicit).** Every `conventions` entry MUST carry a `scope` — there is no silent default. The accepted enum is **`"project"`** (routes into the project-Conventions catalog described above) and **`"conductor"`** (routes into the Conductor-Conventions catalog — see the ⚠️ note below). `"workspace"` is **planned** and recognised-but-rejected at manifest load with a specific error (`scope "workspace" not yet supported (only "project", "conductor" are currently accepted)`); any other value gets the standard invalid-enum error and marks the plugin `invalid`. Expansion is **additive with no migration**: move a scope from planned→supported in `SUPPORTED_CONVENTION_SCOPES` (`src/plugins/manifest.ts`) and wire that scope's group (from the scope-keyed object `pluginHost.conventions()` returns) into its catalog's provider (`workspaceConventions`/`conductorConventions` already exist, built on `fragmentCatalog.ts`). No stored data changes shape.

> ⚠️ **Conductor-scope conventions modify the orchestrator itself.** A `scope:"conductor"` convention injects a fragment into the conductor's **own** operating rules (the composed conductor role prompt) — i.e. a plugin can shape how the orchestrator delegates, reviews, and merges across **every** project, not just a single one. It joins the Conductor-Conventions catalog namespaced `<plugin-id>/<slug>` and is **on by default while the plugin is enabled** (minus any the user unchecks — a remembered off-switch), composed into the conductor's system prompt on the next spawn/context-refresh; disabling the plugin drops it. That is a deliberately powerful, trust-loaded capability — consistent with "plugins are trusted own code", but far beyond a per-project convention, so treat enabling a plugin that ships conductor-scope conventions as granting it orchestrator-wide reach.

**Scaffold delivery (conductor-directive, no persistence).** At project creation the picked conventions that carry a `scaffold` facet have their directive texts composed **in selection order** into one framed orchestrator-guidance block (`Project "<name>" was created with these setup steps…`) that `create_project` (MCP) / `POST /api/projects` (REST) **RETURN** under a `scaffold` field (empty/omitted when none). Nothing is persisted and nothing touches the spawn path. The conductor folds the returned `scaffold` into its **first** `send_prompt` to the project's first worker (see `conventions/conductor/core.md`); the UI shows it read-only in the create confirmation. The scaffold facet has **no `scope` field** by design: it fires at *project creation*, so it is inherently project-scoped — workspaces and the conductor aren't "created", so there is no scaffold trigger for them. *(Future work: persist a lightweight pending-scaffold the conductor can pick up for UI-created projects.)*

Unknown top-level keys are rejected. Every `inputSchema` must stay inside the conductor's `validateArgs` subset — a **flat** `type:"object"` schema (per-property `type`/`enum`/`minLength`/`maxLength`/`pattern`/`minimum`/`maximum`/`items.type`; boolean `additionalProperties` accepted and ignored). `$ref`/`oneOf`/`anyOf`/`allOf`/`not` and nested object `properties` are rejected at manifest load, so an unvalidatable schema can never register. Invalid ⇒ state `invalid`, listed with errors, never startable.

Child env: `$PORT` (conductor-allocated; default your own port when absent so the plugin stays standalone-runnable), `CONDUCTOR_PLUGIN_ID`, `CONDUCTOR_URL` (`http://127.0.0.1:<conductor-port>`), `PROJECTS_ROOT` (the conductor's *resolved* projects root — injected explicitly, so it carries the default even when the conductor's own env never set the var), `CONDUCTOR_PROJECT_DIR` (the conductor's own running checkout dir, holding its `server.ts`/`package.json` — may be outside `PROJECTS_ROOT`). No fixed-port option in v1.

**Discovery rules.** The manifest is read from each project's main checkout **through that project's System** (`readManifest(system, dir)`) — a manifest and its fragment files are files in a project tree, and a bare local read against a remote project's path does not no-op, it reads cc's OWN file at that path and registers a plugin that is not there. A project whose System cannot be reached contributes no plugin and is warned about, never silently read locally — and when the store holds an **enabled** plugin record for that project, the catalog is additionally flagged **degraded**, because the manifest was never read and cc therefore cannot vouch for the absence of that plugin's conventions. The flag is computed live against the store (never latched into a stored boolean), so it clears at the next **Rescan** — or the moment that plugin is disabled. When the main checkout has **no manifest file at all**, the project's worktrees (sorted by name) are checked and the first **valid** manifest wins — so a plugin whose manifest exists only in an unmerged worktree (first-time plugin-ification) can bootstrap. Rows carry `manifestSource: {type:"main"} | {type:"worktree", name}`; enabling a worktree-sourced plugin defaults `activeVersion` to that worktree. A present-but-invalid main manifest keeps its `invalid` state (never masked by a worktree), and `POST /api/plugins/:id/version {type:"main"}` is refused with 400 while the main checkout lacks a valid matching manifest.

**A project mutation reaches the contributions immediately; discovery still needs a Rescan.** `conventions()` and `claudePluginDirs()` resolve each contributing plugin's placement LIVE, per call (`resolvePlacement`, `src/plugins/registry.ts`), so changing a project's target (`setProjectRemote`), deleting it, or re-pointing its system's provider command changes what those two return on the very next call — no rescan. A cached fragment body is served only under the exact state it was read under — the placement, the provider generation, and the host's own invalidation epoch — so bytes from one machine can never be served for another. That is enforced by labelling each cached body individually rather than tracking one label for the cache: a scan reads over a duration, not at an instant, so a gesture landing mid-scan would otherwise leave that scan's own later reads unaccounted for. See [architecture.md](architecture.md#component-layout) → `contributions.ts` for the invariant and the two interleaves that ruled out the simpler shapes. What a mutation does NOT do is change the discovery catalog (`byId`): in a running server only `POST /api/plugins/rescan` and the Library's install/update rebuild it, so the plugin's ROW keeps its pre-mutation `state`/`system` until then, and a NEW plugin project (created, adopted, or one whose manifest first appears in a worktree) is undiscovered — and therefore un-enableable — until a Rescan.

Placement outcomes, at COMPOSE time (each entry's placement resolved live, per call):

| Situation | `conventions()` | Why |
|---|---|---|
| Target changed and the tree is not on the new target | slug absent, `degraded:false` | the far side ANSWERED by name — a refusal, not "I cannot tell" |
| Project unregistered (`deleteProject`, all three branches) | slug absent, `degraded:false` | cc's own store dir (`projectStoreDir(name)`) and the registering artefact are both gone — removed on every delete branch, and an `rm -rf` of a checkout removes neither |
| Checkout vanished while cc still holds store state for the project | slug absent, `degraded:true` | gone or unmounted — for an in-root project the directory IS the registration, so this genuinely cannot be told apart |
| System unreachable, or worktree metadata unreadable | slug absent, `degraded:true` | a box being briefly down must freeze a committed `CONVENTIONS.md`, not rewrite it without the fragment |
| `orchStoreRoot()` itself absent | `degraded:true` | the guard that stops a vanished store root reading as "every project is unregistered" |

And at DISCOVERY-SCAN time, for a project the scan itself could not resolve through its System (so it is absent from the catalog entirely, not merely unplaceable):

| Situation | `conventions()` | Why |
|---|---|---|
| Unreachable at the last discovery **scan**, and the store holds an **enabled** record for a plugin in that project | slug absent, `degraded:true` **until the next Rescan** | the manifest was never read, so cc cannot tell whether that plugin contributes conventions — it flags on the enabled record alone, deliberately over-flagging rather than risking a rewrite |
| Unreachable at the last discovery **scan**, with no enabled record for that project | `degraded:false` | a project the store holds no **enabled** record for contributes nothing to `conventions()` in the first place, so its ABSENCE FROM A SCAN cannot drop a line from a committed `CONVENTIONS.md`. (A *disabled* plugin's body may still be sitting in one — but the next regenerate removes it because it is disabled, which is by design, and not because a scan could not see it.) |

The scan-time policy is therefore a **strict superset** of the compose-time one, and deliberately so. Of the five filters the compose path applies before it degrades, four (`discoveryState`, the id, the manifest, a non-empty `conventions` list) come out of the manifest — the exact file the scan never got to read, because the project did not resolve through its System — leaving only "is there an enabled record" answerable at scan time. Over-flagging costs a freeze the next Rescan clears; under-flagging rewrites a committed file.

### Reverse proxy — `/plugins/<id>/*`

- `/plugins/<id>/foo?q=1` → child `/foo?q=1` (prefix strip). Injected headers: `X-Forwarded-Prefix: /plugins/<id>`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `X-Forwarded-For`.
- `GET /plugins/<id>` → `301 /plugins/<id>/` (query preserved). Child `Location:` headers starting with `/` get the prefix re-added.
- cc's own security headers (`HOST_SECURITY_HEADERS`) are removed from proxied responses; the plugin's `Content-Security-Policy`, `X-Frame-Options` and `X-Content-Type-Options` pass through unchanged. A plugin's framing policy counts only if its `X-Frame-Options` is `DENY` or `SAMEORIGIN` (trimmed, case-insensitive) or its `Content-Security-Policy` has a `frame-ancestors` directive. Otherwise cc sets `X-Frame-Options: SAMEORIGIN`, replacing any unusable value the plugin sent, such as a blank one or the legacy `ALLOW-FROM …` that browsers ignore (`proxiedPluginHeaders`, `src/securityHeaders.ts`), so cc's same-origin frame loads the page and no other origin can. The proxy's own 301/404/502/503 responses carry cc's full policy.
- Bodies are never parsed — pure req→upstream→res streaming (SSE works). WebSocket upgrades are raw-socket piped with the original header order/casing replayed.
- Requests to an enabled-but-stopped plugin wait through the lazy start (`READY_TIMEOUT_MS` in `src/plugins/supervisor.ts`). Unknown/disabled id → 404 JSON; `failed` → `503 {error, status:"failed", tail}`; crash-backoff window → `503 {error, status:"crashed", retryAfter, tail?}`; child unreachable mid-request → 502.

### Bridge protocol — `/pluginBridge.js`

Plugin frontends include `<script src="/pluginBridge.js"></script>` as a blocking script, first in `<head>` (no `defer`: the theme and session-width syncs below then run before first paint; a deferred bridge still syncs, but only at deferred-script time) (`web/src/features/views/pluginBridge.js`, served by an explicit `GET /pluginBridge.js` route in `server.ts` whether or not the web UI is built; harmless 404 standalone, no-op when not iframed; the parent side is `pluginFrames` in `web/src/features/views/plugins.ts`). Envelope `{cc:1, type, ...}` over `postMessage`, same-origin both ways. Three core messages (every page) plus four optional session-awareness messages (pages that use `window.ccBridge`):

| Direction | Type | Payload | Meaning |
|---|---|---|---|
| child → parent | `ready` | — | bridge alive (initial `route` follows); the parent answers with a `session` |
| child → parent | `route` | `{path}` | child-relative path (incl. search+hash), which **must begin with `/`** — the parent ignores a `route` whose path does not; parent mirrors it into `#plugin/<id><path>` via `replaceState` |
| parent → child | `navigate` | `{path}` | external navigation; bridge `replaceState`s `<prefix><path>` and dispatches a synthetic `popstate` |
| parent → child | `session` | `{session: {sessionId, project, worktree} \| null}` | the active session. `worktree` is the instance's `worktree.worktreeName` (the `worktreeName` key of `GET /api/projects/:name/worktrees`), `null` for the main checkout |
| child → parent | `openSession` | `{id, sessionId}` | make a live session the selection, as a sidebar pick does |
| child → parent | `sendPrompt` | `{id, sessionId, text}` | deliver `text` to a live session as its composer's Send does, without selecting it |
| parent → child | `result` | `{id, ok, code?}` | the answer to one `openSession` / `sendPrompt`, posted to the calling frame only |

**Active session** = `activeInstance(appStore.get())` (`web/src/state/app.ts`): cc's one selection, in every layout; `null` when nothing is selected or the selected instance has no `sessionId` yet. The per-layout table is in [plugin-ui.md](plugin-ui.md) → Session awareness.

**`session` is sent** to one frame on its `ready` (a reload in place sends a fresh `ready`), and to **every** frame — the shared frame and each resident frame, hidden ones included — whenever the active `(sessionId, project, worktree)` triple changes. An unchanged triple (an instance-list refresh, a status change) posts nothing.

**`openSession` / `sendPrompt` rules:**
- `id` must be a string; a call without one is ignored (nowhere to reply). Exactly one `result` per received call.
- The child accepts `session`, `result` and `navigate` only from `window.parent` (same origin and `ev.source`).
- Accepted from any known frame (shared or resident, hidden included): same origin, and `ev.source` is that frame's `contentWindow`. An unknown source gets no reply.
- Instance lookup by `sessionId`: the listed instances plus the pristine slot; a live instance (status not `exited`/`crashed`) wins over a dead one sharing the id; none → `GET /api/sessions/:sid/locate`.
- `openSession` on a live session calls `selectInstance(id, {userGesture: true})` — what a sidebar row pick does (split: the session column switches and the dock stays; full-screen / phone: leaves the plugin view for the session). A session that is not live is refused; nothing is resumed.
- `sendPrompt` goes through `web/src/features/composer/send.ts` (`promptSendable`, `sendPrompt`), the composer's own path: `text` is trimmed, `notePristineSent` runs, the `prompt` frame is sent with `{ack: true}`. The server treats it as typed text (`promptOrQueueSteer`: a steer when busy, queued under the overage lockout; a conducted worker's conductor wake fires on its turn end). It never changes the selection, the route, drafts or attachments.

| `code` | When |
|---|---|
| `INVALID_ARGUMENT` | `sessionId` is not a non-empty string, or (`sendPrompt`) `text` is not a string or is empty after `trim()` |
| `SESSION_UNKNOWN` | no instance carries the id and `locate` refuses it (`ApiError`) |
| `SESSION_NOT_LIVE` | the session exists but no live instance carries it (`exited`/`crashed`, or a `locate` hit, archived or not) |
| `SESSION_NOT_READY` | `sendPrompt` only: live, but the composer's Send would be disabled (status not `idle`/`turn`, a `modelSwitch` in flight, `overageStoppedUnarmed`) |
| `SEND_FAILED` | `sendPrompt` only: the acked `prompt` frame was rejected (server error ack, closed socket, the 10 s ack timeout in `shared/ws.ts`) |
| `LOOKUP_FAILED` | the `locate` read failed with a network error, or did not settle within 10 s |
| `HOST_ERROR` | an unexpected failure inside cc while carrying out the call |

`SESSION_UNKNOWN` and `SESSION_NOT_LIVE` reuse the MCP vocabulary of `src/mcp/handlers.ts`.

**Child API.** Outside an embed, or on a host without these messages, `window.ccBridge` is absent. Embedded it holds `session` (`undefined` until the first `session` message, then the payload or `null`), `onSession(fn)` → unsubscribe (`fn` runs on every `session` message, and at once when one has arrived), and `openSession(sessionId)` / `sendPrompt(sessionId, text)` → `Promise<{ok, code?}>`. A promise never rejects: it resolves with the host's `result`. The parent sends exactly one `result` per received call, and bounds the slow parts: the send ack and the `locate` read at 10 s each. A frame that navigates or reloads mid-call loses its reply, so a plugin that needs a deadline sets its own.

**Security.** `openSession` / `sendPrompt` let any plugin page, hidden keep-alive frames included, drive any session. That adds no reach: a plugin page is same-origin with cc and can already call cc's unauthenticated API and socket. It is why the content-rendering rules in [plugin-ui.md](plugin-ui.md) Part 2 matter.

**REST metadata a plugin backend reads** alongside these messages (full shapes in [protocol.md](protocol.md)): `GET /api/projects/:name/worktrees` per worktree — `worktreePath`, `branch`, `baseBranch`, `baseSha`, `baseWorktree` (the parent worktree's `worktreeName`; absent = forked from the main checkout), `parentPath` (the main checkout); `GET /api/projects` row `path` (the main checkout when a project has no worktrees); `GET /api/instances` — `{sessionId, project, status, cwd, worktree: {worktreeName, branch, baseBranch, baseSha} | null}` per instance, `worktree: null` = the main checkout. **Live = `status` not `exited`/`crashed`**: the `sessionIds` lists on the worktrees and projects rows are *not* liveness-filtered (they include retained exited non-temp instances), so use `GET /api/instances` for "live". To run a command on a project's System (git, a temp file, anything with stdin or env), use [`POST /api/exec`](#host-exec--post-apiexec).

Inside the iframe the bridge patches `history.pushState` → `replaceState`, so a plugin visit adds exactly one joint-history entry (hardware Back exits to the conductor). Multi-page plugins bypass this and pollute history.

**Theme sync** (not a message): the bridge reads the parent's `<html>` directly and mirrors cc's resolved theme onto the page's own `<html>` — the `dark` class, plus `data-cc-theme="light"|"dark"`, which is present only while cc owns the theme. It applies it synchronously when the script executes and again on every change through a `MutationObserver` on the parent `<html>`'s `class`, hidden frames included. cc's `<html>` carries `.dark` exactly when its resolved theme is dark (`web/index.html`'s pre-paint script, then `web/src/app/theme.ts`, which also follows `prefers-color-scheme` under "system"). A parent whose `document` cannot be read (cross-origin: `SecurityError`) leaves the page's theme alone; standalone or outside a `/plugins/<id>/` mount the bridge does nothing at all.

**Session width sync** (not a message): the bridge mirrors cc's committed session-column width onto the page's own `<html>` as the custom property `--cc-session-width`: `<n>px` while Full is off, `none` while it is on (`sessionWidthCss`, `web/src/app/sessionWidthScale.ts`). cc publishes it as `data-cc-session-width` on its own `<html>` (`startPluginSessionWidth`, `web/src/features/views/pluginSessionWidth.ts`, started from `main.tsx`); the bridge copies the attribute when the script executes and again on every change through a `MutationObserver`, hidden frames included. Only the committed setting is published: a handle drag updates plugins on release, not during it. Unset under an unreadable parent, standalone, or outside a `/plugins/<id>/` mount, and while the attribute is absent. Use it as `max-width: var(--cc-session-width, <fallback>)`. A plugin never reads cc's storage.

### Host exec — `POST /api/exec`

A plugin backend runs a command on a project's System, or on a System addressed directly, with `fetch("$CONDUCTOR_URL/api/exec", {method: 'POST', body: JSON})`. No helper library and no MCP tool. Implemented in `src/hostExec.ts`, mounted in `buildRoutes` (`src/routes.ts`). There is no allow-list, path scoping or caller check — same trust model as the rest of cc's API.

**Target — exactly one form:**

| Form | Fields | Resolution |
|---|---|---|
| A | `project`, `worktree?` | `resolveProjectCwd` (`src/worktrees.ts`): cwd = the project's tree, or the worktree's; system = the project's |
| B | `system`, `remoteId?`, `cwd` | `systemById` (`src/systems/registry.ts`). `cwd` required and absolute. `remoteId` `''`/absent/`null` = the provider's default target. `system: 'local'` allowed; `remoteId` with `local` is refused |

**Request fields** (JSON; an unknown key is refused, so a typo like `input` for `stdin` fails loudly):

| Field | Rule |
|---|---|
| `argv` *or* `shell` | exactly one. `argv`: non-empty array of strings, no NUL, `argv[0]` non-empty — run directly. `shell`: non-empty string, no NUL — run through the target's shell — `bash -lc` locally and in the reference provider; a provider may use `sh -c` ([systems-protocol.md](systems-protocol.md) §5, `shell`), so write POSIX sh |
| `env?` | object; names match `ENV_NAME_RE` (`src/systems/execWrap.ts`), values strings without NUL. **Overlays** the target's default environment (`{...defaultEnv, ...env}`); never replaces it. In shell form it is applied after the login profile, so a profile cannot override it |
| `stdin?` / `stdinB64?` | at most one. `stdin`: UTF-8 text. `stdinB64`: strict base64 bytes. Absent = a closed stdin (EOF) |
| `encoding?` | `'utf8'` (default) or `'base64'` — `stdout`/`stderr` returned base64 of the raw bytes |
| `timeoutMs?` | positive integer ≤ `EXEC_MAX_TIMEOUT_MS`; default `EXEC_DEFAULT_TIMEOUT_MS` (both in `src/hostExec.ts`) |
| `maxOutputBytes?` | positive integer ≤ `EXEC_MAX_OUTPUT_BYTES`; default `EXEC_DEFAULT_OUTPUT_BYTES`. Total across both streams |

Request body limit: `EXEC_BODY_LIMIT` (route-local parser, ahead of the router-wide 1mb one); over it is express's own 413 `{error}` with no code.

**Response 200** — the command ran, whatever its exit code: `{exitCode, stdout, stderr, encoding, durationMs, system, remoteId, cwd, descendantsMaySurvive?: true}`. `system`/`remoteId`/`cwd` echo the resolved target (`remoteId` is always `null` for `local`).

**Refusals** — every body is `{error, code, …}`:

| Status | `code` | When | Extra fields |
|---|---|---|---|
| 400 | `INVALID_ARGUMENT` | any shape rule above, both or neither target form, both `argv` and `shell` | |
| 400 | `CWD_NOT_ABSOLUTE` | form B with a relative `cwd` | |
| 404 | `PROJECT_UNKNOWN` | unknown project | |
| 404 | `WORKTREE_UNKNOWN` | unknown worktree of that project | |
| 501 | `SYSTEMS_UNAVAILABLE` | a non-local system on a platform with `remoteSystems` off — form B is refused before any provider launches | |
| 501 | `SYSTEM_NOT_REGISTERED` / `SYSTEM_NO_PROVIDER` / `SYSTEM_NO_REMOTES` | from resolution | |
| 502 | `SYSTEM_UNREACHABLE` / `REMOTE_NOT_FOUND` | from resolution, or **during** the command (provider died, staging write unanswered; an unknown remote) | |
| 422 | `EXEC_SPAWN_FAILED` | the command never started: missing binary, bad cwd, `EACCES`, unopenable staged stdin (`ESTDIN`) | `errno` (or `null`) |
| 422 | `EXEC_OUTPUT_TOO_LARGE` | output passed `maxOutputBytes`; the command was killed | `limitBytes` |
| 504 | `EXEC_TIMEOUT` | `timeoutMs` passed; the command was killed | partial `stdout`/`stderr` (in `encoding`), `encoding`, `durationMs`, `descendantsMaySurvive?`, `abandonedAfterMs?` (cc gave up on a provider that never reported the exit) |

**Output is buffered whole, behind a fence.** No streaming, no paging: re-running a command for page two is neither idempotent nor free, and stream framing would tax every small call. Past `maxOutputBytes` the command is killed and the answer is `EXEC_OUTPUT_TOO_LARGE` — never a clipped 200.

**Kill semantics.** `timeoutMs` bounds the command only. Locally the whole process group is SIGTERMed, then SIGKILLed after the kill grace. On a provider the provider enforces it — group-wide when it advertises `processGroupSignal`, otherwise only the direct child, flagged `descendantsMaySurvive` — and cc abandons at `timeoutMs + EXEC_TIMEOUT_SLACK_MS` (`src/systems/providerSystem.ts`). A client that disconnects before the response kills the command the same way.

**How stdin and `env` reach a provider System** (no wire change; detail in [systems-protocol.md](systems-protocol.md) §7): stdin is written to `/tmp/cc-stdin-<32 hex>` on the target (`writeFile`, exclusive, mode 0600), and a `/bin/sh` wrapper opens it onto fd 0 and deletes it **before** the command starts; `env` rides as `env(1)` assignments (argv form) or `export` lines (shell form), never as a frame `env`. Locally stdin is a pipe and `env` a merge (argv) or the same `export` lines (shell).

**Target-side temp files** — there is no utimes or temp-dir primitive; run them through this route (e.g. the code-review plugin's private index):

```bash
d=$(mktemp -d)                         # shell: create; read the path from stdout
cp .git/index "$d/index"               # argv ['cp', …] or shell
touch -m -d @1700000000 "$d/index"     # set an mtime (seconds since the epoch)
rm -rf -- "$d"                         # clean up
```

**Known limitations.**
- A staged stdin file leaks when the provider dies between the staging write and the wrapper's `rm`. cc then tries to remove it (best-effort, not awaited) and logs `exec: could not remove staged stdin <path> on system <id>: …` when that fails; the file stays under `/tmp/cc-stdin-*` on the target.
- On a provider System, a call with stdin or `env` reports a missing or non-executable `argv[0]` through the wrapper's pre-check (a PATH walk for a bare name; existence, directory and execute bit for a path). It agrees with a local spawn for `ENOENT` and `EACCES` only.

### Theme stylesheet — `/pluginTheme.css`

- **Content:** the `@font-face` rules of cc's installed `@fontsource-variable/geist` and `@fontsource-variable/geist-mono` packages, a `/* cc:tokens */` marker line, then the palette tokens — the `:root` and `.dark` custom properties (plus `.dark`'s `color-scheme: dark`) that cc's own UI uses. **Unlayered**, so it wins over a plugin's `@layer base` fallback whatever the source order.
- **Source:** `web/src/themeTokens.css`, which cc's `web/src/index.css` imports. `src/pluginTheme.ts` (`composePluginTheme`) composes the sheet from that file and the packages' `index.css` on every request: `200 text/css; charset=utf-8`, `Cache-Control: no-cache`. It answers whether or not the web UI is built. Any failure to compose it — an unreadable source, or a font package whose `index.css` has no `url(./files/…)` to rewrite, rather than a sheet without fonts — is logged (`console.error`) and answered **503** `text/plain` `host theme unavailable`, with no detail on the page.
- **Fonts:** the packages' `url(./files/<file>)` references are rewritten to `GET /pluginTheme/fonts/<pkg>/<file>`, where `<pkg>` is a key of `FONT_PACKAGES` (`src/pluginTheme.ts`) and `<file>` matches `^[a-z0-9-]+\.woff2$`; served from that package's `files/` directory as `font/woff2`. Anything else is a 404. Same origin as the plugin page, so a plugin backend whose CSP has `default-src 'none'` needs `font-src 'self'` (and `style-src 'self'` for the sheet itself) or the browser blocks the fonts silently.
- **Guard:** `tests/plugin-theme.test.mjs` fails when a token served differs from cc's effective value (an override in `index.css`'s own `:root`/`.dark`, a dropped `@import`), when a token `index.css`'s `@theme inline` maps is not served, when a served font URL does not resolve, and when the `@theme inline` block in `docs/plugin-ui.md`'s reference setup differs from `index.css`'s.

### Authoring playbooks from a plugin

A plugin that lets users edit playbooks (rather than ship them) works against the **user overlay**, not its manifest. cc core serves read + validate only — [`/api/playbooks`](protocol.md#rest--apiplaybooks) at `$CONDUCTOR_URL/api/playbooks`; the plugin does the writing.

- **Create / edit** = write `$PROJECTS_ROOT/.code-conductor/playbooks/<id>.json` (`orchStoreRoot()/playbooks`; the dotfolder is `ORCH_STORE_DIRNAME`, `src/projects.ts`), creating the directory if missing. The body's `id` must equal `<id>`.
- **Delete** = remove that file.
- **Validate first:** `POST /api/playbooks/validate` with the draft; write only on `{ok:true}`.
- **Collisions:** check `GET /api/playbooks` → `takenIds` — a `builtin` id overrides the shipped definition (legal; warn), a `user` id overwrites that file, a `reserved` id is **silently ignored** by the loader (refuse it).
- **Pickup:** the next `loadPlaybooks` call reads the file — bodies are read per call, no restart. The conductor's role doc picks it up from its next spawn/resume.
- **Live runs drift:** editing an id live workers are bound to changes their graph under them (`GET /api/playbooks/:id` → `liveWorkers`; protocol.md → Playbooks → Known limitations).
- **Plugin-contributed playbooks are read-only** here (`editable:false`): edit them in the contributing plugin's manifest files.

### Auto-start

- **Flag:** `autoStart` on the plugin's `registry.json` record (`setAutoStart` in `src/plugins/store.ts`); default `false`. Set with `POST /api/plugins/:id/autostart` or the Settings → Plugins **Auto-start** switch.
- **Applies to** enabled, `local`, backend-bearing plugins only — the same refusals as the route. A disabled plugin never auto-starts; disable keeps the flag, and re-enable (including a Library install's enable) restores it.
- **Boot only.** Setting the flag starts nothing, clearing it stops nothing. At boot, `server.ts` runs `pluginHost.autoStartAll()` (`src/plugins/registry.ts`) after `init()` (so after adoption), fire-and-forget — boot does not wait on it.
- **Targets:** every record with `autoStart` and `enabled` whose backend is neither `ready` nor `starting`. A child adopted from `runtime.json` is `ready`, so it is left running, never restarted or duplicated.
- **Each start goes through `start()`** — the Start button's path — all in parallel.
- **A failure blocks nothing:** it shows on the row as `crashed` + **Crash output** (a refusal such as an undiscovered plugin shows only in the log), plus one server log line `plugins: auto-start of '<id>' failed: <error>`. `autoStartAll()` returns `{started, failed:[{id, error}]}` and never rejects except through init.
- **Not a crash supervisor:** a backend that dies later is not restarted; the lazy start on its next proxied request or MCP call still applies.

A registration refused after the clone rolls the checkout back, so no half-installed directory is left for an adopt or a rescan to find. Then rescan (drops cached fragment bodies), **enable the freshly-discovered plugin by default** (start-neutral — no process launched; an invalid/conflicting manifest is left disabled), run `postClone` if set, then regenerate every referencing project's `CONVENTIONS.md`. **Streaming response** — see below. |
| `POST /api/plugins/library/:id/update` | the real sequence: discard the checkout's **proven cc-generated** `CONVENTIONS.md`/`CLAUDE.md` (predicates: `src/conventionsCheckout.ts`; one `"[discarded cc-generated <paths> before pull]"` `pull`-phase chunk) → `git pull --ff-only` in the checkout its RECORD names → rescan (drops cached fragment bodies) → regenerate this plugin's own `CONVENTIONS.md` (one `"[regenerated CONVENTIONS.md]"` `pull`-phase chunk; this step also runs when the pull **fails**, before the 502, so a failed update leaves the generated files as they were) → run `postPull` if set → resolve which of the plugin's children are actually running (`ready`/`starting`) **first** → if none are running, nothing to restart, regardless of `postPull`'s outcome; if some are running and `postPull` ran and failed, the restart is **skipped entirely** (a broken `postPull` means the checkout is half-built, and restarting into it would trade a healthy child serving old code for one that crash-loops serving no code at all — the child is left exactly as it was); otherwise **auto-restart every running child of this plugin** → regenerate every referencing project's `CONVENTIONS.md`. The result gains `restarted: {ids, ok, error} | {skipped:"postPull-failed"} | null` (`null` when nothing was running, checked before the skip so it's never mislabeled as one) and the NDJSON `phase` set gains `"restart"` (one `"[restarted <id>]"` chunk per restarted child, or one `"[skipped restart: post-update command failed]"` chunk on a skip). **Streaming response** — see below. |

Errors: `{error}` JSON with 400/404/409/502/503 per the registry rules above. A failed update's 502 `error` gains `; local changes cc did not generate: <paths>` when the checkout holds dirt cc cannot prove it wrote (a hand edit, a staged change, any other path) — that dirt is never discarded, and git alone decides whether it blocks the pull.

**Known limitations.**
1. **Already-running sessions are not reached.** `.conduct/CONVENTIONS.md` is re-materialized per launch and read at session start. New convention text reaches a conductor on its **next spawn/resume**, and a worker's project `CLAUDE.md`/`CONVENTIONS.md` on its next session — never mid-turn.
2. **A project whose marker holds an unvouchable slug stays frozen for that cycle.** `ensureProjectConventionsMd` regenerates the resolvable slugs of a partially-unresolvable marker normally (an unresolvable slug just drops out of the body and is named in a visible note — see [architecture.md](architecture.md#component-layout) for the full contract), and declines to write — leaving the committed file untouched — in exactly one case: an unresolvable slug's absence can't be confirmed because the catalog is degraded (its plugin-conventions provider threw, a plugin's own **placement** resolution failed, or the last **discovery scan** could not resolve a project an enabled plugin lives in — see the two tables under *Discovery rules* for which situations degrade and which do not). Two cases deliberately do NOT freeze, because their absence IS confirmed: a vanished fragment/scaffold *file*, and a plugin whose project cc no longer has any record of. A system OUTAGE does degrade, and that is the accepted trade: freezing a committed `CONVENTIONS.md` beats rewriting it without a fragment because a box was briefly down. **The two sources clear differently.** A compose-sourced degrade clears on its own as soon as the placement resolves again, with no rescan and no other gesture. A scan-sourced one does not: the plugin is missing from the discovery catalog until something rebuilds it, so the freeze outlives whatever stopped the project resolving — a box that came back, a project record that was fixed — and **Rescan** (or disabling the affected plugin) is what ends it. That plugin's row in Settings → Plugins carries the reason and names Rescan as the retry. The freeze is whole-file, so the **workspace** conventions folded into the same document also stay stale until the next regenerate. It logs a distinct, greppable message (quoted in full in [architecture.md](architecture.md#component-layout)) via `{ log: console }` passed to `regenerateAllProjectConventions()` from every plugin route above and from the Settings → Conventions → Project custom-convention routes (`src/routes.ts`). The server log is the only signal on this path.
   **Blast radius of the degraded-catalog case:** it is global to the sweep, not per project — one plugin's placement-resolution failure degrades the catalog for every project regenerated in that pass. The unresolved slug that trips the gate need not be a plugin slug at all: a project whose only unresolved slug is a **deleted custom convention**, with no plugin involvement whatsoever, still declines to write while an unrelated plugin's placement is failing to resolve, until a later fan-out sees the catalog clear (a project whose marker fully resolves is unaffected either way — see the contract link above).
   **The conductor role doc does NOT freeze under the same degrade.** `composeConduct` composes and `materializeCurrentConduct` writes `.conduct/CONVENTIONS.md` anyway, so a conductor spawned mid-outage gets a role doc missing that plugin's `conductor`-scope sections — byte-identical to one composed with the plugin deliberately disabled. There is no marker analogue to key a freeze on: the conductor scope's plugin selection is derived live from the catalog and appears nowhere in `<store>/conventions/conductor.json`, so no `missing` set exists, and keying on `degraded` alone would also freeze outages that cost that document nothing. The server log is again the only signal — one `conductorConventions:` warn per conductor spawn/resume while the catalog is degraded (quoted in full in [architecture.md](architecture.md#component-layout)).
   **A project CREATED during the degrade is never protected by the freeze at all.** The freeze keys on unresolvable slugs in that project's line-1 marker — and a project created while the catalog was degraded has a marker that never NAMED the unreachable plugin's slug, because `list_project_conventions` could not offer it and `create_project` refuses a slug outside the catalog (400). So `missing` is empty forever, every later `ensureProjectConventionsMd` **writes**, and the slug is never added back; the convention's one-time `scaffold` directive is not emitted either, and nothing reissues it. The catalog degrade is surfaced instead: `list_project_conventions` carries an `incomplete` sentence (see [protocol.md](protocol.md#mcp-tool-protocol)) and `create_project` logs one `createProject:` line naming the project.
3. **Update under a degraded catalog leaves the checkout at HEAD's versions.** When the post-pull regeneration declines (`catalog-degraded`, same gate as item 2), a `"[CONVENTIONS.md left as upstream: catalog degraded]"` `pull`-phase chunk is streamed and the decline returns before `ensureConventionsImport`: `CONVENTIONS.md` **and** `CLAUDE.md` stay as the pulled HEAD has them, so `CLAUDE.md` lacks the `@CONVENTIONS.md` import; in a repo that tracks neither file, neither file exists. The next regeneration sweep writes both.

**Install/update streaming response.** Both routes validate synchronously first (unknown id, a refused `repo` — see the resolution table below — or an invalid derived name, name already registered for install; unknown id, a refused `repo`, not installed for update) — a validation failure is a plain `{error}` JSON body with the usual 400/404/409 status, no different from any other route. Once validation passes, the response becomes `Content-Type: application/x-ndjson`, one JSON object per line, status always 200 from that point on (headers are already committed):
- `{"type":"chunk","phase":"clone"|"pull"|"hook"|"restart","text":"..."}` — live stdout/stderr text from the clone/pull or the postClone/postPull hook, as it arrives; `"restart"` chunks (`update` only) are one `"[restarted <id>]"` line per plugin backend the update auto-restarted.
- exactly one terminal `{"type":"result","ok":true,"result":{id,name,project,path,postClone|postPull,restarted?}}` on success, or `{"type":"result","ok":false,"error":"...","tail":"..."}` on a clone/pull failure (`postClone`/`postPull`/`restarted` failures are still a soft warning inside the `ok:true` `result`, same shape/semantics as before — see below) — a failed clone is also rolled back (partial dir removed) before this event is written. `restarted` is present only on `update`'s result: `{ids, ok, error} | {skipped:"postPull-failed"} | null` — `null` when the plugin had no running backend to restart (this check runs before the skip decision, so a failed `postPull` on a plugin that was never running is still `null`, never the skip shape); `ok:false` (with `error`, and `ids` holding whatever restarted before the failure) means the pull/postPull already succeeded and landed on disk, only the restart itself failed — the caller should manually **Restart**; `{skipped:"postPull-failed"}` means a running backend was found but its restart was never attempted — a failed `postPull` already left the checkout half-built, so that running backend is left untouched, still serving pre-pull code, until the user fixes `postPull` and retries **Update** (or hits **Restart** once they trust the checkout).

#### Plugin Library — drop-in manifest, `<orchStoreRoot()>/plugins/library/*.json` (+ configured `libraryDirs`)

One JSON object per file (any filename ending `.json`), registering an installable plugin entry:

```jsonc
{
  "id": "my-plugin",             // REQUIRED, unique catalog key — overrides an earlier layer's entry with the same id
  "name": "My Plugin",           // REQUIRED display name
  "description": "optional",     // OPTIONAL
  "repo": "https://github.com/org/my-plugin", // REQUIRED — always a URL: http:/https:/git:, file:///<absolute path>, or catalog:<path relative to the directory holding this JSON>
  "postClone": "bash install.sh", // OPTIONAL shell command, run via `bash -lc`, cwd = the cloned project dir
  "postPull": "bash install.sh"   // OPTIONAL shell command, run via `bash -lc` after a successful Update pull
}
```

A set of built-in library entries (`DEFAULT_ENTRIES`, `src/plugins/library.ts`) is present even with no library dir, unless `plugins.builtinLibrary` is `false` (below). Malformed JSON or a file missing `id`/`name`/`repo` is skipped — never fatal to the list — and is also reported in the response's `skipped` array and shown in the Settings → Plugins Library status line, since a drop-in that silently never appears is indistinguishable from one that was never written. A file with a **wrong extension** (not `.json`) is ignored silently and is **not** reported. An unreadable store library directory (`<orchStoreRoot()>/plugins/library/`) stays a `console.warn`-only degradation, and its absence (ENOENT) is silent; an unreadable **configured** directory is different — see below. The install target project name is the last path segment of the **resolved** clone URL with a trailing `.git` or `.bundle` stripped (e.g. `.../org/my-plugin(.git)` → `my-plugin`, `catalog:repos/code-kanban.bundle` → `code-kanban`), validated the same way as any other project name (`validateName`, 400). `list()` and `update()` derive the name the same way, so a mirror entry whose repo ends in `code-kanban.git` (or `.bundle`) IS the install of the GitHub `code-kanban` entry. A catalog file whose `repo` is refused by the resolution table below, or whose derived name fails `validateName`, gets no row in `entries` — it is reported in `skipped` with the refusal as its `reason` (and logged), so the problem shows before anyone clicks Install. It still takes its `id`: a lower layer's entry of that id is not shown instead, and install/update of that id answer the same 400.

#### Local / offline catalogs

For an air-gapped box: ship a volume holding mirrored plugin repos plus catalog JSON that names them relative to itself, and point cc at it in `<orchStoreRoot()>/settings.json`:

```json
{ "plugins": { "libraryDirs": ["/mnt/cc-plugins/catalog"], "builtinLibrary": false } }
```

Example volume layout:

```
/mnt/cc-plugins/catalog/
├── code-kanban.json          # {"id":"code-kanban","name":"Code Kanban","repo":"catalog:repos/code-kanban.git","postClone":"npm install"}
├── code-hub.json             # {"id":"code-hub","name":"Code Hub","repo":"catalog:repos/code-hub.bundle"}
└── repos/
    ├── code-kanban.git/      # a bare mirror
    └── code-hub.bundle       # a git bundle (`git bundle create code-hub.bundle --all`)
```

- **`plugins.libraryDirs`** — extra catalog directories, read after the store library dir. Each element must be an absolute path; a non-string, empty or relative element is dropped silently (never resolved against the cwd). Elements are trimmed, normalised (`path.resolve`: `..` collapsed, trailing `/` stripped) and de-duplicated keeping the first. Read by `getPluginLibrarySettings()` (`src/appSettings.ts`).
- **`plugins.builtinLibrary`** — `false` (the literal boolean) hides the built-in entries entirely; any other value, or absence, keeps them.
- **Edit `settings.json` only while cc is stopped.** `appSettings` caches the file for the life of the process and writes that cached copy back on any Settings UI save, so a hand-edit made while cc runs is never seen and can be overwritten.
- **An unreadable configured directory** (including one that doesn't exist — an unmounted volume) is reported in `skipped` as `{dir, file: null, reason: "library dir unreadable: <error>"}` and logged; the other layers still serve.
- **Precedence.** Layers apply in the order built-ins → store library dir → `libraryDirs[0]` → `libraryDirs[1]` → …; within a directory, files apply in sorted filename order (code-unit order). **The last entry applied for an `id` wins.** An override keeps the list position of the first entry with that id. A file rejected for malformed JSON or a missing field never removes a lower layer's entry (it has no id to act on); one refused for its `repo`/derived name does, as above. A configured dir equal to the store dir is read once, as the store dir.

**`repo` resolution** (`resolveRepoUrl(repo, sourceDir)`, `src/plugins/library.ts` — the only producer of a clone URL, typed `CloneUrl`; every refusal is a 400 raised before the streaming response starts). `repo` is always parsed as a URL with `new URL(repo)` (no base) — nothing is guessed from its shape. `sourceDir` is the directory the JSON was read from (store dir or configured dir); `null` for a built-in.

| `repo` | Clone URL / refusal |
|---|---|
| `http://…`, `https://…`, `git://…` | the string verbatim |
| `file:///abs/x.git` | the canonical `href` (`..` collapsed, scheme lower-cased) |
| `catalog:x.git`, `catalog:./x.git`, `catalog:repos/x.git`, `catalog:../repos/x.git` | `pathToFileURL(path.resolve(sourceDir, <path>))`. The path is percent-decoded (`catalog:my%20repos/x.git` = `catalog:my repos/x.git`); `..` may leave `sourceDir`; no `~` expansion |
| unparseable — a bare path (`x.git`, `/abs/x.git`), scp-style ssh (`git@host:org/x.git`) | 400 `invalid repo URL`. A bare absolute path is told its own `file:///` spelling (`write it as file:///abs/x.git`); a relative one with no `:` is told `write it as catalog:x.git … or as an absolute file:///<path>` |
| any other scheme (`ftp:`, a drive letter `C:\x`) | 400 `unsupported repo URL scheme` |
| `file://host/x.git` | 400 `names a host` — only local paths are supported |
| `file:x.git`, `file://localhost/x.git` | 400 `must be written file:///<absolute path>` (WHATWG reads `file:x.git` as the filesystem root) |
| `file:///…` or `catalog:…` with a lone or malformed `%` (`file:///mnt/50%/x.git`) | 400 `malformed percent-escape — write a literal % as %25` (`file:///mnt/50%25/x.git` is the path `/mnt/50%/x.git`) |
| `file:///a%2Fb/x.git` (an encoded `/`) | 400 `contains an encoded '/' (%2F)` |
| a path containing a NUL byte (`%00`) | 400 `contains a NUL byte` |
| `catalog:/abs`, `catalog://h/x`, `catalog:` | 400 `catalog: repo must be a relative path` |
| `catalog:x?y`, `catalog:x#y` | 400 — percent-encode `?`/`#` (they would split off the end of the path) |
| `catalog:…` in a built-in (`sourceDir === null`) | 400 `no source directory` |

A `file:` output is always `pathToFileURL` of a NUL-free local path, so turning it back into a path cannot fail once the response is streaming. A local repo may be a **bare repo directory** or a **git bundle** file. `cloneRepo` hands git a `file:` URL as its local path with `git clone --no-local`: git detects a bundle only on a path (`git clone file:///x.bundle` fails `invalid gitfile format`), and `--no-local` is what stops a path clone hardlinking a directory mirror's object files into the install. The install's `origin` is that path. A last path segment that `pathToFileURL` percent-encodes (a space, `#`, `?`, `%`) can't form a valid project name and is refused by `validateName`. `update()` and the list's fetch/`behind` talk to the checkout's own `origin` — all of it works offline; to update a bundle, regenerate it in place with the new commits.

**`postClone`/`postPull` execution.** Run bounded (via `POST_HOOK_TIMEOUT_MS`) via a detached process group so a command that spawns children of its own (`npm install`, a browser-binary downloader) can be fully killed on timeout, not just its direct child; output is captured (bounded via `HOOK_OUTPUT_CAP`, with a tail surfaced in the response). This is a code-execution surface: any catalog file — in the store library dir or in any configured `libraryDirs` directory, including a mounted volume — can name an arbitrary shell command that runs on Install/Update. It is acceptable because built-in entries are trusted and every catalog directory is one the operator put there or named in `settings.json`: whoever can write a file into one is trusted with the same power a plugin's own manifest `backend.start` already has. Only point `libraryDirs` at a volume whose contents you trust. **Asymmetric failure handling is intentional:** a failed `git clone`/`git pull` is a hard failure (the request rejects; a failed clone is also rolled back) because the underlying operation itself didn't succeed, whereas a failed `postClone`/`postPull` is reported as a **soft warning on an otherwise-successful response** — the clone/pull already succeeded and is already discoverable, only the convenience command failed. The documented retry path for a failed `postClone` is hitting **Update** (which reruns `postPull`) rather than reinstalling — `code-playwright` sets both fields to the identical command specifically so Update is a true retry.

### Plugin MCP forwarding — child wire contract (pinned)

The conductor POSTs `{tool, arguments, caller:{sessionId, project}}` (JSON) to the manifest `mcp.endpoint`. The child returns **HTTP 200 for EVERY well-formed tool invocation** with body `{result: <any JSON>}` or `{error: "<message>"}` — unknown tool, bad arguments and tool-level failures are all `200 + {error}`. A **non-200 means a transport-level failure only** (malformed envelope, plugin bug) and surfaces to the MCP client as an HTTP-coded error; `200 + {error}` surfaces as a plain tool error. Calls are aborted at `mcp.timeoutMs`. Tool names are namespaced `<plugin-id>__<tool>`; argument validation against the declared `inputSchema` happens in the conductor **before** any forward. Visibility: every enabled plugin's tools are offered to **every** MCP caller — the conductor UI and workers in any project (`mcp.scope` is dropped at load, and `toolsFor()` takes no caller argument because there is nothing to scope by); a disabled plugin's tools are absent, so calling one refuses as an unknown tool.

**Raw-text results (opt-in, additive).** A success body may return `{text, meta?}` **instead of** `{result}`. `text` is one string **or** a list of strings; each becomes a **raw, UNESCAPED** `content[]` block. With a non-null `meta`, a compact-JSON block holding `meta` comes first, then one raw block per `text` entry. With `meta` omitted or `null`, a **single string** `text` is the whole result: exactly one raw block, no metadata block (the shape of cc's own rendered read tools). A **list** with no `meta` still gets a leading `null` block — send `meta` with a list, or send one string. Use it for anything a human or LLM reads as prose — a wiki page, a diff, file contents — where `{result}`'s `JSON.stringify` would escape every newline. `{result}` remains correct for structured data; a body with no `text` key behaves exactly as before.

Two edges, both deliberate:

- **`text` wins over `result`.** Sending both is a contract violation; it degrades to the `text` path rather than throwing, and `result` is ignored.
- **`meta` without `text` is silently dropped.** With no `text` key the body falls through to the `result` path, which never reads `meta`. This is the design's only lossy case — `meta` is meaningful *only* alongside `text`. To emit metadata with no body, send `{meta, text: []}` (or `text: null`), which yields the meta block and zero text blocks.

`text: null` → zero text blocks. A non-string (`text: 42`) is stringified, not rejected — nothing on this path throws.

### Plugin-compliance checklist

1. `conductor.plugin.json` at the repo root (schema above); keep `id` stable.
2. Respect `$PORT` when set; default your own port so the app stays standalone-runnable.
3. Base-path compliance: reachable under `X-Forwarded-Prefix` — relative asset URLs (or honor the prefix), root-relative redirects only (they get rewritten).
4. `<script src="/pluginBridge.js"></script>` (blocking, first in `<head>`) and `<link rel="stylesheet" href="/pluginTheme.css">` in the frontend, and routing that survives the bridge's history contract: `pushState` is demoted to `replaceState`, and a hash change adds a joint history entry (the bridge reports routes for you; [docs/plugin-ui.md](plugin-ui.md) → Routing).
5. A `healthPath` endpoint (any HTTP response counts as alive).
6. Optional MCP endpoint following the 200-always contract above, tools declared in the manifest with flat schemas. Return `{result}` for structured data; return `{text, meta?}` when the tool's output is prose/diff/file content that should reach the caller un-escaped (omit `meta` and send one string to get exactly one block; `text` wins if both are sent; `meta` alone, without `text`, is dropped).
7. Expect to be killed at any time (Doze) and restarted lazily — persist state, start fast.
8. A `frontend.keepAlive` page stays up while its backend crashes and is lazily restarted under it — reconnect rather than assume the backend it loaded against. (An explicit Restart, Update or version switch from Settings → Plugins evicts the page; the next entry loads it afresh.)
9. If a convention's fragment depends on something its `scaffold` facet sets up, **word the fragment to degrade gracefully** when the scaffold step wasn't run — the picked convention may land in a project where the setup directive was never carried out (e.g. "if a project-local harness wrapper exists, use it to visually verify UX changes; otherwise see the shared harness to create one").
10. A UI follows the host contract in [docs/plugin-ui.md](plugin-ui.md): relative URLs, cc's theme followed live, cc's session width followed through `--cc-session-width` if the page caps its width, servable after the Library entry's `postClone`/`postPull` hook has run. Stack, build tool and tests are the plugin's own.

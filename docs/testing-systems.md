# Testing the systems seam and the gated suites

The systems gate (`npm run gate:systems`), the FUSE-union chroot suites, the gated real-dependency suites, and the remote-placement suites.

**The systems gate (`npm run gate:systems`).**
`CC_LOCAL_SYSTEM_PROVIDER` swaps the in-process `local` System for a `ProviderSystem` over a provider process, so **every project-scoped operation in the app runs over the wire protocol** and nothing in the suite knows it.
`tests/systems-gate.mjs` typechecks once and then runs the WHOLE suite once per row against `src/systems/referenceProvider.ts` — `processGroupSignal+remotes` and `processGroupSignal:false, pty:false`, **concurrently** (each row's live lines are tagged `[1] `/`[2] ` by `tests/rowPrefix.mjs`, mapped to names by the banners printed before either row starts, and the closing block is still printed last and untagged) — which is one gate making two claims: the three primitives plus the derivations are SUFFICIENT for the application, and **the optional-capability fallback actually executes** (a fallback that has never run is not a fallback).
There is no third row: `persistentShell` does not exist, and a row for it would have been byte-identical to a default no-flag row — vacuous, not cheap. The rows are `CONFIGS` in `tests/systems-gate.mjs`, which owns the list.
It is a separate command because it IS `npm test`, once per row; the per-configuration protocol suites below run inside the ordinary suite, so a plain `npm test` still exercises the fallback at the unit level.
The five files: `tests/systems-protocol-codec.test.mjs` (framing + taxonomy, unit), `tests/systems-protocol-conformance.test.mjs` (**the definition of a valid provider** — the three primitives, the exec lifecycle, process-group signalling, negotiation, multiplexed ids, every error code and every derivation, in every configuration, with a closing test that fails if a taxonomy code has no producer — which fires in BOTH directions, so a code with no producer AND a cross-reference naming a code the taxonomy no longer has each red it; that is what caught `EBUSY`'s removal), `tests/systems-shell-framing.test.mjs` (the measured shell failures), `tests/systems-provider-supervision.test.mjs` (a deliberately misbehaving provider, `tests/fake-provider.mjs` — bad version, silent handshake, garbage line, mid-operation death, restart storm, wedge), and `tests/systems-provider-parity.test.mjs` (LocalSystem vs ProviderSystem answering identically).
A test that WRAPS a System method must take the live handle's prototype (`tests/systemHandle.mjs`), never `LocalSystem.prototype`: under the gate the handle is a `ProviderSystem`, and a NEGATIVE assertion against the wrong class passes for the wrong reason.
A test that steers a command through `process.env` reaches `LocalSystem`'s exec live but not a provider's: the provider keeps the environment it was spawned with and no frame carries one, so the test must respawn the provider around the change (`respawnProvider` in `tests/git-dubious-ownership.test.mjs`).
Row 1 carries `--remote gate=/` plus `CC_LOCAL_SYSTEM_REMOTE_ID=gate` (`LOCAL_REMOTE_ENV`, `src/systems/registry.ts`), so every frame that pass emits is target-bound — `remotes` folded into an existing pass rather than given a fourth, because a fourth costs a whole suite and puts the same field on byte-for-byte the same request frames (the counts, and how to re-take them without double-counting the suite's own providers, are in `tests/systems-gate.mjs`'s header).
The seam's guard is structural: `buildLocalSystem` returns the in-process `LocalSystem` before it reads the remote-id variable, so that variable alone can never bind cc's own machine (`tests/systems-local.test.mjs`).
The cost of the fold: no gate row now runs `processGroupSignal:true`+`remotes:false` together — that cell is covered by `CAPABILITY_CONFIGS[0]` of the conformance and parity suites, which run inside every row.
`remoteDescriptors` is not in the matrix at all: `mirror()` is unreachable for the id `local` whatever class backs it, and a `--mirror` row was measured receiving zero `describeRemote` frames.
`remoteListing` is advertised by row 1 (it rides `--remote`), but the application never sends `listRemotes` to the gate's `local` stand-in, because enumeration decides `local` by id; the suites that do send it register their own providers and run inside every row.
`pty` is folded into the `processGroupSignal` toggle — on in row 1 where the host's python3 runs the helper, `--no-pty` in row 2 — and `tests/systems-terminal-seam.test.mjs`, which opens a terminal through the `local` handle, is what gives each row something to run: an echo in row 1, `SYSTEM_NO_PTY` in row 2.
**The terminal tests:** `tests/terminalBattery.mjs` (the shared battery's rows, `TERMINAL_ROWS`; each entry file registers every row with its own `test()` through `terminalRowTest`, so a row's test id is the entry file's — echo, login shell, env overlay, exit code and signal, drain before exit (made deterministic by SIGSTOPping the helper while the program exits), size and resize, `^C`, close/abort kill the session, pause/resume, the cap, spec validation, the overlay reaching the program and not the helper (read from `/proc`), input past one credit window arriving intact, `write` backpressure and `onDrain`), run against `LocalSystem` by `tests/systems-terminal-local.test.mjs` (plus `PTY_UNAVAILABLE` and the local open bound) and over the wire by the conformance suite (plus the credit window, input credit granted for written bytes only, the open-only ceiling, `ETRANSPORT` on provider death, bound views sharing one cap);
`tests/systems-pty-helper.test.mjs` (helper framing, the memoised probe, and the helper's stdio protocol driven raw — EOF before `v`, a bad first frame `EPROTO`, the `w` totals — and ptyHost's `HELPER_INPUT_WINDOW_BYTES` against `tests/fixtures/fakePtyHelper.mjs`, a helper that reports nothing written);
`tests/systems-pty-input-credit.test.mjs` (cc's side of input credit against `tests/fixtures/noCreditPtyProvider.mjs`: exactly one window on the wire, starvation blocking neither `resize` nor `close`, no drain and no failure, an over-grant `EPROTO`);
`tests/hostTerminalRows.mjs` (the `GET /api/terminal` rows, run against `local` by `tests/host-terminal-route.test.mjs` — gate-aware through `expectedLocalTerminalRefusal` — and against a provider system by `tests/host-terminal-route-system.test.mjs`, plus the per-pipe cap and the `remoteSystems` gate) and `tests/host-terminal-bridge.test.mjs` (the pump against fakes);
`tests/systems-pty-fallback.test.mjs` (`SYSTEM_NO_PTY` with nothing on the wire, a provider with no python3, and `tests/fixtures/recordingProvider.mjs --pty-fake epty|silent|overflow|window` for `EPTY`, the open-timeout's `close` + `ETIMEDOUT`, the enforced window's `EPROTO`, and its exact boundary — a full window held is legal, one byte more is the breach).
**A red row states its own diagnosis in the closing `=== gate:systems ===` block** — the hang-guard verdict plus the failing test names (capped at `NAMED_FAILURE_LIMIT`, then counted) — because the gate is read through a `tail` of a captured log and its first-ever red lost its failing test name to exactly that.
A row that reds with **zero `✖` lines** says so explicitly and points at the verdict: that is a killed/wedged file or a leaked process, not a test failure, and the block distinguishes the two at a glance instead of by re-running.
`tests/gateSummary.mjs` scans and renders (ANSI- and chunk-boundary-independent, so a TTY run and a redirected one say the same thing); `tests/systems-gate-summary.test.mjs` drives both against canned rows including the zero-`✖` one.
The row's output is **teed with `.pipe()`, never a bare `write()`** — `process.stdout.write` is asynchronous once stdout is a pipe, so a fire-and-forget tee would lose output under backpressure and reintroduce the very failure the tee exists to prevent; for the same reason the gate sets `process.exitCode` and never calls `process.exit()`, which would discard the summary still buffered in its own stdout.

**A `gate:systems` red is not automatically the diff under test — and two shapes should not be the first guess.** Attribute a red with `tests/gateSummary.mjs`'s closing block. Two mechanisms produce a gate red while being **no Systems-provider behaviour at all**: a test oracle resting on a port the kernel can re-issue (`reservedPort()`), and a detached `git maintenance` landing inside a tree-snapshot window (`pinGitConfig`). **Their row-independence rests on different evidence, and the difference is worth keeping straight:** the port defect is shown independent **by forcing** — the injected steal fails the test in all three arms and passes in all three without it — while the `git maintenance` defect's independence is **structural**, since no gate row's flags touch that actor, and its forcing proof never varied the provider row. Two shapes are **not to be re-assumed**, each stated with the support it actually has: **the orphan shape**, at n=52 (every run, *including both reds*, printed the identical `hang-guard: 346/346 files reported, 0 killed, 0 leaked process(es) swept, stream ended cleanly, run cap not reached` — the real line, `tests/run.mjs`, grep it verbatim), and **the wedge shape**, at n=2 (both reds were ordinary named `✖` failures at normal wall clock, not hangs). n=2 is a weak bound; it is enough to stop presuming the wedge, not enough to call it impossible.

**A test that asserts a port REFUSES connects must not get that port from `allocatePort()`.** `allocatePort` binds `listen(0)`, reads the port and hands it straight back, so the number it returns is one the kernel can re-issue to any other `listen(0)` on the box — after which the connect succeeds and the oracle reports the opposite of the truth. That is what redded `bare-TCP readiness does not fire before the port is actually bound`. `reservedPort()` in `tests/plugins-supervisor.test.mjs` is the provenance to copy: it picks a **verified-free port strictly below `ip_local_port_range`'s low bound**, which no automatic allocator can hand out (measured: **60,000/60,000** `allocatePort()` results land inside the range; the tests at the foot of that file re-check both halves at a 200-draw sample on any host that exposes `/proc/sys/net/ipv4/ip_local_port_range`, and announce-and-skip where it does not, so the re-check is host-conditional rather than universal). `src/plugins/ports.ts` is unchanged — `listen(0)` plus the supervisor's EADDRINUSE retry is correct for real plugins; only the test's port provenance moved.

**Worker sessions on a system.** `tests/systems-concurrent-commands.test.mjs` (two commands of ONE session genuinely overlapping via a filesystem rendezvous, each result holding exactly its own 300 lines in order, and an interrupt reaching one while a sibling that is provably still running completes untouched). `tests/systems-tool-redirect.test.mjs` (the forwarder rewrite, the output fence, cancellation and `close()`, and — since the geometry retirement — that a file tool passes through UNTOUCHED at an absolute system path). `tests/systems-session-root.test.mjs` is now CRITERION 8'S EVIDENCE FILE rather than the allow-list walk's: no session root and no manifest anywhere under the store after a real remote spawn (a full recursive walk, not a probe at a predicted path), and ZERO `find` frames on a recording provider's wire with the recorder's own traffic as the control. `tests/systems-transcript-collision.test.mjs` owns the collision guard, `tests/systems-mirror-wide.test.mjs` a mirror root wider than the project, and `tests/systems-mirror-geometry-follow.test.mjs` the session-fatal re-advertisement refusal. `tests/systems-bash-rules-refusal.test.mjs`, `tests/systems-redirect-hooks.test.mjs`, `tests/systems-mirror-advertisement.test.mjs`, `tests/systems-mirror-fallback.test.mjs` and `tests/systems-remote-worker.test.mjs` keep their subjects. The bridge's own suites (`systems-file-bridge`, `systems-mirror-bridge`, `systems-mirror-refusal`, `systems-session-root-skips`, `systems-mirror-geometry-move`) are DELETED with the bridge — the semantics they specified are under [“What `fileBridge` carried”](components/fuse.md#what-filebridge-carried-and-where-it-has-to-land-again), not in a test file.

**Proving streaming, not just output.** Every streaming assertion is ORDER-based rather than wall-clock-based, so none of them can flake on a slow machine. At the shell layer, the first chunk must have arrived while `run()` was still pending. At the process layer, `part1` must arrive in a write that does **not** also carry `part2` — a forwarder that buffered to completion necessarily coalesces the whole output into one write, so the split itself is the evidence. The docker suite adds the one wall-clock check that is worth having, and only as a second witness: the first write must lead the process's end by most of the command's own pause.

**Every CLI behaviour the redirect depends on has a gated pin, and each pin has a CONTROL.** `disableAllHooks`, `includeGitInstructions` and `CLAUDE_CODE_TMPDIR` are each asserted twice — once with the lever and once without — because a RENAMED key would otherwise leave the with-lever assertion passing for the wrong reason while cc's scan silently stopped finding the live one. And each asserts over a **mechanical** channel, never the model's prose: `CLAUDE_CODE_TMPDIR` from the filesystem (the model was measured reporting "the background task completed" instead of relaying the path it was asked for); `includeGitInstructions` from a `git` shim earlier on `PATH` — measured, `status --short`, `log --oneline` and `config user.name` run only when the block is built, while five other git calls happen either way, so the assertion names the three rather than counting them.

**The FUSE-union chroot's two suites, and why they are two.**
One is ungated and deterministic; the other is the gated real-FUSE family of files over one harness.
`tests/fuse-lifecycle.test.mjs` runs in `npm test`: it drives `runTeardown` against an **injected `MountDriver`** whose fixtures are in-memory tables and whose clock is virtual, so every deadline in the state machine is exercised in microseconds and nothing signals a real pid.
It pins what is otherwise unobservable — that the unmounts are issued deepest-first, every one but the union root BEFORE the abort and the root RIGHT AFTER it, that the abort names the minor captured at mount time and is issued only while the root is attached on it — never to a minor another session took over after the superblock died (the fake driver's opt-in kernel model: `devs`, owner-tagged `conns`, `onSuperblockGone`; its abort is NOT modelled — it is the shipping driver's, built by `createRealMountDriver` with an injected `exec` that runs the real argv against the fixture's table rendered as mountinfo and its connections as a fusectl directory, `tests/fuseAbortSeam.mjs`), that a recycled pid is reported gone and never signalled, that `state == Z` with a second live thread is `WEDGED` and never reaped, that a wedge keeps the record and reports on both surfaces, and that a `fusectl` minor with no record of ours is counted and not aborted.
The `tests/fuse-*.real.test.mjs` FAMILY (`RUN_FUSE_LIFECYCLE=1`) is the gate: real `sudo`, real `unshare`, real FUSE, a fake `claude`.
The files — `fuse-lifecycle.real` (the spawn, the three teardown paths, the boot sweep, the busy-mount wedge, the cost control, the criterion-9 refusal, **arm 8** — the only place on a real host where the sudo claim is observable: a sentinel provably does NOT cross `sudo -n` there, and the worker's own environment reaches the CLI anyway — and the record-independent leak arm), `fuse-union-mount.real` (R1–R7, what the mount itself answers), `fuse-union-routing.real` (R8, R15, R9, R10, R11, R13, R14 — where a path resolves for an UNMARKED caller), `fuse-union-marking.real` (R12, R13w, R14L, R16 — who is marked and when), `fuse-union-pin-ancestors.real` (P1, P2 — a wide root whose remote lacks the directories above a host pin) `fuse-union-listing.real` (L1, L2 — what a marked listing of a remote directory names) and `fuse-teardown-minor-reuse.real` (a session that reused a torn-down session's minor survives that teardown — the reuse forced by blocking the teardown right after its root unmount until a second session has mounted) — over one shared harness, `tests/fuseGateCase.mjs`, which owns the dependency preflight, the server, the three systems, the mirror scaffold and the observation helpers, and which is not named `*.test.mjs`, so `discover()` ignores it.
Four arms, all in `fuse-union-marking.real`, own the marking event between them — `R12` (the mark is the CLI's own and the whole bootstrap chain precedes it), `R13w` (at `mirrorRoot: '/'` the chain is unmarked and host-served, and **no marked op names a path under `/usr/bin`** — the standing licence for the chain carrying no pin; its contrast half measures the other side, that a **marked** caller is not served those paths at all), `R14L` (a backend launcher runs unmarked: its host-pinned handoff reaches the CLI, an unpinned one diverges) and `R16` (a symlinked launcher marks on the **link**, and its realpath is then walked marked — the geometry the gate's default `CLAUDE_BIN` leaves untested).
**Every arm in the family captures a `before` snapshot and asserts a delta** — a host can carry inherited FUSE residue, and an absolute assertion would either fail on it or hide a leak under it.
Every signal anywhere in the family targets a pid read from the session's own `mount.json`, starttime-revalidated through `killPids` (`tests/procTree.mjs`); there is no `pkill`, `pgrep` or pattern of any kind.
**IT SAT AT THE PER-FILE WATCHDOG AS ONE FILE, AND THAT WATCHDOG KILLED IT.**
Its cost is ~2.4s of real mount teardown per arm — `runTeardown` plus the daemon and anchor dying — so a single file was charged the SUM of its arms and the family is charged the MAX.
**THE KILL IS THE REASON THE SPLIT EXISTS, AND IT IS NOT REPRODUCIBLE ON DEMAND** — both halves of that have to stay recorded, because a margin record holding only the healthy figure is what invites raising `FILE_KILL_MS` after a false kill (`tests/hangGuardConfig.mjs` states the rule).
**Crossing runs, as one file on a quiet 16-core box against `FILE_KILL_MS` = 90 000 ms:** 87.0 / 89.7 / 90.2 s over three consecutive runs, then **94 341 ms** after a prose-only commit.
A crossed deadline is a TRUNCATING SIGKILL: the run reports `0/1 files reported`, the file emits no summary, and node's own pass/fail tally and every per-arm name go with it — **with every arm green**.
**Re-measured at the split on the same box class, the same three-run protocol, same deadline: 82 213 / 82 193 / 82 460 ms (1.09x)** — so the file was never reliably over, it was within ~10% of the deadline and crossed under conditions neither protocol controls.
Treat the ~9% headroom as the *good* case and the kill as the one that decides the design.
**Every wall figure and kill count from here to the end of the next paragraph was measured over the lifecycle, mount, routing and marking files; `fuse-union-pin-ancestors.real` and `fuse-union-listing.real` are not in them.**
**After the split**, at the documented `TEST_CONCURRENCY=1`, over **ten** consecutive runs on a quiet 16-core box (`nproc` 16), same deadline — ten, because three clean runs is exactly what hid the contention below: **28 610–29 341 ms (>=3.06x)** for `fuse-lifecycle.real`, **26 119–26 933 ms (>=3.34x)** for `fuse-union-routing.real`, **25 902–26 466 ms (>=3.40x)** for `fuse-union-mount.real`, **13 940–14 534 ms (>=6.19x)** for `fuse-union-marking.real` — **0 kills in 10**, 4/4 files reported every run, total family wall **95.4–96.9 s**.
No `CC_TEST_FILE_KILL_MS` override is needed.
Read each file's wall off the run's own `hang-guard: slowest files` line, whose ranking is capped at five entries, so a four-file family appears on it whole.
**BOTH PER-FILE FIGURES ARE RECORDED, because the capped ones look 30% high against any uncapped re-measurement.**
The same four files, same box, over the clean runs of the 18-run uncapped rate sample above (`node tests/run.mjs tests/fuse-*.real.test.mjs`, NO cap — the configuration that also produces the kills, so these figures are not a recommendation): `fuse-lifecycle.real` **22 311–23 424 ms**, `fuse-union-routing.real` **20 813–21 247 ms**, `fuse-union-mount.real` **20 523–21 277 ms**, `fuse-union-marking.real` **10 876–11 592 ms**.
So serialising costs each file ~25–30%.
**WHERE THAT GOES IS LOCALISED, NOT EXPLAINED:** the two quantities the harness itself prints (`fuse gate timing [chroot]`) are flat between the modes — first spawn→idle ~0.85–1.01 s, later spawns 149–326 ms, turn 100–345 ms, in BOTH — so it is not in spawn and not in the turn.
What is left in an arm is its `inNs`/`sh` probe round trips and `instances.remove` teardown, which are not separately instrumented.
That these are fixed-latency chains which four concurrent file streams overlap, and a serial run cannot, is the standing HYPOTHESIS for the delta; it is not measured.
**THE CAP COSTS WALL AND BUYS MARGIN, and the trade is not free:** serialised, the family's total (~96 s) is ABOVE what the single pre-split file cost (84 695–85 772 ms over six runs of its own invocation against the real guard, 0 failures, same quiet 16-core box, load ~1.0–2.2) — but that file sat at **1.04x** of the deadline with no room for a stall — the 1.09x quoted earlier in this paragraph is the SAME file in a different session and under the `CC_TEST_FILE_KILL_MS` override, so the two multiples are not a drift, they are two sessions — while each file here has 3x or better, and a stall now costs one file's arm names instead of all 26.
**THOSE MARGINS DESCRIBE HEALTHY RUNS, NOT A HANG:** `TURN_TIMEOUT_MS` in the harness's `spawnWorker` is 120 000 ms, above `FILE_KILL_MS`, so a genuinely hung spawn still blows the file deadline before its own timeout fires.
The remedy this config prescribes for a file at its deadline is **more files**, not a later deadline — so an arm added here is an arm that has to be paid for, and the file it is added to is what the margin is charged against.
One observation is genuinely shared across the four concurrent processes: `snapshot()`'s `pid1Total`, a whole-machine `/proc/1/mounts` line count each arm asserts unchanged across itself.
Under a green product nothing reaches pid 1's table, so it is stable; if it ever flakes under concurrency the answer is a concurrency cap, not a widened assertion.

**WHY THE CAP IS IN THE INVOCATION: UNCAPPED, THE FOUR FILES STARVE EACH OTHER.**
The split traded one long file for four that run CONCURRENTLY, and each of them spawns real workers into real FUSE mounts.
The runner's `peak concurrent fake-claude subprocesses` line is a **100 ms sampler's maximum, not a census**, so read it as a range over runs rather than a value: over 11 uncapped runs it read **3 ten times and 4 once**; over 10 capped runs it read **1 every time**.
Measured on the bare glob at the default concurrency, settled box, no override: **3 kills in 18 runs (~17%)**.
Every one had the same shape — a single arm starves, is cancelled at the runner's own 60 000 ms per-test `timeout` (`run()` in `tests/run.mjs`), and its whole file then rides to `FILE_KILL_MS` and is SIGKILLed at ~90 100–90 200 ms, so that file emits no summary and its arm names are lost while every other file passes.
**The stalled arm varied — R9, R10 and R14 — so it is contention, not an arm-specific bug.**
All three observed stalls happened to fall in `fuse-union-routing.real`; nothing in the measurements explains why that file rather than `fuse-union-mount.real`, which spawns a worker in 7 of 7 arms exactly as routing does, so do not read the victim as predicted.
`tests/run.mjs` has no per-file exclusivity (one `run({files, concurrency})` call, one global `TEST_CONCURRENCY`), so the cap is part of how the gate is invoked rather than a property a file can declare.
**Turning the gate on for a whole-suite run is the same hazard by another route** (`RUN_FUSE_LIFECYCLE=1 node tests/run.mjs` with no path arguments — what a mutation round does): measured 1 stall in 6 runs, the same 60 s cancellation, the file reaching 92 570 ms.
`TEST_CONCURRENCY=4` measured green there against the real guard once — 377/377 reported, 0 killed, worst FUSE file 21 983 ms, suite wall 166 s — **and it is NOT established**: a separate gate-on full-suite baseline at that same `TEST_CONCURRENCY=4` red **R14L**, the same starvation shape, and the marking file then passed 4/4 alone at `TEST_CONCURRENCY=1`.
So 4 is a starting point for a re-measurement, not a setting with a rate behind it; the only configuration with a rate is the family glob at `TEST_CONCURRENCY=1`, 0 kills in 10.
Do not answer any of this by splitting further, by folding arms, by moving `FILE_KILL_MS`, or by changing the 60 s per-test timeout.
**ONE FAILURE IN THAT 18 IS NOT EXPLAINED BY CONTENTION AND IS NOT CLAIMED TO BE:** R5 in `fuse-union-mount.real` failed FAST (1711 ms, i.e. it reached the end of the arm rather than timing out) rather than stalling, and its message was not captured.
The obvious candidate is the one machine-global observation this section names as shared across the four concurrent processes — `snapshot()`'s `pid1Total`, a whole-machine `/proc/1/mounts` line count — and it is measured **not** supported: sampled every 100 ms across a whole uncapped family run, `/proc/1/mounts` held constant at 52 lines for 250 consecutive samples.
**That non-support rests on ONE run's window**, so if R5 recurs, sample `/proc/1/mounts` at the arm's own before/after inside `snapshot()` rather than from a background sampler — a background sampler cannot see a disturbance that opens and closes between two of its ticks.
R5 **has not recurred** in the 10 capped runs nor in 10 further logged uncapped ones; that is an absence of recurrence, not a mechanism — a concurrency cap cannot *explain* a 1711 ms assertion failure, and this one stays unnamed.

**The leak check has to be record-independent, and that is a scar.** The obvious one — a `/proc/1/mounts` delta plus starttime re-verification of the pids in `mount.json` — is blind by construction to a leaked process whose namespace is private *and* whose record has been deleted, and exactly one leaked. `tests/fuse-lifecycle.real.test.mjs` arm 7 therefore asserts, from `/proc/<pid>/environ` and without reading any record, that no process carrying its `CC_FUSE_RUNDIR` survives; it is ordered last in that file so it sees every earlier arm's residue. **Its scope is that file, not the run** — `runRoot` derives from each file's own store root, and the four files run concurrently — so the same check runs for the other three in the shared `after()` hook in `tests/fuseGateCase.mjs`, which names the file in its failure message because a hook failure reds no arm. **WHAT THAT HOOK IS WORTH OUTSIDE THE LIFECYCLE FILE HAS BEEN MEASURED FROM BOTH SIDES, and the two answers differ:** removing the anchor's SIGKILL from teardown **reds the marking file** through this hook — a leaked anchor that no arm in that file could see — so the assertion has real teeth where no arm covers it; but blinding the `/proc` scanner itself **survives** in the mount file, because nothing outside the lifecycle file proves the scan can still SEE a live attributable process. Only arm 4 does that, by holding one alive and asserting the scan finds it. **So for the other three the check catches a leak and cannot catch a blind scanner**, and a non-lifecycle file run alone has no positive control at all.

**THE SAME BLINDNESS REACHES THE MOUNT-RESIDUE OBSERVATION, and it is one limitation rather than two.** Every arm in the family that takes a residue delta measures it *under `runRoot`*, so a `runRoot` that is wrong-but-plausible makes both sides read empty and the arm passes vacuously. `setupFuseGate` verifies the `ctx` bag it publishes against `CTX_SHAPE` before handing it to a file, and that DOES fire — measured, in all four files, on a bag published with `runRoot: ''`, throwing in `before()` so no arm runs. But no predicate there can distinguish the true run root from any other absolute path, and `mountsUnder`'s refusal only rejects a non-absolute one: publish `/opt` and the mount, routing and marking files stay green 7/7, 7/7 and 4/4. **The only thing in the family that closes it is arm 1 and arm 4's POSITIVE mount-membership assertion** — that `record.root` is in the daemon's or anchor's table under `runRoot`, which a wrong root cannot satisfy — which is why the same substitution kills the lifecycle file and nothing else. So both record-independent observations, the process scan and the mount delta, rest for the other three files on this file's positive controls holding in a sibling process. A hook failure reds no arm — it surfaces on the suite's `describe` name — which is why the message names the file and says where it fired. (The scan result is NOT swallowed: `attributableProcesses` asserts the `/proc` walk ran, and a `.catch(() => [])` around it would turn "the scan could not run" into "no leak".)

**Two ways that gate can pass vacuously, both closed, in every file of the family.** `bootServer({realProcess:true})` **deletes** `FAKE_CLAUDE_SCENARIO` unless a scenario is passed, and `fake-claude` then exits 2 — so every teardown arm passed against a worker that had already crashed. And `status === 'idle'` is **not** a barrier that the CLI is up: `spawn()` reports idle as soon as the subprocess is alive and stdin is writable, while under the chroot the recorded pid is still `/bin/sh` running as root, mid-bootstrap. Each arm therefore drives a real turn, and the restart arm additionally asserts that the daemon, the anchor and the mount are **still alive** before the sweep runs — otherwise it silently degrades into a second copy of the crash arm.

**The gated real-dependency suites.**

The target therefore needs a Node that can run it and a base image meeting the POSIX assumption, and the shape is one container per registry row; one provider fronting many is [systems-protocol.md](systems-protocol.md) §11.

**`RUN_WIN_SMOKE=1` → `tests/win-smoke.real.test.mjs`, the Windows end-to-end smoke** (harness: `tests/winSmoke.mjs`). It boots cc natively on win32 against a real `claude` and Git for Windows, and drives it over REST, WS and `/mcp`.
- **Covers, as ordered steps sharing one server lineage:**
  - boot in the launcher's env shape (`claude OK`, no Git Bash warning);
  - dropped-feature refusals (`SYSTEMS_UNAVAILABLE` / `VOICE_UNAVAILABLE` and the hidden MCP tools);
  - a prompt and the `Bash` tool under Git Bash;
  - attachments;
  - plan mode's `plan_request`;
  - a forced interrupt;
  - worktree create → hook → sync → merge;
  - `project_bash` via `/mcp`;
  - busy and idle kill (tree gone, graceful stop, jsonl integrity);
  - an auto-continue restart and a gated restart (no orphaned shells);
  - `PROJECTS_ROOT` case drift;
  - self-update (`npm install` under Git Bash, then a restart that inherits stdio);
  - `taskkill /T` of the server pid;
  - no visible console windows.
- **Leak checks are per tree.** A step snapshots the process tree it is about to stop and asserts none of it survives. Entries are keyed on pid + creation time, so a reused pid can't match.
- **A child counts only if it is no older than its parent** (`isChildOf`, `tests/winSmoke.mjs`). Windows keeps a dead parent's pid as `ppid` and reuses pids, so a ppid match alone adopts unrelated processes, including another user's.
- **The server-pid kill runs while the worker is busy in a Bash tool**, so the snapshot holds the tool's shell. It proves nothing survives; it does not prove `/T` is what prevents a survivor. With a single-pid kill (no `/T`) the step stays green, because the CLI tears its own tree down when the server's death closes its stdin. To confirm the leak check is live, remove the busy-kill step's DELETE: it goes red naming the surviving tree.
- **The server under test is a disposable clone of HEAD**, behind a local bare origin that self-update pulls from. Uncommitted changes are not under test; the boot step prints a diagnostic when the checkout is dirty.
- **It boots cc with the real launcher's environment.** The work dir is laid out like an install: the clone at `app`, and a `node` junction to the running node's dir. The env comes from `launcherEnv` (`bin/windows-launch.mjs`), with a neutral git identity added.
- **Cost:** a handful of real-claude turns, a few minutes of wall time, and a full `npm install --ignore-scripts` of the clone (as the installer runs it).
- **Prerequisites:**
  - a Windows host with Node at the `engines` floor;
  - Git for Windows;
  - a signed-in `claude` on `PATH`;
  - `npm install` done in the checkout;
  - a non-elevated user.
- **It needs an interactive-type logon.** Under a network logon such as plain SSH, a standard user is refused process enumeration (WMI/CIM) and `taskkill /T`. The suite's `before()` probes this and fails with that message rather than with scattered leak failures. Run it from a desktop session, or from a process started with explicit credentials, such as PowerShell `Start-Process -Credential`. The server under test dies with that logon, so the whole run must happen inside one.
- **Run command:** `$env:RUN_WIN_SMOKE='1'; node --test --test-reporter=spec tests\win-smoke.real.test.mjs`. Not through `npm test` / `tests/run.mjs`, whose hang guard and `/proc` census are POSIX-only. Run it with `PROJECTS_ROOT` unset: the test plumbing's safe-store guard refuses a non-throwaway `PROJECTS_ROOT` at import, ahead of every check. With the flag set on a non-Windows host (and `PROJECTS_ROOT` unset) it fails loudly.
- **Run it before landing changes to** `src/platform/`, any spawn or kill site, `Instance.kill` / `shutdownForResumeSync` / `src/restart.ts` / the stop-live path, the `src/capabilities.ts` gates, or self-update (`src/selfUpdate.ts`).

**A remapped session can now run that family, and an unreachable API reds it fast**.
`tests/cliContractCase.mjs` launches every CLI child through `cliEnv()`, which — and ONLY when `ANTHROPIC_BASE_URL` is set — drops `ANTHROPIC_BASE_URL`, `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` from the child, so it falls back to whatever first-party credentials the host has stored — and, on a host that has none, to a legible 401.
Measured: no proxy-served model reachable here drives the assertions at all (**0 of 4** on each of two, one of them completing `is_error:false` having never called the tool), and an *unconditional* scrub takes a host authenticated solely by `ANTHROPIC_API_KEY` from passing to **401** — so the gate on the base URL is what makes the helper a no-op on an ordinary host, by construction rather than by assumption.
`ANTHROPIC_DEFAULT_HAIKU_MODEL` is deliberately left alone: at CLI **2.1.258**, the one version measured, an explicit `--model` is not subject to the alias remap, so it diverts only the session-title subquery's one cosmetic `unrecognized_model` line.
That is a third-party invariant at a single version and **no test pins it**, so a release that started honouring the alias for an explicit `--model` would surface either as a misleading gated failure or not at all, while silently re-breaking a remapped reviewer — re-take it on a newer CLI.
The accepted residual is a host whose ONLY route to a capable model is that proxy: it gets a legible 401 in place of a couple of hollow passes.
Separately, ANY condition that makes the CLI return an `api_error` — a bad key and a model the endpoint does not serve were both staged — costs this family a **90 s hang-guard SIGKILL with the file reporting nothing and a process leaked** unless it is discriminated: the `--input-format=stream-json` child holds stdin open by design and never exits, so an exit watcher would fix nothing and the bounded waits simply sum past `FILE_KILL_MS`.
`apiErrorReason()` is the discriminator, keyed on `api_error_status` and nothing else — `subtype` reads `"success"` on the error frame, and `is_error` reads true on the legitimate interrupt the detach suite's second case depends on.
It rejects `runClaude`/`runClaudeEnv` and every pending and subsequent `claudeSession` waiter, and the detach suite's one poll over cc's own state (not over a frame) breaks on `cli.apiError`.
`toolRegistry` is deliberately UNGUARDED: the one case it serves today resolves off the pre-API `system`/`init` frame and was measured passing truthfully under a 404 — guard a launch helper whose cases need the API to answer, leave unguarded one whose every case is pre-API.
`tests/systems-cli-api-error.test.mjs` pins that discriminator against four `result` frames captured verbatim at CLI 2.1.258 (`tests/fixtures/cli-result-{healthy,404,401,interrupt}.json`), plus one fenced SYNTHETIC case: on all four captures `api_error_status != null` and `terminal_reason === 'api_error'` agree exactly, so only hand-built frames can pin WHICH key is read.
It is the ONLY part of this family `npm test` or `gate:systems` executes.

On the arm measured here — `ANTHROPIC_BASE_URL` unset — it bills the host's own first-party account.

**The path invariant** (`tests/systems-absolute-paths.test.mjs`). `requireAbsolute` (`src/systems/system.ts`) refuses a relative path on every path-taking operation and on `exec`'s `cwd` — the one way a `cwd` reaches the wire — hard, because a relative path resolves against wherever the far side runs — the provider's process cwd, or cc's own for the in-process system — so a read answers about a file nobody asked for and a write lands in a directory nobody chose while reporting success. **It lives on the CONTRACT and both implementations call it:** the invariant is a property of cc's callers, not of a transport, and guarding only the wire would leave production `local` — the system every ordinary project uses — covered by `gate:systems` alone and not by `npm test`. The suite runs the same operation table against a directly-constructed `LocalSystem` and a `ProviderSystem` for that reason. `LocalSystem.exec`/`readFile`/`realpath` are `async` purely so a guard violation REJECTS rather than throwing synchronously: the two implementations of one primitive cannot differ on whether a caller's `.catch()` sees it. The suite pins the guard per operation and pins the call site it was breached at: the conventions sweep, which resolved only the system and composed `path.join('', …)` from a listing row with no path. Its two sweep tests `process.chdir` into a scratch directory first — unguarded, the defect overwrites `CONVENTIONS.md` and prepends to `CLAUDE.md` in whatever directory the run started in, which for this suite is the repo itself.

**The remote-placement suites.**
`tests/remoteSystem.mjs` binds the reference provider as a REGISTERED non-local system and hands back a temp dir on it to place trees under — deliberately OUTSIDE `PROJECTS_ROOT`, so any code that still composes a path from `projectsRoot()` lands where the tree is not and the assertion fails instead of passing by accident.
Built on that: `tests/systems-remote-placement.test.mjs` (one test per third-branch site — the resolver hub, the listing union, create, delete, adopt, worktree placement), `tests/systems-remote-e2e.test.mjs` (the whole lifecycle over the real REST + MCP surfaces, asserting the instance registry stayed empty), `tests/systems-remote-refusals.test.mjs` (every named refusal, plus the plugin cases, which plant a decoy manifest at cc's own spelling of the remote path so a wrong-machine read is caught rather than assumed absent), `tests/systems-descendants-surfaced.test.mjs` (the `processGroupSignal` fallback reaching `project_bash` and the post-worktree hook), and `tests/systems-registration.test.mjs` (verify-by-handshake and the session-root placement check).
Each disposes its live handles in `afterEach` (`disposeSystemHandles()`) — a provider process is a child, and the suite's leak guard is not optional.
**`CC_CONFORMANCE_PROVIDER`** (a JSON argv array) points the conformance suite at a THIRD-PARTY provider with no test edits — the suite appends each `CAPABILITY_CONFIGS` entry's `flags` and, in the `remotes`/`remoteDescriptors` fixtures, `--remote`/`--mirror`/`--exclude`, and it builds its fixtures with node's own `fs`, so it verifies a provider reaching the same filesystem as the test process.
The core fixtures are UNBOUND, so a provider serving only named targets must refuse them `ENOREMOTE` (`docs/systems-protocol.md` §8) and loses most of the battery until `CC_CONFORMANCE_REMOTE_ID` binds them — measured: an always-`remotes:true` provider went from a minority of rows to every row that is not skipped.
Binding presupposes `--remote <that id>=<root>` on the provider argv, and only ONE half of that is guarded: cc refuses a `remoteId` client-side when the handshake says `remotes:false`, and `assertNegotiatedCapabilities` turns that into a handshake refusal naming the flag rather than a battery of bare value diffs.
A DECLARED-BUT-DIFFERENT id is NOT guarded — it advertises `remotes:true`, clears the handshake, and reds the battery as value diffs whose actual side carries the provider's own `ENOREMOTE` naming the unknown target.
A third-party run SKIPS every row gated on `IS_REFERENCE_PROVIDER` — the cc-side fixtures, which use a provider to assert what CC does rather than testing the provider, so the gate is provider IDENTITY, not provider shape.
Each prints its own `skip` reason, and those reasons are the list.
§10 of that document is the third-party contract.

# Components: project and session stores, conventions

Project resolution, the session store, the conductor and conventions modules, and small shared server helpers.

## `src/claudeConfigDir.ts`

`claudeConfigDir()`, the CLI's config-dir lookup (`CLAUDE_CONFIG_DIR`, else `~/.claude`). Builtins-only leaf: imported by cc's readers of the CLI's state and by the e2e harness (`web/e2e/harness/`), which must not load the rest of `src/`.

## `src/projects.ts`

FS ops on `<projectsRoot>/`; the store-root helpers (`projectsRoot`, `orchStoreRoot`, `projectStoreDir`, `localWorktreesRoot`, `pluginsRoot`), the record reader (`readProjectRecord`, `validateName`, the record types), the registry and project lifecycle (both below) live in `src/storeRoot.ts`, `src/projectRecord.ts`, `src/projectRegistry.ts` and `src/projectLifecycle.ts`, which `projects.ts` re-exports, while `projects.ts` owns transcript-path resolution (`claudeProjectsRoot`, `remoteConfigDir`, `transcriptRoot`, `encodeCwd`) and session listing and location.

**`src/projectRegistry.ts`** holds the registry: resolution (`resolveProjectDir`, `getProject`, `tryResolveProject`, `placementToken`, `validateProjectRef`), the store-derived listing (`listProjects`, `findSelfProject`, `projectsBySystem`), the record writers (`registerProject`, `writeProjectMeta`, `writeProjectRecord`) and the workspace registry in `<store>/workspaces.json` (`listWorkspaces`, `summarizeWorkspaces`, `addWorkspace`, `removeWorkspace`, `renameWorkspace`, `setProjectWorkspace`).
It must never import `projects.ts`: `src/projectLifecycle.ts` imports `heldNameReason`, `projectKeyCollisionReason` and `writeProjectRecord` from it, and those three are not re-exported.
Its `systems/transcriptKey.ts` import stays lazy, because that module statically imports `projects.ts`.

**`src/projectLifecycle.ts`** holds project lifecycle: creation (`createProject`, with `validatePlacementInput`, the CLAUDE.md and CONVENTIONS.md seed and `commitScaffold`), adoption (`adoptProject`, `heldRecordVerdict`, `staleDiscards`, `deliverAdoptedConventions`), the target change (`setProjectRemote`, `validateRemoteId`, `normalizeSystemPath`) and deregistration (`getProjectForDelete`, `deleteProject`, `removeProjectStoreDir`); `projects.ts` re-exports its public names.
It must never import `projects.ts`, and it reaches `worktrees.ts`, `projectsCache.ts` and `projectClaudeMd.ts` only by dynamic import: `worktrees.ts` and `projectClaudeMd.ts` statically import `projects.ts`, so a static edge to either closes a cycle.

**`resolveProjectDir(name)` is THE resolution chokepoint** every project path in the app comes from, and it is **ONE record read with no filesystem probing**.
`readProjectRecord(name)` answers `null` for an unregistered name and the record's `location` otherwise; `placementOf` turns that into `{system, remoteId, path}`, and the path IS the answer.
**THE RECORD IS THE REGISTRATION for every kind of project**, so resolution does not depend on the tree still existing — which is what lets a vanished, unmounted or unreachable tree still list and still be deregistered instead of reading as a project that never existed, and what stops a same-named directory in the projects root shadowing a tree that lives elsewhere.
A record that exists and cannot be PARSED **throws 500 naming the file, never 404**: with the record as the sole registration, degrading it to an empty one would silently unregister a live project.
It also resolves the project's **System** and returns the handle beside the path (`{path, system}`), so `getProject` hands every caller the seam every project-scoped operation goes through — see [`src/systems/`](systems.md#srcsystems).
`getProject` is `validateName` + that, plus the 404; `validateName`'s refusal is the neutral regex one, since it also guards names being created — `validateProjectRef(name)` is the same rule for an argument ADDRESSING an existing project, whose refusal names the NAME `list_projects` prints rather than a path, and MCP `dispatch` applies it to every core tool's non-empty `project` argument; `tryResolveProject(name)` → `{system, unreachable}` is `resolveProjectDir` for the LISTINGS, **where a refusal is a value rather than a throw.**
Every listing fans its per-project work out through one `Promise.all`, so an unguarded resolve inside it lets one project's refusal reject the whole batch and break the list for every OTHER project — contradicting the guarantee `listProjects` already makes for a record it cannot parse ("the rest of the project list must still render").
It resolves the whole PROJECT rather than just its system, because a record naming a REACHABLE system with no path resolves its system fine and still has no tree to measure.
**Four consumers:** `computeGitFacts` (`src/routes/projects.ts`, behind `GET /api/projects`), MCP `list_projects` and `list_sessions`' group headers (`src/mcp/handlers.ts`), and plugin discovery (`src/plugins/registry.ts`, where an unresolvable project contributes no plugin rather than falling back to reading cc's own disk at the same path).
An **addressed-by-name** caller keeps `resolveProjectDir`/`resolveSystem` and their throw — there the refusal IS the answer.
It catches everything, not just the refusals: a listing owes the rest of the list the same duty for an unexpected fault.
The degraded row is **kept, not dropped** (a project that vanishes reads as deleted) with `systemUnreachable` carrying the reason, `isGitRepo` **absent rather than `false`** (`undefined`, which `deviations` skips and `JSON.stringify` omits — "could not look" is not the claim "not a git repo"), an all-null `mergeStatus`, and its worktree registrations still listed (store-derived, no System needed) with undiverged merge status.
Pinned per site by `tests/systems-listing-degrade.test.mjs`.
A fifth consumer, `findSelfProject`, skips such a row outright: it has no path to compare.
**`listProjects({includeConduct?})` is STORE-DERIVED and reads the projects root not at all** — one row per `<store>/projects/<name>/project.json` that parses, `validateName`-filtered, with `.conduct` skipped unless a caller opts in (`findSessionLocation` and `listArchivedGroupedByProject` do, rather than synthesising a row).
That is what makes a container directory in the root possible: nothing in the root is a candidate.
A record it CANNOT parse is still listed — with an empty `path` and a `degraded` reason — because invisible would also mean undeletable, which is the disappearing row the degraded-listing contract exists to prevent.
`ProjectInfo` is `{name, path, workspace, system, remoteId, degraded?}`: `path` is the ONE path field (the tree's path on whatever machine it is on), there is no kind flag, and there is deliberately no system HANDLE, because both REST and MCP spread it into a response body.
`readProjectRecord` returns `{workspace, location}` and THROWS on a malformed file; `writeProjectRecord` merges over its result, so a location the reader forgot would be deleted by the next unrelated write — and with the location gone the project is unregistered.
**`registerProject(name, location)` is the ONE guarded writer** every creation path funnels through (`createProject`, `adoptProject`, the Library install, the `.conduct` bootstrap): `validateName` → dot-leading refusal (`.conduct` excepted — `.worktrees`, `.plugins` and the store are cc's own, and MCP `create_project` reaches creation through `validateName` alone) → held-name → transcript-key collision → write.
A guard the one chokepoint does not enforce is not an invariant.
**`setProjectRemote(name, remoteId, {liveInstanceIds})` is the one mutation path for the target**, so every surface (`PUT /api/projects/:name/remote`, MCP `set_project_remote`) inherits its guard rather than each carrying a copy.
It refuses **409 `PROJECT_PLACEMENT_IN_USE`** while the project has live sessions or registered worktrees, NAMING both.
The two halves are not equally strong and the code says so: worktrees are an **invariant** (`registeredWorktreeNames`, read inside the function — store-only, no system reached and no filtering by what git currently reports, so neither a caller nor a system being down can change its answer), while live instances are a **caller contract** (`src/instances.ts` imports this module, so the manager must be injected; a required non-defaultable getter raises the bar, but a caller supplying `() => []` still defeats it).
The worktree half is what makes `WorktreeMeta`'s deliberate absence of a stored target safe — a worktree re-derives `(system, remoteId, path)` from its parent on every operation, and the parent cannot move while a registration exists.
On a permitted change it verifies the new target through `systemById` BEFORE persisting, writes the record and invalidates `projectsCache` — it removes NOTHING local, because there is no cc-owned copy of the old target to go stale.
`projectsBySystem()` groups `{name, remoteId}` by the non-local system their record names — the target comes with the name because one row can serve many, and the name alone would not say which holds it — (the still-referenced check behind Settings → Systems' delete refusal); it reads `listProjects`, so a store directory left behind by a deleted project is invisible: without a record it is not a project at all.
An adopted project's stored path is the target's **REALPATH** — load-bearing, not tidiness: the Claude CLI encodes `~/.claude/projects/<encoded-cwd>/` from `getcwd()` (always the realpath) and walks `CLAUDE.md` upward along the realpath, neither with an env lever, so a logical-path project would strand every resume.
`adoptProject(name, target, {system?, remoteId?, onStaleRecord?})` writes the record after every validation (soft refusals returned with a `code`, never thrown) then delivers `ensureProjectConventionsMd` non-fatally.
**NESTING UNDER THE PROJECTS ROOT IS LEGAL** — the old "target is inside the root" refusal is gone, and it is what makes a container directory work; what stays refused is a target that CONTAINS the root (`TARGET_ALREADY_MANAGED`) and one inside cc's own state — `orchStoreRoot()`, `localWorktreesRoot()` or `pluginsRoot()` (`TARGET_IS_CC_STATE`; `.plugins` is not optional there, because the Library's post-clone step is best-effort and a half-installed checkout can persist under it).
The duplicate test compares **(system, remoteId, path)** for BOTH kinds — two targets each hosting `/app` are two different trees.
A held name whose record's path no longer resolves is **`PROJECT_EXISTS_STALE`** carrying `heldPath` + `discards`, and `onStaleRecord: 'relocate'` (repoint the record, keep the store subtree, invalidate `projectsCache` — the cached git facts were measured at the old path — and repair the project's worktrees in both directions: `git worktree repair` from the new tree for the gitdir back-references, and a `parentPath` rewrite for every root-based registration, both best-effort so a relocation that stands is never answered with a 500) or `'replace'` (drop the store subtree, register afresh) resolves it.
A `relocate` is **refused `PROJECT_PLACEMENT_IN_USE`** while a project ON A SYSTEM has registered worktrees, the same shape and reason `setProjectRemote` refuses a target change: `worktreePathFor` derives a remote checkout's path from the project's, the checkout does not move with the tree, and stored-versus-derived would diverge permanently — which disarms the transcript guard, whose whole correctness is that it re-derives.
A LOCAL relocate needs no such guard: cc's `.worktrees` root does not depend on where the project's tree is.
Then: a system that could not ANSWER makes staleness undecidable and gets **`PROJECT_EXISTS_UNRESOLVABLE`** with no relocation offered.
Naming a `system` runs the realpath, stat and `git rev-parse --show-toplevel` ON THAT SYSTEM — and so does the `--git-dir` probe, on the branch where `--show-toplevel` failed; together they decide only the enclosing-repo and no-work-tree questions, a plain non-git directory being adoptable.
The local containment tests are SKIPPED for a remote adopt (a path on another machine neither is inside cc's root nor contains it, however the strings compare).
`createProject(name, {conventionsDoc?, system?, remoteId?, systemPath?})` takes the same triple (`validatePlacementInput` is shared, and requires system+path both or neither, absolute; `remoteId` is optional even with a system and is refused without one, validated by `validateRemoteId` — deliberately NOT `isSlug`, since container names, hostnames and VM ids carry `_` and `.`): the `mkdir` and seed files happen on the system, as do `git init` and the scaffold commit where git is available, and the record is written only AFTER the mkdir succeeds, so a refused create adopts nothing that was already there.
**`deleteProject(name, {deleteDirectory})` DEREGISTERS**: `removeProjectStoreDir` plus an `fs.rm` of `<projectsRoot>/.worktrees/<name>/`, and the TREE goes only when the caller ticks `deleteDirectory` — one behaviour for every project, whichever way it was registered.
For a project on a system that tick is refused **400**: cc owns no area on another machine, and removing a directory there needs its own design.
It deliberately does not resolve the system, and neither does the ROUTE in front of it — `getProjectForDelete` addresses the project by its record alone (and tolerates one it cannot parse, since deleting is the repair for exactly that state), because `getProject` resolves the system and putting it there made a project on a down system undeletable, deadlocking it against its own system row's 409.
Returns `{name, path, system, remoteId, directoryDeleted}`.
The route's cascade runs `removeAllWorktreesForProject` with **`force: false`** and PROPAGATES its refusals — a dirty, dirty-unknown or depended-on worktree 409s the whole delete rather than being force-removed; a checkout that is not there, or whose parent is no longer a repo, has nothing to protect and is dropped instead, which is what keeps a project whose tree vanished out-of-band deletable.
A refusal raised AFTER `git worktree remove` succeeded (the best-effort branch delete) does not abort the cascade: whether the registration is still there is the state that says which happened, and it says so without matching on message text.
A REMOTE project's worktrees are unregistered with no git run — that would delete a checkout and a branch inside the user's repo.
Deleting ONE worktree still removes it: cc created that directory and the user asked for that directory.
The cascade order (worktrees before the project) is load-bearing: deregistering first turns `listWorktrees` into a 404 and orphans both the checkouts and the registrations.
`createProject()` always ATTEMPTS `git init -q` in the new dir (never behind a repo check, though the repo exists only if the init succeeded — the `mkdir` above it proves the dir is new; an `isGitRepo()` guard would be wrong, it walks UP and would skip the init whenever the projects root itself sits inside a repo) before seeding any file.
A failing init does not throw: `runGit` is called inside a `try` (it throws 504 `GIT_TIMED_OUT` / 502 `GIT_DID_NOT_RUN` before returning), a non-zero code or a throw becomes a `gitSkipped` reason on the 201 result and one `console.warn`, seeding still runs, and `commitScaffold` is not called — throwing would be a 500 after `registerProject`, leaving a registered half-project with no seed files whose retry is a 409.
Pinned by `a git init that fails still creates the project, seeded and without a repo`, `a git init that throws still creates the project and attempts no commit` and `POST /api/projects with no git on PATH creates a non-git project` in `tests/projects.test.mjs`, and `a system with no git binary creates a non-git project rather than refusing` in `tests/systems-remote-placement.test.mjs`; `runGit` comes from a lazy `await import('./worktrees.ts')`, since worktrees.ts statically imports this module.
It then ends at `commitScaffold(system, full, runGit, scaffolded)` — `git add -A` (no pathspec, so the commit stays forwards-compatible with whatever a future scaffold writes), then `git add -f --` the paths creation actually wrote (`scaffolded`, appended at each write site rather than listed up front), then `git commit -m SCAFFOLD_COMMIT_MESSAGE` — which is what makes a brand-new project worktree-ready without a human commit.
`-A` decides the scope and `-f` guarantees the floor: `-A` alone honours the user's `core.excludesFile`, so a global ignore listing `CLAUDE.md` would drop it from the commit and a worktree branched off that HEAD would check out no `CLAUDE.md`, losing the `@CONVENTIONS.md` import chain for every worker in the project.
**The commit is preceded by a repo-identity precondition**, established before anything is staged: `git rev-parse --absolute-git-dir --show-toplevel` must answer with `<realpath(full)>/.git` and `realpath(full)` — the realpath because git resolves symlinks in both answers, and both halves because the git dir says which repository the commit lands in while the top level says which working tree `add -A` sweeps.
An ambient `GIT_DIR` already sends the `git init` to a foreign repo (the pre-existing dent pinned by `tests/project-initial-commit-foreign-repo.test.mjs`); without this check the staging then wrote a stray `Initial commit` onto that repo's branch carrying a tree that DELETED every file it had tracked — measured, and the reason target identity is a precondition here rather than something noticed afterwards.
Identity is probed per field and `SCAFFOLD_AUTHOR_NAME`/`SCAFFOLD_AUTHOR_EMAIL` injected as leading `-c` pairs in the argv only for whichever of `user.name`/`user.email` is unset — never `opts.env` (a frame `env` replaces the far side's environment) and never a `git config` write, so the fallback outlives nothing; `runGit`'s `sub` extraction already skips `-c` values, so a refusal still names `commit`.
The whole block is non-fatal: its `try` wraps the `runGit` CALLS (they throw `GIT_TIMED_OUT`/`GIT_DID_NOT_RUN` rather than returning a code), and any failure is a `console.warn` leaving creation successful and HEAD unborn — throwing would 500 over a project whose directory, record, repo and seed files all already exist.
No `--no-verify` and no gpgsign override.
`adoptProject` gains nothing from this: it never inits and never commits, so an adopted repo's history stays the user's. `findSessionLocation(sessionId)` probes every cwd every registered project + worktree ADMITS and returns `{project, worktreeName, cwd}` — **`cwd` REQUIRED**, being the directory the transcript was actually found in, because a caller that re-derives it from the project tree looks on the OTHER MACHINE for a project on a system and reads an empty transcript; an optional field would invite `hit.cwd ?? proj.path`, which is that bug.
It sweeps ONE place list ONCE: each place's cwd, which is its tree path on whatever machine it lives on — `worktreePathFor` for a worktree, the registered path for a project.
There is no second pass and no local-vs-remote split: a place admits exactly ONE candidate cwd.
A SET of candidates — with a raw remote path only ever a demoted fallback — is what a remote session running in a cc-owned local image would need, and there is no such image.

## `src/sessionActivity.ts`

`lastActivityOf(path, stat)`: when a session transcript was last ACTUALLY active, as epoch ms.
The ISO `timestamp` on the LAST timestamped record in the jsonl (last in file order, not newest by value — records are appended in real time, so the two differ only where interleaved sidechain records land a few ms out of order), found by a bounded 64 KB tail read; falls back to `stat.mtimeMs` when the tail holds no timestamped record.
**Not mtime**, because the CLI appends untimestamped bookkeeping records (`last-prompt`, `mode`, `ai-title`) as its process exits — so a mass subprocess exit (a server drain/restart) stamps every live session's file within the same millisecond, collapsing distinct sessions into one indistinguishable minute days after they actually stopped.
Feeds `SessionRow.lastActivity`, `ArchivedSessionRow.lastActivity` and `summarizeSessions().lastActivity`, so every surface reports one definition of recency.
Results are memoized in a process-lifetime LRU (`createLastActivityCache({max})`, cap `LAST_ACTIVITY_CACHE_MAX`) keyed on the path with a `(dev, ino, ctimeMs, mtimeMs, size)` validity tuple.
`ctimeMs` is what makes it sound — it cannot be rolled back from userspace, so it catches even an in-place rewrite that restores mtime and preserves size; `mtimeMs`/`size` catch the common case (an append) without depending on ctime semantics.
`dev`/`ino` are **redundant** against every writer in this repo (the two that replace a transcript go tmp→rename, and a rename-over sets a fresh ctime) and are kept only as a guard against a future writer that replaces a file without moving ctime — no test isolates them, because with ctime in the key the case isn't constructible.
No stale entry is reachable, so there is no TTL.
**In-memory only, never persisted.**
Both callers already stat every file, so a steady-state fan-out across every project costs readdir + stat + a Map lookup — the property the "just readdir + stat, no opens" walk in `summarizeSessions` was protecting.

## `src/sessionStore.ts`

THE session store: one global file, `<store>/sessions.json`, keyed by a session's **public id**. Every per-session fact cc records lives on that session's record, split by what it describes:

```json
{ "version": 2, "sessions": { "<publicId>": {
  "current": "<backingId>",
  "segments": [ { "id": "<backingId>", "reason": "initial|renew|prune", "at": "<iso>",
                  "dropped": true, "persistent": true, "archived": true } ],
  "title": "…", "mode": "plan|bypassPermissions",
  "backend": { "backend": "…", "model": "…|null", "contextWindowTokens": 123 },
  "summaries": { "<tier>": { "summary", "generatedAt", "messageCount" } },
  "conducted": true, "turnEndSeq": 3, "viewedSeq": 2,
  "parent": "<caller publicId>", "project": "…", "worktree": "<worktreeName>",
  "modelSwitches": [ { "id": "<uuid>", "at": "<iso>", "segment": "<backingId>", "afterUuid": "<jsonl uuid>|null",
                       "from": "…", "to": "…", "ok": true, "error": "…" } ] } } }
```

| Kind | Fields | Keyed by | Accessors |
|---|---|---|---|
| Session fact | `title`, `mode`, `backend`, `summaries`, `conducted`, `turnEndSeq`, `viewedSeq`, `parent`, `project`, `worktree`, `modelSwitches` | the record (public id) | `appendModelSwitch`/`getModelSwitchesForSegment(backingId)`/`reanchorModelSwitches`, `getTitle`/`setTitle`, `getSessionMode`/`setSessionMode`, `getSessionBackend`/`setSessionBackend`, `getSummaries`/`setSummary`, `isConducted`/`markConducted(id, {parent?})`, `setSessionPlace(id, {project, worktree})`, `getTurnMarks`/`recordTurnEnd(id)`/`markViewed(id, seq)`; `parent`/`project`/`worktree` are read by `src/conductorSpawns.ts`, `project`/`worktree` also by `findSessionLocation`'s recorded-place fallback and `listArchivedGroupedByProject` (`src/projects.ts`) |
| Transcript fact | `persistent`, `archived` | the segment (one per jsonl) | `isPersistent`/`setSegmentPersistent(id, on, {owner?})`, `isArchived`/`setSegmentArchived(id, on, {owner?})` |
| Identity | `current`, `segments[].id/reason/at/dropped` | the record | [`src/sessionLineage.ts`](instances.md#srcsessionlineagets) |

- **Turn marks** (`turnEndSeq`, `viewedSeq` — the unread indicator's one fact, unread ⇔ `turnEndSeq > viewedSeq`): absent means `0` (a record without them reads read, so none needs a migration); positive integers only, anything else dropped on parse. `recordTurnEnd` is one store write per real `turn_end` (`Instance._handleStdoutLine`, beside `_writeSessionMetadata`'s per-turn write; no precheck, it always changes), registered with `trackLineageWrite` so a read after the turn sees it. `markViewed` raises `viewedSeq` to `max(viewedSeq, min(seq, turnEndSeq))` with a no-op precheck; its one caller is `src/sessionViewed.ts`. Both are record facts, so they survive a rotation, archive and restore, and go with the record on delete and boot cleanup.
- **`version`** (`SESSIONS_DOC_VERSION`) is written first by every serialize; the parser does not gate on it. Its one reader is migration 0043's already-applied probe, since a store of only normal sessions carries no flag either way.
- **Optional fields are present only when set** (`true`, a non-empty value, or a positive count); the parser keeps a flag only when it is `=== true` and drops every malformed fact, segment, and any record left with no live segment. `markConducted`'s `parent` is a patch: a null one never clears a recorded one. `setSessionPlace` sets both fields exactly: a null `worktree` (a project-root session) leaves the record without one. A backend `model: null` means backend-known, model-unknown (resume falls back to the jsonl); no `backend` means the identity `claude` backend. `contextWindowTokens` is a fallback only — live registry resolution wins.
- **Record invariant**: a persisted record has at least one live (non-`dropped`) segment and `current` is live; a mutation that would leave none deletes the record, and every session fact with it. Only the explicit session delete (`deleteSessionForCwd` → `dropSegment` without `unlessLast`) does that. The one other deleter, `removeSessionRecords(pick, {snapshotFile})`, removes WHOLE records at boot for `src/sessionCleanup.ts` (below).
- **Resolution.** Readers take a public key first, then a LIVE segment's owner; unknown ⇒ no facts. Session-level writers (`ensureRecord`) take a public key, then any segment of the FULL chain (tombstones too, so a write never forks a second record for a known id); an unknown **minted-shaped** id (`isMintedPublicId`, `src/identifiers.ts`) is refused (no write, one `console.warn`, return `false`/`null`); any other unknown id creates the base-case record `{current: id, segments: [{id, reason: 'initial'}]}`. Segment-level writers (`ensureSegment`) take a backing id: a known segment wins but a dropped one is refused; an `owner` whose record exists WITHOUT this segment is refused (the rotation write that adds it has not landed or failed — the next per-turn write retries); a minted-shaped id is refused; anything else creates the base-case record. Instance-originated segment writes always pass `owner: this.sessionId`. `fileFacts(index, filename)` → `{publicId, record, segment}` is the listing's pure per-file lookup.
- **Writes**: `mutateSessions(op, id, apply, precheck?)` = `serialize` → precheck → `withLock` → strict re-read → `apply` → write → `.bak` refresh → cache. One per-process `serialize` chain and one lock (`sessions.json.lock`) for every writer, lineage included. The **precheck** runs inside `serialize` (so it sees every earlier same-process write) against the cached doc and returns without locking or writing when nothing would change — the per-turn `system/init` mode write and `turn_end` persistent/conducted writes cost one `stat` each in steady state. A failure anywhere in the locked half is logged ONCE at the store boundary (`sessionStore: <op> <id> failed: <msg>`) and rethrown; the cache is NOT updated, so the next per-turn call's precheck still sees the old value and retries — the self-heal for mode/persistent/conducted. Fire-and-forget callers keep their `.catch(() => {})`.
- **Read cache**: the last doc read or written plus the file's `stat({bigint:true})` signature (`ino`, `size`, `mtimeNs`, `ctimeNs`); a matching stat serves the cache, anything else re-reads. The doc is shared with the cache — readers must not mutate it. Residual: an in-place same-size rewrite on the same inode within one timestamp tick (every cc writer renames, which changes the inode). A test that rewrites `sessions.json` after the store has read it writes tmp + rename.
- **Read barrier (kick-anchored).** `trackLineageWrite(p)` registers a write kicked fire-and-forget onto an instance's `_lineageWrite` chain (`Instance._kickLineageWrite`: the `/clear` rotation item from `system/init`, and `dropSegment(…, {unlessLast:true})` from `loadHistory`'s ENOENT branch). `loadSessions()` — the chokepoint every async reader funnels through — awaits ONE `Promise.all` snapshot of that set, so a read sees every write kicked before it began; segment-level writers await it too, so a `turn_end` `setSegmentPersistent(newId)` after a typed `/clear` lands on the recorded segment. Session-level writers don't (the public id doesn't move). A rejected kicked write is swallowed by the barrier (its owner is `Instance._lineageError` → `flushLineage` → `renew_error`). `mintPublicId` is awaited in `launch()` and deliberately untracked; so are the spawn-time facts (persistent, backend, conducted, mode): `Instance.spawn()` kicks them synchronously and returns their settled promise (never rejects), `launch()` awaits it, so a read ordered after an awaited `launch()` caller (`create`, REST 201, MCP `spawn_instance`, rewind, respawn, prune, restart-resume) sees them, and a read racing an in-flight launch may miss them. Each of those writes (up to four per spawn) takes the store lock on its own and spends its own `LOCK_RETRY_MAX` budget, so a lock held by another process delays `launch()` by up to the sum of the budgets, not one. A write that fails (e.g. a store lock held past `LOCK_RETRY_MAX`) is logged by the store and does not fail the launch; `_writeSessionMetadata` re-asserts persistent and conducted at the next turn end. **Deadlock rule**: nothing reachable from a kicked write (`recordRotation`, `retireSegment(s)`, `dropSegment`) may await the barrier, and every mutation re-reads with the strict loader, never `loadSessions`.
- **Recovery**: a rolling `sessions.json.bak`, refreshed inside the lock after each write. Lenient reads serve `.bak` when the primary is missing or corrupt; the strict in-mutation read quarantines a corrupt primary to `.corrupt-<pid>-<ts>` and recovers from `.bak`; absent primary AND absent `.bak` = legitimately empty; any other I/O error (EACCES, EISDIR) aborts the mutation. The file is **always written, never unlinked** (`{"version":2,"sessions":{}}` when empty), so an absent primary always means external loss. The `.bak` refresh is skipped when the write drops the record count **or** the archived-segment count by more than one relative to the current `.bak`: no single mutation removes more than one of either, so such a write has a wrongly-small base (a leaked or blipped read). `removeSessionRecords` passes `refreshBackup` an `expectedDrop` of exactly the records and archived segments it removed, widening the tolerance by that much for that one write, so a bulk removal neither freezes `.bak` nor masks a wrongly-small base. A superset rule would freeze `.bak` after the first delete or un-archive, and a recovery from it would lose every fact written since. Absent/corrupt `.bak` → written; unreadable → left alone.
- **Growth** is bounded only by the two deleters: a record stays until the session is explicitly deleted or the boot cleanup finds no transcript left in its lineage.
- **`removeSessionRecords(pick, {snapshotFile})`** — `serialize` → `withLock` → read the primary's raw bytes → `writeFileAtomic(snapshotFile, raw)` (every call, byte-exact, before any change; a failed snapshot throws with the store untouched) → parse → `pick(doc)` names public ids → delete them → write → `.bak` refresh with `expectedDrop` → cache. Returns `{removed, skipped?}`. Absent primary: warn, `skipped: 'store absent'`, no snapshot. Corrupt primary: snapshotted, then warn and `skipped: 'store corrupt'` — no quarantine, no write (the next ordinary mutation's `loadStrict` quarantines it). Empty pick: no primary write.
- The vocabulary lives beside it: `src/sessionModes.ts` (`MODES`, `DEFAULT_MODE`, `DEFAULT_RESUME_MODE`, `effectiveResumeMode`, `resumesHot`), `src/sessionTitles.ts` (`TITLE_SCHEMA`, `FORK_TITLE_PREFIX`, `forkTitle`, and a re-export of `MAX_TITLE_LEN`; `MAX_TITLE_LEN` and `normalizeTitle` are defined in the leaf `src/sessionTitleText.ts`, and `applySessionTitle` — the one title write behind the REST rename, `set_session_title`, `spawn_instance`'s `title` and `Instance.forkAtUserMessage` (the fork's starting title): stores on the session any id form names and mirrors the stored value onto every live instance of it), `src/sessionViewed.ts` (`applySessionViewed` — the one `markViewed` caller, behind `POST /api/sessions/:sid/viewed` only: stores the marker and pushes the stored marks onto every live instance through `Instance.setTurnMarks`, which max-merges both counters and on a change emits `turn_marks` — **never `status`**: the turn-end write lands asynchronously, often after a kill, and every `status` costs a projects refetch on every client.
  The manager re-emits it and `src/wsHub.ts` turns it into `{t:'instances'}` alone (pinned by `tests/session-viewed.test.mjs` "setTurnMarks emits turn_marks and never status" and "POST /viewed sets the marker and broadcasts instances, not projects, to every client"; `tests/playbook-enforce.test.mjs` "enforce: a stage binding survives a renewal" counts the one retire).
  **Browser-only by construction** — `src/routes/sessions.ts` is its one importer and nothing under `src/mcp/` reaches it, pinned by `tests/session-viewed.test.mjs` "the viewed writer is imported by routes/sessions.ts alone"; `Instance._hydrateTurnMarks` reads the marks at every launch), `src/sessionSummaries.ts` (`SUMMARY_LENGTHS`, `SummaryLength`, the tier normalizers).
  **Mode rule**: a resume comes up in the recorded mode, else `DEFAULT_RESUME_MODE`; everything reporting on a resume reports the EFFECTIVE mode (`SessionRow.resumeMode`, the `resumes-hot` flag), so an unrecorded session reads as hot. There is no backfill: a session predating the store has no recorded mode and resumes `bypassPermissions`. The default is applied in `_doCreateResolved`, so the sidebar one-click resume and the anchor auto-resume (neither names a mode) inherit the recorded mode, and a crash-respawn relaunches in the mode it was running. An explicit `mode` wins, except against a playbook stage that pins `mode` ([protocol/playbooks.md](../protocol/playbooks.md#playbooks)).
  `writeSessionMetadata` (`src/transcript.ts`) writes the CLI jsonl's `permission-mode` marker and refuses a value outside `MODES`; that marker is not an input to this store.
- **Writers**: `Instance.spawn` (segment `persistent` with `owner`; `backend` on every backend, `claude` included — `_recordBackend`, which `setModel` and `_trackModel`'s adoption of a changed model also kick fire-and-forget; a missing record reads as `claude`; `project`/`worktree` for **every** session (`setSessionPlace` — the worktree name as `InstanceManager.liveOwnedBy` reports it); `conducted` + `parent` when conducted; the mode via `setSessionMode`, called directly; all five writes are collected into the spawn's `facts` and awaited by `launch()`), `_recordMode` (`system/init`, `setMode`; fire-and-forget), `_runRestartSwitch`'s rollback (`_recordBackend`, awaited), `_writeSessionMetadata` (per-turn persistent/conducted re-assert, a no-op in steady state), `makePersistent` (persistent on), `applySessionTitle`, the summary POST route, `archiveSessionForCwd` / both restore routes (`setSegmentArchived`). `storeLock.ts` provides the cross-process advisory lock (`withLock()`, `O_EXCL` create): a held lock is reclaimed **only when the owner PID is dead** — a live owner is never evicted on age, because post-restart CPU throttle on Termux (~10–75×) can starve a live holder for many seconds mid-write, and evicting it lets two writers drop each other's entries; release is ownership-token-checked. `pendingArchive.ts` sweeps `<store>/pending-archive.json`; `resumeManifest.ts` and `pendingContinue.ts` write their files via tmp-write + `renameSync`. ## `src/pristine.ts`

the pristine conductor's presence and abandon decision (user behaviour: [features/session-actions.md](../features/session-actions.md) → Pristine conductor). `PristineTracker`, owned by `InstanceManager` as `instances.pristine`, keeps per pristine instance a **presence set** of viewer sockets and the **last draft** text; `isHiddenPristine(i)` is `i.pristine && i.draftTitle === null`; `draftTitleOf(text)` collapses whitespace runs to one space and caps through `normalizeTitle` (`src/sessionTitleText.ts`).
- **State.** `Instance.pristine` is set only by a `pristine: true` create (`POST /api/instances`, which accepts it only on a fresh normal `.conduct` spawn) and cleared, with `draftTitle`, by `Instance._endPristine()` — called synchronously at the top of `promptOrQueueSteer()` and in `prompt()` right after its `not running` throw, before any `await`, so it covers every sender (WS `prompt`, card answers, MCP `send_prompt`, internal prompts). Its `pristine_ended` event makes the manager `forget` the presence and emit `list_changed`. In memory only: never persisted, no migration.
- **Presence.** `view(id, ws)` adds the socket and cancels the window; `draft(id, text)` records the last draft; `leave(id, ws, text?)` records `text` when given and removes the socket; `drop(ws)` (the wsHub's socket `close`) removes the socket from every set. All are no-ops on an instance that is not pristine. `track(id)`, run once the create's launch returns, arms the window for a conductor no tab has viewed yet.
- **Abandon.** Runs at once when a `leave` empties the set; after `pristineGraceMs` when a `drop` empties it or nobody ever viewed it. A pristine instance whose last draft is blank (`text.trim() === ''`) is reaped (`InstanceManager.reapPristine`: re-checks `pristine` synchronously, then `remove(id)`); otherwise `listPristine` sets `draftTitle = draftTitleOf(text)` (overwriting an earlier one) and emits `list_changed`. The rule reads only "still pristine", so a conductor already listed under a draft is reaped by a later blank abandon: once listed it is never hidden again, but it can still be removed until its first prompt.
- **Grace window: `PRISTINE_REAP_GRACE_MS`.** A reload re-announces presence only at the end of the client's first connect — `refreshProjects` (the project reads, `/api/projects` among them with git status for every project, some on remote systems), then `refreshInstances`, then the anchor lookup — and each list read can take up to twice `READ_TIMEOUT_MS` (`web/src/app/controller.ts`). The window covers a reload whose project read times out once and retries, plus a network blip; a hidden conductor spends nothing while it waits, and a short window would kill one in front of the user.
- **Test seams.** `InstanceManager.pristineTimers` (`{setTimeout, clearTimeout}`, the globals by default) and `pristineGraceMs` (the constant by default), both read when a window is armed, as `relaunchGraceMs` is read per relaunch. `tests/pristine-conductors.test.mjs` installs recorded timers and fires them; nothing sleeps the window out.
- **`listVisible()` versus `list()`.** `InstanceManager.listVisible()` is `list()` minus hidden pristine instances, and it is what every list **payload** serves: `GET /api/instances` and MCP `list_sessions` / `describe_session` (live branch). `list()` stays unfiltered, and lifecycle code iterates `list()` or `byId` — `shutdown()`, the sync stops, the restart drain, the overage and idle-wake helpers — so teardown kills a hidden conductor (and removes it, below) and a new internal caller cannot lose sight of one. A new payload surface uses `listVisible()`. The exclusion sets (`liveBackingIdsForPlace`, `normalSessionIdsForPlace`) stay unfiltered on purpose: filtering them would surface the session as a disk row.
- **Restart and boot.** `finishDrain` (`src/resumeRestart.ts`) skips every pristine instance, hidden or drafted, so none is carried in `pending-resume.json` (it has no transcript to `--resume`). The store record a restart leaves behind lists nowhere — `/api/archived`, `.conduct/sessions` and `locate` all stat-gate on the transcript — and `cleanupSessionsWithoutTranscripts` drops it at a later boot once it is past `CLEANUP_GRACE_MS`.
- Pinned by `tests/pristine-conductors.test.mjs`; the browser side by `web/src/app/pristine.test.ts`, `web/src/features/composer/pristineComposer.test.tsx` and `web/src/features/sidebar/pristineHidden.test.tsx`.

## `src/sessionCleanup.ts`

`cleanupSessionsWithoutTranscripts({log, now})`, the boot pass that removes session records whose whole lineage has no transcript left. Called from `start()` in `server.ts` after `sweepFuseSessions()` and the orphan-CLI reap, and **before `createServer()`**: after migrations and the pending-archive sweep (its store write is queued ahead on the store's `serialize` chain), with no instance live, and before `startResumeLifecycle` reads and unlinks `pending-resume.json` and `running-sessions.json`.
- **Rule**: a record is removed only when no segment of `record.segments` — live **or `dropped`** — is in `transcriptIdsOnDisk()` (`src/projects.ts`). Lineage is the recorded chain only; fresh spawn, renew / typed `/clear` and prune each record a segment, and respawn / resume / rewind reuse the id. A fork is its own session and never keeps its source alive.
- **Scan roots**: `claudeProjectsRoot()` plus every `<claudeConfigFarmRoot()>/<dir>/.claude/projects` that exists on disk, registered remote or not (not `transcriptRoots()`, which lists only registered remotes). Names only: every `<id>.jsonl` in each encoded-cwd dir, no `isFile`. No System handle — every transcript lives on cc's host.
- **Kept** (never removed): an id named by `pending-resume.json` or `running-sessions.json` — each entry's `sessionId` and each entry's `workers[].sessionId` — or by `pending-continue.json` — each notice's `sessionId` and `workers[]` — matched against the public id and every segment id (read with `readResumeManifest`, `readRunningRecord` and `readPendingNotices`, never cleared); any segment id failing `isSessionId` (warned); a newest-segment `at` younger than `CLEANUP_GRACE_MS` against `now()` (an unparseable or empty `at` counts as old) — `mintPublicId` writes a record before its jsonl exists, and a hot restart has the exiting server still writing.
- **Fail-safe**:
  - `transcriptIdsOnDisk` throws on any read error of the local root (absent included — a wrong HOME / `CLAUDE_CONFIG_DIR` must not read as "all gone") and of any encoded-cwd entry that is a directory or symlink (ENOENT included: a dangling symlink is an unmounted volume). ENOENT is tolerated only for the farm root and for a farm entry's `.claude/projects` (a real or symlinked farm dir without one — a dangling farm symlink lands here); ENOTDIR only for that same farm-entry read (a farm symlink to a file, or a `<farm>/<dir>/.claude` that is a file) and for an encoded-cwd symlink that resolves to a file — each means "no transcripts here". Entries are otherwise filtered by dirent: the farm root contributes directories and symlinks, and a non-directory, non-symlink among the encoded dirs is skipped. On a throw the pass warns `session-cleanup: transcript scan failed (…); keeping every record` and still writes the snapshot.
  - **Empty-scan guard**: a scan that found no transcript id at all, against a non-empty store, removes nothing and warns `session-cleanup: no transcripts found anywhere — refusing to remove records (check HOME / CLAUDE_CONFIG_DIR)`; the snapshot is still written. It holds even when a record is kept for another reason (grace, manifest, unresolvable id), which stands the mass-wipe guard down.
  - **Mass-wipe guard**: a pick naming EVERY record of a non-empty store removes nothing and warns `session-cleanup: every record looks transcript-less — refusing to wipe the store (check HOME / CLAUDE_CONFIG_DIR)`; the snapshot is still written. A root that exists but is the wrong one scans as empty, not as an error; the empty-scan guard catches that shape first, and this guard is the backstop for a scan that found some transcript while every store record is dead.
  - Any other failure is logged `session-cleanup: failed (…); nothing removed`.
- **Output**: `<store>/sessions.json.startup.bak` (`startupSnapshotFile()`), the byte-exact pre-image, rewritten every boot that finds a store file (none when `sessions.json` is absent); one `session-cleanup: removed N session record(s) with no transcript left: <ids> (pre-image: <path>)` line when N > 0.
- **No cascade**, like the explicit delete: transcripts, worktrees, `costs.jsonl`, `events.jsonl` and plugin board owners are untouched — append-only history where a dead id is inert.
- Pinned by `tests/session-cleanup.test.mjs`.

## `src/conductorSpawns.ts`

the reader of the session store's spawn-time facts (`parent` / `project` / `worktree`), behind `GET /api/conductors/projects`; reads only through `loadSessions()`, writes nothing. `rootOf(doc, publicId)` climbs `parent` links through conducted records to the first non-conducted one (the rule `rootSessionOf` in `src/instances.ts` applies live); it returns null — the worker is unattributed, never misattributed — when a record on the chain is missing, when a conducted record on it (the worker's own included, which then fails before any climb) has no `parent`, or on a cycle (a conductor-side resume overwrites `parent`). A conducted record has no `parent` when it is a migrated id-only record, when it came from an MCP `spawn_instance` call that carried no live caller, or when the spawn-time `markConducted` (with `parent`) failed and the per-turn re-assert (`_writeSessionMetadata`, `markConducted` with no extras) then set `conducted` on the record `mintPublicId` created at spawn, leaving it with no `parent`. `spawnedProjectsByRoot(doc)` groups conducted records carrying a `project` by root, `lastSpawnAt` = newest segment `at` per (root, project) and `worktrees` = the distinct recorded `worktree` names there, sorted by name, entries sorted newest first then by name, omitting a root whose current segment is archived; memoised in a `WeakMap` keyed on the doc, so repeat fetches between writes reuse the store's cached doc and cost one `stat`. Refresh: the client fetches it in `refreshProjects()` on every `t:'projects'` nudge (spawn/exit and every status flip). `markConducted` and `setSessionPlace` are kicked at spawn and awaited by `launch()`, so the spawn's own nudge (emitted at `spawning`, before `launch()` resolves) may read before the write lands; the worker's next status flip re-fetches. Residual: a worker that crashes before that write lands shows no idle chip until the next nudge from anywhere.

## `src/conduct.ts`

two entry points.
`ensureConductProject()` lazy-creates `<projectsRoot>/.conduct/` (the cwd of every conductor session), guarantees its `CLAUDE.md` carries the `@CONVENTIONS.md` import via the shared `ensureConventionsImport` (`src/conventionsImport.ts`), and returns `{path, created}` (`created` = the dir was created).
`materializeCurrentConduct()` calls that ensure, then writes `` `${await composeCurrentWorkspace()}\n${await composeCurrentConduct()}` `` to `conductConventionsPath()` = `<projectsRoot>/.conduct/CONVENTIONS.md` (`writeFileAtomic`, one fixed path) — the conductor is a delivery destination for **workspace** conventions too, and they go first (the workspace text ends with a newline, so exactly one blank line separates them and the role doc's generated footer stays last).
It is called from `Instance.launch()` for `isConductorInstance()` instances only — before **every** spawn and resume, since every (re)launch entry point funnels through `launch()`, the sole caller of `spawn()`.
A compose/write failure propagates (a role-less conductor is worse than a surfaced error).
**Delivery is the messages stream, not an appended system prompt:** every non-Anthropic backend here is the same `claude` CLI behind a translation proxy, and a proxy that reads only `system[0]` or flattens `system` to a string drops the CLI's extra `system` block — leaving a conductor with no role doc at all.
A CLAUDE.md `@`-import is a channel the backend already honours for every worker.
**In the project rather than a store path `@`-imported from there:** an import resolving outside the project root is gated behind the external-includes dialog, which never fires headless (`migrations/0003`).
**A partial revert of `migrations/0022`, whose two objections are answered:** *freshness* — the pre-spawn materializer is the SOLE writer of `CONVENTIONS.md`, so no ensure-time copy exists that could drift from the live selection (`ensureConductProject()` deliberately does not write it); *ownership* — that file is app-owned and says so in its own composed footer, while the user's `.conduct/CLAUDE.md` only ever gains an import line.
This file is also the diagnostic artefact: it holds the actual delivered bytes, in the conductor's own cwd.
`ensureConductProject()` runs once at a time (concurrent callers share one in-flight promise) and treats a `PROJECT_EXISTS` refusal as success once the record resolves, so two first-ever creates, in one process or two, both succeed; it is called (idempotently) on boot, on any create naming the `.conduct` project (`_doCreateResolved` in `src/instances.ts`, so REST create, MCP `spawn_instance` and resume share it), on conductor resume-restart, and by `POST /api/projects/.conduct/ensure`.
**Selection changes affect newly-spawned / next-context-refresh conductor sessions, not an in-flight turn.**

## `src/conductorConventions.ts`

the toggleable conductor conventions composed into the conductor's role doc (written to `.conduct/CONVENTIONS.md` and reaching the session as a CLAUDE.md `@`-import; see `src/conduct.ts` above).
**Single-slot channel:** the conductor has exactly **one** delivery document, and the CLI's `--append-system-prompt` / `--append-system-prompt-file` flags are deliberately unused (a translation proxy can drop the extra `system` block they produce), so any future feature appending system-prompt text must compose into this same document rather than reaching for a flag.
Always-on `conventions/conductor/core.md` (role, hard boundary, dispatch-and-wake, your own plan mode — its procedure is the skill `cc-conductor:plan-mode` — MCP toolbelt, safety, talking to the user) + `conventions/conductor/footer.md` bracket the enabled conventions.
`SEED_CONVENTIONS` (the built-in `{slug,name,description}` entries; bodies in `conventions/conductor/<slug>.md`) + custom conventions + selection state persist at `<store>/conventions/conductor.json` (`{disabled:[slugs], rules:[…]}`).
`disabled` is a **deny-list** of the user's explicit off-switches — seed, custom and namespaced `<id>/<slug>` plugin slugs alike, in one list; everything else the scope knows is on, so a fresh install matches the pre-carve CONDUCT.md **and** a future-added seed defaults on with no migration (see `src/conventionSelection.ts` below).
A plugin's conductor conventions are **on by default** whenever the plugin is enabled.
The **effective selection** (`getSelection`) is derived: base ∪ (conventions of currently-enabled plugins − `disabled`) — plugin membership comes from the live catalog (`getCatalog` surfaces ENABLED plugins' conventions only), so a disabled plugin's conventions vanish automatically, a plugin update adding/removing a convention flows through with no toggle, and a stale slug can never reach `compose()` (no 400).
`getSelection`/`setSelection`/`deleteCustomConvention` come from the shared `src/conventionSelection.ts` collaborator; this scope supplies exactly one of its hooks — `derive` (fold in the enabled plugins' conventions minus `disabled`).
Also `add/updateCustomConvention`, `composeConduct(slugs)`/`composeCurrentConduct()`.
**A degraded catalog composes anyway, and logs one line**: `composeConduct` takes the flag off the catalog read the compose already makes (`fragmentCatalog`'s `composeWithMeta(slugs)` → `{text, degraded, skills}`; `compose` is `(await composeWithMeta(slugs)).text`) and, when it is up, emits exactly one `console.warn` — `conductorConventions: role doc composed over a DEGRADED convention catalog — a plugin's conductor conventions may be missing from this document`.
The document itself is never marked and the write is never skipped, so a degraded role doc is byte-identical to one composed with that plugin deliberately disabled.
It deliberately does NOT adopt `ensureProjectConventionsMd`'s freeze: that freeze is keyed on the `missing` set a project's persisted line-1 `<!-- cc:conventions … -->` marker yields, and this scope has no such record — the plugin half of the selection is derived live and an ENABLED one appears nowhere in `conductor.json` even after an explicit Save — so a freeze here could key only on `degraded` alone, which also fires when the conductor scope lost nothing (hence the wording's `may`).
The read sits ABOVE the playbooks-gated generated sections, or the signal would vanish whenever that convention is off.
Built on the shared `fragmentCatalog.ts` (`extraProvider` wired to enabled plugins' `conductor`-scope conventions via `setPluginConductorConventionsProvider`/`server.ts`, mirroring `projectConventions.ts`'s provider seam).
Plugin enable/disable needs no regeneration step — the effective selection derives from the live catalog, so a toggled plugin's conventions flow into the composed doc on the next conductor spawn/resume.
Imported by `src/routes/conventions.ts` and `src/mcp/handlers.ts` for the selection/catalog surface; In `src/`, the role doc is composed only by `materializeCurrentConduct` in `src/conduct.ts` (called from `Instance.launch()` in `src/instances.ts` for conductor instances only), through `composeCurrentConductParts()` — the role doc plus its skill parts ([Convention skill parts](playbooks.md#convention-skill-parts)); `composeConduct`/`composeCurrentConduct` are that form's `.text`.

## `src/conventionSelection.ts`

the shared SELECTION collaborator sitting on top of a `FragmentCatalog`: which of its entries are enabled, and what a submitted checkbox set persists.
`createSelectionStore({catalog, seeds, noun, derive?})` → `getSelection`/`setSelection`/`deleteCustom`; `disabledOf(state)` → `Set<string>` is exported for the conductor scope's `derive`.
**The persisted state is a DENY-list `state.disabled`, never an allow-list**: a slug added to a `SEED_CONVENTIONS` array reaches every install, fresh or existing, with no migration — the allow-list it replaced needed one per added seed (`migrations/0015-…`, `migrations/0029-…`) because any store that had ever saved a selection froze the set it was written with.
Owns, once: the base read (`seeds ∪ catalog.customSlugsOf(state) − state.disabled`, in seed-then-custom order — so the effective selection never echoes the order a save submitted, and the composed document's section order is a property of `SEED_CONVENTIONS` alone), `setSelection`'s array guard (`400 'enabled must be an array of slug strings'`) and unknown-slug loop (`400 unknown <noun> slug '<slug>'`), the submitted-set → `disabled` diff (for every slug the LIVE catalog can see: checked clears its off-switch, unchecked records one — a slug the catalog cannot see, e.g. an unreachable or disabled plugin's convention, keeps its off-state, so an off-switch survives disable→re-enable), and the delete-prunes-it-from-`disabled` rule (so a re-created custom of the same slug is not silently OFF).
The two 400 messages and the `setSelection(enabled)` parameter still say `enabled`: the **wire** payload is an allow-list of what the user ticked (`{enabled:[…]}`, unchanged — see [protocol/rest-settings.md](../protocol/rest-settings.md)), and only the persisted representation is inverted.
Two scopes use it: **workspace** with no hooks, **conductor** with only `derive` (fold in the enabled plugins' conventions minus `disabled`; no `persist` override, because one deny-list holds plugin off-switches too).
The **project** scope opts out entirely — it has no selection state, its picks living in the in-tree `CONVENTIONS.md` line-1 marker (`src/projectClaudeMd.ts`).
`derive` gets the catalog as a **lazy thunk**, not a resolved list: workspace's derivation is store-read-only, and an eager fetch would make every `composeCurrentWorkspace()` / `GET /settings/conventions/workspace` re-read all seed fragments off disk.
That is also why `customSlugsOf` is a pure projection over already-read state on `fragmentCatalog.ts` rather than a catalog read — `getSelection` makes exactly one store read and resolves no fragment.
**A newly created custom convention is therefore ON immediately** (nothing switches it off), matching seeds and plugin conventions; under the allow-list it sat unchecked until the next save.

## `src/conventionsDir.ts`

`conventionsDir(scope)`: `conventions/<scope>/` in this checkout, or `$CC_CONVENTIONS_DIR/<scope>`, read per call. The one place the three scope modules learn where their fragment files are.

## `src/fragmentCatalog.ts`

shared helper backing all three convention systems (`projectConventions.ts`, `conductorConventions.ts`, `workspaceConventions.ts`): a catalog of `{slug,name,description}` seed metadata whose body loads from a committed `.md` fragment (`<seedDir>/<slug>.md`), plus custom entries whose body lives inline in a JSON store under `<store>`.
**Seed bodies are read per call and never memoised**, and so are the always-on `core.md`/`footer.md` reads in `workspaceConventions.ts`/`conductorConventions.ts`: every document these bodies feed is regenerated OVER a committed file (`.conduct/CONVENTIONS.md` before each conductor spawn/resume, each project's `CONVENTIONS.md` on boot and after every workspace-settings save), so a body frozen at first read does not merely age — the next regeneration writes pre-edit text back over the correct one and the edit silently reverts until the orchestrator restarts.
The cost this buys off, measured over 1000 iterations with a warm page cache and the reads issued under `Promise.all` as `getCatalog()` issues them: **0.13 ms** per workspace composition (core + 6 seeds), **0.21 ms** per conductor composition (core + footer + 9 seeds), **0.43 ms** for all 22 fragments of the three scopes (42 KB total) — against a conductor spawn launching a `claude` subprocess, and a regeneration sweep doing one read + one write per project through that project's `System`.
`tests/fragment-catalog.test.mjs` and `tests/fragment-freshness.test.mjs` pin it.
`createFragmentCatalog({seeds, seedDir, seedExt?, skillParts?, scaffolds?, storeFile, noun, extraProvider?})` (`seedDir` a path or a function read per call; `skillParts: true` splits each seed body and each custom body, and validates a custom marker at `addCustom`/`updateCustom` — [Convention skill parts](playbooks.md#convention-skill-parts); `scaffolds: true`, passed by `projectConventions.ts` only, lets a custom record carry `scaffold` — any other catalog refuses a non-empty one with 400).
A custom entry carries `source` (its body as stored), `scaffold?` and `skillError?`; `validateFields` requires name and description always and a body unless a non-empty scaffold is given → `getCatalog`/`addCustom`/`updateCustom`/`deleteCustom` (validation with `statusCode` 400/404/409, seeds reject mutation), `compose(slugs)` (`'\n'+bodies.join('\n\n')+'\n'`, unknown slug → 400), and `readState`/`patchState` (arbitrary sibling keys on the same store JSON, preserving `rules` — used by the conductor/workspace scopes for `enabled`).
**`extraProvider`** is an optional `async () => [{slug,name,description,body,…}]` merged into `getCatalog()` after seeds+custom (`builtin:false`, read-only, bypasses the custom-store CRUD) — used by `projectConventions` and `conductorConventions` to fold in enabled plugins' convention fragments (slugs pre-namespaced by the provider), one per routed plugin-convention scope.
A throwing provider degrades to no extra entries (warned).
`getCatalog()` returns a `CatalogList` (`CatalogEntry[] & {degraded?:boolean}`) — `degraded` is set true when the provider threw, or when it returned successfully but flagged its own list incomplete (registry.ts's `conventions()` does this on a transient per-plugin resolution failure).
A caller that treats "slug absent from the catalog" as "safe to drop" must check this first.
**Three places act on it** — the regeneration freeze (`ensureProjectConventionsMd`, the [`src/projectClaudeMd.ts`](web.md#srcprojectclaudemdts) bullet), the conductor role doc's operator warn (`composeConduct`, `src/conductorConventions.ts`), and the conventions LISTING + create path (`listProjectConventions`/`listConductorConventions`/`createProject`, `src/mcp/handlers.ts`) — and a fourth, `compose`/`composeWithMeta`, propagates it rather than deciding on it.
**The flag does not survive projection or serialization**: `degraded` is the array's OWN property, so `.map()` drops it and so does `JSON.stringify` — which is why the two MCP listings return `{conventions, incomplete?}` objects rather than the bare array, and why `GET /api/settings/conventions/{project,conductor}` still drop it (`res.json` is a `JSON.stringify`; deferred by decision, with a comment at each site).

## `src/identifiers.ts`

`SLUG_RE`/`SLUG_MAX`/`isSlug` (lowercase kebab: convention + rule slugs, plugin ids, plugin convention/role slugs, backend registry ids) and `SESSION_ID_RE`/`isSessionId` (also the path-traversal guard, since sessionIds build `<encoded-cwd>/<sid>.jsonl` paths). The RULE is shared; the REFUSAL stays at each call site, which differ on purpose — `fragmentCatalog`/`appSettings` throw 400, `plugins/manifest` accumulates into `errors[]`, `routes` throws 400 while `projects` returns null. NOT the custom-role name rule (`^[A-Za-z][A-Za-z0-9-]*$`, `appSettings.ts`), which is a case-preserving user label rather than a machine identifier.

## `src/mcp/argValidation.ts`

`validateArgs(schema, args, toolName)` (shallow JSON-Schema check at tools/call: object schemas, required keys, unknown-property rejection, scalar types + constraint keywords; no `$ref`/`oneOf`/`anyOf`/`allOf`/`not`) plus the vocabulary it enforces: `VALIDATED_CONSTRAINT_KEYS`, `DESCRIPTIVE_PROP_KEYS`, and the derived `ALLOWED_PROP_KEYS`. Extracted from `mcp/server.ts` so the vocabulary lives with its enforcer and `plugins/manifest.ts`'s `checkSchemaSubset` can IMPORT the allow-list instead of re-encoding it by hand — a hand-encoded copy ships a constraint nothing checks the moment one side widens without the other. Imports nothing from `../plugins` (that edge would close a cycle). Pinned by `tests/schema-keyword-sync.test.mjs`, which drives every listed keyword through the real validator rather than asserting set equality.

## `src/mcp/jsonSchemaSubset.ts`

the strict output-schema subset: `checkSchema(schema, at?)` throws on the first keyword outside `type` (incl. unions), `properties`, `required`, `additionalProperties`, `items`, `enum`, `const`, `anyOf`, `description`, and on an object schema that does not state `additionalProperties`; `validate(schema, value, at?)` returns every validation error (empty when valid). Core `outputSchemas.ts` is written in it (held there by `tests/mcp-json-conformance.test.mjs`); a plugin manifest's `outputSchema` is checked by it at load (`plugins/manifest.ts`), and every typed json reply is validated by it (`plugins/mcpBridge.ts`). Imports nothing.

## `src/sessionOneShot.ts`

`runSessionOneShot({systemPrompt, prompt, signal?})`, the one Fast-tier `claude -p --output-format=json` call about a session; `generateSummary` and `askSession` (`src/summarize.ts`) both go through it. Returns `{result, durationMs, costUsd, usage: {cacheReadInputTokens, cacheCreationInputTokens}}` (a non-number counter reads `null`; `costUsd` is Claude-backend only). `buildSessionPrompt(conversationText, task)` in `src/summarize.ts` is the **single prefix builder**: the flattened session text (text blocks only) is the system prompt, the task (tier instructions, title instructions plus the project hint, or the question, last) is stdin, so every call over unchanged text shares one prompt-cache prefix. Each flag pins a part of the request that precedes the user message:
- `--system-prompt-file <tmp>` replaces the CLI's default system prompt (cwd, env, git status, memory paths). A file, not argv: one argv entry is capped (128 KiB on Linux) and a whole Windows command line is ~32k chars.
- `--tools ""` and `--strict-mcp-config` fix the tool list, which is cached ahead of the system prompt; a connecting MCP server would otherwise change it.
- `--no-session-persistence` writes no CLI transcript.
- Temp file lifecycle: `fs.mkdtemp` dir under `os.tmpdir()`, file mode `0600`, holding only the session text; removed in `finally` on success, failure, timeout and abort.
- Abort: an `AbortSignal` kills the child through `hostPlatform.killProcess` and rejects with an `AbortError`; `POST /api/sessions/:sid/ask` wires it to the client disconnect.
- Known limitation: the session text sits in the system role, which carries more authority than the user-message task, so text inside a session (a pasted document, another agent's output) can steer an answer more than it could from the user message. The cached prefix requires this layout.
- A text change in the session changes the prefix and misses; tool-only growth does not. A model/backend rebinding of the Fast tier, the cache TTL and a prefix under the model's minimum cacheable size also miss. Tests: `tests/session-ask.test.mjs`.

# Components: the System seam

The System seam and its modules: the interface, the local and provider implementations, terminals, the redirected shell, and the registry.

## `src/systems/`

the **System seam**: every project-scoped operation (git, project-tree file I/O, shell commands in a project dir) goes through a `System` handle instead of `node:fs`/`spawn` directly. **Two implementations**: the in-process `local` built-in, and `ProviderSystem`, which reaches a system by speaking a documented NDJSON protocol to a provider process ([docs/systems-protocol.md](../systems-protocol.md)). No TRANSPORT is shipped — cc defines the provider contract and launches a provider, it does not implement SSH or docker: the provider command is the user's, stored as argv on the registry row (`launch`). A project on a system with no such command, or on an id with no row at all, is REFUSED by name at resolution rather than resolved local.

## Terminals — `System.openTerminal` (`src/systems/terminal.ts`, `src/systems/ptyHost.ts`, `src/systems/ptyHelper.py`)

a program under a pseudo-terminal on any System, the target user's login shell when `argv` is absent, streaming bytes both ways. cc is the byte pipe only: the caller owns sessions and scrollback, and a terminal dying with cc, a plugin or a provider is accepted. **One implementation on both sides**: `LocalSystem` runs `ptyHost.ts` in-process and the reference provider runs the same file behind the protocol's optional `pty` capability (`docs/systems-protocol.md` §5, "pty exec"), so a local and a remote terminal are the same code. `ptyHost.ts` spawns `python3 -I ptyHelper.py <cols> <rows> -- <argv…>` (stdlib only, no native npm dependency — `node-pty` would break the installer contract's C3, [windows.md](../windows.md)) and speaks a length-prefixed frame protocol to it (`v`/`d`/`r` in, `S`/`o`/`w`/`x`/`e` out — the full table is `docs/systems-protocol.md` §5, "The pty helper", a contract a provider may reuse with a byte-for-byte copy of the file); close is stdin EOF, which hangs the terminal up and SIGKILLs what is left of the session's groups after a grace. **python3 is required on the host**, found by `probePtyHelper`, run ONCE per process per interpreter name (the promise is memoised; the answer is the interpreter's absolute path), so installing python3 later needs a restart. `Platform.terminalShell()` is the login-shell argv, or `null` on win32 — no local terminals there. Behaviour on macOS and Termux is unmeasured.
- **The spec.** `{cwd, argv?, env?, cols, rows, term, signal?}`: `env` is an OVERLAY on the target's own environment (local base: `process.env`, as for `exec`), then `TERM=term`; dims are integers in `1..PTY_DIM_MAX`; `term` matches `TERM_RE`. An invalid spec is cc's own bug and THROWS. Handlers `{onData(Buffer), onExit(end), onDrain?()}` are passed at open so no early output is lost; the returned `Terminal` is `{write, resize, pause, resume, close}`.
- **The overlay reaches the program only.** The helper runs in the base environment (`PtySpawnSpec.env`); the overlay plus `TERM` (`PtySpawnSpec.programEnv`, and the reference provider's `CC_REMOTE`) is the helper's FIRST stdin frame, `v`, read before it forks and merged into the program's `execvpe` env — so a loader variable in it never reaches python.
- **Input backpressure.** `write` never drops or refuses; it returns `false` once input accepted and not yet written into the terminal is at or above `TERMINAL_WRITE_HIGH_WATER_BYTES`, and `onDrain` fires once when that returns to 0 after a `false`. Both implementations count through one `InputGauge` (`terminal.ts`): `accept` per write, `written` per helper `w` frame locally (`PtyHandlers.onWritten`) or per `inputAck` remotely. `ptyHost.ts` holds sent-minus-reported `d` bytes under `HELPER_INPUT_WINDOW_BYTES`, which bounds the helper's own queue; `ProviderSystem` sends `input` only against `PTY_INPUT_WINDOW_BYTES` of credit and ends a terminal `failed` `EPROTO` on an over-grant (§5, "Input credit"). After the end a `write` is discarded and returns `true`. `TerminalEnd` is `exited {code, signal}`, `closed` (owner close or abort) or `failed {error}` (e.g. `ETRANSPORT` when the provider died).
- **The cap.** `MAX_TERMINALS_PER_SYSTEM` (`terminal.ts`), held by `TerminalSlots`: one per `LocalSystem` (the registry's is process-wide, so per host) and one per owning `ProviderSystem`, shared with every `bindRemote` view. A slot is taken before anything is spawned or sent and released on exit, close, failure or rejection. Both constructors take `maxTerminals` for tests.
- **The refusals** — `openTerminal` REJECTS (it is the one `System` member with no result to carry a refusal in):

  | Code | Shape | When |
  |---|---|---|
  | `PTY_UNAVAILABLE` | 501 `httpError` | cc's own host has no pty helper: `terminalShell()` is null (win32) or the python3 probe failed; the message names the cause and that a restart re-probes. `LocalSystem` only |
  | `SYSTEM_NO_PTY` | 501 `httpError` | The provider's handshake lacks `pty`; names the system and provider. No frame is sent |
  | `TERMINAL_LIMIT` | 429 `httpError` | The per-system cap is reached |
  | `EPTY` | `SystemError` | The target could not allocate a terminal |
  | `ENOENT`/`ENOTDIR`/`EACCES` | `SystemError` | The cwd or `argv[0]` is missing or not usable (the cwd is `stat`ed before the helper spawns) |
  | `ETRANSPORT`/`ETIMEDOUT`/`EUNSUPPORTED`/`ECANCELLED` | `SystemError` | Provider unreachable; the program not started within the open bound — `DEFAULT_OP_TIMEOUT_MS` over a provider (cc then sends `close`), `LOCAL_TERMINAL_OPEN_TIMEOUT_MS` (`terminal.ts`, `LocalSystem`'s `terminalOpenTimeoutMs`) locally (the helper is SIGKILLed); a bound remote on a provider without `remotes`; the spec's signal aborted before the open resolved. Every rejection frees the slot |

  After the open, a terminal ends `failed` with `ETRANSPORT` when its provider dies, and with `EPROTO` when a provider sends past the credit window (`docs/systems-protocol.md` §5) — cc enforces the window, since it is what bounds the output cc holds for a paused terminal.

## The System modules

- `system.ts` — the interface. Three MUST primitives (`exec`, `readFile`, `writeFile`) plus the operations a remote provider will DERIVE from `exec` (`readFileBytes`, `stat`, `readDir`, `realpath`, `mkdir`, `removeTree`, `unlink`, `chmod`) — cc-side helpers, not provider surface. Semantics worth knowing before calling: **`stat` returns `null` for an absent path** and throws for anything else (absence is a value, a broken installation is not); **`unlink` removes one directory entry and never follows it**, `removeTree` is `rm -rf` — which one a call site uses is cc's decision, and a path cc does not own must never reach `removeTree`; `writeFile` takes `{atomic}` (temp+rename) or `{exclusive}` (EEXIST rather than overwrite), never both.
- `localSystem.ts` — `LocalSystem`, the in-process `local` built-in: each method is the `node:fs`/`runGroupedCommand` call a call site would otherwise make, behind the interface. Also the home of `writeFileAtomic` (re-exported by `src/projects.ts`, where most callers import it) — cc's store is always local, so its atomic write and this system's are one operation.
- `protocol.ts` — the **executable half of the wire spec**, shared by cc and any provider written in JS: frame types, `PROTOCOL_VERSION`, the `CHUNK_BYTES`/`MAX_FILE_BYTES`/`MAX_LINE_BYTES` constants, `NdjsonDecoder`, capability reading, and the error taxonomy (`SystemError`, `PROTOCOL_ERROR_CODES` + `FS_ERROR_CODES`, `classifyStderr`, `execFailure`). **A malformed line is FATAL, not skipped** — `push` throws `EPROTO` and drops its buffer, because a stream that has proved it cannot be framed cannot be trusted for the frames after it. **A payload is part of its frame**: `dataB64` on a `stdout`/`stderr`/`data` frame must be present and canonical base64, checked here for both ends and both directions, because `Buffer.from(s,'base64')` stops at the first unreadable character and returns the prefix — decoding leniently turns a corrupted chunk into a `writeFile` that reports success having dropped its tail, or a command whose stdout is quietly truncated with exit 0. Unknown frame types and unknown capability keys are IGNORED: that is the extension point that lets the contract grow without a version bump.
- `execCollector.ts` — `ExecOutputCollector`, the output accounting for one `exec` (per-stream `StringDecoder`, the `cap` tail that also clips the interleaved `output`, the `headCapBytes` head cap that keeps DRAINING after it stops retaining, the `maxBufferBytes` fence that is a FAILURE rather than a truncation). **Shared by both implementations of the primitive** — `runGroupedCommand` and `ProviderSystem.exec` — so a caller cannot tell them apart and a fix in one cannot miss the other. **Byte mode** (`encoding: 'buffer'`) keeps raw `Buffer`s per stream under the same fence and head cap, skips the decoders, and fills `ExecResult.stdoutBytes`/`stderrBytes` (empty on a spawn error; the strings stay `''`); combining it with `cap` or `onChunk` throws at construction.
- `execWrap.ts` — **pure** spec transforms behind the three newer `ExecOptions`, shared by both implementations: `ENV_NAME_RE`, `assertEnvOverlay` (a bad name or a NUL value throws — cc's bug), `shQuote`, `shellWithPrelude` (`export NAME='v'` lines, plus on a provider an `[ -r F ] && exec <F; rm -f -- F` stdin line, prepended to a shell string — after `bash -lc`'s profile, so the caller's values win), `argvWrapper` (`env NAME=V… /bin/sh -c SCRIPT sh <nonce> <stdinPath|''> argv…`: open the staged file onto fd 0 and unlink it, pre-check `argv[0]` the way spawn resolves it — PATH walk for a bare name (first executable regular file wins; only non-executable entries of that name → `EACCES`; none → `ENOENT`; an unsearchable PATH directory reads as none, so `ENOENT` where local spawn says `EACCES`), existence/directory/execute bit for a path — then `exec "$@"`), and `unwrapResult` (an exit 127/125 with empty stdout and stderr EXACTLY `<nonce> <ERRNO>\n` becomes a never-started `spawn <argv0> <ERRNO>` result; anything else passes through). Per-implementation mechanics:

  | `ExecOptions` | `LocalSystem` / `runGroupedCommand` | `ProviderSystem.exec` |
  |---|---|---|
  | `stdin: Buffer` | native pipe (`proc.stdin.end(buf)`, EPIPE ignored); empty = `'ignore'` | staged at `/tmp/cc-stdin-<32 hex>` (`writeFileBytes`, `exclusive`, mode 0600), redirected and unlinked by the wrapper before the command runs; empty = `'ignore'`, no staging. A staging throw is a result (`ETRANSPORT` → `transportFailure`, else `spawnErrorCode`); a non-clean result fires an un-awaited `removeEntry`, a failure logged `exec: could not remove staged stdin …` |
  | `envOverlay` | argv: `{...(env ?? process.env), ...overlay}`; shell: `export` prelude | argv: `env(1)` assignments in the wrapper; shell: `export` prelude. Never a frame `env` |
  | `encoding: 'buffer'` | passed to the collector | passed to the collector, including both early-return collectors in `#exec` |

  The wrapping lives in the PUBLIC `exec`, never `#exec`, so the derivations and the redirected shell are untouched; with neither option set the wire traffic is unchanged.
- `providerConnection.ts` — `ProviderConnection`: spawn, handshake, multiplexing by id, teardown, restart. Supervision is **restart-on-demand with a fail-fast backoff**: a dead provider fails every in-flight operation with `ETRANSPORT` at once, the NEXT operation relaunches, and an operation inside the backoff window (100 ms doubling to 5 s) is **refused rather than queued**. A connection cc **disposed** is the exception and is TERMINAL: `dispose()` sets a flag that `#teardown` deliberately does not — a crashed provider must still reconnect, which is this class's whole contract — and every later `ensureUp` on it throws `ETRANSPORT` instead of respawning the old argv. `ensureUp` is single-flight, so one failed launch is one failure however many callers were waiting on it — the backoff is derived from that count. The handshake MUSTs are ENFORCED, not assumed: an id-carrying frame before the hello, a second hello and a protocol-version mismatch are each `EPROTO` at the handshake. **There is no `system` descriptor to validate** — the hello's required, refusal-enforced `system.shell` is gone with the long-lived shell, which was its only reader and `os`/`pathSep`/`home` had none even before that. A handshake that is torn down BETWEEN resolving and being recorded (a second hello or an immediate exit arriving in the same chunk) fails the connect with the real reason — recording it would mark the connection up with no child behind it, and every later operation would be written into a closed pipe and wait out its deadline. The child and its stdio are **unref'd**, ref'd only while an operation is in flight, so an idle connection can never hold the event loop open — which is what lets a test process exit while a provider is still connected.
- `providerSystem.ts` — `ProviderSystem`, the `System` implementation over the wire.
  Three primitives on the protocol; `stat`/`lstat`/`readDir`/`readlink`/`symlink`/`removeEntry`/`realpath`/`mkdir`/`removeTree`/`unlink`/`chmod` **derived from `exec`** (`stat -L -c '%f %s %.3Y'`, `find <p> -maxdepth 0 -printf '%y\t%m\t%s\t%T@\t%l\n'`, the same fields plus `\t%f` for a listing, `readlink -v`, `ln -sfnT`, `rm -d`, `realpath -e`, …), and `writeFileBytes` beside `writeFile` on the write primitive.
  **`lstat` and the widened `readDir` are one round trip each**, which is the whole reason they carry mode, size, ms mtime and the symlink target rather than name-and-kind: with name-and-kind a listing of N children costs 1 + N round trips to answer the same question.
  `%m` is permission bits alone, so both implementations reconstruct the type bits from the kind (`typeBitsFor`, `src/systems/system.ts`) and a kind cc cannot name reports none on either side; `%T@` is `seconds.nanoseconds`, parsed as TWO INTEGERS and never as a float, and **both implementations derive whole milliseconds through the one `msFromNanos`** — the local side from a `bigint` stat's exact nanoseconds — so the two are comparable exactly rather than within a tolerance.
  Rounding each side in its own arithmetic converged by luck and missed about once in 5000, on a half-millisecond boundary.
  **`writeFileBytes` is the whole of the binary fix and needed nothing from a provider** — the wire already carried base64 of raw bytes, and the only lossy step was cc's own `Buffer.from(data, 'utf8')` on the way in; `writeFile` now delegates through it.
  **No `exec` cc issues carries an `env` frame field** — cc's own plumbing and a caller's command alike run in the provider's own environment — the far side's PATH and toolchain, which across a boundary is the only environment whose paths exist; sending cc's made the target's own toolchain unreachable and put cc's whole environment, a live session token among it, in front of every far-side process.
  Derived commands run under `env LC_ALL=C …` because `env(1)` ADDS to that environment where a frame `env` would replace it, keeping the `strerror()` text `classifyStderr` matches on; a caller needing a variable there ships it in argv the same way, as the post-worktree hook's `CC_*` vars do.
  `opts.env`, when a caller names one, still REPLACES.
  `exec` **never rejects**, matching `runGroupedCommand`: a dead channel becomes a `spawnError`.
  **No operation is unbounded, with no exceptions**: every `exec` arms a cc-side deadline (`timeoutMs + 5 s` when the caller named one, a generous `defaultOpTimeoutMs` ceiling when it did not), and `readFile`/`writeFile` carry the same ceiling and fail `ETIMEDOUT` — without it a provider that completes the handshake and then goes mute leaves project listing and git status pending for ever, with no `ETRANSPORT` and no refusal.
  A redirected shell command is an ordinary bounded `exec` like any other, carrying `ProviderShell`'s per-command ceiling (next bullet) as its `timeoutMs`; the long-lived `openStream` that armed nothing went with the long-lived shell.
  The ceiling is a liveness fence, not a performance budget; it is a constructor option so a test can assert it without waiting for it.
  The `find <p>/.` trailing dot is load-bearing — `find <file> -mindepth 1` exits 0 with no output, which would read as an empty directory instead of `ENOTDIR`.
  **`listRemotes()`** is cc's one `listRemotes` sender (§2.2): `null` when the handshake does not advertise `remoteListing`, and then the frame is never sent; otherwise the ids `readRemoteList` accepts, or a rejection — every `error` answer (`EUNSUPPORTED` included, unlike `mirror()`), the backstop's `ETIMEDOUT`, a dead transport, and a refused list (`code: 'REMOTE_LIST_INVALID'`).
  Not memoised.
  `canListRemotes(sys)` is its structural guard; the method is not on the `System` interface.
- `remoteEnumeration.ts` — `enumerateSystemRemotes(id)` / `enumerateAllRemotes()`, the one caller behind `GET /api/systems/:id/remotes` and the `enumerate_remotes` MCP tool. Answers one of **three states, never collapsed**: `listed` (`remoteIds`, possibly `[]`), `not-enumerable` (`reason`), `failed` (`reason`, optional `code`) — the last two never carry `remoteIds`. **`local` is decided by id** before any handle is touched (`LOCAL_NOT_ENUMERABLE`), so the gate's `local` stand-in is never asked. Every per-System problem — an unregistered id, no provider command, an unreachable provider (the `systemById` refusal codes), an `error` answer, `ETIMEDOUT`, `REMOTE_LIST_INVALID` — is that System's `failed` entry: it **never rejects**, which is what isolates one broken System from the rest of `enumerateAllRemotes` (registry order). No cache.
- `transfer.ts` — `transferFile(src, dst, {move, overwrite})`, the engine behind the `system_transfer` MCP tool: ONE regular file between two `{sys, path}` endpoints, either of which may be `local`. Pure System logic — no registry, store or MCP. **Ordering invariant:** nothing is written before the single `writeFileBytes(…, {atomic: true, mode})`, so every refusal up to it leaves both sides untouched; a move `unlink`s its source only after that write is acknowledged, the destination is re-`lstat`ed and the source re-`stat`ed (size + mtime), and every refusal from the write on carries `written: true`. Uses only members [systems-protocol.md](../systems-protocol.md) already defines: the `readFile`/`writeFile` primitives plus the `stat`, `lstat`, `realpath` (the `SAME_FILE` entry key: realpath'd parent + leaf) and `unlink` derivations. Reads with `length: stat.size` because `LocalSystem.readFileBytes` has no cap of its own. A System error carrying a string `code` becomes a result; one without is cc's own defect and is rethrown.
- `shellFraming.ts` + `providerShell.ts` — the **redirected shell**, framed by cc rather than by the provider: `{ <cmd>\n} < /dev/null` plus a sentinel carrying `$?` and base64 `$PWD`, with a **random 128-bit nonce per command** and **first-match-wins** (a CONSTANT nonce was measured desynchronising the parser when a command echoed the sentinel).
  **The nonce's per-command FRESHNESS is not load-bearing, and only its randomness is** — stated because the obvious rationale rests on freshness, and the world that rationale needs is not this one: freshness matters where a single byte stream carries every command and a forged sentinel can move the NEXT command's boundary, whereas each command here has its own `exec`, stream and parser and a forgery is confined by construction.
  A nonce shared across a session's commands would break nothing.
  What survives as load-bearing is the PAIRING — a command must be parsed with the nonce it was framed with — which is lexical today (one `const` per call in `#runOneShot`) and is what the concurrency tests would catch if it became a per-run field two overlapping commands could overwrite.
  **ONE `exec` PER COMMAND** — the shape a local `Bash` call already has, and the only shape there is now that the long-lived shell is gone.
  Each framed command **opens with a sentinel of its own on both streams** and everything before it is discarded — that is what keeps a profile-file banner out of a command's output, and it is load-bearing on EVERY command, because every command gets its own shell and its own copy of that banner.
  It is also what makes the framing **interpreter-agnostic**: measured on Linux 6.17 / bash 5.2.37 / dash 0.5.12 as `/bin/sh`, under `bash -lc`, `bash -c`, `/bin/sh -c` and `/bin/sh`: identical `$?` propagation, identical `$PWD` capture, and the preamble discarded in every case — so the interpreter is the provider's choice and a login shell is not required.
  **The sentinel's `$?` is the only exit code there is**, and is NOT redundant with the `exit` frame: measured, the framed script's own `exec` exits 0 while the user command exits 2, because the script's last statement is a `printf`.
  **EVERY sentinel — opening and closing, both streams — is emitted with an injected leading newline**, because a sentinel only counts when it STARTS a line and what precedes it may have none: a command ending in `printf err >&2`, or a profile printing an unterminated banner.
  Without it the marker glues to that text, never matches, and the command runs to its deadline instead of returning — on every command, because every command gets its own shell and its own copy of that banner.
  The parser strips the newline back off the CLOSING sentinels only; before an opening one everything is discarded anyway.
  **CAPTURE, NOT CARRY**: cc reads `$PWD` back out of the sentinel so it can TELL the worker where its command ended, and feeds it to nothing — every command starts at the project root.
  Carrying it forward on the one-shot path (`#cwd` → the next `exec`'s `cwd`) is a second deletion parity required, not a code path already in place — which is why "the code path already exists" was the wrong reading.
  **THE PER-COMMAND CEILING NOW DOES ONE JOB** — the longest a command may **run** — and the value is therefore simply correct for it, where a ceiling doing three jobs could only say no value was right: `DEFAULT_COMMAND_TIMEOUT_MS` (605 000 ms = `BASH_TOOL_MAX_TIMEOUT_MS` 600 000 + `SHELL_TIMEOUT_SLACK_MS` 5 000, `ORCH_SHELL_COMMAND_TIMEOUT_MS` overrides it, `commandTimeoutMs` is the test seam).
  Its other two jobs — the longest a **wedged** shell stayed wedged, and the longest a queued command **waited** for its turn — were the counter-pressure that wanted it small, and both went with the long-lived shell and the queue.
  It is enforced by the PROVIDER, as the `exec` frame's own `timeoutMs`, where every other operation's ceiling already lives — **but it is NOT the only bound, and the earlier claim that it was is measured false.**
  When the provider reports nothing at all, cc's own abandon timer (`providerSystem.ts`, `timeoutMs + EXEC_TIMEOUT_SLACK_MS`) is what fires; it reports its own computed value as `ExecResult.abandonedAfterMs`, and `providerShell.ts` names THAT number, because it is longer than the deadline the provider was given and naming the ceiling told a worker it had waited a time it had not.
  **The caller cannot move it, and no longer offers one**: the tool `timeout` a redirected `Bash` carries does not reach cc at all, and cc needs it for nothing.
  At the tool timeout the CLI **DETACHES** the forwarder and hands the agent a background task — measured at CLI 2.1.258, for a rewritten forwarder command and for the same command left un-rewritten alike, and whether its output was flowing or silent — so the command keeps running and THIS ceiling is what bounds it, which is why it sits above the documented max rather than at it.
  **NO ABORT REACHES cc AT A DETACH** — measured at CLI 2.1.258, the forwarder's socket stays open and still accepts frame writes long past that timeout, so cc has nothing to act on.
  A **kill** of the forwarder (an interrupt, or a stopped background task) closes the socket and is cc's cancellation channel, carrying no number either.
  The mirroring defect it avoids is this number becoming the deadline, which kills the command at the instant the agent was handed a pointer to it.
  **WHAT SETTLES A COMMAND IS cc's OWN CLOSING SENTINEL, not the `exit` frame**.
  The reference provider emits `exit` from the child's `'close'`, which fires when the STREAMS close — so a `cmd &` job that inherits the command's stdout pipe holds it open and the exit is never reported, and a command that exited 0 was handed to the worker as a FAILURE with an EMPTY stdout at the abandon timer above, while the complete parsed answer had been on the wire since ~154 ms.
  Reporting `exit` at PROCESS exit instead is not the fix and was measured losing up to 64 KB of a command's output to an undrained stream, with no zero-heuristic way for a provider to know a drain is done — so the fix is at cc's seam, where the sentinel is an exact boundary needing no grace timer.
  `ProviderShell` passes `completeMarker` (the closing sentinel) on `ShellExecOptions`; `ProviderSystem.#exec` scans each stream for it with the parser's own rules — line start, complete line — and settles when BOTH have it (stdout carries `$?` and the cwd, stderr carries a bare marker, and `#runOneShot` throws `ESHELLGONE` unless both parse).
  **`completeMarker` lives on `ShellHost`, never on the shared `ExecOptions`**: `LocalSystem.exec` takes the same options type and would accept-and-ignore it, so a caller could not tell which semantics it got; `ShellHost` has exactly one implementor.
  Settling then sends the **`detach` frame** — the operation is over, kill nothing — rather than `close`, which is abandon-and-kill-hard; without it the provider keeps the exec open with its timer armed and reaps the survivor when that fires.
  **That also closes a divergence between the two shipped capability configurations**: `close` reaps the background job only where `processGroupSignal` gives it group reach, so without the settle the same redirected command leaves a survivor on one system kind and not the other.
  Failure modes: `ETIMEDOUT` (the ceiling expired and the provider killed the command, OR the provider never reported the exit and cc abandoned it — the message says which), `ESHELLGONE` (the command destroyed its own framing — an `exit`, a syntax error — so no sentinel arrived; immediate, measured 17 ms against the 1504 ms a long-lived shell took on the same input, which is the whole of why the WEDGE CLASS IS GONE), `ECANCELLED`, `EFBIG`.
- `referenceProvider.ts` — **the local machine over the protocol**, with every optional capability settable by flag: `--no-process-group-signal` and `--remote <id>=<absolute root>` (repeatable — given at least one it advertises `remotes`, requires every `exec`/`readFile`/`writeFile` to name a known target (unknown or absent → an **id-addressed** `ENOREMOTE`), scopes each target to its own root, and injects `CC_REMOTE=<id>` into every child; it also advertises `remoteListing` and answers `listRemotes` with exactly its `--remote` ids (`docs/systems-protocol.md` §2.2), and refuses at launch an id `remoteIdDefect` rejects.
  Without `--remote` it advertises no `remoteListing` and refuses a stray `listRemotes` `EUNSUPPORTED`, id-addressed), plus `--mirror <[id=]absolute root>` and `--exclude <[id=]absolute path>` (repeatable) — the **mirror advertisement** (`docs/systems-protocol.md` §2.1), advertised as `remoteDescriptors` iff at least one is given, so with neither the wire is byte-identical.
  Those two are deliberately **independent of `--remote`'s root**: that root is a *fence* (outside it → `EACCES`) while an advertised mirror root is a *claim about geometry* cc consumes, and keeping them apart is what lets a test advertise a mirror wider than the fence and prove cc reads the advertisement rather than deriving it.
  The root scoping and `CC_REMOTE` exist because the provider runs on cc's OWN machine, where a wrong-target operation would otherwise still find the file and still go green: they make a misroute refusable and a correct route positively assertable.
  **The `exec` cwd fence exempts the exact path `/`** — cc's placeholder for a derived command, which carries its real target in `argv` (see `docs/systems-protocol.md` §7); what binds those instead is the `remoteId` on every frame.
  With no `--remote` flags nothing is injected and behaviour is byte-identical.
  **It reports `exit` from the child's `'close'`, i.e. when the STREAMS close, not when the process exits** — measured as the ONLY choice that does not drop output (reporting at process exit lost up to 64 KB of an undrained stream), and the reason cc settles a redirected command on its own sentinel instead of waiting for the frame.
  Its `detach` handler is `close` minus the kill: it marks the exec closed, clears the deadline and drops the entry, and **leaves the `'data'` listeners attached with the streams flowing**, so a survivor holding the pipe is drained-and-discarded rather than blocked (`pause()`) or SIGPIPEd (`destroy()`) — both measured, both divergences from a local background job.
  Dropping the entry also matters for teardown: `shutdown()` group-kills every exec still in the map.
  **fd accounting, measured: 2 fds per stream-held exec, and this is unchanged by `detach`** — the pipes never EOF while a survivor holds them, so they are released when the provider exits (stdin EOF → `shutdown()`), exactly as they already were after a `close`.
  Not a transport: it exists so the protocol's sufficiency is TESTABLE (see Testing → the systems gate), and as the worked example a third-party provider is written from.

**Where the seam sits.** `resolveProjectDir` resolves the system alongside the path and returns it (`{path, system}`), so `getProject` hands every caller a handle; path-taking git helpers (`runGit`, `isGitRepo`, `hasUnbornHead`, `worktreeDirtyLines`, `getHeadBranchAndSha`, `getProjectUpstreamStatus`, `getWorktreeMergeStatus`) take a `System` as their first argument; name-taking entry points (`createWorktree`, `syncWorktree`, `mergeWorktreeIntoParent`) resolve it internally — and the ones that take a project-or-worktree pair (`getProjectCommits`, every entry point in `src/gitDiff.ts`, and the `project_status` / `project_read` / `project_bash` MCP tools — `project_diff` REQUIRES a worktree and resolves its own via `getWorktree` + `resolveSystem`) go through the one exported `resolveProjectCwd` (`src/worktrees.ts`), which answers `{cwd, worktreeMeta, projectPath, system}` and throws a 404 for a worktree unregistered under that project. A worktree is on the same system as its parent by construction, so naming the pair is the ONLY addressing form that reaches one: a worktree has no record of its own in `<store>/projects/`, so nothing resolves its name as a project. `ProjectInfo` deliberately does NOT gain a handle — both REST and MCP spread it into a response body. **`runGit` is derived from `exec`, not a system operation of its own**, which is why one signature change converted the whole git surface. cc's own paths — the store, `~/.claude/**`, `<projectsRoot>/.worktrees/`, `<projectsRoot>/.plugins/`, self-update — stay direct local calls: they are not on any system.

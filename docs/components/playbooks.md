# Components: playbooks and convention skill parts

The playbook engine and convention skill parts.

## Playbooks

The playbook modules are layered so the policy is pure and the wiring is thin. The wire contract, the tool arguments and the known limitations are in [protocol.md → Playbooks](../protocol.md#playbooks); this is the internal shape.

- **`src/playbooks.ts`** — definition catalog (built-in seeds + user overlay through the shared `fragmentCatalog.ts` factory, plus enabled plugins' playbooks through `setPluginPlaybooksProvider` — wired by `server.ts` to `pluginHost.playbooks()`, deliberately NOT through the catalog's `extraProvider`, whose throw path discards every extra entry including the overlay; plugin ids are namespaced `<plugin-id>/<slug>`, the loader stamps `plugin` on them and `builtin` on a shipped definition — `playbookSource` reads the pair, and `pluginIdOfPlaybook`/`missingPlaybookCause` attribute an unloaded id to its plugin off the `/` alone), the load-time validator, and the **pure** policy decision `decide({toolName, args, projection, playbooks, isLive})` → `{ok, patchedArgs, move}` or `{ok:false, code, reason, legalMoves}`. `isLive: (sessionId) => boolean` is a **required** parameter, never defaulted — a default reading the projection would reintroduce the second liveness authority this shape exists to rule out — so every call site is a compile error away from being found. A bad definition is rejected **at load time**, not at spawn time. The governable-tool index resolves through a **memoized dynamic import** of `mcp/tools.ts` specifically so `handlers.ts → playbooks.ts` (which the read tools need) cannot close a cycle; `validatePlaybook` is pure and synchronous, taking that index as a parameter; `locateValidationError`, beside it, maps its messages back to a stage or edge by their prefixes. Also owns the payload builders both read surfaces share — `playbookSummary` / `playbookDetail` (`list_playbooks`/`describe_playbook` and the REST routes) — and the overlay's id listing `userPlaybookIds` + `RESERVED_OVERLAY_ID`.
- **`src/eventLog.ts`** — the event log's writer and reader (`<store>/events.jsonl`; format owned by [event-log.md](../event-log.md)). Append-only (**never** `writeFileAtomic` or a rewritten document — the `archive-store-corruption` failure was a rewritten JSON store wiping itself). `createEventLog({file, lease, onWritten, onBlocked})` owns the **serial chain**: each step resolves a thunk (so a row decided against the projection reads it after every earlier row folded), runs `lease.check()` and the write in **one synchronous step** (`fs.appendFileSync`, one call per `append` — a row array lands adjacent), stamps `v`/`ts`, then calls `onWritten` per row. A refused lease drops the rows and reports the episode (`console.error` once, `onBlocked` once, a `console.warn` per row, a `console.log` on recovery); nothing is queued, since a late row would land out of order. A failed write warns and never poisons the chain. `readEventLog` skips torn lines, other `v`s and unknown kinds, and creates nothing. The store path resolves through a **lazy** function so a `PROJECTS_ROOT` override is honoured per call.
- **`src/playbookState.ts`** — the in-memory **projection** folded from event-log rows. One `applyRow` serves both the boot fold (`foldPlaybookState`) and each live write, so an incrementally-updated projection cannot diverge from one folded from the file. Only a `call` with `bind` (replaces the worker's state) or `move` (sets `stage`, pushes it onto `stageHistory`, merges `provenance`; a `move` onto the stage the worker already holds folds nothing) and a `config` row (`enforcement.set(subject, to)`) fold to anything. The projection carries **no liveness bit** — `session` rows fold to nothing — so `WorkerState` has nothing for a second reader to consult by mistake. Run membership is **derived** — the connected component over `provenance` edges, via union-find — so there are no run ids and no external entity to keep in sync. `stageHistory` lists stage changes (a same-stage call has no `move`) and is what makes a `needs` entry's provenance half answerable; its `liveness` half is answered from `InstanceManager.isSessionLive` (`src/instances.ts`), THE single liveness authority — `liveSessionsInStage(p, anchor, stage, isLive)` and `liveSessionsOnPlaybook(p, playbook, isLive)` take that oracle as a required parameter rather than reading a fold. `playbookBinding(p, sessionId)` is the one binding reader every surface that reports a worker's playbook/stage folds through — `null`/`null` for an untracked worker, a null projection, or a non-string sessionId — so MCP's `conductorRowView`/`describeSession`/`listSessions`' inactive rows can never drift from REST's `GET /api/instances`, which reaches it only through the gate's `readBindings` (below).
- **`src/mcp/playbookGate.ts`** — the single enforcement point and the **single write path** into the event log: its `append` is the only `eventLog.append(` call in `src/` (`tests/event-log-chokepoint.test.mjs`).
  Constructed **once** in `createServer` (`server.ts`) with the lease `{check: () => rootLock.writerCheck()}` (a server built without the root lock gets a lease that always refuses; `createServer`'s `eventLogLease` is the test seam) and shared by `buildMcpRouter` and `buildRoutes`, rather than composed inside either router: a second gate would double-record the session stream and hold a projection the other router's writes never reach.
  Owns the conductor predicate lookup, the enforcement-level read, `decide()`, the refusal payload, and the `call` rows: **exactly one per governed call** that is refused (`check()`, either level, any governable tool) or that runs as an interaction call or `spawn_instance` (`commit(result)`: `ok`, or `failed` on an `ok:false` result; `fail(err)`: `failed` on a throw, called from the call core's catch in `runToolSteps` (`src/mcp/server.ts`), which `runTool` runs for both `dispatch` and the REST alias's `restCall` — a throw after the handler returned is not recorded twice).
  A governed read-only call that is not refused writes nothing.
  `failure.reason` comes from the result's `reason` or the error's message, capped at `FAILURE_REASON_MAX`, never from arguments.
  A spawn's `bind` and a transition's `move` are decided **inside the chain** (thunks): a result naming an already-bound session writes its row without `bind`, and a `move` is written only while the subject still holds `move.from` — so two concurrent calls decided against one projection can neither both bind nor both move.
  Under `warn` it also pushes a UI-only `system`/`playbook_warn` event onto the **calling conductor** (`_emitUi`, strictly after the row) — the log has no reader, so without it the mode that exists to warn a human warns nobody; the conductor *agent* is unaffected, since `_emitUi` never reaches the CLI.
  The gate's `append` chains every write behind the one memoised fold of the file (`ensureLoaded`, on first use — after the root lock is held, so the fold sees every row a previous server wrote), and the log path is **pinned on first resolution**, so a deferred write lands in the store it was decided against.
  `onWritten` folds each row into the projection and, after a row carrying `bind` or `move`, emits `playbook_changed({sessionId})` on the manager — AFTER the fold, so a listener reading the projection always sees the new binding — which `wsHub` turns into the same `instances` hint a status flip produces.
  `onBlocked` pushes the `event_log_blocked` bubble into the live conductor the first dropped row names.
  The gate also exposes `isLive(sessionId) => instances.isSessionLive(sessionId)`, the SAME oracle every `decide()` call here uses, so a read surface (`playbook_state`, `describe_playbook`'s dry-run) answers from the identical source — and `readBindings(sessionIds)` (`playbookBinding` mapped over one `readProjection()` read), the batch binding lookup `GET /api/instances` uses, and `readLiveWorkers(playbook)`, the same service for `src/playbookApi.ts`'s `liveWorkers`.
  A host reboot (or an orchestrator crash) needs no boot-time repair: capacity and `needs.liveness` both read `isSessionLive` directly, so a session this process's registry never heard of simply holds no slot — see [protocol.md → Playbooks](../protocol.md#playbooks).
- **`src/mcp/sessionRecorder.ts`** — `attachSessionRecorder`, called once by the gate, turns the manager's session stream into rows through the gate's `append`, so whichever surface causes an edge is recorded without knowing the log exists. Neither `instances.ts`, `idleSubscriptions.ts`, `routes.ts`, `wsHub.ts` nor `playbookApi.ts` imports the log (`tests/event-log-chokepoint.test.mjs`).
  - `session_launched` → `session` `start`/`resume` for **every** session (`Instance.launch` emits `launch` after its pre-spawn refusal checks and before this launch's first `status`; the manager relays it with the public id, `conducted`, `project`, `playbookEnforcement`, `cause` and `actor`). For a conductor whose level the projection lacks, a `config` birth follows in the same write.
  - `session_exited` → `session` `exit`, once per announced launch (`Instance._setStatus` on the alive→dead edge while `_sessionOpen`; `kill({actor})`/`remove(id, {actor})` set `_exitActor`). A session still in a recorded turn gets a synthesized `turn` `end` in the same write, before the exit.
  - `turn_started` / `turn_ended` → `turn` rows for conductors and conducted workers (`turn_start` from `_setStatus`'s into-`turn` edge, its actor set by `prompt()` around that transition — the explicit `actor` a sender passes (the MCP send handlers' caller, the renewal reseed's requesting conductor; a batch of parked steers from several conductors is `{type:'conductor'}` with no sessionId), else `system` for an `internal` prompt, else from the prompt's `author` with the root (`rootSessionId`) standing in for an unnamed conductor; `turn_ended` at the outer, live `turn_end` in `_handleStdoutLine`).
  - `wake_delivered` (from `IdleSubscriptionHub.deliver()`) → `wake`, for a conductor caller only.
  - `enforcement_changed` (from `Instance.setPlaybookEnforcement`) → `config` with `from` read off the projection, skipped when equal.
  - **`session` rows follow the process, not the session.** A rotation that kills and relaunches its process (`pruneSession`, `rewindToUserMessage`, a restart model switch, `respawn`, a restart restore) writes an `exit` then a `resume` with that cause, for a session that continues under the same public id; an in-place rotation (renew, a typed `/clear` — the new `session_id` arrives in `system/init` on the running process) writes neither.
- **`src/playbookConvention.ts`** — the pure renderer `renderPlaybookConvention(pb)` behind the preferred-playbook convention (contract in [protocol.md → Playbooks](../protocol.md#playbooks)). Pure and store-free so it is unit-testable against a definition object; composed by `conductorConventions.ts` (`getDefaultPlaybookSelection`/`setDefaultPlaybook`/`resolveDefaultPlaybookId`/`defaultPlaybookConvention`), which resolves the selected id through `loadPlaybooks()` rather than a second discovery layer. Authored `description` text is passed through **verbatim** — the definition is its one home, and a renderer that reflowed or truncated it would become a second.
- **`src/mcp/handlers.ts`** — the three read tools, reading the gate's one projection through `readProjection()`/`readHistory()` rather than folding a second. Both load on demand, and that load is read-only, which is what lets a read tool answer on an install with no event log yet without materialising the file. `playbook_state`'s history keeps only the run members' `call`/`session` rows and the caller's own `config` rows before its cap (`HISTORY_CAP`), so `turn` and `wake` rows cannot evict it.
- **The worker-tools check** — `PlaybookGate.checkWorkerTool` answers the PreToolUse entry every session carries on `?policy=worker-tools` (`WORKER_TOOLS_MATCHER`/`WORKER_TOOLS_POLICY`, `src/settings.ts`). The `POST /instances/:id/hook-callback` route in `src/routes.ts` branches on that query **before** the `HookBroker`, so no broker handler runs twice, and answers through `workerToolsHookBody` (`src/hookBroker.ts`): deny or `{}`, never allow. The check reads the binding from the in-memory projection (an unbound session costs one Map lookup, no disk read), then the definition per call, and resolves through `resolveWorkerTool` (`src/playbooks.ts`). It writes through the same `append` as every other row (actor `worker`), so the chokepoint test is unchanged. Fails open, with a `console.warn`, on definition drift (once per binding, a module-level set) and on any throw. Contract: [protocol.md → Worker tools](../protocol.md#worker-tools-workertools). The CLI behaviours it rests on — a hook deny blocks under `bypassPermissions` beside a sibling allow; a `*` matcher reaches MCP tools and subagent calls — are pinned by `tests/worker-tools-cli-deny.real.test.mjs` and `tests/worker-tools-cli-scope.real.test.mjs` (`RUN_CLI_CONTRACT=1`).
- **`src/playbookApi.ts`** — `buildPlaybookApi({playbookGate})`, the `/api/playbooks` read + validate router mounted from `routes.ts` (contract in [protocol.md → REST — `/api/playbooks`](../protocol.md#rest--apiplaybooks)). Delegations to `src/playbooks.ts` only; no write route. Reads playbook state through the gate's `readLiveWorkers()` alone — `tests/event-log-chokepoint.test.mjs` refuses an `eventLog` import here.

**Definitions are the authority on what the graph is; the projection is the authority on where workers are; the instance field is the authority on the enforcement level.** The persisted `defaultPlaybookEnforcement` (`conductorConventions.ts`) supplies only the level a conductor is **born** at, applied in `Manager._doCreate` before `launch()`; nothing writes back to it, so the runtime authority is never split. `projection.enforcement` serves the audit trail — the `config` birth/change rows read it for `from` — and has **no policy reader**: `playbook_state` reports the calling conductor's live mode off its instance instead, which also means nothing can surface a non-conductor as a governed actor.

## Convention skill parts

A convention fragment file may hand part of its text to a Claude Code **skill**, which costs nothing in the system prompt until the model invokes it. The skill part travels through exactly the selection its inline part does — the toggle, the plugin being enabled and `ok`, and the scope — because both come out of one compose.

**Marker grammar** (`splitSkillPart`, `shared/skillPart.ts`):

| Line | Where | Skill name |
|---|---|---|
| `<!-- cc:skill <description> -->` | a seed fragment, a plugin convention `file`, or a custom convention body (Settings) | the slug (plugin: the part after `<id>/`; custom: the custom slug) |
| `<!-- cc:skill:<name> <description> -->` | a scope's `core.md` | `<name>`, matching `SKILL_NAME_RE` (`^[a-z0-9][a-z0-9-]*$`) |

- The marker is a line starting at column 0 with `<!-- cc:skill` followed by a space, `:` or `-->`; any such line is parsed, so a malformed one is an error, never inline text.
- **Inline part** = everything above the marker, trailing whitespace stripped. May be empty (a skill-only fragment; compose already skips empty bodies).
- **Skill body** = everything below, leading blank lines and trailing whitespace stripped. Must be non-empty.
- **No marker → `{inline: text.replace(/\s+$/, '')}`**, the exact transform a seed body always had, so a marker-less tree composes byte-identically.
- Errors (thrown, naming the file): a second marker, an empty description, an empty body, a malformed marker line, an explicit name on a seed/plugin fragment, a missing name on a core, and a core name equal to a seed slug of its own scope (`readCoreFragment`, `src/fragmentCatalog.ts`) — so each skill name in a namespace has exactly one source.

**Read sites — the only four that split:**
1. Seed bodies, in `createFragmentCatalog` behind `skillParts: true` (the three convention scopes; `playbooks.ts` passes nothing, its seeds are JSON). The entry gains `skill: {description, body}`; `body` is the inline part.
2. The always-on cores, `getCore()` in `conductorConventions.ts` / `workspaceConventions.ts` via `readCoreFragment`. `conventions/conductor/footer.md` is never split.
3. Plugin convention `file` bodies in `contributions.conventions()` (`src/plugins/contributions.ts`). `checkFragmentFiles` (`src/plugins/manifest.ts`) runs the same parser at manifest load, so a malformed marker makes the plugin `invalid`; one edited in after load drops that entry whole at compose time (warned), so neither part ships.

4. Custom bodies, in `getCatalog` (`customEntry`) behind the same `skillParts: true`. `source` is the stored text and `body` the inline part. A body with no marker is returned untouched (not right-trimmed), so a regenerated `CONVENTIONS.md` and the role doc stay byte-identical. The marker is validated on write (`addCustom`/`updateCustom` → 400 `<noun> body: <parser message>`); a stored marker that does not parse (a hand edit) keeps the whole body inline, sets `skillError` and warns naming the store file and slug, and the entry stays — custom slugs enter the conductor and workspace selections from the store, so dropping it would make every compose 400.

Never split: a scaffold, a playbook custom body or seed (`skillParts` off).

**One selection → both parts.** `composeWithMeta(slugs)` returns `{text, degraded, skills}`, with `skills` (`skillsOf(catalog, slugs)`, each slug once) taken off the same `getCatalog()` read as `text`. The scope composers have a parts form that reads the selection once — `composeWorkspaceParts` / `composeCurrentWorkspaceParts` and `composeConductParts` / `composeCurrentConductParts` → `{text, skills}`, core skill first — and the plain `composeWorkspace` / `composeConduct` (and `Current` forms) are their `.text`.

**Namespaces.** Each generated root is a Claude Code plugin (`.claude-plugin/plugin.json` `{name}` + `skills/<name>/SKILL.md`, frontmatter `name` + `description` as a JSON string, then the body — `renderSkill`). A skill is invoked as `<namespace>:<name>`:

| Source | Namespace | Skill |
|---|---|---|
| seed or core of scope `S` | `cc-<S>` (`cc-conductor`, `cc-workspace`, `cc-project`) | the slug / the core's `<name>` |
| custom convention of scope `S` | `cc-custom-<S>` | the custom slug |
| plugin `<id>`'s convention of scope `S` | `cc-<S>-<id>` | the plugin-local slug |

Slugs are unique per catalog (a custom slug 409s against seeds, customs and plugin slugs) and per manifest, a core name may not equal a seed slug, each plugin gets its own root, and no scope is named `custom`, so the three namespace forms are disjoint and no two sources can collide.

**Lifecycle.**
- `<store>/convention-skills/<instanceId>/` (`conventionSkillsDir`) is frozen on the `Instance` at create (`_conventionSkillsDir`; `null` for an `Instance` constructed directly, which writes none).
- Its **content is rewritten on every `Instance.launch()`** — fresh spawn, resume, respawn, rewind, restart-resume — because `.conduct/CONVENTIONS.md` is too; skills frozen at create would outlive a convention switched off since and then resumed, respawned or rewound. A **renewal does not relaunch** (it is an in-process `/clear`; no `launch()`/`spawn()` runs), so it refreshes neither the role doc nor the skills: both stay as the last launch wrote them. `writeConventionSkills` removes the dir, writes one root per non-empty namespace, and returns the roots in order: every built-in root (workspace, then the session's scope), then custom roots, then plugin roots. **No skill in force → nothing written, `[]` returned.**
  - Conductor: `materializeCurrentConduct(dir)` (`src/conduct.ts`) writes the role doc and the workspace + conductor skills from the same two composes.
  - Any other session: `projectSessionConventionSkills(system, cwd)` (`src/projectClaudeMd.ts`) reads `<cwd>/CONVENTIONS.md` through the project's System (`resolveSystem(project)`, live per launch). Absent → no skills. Otherwise the live workspace selection's skills plus the project skills of the file's line-1 marker slugs, off one `getCatalog()`; a slug the catalog lacks is skipped, as the document's `missing` set is.
  - **A worker's skill failure never blocks its launch.** Any throw computing or writing them (a non-ENOENT `CONVENTIONS.md` read, a failing workspace compose) logs `instances: convention skills for session <id> (<cwd>) unavailable — launching without them: <cause>` and launches with no convention roots. A conductor's skills come out of its role-doc compose, whose failure refuses the launch as it always has.
- **Known limitation — a worker's two parts have different sources.** Its inline text is the bytes of its `CONVENTIONS.md`; its skills are derived at launch from the live workspace selection plus that file's line-1 marker, resolved against the live catalog. While the file is stale — a worktree's tracked copy that predates a settings change, or a regeneration that declined (degraded catalog) or has not run yet — the two can disagree until the file is regenerated and the session relaunches. The conductor has no such gap: its doc and skills come from the same composes.
- `Instance.spawn()` appends `--plugin-dir <root>` for each `_conventionPluginDirs` entry **after** `claudePluginDirs`, so with no skill in force argv is unchanged.
- **Custom conventions.** An edit goes live on the schedule of its inline part, since one compose reads both: a conductor at its next `launch()` (a renewal does not relaunch), a worker's inline text when `CONVENTIONS.md` is regenerated (after every workspace or project Settings save) and its skill at its next launch. A running session keeps the files its last launch wrote. A deleted or disabled convention writes no skill at the next launch (a project marker naming a deleted slug skips it, as it does for the inline part). The slug is immutable, so a rename of `name` never changes the skill name; a new slug is a delete plus an add. A scaffold is read only at `create_project`, never persisted.
- Teardown is unconditional (not gated on `_redirect`) in `remove()`, `removeAllForProject()` and `shutdown()`; `sweepConventionSkillDirs([])` runs at boot in `server.ts` beside `sweepSessionTmpDirs([])`, for a killed orchestrator.

**Remote placement — delivered, never inlined.**
- A remote-backed session: the roots are under `orchStoreRoot()`, inside `projectsRoot`, which `buildTierTable` host-pins, so inside the FUSE chroot each `--plugin-dir` resolves to the host at the same spelling. No `localRoots` allow entry is added: a generated skill has no reference files, and the CLI's own skill load is not a file-tool call.
- A plugin whose project is on a remote System: its fragment is read through that System (as its inline part is) and the skill is written **locally**, so it reaches sessions even though the same plugin's `claudePlugin` root is skipped (`PLUGIN_DIR_LOCAL_ONLY` — a remote *directory* cannot be a `--plugin-dir`; this is a local copy of text cc already reads).

**Shipped skill parts.** The conductor core's plan-mode procedure (`cc-conductor:plan-mode`) and the `capturing-learnings` seed's procedure (`cc-conductor:capturing-learnings`) ship as skills; each inline part keeps its trigger pointer and the rules that must hold before the skill loads, and no sentence sits in both parts. A pointer to a skill belongs in the inline part of the same fragment, so a deselected convention drops both together.

**Tests:** `tests/convention-skill-parts.test.mjs` (grammar, catalog split incl. custom bodies, core naming), `tests/convention-skills-byte-identity.test.mjs` (no non-blank line of a shipped skill body appears in any composed doc; shipped files are well-formed and all read), `tests/conductor-conventions.test.mjs` → "Shipped skill parts" (the two shipped splits, and pointer ↔ delivery in the conductor doc), `tests/convention-skills-launch.test.mjs` (every gate end-to-end, relaunch, cleanup), `tests/convention-skills-remote.test.mjs` (remote session and remote plugin).

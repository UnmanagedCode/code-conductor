# Components: the plugin host

The plugin subsystem's server modules.

## `src/plugins/`

the plugin subsystem ([features](../features/plugins.md#plugins), [wire contracts](../plugins.md)). **Trust stance: plugins are trusted own code** — same-origin iframes + supervised child processes with the conductor's privileges; there is no sandboxing. Modules:
- **registry.ts** — `createPluginHost({instances})`, the single service layer shared by REST (`api.ts`), the reverse proxy and MCP forwarding.
  Owns discovery (iterate `listProjects()` — so an **adopted** out-of-root project carrying a manifest is discovered exactly like an in-root one — reading each project dir's manifest; a project whose main checkout has NO manifest file falls back to its worktree checkouts — first valid manifest in sorted-name order, via the store metadata with no git spawns — so a plugin-in-progress in an unmerged worktree can bootstrap (`manifestSource` marks the origin; enable then defaults `activeVersion` to that worktree; an invalid main manifest is never masked); duplicate id ⇒ first-alphabetical wins, rest `conflict`), lifecycle state (`stopped|starting|ready|crashed|failed` on top of `discovered/enabled⇄disabled` + `invalid|incompatible|conflict`), lazy `ensureStarted` (deduped in-flight start, exponential crash backoff and a crash-count threshold ⇒ `failed` (constants in `src/plugins/registry.ts`)), discovery-time CC-Dev workspace auto-assign (every rescan/boot places any unassigned discovered plugin project into CC-Dev, not just on enable — the conductor's own project gets the same placement via a separate one-time boot seed in `server.ts`, since it isn't a plugin), worktree-version activation (cwd resolved via `worktrees.ts` metadata; manifest re-read + id-checked from the active checkout every start), and **adopt-don't-drain**: children are detached process groups that survive the conductor's self-respawn — `init()` re-adopts a recorded pid that's alive+answering, else clears the record (the liveness predicate and the ready/adopted lifecycle mutation are here; the record pruning + its single write are the store's, see `store.ts` below).
  Health is passive (child exit events, proxy `reportUpstreamFailure`, on-demand `status()` probe, the `ensureStarted` fast path, the boot adopt pass) — no periodic poller (battery). Those touches also record an adopted backend's death (`markDead`, `adoptRunning`) and check its log size (`maybeTrimLog`). **Limitation:** an idle adopted backend's death is recorded only on the next touch or boot, and a long-running backend nothing touches can grow its log without bound until the next start rotates it.
  Init is lazy + memoized **on success only** and keyed to `projectsRoot()` (test roots swap) — a rejected init clears the memo before rethrowing, so one transient failure (e.g. a boot-time EMFILE/EIO) doesn't poison every later plugin-host call for the process lifetime; the next call reinitializes instead.
  **Contributions-only plugins** (manifest with `conventions` but no backend) enable but never start — the row reports `hasBackend:false` and state `enabled` (not `stopped`), and start refuses 400.
  Convention/role/playbook/`claudePlugin` contributions are NOT here — they live in the composed collaborator `contributions.ts` below, which the `conventions()`/`roles()`/`playbooks()`/`claudePluginDirs()` members point straight at; the registry keeps no cache state and only signals change into it (`invalidate()` from `rescanInternal`/`doStart`/`setActiveVersion`/`enable`, `noteRegistryChange()` from `saveRegistry` and `doStart`'s manifest reassignment).
  It does own `contributingEntries()` — the enabled+`ok` filter, which reads both the discovery catalog and the persisted records — and injects it, along with `ensureInit` and **`resolvePlacement`** — where a contributing plugin's checkout is RIGHT NOW, resolved on every read rather than captured at rescan.
  Three answers: `{kind:'ok', system, dir, cwd}`; `{kind:'unregistered'}` when `resolveProjectDir` returns null AND `projectStoreDir(name)` is gone AND `orchStoreRoot()` is still there — and each of those two store probes is an `fs.stat` with a deliberate error direction, never `existsSync`, which answers false on every error and so cannot tell "gone" from "unreadable": for the project's store dir **only ENOENT is gone** (anything else must not read as authoritatively unregistered), while for the store ROOT any error reads as absent (which sends the classification to the degrade branch) (that order is fixed — `deleteProject` removes the store dir on all three of its branches and an `rm -rf` of a checkout removes neither, which is what makes the middle term the discriminator, and the last term is the guard that stops a vanished store root classifying **every** plugin as unregistered at once); else a THROW, which the caller degrades on.
  `resolveCwd` stays for `doStart`, and the pure `versionCwd(activeVersion, worktreeMeta, base)` line is shared by it, `describeRow` and `resolvePlacement`.
  `describeRow` is now a ~15-line gatherer over `row.ts` — note it re-resolves the active VERSION per call but not the PLACEMENT, so a row's `system`/`localOnly` badge stays as of the last rescan.
- **contributions.ts** — `createContributions({ensureInit, contributingEntries, resolvePlacement})`, the composed collaborator owning everything enabled plugins contribute to the conductor beyond an HTTP backend: `conventions()`, `roles()`, `playbooks()`, `claudePluginDirs()`, `runCodeMembers()` (sync: every enabled `ok` plugin's declared `runCode` members, read per request by the MCP server) and `runCodeModule(id)` (where plugin `id`'s `runCode.module` file is, in its active checkout, plus its members' `{name, inputSchema}`, or why it is `unknown` (provides none right now) / `unavailable` (not on this machine); local-only like `claudePluginDirs`, read live per call through the registry-injected `lookupEntry(id)` over the `ok`-only `byId` and `store.isEnabled`, served to a program's first call into the namespace by the run channel's `GET /mcp/<sid>/run-modules/<id>`), BOTH caches (`fragmentBodyCache`, the memoized `conventions()` result) and the `registryGeneration` counter that invalidates the second — a counter whose only reader is that memo.
  The registry signals into it through `invalidate()` (drop bodies + bump) and `noteRegistryChange()` (bump only), and holds no cache of its own.
  `roles()` is deliberately **synchronous and init-free** (a role binding is inline in the manifest, and `appSettings.resolveRoleBackend` resolves it at spawn time; `server.ts` installs the provider before `init()`) — pinned by `tests/plugins-host-surface.test.mjs`.
  `playbooks()` is the inverse: **async and `await ensureInit()`** — it returns `{id:'<plugin-id>/<slug>', slug, plugin, body}` per declared playbook of an enabled+`ok` plugin, with the body `readManifest` read at manifest load (no placement, no cache), and its consumer (`loadPlaybooks`) runs on every governed MCP call and resume, so one arriving at boot before discovery must not see an empty set and refuse a good binding `PLAYBOOK_UNKNOWN` — pinned by the same file.
  The `conventions()` accessor returns the contributions of enabled+`ok` plugins only (bodies read from the active checkout through the placement's own `System` handle, cached in a single process-lifetime `fragmentBodyCache` keyed `${system.id}\0${system.remoteId ?? ''}\0${abs}` — **taken off the handle the read goes through**, never from a placement stored elsewhere, because a key derived from a second source can be a correct key for a machine the read never spoke to, i.e. a stale body served as healthy.
  For the same reason the narrow `ContributingEntry` this module declares carries `{id, project, manifest}` and no `dir`/`system`/`remoteId` at all) — each entry carries `body` (fragment, `''` when the convention is scaffold-only) and optional `scaffold` (resolved directive text).
  Two distinct failure modes, treated differently: a **vanished fragment/scaffold file** is skipped with a warning, same as always — the convention just contributes nothing, same as if it were never declared.
  A **failed placement resolution** is transient infra (a worktree checkout not yet mounted, a system that is down, or a checkout that vanished while cc still holds store state for the project), not "contributes nothing", so it additionally flags `.degraded` on **every** scope array the function returns — including ones left empty — because an empty-and-unflagged array is exactly what "this scope genuinely has no plugin contributions" looks like, and the one plugin that failed may have been the only would-be contributor to that scope; see `fragmentCatalog.ts`'s `CatalogList` and the [`src/projectClaudeMd.ts`](web.md#srcprojectclaudemdts) bullet for what a reader does with that.
  A third case sits between them: an **authoritatively unregistered** project (`resolvePlacement` → `{kind:'unregistered'}`) is skipped like a vanished file, NOT degraded — its absence is confirmed by cc's own local bookkeeping, and degrading would freeze every referencing `CONVENTIONS.md` until someone pressed Rescan, which in a running server is the only thing that retires a discovery entry.
  The cache is dropped wholesale (the registry calls `contributions.invalidate()`) at the start of `rescanInternal()`, at the top of `doStart()`'s async body, right after `setActiveVersion()`'s `saveRegistry()`, and right after `enable()`'s `saveRegistry()` — every explicit "the checkout on disk moved, or a disabled plugin's fragments are about to matter again" gesture (rescan, start/restart, an active-version switch even on a stopped/backendless plugin, and enable — a fragment can be edited while its plugin sits disabled) — so neither a `git pull` into an already-loaded checkout nor an edit made while disabled keeps serving stale fragment text for the process lifetime.
  `conventions()` itself is **memoized**, because it is not a cheap read (it walks `contributingEntries()` and calls `resolvePlacement()` per contributing plugin, which resolves the project and — for a worktree-pinned plugin — does a dynamic `import('../worktrees.ts')` plus a store read — and `server.ts` wires **two** providers onto it, so one `GET /api/settings/conventions/conductor` was two full scans and a mutating plugin route fanned out through `regenerateAllProjectConventions` at two scans per project).
  The invalidation signal has **three parts, all load-bearing**: (1) a `registryGeneration` counter, owned here and bumped through `noteRegistryChange()` from `saveRegistry()` (which every mutation of `persisted.plugins` is immediately followed by — so the set is provably complete rather than hand-enumerated, and it is what catches `disable()`, which deliberately does *not* drop fragment bodies), inside `invalidate()` (so a stale fragment body can never survive in a cached result), and — again via `noteRegistryChange()` — immediately after `doStart()`'s `entry.manifest = result.manifest` reassignment (which happens ten lines *after* that function's own invalidate, so a concurrent read landing in between would otherwise be cached pre-reassignment); and (2) a per-call `existsSync` liveness re-check of the checkout dirs the cached scan actually read — both the discovered project dir and the resolved cwd.
  A checkout deleted from under a running server mutates no registry state, so the counter alone cannot see it, and serving a cached "still here" would silently disable the `.degraded` flag that `ensureProjectConventionsMd`'s never-blanks decline depends on; a vanished dir simply falls through to the real scan, which degrades exactly as it does uncached; and (3) a per-call **placement fingerprint** — `systemHandleGeneration()` (`src/systems/registry.ts`, bumped whenever a live provider handle is dropped) joined with `placementToken(project)` (`src/projectRegistry.ts`) per contributing plugin.
  Part (2) exists because a project's TREE is state this host does not own; a project's PLACEMENT is the same kind of state, so this is that argument one step out rather than a third mechanism.
  `placementToken` is the cheap LOCAL prefix of `resolveProjectDir` — the record's `(system, remoteId, systemPath)` tuple for a non-local placement, else which local artefact registers the project (`root` / `ext:<realpath>` / `gone`) — and it reaches no system and never throws, because a version that resolved the system would throw on every compose while a box was down and flip the catalog permanently degraded.
  `systemHandleGeneration()` is the one term the per-plugin tokens cannot carry: re-pointing a system's provider command leaves the record, the fragment path and the cache KEY byte-identical while the machine behind them changes.
  **`fragmentBodyCache` is labelled PER ENTRY, and that is the whole of its correctness: a cached body is served only under the exact state it was read under.**
  Each entry is `{label, body}` where the label joins `cacheEpoch` (bumped by `invalidate()` — the bytes at a path may have changed under a placement that did not move: a `git pull`, a version switch, a fragment edited while disabled) with the placement fingerprint above (the path may now name a different tree — and `setProjectRemote`/`updateSystem` call no `invalidate()`, so neither half implies the other).
  The label is captured ONCE at the top of a scan and handed to every read it makes; `readFragment` is the one insert site and the one lookup site, and it always writes the label it was handed.
  A retired entry is kept out by **two deliberately redundant guards** — the lookup treats a non-matching label as a miss, and `conventions()` sweeps non-matching entries at the top of each scan.
  Neither is *the* guard: mutation proof measured that removing either one alone leaves the suite green, and only removing both reopens the hole, so they are kept together (opposite ends of the same property, for the price of a string compare).
  **A per-MAP label was tried and is not sufficient**: it is a claim made at one instant about a map written over a whole scan, and two interleaves broke it — a degraded compose discards the memoized result while leaving the bodies cached, and an `invalidate()` landing MID-SCAN voids the running scan's claim after some of its inserts have happened.
  Both ended as a body from one machine served for another at `degraded:false`.
  With the label on the entry, a scan whose label is voided while it runs cannot contribute a servable entry at all — its inserts are inert rather than mislabelled — so the property holds without any assumption about which other gesture fired when.
  `invalidate()` still clears the map outright, and bumps the epoch as well — clearing alone is undone by an in-flight scan repopulating the map, and the epoch is what makes those late inserts unservable.
  **A degraded result is not memoized at all** — degraded means "a transient failure stopped me telling you", and a cached transient needs an unrelated gesture to clear (a remote system coming back up changes neither the generation nor the fingerprint, so the catalog would keep declaring itself degraded, and keep every referencing `CONVENTIONS.md` frozen, until the next rescan); the re-scan cost is bounded by the fact that a degraded catalog is exactly the state in which the fan-out it feeds does not write.
  The generation is snapshotted **before** the scan loop, because `reconcileActiveVersion` can `saveRegistry()` mid-computation when it self-heals a vanished worktree pin — the result is then tagged stale and recomputed once, and the idempotent self-heal does not bump again.
  **The returned object is shared by reference and must be treated as read-only**; both consumers are verified non-mutating (`fragmentCatalog.ts` reads `.degraded` then copies every entry via `raw.map(r => ({...r, builtin:false}))`; `server.ts`'s two providers only index `.project` / `.conductor`).
  No defensive shallow copy is made — the entry objects would still be shared, so it would buy the appearance of safety rather than safety.
  `server.ts` wires it to the projectConventions and conductorConventions providers.
  `conventions()` is **grouped by the required per-entry `scope`** (keyed by `SUPPORTED_CONVENTION_SCOPES` from manifest.ts; `project`/`conductor` today, `workspace` rejected at load); `server.ts` routes the `project` group to `projectConventions` and the `conductor` group to `conductorConventions`, so adding a scope is a one-line enum move + one provider wiring, not a redesign.
- **store.ts** — `createPluginStore({onRegistryChange})`, the persistence collaborator: the three JSON files under `<orchStoreRoot()>/plugins/` — `registry.json` `{plugins:{<id>:{project, enabled, activeVersion, autoStart}}}`, `runtime.json` `{<id>:{pid, pgid, port, startedAt, gitHead}}` and `exits.json` `{<id>: ExitRecord[]}` (newest first, `EXIT_HISTORY` per id; `recordExit` saves through a promise chain so the last write carries the newest state, and a failed write is warned, never thrown) (shapes pinned by `tests/plugins-store-files.test.mjs`) — plus their load policy and the adopt pass's record pruning.
  A non-ENOENT load failure of any of the three is **not** swallowed: the bad file is renamed to `<file>.corrupt` — a fixed name, so a prior backup is overwritten — and recorded on `notices()`, which the registry re-exports, `GET /api/plugins` returns and the Settings → Plugins status line renders; without that, the `{plugins:{}}` fallback silently resets every plugin's enabled state and pinned version with nothing anywhere saying so.
  A failed rename is itself non-fatal — the notice carries `backup: null`.
  Notices reset per `load()` pass, and `load()` reads registry.json, then runtime.json, then exits.json.
  **Reads hand out shallow copies and every mutator writes** (`upsert`/`setEnabled`/`setAutoStart`/`setActiveVersion` for registry.json; `recordStart`/`clearRuntime`/`clearRuntimeDetached`/`adopt` for runtime.json) — that is what the boundary buys: no code outside this module can change persisted state without going through a method that persists it.
  `onRegistryChange` fires from the single registry.json save path, BEFORE the write (a failed write still leaves the contributions cache invalidated), which is what makes the invalidation set provably complete rather than hand-enumerated.
  `adopt({isAdoptable})` is **inverted** rather than lifted whole: the store iterates only its own records, asks the injected predicate, clears the rejects in one write (only when something changed) and returns the adopted ids for the registry to mark ready — moving the whole pass here would have needed back-references to discovery and lifecycle.
  The file paths are functions, recomputed per call, so a `PROJECTS_ROOT` swap between test roots is picked up.
  It also exports `pluginDataDir(id)`: the path of a plugin's data dir under a dedicated `plugins/data/` (an id may equal `library`), slug-guarded, never touched by the store — contract in [plugins/manifest.md → Child env](../plugins/manifest.md#manifest--conductorpluginjson-at-the-plugin-project-root).
- **row.ts** — `buildPluginRow({entry, reg, runtime, record, exits, activeVersion, cwd})` → `PluginRow`, the view-model `GET /api/plugins` serializes verbatim and Settings → Plugins (`web/src/features/settings/PluginsSection.tsx`) and the app switcher (`web/src/features/views/AppSwitcher.tsx`) read field by field (`crashTail`, `navLabel || name`, …). A **pure projection**: it writes nothing and closes over nothing, so every input is passed in and no shared mutable state crosses the boundary — which is what makes the field-set contract explicit instead of implicit. The registry's `describeRow` is the gatherer: it resolves (and self-heals) the active version, computes the checkout `cwd`, reads the persisted record / runtime state / runtime record, and calls this. The `headSha` git spawn stays behind `state === 'ready' && record?.gitHead` — only a running plugin can have moved past the sha it started at; `cwd` itself is computed unconditionally by the caller (pure, no I/O). `describe`/`list`/`status`/`rescan` stay in the registry — they are catalog/lifecycle queries that happen to return rows. `menuItems` is the manifest's validated entries (`[]` when none); `icon` is gated on `discoveryState === 'ok'` like it. Row-level contributions metadata (`conventions:[{slug,name,description,hasScaffold}]`, namespaced) is built here for the Settings badges; `hasScaffold` flags a convention whose pick triggers a one-time setup directive in addition to any fragment. Field set pinned by `tests/plugins-row-shape.test.mjs`.
- **manifest.ts** — `readManifest(dir)`/`validateManifest(json)` → normalized manifest or structured error list; rejects anything `validateArgs` can't validate (flat-object schema subset) at load time.
- **supervisor.ts** — factory port of code-hub's runner: `bash -lc <start>` spawned `detached` (pgid = pid) with the child env per [plugins/manifest.md → Child env](../plugins/manifest.md#manifest--conductorpluginjson-at-the-plugin-project-root) (`PORT` and `CONDUCTOR_PLUGIN_ID` set here, the rest passed in by the registry's `doStart`), readiness readyWhen-regex → healthPath → TCP within 30 s, 400 ms settle window + EADDRINUSE retry ×3 on fresh ports, stdout+stderr as ONE append-mode log file cc opens and hands over as fds 1 and 2 (rotated once per `start()`; `readyWhen` and the crash tail are read back from it from a per-attempt `logOffset`; a bounded tail, `OUTPUT_CAP`, `src/plugins/supervisor.ts`), an `onChildExit` callback fired for every exit of a spawned child (`stopRequested` set by `stop()`), stop = `kill(-pgid, SIGTERM)` → SIGKILL after 3 s, `git rev-parse HEAD` recorded per start. **All three readiness modes share ONE `poll`** — the mode picks the predicate (regex / `httpOk` / `tcpOpen`), never the loop — and that loop is **cancelled when the child exits before readiness**, via an `abort` predicate that reads the same `status !== 'starting'` condition `settle()` guards on, so liveness has exactly one authority. Without that cancellation a child that dies *after* the settle window left the probe running for the full 30 s timeout, aiming HTTP GETs / connects at a port it never owned and that `allocatePort()` may already have reissued to another plugin (in tests it also leaked a ref'd `Socket`/`Timeout` past the file's own teardown). The bare-TCP mode's timeout error is now `readiness not confirmed within timeout` like the other two, not `waitForPort`'s `port … not listening within …`.
- **backendLog.ts** — stateless log-file lifecycle: `backendLogPaths(id)` (slug-guarded, `plugins/logs/<id>/backend.log` + `backend.prev.log`), `rotateBackendLog` (delegates to `rotateFile` in `src/logRotation.ts`), `openBackendLog` (`O_APPEND`, load-bearing: the child's duplicated fds share the file description, so a write after a trim lands at the new end), `readLogTail` and `trimLog` (re-exported from `src/logRotation.ts`); the size constants `LOG_MAX_BYTES`, `LOG_KEEP_BYTES`, `LOG_TAIL_BYTES`. Behaviour and limits: [plugins/runtime.md → Backend output and exit history](../plugins/runtime.md#backend-output-and-exit-history). Pinned by `tests/plugins-backend-log.test.mjs` and `tests/plugins-backend-orphan.test.mjs`.
- **ports.ts** — `allocatePort` (bind-:0-close), `tcpOpen` (one-shot connect probe → boolean; destroys the socket on both paths), `waitForPort` (`tcpOpen` on a poll loop — supervisor readiness no longer uses it; `registry.ts`'s `probeAnswers` does), `pidAlive`.
- **proxy.ts** — hand-rolled streaming reverse proxy (no body parsing; SSE free) + raw-socket WebSocket upgrade pipe with `rawHeaders` order/casing replay; mounted after `/mcp`, before static. Response headers go through `proxiedPluginHeaders` (`src/securityHeaders.ts`).
- **api.ts** — `/api/plugins` REST router, thin delegations to the registry and to `library.ts`, mounted from `routes.ts`. Also owns the project-conventions fan-out: every mutating route (`rescan`, `:id/enable`, `:id/disable`, `:id/restart`, `:id/version`, and the two library routes) calls a local `refreshProjectConventions()` after its underlying mutation succeeds, which best-effort-calls `regenerateAllProjectConventions({log:console})` (`projectClaudeMd.ts`) so every project's `CONVENTIONS.md` picks up the change — never throws (a regenerate failure must never turn a successful mutation into an error response); the `{log:console}` surfaces `ensureProjectConventionsMd`'s per-project log lines in the server log (contract + exact strings: the [`src/projectClaudeMd.ts`](web.md#srcprojectclaudemdts) bullet).
- **library.ts** — `createPluginLibrary({pluginHost, _cloneImpl, _runHookImpl})`, the Plugin Library collaborator: a catalog of installable plugins (git repo URLs) separate from the discovery-based registry above.
  `list()` layers the built-in `DEFAULT_ENTRIES` (omitted when `getPluginLibrarySettings().builtinLibrary` is false), then drop-in manifests from `<orchStoreRoot()>/plugins/library/*.json`, then each configured `libraryDirs` directory (`readLibraryEntries` → `readCatalogDir`; files in sorted filename order; the last entry applied for an `id` wins; malformed/incomplete files and unreadable configured dirs land in `skipped: [{dir, file|null, reason}]`).
  Each internal `CatalogEntry` carries its `source: {dir, file}` (`null` for a built-in; stripped from the wire row) — `dir` is what a `catalog:` repo resolves against, and `dir`/`file` name the entry in `skipped` when its repo is refused.
  **`resolveRepoUrl(repo, sourceDir)` is the choke point** — the only producer of a `CloneUrl` (a branded string; `CloneImpl`/`cloneRepo` accept nothing else): an http(s)/git URL verbatim or a canonical `file:///` URL, with `catalog:<relative path>` resolved against `sourceDir` (full table in [plugins/rest.md](../plugins/rest.md#local--offline-catalogs)).
  `cloneRepo` hands git a `file:` URL as its local path with `clone --no-local` — the path so a git bundle is detected, `--no-local` so a directory mirror's objects are never hardlinked.
  Every refusal is raised there, before streaming: a `file:` output is `pathToFileURL` of a NUL-free path, so `cloneRepo`'s `fileURLToPath` is total.
  `projectNameFor(entry)` runs the resolver, derives the name from the RESOLVED URL and runs `validateName` on it — shared by `list()`, `install()` and `update()`; `list()` moves a catalog file's entry it refuses out of `entries` into `skipped` (a built-in's refusal is thrown as a bug).
  Each row is flagged `installed`/`installedAs` by whether that name is registered.
  `install()`'s own "already installed" probe reads the project RECORD (`readProjectRecord`) rather than an in-root `fs.stat`, so an **adopted** project holding that name refuses the install too instead of minting a second identity for one name.
  `install(id)` resolves the repo (400 on refusal, before `onValidated` flips the route into streaming), derives the target project name from the resolved URL's last path segment (`.git`/`.bundle` stripped, run through `projects.ts`'s `validateName`), refuses if the target already exists (409), clones via the shared streaming `runGitLive` (`src/gitLive.ts`; bounded timeout, never throws — `{code,stdout,stderr}` shape), cleans up a partial directory on failure (502 + stderr tail) so a retry isn't permanently blocked, and on success calls `pluginHost.rescan()`, **enables the freshly-discovered plugin by default** (only a `state:'discovered'` row — an invalid/conflicting manifest is left disabled; `enable()` is start-neutral so no process launches at install time), then runs the entry's `postClone` if set.
  `update(id)` is the symmetric counterpart: 404 if not installed, `git pull --ff-only` via the same `runGitLive` — the pull and the rescan wrapped in `pullPastGeneratedConventions` (`src/conventionsCheckout.ts`) — 502+tail on pull failure (never attempts a merge), else rescan (drops the registry's fragment-body cache), run `postPull`, then resolve the eligible-to-restart set via `resolveRunningIds(pluginHost, projectName)` (reads `pluginHost.list()`, filters to this project's rows whose `state` is `ready`/`starting`) **before** looking at `postPull`'s outcome — this ordering matters: an empty set always reports `null` regardless of `postPull`, so "nothing was running" is never mislabeled as a skip.
  A non-empty set with a failed `postPull` skips the restart outright — `restarted = {skipped:'postPull-failed'}` — rather than attempting it, because a failed `postPull` leaves the checkout half-built and restarting into it would trade a healthy child serving old code for a crash-looping one serving no code at all; otherwise `restartIds(pluginHost, ids, onChunk)` restarts (`pluginHost.restart(id)`) each of them and returns `{ids, ok, error}` on success/failure; never throws (a restart failure is soft, exactly like a failed `postPull` — the pull already landed on disk) and never starts a stopped plugin (it'll pick up the new code lazily on its next start).
  `update()`'s result gains a `restarted: {ids,ok,error} | {skipped:'postPull-failed'} | null` field carrying that value.
  Update **detection** in `list()` runs a bounded best-effort `fetchOriginBounded` (`src/gitLive.ts`) then `getProjectUpstreamStatus` (`worktrees.ts`) per installed row, flagging `updateAvailable`/`behind`.
  Both `postClone`/`postPull` go through a shared `runHook()`/`runHookCommand()` pair: `runHookCommand` runs the command via `spawn('bash', ['-lc', cmd], {detached:true})` with a process-group kill on timeout (mirrors `worktrees.ts`'s `runWorktreeHook`, not `cloneRepo`'s simpler `execFile` timeout — a hook like `npm install` can spawn grandchildren a plain child-kill would orphan) and never rejects; `runHook()` wraps it into `{ran, ok, code, tail}` (or `null` if the entry has no such field).
  Failure handling is deliberately asymmetric: a failed clone/pull is a hard failure (reject + rollback for clone); a failed post-hook or restart is a **soft warning** on an otherwise-successful `install()`/`update()` response — the clone/pull already succeeded and is already discoverable, so the result resolves with `postClone`/`postPull: {ok:false, tail}` / `restarted: {ok:false, error}` instead of throwing.
- **mcpBridge.ts** — composed collaborator turning enabled plugins' manifest tools into core-shaped entries (`<plugin-id>__<tool>`, with the manifest `outputSchema` when declared); `buildMcpRouter`'s `composeTools(format, callerKind)` builds `ctx.tools` per request from the core registry plus `pluginHost.toolsFor()` — first dropping the tools outside the caller's audience into `ctx.barredTools` (`audienceAdmits`, `src/mcp/toolAudience.ts`; the kind comes from `callerKindOf` over `isConductorInstance`; core tools are barred the same way, from the per-kind core registry), so a call is refused `TOOL_UNAVAILABLE_TO_CALLER`; then, in json only the plugin tools with an `outputSchema`, the rest named in `ctx.textOnlyTools` so a call is refused `TOOL_UNAVAILABLE_IN_FORMAT` — so dynamism (enable/disable) lands without touching tools/list / tools/call. Each forward carries the request's `format`; the handler re-reads the active checkout's manifest, refuses a json call to a tool that no longer declares `outputSchema`, and checks the child's reply against its format's shape (a tool error first — shape in docs/plugins/tools.md → Typed plugin tools, rule 6; json `{structured}` alone, validated by `validate()` from `src/mcp/jsonSchemaSubset.ts`; text `{text, meta?}` for a typed tool, the legacy body for an untyped one), throwing `PLUGIN_REPLY_INVALID` (HTTP-500-coded) on any other. Rules in docs/plugins/tools.md → Typed plugin tools. The handler also re-checks the active manifest's audience. `toolsFor()` takes no caller argument: it returns every enabled plugin's tools with their `audience`; the manifest `mcp.scope` field is accepted for compatibility with shipped manifests but dropped at load. The caller's identity/project still rides each forwarded call's `caller` payload.

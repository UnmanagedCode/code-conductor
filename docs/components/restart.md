# Components: routes, restart and resume, git and services

The REST shell, the restart and resume contract, worktree and git paths, model catalogs, installers and server-side caches.

## `src/routes.ts`

## `src/restartSupervisor.ts`

the restart contract between a supervisor process and the server; `docker/supervise.mjs` is its thin entry (`process.title = 'cc-supervisor'`), `exec`ed by `docker/entrypoint.sh` so the container's tree is init → supervisor → `conductor.sh` → server.
- **Env key** `CC_RESTART_SUPERVISOR` (`RESTART_SUPERVISOR_ENV`) = the supervisor's pid, set on every server it launches. `takeRestartSupervisor()`, called once in `start()` before `acquireRootLock`, reads and deletes it; the server counts as supervised only when the value equals `process.ppid` (a mismatch warns with both pids and falls back to self-respawn).
- **Exit codes** `SUPERVISED_RESTART_EXIT` (relaunch) and `SUPERVISED_SHUTDOWN_EXIT` (park), disjoint from each other, from `EXIT_CODES` (`src/headless/result.ts`), `ROOT_LOCK_HELD_EXIT` and 128+n; the values are in the module.
- **`superviseServer`** spawns the command (inherited stdio, its own process group via `spawnOptions('daemon')`, same argv/cwd/env plus the key). `SUPERVISED_RESTART_EXIT` with no stop signal received ⇒ log `relaunching` and spawn again. `SUPERVISED_SHUTDOWN_EXIT` with no stop signal received ⇒ log `parked`, drop the server handle and hold the event loop open (`keepAlive`, injectable; signal listeners alone do not), neither exiting nor relaunching; a forwarded signal while parked releases the keep-alive and `exit(0)`, signalling nothing — so `docker stop` ends a parked container cleanly, `make restart` brings cc back, and a host reboot with a parked (running) container restarts it into a clean boot. Any other exit ⇒ `exit(code)`; death by signal ⇒ `exit(128+n)`; a spawn that throws ⇒ `exit(1)`. SIGTERM/SIGINT/SIGHUP/SIGQUIT are forwarded to the server pid (not SIGUSR1, node's inspector signal) and mark the supervisor stopping. No restart counter or backoff: only a booted, listening server can exit `SUPERVISED_RESTART_EXIT`, so it cannot spin; boot failures (1, 7) end the container and docker's restart policy applies. Log lines are prefixed `cc-supervisor:`.
- What survives a supervised restart: the supervisor pid, init, the entrypoint's detached services, and the detached plugin backends (reparented to init, adopted by the replacement). What does not re-run: the entrypoint's pre-flight guards, services and deps check (the deps sync happens in-process in `relaunchPrep`).

## `src/restart.ts`

the Restart behind `POST /api/admin/restart` and the Shut down behind `POST /api/admin/shutdown`. `runRestart({action: 'restart'|'shutdown', deliver, ctx, flags, prep, onChunk, onCommit, spawnAndExit, exitForShutdown, rootLock, supervised, recorder})`. Every restart and every shutdown drains to the resume manifest; there is no other teardown path.
- **Restart order.** `drift = flags.syncDeps ? prep.drift() : null`. In sync: `prep.stageWeb` first, before anything is touched. With instances: `recorder.pause()`, `drainToIdle`, then on drift `prep.installDeps` + `prep.stageWeb` — a failure there runs `abortDrain`, then `recorder.resume()`, and rethrows, with networking still up — then `onCommit`, `teardownNetworking` (terminate WS clients, close the WSS and the http server), `finishDrain(…, {deliver})` (manifest, running record removed, `shutdownForResumeSync`), `spawnAndExit`. Without instances: install + stage on drift, `onCommit`, `teardownNetworking`, `spawnAndExit`.
- **Shutdown order.** No preparation. `recorder.pause()`, `drainToIdle`, `onCommit`, `teardownNetworking`, `finishDrain(…, {deliver: 'gated'})`, then `exitForShutdown({log, rootLock, supervised})` — `exitAfterShutdown` by default: `rootLock.releaseSync()`, then after the same ~50 ms floor `exit(supervised ? SUPERVISED_SHUTDOWN_EXIT : 0)`. Never a spawn.
- **`deliver`** (restart only; default `gated`): `auto` has the next boot prompt each busy session at once, `gated` holds its notice for the resume banner. The route sets `auto` only for `{autoContinue:true}`.
- **The recorder pause** keeps the closing CLIs' status events from writing the running record back after `finishDrain` removed it.
- **What holds about the install.** `node_modules` changes only once every turn has ended: the drain's soft interrupt lands at a block edge, so a session's in-flight tool call (an `npm test`, a Playwright run) still finishes during the drain, and installing then would hand it a broken tree whose red result survives into its resumed context. Cost: an install or build failure is found after turns were wound down (`abortDrain` hands them back). With dependencies in sync, every failure is found before any session is touched. **Not covered:** `run_in_background` shells and processes outside cc that use the tree.
- **Failure** throws; nothing after the failed step runs and nothing is spawned or exited. `onCommit` marks the point after which the step can no longer be refused; the route answers its client there. `onChunk(phase, text)` streams `deps` (the drift found), `npm`, `build` and `drain`.
- **Normal sessions** are carried over by every restart and shutdown, never archived by one. A normal segment orphaned by a crash (its CLI died with cc and no restore resumed it) stays listed until archived by hand.
- `spawnReplacementAndExit({log, rootLock, supervised})` — with `supervised` it returns `exitToSupervisor` (below) before any offer, spawn or wait. Otherwise it spawns a detached child with the same argv/env/cwd and exits; the child's listen-with-retry handles `EADDRINUSE`. If the spawn throws it does not exit. With a root lock it hands the lock over first and exits only once the child adopted it (or `CC_ROOT_LOCK_HANDOVER_WAIT_MS` ran out), never before ~50 ms — [The projects-root lock](headless.md#the-projects-root-lock) → Restart handover.
- `exitToSupervisor({log, rootLock, exit})` — the supervised relaunch: `rootLock.releaseSync()`, then `exit(SUPERVISED_RESTART_EXIT)` after the same ~50 ms floor. `runRestart({…, supervised})` passes `supervised` on to `spawnAndExit`; `RelaunchOptions.supervised` feeds it from `server.ts`.
- **`sweepPendingArchive`** (`src/pendingArchive.ts`, called at boot) archives every session a `<store>/pending-archive.json` lists (jsonl kept, `subagents/` dir removed, segment retired) and unlinks the file. cc writes no such file; a build whose restart archives normal sessions writes one on its restart, and the boot after it consumes it. It stays in `src/` rather than a migration because it needs `retireSegments`.

## `src/gitLive.ts`

shared git-subprocess helpers for the paths that pull/fetch a managed checkout: `runGitLive(args, cwd, {timeoutMs, onChunk})` (streamed spawn, detached process-group timeout/kill, resolves `{code,stdout,stderr}`, never rejects), `fetchOriginBounded(cwd)` (bounded best-effort `git fetch` for update-detection, `NO_PROMPT_GIT_ENV` so private-repo auth fails fast). ## `src/depsDrift.ts`

`dependencyDrift(repoRoot)` → `null` or `{reason}` naming the first offender. Reads `<repoRoot>/package.json` and the packages on disk; never `package-lock.json` nor npm's hidden lockfile. No `package.json` ⇒ `null`; an unparseable one ⇒ `package.json is unreadable: …`. Offenders, first one wins, in this order:
- **Roots** — `dependencies` + `optionalDependencies`, plus `devDependencies` when a dev root is on disk that the prod roots' graph does not reach (an `--omit=dev` install is in sync, a full install sees a devDep change; a dev root a prod package also needs — e.g. `@types/react`, an optional peer of `radix-ui` — stays on disk under `--omit=dev`, so it does not count). Checked in declaration order: `node_modules/<name>/package.json` must exist (`node_modules/<name> missing`; a directory without one counts as missing; an absent optional root is fine) and its `version` must satisfy the range (`node_modules/<name> <v> does not satisfy <range>`).
- **Range grammar** — `X.Y.Z`, `^X.Y.Z`, `~X.Y.Z`, `>=X.Y.Z`, caret per semver for `0.x`/`0.0.x`; an installed prerelease satisfies none of them. Any other range is drift (`package.json range for <name> ("<r>") is not supported`); `tests/deps-drift.test.mjs` pins that cc's own `package.json` uses only this grammar (`isSupportedRange`). No semver package: the check must run when `node_modules` is broken.
- **Transitive** — breadth-first from the roots on disk: every `dependencies` name of every reached package must resolve by Node's lookup (`<pkg>/node_modules/<n>`, then each ancestor `node_modules` up to the root's), else `<n> missing, required by <pkg dir>`. A missing `optionalDependencies` entry is fine (other platforms' bindings); present optional and `peerDependencies` count toward reachability only. Visited set keyed by package dir (cycles terminate).
- **Extraneous** — a top-level `node_modules/<name>` or `node_modules/@scope/<name>` with a `package.json`, not a symlink, not a dot-entry (`.bin`, `.package-lock.json`, `.vite`, `.cache`), and not reached ⇒ `node_modules/<name> is extraneous`, in sorted order. This is how a dependency removed from `package.json` is detected; the `npm install` that follows prunes it.
- **Not detected:** transitive versions (existence only — a `package.json` edit cannot produce an out-of-range transitive, since npm resolves those during the install a root change forces; only an on-disk edit or a corrupt partial install can); extraneous packages nested below the top level; a missing peer (npm ≥7 installs peers, so only a deletion produces it); a newer in-range release on the registry (ranges float by design); a package with corrupt contents but an intact `package.json`; non-npm layouts (pnpm).
- **Why not `npm ls`:** it reports every package extraneous through a symlinked `node_modules` (a worktree's, an isolated preview's), and it is a subprocess. **Why not an install-time stamp of `package.json`:** it cannot see a package deleted from disk.
- Leaf module (`node:fs`, `node:path`), sync. Callers: `src/relaunchPrep.ts`, the boot build's failure hint, `docker/deps-complete.mjs`.
- **`package-lock.json` is untracked** (`.gitignore`); the lock npm writes stays local.

## `src/relaunchPrep.ts`

the preparation every relaunch runs in the OLD process, shared by the restart route and self-update. `ensureDependencies({repoRoot, npmCmd, onChunk})`: no drift (`dependencyDrift`: `node_modules` satisfies `package.json`) ⇒ `{ran:false}`; drift in a `node_modules` that `lstat`s as a symlink ⇒ `409 DEPS_LINKED` without running anything (a worktree's or isolated preview's shared tree); otherwise `npmCmd` (`CC_NPM_INSTALL_CMD`, default `npm install`) through `runGroupedCommand({shell})` with a 300 s timeout, then a re-check — a non-zero exit, or drift that survives exit 0, throws with `{ran, exitCode, tail}`. `withMaintenanceLock(kind, fn)`: one module-level slot for `'restart'`, `'update'` and `'claude-update'` (`src/claudeUpdate.ts`); a second caller gets `409 MAINTENANCE_IN_PROGRESS` and its `fn` never runs. `relaunchPrep` is the real `RelaunchPrep` (`drift`, `installDeps`, `stageWeb` → `stageWebBuild`) that `runRestart` drives; tests inject stubs.

## `src/selfUpdate.ts`

conductor self-update service (Settings → About), the app's own version of the Plugin Library update path. `getSelfUpdateStatus({repoRoot})` → `{version, upstream, behind, canCheck, updateAvailable}` (version from `package.json`; bounded `fetchOriginBounded` then `getProjectUpstreamStatus` on the repo root — `canCheck:false` when detached/no-upstream). `applySelfUpdate({repoRoot, npmCmd, onChunk, onValidated})` runs `git pull --ff-only` (streamed `runGitLive`, wrapped in `pullPastGeneratedConventions` with the project `findSelfProject(repoRoot)` names — `null`, and so untouched, when the checkout is not registered), then `ensureDependencies` (`src/relaunchPrep.ts`) — so drift that predates the pull is repaired too — and returns `{ok, version, depsChanged, npm, restartRequired}`; a failed or unverified install and a `DEPS_LINKED` refusal all become `npm.ok:false` (`ran` false for the refusal) with `restartRequired:false`. The whole apply runs under `withMaintenanceLock('update')`, so it never overlaps a restart; contention throws 409 before `onValidated`. It does not build the web UI: the restart that follows stages it. **It never restarts** — the client (Settings → About, `AboutSection.tsx` → `performRestart({autoContinue:true})` in `web/src/features/sidebar/restart.ts`) hands off to the power menu's restart after a successful apply, so a self-update reuses `restart.ts`/`resumeRestart.ts` wholesale rather than reimplementing drain/respawn/health-poll. Repo root resolves from `import.meta.url` (one level up from `src/`), overridable per-call and via `SELF_UPDATE_REPO_ROOT` (test seam); `npmCmd` defaults to `ensureDependencies`'s (`CC_NPM_INSTALL_CMD`). **First update onto this preparation:** it relaunches through the previous process's restart code, which has no preparation; that previous self-update installed on a manifest change and the new process builds at boot, so it still comes up.

## `src/claudeUpdate.ts`

Settings → About's Claude CLI update. `applyClaudeUpdate({platform, timeoutMs, onChunk, onValidated})` (`platform` required, per the holder rule) runs `<resolveClaudeBin> update` with `cliEnvBase` (the binary and env a worker spawn uses, as `src/claudeAuthStatus.ts`) through `runGroupedCommand` (`stdin: 'ignore'`, `CLAUDE_UPDATE_TIMEOUT_MS`, group-killed on timeout), all under `withMaintenanceLock('claude-update')` — contention throws 409 before `onValidated`. A spawn error or non-zero exit throws 502, a timeout 504, each with the output `tail`; success re-probes with `probeClaudeBin` and returns `{ok:true, version}`. No restart: a running session keeps its CLI process, and every spawn resolves the binary afresh. Routes: `GET`/`POST /api/settings/claude-update` in `src/routes/admin.ts`.

## `src/ndjsonAction.ts`

`streamNdjsonAction(res, next, run)`: the one NDJSON streaming contract for long actions — the plugin library's install/update (`src/plugins/api.ts`), `POST /api/settings/self-update` and `POST /api/settings/claude-update`. Before `run` calls `onValidated`, a rejection goes to `next` (the trailing error middleware, keeping its status code); `onValidated` commits a 200 `application/x-ndjson` response, after which `onChunk(phase, text)` writes `{type:'chunk',phase,text}` and the outcome is one terminal `{type:'result',ok:true,result}` or `{type:'result',ok:false,error,tail}` line (`error` from `errMessage`, `src/httpError.ts` — `'internal error'` for a thrown value with no string `message`, as the trailing error middleware reads it).

## `src/resumeManifest.ts`

the two files a boot restores from, both under `orchStoreRoot()`, both written tmp + `renameSync` and synchronously. **`pending-resume.json`** (the manifest; a clean stop): `writeResumeManifest(entries, {deliver = 'auto', clis = []})` (no-op when both lists are empty), `readResumeManifest()` → `{present, deliver, instances, clis}` (an absent `deliver` reads `auto`; a corrupt file is removed and reads as absent), `clearResumeManifest()`. **`running-sessions.json`** (the running record; cc is running, or stopped without a drain): `writeRunningRecord({instances, clis})` (an empty one too), `readRunningRecord()` → `{instances, clis}` or null (malformed `clis` rows dropped), `clearRunningRecord()`. **`takeRestoreSource()`** reads both and unlinks both (at-most-once): manifest present ⇒ `{kind:'restart', deliver: <its deliver>, entries}`; else record present ⇒ `{kind:'unclean', deliver:'gated', entries}`; else null. Each entry carries the spawn descriptor (`project/sessionId/cwd/mode/effort/thinking/model/worktreeName/persistent/conducted/debug/title/firstPrompt/autoApprovePlan/group/wasBusy`, `workers` for conductors) plus the **pending overage auto-resume** state (`overageResumeAt` = fire deadline epoch secs, `overageStopped` = stop-resume intent, `overageResetsAt` = window reset epoch secs; all falsy when no resume is pending, `overageQueue` = messages queued during the wait window) — schemas in protocol/rest-instances.md.

## `src/resumeRestart.ts`

carrying live sessions across a stop: the resume facts, the drain, the restore, and the notice texts.
**The facts**: `captureResumeFacts(instances)` → `{subtreeOf, busy}` and `buildResumeEntries(instances, facts)` → the entries; `finishDrain` writes them as the manifest and the running recorder (`src/runningRecord.ts`) as the record, so both name the same sessions with the same fields.
`drainToIdle()` (old process, driven by `runRestart`): **soft-interrupt** every mid-turn instance (`Instance.interrupt()` — the armed SOFT tier, landing at the model's next block edge), then `waitAllIdle` with `RESUME_DRAIN_GRACE_MS`=60 s: on timeout it logs a warning, **escalates** every live instance not already `turnForceAborted` to `interrupt({force:true})`, and re-arms *the grace window*.
No status re-check here — both tiers are contracted to no-op off-turn (protocol/subprocess.md → Two-tier interrupt), pinned for the forced tier by `tests/instances.test.mjs` → *forced interrupt is a no-op when not in a turn*.
The soft arms themselves are bounded too — the drain passes `{ deadlineMs: softInterruptDeadlineMs() }`, so an arm that can never reach a block boundary (a wedged tool; a gateway framing the whole turn as one never-closed block) escalates on its own deadline instead of holding the restart open forever.
A stop, not a wind-down steer — a steer is silently dropped by a model declaring `midTurnSteering:false`, and with an unbounded wait that hung the restart forever; the trade is that the human loses the in-transcript `user_echo` explaining the stop, and the boot-side notice is its sole owner.
Right after the facts snapshot and before the soft interrupts the drain calls `instances.suspendWakes()`: no wake is delivered until `resumeWakes()`, so a worker the drain winds down does not wake its owner into a turn `finishDrain` would only kill.
Step (1) snapshots `conductedSubtreeOf(id)` for every live non-`worker` entry — a BFS over `callerInstanceId`, one `{project, sessionId, worktreeName, parentSessionId}` row per descendant, `parentSessionId` being the spawner's CURRENT sessionId — and a non-empty list becomes the entry's `workers`.
`busy` = mid-turn ∪ `isIdleCaller`.
`drainToIdle` resolves the facts once every turn has ended; `runRestart` then installs if needed, tears down networking, and calls `finishDrain(ctx, facts, {deliver})`: `writeResumeManifest(entries, {deliver, clis})` (normal sessions carried over, not archived; `clis` the recorder's rows, `recorder.clis()`, passed by `runRestart`), then `shutdownForResumeSync`, then `clearRunningRecord()` — always, an empty entry list included, and in that order, so a crash anywhere before the clear (during the CLI stop included) leaves both files: the boot restores from the manifest, and the orphan reap, which reads only the record, still sees every CLI it listed.
`buildResumeEntries` widens `wasBusy` for every non-`worker` entry: `wasBusy` = in `busy`, or the entry's own session or any session in its `subtreeOf` rows (resolved via `liveForSession`) `holdsBackgroundWork` — `backgroundJobs` non-empty (background Bash runs and Monitors; the CLI's `task_started` and `background_tasks_changed` frames report a Monitor as `task_type:'local_bash'`) or `activeAgentTaskCount > 0` (background subagents).
That work lives only in the CLI process, and `shutdownForResumeSync` kills it.
Those sessionIds (the root's own included) become the entry's `backgroundWorkLost`, present only when non-empty; a `worker` entry never gets one and is never widened.
`abortDrain` reads `busy` only — an aborted restart kills no background work.
`drainToManifest({deliver = 'auto'})` is the two composed, without networking or a relaunch, for tests.
`abortDrain(ctx, state)` — the restart was refused after the drain: `resumeWakes()`, then `RESTART_ABORTED_TEXT` (lead `RESTART_ABORTED_LEAD`, `shared/injectedTurns.ts`) is prompted to every live non-worker in `busy` — the set a restore would prompt; workers are left to their conductor — carrying the waits whose wakes were dropped while suspended.
It writes no manifest and spawns nothing.
`restoreFromResumeManifest({source, pending})` (new process, on boot; `source` from `takeRestoreSource`, taken itself when omitted): three-group split (conductor / conducted worker / other), staggered `--resume` respawns (`RESUME_STAGGER_MS`=1.5 s), per-instance continue notice, `noticeFor(entry, kind)`: for kind `restart` an entry with `workers` (any group) gets `buildWorkersResumeText(sessionId, workers)` — every subtree row with "spawned by you" or its spawner's sessionId; a row with no `parentSessionId` reads as the root's — and every other entry `RESUME_TEXT`; for kind `unclean` `buildWorkersUncleanResumeText` / `UNCLEAN_RESUME_TEXT` (trunk `UNCLEAN_STOP_NOTICE_TRUNK`, `shared/injectedTurns.ts`: the turn was cut off mid-flight, so the last tool call's effect needs checking, and the workers were killed mid-turn too); either kind appends `\n\n` + `backgroundWorkLostNote(sessionId, backgroundWorkLost, kind)` when that list is non-empty (the root reads as "you", others by sessionId; `restart` says the restart killed it, `unclean` the unexpected stop).
The notice gate is `wasBusy !== false && !honourMark`; a source delivering `auto` prompts the notice, a `gated` one `pending.add`s it (`{sessionId, kind, text, workers, at}`, `src/pendingContinue.ts`) and prompts nothing.
Every top-level entry's sessionId is in `pending.restoring` from the call's synchronous start until the loop has settled that entry (notified, skipped or failed); a `finally` empties it when the restore ends.
`wait` (default: sleep) is the stagger's pause, a test seam.
Before `create()`, the restore adopts `liveForSession(sessionId)` when a user's resume already attached the session, brings it to the entry's `playbookEnforcement` (via `normalizePlaybookEnforcement`, as `create()` reads it), `autoApprovePlan` and `debug` (`enableDebug()` when the entry's `debug` is set; there is no runtime disable) as a fresh restore would set them, and notifies that instance; a browser resume still in flight is coalesced by `create()`'s synchronous `_resuming` prefix (no await separates the check from it), and a later browser POST gets 409.
The restore is the only sender of the notice and runs once per boot, so it arrives (or is stored) once.
Owns the notice texts (`RESUME_TEXT`, `UNCLEAN_RESUME_TEXT`, `buildWorkersResumeText`, `buildWorkersUncleanResumeText`, `backgroundWorkLostNote`).
**Overage auto-resume survival**: a session with a pending overage resume re-arms the wall-clock sweep on boot — *after* it's live + idle (so `spawn()`'s flag-clear can't wipe it) via `instances._armRestoredAutoResume(inst, overageResumeAt*1000)` (fire-and-forget, like the resume notification; `OverageResumeController.armRestored` bypasses `arm()`'s past-deadline skip).
Queued messages are restored onto `inst._overageQueue` **before** the re-arm so `armRestored`'s status emit carries the restored `queuedCount`, and they flush with the resume.
A deadline that elapsed while the orchestrator was down fires on the first post-boot sweep tick (`AUTO_RESUME_TEXT`); the continue notice is skipped for these sessions to avoid a double-prompt.
The running record carries the same overage fields, so an unclean stop restores the pending resume too, to the last debounce window.

## `src/runningRecord.ts`

the running record's writer and the boot-time orphan-CLI reap.
- **`createRunningRecorder({instances, platform, log, debounceMs = RUNNING_RECORD_DEBOUNCE_MS, write, startRetryMs = START_TIME_RETRY_MS, setTimer})`** → `{start, pause, resume, stop, clis}`. Built (not started) by `createServer`; started by `startResumeLifecycle`. `start()` subscribes to the manager's `status`, `list_changed` and `subscription_changed` events (the last moves `isIdleCaller`) and writes at once; each event schedules a trailing-debounced flush, which builds `{instances: buildResumeEntries(captureResumeFacts()), clis}` and writes only when its JSON differs from the last write. `pause()` cancels the timer and writes nothing (the restart and shutdown drains); `resume()` writes at once (an aborted restart); `stop()` unsubscribes (server close); `clis()` returns the current `clis` rows from the start times already read (no new read) for the manifest. A crash loses at most the last debounce window. `write` and `setTimer` (the retry scheduler) are test seams.
- **`clis` rows** (`cliRows`): one `{sessionId, pid, start, group}` per instance with a live `proc` and a numeric `pid` — top-level, conducted and pristine alike, regardless of the entry filters. A FUSE-wrapped instance (`_fuse`) gets none: its worker and daemon pids are in the FUSE run record, which `sweepFuseLeftovers` verifies and kills. `group` is `!!platform.spawnOptions('child').detached`. `start` is `Platform.processStartTime(pid)`, read once per CLI process (cached by the `proc` handle, so a reused pid never inherits an earlier start) and `null` until a read answers. A read that answers null is not cached: it is retried `START_TIME_RETRY_MS` later, doubling, until `START_TIME_ATTEMPTS` reads in all (`startRetryMs` is a test seam), after which the row stays null — never a guessed value. A read counts only while that `proc` is still the instance's live CLI, checked before and after it: cc holds the child, so its pid cannot be reused until the exit that clears `proc`.
- **`reapOrphanedClis({platform, log, termGraceMs = ORPHAN_CLI_TERM_GRACE_MS})`** → `{terminated, unverifiable, reused}`, called by `prepareResumeBoot`. Reads the `clis` of the running record and of the resume manifest, without consuming either, and reaps their union once per pid: a pid's rows with a known start (one per distinct start) win over its null-start row, since both files describe one boot's live set; two different known starts are both kept, and the start check sorts them out. Every row's start time is read concurrently, and each row is decided and signalled in its own continuation, right after its own read answered — so no identity check is older than its signal by more than that one read: `start` null, or `processStartTime(pid)` null while `pidIsAlive(pid)` ⇒ not signalled, a warning names the session and pid (restore still runs); a different start time ⇒ a reused pid, left alone and logged; equal ⇒ `group ? killGroup : killProcess` with SIGTERM (on Windows both are `taskkill /T /F`), then `pidIsAlive` polled every 50 ms up to `termGraceMs`, and every survivor is re-read concurrently and gets SIGKILL through the same helper right after its own re-read matches. ESRCH is "already gone". Never throws. Its time is bounded by about two start-time reads plus `termGraceMs`: a read that runs a helper process (`ps`, PowerShell) is capped at `START_TIME_TIMEOUT_MS` (`src/platform/platform.ts`), a `/proc` read is immediate, and the survivor poll only runs when something was signalled.
- **Why**: a CLI is spawned `spawnOptions('child')` — not tied to cc's lifetime — so after a crash or a kill of cc alone it lives until its next stdout write fails, and one blocked in a long tool call can still be writing its transcript when the next boot resumes the session (or its conductor resumes a worker). A clean stop is covered too: on posix the sync stop kills no survivor (see "Stopping the CLI without `softSigterm`"), so a CLI that ignores stdin EOF past the grace outlives a Restart or Shut down after `finishDrain` has removed the record — and the manifest carries the same `clis` rows (`recorder.clis()`, written before the stop), which the reap reads. When the stop died before the record's removal, both files are present and name the same rows, reaped once. A CLI that did exit reads as gone (ESRCH) or as a reused pid (a different start time).

## `src/pendingContinue.ts`

the resume banner's held notices, `<store>/pending-continue.json` = `{notices: [{sessionId, kind, text, workers, at}]}`. `createPendingContinue({onChange, log})` → `{add, drop, take, list}`: each a synchronous read-modify-write with an atomic write (the file is removed when empty; a corrupt file is warned, removed and read as empty), `onChange` after every operation that changed the set — `createServer` wires it to the `{t:'resume_notices'}` hint to every WS client. `add` replaces the session's notice; `drop(sessionId)` → boolean; `take(keep?)` removes and returns every notice `keep` does not keep (all of them without it) in one write, so two concurrent Continues cannot both send. `restoring` is the set of sessions the running boot restore has not settled (filled and drained by `restoreFromResumeManifest`). `continuePendingNotices({pending, instances})` → `{sent, dropped, kept}`: `take` every notice whose session is not in `restoring` — those are kept, and the banner keeps listing them — then `prompt(text)` to each taken one whose session is live (failures logged), dropping the notice of one not live. So a Continue clicked while the restore is still staggering never drops a notice whose session is about to come up; once the restore has settled a session (or never had it), "not live" means stopped. `readPendingNotices()` reads without changing anything (`src/sessionCleanup.ts`). The file is independent of the manifest and the record: a notice outlives any number of further restarts or crashes — its session was live and idle, so the next manifest or record lists it `wasBusy:false` and the next boot respawns it silently — until Continue, Dismiss or the session's own turn removes it.

## `src/resumeBoot.ts`

the boot half. The boot order (`startHolding`, `server.ts`): FUSE sweep → orphan-CLI reap → session cleanup → `createServer` → listen → `setServerPort` → resume lifecycle. `prepareResumeBoot({platform, log})` runs `reapOrphanedClis` right after `sweepFuseLeftovers` and before `cleanupSessionsWithoutTranscripts` and `createServer`, in every mode, headless included — no instance exists yet, so nothing is respawned and no conductor can resume a worker while an old CLI may still run; the await is bounded by `reapOrphanedClis`'s own bound — about two `START_TIME_TIMEOUT_MS` reads plus `ORPHAN_CLI_TERM_GRACE_MS`, the grace only when something was signalled. `startResumeLifecycle({instances, recorder, pending, log, staggerMs})` → `{restored, dispose}` runs after `setServerPort` with no await in between, **skipped in headless mode** (a headless run neither consumes nor kills the interactive server's sessions; both files wait for the next interactive boot): `takeRestoreSource()`, `recorder.start()`, `turn_started` → `pending.drop(sessionId)` (any turn — composer, MCP, wake — makes the session's notice stale), then the fire-and-forget `restoreFromResumeManifest({source, pending})`. `dispose()` unwires the drop and stops the recorder; the record stays.

## `src/waitFor.ts`

`waitFor({initial, subscribe, timeoutMs, onTimeout})`: the one promise shape behind every LISTENER-driven wait. `initial()` is the already-satisfied fast path, checked before any listener is attached (returns `{value}` or `null`); `subscribe(settle, fail)` attaches whatever listeners it likes and returns an opaque teardown that detaches all of them — which is why the N-listener case needs no special support; `onTimeout()` picks the timeout's disposition by RETURN TYPE — an `Error` rejects, anything else resolves. The point is that the `clearTimeout` + teardown pair is written **once** and runs exactly once, on whichever of settle/fail/timeout fires first, instead of being hand-rolled on both paths at each call site. Adopter — the module's sole importer now: `waitForIdleOnce` + `waitAllIdle` (`resumeRestart.ts` — the per-instance and all-idle drains, both **resolving** on timeout, with `'timeout'` / `{timedOut:true, stragglers}` respectively). Neither passes `fail`, and neither returns an `Error` from `onTimeout` (`resumeRestart.ts` — both resolve), so `waitFor`'s `fail` callback and its reject-on-timeout disposition have **no production caller** — the Error/reject path is currently exercised only by `tests/wait-for.test.mjs`. Deliberately **not** adopted by the two POLLING loops (`plugins/registry.ts` `waitSettled`, `plugins/supervisor.ts` `poll`): both re-enter a `setTimeout` over a synchronous accessor or an HTTP/TCP/regex probe, so there is no emitter and nothing to detach — the supervisor's `abort` is likewise a predicate polled at each tick, not a listener — the helper's entire value is nil for them, and unifying those two with each other would need a three-knob helper for two call sites.

## `src/worktrees.ts`

`mergeWorktreeIntoParent` records a landing via `recordWorktreeLanding` (`src/worktreeLandings.ts`: an in-memory map, `ok:true` path only; keyed `project + name`, valued with the worktree's `createdAt` so a same-name successor never matches, which also covers a worktree removed outside cc; `dropWorktreeStoreEntry` deletes one worktree's entry and `removeProjectStoreDir` a whole project's — the only two places cc deletes worktree records; never persisted, so a restart forgets it; `clearWorktreeLandings` is the test reset) and `worktreeWorkLanded(project, meta)` checks it (a recorded landing and `getWorktreeMergeStatus` ahead `0`; the MCP `delete_worktree` landing renewal nudge is its only caller — behaviour: [features/conduct.md](../features/conduct.md) → Conduct mode → Landing renewal nudge).
`createWorktree(project, {baseWorktree?, name?, lock?})` captures `{baseBranch, baseSha, branch}` from the **base's** HEAD — the project root, or another worktree of the project when `baseWorktree` names one (then `parentPath` is that worktree's checkout and `baseWorktree` is recorded; chains nest to **any depth** — `baseWorktree` has exactly one write site, this meta literal, written at creation and naming a record that already exists, so creation order is a topological order, the base graph is a DAG by construction, and no cycle check exists or is needed; a re-parenting API would end that) — resolving that base through the store records (`listWorktrees`), never by assembling a path, since `getProject` validates only the name charset and directory existence.
`name` is slugified by `slugifyWorktreeName` into the branch + dir name in place of `shortId()`, with a collision on the branch ref `refs/heads/code-conductor/<slug>` refused 409 — one check covering both collision cases, since dir name and branch derive from the same slug and a registered worktree always still holds its branch; it buys a clean 409 rather than `git worktree add`'s 500, not cleanup.
Then writes `worktree.json` into the central store and `git worktree add` off the captured SHA; after the worktree is fully set up it runs `runWorktreeHook(system, 'create', meta, {cwd: worktreePath})` — the `post-worktree-create.sh` hook resolved in priority order from the **in-tree parent checkout** (`<meta.parentPath>/.code-conductor/…`, need not be committed) else the **central store** (`projectStoreDir(meta.parentProject)/post-worktree-create.sh`), run with `cwd` in the new worktree (non-fatal, always resolves, result attached to return as `postWorktreeCreate` with `source: 'in-tree' | 'store'`).
`syncWorktree` picks no-op / FF / `git rebase --rebase-merges` / `commit-required` / `rebase-conflict`, and prompts nobody — the two blocked results carry `buildRebasePrompt(meta, blocker)`'s rendered text for the caller to dispatch (the flag is in both of its briefs; all three sites must carry it or the conflict path flattens the merge commits the automated path preserved).
**`requireWorktree(project, name, what?)`** is every addressing site's lookup-or-404: one `listWorktrees` read yields both the exact-name hit and, on a miss, `unknownWorktreeMessage`'s list of the project's worktrees by exact name (`list_sessions` builds the same message from its own targets).
**`listWorktrees` is STORE-DERIVED**, enumerating `<store>/projects/<name>/worktrees/` (`worktreesStoreRoot`), with git used only as a FILTER to prune a worktree removed out-of-band.
A registration is cc's own record, not a git fact, so it must list whether or not the system answers — gating the whole enumeration on `isGitRepo` made a degraded row show NO worktrees, which then told the user at the delete confirmation that it would unregister zero of them while one was registered.
When git cannot answer (a system refusal, and only that — any other fault still throws) no filter is applied.
**ONE SPELLING PER WORKTREE**: the store key, the `worktreeName` and the directory basename are one string — `slugifyWorktreeName(name)` or `shortId()` — so there is no alias to resolve and no name to parse out of a path.
`listWorktrees`' `path.basename` live-prune is correct *because* of that identity, and `worktreePathFor` is the one place a checkout's location is decided: `<projectsRoot>/.worktrees/<project>/<key>` for a local project wherever its tree lives (cc owns that area; the user's parent directory is not cc's to scatter checkouts in), and for one on a system that system's `worktreesDir` else `<dirname(project path)>/.worktrees/<project>/<key>` — same shape, only the root differs, and no per-kind exception.
Everything downstream of a resolution passes `meta.worktreeName`: `createWorktree` persists `base.worktreeName` as `baseWorktree` (the foreign key `listDependentWorktrees` matches on), `removeWorktree` `fs.rm`s `worktreeStoreDir(project, meta.worktreeName)`, and the two delete entry points (`src/routes/worktrees.ts` DELETE, `mcp/handlers.ts` `deleteWorktree`) resolve once at the top before `instances.idsForWorktree` — an exact in-memory compare that would otherwise report no attached instances and skip the live-instance guard.
`listDependentWorktrees` walks the **whole subtree, deepest-first** (downward-only over one `listWorktrees` load, `seen`-guarded like `agentTreeBackends`; level order, never `createdAt`) — transitive for the MESSAGE, not for the GATE: a subtree is empty exactly when the direct-child set is, so no operation is newly permitted or refused, and what the walk buys is a refusal that names the real blocker on the first call instead of a child whose own delete then refuses.
It + `dependentsRefusal` back the `WORKTREE_HAS_DEPENDENTS` soft refusal minted once here and passed through un-reworded by both surfaces (unlike `WORKTREE_BEHIND`, which each surface re-words); it gates `syncWorktree` (before any status computation), `mergeWorktreeIntoParent` (gate 1, ahead of `WORKTREE_BEHIND`), and `removeWorktree` (ahead of the dirty check, so a refused delete has touched neither dir, branch, nor store entry).
**The user's lock** (`WorktreeMeta.locked`, absent = unlocked) is cleared, and set on an existing worktree, by `setWorktreeLock` alone, imported by `src/routes/worktrees.ts` alone (`PUT …/worktrees/:wt/lock`) — browser-only by construction, pinned by `tests/worktree-lock.test.mjs`.
Its one other writer is `createWorktree`'s `lock:true` (MCP `create_worktree`), which puts `locked: true` into the same single `worktree.json` write that registers the worktree — as the last key, so the record is byte-identical to the same one locked by hand — and takes no git lock (`git worktree remove --force` refuses a git-locked tree).
`worktreeLockedRefusal(meta, 'merging'|'deleting')` mints the one `WORKTREE_LOCKED` refusal for both audiences, like `dependentsRefusal`.
It is `mergeWorktreeIntoParent`'s **gate 0** — ahead of `resolveSystem` and the dependents gate, keyed on the source record only — and the first check in the MCP `deleteWorktree` handler, outside its `!force` block; `removeWorktree` stays lock-agnostic because it is also the human's REST delete.
Readers take it from `listWorktrees` / `getWorktree` / `requireWorktree`, never from `inst.worktree` (a snapshot taken at spawn).
`writeMeta` writes through `writeFileAtomic` (a torn `worktree.json` reads as `null`, which drops the worktree from every listing), and `updateMeta` is the read-modify-write of an existing record: re-read under `withLock` (`src/storeLock.ts`) on the record's path, 404 when the record is gone.
`setWorktreeLock` and `repairWorktreesAfterProjectMove`'s `parentPath` rewrite both go through it, so neither can write back a copy that predates the other's change.
The dependents delete gate is split across two layers, exactly like the dirty check: `removeWorktree` **throws** 409 with the same `reason` — which is what covers the REST/GUI delete path (`DELETE /api/projects/:name/worktrees/:wt`), the surface that would otherwise orphan children — while the MCP `deleteWorktree` handler pre-checks the same predicate to keep the soft `{ok:false, code, dependents}` channel.
`force` skips the dependents gate on both layers (it is the whole reason `removeAllWorktreesForProject`'s `{force:true}` cascade can still sweep a feature/task graph); it never skips the lock, which only the MCP handler checks.
**`removeWorktree`'s step order is load-bearing**: `git worktree remove --force`, then `dropWorktreeStoreEntry`, then the best-effort `git branch -d/-D`.
The store entry is dropped BEFORE the branch delete because `runGit` throws a system refusal when git could not be run or never answered (`local` included) — written last, that throw left cc's registration behind for a worktree git had already forgotten, and `listWorktrees` (which prunes by `git worktree list`) then disagreed with `registeredWorktreeNames` (which does not consult git), so `setProjectRemote` refused 409 `PROJECT_PLACEMENT_IN_USE` naming a worktree the listing did not show (measured), and the retry could not clear it either, since `getWorktree` prunes the same way and 404s.
The branch delete's refusal is re-raised ANNOTATED, not swallowed: `statusCode` / `code` / `systemRefusal` preserved, message asserting only what the code measured (`worktree '…' was removed, but its branch '…' may still exist`) — the branch clause is hedged because `GIT_TIMED_OUT` means the answer never arrived, so the far side may have deleted it — swallowing it would report a transport failure as a clean removal.
Git's own non-zero exit there stays unread, which is what best-effort means here.
The guarantee covers the GIT steps; its bound is stated once, at the `dropWorktreeStoreEntry` call site in `src/worktrees.ts`.
**Every guard here reads a FAILED check as UNKNOWN, never as passed** — `removeWorktree`'s dirty gate, the MCP `deleteWorktree` precheck (`WORKTREE_DIRTY_UNKNOWN`), merge's parent-status gate (`PARENT_STATUS_UNKNOWN`) and merge's step-5 gate on the worktree's own tree (`WORKTREE_STATUS_UNKNOWN`) all refuse rather than proceed, because `if (dirty.ok && lines.length)` let a check that never ran authorise `git worktree remove --force`, and let a merge silently not land the uncommitted work step 5 exists to protect.
The same rule holds on the READ surfaces — for a command that RAN and answered non-zero, which is the only way these degraded shapes are reached, since one that never ran or never answered throws a system refusal instead (`GIT_DID_NOT_RUN` 502 / `GIT_TIMED_OUT` 504): `project_status` reports `dirtyUnknown` rather than an empty `dirty` list; `getProjectCommits` reports `hasUncommitted: undefined` + `uncommittedUnknown` rather than `false`, and **throws** on a `git log` that did not answer — distinguished from a legitimately empty history by asking `hasUnbornHead` ONLY on that failure path, so the normal case pays nothing; `project_diff`'s summary reports `uncommitted: {unknown, reason}` rather than zeroed totals, matching what its own committed half already did by throwing; and a listing row runs both its git probes inside one try so a death BETWEEN them sets `systemUnreachable` instead of inventing `unbornHead: false`.
`force:true` is still the override of a KNOWN-dirty tree.
**`git merge` is NOT individually atomic**, contrary to the original design note: killed mid-merge, the orphaned command was observed completing the merge commit AFTER cc had reported failure — parent HEAD moved, `MERGE_HEAD` left set, worktree branch never fast-forwarded.
So `mergeWorktreeIntoParent` wraps its WHOLE body (not just the prelude) and flags `mayHaveCompleted` on any refusal raised after the merge was issued, and the state that leaves behind is reported as `PARENT_MID_MERGE` — `PARENT_DIRTY`'s "commit or stash" is the wrong repair for a half-finished merge.
`mergeWorktreeIntoParent` runs `git merge --no-ff --no-edit` with safety checks, then best-effort fast-forwards the worktree's own branch (`git merge --ff-only`, run from `meta.worktreePath` since that's where the branch is checked out) up to the new merge commit — always a valid FF since the worktree branch is one of the merge commit's parents — reporting the outcome as `worktreeFastForwarded` without affecting the overall `ok` result.
Also `getProjectCommits` (`git log` on HEAD, bounded by `COMMITS_DEFAULT_LIMIT`/`COMMITS_MAX_LIMIT`, `src/worktrees.ts`) — which reads the project's tree, or the worktree its optional `worktree` option names, resolving both through `resolveProjectCwd` and taking the `aheadOf` base-branch fallback from the `worktreeMeta` that resolution returns, so nothing has to reverse-scan the store for a record matching a path — the diff surface itself moved to `src/gitDiff.ts` (below).
**Worktree hooks: one runner, one table.**
`runWorktreeHook(system, event: 'create'|'merge', meta, {cwd, vars})` is the only hook runner; `WORKTREE_HOOKS` maps each event to its script name, kill-switch and timeout variable, with one default (`WORKTREE_HOOK_TIMEOUT_MS`).
Everything else is one path: the in-tree lookup at `<meta.parentPath>/.code-conductor/<script>` through the project's system, then the store lookup; the `STORE_HOOK_LOCAL_ONLY` refusal; the `['env', CC_*…, …vars, 'bash', script]` argv; `system.exec` with `HOOK_OUTPUT_CAP`; and the spawnError / truncation / `timedOut` / `descendantsMaySurvive` shaping.
**No chmod**: the script runs as `bash <script>`, and setting the exec bit on a tracked in-tree hook is a mode change git reports, which would dirty the target and refuse the next merge into it `PARENT_DIRTY`.
Exported so `tests/post-worktree-merge-hook.test.mjs` drives it through an injected `LocalSystem(platform)`.
**The merge call site:** `mergeWorktreeIntoParent` step 9, after the worktree branch's fast-forward, runs `runMergeHook(system, meta, head.sha, newSha)` and returns its report as `postWorktreeMerge` on success only.
`runMergeHook` runs inside the module's `createKeyedQueue()` keyed on `meta.parentProject` (so the script is resolved when its turn comes, and an in-tree copy is read from the target after the merge), with `cwd: meta.parentPath` and `vars` `CC_PRE_MERGE_SHA` (step 3's `head.sha`, the HEAD the gates measured) / `CC_POST_MERGE_SHA`.
It **catches everything**: a throw there would reach the function's `isSystemRefusal` catch and report `SYSTEM_UNREACHABLE` + `mayHaveCompleted` (or a 500) for a merge that certainly landed, so a caught throw becomes `{ran:false, error:true, output:<message>}`; `system.exec` itself never rejects, so what it catches is a stat, a store-path or a programming error.
Only merge hooks queue: create hooks run in distinct new worktrees, and queuing them would slow conductors creating several at once.
Hook env vars: `CC_WORKTREE_PATH`, `CC_PROJECT_NAME`, `CC_BRANCH`, `CC_BASE_BRANCH`, `CC_PARENT_PATH`, plus the merge hook's `CC_PRE_MERGE_SHA` / `CC_POST_MERGE_SHA`.
Kill-switches: `ORCH_DISABLE_POST_WORKTREE_HOOK=1` (create), `ORCH_DISABLE_POST_WORKTREE_MERGE_HOOK=1` (merge).
Timeouts: `ORCH_POST_WORKTREE_TIMEOUT_MS` / `ORCH_POST_WORKTREE_MERGE_TIMEOUT_MS`.
Output capped to a tail bound (`HOOK_OUTPUT_CAP`, `src/worktrees.ts`).
The hook runs BEFORE `Instance.spawn()` so it cannot interfere with the 5 s control-request timeout.

**`runGit(system, cwd, args)` is fenced at `GIT_OUTPUT_LIMIT_BYTES` (16 MB), and it fails past it rather than truncating.** Every caller parses git's output whole — porcelain, numstat, a unified diff — so a clipped parse would be handed back as the truth; and cc is a single process hosting every worker session, where an unbounded retention is a real memory failure (measured: 37 MB of output held a 37 MB string at 248 MB RSS, and a ~150 MB diff extrapolates to ~1 GB). Crossing the fence surfaces through the paths callers already have: a 500 from the diff surface, an empty history from `getProjectCommits`. Pinned by `tests/worktrees.test.mjs` → "runGit fences git output".

**Git's dubious-ownership refusal throws, never returns.** When the uid git runs as does not own the repository, git refuses every command in it with exit 128 — the exit a genuine non-repo gets. `runGit` throws **403 `GIT_DUBIOUS_OWNERSHIP`** (`systemRefusal: true`; exported constant `GIT_DUBIOUS_OWNERSHIP`, predicate `isGitOwnershipRefusal`) when `code === 128` AND stderr has a line matching `/^\s*git config --global --add safe\.directory (.+?)\s*$/m`. That hint command is printed verbatim in every git locale and every git version that has the check, so the match is locale-independent and `runGit` does not force `LC_ALL=C`; the exit gate keeps a hook that merely prints the text on a non-fatal exit from matching. The message names git's captured path (the work tree's toplevel — for a linked worktree, the worktree's own path; not necessarily `cwd`) and the `safe.directory` command to run as the owning user. Because it is a system refusal, every "could not measure" path handles it unchanged (`listWorktrees` lists unfiltered, `checkoutIsProtectable` refuses the delete, merge/sync return a refusal whose `reason` carries the fix); the listings split it off by code into `gitRefusal` rather than `systemUnreachable`, and `adoptProject` returns `TARGET_DUBIOUS_OWNERSHIP`. cc never sets `safe.directory`. Pinned by `tests/git-dubious-ownership.test.mjs`, which drives real git with git's own `GIT_TEST_ASSUME_DIFFERENT_OWNER=1` knob in both System implementations: under `gate:systems` it respawns the provider around each knob window, because the provider keeps the env it was spawned with.

## `src/gitDiff.ts`

## `src/appSettings.ts`

(policy: [docs/models.md](../models.md)) — read/write `<store>/settings.json` (cached, atomic writes).
`getTranscribeModel()` / `setTranscribeModel(name)`, `getTierBackend(tier)` / `setTierBackend(tier, {backend,model})` (tier→backend binding), `getEnabledTiers()` / `setTierEnabled(tier, enabled)`, `getDefaultSpawnTier()` / `setDefaultSpawnTier(tier)`, `defaultSpawnBinding()` (= `getTierBackend(getDefaultSpawnTier())`, the binding a model-less fresh spawn runs on when it names no row at all — shared by `resolveSpawnModel` and the `POST /api/instances` route, and reused internally by `resolveRoleBackend`'s dead-Claude revert); namespaced (`transcribe`, `models`) for future groups.
**The backend registry** lives in `models.backends: [{id,label,template,env}]`: `getBackends()` (managed rows are fully code-authoritative — id/label/template/env all from code; nothing on a managed row is stored) / `getBackend(id)` / `getSubstitutionBackends()` / `addBackend` / `updateBackend` / `removeBackend` (**never cascades** — throws 409 while a custom model still references it, and a second 409 while any *tracked* instance is still on it, via the `setLiveBackendsProvider(() => instances.liveBackendUsage())` seam wired in `server.ts` so this store never imports the instance registry).
**Custom models** live in `models.customModels: [{label,model,backend,contextWindow,midTurnSteering}]` (the `(backend, model)` pair is the identity AND the exact lookup key — the model id is never normalized, and one id may sit on several backends; `contextWindow` is required): `getCustomModels()` / `addCustomModel(…)` / `removeCustomModel(backend, model)` / `backendModels(backend)` (the backend's registered models — custom rows plus, for `ollama`, the curated presets — one `{model,label}` per id, a custom row overriding a preset) / `isKnownBackendModel(backend, model)` (membership in it) / `backendsForModel(model)` (every backend the id is bindable on, registry order) / `contextWindowForModel(backend, model)` (exact-pair match on a custom row; wrapped by `resolveContextWindowTokens({backend, model})`, the single place a session's capacity is resolved).
A tier binding is `{backend, model}`; `getTierBackend` returns a **valid** binding verbatim (no silent revert) and falls back to the tier's default Claude binding only for an invalid/dead one (unknown Claude version, or a removed model/backend).
There is **no** per-family active-version setting anymore — a tier stores a concrete version id directly.
**Roles** are a parallel bindable layer: `getRoleBinding`/`setRoleBinding`/`resolveRoleBackend` back built-in + user-custom roles (binding in `models.roleBackend`), with **name-only** custom roles in `models.customRoles:[name]` (a string list — no label; the name is the display) via `getCustomRoles`/`addCustomRole`/`removeCustomRole`.
A custom role starts on the `powerful` tier and is rebindable via `setRoleBinding`.
**Role NAME matching is case-insensitive** (a spawn caller may type `MyRole` for a role stored `myrole`): names are stored/displayed as typed but matched, deduped, and collision-checked by lowercase (`canonicalBuiltinRole`/`canonicalCustomRole` return the stored key for a case-insensitive lookup).
The custom-role name rule (`^[A-Za-z][A-Za-z0-9-]*$`) is deliberately distinct from the lowercase plugin-slug rule (`manifest.ts`) — a custom role name is a case-preserving user label, a plugin slug is a lowercase identifier.
**Plugin-owned roles are live-derived, never persisted**: a provider injected by `server.ts` (`setPluginRolesProvider(() => pluginHost.roles())`, `getPluginRoles()`) keeps this store free of a plugin-registry import, so disabling a plugin drops its roles automatically.
`getAllRoles()` merges the three (built-in/plugin carry `label`; custom entries are `{role}` name-only); `isResolvableRole()` is the dynamic case-insensitive guard `spawnInstance` uses in place of the static `isKnownRole`; `resolveRoleBackend` resolves a plugin role from its inline manifest binding (re-guarding a retired Claude model → default spawn tier) and a custom role's dead binding to the default spawn tier.
**Default effort** is the second axis on those same rows (`models.tierEffort`, `models.roleEffort`; policy + precedence: [docs/models.md](../models.md#default-effort)): `getTierEffort`/`setTierEffort`, `getRoleEffort`/`setRoleEffort` (role names canonicalized case-insensitively like the bindings), `inheritedRoleEffort` (what a role's `'inherit'` resolves to — exported only so `modelsSettingsState` can ship it as the UI's `Inherit (<level>)` label), `resolveRoleEffort`, and **`resolveSpawnEffort({effort, tier, role})` — the single resolution point for spawn effort, called by `InstanceManager._doCreate` and nothing else** (it owns the `400 invalid effort` validation too, so an invalid explicit value can't decay into a default).
**The system registry** is its own namespace, `systems.registry: [{id,label,launch?}]`, on the same managed-row contract as the backend registry: `getSystems()` / `getSystem(id)` / `isKnownSystem(id)` / `addSystem` / `updateSystem` / `removeSystem`, with `local` fully code-authoritative (from `MANAGED_SYSTEMS` in `src/systems/registry.ts`, never persisted, not editable, not removable) and ids validated by `isSlug`.
`getSystems` dedupes stored rows by id (**first wins**, matching the writers, which rewrite the list filtered by id) — only reachable by hand-editing, since `addSystem` 409s a duplicate.
`removeSystem` **never cascades** — it throws 409 NAMING the projects whose record still points at the system (via `projectsBySystem()`), because a dangling `system` field resolves to nothing and cannot be repaired without knowing which projects were affected.
`launch` is the provider command as argv, and it is **verified before it is persisted** (`verifySystemLaunch` → `probeSystemLaunch`): cc spawns the command, completes the handshake and throws the connection away, so an unreachable system is a 502 quoting the provider rather than a saved row that fails on the first project put on it.
Re-verified only when the command CHANGES — a relabel must not fail because the system is currently down — and a change also disposes the live handle.
A row with no `launch` is registration only: it declares that an execution environment exists and what to call it, and a project on it refuses `SYSTEM_NO_PROVIDER` at resolution.
**Plugin Library** settings (`plugins.libraryDirs`, `plugins.builtinLibrary`) are read-only here — `getPluginLibrarySettings()`, hand-edited, no setter; sanitising rules in [docs/plugins/rest.md](../plugins/rest.md#local--offline-catalogs).
**Landing renewal nudge**: `getLandingRenewNudge()` / `setLandingRenewNudge(on)` over `models.landingRenewNudgeEnabled` (absent → on; read at each MCP `delete_worktree`, no sync hook; the nudge rides that call's PostToolUse hook, `src/toolResultNudges.ts`).
**Idle renewal nudge**: `getConductorIdleNudge()` / `setConductorIdleNudge({enabled,value})` over `models.conductorIdleNudgeEnabled` + `models.conductorIdleNudgeMinutes` (off by default; clamped on write only to `IDLE_NUDGE_MIN_MINUTES`…`IDLE_NUDGE_MAX_MINUTES`; no migration — an absent key is the default).

## `src/hostTarget.ts`

the target forms shared by the plugin-facing host surfaces (`/api/exec`, `/api/terminal`): `HOST_TARGET_KEYS`, `parseHostTarget(body, op)` (form A `project`+`worktree?` / form B `system`+`remoteId?`+`cwd`, 400 `INVALID_ARGUMENT` / `CWD_NOT_ABSOLUTE`), `parseEnvOverlay(v, op)`, `resolveHostTarget(target, capabilities, op)` → `{sys, cwd}` — the `remoteSystems` gate, form B before `systemById` so no provider launches, form A after `resolveProjectCwd` — and `placeOf`. `op` prefixes every message, so each surface's refusals read as its own.

## `src/hostTerminal.ts`

`GET /api/terminal`, the plugin-facing terminal WebSocket: `createTerminalEndpoint({capabilities})` → `{handleUpgrade(req, socket, head)}`, called from `server.ts`'s upgrade dispatcher after the global Origin guard. In order: refuse ANY `Origin` (403 `ORIGIN_REFUSED`), parse the `spec` query parameter, resolve through `hostTarget.ts`, `openTerminal`, and only then complete the handshake on its own `WebSocketServer` (`noServer`, `maxPayload: TERMINAL_WS_MAX_MESSAGE_BYTES`, no deflate, no client tracking) — so every refusal is an HTTP JSON answer (`refuseUpgrade`; `SystemError` → 502 `SYSTEM_UNREACHABLE` / `REMOTE_NOT_FOUND` or 422 `TERMINAL_SPAWN_FAILED` with `errno`; an `httpError` keeps its status via `errorBody`; anything else is a logged 500). The client's socket closing during the open aborts it (`ECANCELLED`); `ws` failing the handshake after the open closes the terminal. `createTerminalBridge()` → `{handlers, attach(ws, terminal)}` is the pump: its handlers go to `openTerminal`, output before `attach` is held, binary both ways, a `resize` text in, one `exit`/`failed` text out then 1000/1011, any other text 1008; output pauses the terminal at `TERMINAL_WS_HIGH_WATER_BYTES` unwritten by the socket and resumes at 0; `write() === false` pauses the socket, `onDrain` resumes it; the socket closing closes the terminal once. Wire contract: [plugins/runtime.md](../plugins/runtime.md) → Host terminal.

## `src/hostExec.ts`

`POST /api/exec`, the plugin-facing command runner: `runHostExec(body, {capabilities, signal})` → `{status, body}`. Owns the request validation (unknown keys refused) and the `ExecResult` → status mapping; the target forms, the `remoteSystems` gate and resolution are `src/hostTarget.ts`. A refusal before the run is a thrown `httpError`; an outcome of the run is returned, since several carry fields `errorBody` would drop. Its constants (`EXEC_DEFAULT_TIMEOUT_MS`, `EXEC_MAX_TIMEOUT_MS`, `EXEC_DEFAULT_OUTPUT_BYTES`, `EXEC_MAX_OUTPUT_BYTES`, `EXEC_BODY_LIMIT`) are the single source the route and the docs name. The route in `src/routes/exec.ts` is a mount (placed by `buildRoutes`) ahead of the router-wide JSON parser that aborts the run when the response closes unwritten. Wire contract: [plugins/runtime.md](../plugins/runtime.md) → Host exec.

## `src/dirListing.ts`

the subdirectory listing behind `GET /api/fs/dirs` and the path autocomplete: `listDirectories(q, {deadlineMs?, resolveSystem?})` → `{ok:true, …} | {ok:false, code, reason}`, and `selectDirs(sys, dir, dirents, {linkDeadlineMs?})`, the selection (directories and symlinks, code-unit sorted, capped at `DIR_LIST_MAX_ENTRIES`) plus the bounded link phase.
A separate module because browsing an arbitrary path before it is a project is its own responsibility; the wire contract is in [protocol/rest.md](../protocol/rest.md) → `GET /api/fs/dirs`.
**Cost bound:** one `readDir` plus at most `DIR_LIST_MAX_LINK_STATS` `sys.stat`s in total per listing (links in name order), issued in batches of `DIR_LIST_LINK_STAT_BATCH`, under one `DIR_LIST_LINK_DEADLINE_MS` timer — `readDir` reports a symlink without its target kind and `stat` (which follows links) is the only System call that answers it.
A link past the budget, or unanswered when the sub-deadline fires, is returned **marked** in `links` rather than dropped or failed; a late `stat` result is ignored and its promise carries a no-op catch.
A per-entry error drops that link; any other error that settles in time (`ETRANSPORT`, `ETIMEDOUT`) refuses the listing, so a dead system never produces a quietly thinner list.
**The link phase runs outside the `DIR_LIST_DEADLINE_MS` race** (connect + `readDir`): a `readDir` that already answered must not become a refusal because links were slow.
`DIR_LIST_DEADLINE_MS` exists because the System layer's `DEFAULT_OP_TIMEOUT_MS` is a liveness fence, not a performance budget; `readDir` takes no `AbortSignal`, so a missed deadline leaves the operation to that fence.
**No single-exec alternative:** no `System` method answers "is this a directory, following links" for many entries in one round trip, and `find -xtype d` through `exec` would be a second `readDir` derivation outside `src/systems/` that also spawns `find` on `LocalSystem`, which Windows lacks.
It reaches the System through `systemById(...)` and takes no `node:fs` (see Conventions rule 8).
Unauthenticated, like the rest of REST: it discloses directory names to anyone who can reach the server.
`resolveSystem` is the seam unit tests use to hand it a fake System.

## `src/projectSuggestions.ts`

the scan behind `GET /api/projects/suggestions` and the Adopt dialog's list: which directories under the projects root are **not** registered. A separate module from `src/projects.ts` because filesystem discovery of unregistered directories is a second responsibility, and the edge runs one way — it imports the registry (`projectsRoot`, `listProjects({includeConduct:true})`, `LOCAL_SYSTEM_ID`), never the reverse. `suggestAdoptableDirs({maxDepth?, maxDirs?})` → `{root, maxDepth, truncated, unreadable, candidates[]}`; both options exist only as a TEST SEAM (the cap test would otherwise need 2000 directories) and the route passes neither. `suggestedNameFor(basename)` encodes the two rules `registerProject` enforces (`NAME_RE`'s charset, and the dot-leading refusal) so the endpoint cannot suggest a name the server would refuse; `null` when nothing usable is left. The rules, the caps and the wire shape are in [protocol/rest.md](../protocol/rest.md) → `GET /api/projects/suggestions`. **Its correctness condition is agreement with `adoptProject`** — a candidate the backend would refuse is a broken suggestion — so every rule is derived from one of that function's refusals and `tests/project-suggestions.test.mjs` adopts every candidate a fixture root yields. **`node:fs`, not a `System` handle, and that is not an exception to Conventions rule 8**: the seam is for PROJECT-scoped I/O, a suggestion is not a project and has no handle to take, and the scan asks about cc's own machine by construction (the dialog names a system but shows this list only for the local placement, and a remote adopt's probes already run on the named system inside `adoptProject`). Same standing as `listProjects`, which readdirs the store with `node:fs`.

## `src/modelVersions.ts`

curated per-family Claude model-version catalog (`MODEL_FAMILIES` (the family catalog), `DEFAULT_VERSIONS`) — this is the `claude` BACKEND's model list, shipped as the `claudeFamilies` payload key (`src/routes/models.ts` `modelsSettingsState`); the backend catalog proper is the registry (`models.backends`, see `docs/models.md`) — single source of truth for the Settings → Models Claude-version picker + the allow-list (`isKnownFamily`, `isKnownVersion`, `isKnownClaudeModel`, `defaultVersion`). Also exports `MANAGED_BACKENDS` / `MANAGED_BACKEND_IDS` (the code-owned managed registry rows) and `CLAUDE_BACKEND_ID` (the identity backend every "is this a substitution backend?" test compares against). Owns Claude context-window policy: each catalog version declares one numeric `contextWindow` plus an optional `launchTag` (the suffix the CLI needs to reach it, for a model whose native window ships as a separate build id). `claudeContextWindowTokens(id)` reads that number. `canonicalizeModel(id, backend)` applies the tag — `backend` is a **required positional**, and that gate is the only thing making it a no-op for a substitution model: any non-`claude` backend returns the id byte-exact, because that string is the registry key. Do **not** re-derive the gate from `familyOf(id)`: that is a naming heuristic, and inferring "not Claude ⇒ safe to normalize" from it is precisely what truncates a tagged substitution id and desynchronises it from its own registry row. Applied server-side at spawn/resume only — `shared/models.ts` holds no mirror.
- **Capability tiers** (policy + the full binding contract: [docs/models.md](../models.md)) — `CAPABILITY_TIERS` (the data-driven tier array in `src/modelVersions.ts`) + `DEFAULT_TIER_BACKEND` (each tier → `{backend:'claude', model:<family default version>}`) + `isKnownTier`.
  A tier binds to a `{backend, model}` pair via `getTierBackend`/`setTierBackend` (appSettings.ts), rebindable in Settings → Models.
  Resolution (in `spawnInstance`, `src/mcp/handlers.ts`): a tier → `getTierBackend(tier)` `{backend, model}` → passed to `create()` as `model` + `backend`.
  A **role** (built-in / user-custom / plugin-owned, checked via `isResolvableRole`) → `resolveRoleBackend(role)` — tiers and roles are a disjoint name-space (custom names can't be tier/family aliases; plugin names are `/`-namespaced), so the tier→role order is safe.
  A **legacy family alias** (`opus`/`sonnet`/`haiku`/`fable`) → `{backend:'claude', model:defaultVersion(family)}`; a **model id served by exactly one configured backend** passed directly → that backend (`backendsForModel`), served by several → `MODEL_AMBIGUOUS` unless the `backend` argument picks one; a **Claude model id** → pass-through claude; **omitted entirely on a FRESH spawn** (no `resume`) → `defaultSpawnBinding()`, which also sets `tier` so that row's default effort applies; anything else is refused (no silent bare-claude spawn).
  The omitted branch is gated on `!resume`, and on a resume with no model named `resolveSpawnModel` resolves **neither** axis — it returns no backend at all (`backend: undefined`), deferring model+backend to `_doCreate`'s session-store recovery; asserting `'claude'` there would make the resume's backend look explicit and suppress that recovery.
  The branch lives *downstream* of the MCP playbook gate — a stage `pin: {model}` has already filled `args.model` by then, so a pin always wins and never hits `ARG_PIN_CONFLICT`.
  `backend` is the sole discriminator; `model` is a plain id for every backend, so resume/canonicalize apply uniformly.

## `src/keyedQueue.ts`

`createKeyedQueue()` returns `run(key, fn)`: a per-key promise chain, in-process. Calls on one key run one at a time in call order; different keys run concurrently; a rejection goes to its own caller and never blocks the next call; a key's entry is dropped once its tail settles. Used by `src/projectClaudeMd.ts` (one project's `CONVENTIONS.md` writes), `src/worktrees.ts` (one project's merge hooks) and `src/logRotation.ts` (appends to one log file).

## `src/logRotation.ts`

Generic file mechanisms for cc-owned logs; callers own the policy (paths, caps).

- `rotateFile(current, previous)`: one generation, `previous` is overwritten; creates `current`'s parent; a missing `current` is tolerated (ENOENT).
- `trimLog(file, { maxBytes, keepBytes })`: the plugin backend log's keep-newest trim behind a marker line, on one `r+` descriptor, never creating a file.
- `appendRotating(file, data, { maxBytes, previous })`: the size check happens before the append, `>` means strictly over, then the file is renamed to `previous` and restarts at this call's first byte. Serialised per resolved path through `createKeyedQueue`; a failure rejects to its own caller.
- Users: `src/plugins/backendLog.ts` (`rotateBackendLog`, the `trimLog` re-export) and `harvestEvents` in `src/systems/fuse/session.ts`.
- Pinned by `tests/log-rotation.test.mjs`.

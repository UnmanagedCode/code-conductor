Testing the `shared/` modules under happy-dom, the web UI's Vitest and Playwright suites, and what a fake-CLI + headless-Chromium pass can reach: [frontend-testing.md](frontend-testing.md).

**Two suites, and the card gate.**

| Command | Runs |
|---|---|
| `npm test` | `tests/gate.mjs`: `typecheck:node`, `typecheck:web`, then `tests/run.mjs` (`node:test`), then Vitest; red if any step is. The gate |
| `npm test -- <files>` | `tests/…` files to `tests/run.mjs`, `web/src/…` files to Vitest; only the suites named, each after its typecheck half — `typecheck:node` only when the diff against main can reach it (below) |
| `npm test -- --changed` | The suites and halves the diff against main selects (below), whole suites |
| `npm run test:node` | `typecheck:node`, then `tests/run.mjs`; `-- <files>` appends test files (it takes no flags) |
| `npm run test:web` | `typecheck:web`, then Vitest over `web/src/**/*.test.{ts,tsx}`; `-- <file>` or `-t name` append to Vitest |
| `npm run typecheck` | `typecheck:node` then `typecheck:web` |

- **The gate (`tests/gate.mjs`, pinned by `tests/gate.test.mjs`) runs its steps one after the other, never in parallel:** the typecheck halves first, then the suites. `parseGateArgs` routes arguments and `planGate` turns a scope into steps. A file-list run with `tests/` files skips `typecheck:node` (it prints a line naming the merge-base) when git produced the change set against main's merge-base and every path in it is a `tests/` or Markdown file and none is TypeScript (`.ts .tsx .mts .cts`, declarations included) or `.json`: the node programs read only TypeScript and JSON and reach nothing under `tests/`. An empty diff skips it; a git failure keeps it. The skip trusts the merge-base to typecheck; `npm test` with no arguments and `--changed` never skip it, and a change to ignored files or `node_modules`, which no diff shows, is the full gate's to catch. A typecheck step is `blocking`: red, it starts no later step. A red node suite does not skip Vitest. The closing `npm test: …` line names each step with `PASSED`, `FAILED (exit N)`, `FAILED (<signal>)` or `NOT RUN`, and goes to stderr when red. The halves run as `npm run typecheck:<half>` through `npm_execpath`, so the gate refuses to plan without it (exit 2: run it through `npm test`). Refused with exit 2 and a pointer: a `web/e2e/…` path or `web/playwright.config.ts` (→ `npm run test:e2e`), any other path outside `tests/` and `web/src/` (→ name test files there, or `--changed`), any `-flag` (→ `npm run test:web -- …`; `npm run test:node -- …` takes test files only), and `--changed` with any other argument. npm eats a bare `npm test --changed`; write `npm test -- --changed`. An interrupt (or a suite ended by a signal) starts no further suite and exits 128 + signo; SIGTERM is forwarded to the running suite, SIGINT is not (the terminal already sent it to the group). Vitest is spawned with the gate's own env, never `tests/run.mjs`'s.

- **The node suite never builds `web/` and never installs into `node_modules`.** `tests/run.mjs` sets `CC_SKIP_WEB_BUILD=1` and `CC_SKIP_DEPS_SYNC=1` for every child (and appends `--max-old-space-size=512` to `NODE_OPTIONS`: a runaway-test bound at about 4× the measured per-file peak RSS, set there so it reaches node test children and not Vitest), and `bootServer` calls `createServer`, never `start()`. `tests/web-build-wiring.test.mjs` pins each link: `tests/run.mjs`'s source setting both, `entryStartOptions` and the entry block's call to it, `start()` handing both flags to `createServer`, and an in-process `start()` whose injected `webBuild` is not called with `buildWeb:false` (and is, once, with `true`). `tests/web-routes.test.mjs` pins the mounts against the real server for the paths that do not depend on a build, and the ready / building / failed states against `webHandler` over a fixture dist.
- **`tests/run.mjs` is quiet by default.** `QuietFilter` (`tests/quietReporter.mjs`) sits between the `run()` stream and the `spec` reporter and decides which events `spec` sees, per test file:

  | A file that… | Prints |
  |---|---|
  | passes (its per-file `test:summary` arrives) | its skip and todo lines only — no `✔`/`▶` lines, none of its stdout/stderr |
  | fails (any `test:fail` — an assertion, a Layer-B leak, node's synthesized failure for a killed child) | its whole output from its first event on, in order, then everything after live |
  | never reports (no summary, no failure: `NO REPORT`) | its whole output, above the `ℹ` counts and the `failing tests:` block |
  | belongs to a run that goes red for a reason no file owns — the run cap, a stream stall, or a leaked-process sweep that is the run's **only** red cause | every passing or unreported file's held-back output, after a `quiet-reporter: the run went red (<reason>) …` line (`run cap` and `stream stall` from the wait's exit, `leaked process swept` after the run-end residual check), each file rendered by its own `spec` instance; a passed file's skip and todo lines, already printed at its summary, are not repeated |
  | belongs to a run where a sweep fired but something else is red too — a failed test, a killed or unreported file, a `RESIDUAL`, the fake-claude `guardrail` budget | nothing held back: the files that went red printed their own output. One `quiet-reporter: a leaked process was swept, but … not dumped …` line names `CC_TEST_VERBOSE=1`. No line after a cap or stall, which already dumped |
  | is running when SIGINT/SIGTERM interrupts the run | nothing held back — rerun with `CC_TEST_VERBOSE=1` |

  The run-level `ℹ` counts, the `failing tests:` block and every `hang-guard:`/`guardrail:` line print as before, and a quiet run ends with a `quiet-reporter: … CC_TEST_VERBOSE=1 …` hint. **`CC_TEST_VERBOSE=1` restores the full `spec` report**; it reaches the runner through `npm test`, `gate:systems` and the mutation harness, which all inherit env. Every ledger and hang-guard listener in `tests/run.mjs` stays on the **source** stream, so `reported`, `killedFiles`, `nodeFinished` and `settledAt` do not depend on the filter. The filter keys each file by its **realpath**, because through a symlink node reports one file under two spellings (the `run()` path on enqueue/dequeue/complete/plan/summary, the realpath on start/pass/fail/stdout/stderr). Pinned by `tests/runner-quiet.test.mjs` (passing, failing, verbose, a fixture reached through a symlinked directory) and by a fixture marker asserted in each hang-guard case for a killed file, `NO REPORT`, the cap, a stall and a run-end sweep.
- **The real builds are in `test:web`:** `web/src/build.test.ts` runs `ensureWebBuild` into private dirs under `os.tmpdir()` (each `distDir` in a `mkdtemp` parent of its own, because the leftover sweep reads the parent) and writes nothing under `web/` (an output dir there would change `webSourceHash()` between calls; its hash probes run over a fixture root). Builds run as the child process the server runs, which sets `NODE_ENV=production` itself, so the bundle checked is the one the server ships. Staging, adoption, the drift hint, the leftover sweep and the three swap failures run with an injected builder; `runViteBuild`'s argv, cwd and env are pinned against a fake `vite.js`. One real build pins the stamp, no-rebuild on unchanged sources, every chunk under a pinned 500 kB (not read from the config it guards), the root-absolute URLs in the built `index.html`, no dialog code (`data-dialog`) in the entry or the chunks it imports statically (the closure walker is unit-tested over synthetic chunk text, bare `import"./x.js"` edges included) while a lazy chunk carries it, the built manifest's `start_url`/`scope` resolving to `/` and serving every shipped file; the swap failures (rename fails; rename and restore fail; old-build removal fails) exercise the same swap code through the injected builder.
- **`npm test -- --changed` (`tests/changedScope.mjs`, pinned by `tests/changed-scope.test.mjs`).** `changedPaths` lists every path changed since main's merge-base with HEAD: committed on the branch, staged, unstaged, both sides of a rename, and untracked files that are not ignored. `buildReach` reads the tree once, and `classifyChanged` selects:
  - **both suites** for toolchain files (`package.json`, `package-lock.json`, any `tsconfig*.json`) and for `shared/`;
  - otherwise **every suite that reaches the path**: its import closure contains it, its closure's source names its basename (a file read by name), or the path lies under one of its reached roots (below);
  - **both suites** for a path nothing reaches (deleted or unknown files included), listed as `unclassified`.

  A suite's closure starts from its test files (`tests/`; `web/src/` plus the Vite and Vitest configs) and follows relative, `@/` and `@shared/` imports and a `.css` file's relative `@import`s, plus every code file its comment-stripped source names by path: a literal, or a run of quoted segments (`path.join(ROOT, 'bin', 'x.mjs')`), read repo-relative after dropping leading `./`/`../`. A sibling named by its bare basename is caught by the basename rule.

  A suite's **reached roots** come from its closure files' calls:
  - **a walk** (a `WALK_CALL` match) reaches every directory its file names, plus its own directory when it uses a dirname (`__dirname`, `import.meta.dirname`, `import.meta.url`);
  - **a read** (a `READ_CALL` match, anywhere in the file, so a wrapping helper counts) reaches every directory its file names on the other suite's side: under `web/` for a node file, outside `web/` for a web file. This catches a fixture dir read through a computed name (`testkit.ts`'s `FIXTURES`);
  - a named path also names its leading directories (`'web/src/a.ts'` names `web` and `web/src`).

  A `WALKS_REVIEWED` entry narrows a file's inferred roots for each suite it names, to a list of directories (`[]` reaches none) or to `{ closureOf: [roots] }`, an import closure for a file that follows imports itself (`tests/web-build-deps.test.mjs`; an `.html` root contributes its module `<script>` srcs). Its `sites` fingerprints its call sites and the git-tracked paths its literals name (`sitesOf`; `buildReach` returns the live value per reviewed file); an ignored or untracked dir on disk, such as Playwright's `test-results/`, does not count, and a new path counts once it is staged. The entry goes stale when that changes, or a `closureOf` root is gone: the inferred roots apply again, the gate prints the file, and the freshness pin reds with the live `sites`. The classifier's own files are reviewed because their directory literals would otherwise make whole trees node-reached roots. Separately, the real-tree pins live in the node suite, so a `web/`-only diff does not run them. `--changed` is a pre-merge shortcut, not a substitute for the full gate. Halves: each selected suite's own, plus both whenever a path lies outside `web/` and `tests/`. An empty diff, or a git failure (no `main`), runs the full gate. Before running, the gate prints the paths that selected each suite.
- **The typecheck halves are the `typecheck:node` and `typecheck:web` scripts in `package.json`;** `typecheck` runs both. `shared/`'s own project is in the node half because it carries node's strip-only constraints (`tsc -p web` checks `shared/` under web settings). The plugin bridge config is web-side. `web/e2e` is web-side even though it typechecks `src/` files, which is why `--changed` adds both halves for a path outside `web/` and `tests/`.
- **The mutation harness runs the node, Vitest and Playwright suites,** routed by test file through the `routes` of `harness/mutation/config.json`, the command shape is described in `harness/mutation/README.md` → Three routes, and the `config.json` values field by field in `harness/mutation/RATIONALE.md` §7. Each non-opt-in route's `baselineCommand` typechecks its own half (`node` → `typecheck:node`, `vitest` → `typecheck:web`); a mutant's command never does: its node route calls `tests/run.mjs` directly.

**TypeScript toolchain.** Server-side `src/*.ts` runs directly under Node 24's native type stripping — no emit, no `dist/`, no bundler — so converted files are limited to **erasable syntax** (`tsconfig.json`: `strict`, `erasableSyntaxOnly`, `verbatimModuleSyntax`, `allowImportingTsExtensions`, NodeNext ESM). Because stripping never type-checks, `npm run typecheck` (`tsc --noEmit`) is an **enforced gate**, not an optional script: `npm test` runs its halves (`typecheck:node`, `typecheck:web`) as blocking steps before the suites, and each mutation route's baseline runs its own half first — never in a mutant's command (`harness/mutation/README.md` → Three routes). The `package.json` `typecheck:node` and `typecheck:web` scripts are the list of programs it checks. Converting a module renames it `.js` → `.ts` and every importer's specifier with it (Node resolves import specifiers literally — no extension fallback); a still-`.js` sibling is imported via a minimal hand-written `.d.ts` that declares only what the `.ts` consumer uses. The `shared/*.ts` modules follow the same rules and run two ways: type-stripped by Node for the server and the node tests, and compiled by Vite for `web/`. `shared/tsconfig.json` extends the root config, so `erasableSyntaxOnly` and `verbatimModuleSyntax` hold them to what Node can strip, and sets the DOM `lib` with `types: []`: browser globals, no node globals. The root `include` leaves `shared/` out, because its DOM-less `lib` cannot type the browser modules, but the root program still checks every module `src/` imports by following the imports, which keeps those DOM-free. `tsc -p web` checks them once more through web's imports. `pluginBridge.js` is the one browser file left as JS: it is served byte-for-byte as a classic script with no build step, so `web/tsconfig.bridge.json` checks it alone with `allowJs` + `checkJs` under web's strict settings.

**Session-state test gotchas.**
- `wsClient`'s `close()` (`tests/ws.test.mjs`) resolves on the socket's `'close'` event, so closing an already-closed socket never resolves: put closes in `finally`, or a failed assert surfaces as a teardown timeout.
- `spawn()`'s `_replayDone` tail awaits `loadHistory` before flipping to `idle` (`spawn()` itself and the create POST do not wait for it), so waiting for `status === 'idle'` is the replay barrier.
- The `turn_end` exclusion from the ctx latch is pinned only by a usage-BEARING `turn_end` ("lastContextUsage ignores a usage-bearing turn_end (the ctx 743% shape)", `tests/ws.test.mjs`); a usage-less fixture passes a latch widened to any `ev.usage`.
- Ring content written before the first `launch()` (the redirected create path's inert-exclude `system/stderr`) is reachable only on a remote project; T12 in `tests/segment-seam-paging.test.mjs` builds that state. Local fixtures never have it, so seq 0 is not reliably the CLI's first event.
- A provider without `remoteDescriptors` resolves the narrowest mirror root, so union tier geometry tested through it covers only that arm (see [systems-protocol.md](systems-protocol.md) §2.1).

The suite is isolation-safe: `bootServer` binds an ephemeral port (`listen(0)`) and `mkdtemp`s a unique home per server, so files never contend over ports or paths.
Concurrency defaults to a cores-derived cap (see `resolveConcurrency` in `tests/run.mjs`).

**Box-wide test slots (`tests/testSlot.mjs`).** Every suite sizes itself to the machine and none knows about the others, so demand grows linearly with concurrent runs (parallel worktrees, mutation baselines) and deadline-bound tests time out under load. At most `CC_TEST_SLOTS` (default `DEFAULT_SLOTS`) leased suites run at once across the whole box; any further run waits, then runs; each suite keeps its own sizing. The measurements behind the default, and why it is not 1, are in the header of `tests/testSlot.mjs`.
- **Mechanism.** Slot *i* is loopback TCP port `CC_TEST_SLOT_PORT + i`; holding a slot is listening on it, so the kernel frees it when the holder dies, `kill -9` included — no lock file, no stale-lock recovery. The holder's server is `unref`'d and answers each connection with one JSON line `{magic, pid, cwd, label, since}`. A probe of a busy port has four outcomes: the holder line (waits for that holder); a completed answer without the magic, a foreign listener (logged once and skipped; every slot foreign throws, naming the ports and `CC_TEST_SLOT_PORT`); a refused connection, meaning nothing listens any more (the listen is retried at once and takes the free slot); or no completed answer — no reply within 1s, any other socket error, a close with nothing sent — which is unknown, so the run keeps waiting and never throws (a stopped holder looks the same).
- **Log lines (stderr).** `test slot: waiting — held by <label> <cwd> pid <pid> for <n>s; …` when the wait starts and every 60s; `test slot: acquired after <n>s` only when there was a wait. A port with no completed answer adds `port <n>[, <n>…] unresponsive (a stopped holder, or a listener that never answers)` to the waiting line, after the holders separated by `; `, or alone as `test slot: waiting — held by port <n> unresponsive (…)` when no holder answered.
- **Nested runs.** A holder puts `CC_TEST_SLOT_HELD` in the env of everything it spawns; `acquireTestSlot` returns a no-op lease when it is set, so a child never waits on its parent. A spawn that builds a curated env must carry it through.
- **Entry points** — one lease each, taken before any work:

| Entry point | Acquires in | Covers |
|---|---|---|
| `npm test` (all, `-- <files>`, `--changed`) | `main()` in `tests/gate.mjs`, after planning | both typecheck halves and both suites |
| `npm run test:node`, `node tests/run.mjs`, each `gate:systems` row | top of `tests/run.mjs`, before the run cap starts | the node suite and every per-file child |
| `npm run test:web`, `npx vitest run …` | `globalSetup` `tests/vitestSlotSetup.mjs` (`web/vitest.config.ts`); Vitest awaits it before any worker starts. Skipped in watch mode | every Vitest worker |
| `node harness/mutation/run.mjs …` (every subcommand) | `harness/mutation/run.mjs`, before the plugin runner starts | the whole campaign; the wait is outside `timeoutMs` and the hang deadlines |

**Port ownership.** Picking a port by binding it and freeing it leaves a window in which another file's `bootServer()` `listen(0)` is handed the same port — after which an HTTP readiness probe is answered by that stranger and a destructive `POST /api/admin/restart` kills *another test file's process* mid-run. Two rules:

1. **Hold the socket when you can.** `tests/eaddrinuse-retry.test.mjs` and `tests/plugins-supervisor.test.mjs` bind `listen(0)` and never release until the test says so, which also makes the collision deterministic rather than lucky. **`tests/server-restart.test.mjs` deliberately does not** — it keeps bind-then-free `getFreePort()`. Converting it to hold-then-release was **measured and declined**, not deferred (16-core host, idle; 5 instrumented runs + forced-contention runs):
   - **Window A**, `getFreePort()` resolve → the child's banner: **241–278 ms** (median 268; spawn lag 0–2 ms, the rest is boot). Hold-then-release does **not** close it — the gate is the child's first `EADDRINUSE on port` stderr line, which `listenWithRetry` (`server.ts`) writes at the *start* of its 100 ms sleep, leaving a measured **111–114 ms** residual.
   - **Window B**, `teardownNetworking`'s `server.close()` (`src/restart.ts`, before the replacement spawns) → the replacement's banner: **254 ms**, and it is not test-side at all — a competing bind took the port on its **first attempt, 2 ms after** the parent's `restart: spawned replacement pid=` log. No test change narrows it. Tracked separately.
   - So the conversion narrows **window A — the larger of the two (median 268 ms vs B's 254) — by ~2.4×** (268 → 111–114 ms). **Two different ratios, do not conflate them:** the per-file aggregate falls only **~1.43×** (2 tests × each window: 536 + 508 = ~1044 ms → 224 + 508 = ~732 ms), because window B is untouched and carries 508 of the remaining 732 ms. That is **~0.022% → ~0.016% collision per suite run** (~261 ephemeral binds per run over ~30–60 s against 28232 free ports, `/proc/sys/net/ipv4/ip_local_port_range`) — that denominator is an **upper bound**: leaked fixture listeners held 12 of those ports on the measuring box. It does not move the rate. The kernel never hands out a port already in `LISTEN`, so an orphan holding *P* removes a candidate rather than causing an `EADDRINUSE`; 12 of 28232 shrinks the pool by 0.042%. The reason to decline is not that A is the smaller window — it is the larger — but that a production window **nearly as large** survives untouchable from a test while the machinery reads as "window closed". Declined on those numbers; do not re-open without new ones.
   - What makes ~0.022% acceptable is rule 2: forced contention on either window ends at `waitForBanner` rejecting (`child never printed listening banner #<n> for port <p>`), and in both forced runs the stranger received **zero** requests. The cost of a collision is this file timing out, never another file's process.
   - Dead alternative: spawning with `PORT=0` and reading the bound port back from the banner would close window A entirely, but `spawnReplacementAndExit` passes the parent's own env (`src/restart.ts`), so the replacement inherits `PORT=0`, binds a *different* port, and destroys the same-port invariant.
2. **Never trust the port as identity.** Readiness on a spawned `server.ts` waits for that child's own stdout banner `code-conductor listening on http://<host>:<port>`, printed from the address it actually *bound* — never an HTTP probe a stranger answers just as happily. The rule lives once in **`tests/serverBanner.mjs`** (`waitForBanner(captured, port, {nth})`; the restart replacement inherits the same stdout, so its banner is occurrence #2) and is imported by every test that waits on a `server.ts` child. Additionally, never send a destructive request to a port whose owner you have not established: `server-restart.test.mjs` asserts the port is still `EADDRINUSE` immediately before each restart POST.

`tests/restart-port-identity.test.mjs` is the regression guard — a decoy `node:http` server answers the old probe while the real child cannot bind, and the test asserts that `waitForBanner` (the same import the restart tests use, which is what makes the guard cover them) rejects rather than reporting ready.

**Store isolation (`tests/safeStoreRoot.mjs`).** The stores resolve their on-disk root from `PROJECTS_ROOT`, falling back to a source-relative default (`src/../..`) that IS the real production `.code-conductor` when it's unset — so a test touching a store with `PROJECTS_ROOT` unset corrupts the live store. `run.mjs` pins the whole run to a throwaway temp root (`createSafeRoot()`) before any file forks — every child inherits it — and asserts via `assertStoreIsolated(orchStoreRoot())` that the store never resolves into the real workspace (aborting the run if it would). `bootServer` teardown restores `PROJECTS_ROOT`/`CLAUDE_PROJECTS_ROOT` to that safe root, never to unset, so out-of-window writes stay in the temp dir. `tests/store-isolation.test.mjs` is the regression guard.

**Temp dirs (`tests/tmpRegistry.mjs`).**
- A test temp dir is minted by `mkdtemp(prefix)` (async) or `mkdtempSync(prefix)` from `tests/tmpRegistry.mjs` and removed by exact path in the registry's root `after()`; a synchronous `process.on('exit')` backstop retries leftovers. There is no `/tmp` prefix sweep, and SIGKILL is uncovered.
- `tests/tmp-dir-guard.test.mjs` fails on any spelling of `mkdtemp`/`mkdtempSync` under `tests/` — code, comments and strings alike — except a bare use of a name imported unrenamed from `tmpRegistry.mjs` in the file's leading import block (an import spelled inside a string or template binds nothing). In prose write "temp dir". The guard's `ALLOWED` list and file exemptions own the reasoned exceptions.
- The registry's `after()` runs before a file's own root-level `after()` hooks. Tear down anything still writing into a registered dir in `t.after`, `afterEach` or a `describe`-level `after`.
- A test that runs the migration chain (`runMigrations` or `ALL`) or boots the server (`start()` / `node server.ts`) pins `HOME` to a registry dir first: migration 0004 moves `$HOME/.code-conductor/{whisper.cpp,piper}` into the migrated root, and a registry dir that owns the migrated root deletes what it moved.

**Store teardown drain.** A store write resolves its file from `PROJECTS_ROOT` when it *runs*, not when it is issued, so a write still queued when a test retargets the root lands in the next test's store. `bootServer().close()` therefore calls `settleSessionWrites()` (`src/sessionStore.ts`: waits out the serialize chain and the read-barrier set until neither moves) after `instances.shutdown()` and before restoring the env and deleting the home; `InstanceManager.shutdown()` resolves only after every normal instance's exit archive has landed, including one removed from `byId` earlier (`kill_instance`, the exit drop) — the manager tracks them in `_exitArchives`. A test that parks the lineage chain (`_kickLineageWrite(() => held)`, `trackLineageWrite(held)`) releases it in `finally`, or `close()` waits on it until the hang-guard. Files sharing one server across tests via `freshProjectsRoot()` get no drain between tests (see that helper's comment). `tests/store-teardown-drain.test.mjs` pins all three.

**Git isolation (`pinGitConfig`, `tests/safeStoreRoot.mjs`).** The store root's sibling: `run.mjs` also writes a run-scoped `gitconfig` into the safe root and exports `GIT_CONFIG_GLOBAL` at it before any file forks, so no repo the run creates reads the developer's `~/.gitconfig`. Its load-bearing key is `maintenance.auto=false`. Without it git spawns `git maintenance run --auto --quiet --detach` after ordinary write commands — **measured 765 spawns per `npm test`, 0 after** — and because that child is DETACHED it outlives its parent and repacks whenever it lands, including inside a `snapshotTree`/`assertTreeUnchanged` window, where it reds a systems row as a spurious tree diff (`.git/info/refs`, `objects/info/packs`, `multi-pack-index`, `pack-*.{idx,pack,rev}` appear; every loose object goes). `GIT_CONFIG_GLOBAL`, **not** `GIT_CONFIG_COUNT/KEY/VALUE`: git clears the `GIT_CONFIG_*` family for commands run against another repository (`local_repo_env`), so the env form leaks on git's local transport — measured on one local push against a three-arm control: no config **1** spawn, `GIT_CONFIG_*` env form **1** (it does not bite), `GIT_CONFIG_GLOBAL` **0**. `gc.auto=0` is a second key for the same outcome (each ALONE takes the spawn to 0 on git 2.55 here); it is kept for git versions that reach the repack through `git gc --auto` instead, which this host cannot check. Consequence: **a test needing a global git setting must add it to `GIT_CONFIG_BODY`**. `tests/git-maintenance-isolation.test.mjs` is the regression guard. **Every spawn figure here is a measurement from 2026-09-02 on git 2.55, not an invariant** — `pinGitConfig`'s comment carries the two-line command to re-take them.

**Forcing a spawn-time store write to be late.** `launch()` awaits the spawn-time store facts, so an awaited `create()` must resolve only once they are durable. The deterministic pin (`tests/backend-spawn.test.mjs`, describe `'the spawn response waits for the spawn-time store facts'`) pre-creates `sessions.json.lock` with a live PID (this test process's own) *before* triggering the writes — through a resume, because a fresh spawn awaits `mintPublicId` under the same lock and would stall before the facts are kicked: `storeLock.ts` reclaims a held lock only when the owner PID is dead, so no write can have landed while the lock stands — a hard mutual-exclusion barrier, not a timing delay. Start `create()` un-awaited, wait for the instance to be idle (a child round trip), assert `create()` has NOT resolved (the forcing assertion), release the lock, await it, then read each fact once with no `waitFor`. The failure path is `tests/spawn-facts-lock-failure.test.mjs`: it shrinks the lock budget via `ORCH_STORE_LOCK_RETRY_MAX` / `ORCH_STORE_LOCK_RETRY_BASE_MS` (read at `storeLock.ts` module load, so set before the dynamic import; a separate file because the budget is per process), holds the lock for the whole test, and asserts `create()` still resolves, the store logs `sessionStore: <op> <id> failed:` for each write, and nothing was written. `settledSessionBackend` (`tests/helpers.mjs`) remains a polling read; after an awaited spawn it returns on its first read.

**Never assert across a machine-speed window.** `SPAWN_SETTLE_MS = 400` (`src/plugins/supervisor.ts`) bounds how fast a crash must be **observed**, not how fast a child boots — the latter is a property of the host. `tests/plugins-supervisor.test.mjs`'s settle-window test squatted a port and required a real `bash -lc 'node server.mjs'` to fail `listen()` and be reaped inside that window. Measured spawn→exit for that child: **p50 42 ms idle (max 46, 0/12 over 400 ms)** vs **p50 ≈ 420 ms at load1 ≈ 75 (min 219, max 813)** — so it went red **7/9 runs at load1 73.8–77.5** and never once idle. The rule: make each branch reachable **only** by construction, never by margin.
- *Inside the window* → the `_spawn` seam (`createSupervisor`). A fake child emitting its stderr + `exit` on `process.nextTick` is settled before any timer can run, so `raceSettle`'s first 20 ms tick always observes it — true on an arbitrarily starved box. Never a real process.
- *Outside the window* → `_settleMs: 0`, which makes "the window expired first" the only reachable branch, again with no competing clock. That test also cross-checks node's **actual** bind-failure line against the string the fakes emit, so the fixture cannot drift out of sync with reality.
- The **event-driven retry** (retry on the child's exit event instead of a window) was **measured and declined**, not deferred — same treatment as above. The retry heuristic is anti-correlated with its own risk: `allocatePort()`'s TOCTOU window widens under exactly the load that stops a 400 ms window from catching the resulting crash. But retrying after `start()` returned means rewriting a record `registry.ts` has already persisted via `store.recordStart(id, rec)`, i.e. a record-rewrite path for a ~0.02 %-class event (the collision rate computed under "Port ownership" above). Do not re-open without new numbers.
- The **readiness-cancellation** half is load-independent and pinned by a pair: a squatter that counts accepts and destroys each socket (so a probe cycle is countable and cannot leak), one test asserting accepts stop growing once the child is dead (`<= base + 1`, the one probe that can be in flight) and its **control** asserting they *do* grow over the same shared `PROBE_WINDOW` while the child lives (`> base + 1`). The two bounds are exact complements, so neither can pass vacuously.

**Second worked example of the same rule — a RATIO between two wall figures.**
`tests/summary-attribution.test.mjs` compared per-file durations as `fast * 3 < medium` and `medium * 1.25 < slow`.
A difference cancels the per-file spawn cost `C` to first order; a **ratio multiplies it**.
`fast * 3 < medium` reduces to an absolute cap of `C < 600 ms` — not a spread tolerance — and `C` reaches ~770 ms at 72-way (above), so it went red **10/24 (42 %) at load1 72.8–74.4** on a completely correct reporter, while passing **30/30 at 24-way**.
The construction that replaced it: **chain the fixtures' completions through a rendezvous** (`tests/fixtures/attribution/chain.mjs` — each waits for its predecessor's **process to exit**, spends its own designed increment, then publishes its own pid) and assert **differences against those increments** (`medium - fast >= 1200`, `slow - medium >= 900`, `sub - fast >= 550`).
Because `reported_a - reported_b = (done_a - done_b) + (dequeue_b - dequeue_a)` and both terms are non-negative when `a` is listed before `b` in argv, every bound is a lower bound **no child-side cost** can violate.
**State that claim precisely** — `done` is stamped in the runner's `test:complete` *handler*, so the identity also carries a parent-side delivery term, and one contiguous stall of the parent's event loop spanning both completions compresses the difference toward zero.
The stall must be roughly the size of the increment it attacks (~600 / 850 / 1150 ms for the 550 / 900 / 1200 bounds); measured buffers over the floors are **+12…+53 ms quiet, +46…+539 ms at 72-way**.
That branch is still margin-reachable and the test header says so — **the smallest increment, 550 ms, is what sets the breaking stall size, so do not shrink it without re-measuring.**
It fails loud (red), never silently green, and the exposure is far smaller than the multiplied-`C` term it replaced.
Two things are load-bearing and commented at their call sites: `TEST_CONCURRENCY=4` (fewer slots than chained fixtures deadlocks the chain, loudly) and the **descending** argv order `slow, medium, subsecond, fast`.
Resolution claims get the same treatment — a `(0, 1000)` band on a difference was measured *outside* its own range (gap 1053 ms) on a correct reporter and is now a load-free lattice residue, `some(ms => ms % 100 !== 0)`.
**Gate a rendezvous on the predecessor's process EXIT, not on its marker appearing** — a marker written at the end of a test body leaves that child's whole teardown+exit cost inside the difference, subtracting: measured at 72-way, marker-gating broke all three bounds (minima 1200/900/550 → **1050 / 811 / 460**, standalone red **13/24**, i.e. worse than the ratio it replaced), and the deficits tracked the *predecessor's* own reported figure monotonically.
Exit-gating removes that term and makes the successor's exit cost a positive buffer: **24/24 green at load1 70.9–75.8**, minima **1312 / 953 / 596**.

**Third worked example — a fixed PRE-SIGNAL DELAY.** `tests/hang-guard-sweep.test.mjs`'s two interrupt legs (`SIGTERM …exits 143`, `SIGINT …exits 130`) signalled the nested runner a fixed **1200 ms** after spawn (`runGuard(…, { signalAfterMs: 1200, signal })`) and then read the fixture's `silent-orphan: holder pid=<n>` line back out of the captured stream. That is a margin claim about a **host property** — the case's own header said the delay was "well clear of process start-up on a starved box" — because the whole nested boot chain (runner boot + `node:test` dispatch + fixture boot + two `--import` preloads + `spawn`) has to fit inside it. Measured spawn→marker: **759 / 952 / 1585 ms** (min/med/max, n=8) **at 72-way** vs **87–115 ms idle**. Three ratios, none of them interchangeable: loaded boot vs idle boot is **13.8×** (1585 / 115), the window vs idle boot is **10.4×** (1200 / 115) — the headroom the test was written against — and the window vs *loaded* boot is only **0.76×** (1200 / 1585), which is the one that decides the case. Load moves the boot cost by an order of magnitude while the window stays fixed, so the margin inverts. Standalone `node tests/run.mjs tests/hang-guard-sweep.test.mjs` ×14, measured twice independently at 72-way: **6/14 runs (43 %) / 8/28 legs** at load1 75.1–76.6 / load5 53.0–63.5, and **5/14 runs (36 %) / 6/28 legs** at load1 73.9–75.5 / load5 70.9–72.6 — always on `the fixture never printed its holder pid` and never on a product assertion: on every red the runner still printed its interrupt banner, swept under the correct trigger label, and exited 130/143 with `signal === null`. **Test defect against a correct product — no `src/` and no `tests/run.mjs` change.**

The construction that replaced it: **`signalWhen`, a rendezvous on the fixture's own marker** (`runGuard`, `tests/hangGuardCase.mjs`) — one signal, sent synchronously in the same tick the captured stream first matches the regex, rather than after a duration. Five preconditions are *eliminated*, not widened. **E1** *the marker precedes the signal* (the assertion that failed): was a 1200 ms margin, now causal — the signal exists only because the line arrived. **E2** *the holder is alive when the sweep runs*: structural — the fixture writes the pid only after `spawn()` returned. **E3** *run.mjs's SIGINT/SIGTERM handlers are armed*: structural — registered by the `for (const [sig, code] of [['SIGINT', 130], ['SIGTERM', 143]])` loop in `tests/run.mjs`, which precedes that file's `const stream = run({` call, and only an already-dispatched file can emit the marker. **E4** *the holder-is-actually-dead poll executes*: it was silently skipped on every flake (`holderPidFrom` aborted first), so **coverage strictly increases**. **E5** *no armed timer outlives the case*: the interrupt path now arms no timer at all, leaving `bail` as the only one `runGuard` has to clear (the `stdoutPauseMs` pause-release is armed in that configuration only, and is `.unref()`d). `CC_TEST_DWELL_MS` stays at **4000**; nothing was widened. The firing pattern and the read-back are one `HOLDER_LINE` const in the test file (no `g` flag — a global regex carries `lastIndex` across `.test()` calls), so the signal cannot fire on a line the assertion then refuses. `runGuard` also **throws** on `signalWhen` together with `discardStdout` — the rendezvous reads the accumulator `discardStdout` throws away, so that pair would proceed to a state where the signal could never be sent; pinned by `runGuard refuses signalWhen together with discardStdout` in the sweep file, because demoting the throw to a warning otherwise leaves the suite green.

**Residual (R1), stated rather than hidden:** the interrupt must still land mid-run, so one contiguous **>~4000 ms** stall of the *outer* test process's event loop — between the pipe becoming readable and the `data` handler running — would miss it.
Issuing the kill synchronously inside that handler is what keeps the window that tight, but it is a **description of the code, not an invariant**: a mutant deferring the kill via `setImmediate` survived with both legs green, because a late signal either still lands inside the fixture's dwell or the leg goes loud red down the healthy-end path.
Do not add an assertion pinning same-tick delivery.
Measured fixture-write→parent-observation latency at 72-way: **1–52 ms (n≈88, median ~12)**, a ~330× buffer on a term that was never the failing one, and the failure direction is a loud red (`code=1`, `trigger: run end`), never a silent green.
**No fallback timer or absolute cap was added, deliberately:** "wait N ms then signal anyway" *is* `signalAfterMs` renamed; the two bounds are different objects (1200 ms was a **lower** bound the green path had to clear, while a cap is an **upper** bound whose exceedance reds at *any* value, since the assertions fail either way); and the run is already bounded three times over — the fixture's 4000 ms dwell, then `CC_TEST_RUN_CAP_MS` 12 000, then `hardTimeoutMs` 20 000.
**Negative control** (point `HOLDER_LINE` at a pattern the fixture never prints): **3/3 runs red at 72-way**, each leg failing in **5.0–5.8 s** on the `no-holder-pid` assertion — exactly **one** AssertionError per leg, because `holderPidFrom` throws before any later assert runs, so the exit-code contract is violated (code 1, observed) as an *unreached* assertion rather than a second firing guard — with **no hang** — the construct holds the authority rather than relocating it.
Because `HOLDER_LINE` is single-sourced, that same neutering also reds the run-end sweep case that only *reads* the pid (3 failures per run, not 2), which is the drift it exists to prevent.
Post-fix, the real file went **0/20 red** at load1 73.2–74.5 / load5 65.8–70.7, with each interrupt leg completing in **0.99–1.44 s** — below the 1200 ms a fixed delay waits, because the signal lands when the marker does.
Dead alternative: an **open-ended dwell** (`await new Promise(() => {})`, so only the interrupt can end the run) removes R1 and measured **0/8 red**, declined because it slows the *broken*-path failure from ~5 s to `FILE_KILL` 8000 ms and adds an env knob for no measured gain.

**This does not contradict the rule "gate a rendezvous on the predecessor's process EXIT, not on its marker appearing"** — that rule is scoped to **duration differences**, where marker-gating leaves the predecessor's teardown+exit cost inside the quantity under assertion. These legs assert no duration at all: only ordering, an exit status, and a liveness fact. And the rendezvous target here must be **alive** when the signal lands, so exit-gating would guarantee the interrupt arrived after the run was already over. Marker-gating is not the weaker choice here, it is the only admissible one.

**Negative assertions ("X did not happen") — barrier + `settle()`, never a fixed sleep.** `await new Promise(r => setTimeout(r, 200))` before asserting an absence is both flaky (too short on a starved box) and weak (vacuous on a fast one, because nothing forced the thing you are asserting the absence of to have had its chance). Instead: `waitFor` on an observable that is **causally downstream of the decision under test**, then `settle(turns = 3)` from `tests/helpers.mjs` (drains queued micro/macrotasks via `setImmediate`; load-independent). `settle()` is **not** a barrier on its own — it cannot wait for work that has not been scheduled yet, so a `settle()` with no barrier in front of it is exactly as vacuous as the sleep it replaced. Worked examples across `tests/idle-wake-defer.test.mjs` (which owns the fire-or-defer barriers): the barrier is the target's turn_end handler having run (`waitFor(() => target.status === 'idle')`), because that same handler both sets the status **and** makes the fire-or-defer decision — so a wrong delivery is already queued and `settle()` puts it in the ring where the assertion sees it.

**The overage usage seams default to a non-network tripwire, not the live fetcher.**
`OverageResumeController.fetchUsage` and `UsageOverageMonitor.fetchUsage` default in production to the real `getAccountUsage`, so a fire-path test that forgets to inject makes a live `api.anthropic.com` request bounded by a 10 000 ms `AbortSignal` (`src/accountUsage.ts`) — racing the overage tests' own 10 000 ms `waitFor` budget.
So `tests/overage-action.test.mjs`, `tests/overage-turn-guard.test.mjs` and `tests/overage-backend-exempt.test.mjs` install `installUsageSeamTripwire(instances)` in `beforeEach` (both seams → one counting stub returning `null`, the existing "can't confirm" branch) and call `assertUsageSeamInjected(seam)` in `afterEach`, after `shutdown()`/`rmrf()`.
Both live in **`tests/overageUsageSeam.mjs`**.
A **throw** inside the stub would not work as the guard — both call sites swallow it into `usage = null` — hence count-then-assert.
`null` rather than an under-the-bar payload is deliberate: an un-injected test must not silently *work*.
When the assertion fires, inject what that test actually means (`setResumeUsage(UNDER)`/`(OVER)`, or `async () => null`); never relax the assertion.
**Each of the three files also carries its own usage-seam tripwire test calling `assertUsageSeamsInstalled(instances, seam)`** (`tests/overage-action.test.mjs` and its two siblings) — the wiring pin has to live in the same file as the wiring, because each `beforeEach` is independently editable and a sibling's assertion cannot see this one reverted (mutation-proven: without it, reverting either of the other two files' `beforeEach` to the live default survives the whole suite green).
That helper compares each seam against `state.fn` by **identity before invoking anything** — if the tripwire is absent the seam may be the real `getAccountUsage`, and calling it to find out would make the request the guard exists to prevent.
How an un-injected test then fails depends on its `resetsAt`, because `_reschedule` parks at `max(resetsAt, now + recheck)`: a **future** `resetsAt` (these files' usual `nowSec() + 3600`) parks ~1 h out, so the fail-open counter stalls at 1 and the body burns its full 10 s `waitFor`; a **past** `resetsAt` (the fail-open tests' `nowSec() - 100`, chosen so the counter *can* climb) fails open and lets the body pass, leaving the call count as the only detector.
Both regimes are offline and deterministic.

**A negative assertion needs a positive control, or it decays silently.** "No stub arrived" proves a timer was cleared only if a stub *would otherwise* have arrived. Pair the negative with an identical test that omits the cancelling step and asserts the event **does** land in the same window, and single-source the window constants so the pair cannot drift (`HEARTBEAT_SECONDS` / the derived `OBSERVE_MS` in `tests/idle-wake-interval.test.mjs` — module-local to that file precisely because it is the one file holding both halves of the pair). Verified by mutation: with the production heartbeat patched never to fire, the negative goes **vacuously green** and only the control goes red. Where an assertion genuinely requires a real timer to fire, a wall-clock window is unavoidable without a fake clock (an `src/` change) — widen it for margin, keep the control, and if it still flakes change the assertion rather than the number.

**DOM-vs-null assertions (`tests/dom-assert.mjs`).** Never compare a DOM node against `null`/`undefined` with `assert.equal`/`strictEqual`/`deepEqual` — use `assertNull(node, label)` / `assertUndefined(node, label)`. On failure node serializes `err.actual` across the per-file child-process boundary, walking a live happy-dom element's circular `ownerDocument`/`Window` graph: the file stalls **33–120s** and then aborts, so **every later test in it silently never runs**. Supplying a message makes it *worse*, not better (3-arg measured slower than 2-arg at the same site — `err.actual` crosses the boundary regardless), so the rule is unconditional on arity. `deepStrictEqual` never terminates at all: it grows unboundedly until the OS kills it (`exit 137` on a smaller device; **27 GB RSS** on a 30 GB host, killed by hand at ~2 min before the kernel acted), and `--max-old-space-size` does **not** bound it — do not raise that flag to chase the symptom. Reproduce **only** under a hard address-space cap, which does bound it because it cuts below V8's own accounting: `( ulimit -v 2000000; node repro.mjs )` aborts in **0.9s** with `exit 134` (SIGABRT) and never passes 2 GB. Without it the process consumes the whole machine, not just its own test run. The helpers compare without handing the node to `assert` and throw an `AssertionError({message, stackStartFn})` carrying only a short `<tag#id.class>` summary, leaving `actual`/`expected` `undefined` — that is what keeps the cycle off the wire. Always pass a `label` naming the element and its source (`'copy button must not be inside <pre>'`): nothing enforces it (a missing one just yields `undefined — expected null, found …`), but it is the whole failure message.

**Enforcing the DOM-vs-null rule — two guards, non-overlapping ownership.** A sweep fixed ~50 occurrences but nothing stopped re-accumulation, and only *failing* assertions stall, so a green suite hides the pattern. Both guards are needed; each module's header says why the other cannot be deleted as redundant.

- **`tests/dom-assert-scan.mjs` (+ `tests/dom-assert-guard.test.mjs`) OWNS the invariant** *no equal-family assertion in `tests/` is written against a DOM-valued expression.* It is the only guard that fails at authoring time on a site that currently **passes** — a latent site is invisible at runtime, which is exactly how the sweep's occurrences accumulated.
- **`tests/dom-assert-tripwire.mjs` GUARDS THE PATH, for one shape only:** *a DOM node compared against `null`/`undefined` by a positive equal-family assertion never reaches assert's serializer.* Preloaded into every per-file child via the `execArgv: ['--import', …]` option on `run({…})` in `tests/run.mjs`; it wraps only the positive family (`equal`/`strictEqual`/`deepEqual`/`deepStrictEqual` — `not*` can only fail when the operand is already nullish) and throws an `AssertionError` carrying just the `<tag#id.class>` summary. It covers DOM-ness the scan is structurally blind to. **Not covered, and still stalling 33–120 s:** a node compared against a non-nullish value (`assert.equal(node, 5)`, `assert.equal(el.parentElement, otherNode)`) and a node nested inside a compared structure. Do not widen the tripwire, because intercepting any node operand breaks legitimate node-vs-node assertions that currently pass.

The shared predicate `isDomNode` and the `describeFound` formatter live in **`tests/domNode.mjs`, which must have ZERO imports**: `dom-assert.mjs` imports `node:assert/strict`, and instantiating assert's ESM namespace during the preload is what creates the hole below.

**The scan is comment-stripped and paren-balanced, not a line regex.** A line regex both over-matches prose (`T3 pins: a multi-line prose comment naming assert.equal(node, null) is not flagged`) and misses multi-line-formatted calls (`T2 pins: the scan flags a DOM-vs-null assertion — multi-line-formatted call (a line regex misses this)`), both in `tests/dom-assert-guard.test.mjs`. `stripNonCode` blanks comments, string bodies, template *text* (`${…}` stays live) and regex bodies; **line numbers stay valid because newlines are preserved**, not because the output is the same length. The argument splitter then walks a `()[]{}` stack. **No JS parser is available** — `typescript@7.0.2` is the Go-native `tsgo` shim (exports only `version`/`versionMajorMinor`), there is no acorn/babel/espree, and `CONVENTIONS.md` forbids adding one.

**Scan direction, and why there is no allow-list.** Enumerating every legitimate primitive-vs-null comparison in `tests/` is intractable — they take too many arbitrary shapes and share no primitive signal. The scanner instead keys on DOM-*producing* signals in **tail position** — so `root.querySelector('a').length` correctly does not match. Receiver scoping on the `DOC_PROPS` and `PICKS` signal sets is load-bearing, not decoration: an unscoped `.body` produced the only false positives measured (5, all HTTP response bodies), and an unscoped `.find` conflates `[...root.querySelectorAll('.x')].find(…)` with `list.body.find(…)`. There is deliberately **no escape hatch**: a genuine future false positive is fixed by narrowing a signal constant in one place, never by an inline ignore comment.

**Measured recall: 46 of the 50 pre-sweep sites, at zero false positives across every legitimate primitive-vs-null comparison in `tests/`** (unchanged after widening `isDocumentReceiver` to accept a `.document` tail and adding the destructuring arm). Exact counts drift as unrelated changes add nullish assertions, so they are not restated here — `tests/dom-assert-scan.mjs`'s header carries a MEASUREMENT RECORD with the numbers, the sha and the date; re-derive with `scanTestsDir('tests')`. The 4 residual occurrences are 3 distinct expressions — `conv.emptyNode`, `main.leadingAssistantWrap` (×2), `batch.leadingWrap` — whose DOM-ness lives in source return values and is absent from the test syntax entirely. Two further shapes are **waived** known misses, named in the scanner's false-negative note: redundant parens around a whole call, and declare-empty-then-assign. **None of this is an oversight and must not be "fixed" with a name list**; the tripwire bounds them at runtime.

**The tripwire must use `createRequire(import.meta.url)('node:assert')`, never a static ESM import.** Measured: with `import assert from 'node:assert'` in the preload, a test file's `import { strictEqual } from 'node:assert'` **bypasses the patch** — the ESM namespace snapshot of the CJS named exports is taken when the preload instantiates it, before the patch lands. `createRequire` leaves the namespace uninstantiated, and all four styles (both modules × named/default) end up patched. Patch `assertObj.strict[k]` as well (`assert.strict` is `node:assert/strict`'s default export). Forward `arguments` (`orig.apply(this, arguments)`) — named parameters would turn `assert.equal(1)` into `assert.equal(1, undefined)` and lose `ERR_MISSING_ARGS`. If the preload itself throws, the child exits 1 before the body runs and `run.mjs`'s `test:fail` counter increments; it cannot silently no-op.

`tests/dom-assert-guard.test.mjs` holds T1–T11, each titled with the invariant it pins: tree-is-clean (T1), induced-violation recall across seven shapes (T2), comment/string immunity incl. the real prose comment (T3), `not*` never flagged (T4), historical-recall floor (T5), tripwire behaviour parity via two child processes over a 12-case table (T6), tripwire installed-and-fires via a node-*ish* plain object — never a live node, so an absent tripwire fails instantly instead of stalling (T7), `dom-assert.mjs` reads the shared predicate (T8), the predicate accepts a real happy-dom node (T9), all four import styles patched (T10), throwing-preload fails loudly (T11). **Cost:** scan ≈300 ms including its extra `node:test` child (~180 ms of blanking + matching over all of `tests/`); the tripwire's per-child cost is below the ±7 ms run-to-run noise floor; T6/T10/T11 add 4 child spawns ≈200 ms.

**ClaudeLauncher seam (in-process fake by default).**
`Instance` never calls `child_process.spawn` directly — it spawns through an injected `ClaudeLauncher.launch({command,args,cwd,env})` (`src/claudeLauncher.ts`), threaded `createServer({claudeLauncher})` → `new InstanceManager({claudeLauncher})` → `Instance`.
Production default is `RealClaudeLauncher(platform)` (a raw `child_process.spawn` with the platform's `child` spawn options — behavior byte-for-byte unchanged on POSIX); `resolveClaudeBin(platform)` and `resolveBackendLaunch(…, platform)` split through `platform.splitCommand`.
`src/claudeLauncher.ts` also owns the two pure launch-resolution primitives — `resolveClaudeBin()` (splits `CLAUDE_BIN` into `{command,prefixArgs}`; **unset, empty and whitespace-only all default to `claude`** — the empty case is what stock docker ships, and a default firing only on `undefined` made every spawn and the boot probe `spawn('')`; test injection via `CLAUDE_BIN="node fake.mjs"`) and `resolveBackendLaunch(backendRecord, model, claudeBin)` — so one-shot spawners that need no `Instance` (`health.ts`'s boot probe, `sessionOneShot.ts`'s one-shot call, `claudeShellEnv.ts`'s bundle-gen) can import just these without pulling in the 2000+-line `instances.ts`.
**Backend-agnostic spawn:** `resolveBackendLaunch` computes only command + prefix (plus the backend's `env`) from the **backend record**; every caller then appends the same claude args (including `--model <model>`) uniformly.
A blank `template` returns the resolved claude bin's `{command,prefixArgs}` unchanged; otherwise the template is whitespace-split with `{model}` substituted **inside each token** (so `--model={model}` works too), token 0 becoming the command and the rest the prefix — e.g. the built-in `ollama` row yields `['launch','claude','--model',<model>,'--yes','--']` (the model also rides in the forwarded `--model` — a harmless no-op duplicate).
Because templates are DATA, there is no per-command env shim: a test pointing a backend at a fake binary just registers a row whose template names it.
The helper owns the **null-model invariant** — it throws whenever the template is non-blank and no model resolved (unconditional on the template shape; see the create-time guard below), rather than emit `--model undefined` — so `Instance.spawn()` wraps the call in a try/catch only to add its own `_setStatus('crashed')` side effect before rethrowing.
A backend needing a non-default host sets it as an `env` pair on its registry row (e.g. `OLLAMA_HOST`) rather than through any dedicated plumbing.
Only `model` + `backend` thread `create()→_doCreate→Instance ctor→spawn()`; both appear in `summary()` (so the resume manifest carries them) and survive an in-place `/clear` renewal.
On resume, `backend` is recovered from the `backend` on the session's record in `<store>/sessions.json`; `model` is recovered from that same record on every backend, `claude` included — the record holds the exact tagged id (the jsonl `message.model` is bare — tag dropped by the inner CLI — so a jsonl-only recovery would relaunch the unpullable tagless name) and follows every model change, while the jsonl names the previous model until a turn runs on a new one.
The jsonl (`readLastSessionModel`) is the fallback only for a session with no record (which reads as `claude`) or a model-unknown one.
There is **no** spawn-time reachability preflight — a bad backend or model fails at launch, and a subprocess on a substitution backend that terminates on its own emits a `system/launch_failed` event (`_handleExit`, gated by a `_killing` flag so a commanded kill isn't mislabeled).
`stderr` on that event carries what the wrapper wrote **if it ran**; for a wrapper that never started there is none (`stderr: null`, `code: -2`) and the reason rides on the preceding `spawn_error` — that sub-case reaches `_handleExit` only via the terminal latch (see [Instance lifecycle](architecture.md#instance-lifecycle)).
That event is therefore the only failure signal for a misconfigured backend.
Four create-time guards still fire before any spawn: `422 BACKEND_MODEL_MISSING` when a substitution backend has no resolvable model (unconditional on the template shape — the model also rides in the forwarded claude args and drives the context-window env, so a template that omits `{model}` is no exception), `422 BACKEND_GONE` when the named backend isn't in the registry, whether it came in explicitly or from the session's recorded backend, `501 FUSE_LAUNCHER_UNRESOLVED` when the session is on a system and `resolveOnPath(resolveClaudeBin().command)` is empty — that path is the union's marking event and the CLI's only host pin, so it is a refusal rather than a degraded spawn; exempt on an `inProcess` launcher, which has neither — and `501 FUSE_BACKEND_UNRESOLVED` when the session is on a system and `resolveOnPath(resolveBackendLaunch(…).command)` is empty.
The last is **diagnosis, not pin correctness**: that command is exec'd by `setpriv` before the CLI and runs unmarked throughout, so it needs no host pin (gate arm `R14L`) — but an unresolvable one dies inside the chroot naming nothing, and the spawn seam knows the token.
It sits after the model is settled, because `resolveBackendLaunch` refuses a model-less substitution launch; same `inProcess` exemption, and for the `claude` backend the token is the one `FUSE_LAUNCHER_UNRESOLVED` already checked.
`Instance.spawn()` re-checks the record and refuses a null one, so a row removed under a live instance crashes it visibly instead of falling into resolveBackendLaunch's identity branch and launching the real `claude` with a foreign model id.
"Change model" enters through `Instance.switchModel`: only Claude→Claude goes live (`Instance.setModel`, between turns — mid-turn it refuses `409 SESSION_BUSY` before writing the control request; called off `claude` it throws a plain invariant `Error`), because the running endpoint is fixed at launch.
Every other pair, same backend or not, restarts the CLI onto the target backend's template and model; a target backend no longer in the registry is refused `422 BACKEND_GONE` ([models.md](models.md)).
**`bootServer()` defaults to `InProcessClaudeLauncher`** (`tests/inProcessLauncher.mjs`): the fake-claude engine runs on the event loop against in-memory `PassThrough` streams — **zero OS subprocesses per instance**.
This is the forget-proof default (an Android phantom-process-killer defense: the app UID is killed above ~32 processes), so a normally-written test forks nothing.
The in-process handle is a `FakeChildProcess` (EventEmitter + 3 PassThrough + `pid=null`); it defers engine start to `setImmediate`, gates `'exit'` on the readable-side `'end'` of stdout/stderr (so a trailing `turn_end` is never delivered after `'exit'`), and maps `kill('SIGKILL')` → `exit(null,'SIGKILL')`, `kill('SIGTERM')`/`stdin.end()` → graceful `exit(0,null)`.
`pid=null` makes the manager's OS-`process.kill` sync-shutdown path (`shutdownForResumeSync`) a safe skip and gives the running record no `clis` row.

The fake-claude **scenario engine** lives once in `tests/fake-claude-engine.mjs` (`runFakeClaude({argv,env,cwd,stdin,stdout,stderr,onReaderReady})`): silent until first stdin message, auto-acks `control_request`s, emits canned events from `env.FAKE_CLAUDE_SCENARIO`, matches `control_response`s so scenarios can branch on allow/deny. `env.FAKE_CLAUDE_ARGV_DUMP` / `FAKE_CLAUDE_ENV_DUMP` capture the launch argv / computed child env; `FAKE_CLAUDE_TRANSCRIPT` records stdin. A scenario's `"strict_resume": true` (e.g. `tests/fixtures/scenario-resume-strict.json`) makes `--resume <id>` exit 1 with `No conversation found with session ID: <id>` when the transcript holds no user/assistant line, as the real CLI does — opt-in, since the fake writes no transcript. `"plugin_skills": true` (`tests/fixtures/scenario-plugin-skills.json`) makes the top-level `system`/`init` list each `--plugin-dir` root the way the real CLI does: `plugins` gains `{name, path, source: '<name>@inline'}` from the root's `.claude-plugin/plugin.json`, and `skills` gains `<name>:<d>` for every `skills/<d>/SKILL.md`; `--plugin-dir` is read only for this. `bootServer` sets `instances.relaunchGraceMs = 50` (copied onto every `Instance` the manager constructs) unless `useRealClaude`, so a rewind/prune response does not wait out `RELAUNCH_GRACE_MS`. It reads everything from its params (not `process.*`), so the same engine drives both the in-process launcher and the thin subprocess entrypoint `tests/fake-claude.mjs`. Config flows through `env` (bootServer sets `FAKE_CLAUDE_SCENARIO`), and for the in-process path `CLAUDE_BIN` is a **bare sentinel** (`claude`, no script path) so `resolveClaudeBin`'s `prefixArgs` stay empty and the argv the engine sees equals the real CLI flag set.

**`bootServer({claudeLauncher})`** injects a custom launcher (e.g. `ControllableLauncher`, `tests/controllableLauncher.mjs`, whose child stays alive until the test triggers a spontaneous `crash()` or a `kill()`, and whose `crashNext` / `failNext` arm a startup crash / a spawn that never started) to exercise post-launch crash paths. `ReplayLauncher` (`tests/replayLauncher.mjs`) replays a captured CLI stdout stream on its captured schedule for a launch whose env carries `CC_TEST_REPLAY_CAPTURE=<fixture>` (other launches go to its delegate); `tests/autoBackgroundReplay.mjs` is the owner/worker/wake-recorder rig over it, fed from `tests/fixtures/auto-background/`. A test needing a **substitution backend** that reaches a real fake binary registers a registry row whose `template` names it (`addBackend`) — templates are data, so that is the injection seam; there is no per-command env shim.

**`bootServer({realProcess:true})`** opts a test back into a real `node fake-claude.mjs` subprocess (`RealClaudeLauncher`) — needed only where a test uses a real `.pid` / OS `process.kill(pid)`: the `instances.test.mjs` crash+respawn test. It opts in per-test (booting its own dedicated realProcess server) so the rest of its file stays in-process. `ControllableLauncher({realProcess:true})` is the lighter way to a real pid: each fake child is backed by a real idle `node` process, `kill()` signals it, and `orphanAll()` detaches them all so teardown leaves them running — a crash of cc, for the orphan-CLI reap (`orphan-cli-reap.test.mjs`); `onLaunch(spec)` observes every launch. **`bootServer({home, keepHome})`** boots on an existing tmp home and leaves it on disk at `close()` (also `close({keepHome})`), so two boots in a row share one store, as a restart does; it also returns the server's `runningRecorder` and `pendingContinue` (built, not started). `shutdownForResumeSync` is graceful (`stdin.end()`), so `resume-after-restart.test.mjs` stays fully in-process.

**`tests/fake-claude-auth.mjs`** is the separate fake for `claude auth …` (the session fake does not speak it), run as `CLAUDE_BIN="<node> tests/fake-claude-auth.mjs"`. **Hand-editing `settings.json` in a test — do it BEFORE the first `appSettings` call under that root.** `appSettings` caches the parsed document keyed by `settingsPath()`, so the cache goes cold exactly once per `freshProjectsRoot()` and a direct `fs.writeFile` **after** any read or write through the module is never seen. A test that plants a malformed shape and then asserts on it therefore asserts against the pre-edit state — i.e. against nothing, silently green even with the code that handles the shape deleted. Measured: two `tests/systems-registry.test.mjs` cases written that way (a stored row shadowing a managed id; duplicate ids) passed against the unfixed code both times, and only started failing once the seed moved ahead of the first API call (`seedSettings` in that file). This is the same "it passes for the wrong reason" trap as the mutation checks elsewhere in this section — a test over a cached store must control when the cache is seeded.

**System-seam interception** (`tests/systems-seam.test.mjs`). Two escape hatches, two techniques, and the difference matters if you write another test like this. `fs.promises` is ONE shared object and src modules call `fs.readFile(…)` by property lookup, so wrapping its methods is visible to already-imported code (the same trick `withFirstLstatMissing` in `tests/systems-remote-config-dir.test.mjs` uses to inject an `lstat` failure). `node:child_process` is NOT: an ESM `import { spawn }` binds the function at instantiation, so patching `require('node:child_process').spawn` afterwards is invisible to a module that was already loaded — **measured, both directions**. The test therefore patches first and imports every src module DYNAMICALLY, and must not statically import any of them. Attribution is per call via `new Error().stack` (with `Error.stackTraceLimit` raised — the default 10 frames can cut the frame being looked for): a call is a leak unless a `systems/localSystem.ts` frame sits beneath it. The fixture is an ADOPTED project, so the project tree and cc's own paths occupy disjoint path spaces and "reached the project tree" is a pure prefix test.

**Compile cache** (`tests/compileCache.mjs`, wired once in `tests/run.mjs`'s pre-fork block). `NODE_COMPILE_CACHE` is pointed at `<repoRoot>/.compile-cache` (gitignored) before any child forks, so every test child — `npm test`, both `gate:systems` rows, every mutation iteration — reuses the V8 compile + type-stripping of the `helpers.mjs → server.ts → src/*.ts` graph instead of redoing it. Measured: importing `tests/helpers.mjs` in a bare child ~220 ms uncached against ~120 ms cached; a whole gate 166.9 s / 973.6 s CPU with the cache off against 143.4 s / 717.3 s with it on, back to back. **Shared and persistent** on purpose — a per-run directory pays the cold compile every time — and **per worktree**, because a shared `os.tmpdir()` location would let one checkout's size-bound wipe delete entries under a sibling's live run. Bounded by `COMPILE_CACHE_MAX_BYTES`, which wipes the directory (Node recreates it lazily) and prints a `compile-cache: reset` line; that is the only line it ever prints. Node's cache is **path-keyed and overwrites** (verified on v24.18.0), so an in-place mutation campaign replaces one entry per mutant rather than adding one. `CC_TEST_COMPILE_CACHE=0` is the opt-out; a **pre-set `NODE_COMPILE_CACHE` wins verbatim and is never walked or wiped** — we do not delete a directory we did not choose.

**Process-count guardrail** (`tests/run.mjs`): samples the peak concurrent `fake-claude.mjs` subprocess count (~100 ms) and fails the run if it exceeds a process-count budget `FAKE_CLAUDE_BUDGET` (`tests/run.mjs`) — catching a regression that flips the default back to subprocess or a new test that spawns real processes without `realProcess:true`. A clean default run peaks at ~2–3 (only the realProcess opt-in tests). **The count is scoped to this run's descendants** (`censusMatching`, `tests/procTree.mjs`): a `/proc/*/cmdline` match is narrowed by `CC_TEST_RUN_ID` in `/proc/<pid>/environ`, so concurrent suite runs on one box — a sibling worktree, or the two `gate:systems` rows — do not count each other's children. Measured before the fix: two concurrent runs, both `fail 0`, both exit 1 at peaks of 14 and 15 against a budget of 12. Only the cmdline matches get an environ read (the sampler ticks over every visible pid, so a read per pid would regress it), and the box-wide peak is printed as a second `guardrail:` line whenever it exceeds the counted one — `hasMarker` fails closed, so a counted figure collapsing against a high box-wide one is the guard going blind, not a clean run. Enforcement is skipped under `RUN_REAL_CLAUDE=1` and when `/proc` is unavailable. It reads `/proc` through `tests/procTree.mjs`, the suite's single `/proc` reader (one `snapshot()` per sampler tick answers every question the tick asks, so the answers cannot disagree mid-tick). (Use `/proc` reads only here — `pkill`/`lsof` misbehave on this host.)

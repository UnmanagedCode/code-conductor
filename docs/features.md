## Features

### Projects & workspaces
- **Project list** — sidebar shows every dir under `<projectsRoot>/`, plus every symlink under `<projectsRoot>/.external/` (see **Out-of-root projects** below). `+ New project` creates a dir, `git init`s it (no commit), and seeds `CLAUDE.md` containing exactly `@CONVENTIONS.md` — the import of the regenerated in-project conventions file that carries both workspace and project conventions (see **Conventions** below), written whether or not any project convention was picked. Worktree-owned dirs are hidden from the list (filtered against a Set built from the central store). The list also carries every project placed on a **system** (see **Projects on a system** below) — those have no directory here, and their record is what registers them.
- **Delete project** — `×` per row, typed-name confirm; cascades through instances + worktrees then `rm -rf`s the project. **An adopted or system-placed project is only UNREGISTERED** — `fs.unlink` on its `.external/<name>` symlink, or the record cleared; its repo, contents and history are never touched, and its worktree directories and branches are left in place too. The confirm dialog says so before the click — it reads *Unregister*, names what is being left behind (and which system it is on), and never promises a removal. `~/.claude/projects/<encoded>/` jsonls are left intact (still resumable by the standalone CLI).
- **Out-of-root ("adopted") projects** — a repo that already exists anywhere on disk becomes a project without being copied or moved. MCP `adopt_project({name, path})` / `POST /api/projects/external` (no UI affordance).
  - **Layout** — the record is a symlink at `<projectsRoot>/.external/<name>` → the target. Nothing else is persisted; the store entry at `<store>/projects/<name>/` is keyed by name as for any project. `.external/` is created on the first adopt.
  - **Paths are REALPATHS.** `resolveProjectDir` / `getProject` (`src/projects.ts`) hand back the target's realpath, never the symlink, and `list_projects` / `GET /api/projects` report that. Load-bearing: the Claude CLI encodes its `~/.claude/projects/<encoded-cwd>/` session dir from `getcwd()` (always the realpath) and walks `CLAUDE.md` upward along the realpath, with no env lever — a logical-path project would strand every resume.
  - **Refusals** (returned as `{ok:false, code, reason}`, never an error): `INVALID_NAME` (bad charset, or dot-leading — reserved for orchestrator-managed projects, which is what stops an adopted repo shadowing `.conduct`), `INVALID_TARGET_PATH` (not a non-empty absolute path), `TARGET_NOT_FOUND`, `TARGET_NOT_A_DIRECTORY`, `TARGET_ALREADY_MANAGED` (inside the projects root, or already adopted under another name), `TARGET_NOT_A_REPO` (not a git repo, or a *subdirectory* of one — `reason` names the toplevel it found), `PROJECT_EXISTS` (the name is held by an in-root or adopted project), **`SESSION_ROOT_COLLISION`** (only with a `system`: the name's session-root key is already taken on that system by another project or by a registered worktree — `reason` names the holder). Every check runs before the symlink or record is written, so a refused adopt leaves nothing behind.
  - **cc writes into the adopted repo, at adopt time.** `<target>/CONVENTIONS.md` is created/overwritten with the composed document (app-owned, no sentinel), and `<target>/CLAUDE.md` gains an `@CONVENTIONS.md` line — prepended, every existing byte kept below it; already present ⇒ no write at all. That is the only channel the workspace conventions have, so it is unconditional and not skippable; **both land as uncommitted changes in the user's repo.** Recomposition is a pure function of the selections, so repeat sweeps are byte-identical and the repo is dirtied exactly once.
  - **Worktrees live under `.external/`** — `<projectsRoot>/.external/<name>_worktree_<id>`, beside the project's *record* rather than beside the target repo: a literal sibling would put a cc-owned, cc-deleted directory in the user's own parent dir. They never surface as projects (only symlinks in `.external/` are listed).
  - **A broken link is skipped, not fatal** — a target that was unmounted, moved or deleted drops out of `list_projects` and the rest of the list still renders.
- **Projects on a system** — a project's tree, git repo and shell commands can live on a registered **system** (Settings → Systems) instead of on the machine cc runs on. A third placement: neither in-root nor adopted.
  - **A system is an endpoint; a TARGET is what it serves.** One registered system can serve many targets — one `docker exec` provider talks to the daemon on behalf of every container — so ten containers are one Settings row and one provider process, not ten of each. Which target a project is on is chosen **per project**, by its `remoteId`, and all three of `(system, remoteId, path)` together identify a tree: the same path on two targets of one system is two different projects. **Absence of `remoteId` means the provider's own default target**, exactly as absence of `system` means cc's own machine.
  - **Creating one** — `+ New project` offers a **System** picker (the built-in **This machine**, the default, plus every user row that has a provider command — a row with none is skipped, since a project on it could never be opened) and, when one is chosen, the absolute **path on that system** plus an optional **Remote** (the target's name — a container name, a hostname, a VM id; left blank for the provider's default). The `mkdir`, `git init` and seed files all happen there; under the projects root there is no tree, no directory and no symlink — only the `<store>/projects/<name>/` record, which IS the registration. Adopting an existing repo on a system is `adopt_project({name, path, system, remoteId})` / `POST /api/projects/external` — every check (realpath, directory, git-repo-ROOT) runs on that target.
  - **Changing the target** — `set_project_remote({project, remoteId})` / `PUT /api/projects/:name/remote`, or the **Change target** dialog behind a remote project's **system pill** in the sidebar (the pill reads `<system>/<target>`; it is a control only when the system is reachable, since the change verifies the new target there before persisting). `remoteId:null` (or `""`) clears it back to the provider's default; **omitting the field is refused**, not read as a clear. It is **refused 409 `PROJECT_PLACEMENT_IN_USE`** while the project has live sessions or registered worktrees, and the refusal **names whichever of the two is blocking** (the parts are `Boolean`-filtered, so a project blocked only by worktrees is not told about sessions) while the 409 BODY always carries both `instances` and `worktrees` arrays — kill the sessions and delete the worktrees first; nothing is discarded for you. A permitted change discards the project's local session root, so the next spawn re-pulls its config surface from the new target rather than reading the old one's.
  - **`remoteId` is not a slug** — container names, hostnames and VM ids legitimately carry `_` and `.`. It must be non-empty after trimming, at most `REMOTE_ID_MAX` characters (`src/projects.ts`), and free of whitespace and control characters. A `remoteId` with no `system` is a 400: cc's own machine is one machine.
  - **Layout** — the record IS the registration: `<store>/projects/<name>/project.json` carries `system` + `remoteId` + `systemPath`. No directory, no symlink. Names stay globally unique, and the same path on two different targets is two different projects.
  - **What works** — worker sessions (below), the project list and its git facts, worktrees (created **on the system, beside the tree**), diff, status, merge, sync, the **in-tree** `post-worktree-create.sh` hook, conventions materialisation, and every `project_*` tool.
  - **What does not** — `project_bash` runs in a plain login shell there (claude's own restored shell bundle is a file on cc's machine). A **store-sourced** `post-worktree-create.sh` is skipped with `STORE_HOOK_LOCAL_ONLY` in its own report — it lives under cc's store, and putting a cc-owned file on the system is a later phase; the in-tree hook works. Plugin **backends** and repo-tracked **`claudePlugin` dirs** stay local-only — see [plugins.md](plugins.md).
- **Worker sessions on a system** — spawning works exactly as on a local project; what changes is where the worker's tools land. The `claude` CLI always runs on cc's machine (a system cannot be assumed to host node or Claude credentials), so cc gives it a **local session root** to work in and redirects the tools that touch the project.
  - **The session root** — `<store>/systems/<id>/sessions/<project>[--<worktree>]/`, cc-owned, keyed so two systems each hosting a project at `/app` cannot collide. **Two places on one system cannot share a key**, and that is enforced at CREATION: `--` is legal inside a project name, so `p--p_worktree_w` would otherwise compute the same key as worktree `w` of project `p` — one root, one manifest, one transcript directory, each place silently reading and listing the other's. Creating or adopting a project, or creating a worktree, whose key is already taken on that system is refused (**`SESSION_ROOT_COLLISION`** / **409**), naming the holder. The comparison is over `encodeCwd`-equal keys, not byte-equal ones, so it also refuses `my_app` beside `my-app` — two roots whose sessions would **normally** land in one transcript directory. Only normally: the CLI's cwd also carries the provider's mirror offset, which the key comparison never sees, so this is a proxy and not a complete test for a shared transcript directory. Local projects have no session root and are not covered. Its manifest records **which target it was pulled from**, and a change of target **wipes the whole root and re-pulls**: a root kept across a target change would hand the worker the old machine's `CLAUDE.md`, `CONVENTIONS.md` and cached file content, and the write-back would push its edits to the new machine. It is a **sparse image, never a copy of the tree**: what is pulled ahead of time is only the config surface the CLI reads implicitly and cannot hook — `CLAUDE.md`, `CONVENTIONS.md`, one level of `@`-import, and `.claude/{settings.json,settings.local.json,skills/**,commands/**,agents/**}` — one way from the system before every spawn and resume. An entry over a cap is **skipped and named** rather than failing the spawn — per-file bytes, total bytes, and a 2,000-entry cap on how many entries are pulled at all, the last reported as one summary line naming the first entry dropped and a per-directory count. `CLAUDE.md`, `CONVENTIONS.md`, both `settings*.json` and every `@`-import are pulled before that cap applies, so a project with thousands of skills still gets the surface a session cannot work without — up to the separate 8 MiB listing fence (~92,000–112,000 entries at ordinary path lengths), past which the spawn refuses rather than degrading. A worker that writes a new skill mid-session sees it at the next spawn, exactly as locally. A session that ran in one is **locatable by `sessionId` alone**: `spawn_instance({resume})` with no `project` recovers the project and worktree from where the transcript is, not from any record, and its transcript is READ from cc's own disk — the read still works while the system is unreachable, where the RESUME refuses by name with whichever of the addressed-by-name refusals below applies, because a worker there needs the box and a read does not.
  - **How wide the image is, is the provider's to say.** A provider may advertise a **mirror root** and an **exclude list** for each target (`describeRemote`, [systems-protocol.md §2.1](systems-protocol.md)). Advertise nothing — the default, and every provider that predates the frame — and the image is the project root's, exactly as before. Advertise a root **above** the project and the session root becomes the image of *that*, with the CLI's working directory moving to the project's place inside it: a worker can then `Read`, `Write` and `Edit` a file **outside the project tree** (`/etc/app/config.toml`, a sibling checkout) at its counterpart path, pulled and pushed the same way a project file is. The manifest records the mirror root beside the target, and a change to either **wipes the root and re-pulls**. A **mirror-root** change also **moves the CLI's working directory** (a `remoteId`-only change re-pulls and moves nothing), and a live session **is moved to the new geometry at its next relaunch** — working directory, file-tool path map and transcript together — and told so by name on its event stream. A relaunch that cannot complete the move is **refused** rather than started, leaving the session where it was. A session resumed **cold** — by the boot restore after an orchestrator restart, or by resuming a session that is no longer running — is moved at its **resume** instead, so the two paths agree and a restart no longer leaves a session stranded at the old working directory; a cold resume that cannot complete the move is refused the same way, with no worker started and no session registered. This only happens when the relaunch **re-asks** the provider (a new connection generation, i.e. after a provider restart) and gets a different answer. **Each session moves at its own next relaunch**, so another session still running on the project stays at the old working directory until then; a session that is neither relaunched nor resumed is never moved. A change to the system's launch argv alone announces nothing to a live session: its placement keeps the system handle captured at create and re-asks nothing. The allow-list walk does **not** widen with the mirror — it stays anchored at the project over its fixed targets, whatever the mirror root is. Refused by name at spawn: **501 `MIRROR_ROOT_EXCLUDES_PROJECT`** (the advertised root does not contain the project — cc will not narrow the mirror to fit), **501 `MIRROR_EXCLUDE_COVERS_PROJECT`** (an exclude covers the project itself), **502 `MIRROR_ADVERTISEMENT_INVALID`** (a malformed or non-normalised claim, quoted back). An exclude *outside* the mirror root is inert and reported on the session's event stream, once per launch — never a refusal.
  - **An excluded path is refused, and the refusal says so.** `Read`/`Write`/`Edit`/`NotebookEdit` on a path under an advertised exclude are denied with a message that names cc as the actor, names the excluded **prefix** (so the answer generalises), states twice that this is cc declining to carry the file and **not** the file being absent, and points at `Bash` — which runs on the system under no such restriction — with `cat`, `sed -i` and `>` as the verbs. A worker that read the refusal as "not found" would conclude the file does not exist instead of using the channel that works.
  - **`Bash` runs on the system** — **one fresh shell per command**, exactly as locally: each local `Bash` call gets a brand-new shell and the CLI resets the working directory to the project root (measured on CLI 2.1.258), and a redirected one behaves the same way. So nothing carries between two commands — not `cd`, not `export`, not a shell function, and not between agents in either direction. **A command that ends somewhere else is told so**, on stderr after its output: cc names where it ended and where the next command will start, because a `cd` that silently vanished is worse than one that is announced. Commands that did not move the working directory are told nothing, matching a local session's silence. **Output streams as it arrives**, not at exit: a long build or test run is visible while it is still running, and a backgrounded command's output accumulates in its task file as it goes rather than appearing at exit. stdout and stderr stay on their own descriptors, and the exit code is still the command's own. A command that dies without finishing still delivers what it printed first. **Commands run concurrently** — nothing takes a turn, so two agents' commands, or a session's own, overlap freely. **A command's own `timeout` does not cut it short**, exactly as locally, where a foreground Bash past its `timeout` is handed to you as a background task and keeps running — a redirected one is handed over the same way. That it then **keeps running on the system** follows from cc never being told to stop it, and has not been observed directly — treat it as the expected behaviour rather than a verified one. cc is not even told the number and needs it for nothing. What does bound it is cc's per-command ceiling, set just over the built-in Bash tool's **documented** maximum so it never cuts short a command that tool would still be waiting for — a `timeout` above that documented maximum is untested territory, and `ORCH_SHELL_COMMAND_TIMEOUT_MS` is the knob that raises cc's ceiling back above it.
    - **Output is fenced at 8 MiB per command.** Past it the command is killed and the call fails, naming the limit — cc accumulates a command's output in its own memory while it runs, and a truncated success would be read as the command's real output.
    - **Interrupting cancels that call and nothing else.** A call cancelled before it crosses never runs on the system at all; one already running is stopped there, through its own command's kill signal — so a concurrent command is untouched. Ending the session stops every command it still has running, rather than leaving them to finish on a machine nobody is reading.
    - **A backgrounded job returns immediately and outlives its command, as it does locally**, and the command still reports its own exit code and its own output. Every shape behaves the same way — `cmd &`, `cmd & disown`, `setsid cmd &`, and `nohup cmd &` **with or without** an output redirect — so there is no form to prefer and nothing to work around. (`nohup` alone diverts a TTY, not a pipe, which is why the redirect used to matter.) **Measured on cc's reference provider** — same-host and across a real container boundary, in both capability configurations (card 2026-0318 §1, §G5); a third-party provider is not covered by that measurement. Before the fix a job holding the command's stdout open kept the provider from ever reporting the command's exit, and a command that exited 0 reached the worker as a failure with an empty stdout, minutes late; cc now settles a redirected command on **its own framing sentinel**, which is where the output ends by construction.
  - **`Read`/`Write`/`Edit`/`NotebookEdit` work at their local paths.** cc fetches the file from the system before the tool runs and pushes the result back after. Nothing is rewritten to a system path: the CLI opens files on its own machine. A **failed push is a hard failure** — the divergence is named on the tool result, raised as an error in the session, and every further write to that path is refused until the file is read again.
  - **`Glob`/`Grep` are unavailable.** A search cannot be redirected (a tool result can be annotated but never replaced), so they are removed and refused; `find`/`grep` through `Bash` answer about the right machine. The cost is coverage confidence, not correctness.
  - **Anything outside the boundary is refused**, by name: a file tool aimed at a path that is neither in the session root nor somewhere cc knows is local (attachments, `~/.claude`, plan files) would write to the orchestrator's disk where no command on the system can see it. The refusal boundary and the mirroring boundary are the same two fields on the same object, so they cannot drift. When the refused path *does* have a local counterpart — a worker naming a system path directly, which is the common mistake — the refusal **translates** it, handing back the local path to use instead of only declining.
  - **The worker is told**, in two sentences at the top of the project's `CONVENTIONS.md`: where the tree is, that `Bash` runs there, and that it must read, write and edit files at their paths under the session's working directory and **never** at their system paths, which name the same files seen from the system. It deliberately makes no claim about *where* a system path can appear — cc's own write-back note puts one on a tool result — so the prohibition is what carries the behaviour, true wherever the path came from. It says nothing about shells or where a command starts: that is delivered at the point of use, by the notice on the one command whose `cd` was discarded. Command output that mentions the system path also carries a one-line note saying the same thing.
  - **Refused before it starts** — **501 `REDIRECT_HOOKS_DISABLED`** when any scanned settings file sets `"disableAllHooks": true`. That switch turns the whole redirect off: the worker's commands would run on the orchestrator's machine while every result claimed the system, and no edit would reach it — and because it leaves `permissions.*` working, nothing else would fail loudly. **501 `BASH_RULES_NOT_ENFORCEABLE`** when a `Bash(…)` pattern rule appears in `permissions.deny`/`ask`. Both scan the same files: the session root's `.claude/settings*.json` (pulled from the system), `~/.claude/settings.json`, and `/etc/claude-code/managed-settings.json`. Redirection rewrites every command into one forwarder invocation, so the CLI — which matches rules against the rewritten command — could no longer tell two commands apart and the rule would apply to nothing. cc does not reimplement the matcher; it names the rules and their files and declines. **501 `WORKER_SESSIONS_NEED_A_SHELL`** when cc cannot run a command on the system at all. Three more come from the mirror advertisement — **501 `MIRROR_ROOT_EXCLUDES_PROJECT`**, **501 `MIRROR_EXCLUDE_COVERS_PROJECT`**, **502 `MIRROR_ADVERTISEMENT_INVALID`** — described under **The session root** above. All of these refuse the SESSION and nothing else: the project keeps its row and every `project_*` tool still works, because none of them consults the mirror.
  - **When the project cannot be resolved** — an unregistered system, one with no provider command, one that is down, or a record naming a system with no `systemPath`: the project **keeps its row** in every listing, carrying `systemUnreachable` with the reason; its git facts are absent rather than invented. The sidebar row shows a red **system pill** with the refusal in its tooltip and hides the controls that would fail; delete stays, and works — unregistering never reaches the system, at any layer, so a project on a system that is down (or one whose record is malformed) is never stranded holding its system row at 409. Its worktree **registrations still list** — they are cc's own records and need no system — with their divergence unknown rather than invented. Addressed-by-name calls refuse: `SYSTEM_NOT_REGISTERED` (501), `SYSTEM_NO_PROVIDER` (501), `SYSTEM_UNREACHABLE` (502), **`SYSTEM_NO_REMOTES`** (501 — the record names a target but the provider does not serve named targets; drop the target or upgrade the provider) and **`REMOTE_NOT_FOUND`** (502 — it does serve targets, but not this one: the container is gone, or the name is a typo). The two new codes are raised at creation and at every resolution, so a bad target is refused before anything is written and again on every later use. A system that dies MID-operation refuses the same way rather than reporting a git answer, and `merge_worktree` adds `mayHaveCompleted` when the transport dropped after `git merge` was issued — cc cannot know whether it landed.
- **Workspaces** — `≡` hamburger menu hosts `+ New workspace`; nest projects under collapsible `<details>` headers, one workspace per project, empty workspaces persist. Edit (rename / re-pick members / delete) via the ✎ button on each header. Workspaces default-collapsed; expand state persists in `localStorage` (`code-conductor:workspaces-expanded`). Stored server-side at `<store>/projects/<name>/project.json`; the workspace set is the union of `<store>/workspaces.json` and any referenced names. Workspace names use the same `^[a-zA-Z0-9._-]+$` charset as project names, capped at 40 chars and barred from starting with `.` (`^[a-zA-Z0-9_-][a-zA-Z0-9._-]{0,39}$`), so a name stays safe as a path segment.
- **Resizable sidebar** — desktop grid layout only (>720px). A drag handle on `#sidebar`'s right edge (`#sidebar-resize-handle`) resizes the column live via the `--sidebar-width` CSS variable (default `280px`), clamped to 220–560px. Persisted in `localStorage` (`code-conductor:sidebar-width`). Hidden below the 720px breakpoint, where the sidebar is a fixed-width slide-in drawer instead.
- **Git status pill** —
  - **Project rows**: amber `↑N ↓M` against the currently-checked-out branch's *configured upstream* (e.g. `origin/<branch>`), using cached refs only (no `git fetch`). No pill when in sync / detached / upstream-less.
  - **Worktree rows**: same shape but compares the worktree branch to its captured *parent base branch* (may be a local branch, not a remote). `↑N` = ahead and FF-able, `↓M` = behind and FF-able, `↑N ↓M` = diverged → rebase needed before merge.

### Worktrees
- **Isolated environments** — "Run in isolated git worktree" checkbox in the new-instance dialog runs `git worktree add ../<project>_worktree_<short-id> -b code-conductor/<short-id> <currentSha>` and spawns the agent with `cwd` set to the worktree. (An **adopted** project's worktrees go under `<projectsRoot>/.external/` instead — see **Out-of-root projects** above.) The orchestrator captures `{baseBranch, baseSha, branch}` at creation so you can spawn off any branch and land back later. Worktrees survive instance death — re-spawn into the same worktree from the sidebar. The checkbox is disabled with the reason in its hint when the project is not a git repo **or** is a repo with no commits yet (`unbornHead`); the sidebar flags the same state with a `no commits` pill on the project row.
- **Named worktrees** — MCP `create_worktree` / `spawn_instance({createWorktree:true})` accept `name`, slugified (lowercase, non-alphanumerics → `-`, trimmed, capped at `SLUG_MAX_LEN` in `src/worktrees.ts`) into `code-conductor/<slug>` + `<project>_worktree_<slug>` in place of the random 6-hex id. A name with no usable characters is refused **400**; a slug whose branch `code-conductor/<slug>` already exists is refused **409**; so is one whose session-root key is already taken on the project's system (**`SESSION_ROOT_COLLISION`**), checked before any git state is touched. That one branch-ref check covers both collision cases — a still-registered worktree (whose branch git won't let you delete while it is checked out) and a worktree that was deleted but left its branch behind — and its value is the clean 409 in place of the 500 `git worktree add` would otherwise raise. Worth setting for a worktree others will be based on, whose branch is read in `git log` long after it was created. The slug alone is accepted anywhere the full `<project>_worktree_<slug>` name is (see [protocol.md → Input params](protocol.md#mcp-tool-protocol)), and `name` itself tolerates one leading `<project>_worktree_` prefix — stripped before slugifying, so `name:"demo_worktree_x"` and `name:"x"` name the same worktree, while `name:"demo_worktree_"` still refuses 400. No GUI affordance — the browser checkbox still creates hash-named worktrees.
- **Two-step rebase-back**:
  - **Sync** — already in sync → no-op; purely behind & clean → server-side `git merge --ff-only <baseBranch>`; diverged & clean → orchestrator attempts `git rebase --rebase-merges <baseBranch>` directly (`rebased` on success) and on conflict aborts cleanly and returns `rebase-conflict`; behind-but-dirty → `commit-required`. **Sync never prompts an agent.** Those last two are `ok:true` results carrying `branch`/`baseBranch`/`baseSha`/`ahead`/`behind` plus a rendered `rebasePrompt` — two briefs (commit-then-rebase, or rebase-by-hand from a clean tree), both telling the agent to run the same `--rebase-merges` command, to consult the user via `AskUserQuestion` on non-trivial conflicts, and to reply `REBASE_DONE`. Neither brief claims an earlier rebase attempt: a dispatch can arrive after the worktree's state has moved, so the conflict brief asserts only the standing invariant (the orchestrator aborts a failed rebase, never leaves one half-applied) and tells the agent to verify with `git status` — and to say so if the branch turns out to need nothing. Dispatch is the caller's own explicit step: the conductor `send_prompt`s the text to whichever worker should do the work; the GUI confirms, naming the session, then `POST /api/instances/:id/rebase-prompt`. **`--rebase-merges` is load-bearing** on every path: a branch that other worktrees merged into carries their merge commits, and a bare `git rebase` flattens them silently, looking like a clean sync.
  - **Merge** — `git merge --no-ff --no-edit <worktreeBranch>` on the parent. Always produces a merge commit (default msg `Merge branch 'code-conductor/<id>'`) so each contribution stays visible in `git log --graph` and is revertible as one commit. Refuses inline (not as a 500) if the worktree is behind the parent, the parent is on a different branch than `baseBranch`, or the parent tree is dirty. On success, also fast-forwards the worktree's own branch up to the new merge commit (best-effort — reported as `worktreeFastForwarded: true/false`) so a kept worktree lands at `ahead:0/behind:0` instead of looking one commit behind.
- **Delete** — refused if there's a live instance, uncommitted work, or another worktree based on this one, with a `force=1` override.
- **Feature branches (a worktree based on another worktree)** — `create_worktree` / `spawn_instance({createWorktree:true})` accept `baseWorktree: "<worktree name>"`. The new worktree takes `baseBranch`/`baseSha` from **that worktree's HEAD** and its `parentPath` points at that worktree's checkout, so it syncs against and merges into the base worktree instead of the project root. That yields two-level history — `main ← merge(feature) ← merge(task) ← task commits` — lets a multi-stage feature be tested integrated without landing partial work on `main`, and gives a whole feature one reviewable diff.
  - **"Feature" is a position in the graph, not a type.** A worktree others are based on is a feature; a worktree with a `baseWorktree` is a task. The only stored field is `baseWorktree` (`WorktreeMeta`, `src/worktrees.ts`) — absent means based on the project root. `parentProject` stays the **root project name** either way. There are no `*_feature` tools: the existing sync/merge/delete tools do the work.
  - **Depth is capped at one.** A `baseWorktree` naming a worktree that itself has a `baseWorktree` is refused **400**. This is not a safety rail — it is what keeps `WORKTREE_HAS_DEPENDENTS` non-recursive: a base is always a leaf's direct parent, never a chain.
  - **`WORKTREE_HAS_DEPENDENTS`** — `sync_worktree`, `merge_worktree`, and `delete_worktree` all refuse, listing the blocking worktree names in `reason` and in `dependents[]`, while any worktree record names this one as its `baseWorktree`. Every sync path rewrites this branch, which is the base the children were created from; a delete removes that branch outright. The predicate is over **worktree records, not live instances**: killing a child's worker is not enough, the worktree must be deleted. A surviving child whose base was rewritten or deleted under it is genuinely broken, so this is deliberate. The refusal is unconditional on ahead/behind, and on `merge_worktree` it is checked **before** `WORKTREE_BEHIND` — merging needs a prior sync that would also refuse, so this names the real blocker on the first call.
  - **`force` overrides it on delete, and orphans the children.** `delete_worktree({force:true})` / `?force=1` deletes the feature branch anyway, so each surviving child's `baseBranch` ref disappears and its next sync fails loudly with "base branch may have been deleted or renamed". Legitimate when abandoning a whole feature including its children; otherwise delete the children first. (The project-delete cascade sweeps with `force`, so it is unaffected.)
  - **It applies to the worktree being synced/merged/deleted, never to the one being merged INTO.** Merging task `A` into feature `F` succeeds while `F` still has task `B` based on it: a `--no-ff` merge onto `F` appends to `F`'s history rather than rewriting it. (Were it otherwise, no feature with two children could ever take a merge.) A task's own delete is likewise unaffected by having a base.
  - **Two disciplines, both valid — pick per feature; nothing here prescribes one.** *Serialized*: land child → delete child worktree → sync feature → spawn next child → … → sync → merge feature. The feature tracks `main` continuously. *Concurrent*: several children at once; the feature's base is frozen for that window (its sync is refused), so all `main`-integration risk lands at the end.
  - **Known shortcoming: a task's merge sha is ephemeral.** Each feature sync rewrites the feature's history, so a task's merge commit is renewed every time. Only the feature's landing commit on `main` is durable — don't cite a task's merge sha as a stable reference.
  - **A feature worktree is a merge target, so it must be kept clean.** `PARENT_DIRTY` is evaluated against it and has **no override** (`allowDirty` covers only the *merging* worktree's own tree), so untracked build artifacts there — e.g. from `post-worktree-create.sh` — will refuse every task merge into it.
  - A task worktree's `post-worktree-create.sh` is resolved from the **feature's checkout** (in-tree lookup uses `parentPath`), not the project root — same repo, and a feature that edited the hook correctly passes the new one down. `CC_PARENT_PATH` likewise points at the feature checkout.
  - `list_projects` and `list_worktrees` show the relation as `base <branch>@<sha>`; `list_worktrees` additionally marks a derived row `← <baseWorktree>`. There is no GUI tree view — the sidebar renders every worktree as a flat sibling row.
- **Post-worktree-create hook** — a `post-worktree-create.sh` script (need not be committed — read from disk, not the new worktree) is resolved from two locations in priority order: **in-tree** `<parent>/.code-conductor/post-worktree-create.sh` first, else the **central store** `<root>/.code-conductor/projects/<name>/post-worktree-create.sh`. When found, the orchestrator runs it automatically with `cwd` in the new worktree, after the worktree directory, branch, and metadata are written. Use case: symlink `node_modules`, copy `.env`, run `npm ci`, etc. The script receives env vars `CC_WORKTREE_PATH`, `CC_PROJECT_NAME`, `CC_BRANCH`, `CC_BASE_BRANCH`, `CC_PARENT_PATH`. Non-fatal: a failure warns but does not roll back the worktree. Output is capped to a tail bound (`HOOK_OUTPUT_CAP`); timeout via `ORCH_POST_WORKTREE_TIMEOUT_MS` (see `src/worktrees.ts`). Kill-switch: `ORCH_DISABLE_POST_WORKTREE_HOOK=1`. Result is reported in the spawn/worktree-create response as `postWorktreeCreate: { ran, source, exitCode, durationMs, output, truncated?, timedOut? }` (`source` is `'in-tree'` or `'store'`). The spawn dialog re-opens briefly with a one-line summary (expandable output) when the hook ran.

### Diff / review & commit history
- **Worktree diff/review** — `±` button on every worktree row opens a full-page, mobile-friendly diff browser (`#review-view`, `public/review.js`). Fetches a per-file **summary** (no hunks, never truncated — a `--numstat`/`--name-status` pass) from `GET /api/projects/:name/worktrees/:wt/diff` (`<baseBranch>...HEAD`) and renders collapsible `<details>` per file (status badge, `±` counts). A file's hunks are fetched lazily via `?path=<file>` only when its card is expanded, and cached on the card so collapsing/re-expanding doesn't refetch; an expanded card shows a brief loading state, then hunks reusing `.diff-line.add/.del/.ctx` with `overflow-x:auto` for horizontal scroll. Failure states per file: a retryable `.review-file-error`, an `.review-file-note` for a binary file (no fetch at all) or an oversized file (`adds+dels > FILE_DIFF_LINE_GUARD`, hunks never fetched), and a truncation note if that one file's raw diff still exceeds `DIFF_BYTE_CAP` (both constants in `src/gitDiff.ts`). Because the summary has no size cap, a change touching any number of files always lists every one, with exact totals.
- **Commit history** — `≡` button on every git-repo project row opens a full-page scrollable commit list (`#commits-view`, `public/commits.js`) of the project's **current branch (HEAD)**: short sha, subject, author, relative date, newest first. Backed by the commits endpoint (bounded limit, default in `src/worktrees.ts`; header shows `(showing latest N)` when truncated). Tapping a commit opens the **same diff renderer** showing just that commit's change (`GET /api/projects/:name/commits/:sha/diff`, via `git show`); the diff layers over the list and `← Back` returns to it. Merge commits (parents.length ≥ 2) show the **first-parent aggregate** — the full diff the merged branch brought onto mainline (`git show --first-parent`), not git's default combined/conflict-only diff — and every file in that aggregate is listed regardless of the change's total size. A **branch/merge graph rail** (git-log --graph style) is drawn to the **left** of each row: colored lanes, a dot per commit, diagonals where branches fork and merges converge. Topology is computed client-side in `computeGraph()` (`public/commits.js`) from each commit's `parents` (SHAs from `%P`); lanes use stable column indices so pass-through lines stay aligned. Each rail is a fixed-height SVG "node band" (dot + diagonals) plus full-height CSS filler lines, so it aligns with variable-height (wrapping) rows without measurement. Parents older than the cap / on unfetched branches simply trail off the bottom. A soft lane cap (`MAX_LANES`, `public/commits.js`); extras clamp to the last column, logged to console.

### Sessions & instances
- **Unified view** — Sessions list per project (and per worktree) shows live + historical. Header: `Sessions (N) · K live · last <ago>`. Click to focus live instance, or resume stopped one (`POST /api/instances` with `--resume <sid>`). Synthetic `(new session)` row for spawned-but-no-jsonl-yet instances. Rows bucket into up to three sections: the normal list, then a dim `— temp —` separator, then a dim `— conducted —` separator (each section only renders when non-empty).
- **Conducted sessions** — a session spawned via the MCP `spawn_instance` tool (orchestrator-driven) rather than the browser/HTTP path is marked **conducted** (a worker an orchestrator conducts; the orchestrator itself is the `.conduct` session). Orthogonal to temp: unlike temp (in-memory, wiped on exit) the conducted marker is **durable** — persisted to `<store>/conducted-sessions.json` (a `{sessions:[sid,…]}` set, written on turn-end via the same path as last-prompt/permission-mode metadata) so it survives exit, restart, and `--resume` (a UI-resumed conducted session re-acquires the marker from the sidecar). Set **only** in the MCP `spawn_instance` handler — plain UI spawns stay non-conducted. Grouping precedence: a conducted session renders under `— conducted —`; a conducted **and** temp session renders under `— conducted —` but keeps the warm temp preview colour (`.session-row.temp`); a temp-but-not-conducted session stays under `— temp —`. Pure conducted rows get a cool preview tint (`.session-row.conducted:not(.temp)`). It's a grouping, never a filter — conducted sessions stay fully visible in `list_sessions`, the HTTP session APIs, and the sidebar. The marker is cleaned up alongside the session-title sidecar only on session delete (Settings → Archived); it survives temp-exit archiving and the boot sweep, staying meaningful on the archived row.
- **Unread indicator** — small accent pill next to a row when its instance finishes a turn while you're viewing a different session (per-instance, persisted in `localStorage` key `code-conductor:unread`).
- **Archive session (the `×` action)** — the hover-revealed `×` on a session row **archives** it (never deletes): single confirm, `POST …/sessions/:sid/archive`; on 409 the client auto-retries with `?force=1` (stops the live instance) without a second prompt. Archived sessions keep their jsonl (still resumable) + title + conducted markers and **disappear from the sidebar entirely** — they're managed only from **⚙ Settings → Archived**. There is no longer an inline `— archived —` sidebar section, and sessions are never deleted from the sidebar.
- **Archived page (Settings → Archived)** — lists every archived session grouped by owning project (`GET /api/archived`). Each project group is a `<details>` **collapsed by default**; expanding reveals its archived sessions (title/first-prompt/sid + worktree tag + last-active). Per session: **Restore** (`POST …/restore` un-archives it, then resumes/spawns it and navigates straight to it, closing Settings — restoring alone doesn't create a live instance, so the client drives `resumeSession` itself via the `onSessionRestored` callback) and **Delete** (confirm → `DELETE …/sessions/:sid`, the single permanent jsonl-removal path; cannot be undone). The `.conduct` (orchestrator) project's group is always pinned first and rendered as `🎼 Conductor` instead of its raw folder name — sorting/labeling happens client-side in `renderArchived()`.
- **Session summary** — `⋮` menu's `📝 Summarize` opens a modal dialog that generates and displays an AI-written summary of the session via a one-shot `-p --output-format=json` call using the **Fast capability tier**'s bound model/backend, launched through that backend's template — the same `resolveBackendLaunch()` seam `project_bash`'s shell-env bundle uses (see `src/summarize.ts` and [models.md](models.md)). Four options, **Title** shown leftmost: **Title** (a single line in the form `{Project}: <title>`, the title part ≤60 chars, naming the session's *current end goal* — not a recap of what happened, the objective the most recent turns are working toward; the project prefix is the instruction's own output format, not string concatenation). The project name comes primarily from the **conversation itself** — the projects it spawns workers into, the paths/repos it discusses — because a conductor session's own checkout is the hidden `.conduct` project, never the project it's actually orchestrating; the checkout-derived project name (worktree-aware, so a worktree checkout still resolves to its root project) is passed in only as a labelled hint the model may use when the conversation is ambiguous, and is dropped entirely rather than passed through when it would resolve to `.conduct`. If no project can be identified from either source, the model omits the prefix and outputs a bare title. **Short** (~40 content words, plain prose gist), **Medium** (~150 words, scannable recap with bullets/tables), **Long** (~400 words, thorough with `##` headings and structured tables). All four are generated, cached, and rendered identically (same markdown pipeline, same stale badge, same `↺ Regenerate`); the default tier on open is still **Medium**. Title adds one extra affordance: an **✏️ Use as session title** button (shown only when Title is selected and has a cached value) that PUTs the generated text through the same `/api/sessions/:sid/title` path as **Rename** below, sharing its client-side apply logic. The dialog also shows the **cost of the last generation** (`Cost: $0.00xx`, from the POST response's `costUsd`, itself the CLI's `total_cost_usd` — `null`/hidden for a non-Claude backend, same policy as the cost dashboard) — this is **ephemeral**: it clears on open and on every tier switch, is never persisted, and is absent from the GET response. Summaries are rendered as full markdown (headings, tables, code) via the same `renderMarkdownInto` pipeline as assistant messages. A **stale indicator** (`⚠ Session has grown since this summary`) appears when the session has received more turns since the last generation; regeneration is always user-initiated. Stored in `<store>/session-summaries.json` keyed by `sessionId` — `{ short?, medium?, long?, title? }`, each a `{ summary, generatedAt, messageCount }` record (the key IS the tier; cost is never stored); auto-removed when the session jsonl is deleted. That store is cc-owned rather than filename-keyed, so it needs no public→backing resolution; the transcript reads behind the generation do. `sessionId` is stable across `--resume`, renewal and prune, so summaries simply persist.
- **Rename session** — `⋮` menu's `✏️ Rename` opens a prompt to set a custom human-readable label (≤100 chars, empty clears) that overrides the first-prompt preview in the sidebar and prepends an italic chip to the active header. Stored in `<store>/session-titles.json` keyed by the **transcript** id (the session's current backing id — what the sidebar's bulk title load matches by filename, and what `Instance._hydrateTitle` reads), so the REST route resolves the public id a client sends before writing. Auto-cleaned only when the session jsonl is deleted (Settings → Archived); survives a temp session's exit, since that archives rather than deletes. Survives rewind, `--resume`, renewal and prune — a renewal carries the title onto the rotated id; fork starts un-titled.
- **Change model** — `⋮` menu's `🧠 Change model` (directly below Rename) opens a capability-tier picker (Fast / Balanced / Powerful / Frontier) using the same catalog/source of truth as the spawn dialog (`Settings → Models`). Selecting a tier resolves it to its bound `{backend, model}` and switches the **live** session's model via a `control_request` (`subtype:set_model`) — no restart, no history loss. **The tier's default effort is not applied** — a live switch changes the model alone; move the level with the sibling **Change effort** item below. The picker highlights the tier the running session is on with `.qs-selected`. **A session on a non-Claude backend can't switch model live** (the endpoint is fixed at launch): every tier is disabled with a "kill and respawn on that tier" note, and switching a Claude session *to* a tier on another backend is likewise blocked — as is substitution↔substitution (server-enforced too — `409 BACKEND_LOCKED`).
- **Change effort** — `⋮` menu's `⚡ Change effort` (directly below Change model) opens a picker over the level catalog (`EFFORT_LEVELS`, `src/effortLevels.ts`, ordered low → high; the client renders the `efforts` key of `/api/settings/models`, never a literal). Picking a level repoints the **live** session — no restart. There is no `set_effort` control_request, so the server sends `/effort <level>` on the session's stdin and the CLI runs it as a **local slash command**: no model turn, zero tokens, a `$0.00` turn footer. The exchange therefore **shows in the transcript** as a user bubble plus the CLI's own `Set effort level to …` confirmation — deliberately, since the CLI persists that line in the session jsonl and rewind/fork indices count it. **Idle-only**, like 🪒 Prune: mid-turn the item is greyed (`Effort can only be changed between turns`) and the server refuses it `409` — mid-turn the CLI would fold the line into the running turn's input instead of running it. The picker highlights the current level with `.qs-selected`. **No backend is refused** (unlike Change model): nothing here repoints an endpoint. The new level is what every later relaunch that reuses the live value comes back at — per-path table in [models.md](models.md#default-effort).
- **Rewind & fork** — every user message bubble has `↶` (rewind in place, same `sessionId`) and `⑂` (fork to a new `sessionId`) on hover. Both atomically rewrite the jsonl, preserve the dropped prompt in the composer, and 409 during a running turn. Bubbles anchor on the **server-stamped `userIndex`** riding on each outer `user_echo` (the absolute Nth-pure-user-prompt ordinal) — never a client-side bubble count, which would drift once the capped ring / tail-only snapshot starts the view mid-history. An echo without a stamp (rare orphan) renders without the buttons.
  - Rewinding **to the first user message** is special-cased: prefix is empty, so the orchestrator deletes the jsonl entirely and respawns with `--session-id <sid>` (not `--resume`, which the CLI rejects on zero-line files).

- **Prune** — `⋮` menu's `🪒 Prune` shrinks a session's context **deterministically and at zero token cost**: no LLM pass, no `/compact`. It rewrites a *copy* of the jsonl under a fresh **backing** id, replacing fat block content with size stubs, archives the original (still resumable), and respawns the **same instance** against the pruned file. The session's public `sessionId` does not move, so every reference to it stays valid. The session comes back **idle** — unlike `renew_session`, nothing is seeded as a first turn. Idle-only (the button is disabled mid-turn; the endpoint 409s).
  - **Controls.** A slider over turn boundaries (`cutTurnIndex`, the same pure-user-prompt index space rewind/fork anchor on, so the cut can never land between a `tool_use` and its `tool_result`); its range is `0…turnCount`, so a full prune (newest turn included) is reachable, but the slider's DEFAULT is `turnCount-1` — shedding the newest turn is a deliberate drag to the far right. Plus two tickboxes: **prune all thinking blocks** (global, independent of the slider — thinking staleness is categorical, not temporal) and **minimal tool inputs** (squeeze any string value over 80 chars to a size marker; the default truncate mode keeps the first 500 chars, so a value under ~519 chars shrinks not at all — minimal always saves at least as much). A session with one turn is prunable (only `turnCount === 0` is refused).
  - **What it does in the pruned region.** Tool outputs → `[pruned: 12.4 KB]`. Tool input string values → truncated or squeezed; **path keys (`file_path`/`notebook_path`) and the input's key set are never altered** (see architecture.md → Prune for why this is load-bearing). Thinking text → `[pruned: thinking]`, signature retained, exempt on an assistant entry holding an unresolved `tool_use`. `text` blocks are never touched. A stub that would be *larger* than what it replaces is skipped, so pruning can never inflate the context.
  - **Exempt tools** (`isPruneExemptTool`, sessionPrune.ts) — a `tool_use` **and the `tool_result` answering it** are copied verbatim in every mode, at any cut, for: **`AskUserQuestion`** (the question card is rebuilt from `input.questions` on replay and the answer is recovered by string-matching the question text + option labels against the following user echo — squeezing either strands the human with an unreadable question and no answer on the card) and **core conductor MCP calls**, i.e. `mcp__code-conductor__<tool>` (the orchestration record: what was spawned, approved, merged, filed). Exempt by *namespace*, so a core tool added later is exempt by default. Three things stay prunable: **`mcp__code-conductor__project_read`** and **`mcp__code-conductor__project_bash`** (bulk file/command output — exactly what Prune exists to shed; a hardcoded two-entry denylist, not user-configurable), **plugin-namespaced** tools (`mcp__code-conductor__<plugin>__<tool>` — `code-kanban__*`, `code-hub__*`, and any third-party id such as `acme-tools__*`; what discriminates them is the *further* `__` after the prefix, not the first-party `code-*` naming habit, so matching the prefix alone is not enough), and any foreign MCP server. An *orphaned* `tool_result` (no `tool_use` in context ⇒ no name) stays prunable. Thinking on an assistant entry that carries an exempt `tool_use` is unaffected — it follows the normal thinking rules.
  - **Never deletes an entry or a block** — only block content is replaced. That is what keeps the `parentUuid` chain and the `tool_use`/`tool_result` pairing invariant intact with no relinking.
  - **Read-before-edit re-arms.** A pruned Read/Write result drops the CLI's cached file-state entry, so the model must re-Read before editing that file. At a full cut (`cutTurnIndex === turnCount`, or `prune_session({keepLatestTurns: 0})`) that includes a file the worker read moments ago, so it owes a re-Read before its very next edit. Deliberate: the guard exists to guarantee current file content is in context, and pruning is what removes it. Costs one refused Edit per file, self-corrected by a Read.
  - **Sidechains are untouched** and stay readable — sub-agent transcripts are copied to the new `sessionId` alongside the jsonl.
  - **Fails safe.** A throw partway through (the cut is out of range, the copy fails) respawns the instance against the ORIGINAL, unpruned session rather than leaving it with a dead subprocess — the original jsonl is intact by construction. A prompt arriving while a rewrite is in flight is refused with 409 rather than racing the transform — for prune and rewind that spans the whole kill→respawn, for fork (which never kills the source subprocess) it spans the jsonl read, after which a prompt can no longer affect the copy.
  - **Savings estimate** is a `chars/4` heuristic computed over **in-context entries only**: sidechain entries and the disk-only `toolUseResult` sidecar are excluded (counting them would report a large saving while the model's real context barely moves). **Exempt tools contribute zero savings** but stay in the denominator — they remain in the model's context. The `~X% of conversation tokens` denominator counts every in-context entry kind including **`attachment` entries** (CLAUDE.md / nested-memory / file injections) — Prune never touches them, but they are in the model's context, and omitting them would over-report the percentage saved. The dialog shows a per-category breakdown (thinking / tool inputs / tool outputs) recomputed client-side from one analysis call; the preview and the transform share one code path, and a test asserts they agree exactly for every slider/tickbox combination.
  - **Known degradations.** A pruned `Write`'s `input.content` becomes the harness's cached content for that path, so a later on-disk change diffs against the stub in the watched-file attachment. Pruned `Edit` `old_string`/`new_string` shorten the tool-diff rendering (truncate mode keeps the first 500 chars). The ctx chip reads `ctx —` until the first live turn — the jsonl's newest `usage` still reports the pre-prune size, and a known-wrong number is worse than none.
  - **Temp sessions cannot be forked** — the on-exit cleanup races the fork's source copy.
  - **Also reachable from a conductor** — `prune_session` ([MCP interface](#mcp-interface)), which spells the cut relatively (`keepLatestTurns`) rather than as this dialog's absolute `cutTurnIndex`.
- **Crash recovery** — subprocess death → `crashed`; Resume respawns with `--resume <sid>`, preserving the in-memory event ring + conversation.
- **Session anchor** — `#session=<sid>` URL hash; on reload, auto-resumes by locating the jsonl on disk (worktree-aware) via `GET /api/sessions/:sid/locate`. `--resume` spawn costs zero API tokens until the next prompt. Stale anchors are silently cleared.

### Spawn options
- **Mode** — `plan` (read-only, propose then `ExitPlanMode`), `ask` (every destructive tool gates through Allow/Deny card), `code` (full power, CLI's `bypassPermissions`). CLI's `default` / `acceptEdits` are not exposed: in `stream-json --print` (no SDK `canUseTool` callback) they auto-deny tool calls and the only recovery is forcing the model to regenerate the entire tool input.
- **Effort** — `low` / `medium` / `high` / `xhigh` / `max` (`EFFORT_LEVELS`, `src/effortLevels.ts`). **A separate axis from the tier/model binding** — how hard it reasons, not which model. The dialog's Effort select opens on `Default (<level>)`, which sends no `effort` and lets the server resolve the selected **tier's** default (set per row in Settings → Models; the Conduct button resolves the **Conductor role's** instead). Picking a level overrides it for that one spawn. A **resume** names no tier/role, so a sidebar/anchor resume falls back to `DEFAULT_EFFORT` (`high`), while a respawn or a post-restart resume keeps the level the session was already running at. Precedence + per-path table: [models.md](models.md#default-effort). A running session's level can be moved without a restart — see **Change effort** above.
- **Thinking** — `adaptive` (default) / `enabled` / `disabled`.
- **Model** — pick a capability tier (Fast / Balanced / Powerful / Frontier; a tier hidden if disabled in Settings → Models). There is no empty option — the dialog renders one card per tier and pre-selects the **default spawn tier** (Settings → Models), which the client resolves through its binding before POSTing. Each tier binds to a **backend + model**; the backend is a row in the user-managed **backend registry** (`claude` runs the CLI directly, any other row wraps it via a command template — Settings → Backends). A tier on a non-Claude backend resolves straight to its model id (no version choice) and its declared native context window drives both the context-usage bar and the cc-managed `CLAUDE_CODE_AUTO_COMPACT_WINDOW` + `CLAUDE_CODE_MAX_CONTEXT_TOKENS` at spawn. Every model — Claude or not — has exactly one native window, so there is no window picker. MCP `spawn_instance` also accepts a **role** name — built-in, user-custom, or plugin-owned (`<plugin-id>/<slug>`) — a legacy family alias (`opus`/`sonnet`/`haiku`/`fable`, → that family's default version), or a full Claude model id; **omitting `model` on a fresh spawn resolves the default spawn tier's binding** — this tool has no `tier`/`role` argument, so that is always the row it lands on, whereas `POST /api/instances` applies the same never-the-account-default rule but prefers a named `role`, then a named `tier` ([models.md](models.md#same-row)). A resume with no `model` recovers the model **and backend** it last ran. Full contract — registry, custom models, tier/role binding + dead-binding revert, context-window policy: [models.md](models.md).
- **Temp session** — archives on exit (jsonl kept and stays resumable, sibling `subagents/` dir deleted), drops itself from the sidebar's Sessions list on exit/crash (no ghost row to clean up by hand — it surfaces under Archived instead), and skips `last-prompt`/`permission-mode` metadata appends during the run; mode defaults to `code`; header shows a `TEMP` pill.
- **Debug mode** — mirrors raw CLI traffic (`claude-stdin.jsonl`, `claude-stdout.jsonl`, `claude-stderr.log`, `meta.json`) to `<store>/projects/<p>/[worktrees/<wt>/]debug/<instance-id>/`. Append-mode, survives session end. Header shows a `DEBUG` pill. Spawn calls that omit `debug` fall back to the persisted **debug-by-default** setting (Settings → Models → Debug capture fieldset, `spawn.debugByDefault` in `settings.json`); an explicit `debug` on the spawn call always wins. The New Session dialog's checkbox is pre-checked from this default when it opens, and always sends its literal checked state (never omitted) so unchecking it reliably opts a single session out even when the default is on.

### Live conversation
- **Tail-first load + scroll-up history** — subscribing renders the ring tail (around `ORCH_SNAPSHOT_TAIL` events, default in `src/instances.ts` — quiescent-aligned: whole blocks, resolved tools; the quiescent snap can land the served count either shorter or longer than that count, and a backstop serves the nearest quiescent cut rather than an empty tail). When older history exists, a tappable `⋯ earlier messages` sentinel sits above the oldest content and scrolling near the top auto-fetches the previous page (`GET /api/instances/:id/events?before=<cursor>&limit=<limit>`, limit clamped by `clampLimit` — default `LIMIT_DEFAULT` in `src/eventArchive.ts`; flipping the sentinel to `loading earlier…`). If the rendered tail is shorter than the scroll viewport, the controller **auto-fills**: it keeps paging earlier chunks in (same path) until a scrollbar exists or history is exhausted, so the sentinel is never the only thing on screen — it stops on the no-more-history terminal case, on a fetch error (no hot-loop; sentinel stays tappable), and while the container has no layout (background tab). Pages render through the standard block pipeline on a detached node and splice in above with the viewport preserved; a turn split across page seams **merges back into one assistant bubble** (the batch's trailing open bubble concatenates into the chunk below), and sub-agent (Task) groups always travel whole with their nested panel — live children of a not-yet-loaded Task head are parked and adopted into the panel once its page loads. Events evicted from the in-memory ring are reconstructed from the session jsonl.   - **Cache-miss detection** is **cross-turn**, so it catches *partial* (minority) evictions the old stateless rule missed. Captured live in `src/instances.ts`, it compares this turn's **first**-request `cache_read` (`read_N`, pre-tool-call) against the **previous** turn's **last**-request full prefix (`P = cache_read + cache_creation`, the fully-accumulated cacheable prefix — cache_read accumulates across a turn's tool-call iterations, so the first request is used for read_N and the last for P). A miss is flagged when `read_N < P − tolerance` (`tolerance = max(1024, 1% of P)`): this turn served less of the prefix than was demonstrably cached last turn ⇒ an eviction, full or partial. A warm continuation reads exactly `P` (drop 0) and is never flagged. **Turn 1** (no prior `P`) and the turn after a **compaction / model switch / rewind** fall back to the old stateless `creation > read` rule, which still flags a genuinely cold prefix (cold start, expiry, resume, cold rewind). **Guards:** compaction (`system`/`compacting`), model switch (`_trackModel`), and rewind/respawn (`_wipeForResume`) legitimately shrink the prefix, so each sets a `_prefixBaselineInvalid` flag consumed on the next turn's first request — the cross-turn rule is skipped there and `P` is re-established fresh, preventing false positives. **Known limitation:** a miss on a request *after* the first (e.g. a turn outliving the ~1h cache TTL) isn't caught — detection is first-request-only. The verdict + evidence persist on each row (`cache_miss`, `first_req_cache_read`, `first_req_cache_creation`, and `first_req_evicted` = the `P − read_N` estimate on the cross-turn path), and the dashboard's **Cache misses** column counts the flag. On every detected miss an informational in-session notice appears in that session's conversation (a `SystemBlock`, same surface as the overage/rate-limit notice, no action): the cross-turn path shows `♻ ~<evicted> tokens evicted (<read> served of <P> cached).`, the fallback path `♻ <creation> tokens written to cache, <read> served.`. Trip detection + conductor-aware routing live in [architecture.md](architecture.md) → overage. The action buttons, the threshold enable checkbox, and the threshold slider (below) are staged locally and committed together — see **Apply**, below. **Non-Claude exemption:** a usage window is an Anthropic-account concept, so a session whose **root** agent tree touches **no monitored usage-window domain** (i.e. no `claude`-backed agent anywhere in it) is left entirely out of this flow — never auto-stopped, never queued behind the lockout, never armed for auto-resume, and it shows no overage badge. **The unit of stopping is the tree, and it is resolved from the tree's ROOT, not from the session:** a tree with **any** Claude agent stays in *as a whole*, so both a non-Claude conductor with Claude workers **and** a non-Claude worker under a Claude conductor are in the flow, handled exactly as a Claude session in that same position would be — stopped and badged, then either armed-and-queueing or, for a worker that was **mid-turn when the window tripped** **and** whose conductor is in control, stopped **un-armed** (which *refuses* sends instead of queueing them, per **Global stop-and-queue lockout** below). Both conjuncts are needed: in-control alone is not enough, since a worker that had already gone idle is not stopped at all and queues like any other in-flow session. Which case a given session lands in follows from its position in the tree and what it was doing when the window tripped, not from its backend; what root-scoping fixes is membership. Only a whole root tree that touches no monitored domain is exempt. **Trip detection is scoped differently — per session, by its own backend:** a non-Claude session's own `rate_limit_event` reports its own endpoint's window, so it never trips the monitored flow even when its tree is in-flow. This is backend-scoped by *usage-window domain* (`src/usageWindowDomains.ts`), where `claude` maps to the monitored `anthropic` domain and every other backend to its own unmonitored one — not hardcoded per provider, so monitoring another backend's window is a one-line addition.
      - **Global stop-and-queue lockout** — under `Stop & resume`, while the window is active **every** session queues its sends, not just the one stopped mid-turn: an idle/existing chat and a **brand-new chat started during the window** both queue (each queued-only session **arms its resume deadline immediately**, since there's no mid-turn→idle transition to arm on). Typing does **not** resume a session inside the still-throttled window: each message is **queued** and delivered as **one combined prompt** (reset text + numbered list + all queued attachments) when the deadline fires. This is a **hard lockout — no override, no early-resume button** (resume happens only on the deadline; internally `fireNow()` stays as the sweep/test seam). **Safety rail:** global queueing engages only when there's a valid *future* reset time with an armed clear timer — a missing/past reset means sends flow normally (never a permanent lockout). Plain `Stop` never queues (no flush path). **One session does not queue:** a worker the stop left **un-armed** (its conductor is the sole driver) *refuses* sends instead — the MCP tools soft-refuse `OVERAGE_STOPPED_UNARMED`, the WS path fails the send, its composer **disables Send** rather than relabelling it, and its banner reads "Stopped for account overage — your conductor resumes this worker. Messages can't be queued here." Queueing it would strand the text: the queue flushes only on a resume deadline it deliberately does not have. A **queued-only** session (idle/new, never stopped mid-work) resumes with a **softened preamble** ("Delivering the messages you queued while paused") instead of "continue where you left off". The composer stays usable but shows a **"Paused until &lt;time&gt; — messages are queued"** banner (keyed on the global `overageActive` signal, so it shows before the first message is even typed) and its send button reads **"Queue"**; queued messages render as muted **ghost bubbles** ("queued" chip + clock) that collapse (dim) into the delivered turn on fire, marked by a `Window reset — delivered N queued` system line. The auto-resume badge (header chip + sidebar) appends `· N queued`. Queued messages + every resume-preamble selector are persisted in the resume manifest so a restart doesn't drop them (all three states — stopped mid-work, idle-parked, queued-only — are carried; losing one resumes the session on a preamble that is false for it).
    - **Usage threshold** — `models.overageThresholdEnabled` + `models.overageThresholdPct` (default `{false, 85}`, int percent clamped to the bounded range in `src/appSettings.ts`, no step snap); a checkbox + 10–99% slider that fires the same action when `utilization` crosses the percent. Watched from **two** sources: the live `rate_limit_event` stream (which Anthropic only emits near its own ~90% mark) and a periodic server-side usage poll (`src/usageOverageMonitor.ts`, cadence `ORCH_USAGE_POLL_MS` (default in `src/usageOverageMonitor.ts`)) of the **five-hour** window — so *low* thresholds (e.g. 25%) trip even though the stream never reports that low. - **Two-tier interrupt** — ⏸ Interrupt is a **deferred** stop by default: it **arms** an abort that fires at the next output boundary — when nothing is mid-stream and every dispatched tool has returned its result — so the block being written and any finished tool work are preserved, and the model is never asked to acknowledge anything (no extra round-trip). Armed with nothing in flight, it fires at once. Repeating ⏸ while armed does nothing. An unanswered ask-mode permission card never holds the stop up (the tool has not started) and flips to **✗ denied** once the abort lands, rather than waiting out the hook timeout. While armed, the header status chip reads **stopping…** and the bottom turn-indicator label switches to **Stopping…** with an inline **⏹ Interrupt now** button — the explicit escalation to an **immediate** abort that severs the turn and discards in-progress work. The split is driven by a transient `interrupting` flag on the `status`/`snapshot` WS frames; it auto-clears when the turn ends. Either tier leaves the CLI's `[Request interrupted by user]` marker line, which renders as the **⏸ Turn interrupted** system annotation rather than a user bubble, and is never counted as a real user prompt (so rewind/fork indices stay correct) — live it is dropped while the post-abort drain window (below) is open, which the abort itself opens, so it typically surfaces on replay/resume where that turn's `drain_abort` line is not there to say the same thing. Omitting `force` (WS `interrupt`, MCP `interrupt_turn`) is always the deferred tier.
  - **Post-abort drain window** — after an abort the CLI's internal stdin queue is not cleared: any messages written mid-turn (a prompt sent while busy) remain queued, and the CLI will dequeue them and start spurious new turns. The orchestrator opens a **drain window** (`POST_ABORT_DRAIN_WINDOW_MS`, default 3 s) after every abort — forced, or an armed ⏸ firing. The moment a spurious turn announces itself (via `system/init` on the event channel, ~39 ms after the abort and ~3.7 s before the first API round-trip), the orchestrator fires an immediate `control_request interrupt` to sever it — each spurious drain resets the window deadline (sliding window) so a queue of N messages is fully drained. Each drained turn shows a `drain_abort` system annotation ("⏹ Drained queued turn after interrupt") in the conversation. The window closes automatically when it elapses with no new turn-start. Calling `prompt()` (any explicit new-turn path) closes the window immediately so intentional follow-up prompts are never intercepted. A safety cap `POST_ABORT_DRAIN_MAX` (`src/instances.ts`) bounds the number of drains per window.

- **Playbooks** — declarative, enforceable workflow graphs, so a conductor's flow is checked by the server instead of only described in its prompt. A playbook is a graph of **stages** a worker is bound to; illegal moves are refused at the MCP boundary and every legal one is appended to a ledger, which makes the current state inspectable and the history backtrackable. Three ship in-repo (`playbooks/*.json`): `solo` (one worker plans, implements and refines; separate reviewers), `relay` (a planner that can never implement, handing off to a fresh implementer) and `freeform` (the unconstrained escape hatch — a fan-out, a one-off command, or a worker that lands code). **Author your own** as a JSON file under `<projectsRoot>/.code-conductor/playbooks/` — it is picked up without a restart, and `list_playbooks`' `errors` tells you why one failed to load. Enforcement is per conductor session, starting at the **Playbook enforcement** level set in **Settings → Conventions → Conductor** (beside the Preferred-playbook picker; **`enforce` out of the box**, applied to the next conductor spawned). **⋮ → Enforce Playbooks** (below Prune, shown for `.conduct` sessions only) overrides that level **for the current session only** — it never changes the setting — toggling between the two levels — on refuses illegal moves; off allows the call but records the refusal in the ledger **and** drops an amber ⚠ warning bubble into the conductor's own transcript naming the tool, the refusal code, the reason, and the target worker when the refused call named one, so a would-be refusal is visible as it happens instead of only in the ledger. Under `enforce`, a spawn that starts a new run must name a `playbook` and a `stage`; the refusal names every playbook and where each can be entered (under `warn` the same spawn is warned about and proceeds untracked). Conductor-facing surface: `list_playbooks`, `describe_playbook`, `playbook_state` (which reports where a run is and what each next move would do). Contract, refusal codes and known limitations: [protocol.md → Playbooks](protocol.md#playbooks); internals: [architecture.md → Playbooks](architecture.md#playbooks).

### MCP interface
Mounted at `POST /mcp` (Streamable HTTP, JSON-RPC 2.0); tools exposed as `mcp__code-conductor__*`. Auto-registered on every spawn via `--mcp-config` (opt out with `ORCH_DISABLE_MCP_AUTOREGISTER=1`). No auth — localhost-only.

**Contract conventions (clean, no legacy aliases).** The worker handle is always `sessionId` (stable across respawn / `--resume` / restart, **and** across a `renew_session` or a prune — it is a permanent public id, never the CLI's rotating one); the per-process `instanceId` is internal and **never** appears on, nor is accepted by, the conductor-facing surface (a legacy `{id}` hard-fails; the REST/browser path keeps `id`). Every worker-addressing tool accepts three forms — the public id, an unambiguous **prefix** of it, or **any** of the session's backing/segment ids (permanently, so ids already written into wiki pages and old cards keep resolving) — resolved at the MCP boundary; exact matches always win, an ambiguous prefix soft-refuses `{ok:false, code:'SESSION_AMBIGUOUS', matches:[…]}` (see [protocol.md → MCP tool protocol](protocol.md#mcp-tool-protocol)). Worktree is always `worktree`, and takes either spelling — the full `<project>_worktree_<slug>` dir name or the bare slug — with the exact match always winning. Worker resolution is **strict-live + soft-erroring** — `{ok:false, code:'SESSION_NOT_LIVE'|'SESSION_UNKNOWN', reason}`, never auto-respawns (`respawn_instance` excepted) — except for the three call sites that read a session's bytes rather than drive it (`get_transcript`, `get_recent_messages`, `send_prompt`'s `forward` source), which fall back to the on-disk transcript so a retired worker stays readable and forwardable. Inputs are schema-validated (unknown properties rejected); text-payload tools (`project_read`, `project_diff` diff mode, `project_bash`, `get_recent_messages`) append raw un-escaped body blocks after the `content[0]` metadata; the four recon read tools and `describe_playbook` instead return a plain-text rendering as their whole result (no JSON); `ok:false`+`code` for soft refusals, prose+`statusCode` for errors. Full wire contract: [protocol.md → MCP tool protocol](protocol.md#mcp-tool-protocol).

- **Read:**
  - `list_projects`, `list_worktrees` — **text-rendered**, no JSON (see [protocol.md → Rendered read results](protocol.md#rendered-read-results)). `list_projects` counts a project's live workers (`live N`) but does not name them — that is `list_sessions`' job; an adopted (out-of-root) project carries an `external` line, and its listed path is the target's realpath.
  - `list_workspaces`, `locate_session` — bare listings / lookup.
  - `list_sessions` — **text-rendered**; the single session-listing entrypoint (live workers *and* resumable stopped sessions). Args `project?` (omit = everything; **covers the project's worktrees**, validated — an unknown name soft-refuses `PROJECT_UNKNOWN`), `worktree?` (narrows; requires `project`, else soft-refuses `PROJECT_REQUIRED`), `includeArchived?` (default false). Output groups by directory — each project's main checkout first, then its worktrees — with a per-group `live N · inactive N · archived N` header carrying the branch. A worktree group also shows `↑N ↓N vs base` (commits vs the base branch it merges into); a main checkout shows no divergence — its equivalent is vs the remote upstream, a different question, reported by `list_projects` instead. Live rows lead their group marked `LIVE`, carrying displayStatus and activeAgentTasks; inactive rows are one line each (sessionId, last-activity, playbook/stage, flags, title), newest first. Archived collapses to a per-group `+N archived` line unless `includeArchived:true`. The `resumes-hot` flag marks a session whose resume comes up in `bypassPermissions`.
  - `get_transcript` — disk-backed ring-first event stream (forward-paged via `fromSeq`, inclusive); also serves a **retired** session wholly from its transcript (`source`, `status:"exited"`).
  - `get_recent_messages` — multi-block (text + tool_use + thinking), default-call bonding, disk-backed ring-first; also serves a **retired** session wholly from its transcript. Tool inputs come back as a per-argument descriptor (pointers verbatim, oversized arguments marked) unless `includeToolCalls:true`.
  - `project_status` — **text-rendered**; dirty-state output capped.
  - `project_read` — path-traversal guarded, multi-block (metadata + body).
  - `project_diff` — unified diff, summary mode, line-index pagination.
  - `list_project_conventions` — `{conventions, incomplete?}`; hasScaffold flag per convention. `incomplete` appears **only** while the convention catalog is degraded — cc could not read a plugin's conventions and cannot tell those apart from conventions that are genuinely absent. It is phrased conditionally on the loss, because the flag fans out to every convention scope and can fire where this scope lost nothing: whatever *is* missing from the listing cannot appear in the line-1 `CONVENTIONS.md` marker of a project created from it, and no regeneration adds it back.
  - `list_conductor_conventions` — `{conventions, incomplete?}`; conductor convention catalog. Same degrade field, with the opposite consequence: nothing here is committed, since the role doc is recomposed from the catalog on every spawn.
- **Shell** (read-only inspection only): `project_bash` — run a shell command inside a project/worktree cwd, in the exact shell environment claude's own built-in Bash tool uses (the `rg`/`find`/`grep` shims and shell functions/aliases from a captured shell snapshot, generated once per (`claude` version, shell) via a throwaway one-shot `-p` run — spawned through the **Fast capability tier**'s bound backend (Settings → Models) — plain `claude -p` on the identity `claude` row, or that row's command template followed by the claude args (the built-in `ollama` row happens to end in `--`, but a template need not — e.g. `ollama launch claude --model <tag> --yes -- -p ...`) — honoring that tier's model either way (no Anthropic default fallback) — cached under `<store>/shell-env/` as `bundle-<version>-<bash|zsh>.sh` (the cache key is the real `claude --version`, independent of the Fast tier's backend), and memoized in-memory for the life of the daemon process — at most one `claude --version` spawn per restart; see `src/claudeShellEnv.ts` + the shared `resolveBackendLaunch()` in `src/claudeLauncher.ts`). The bundle records which shell (bash or zsh) actually produced it, and `project_bash` spawns that same shell to source it — a zsh-flavored capture (e.g. oh-my-zsh completion internals) is only ever re-sourced by zsh, never by bash. Mirrors `project`/`worktree` for cwd scoping plus the meaningful subset of the built-in Bash tool's schema: `command` (required), `description`, `timeout` (ms, default and clamp defined in the `project_bash` schema). **multi-block** — metadata `{project, worktree, cwd, exitCode, durationMs, truncated?, timedOut?, error?}` + a raw body block carrying the combined stdout+stderr output in arrival order; a non-zero `exitCode` is a normal result, not a tool error; `truncated:true` means retained output was capped at the bash output cap (`BASH_OUTPUT_CAP`) but the command still ran to completion (drain-and-discard, not kill-on-cap); on `timeout` (the only hard kill) the whole process group is killed, `exitCode` is `null`, `timedOut:true`. Replaces the former `grep`/`glob` tools — use `rg`/`grep`/`find` through this tool for search.
- **Create:** `adopt_project` (`{name, path, system?, remoteId?}` — register an EXISTING out-of-root git repo root as a project in place, or one on a target of a registered system; returns JSON, refusals as `{ok:false, code, reason}` — see **Out-of-root projects** above for the codes and for what cc writes into the target). `create_project` (`{name, conventions?:[slug,…], system?, remoteId?, systemPath?}` — the new dir is always `git init`-ed (no commit), so its HEAD is unborn and it cannot take a worktree until the first commit; optional `conventions` appends each picked convention's CLAUDE.md fragment inline (call `list_project_conventions`; 400 on unknown slug); any picked convention with `hasScaffold:true` also contributes its one-time setup directive, composed in selection order into one framed block **returned** as the result's `scaffold` field (empty/omitted when none) — nothing persisted, the conductor folds it into the first worker's brief).
- **Placement:** `set_project_remote` (`{project, remoteId}` — change which TARGET of its system a project is on, or clear it with `null`/`""`; refuses `PROJECT_PLACEMENT_IN_USE` (409, naming the live sessions and registered worktrees), `SYSTEM_NO_REMOTES` (501) and `REMOTE_NOT_FOUND` (502), all before anything is written; refuses a project on `local`). Twin of `PUT /api/projects/:name/remote` — both call the one helper, so both inherit the same guard.
- **Workspaces:** `create_workspace` (`{name}` — register), `delete_workspace` (`{name}` — removes registry entry + clears member assignments), `rename_workspace` (`{oldName, newName}` — atomic), `set_project_workspace` (`{project, workspace}` — assign or clear with `null`/`""`; refuses `.conduct`; auto-registers a new workspace name).
- **Spawn/drive:** `spawn_instance` (`createWorktree:true` makes a fresh worktree off HEAD; `worktree:"<name>"` attaches to an existing one — the old `worktree: boolean|string` overload is gone. MCP-path spawns are always `temp` (archived on subprocess exit — transcript retained and resumable, just out of the default session list) with **no MCP knob for it**; mode still stays `plan` — `InstanceManager.create()` is policy-light and never couples temp to mode, so conducted workers plan before acting; an explicit `mode` still wins. The UI's temp⇒`bypassPermissions` shortcut lives only at the `POST /api/instances` route, not in `create()`; the UI temp checkbox and `POST /api/instances/:id/promote` remain the human's affordances), `send_prompt` (`{sessionId, …}`; a mid-turn send to a worker whose model declares **no mid-turn steering** stops that turn at a block boundary — finished text and completed tool work are kept — and arrives as a fresh turn instead, told that its turn was cut off; same tool, same result shape. `approve_plan` / `reject_plan` / `answer_question` and the web UI's composer and card surfaces take the same route, and no result field says which one ran; [protocol.md](protocol.md#subprocess-protocol)'s `user` row is the authoritative routed-site list; **you are woken when its turn ends** — see below; optional `forward:{sessionId}` injects another worker's recent output into the prompt server-side — the same default `get_recent_messages` selection, framed as context-only, with the conductor's own `text` placed last; an empty/tool-only source soft-refuses `NOTHING_TO_FORWARD` before any prompt is sent), `set_idle_timeout` (`{sessionId, timeoutSeconds}`; adjusts the HEARTBEAT window on one owned session and re-arms a running heartbeat — `armed:true` means the target was mid-turn — with the default as its ceiling, so it can only shorten. The wake itself needs no tool: when an owned target hits `turn_end` the orchestrator injects a stub user prompt into the *owner* via `Instance.prompt()`, naming the worker by sessionId; **folded wake** — on an ordinary `turn_end` delivered to an already-idle caller the stub **folds the worker's recent output inline** (the SAME content a default `get_recent_messages({sessionId})` call returns — bonded prose + plan/questions — via the shared `buildRecentMessages` builder + `flattenPayload`), so the conductor needs no follow-up call; the folded stub is tagged with a `[[cc:wake-callback]]` marker (`public/wakeCallback.js`) that the conductor UI renders as a **collapsible wake-callback bubble** (worker id + a one-line summary always visible — "finished its turn" for this folded variant; the other variants say plainly that it did NOT finish — with the folded payload collapsed by default) with an orchestrator badge (🔔) marking it as system-injected; caller identity is read from `?caller=<caller sessionId>` baked into the per-worker MCP URL at spawn time (after the sessionId is minted); **carve-outs** — the heartbeat stub, the mid-turn-deferred stub and the force-abort **interrupted** stub all keep a plain "call `get_recent_messages` to inspect" pointer (no fold), while still being tagged with the marker (via `markPlainStub`, body-less) so they render as the **same wake bubble** — badge + summary line only, no expandable body or caret. On the interrupted one the carve-out is deliberate rather than incidental: a force-abort's output is PARTIAL, and the body separator is the client's "this is the finished result" signal, so folding it would invite the conductor to act on exactly what the abort was meant to stop it acting on. It reaches every owner except whoever called for the abort (that one is silenced), and the UI's stop button — same `Instance.interrupt` chokepoint — has no interrupter, so there every owner gets it; the idle-wake graph is keyed internally by the stable instanceId (the `?caller=` sessionId is translated at the dispatch boundary); the heartbeat repeats every window with a clearly-labelled "did NOT finish" stub while the target is mid-turn — **without consuming the pending turn-end wake** — so a hung worker is never misread as finished, and keeps saying so for as long as it can still finish. It does NOT ping forever: a target that is gone for good (subprocess dead with no prune/rewind/respawn reviving it) gets one final ping and then the heartbeat retires, because no `turn_end` can follow and an unbounded series would be a false report rather than a warning. Silence after a "did NOT finish" ping therefore means the worker died, not that the wake was lost; a conductor whose own model declares **no mid-turn steering** (Settings → Models) never receives a wake into its running turn — the wake is **held** and delivered at that conductor's own next `turn_end`, folded, or marked "no longer idle" if the worker has since started another turn), `set_mode`, `interrupt_turn` (default arms a deferred abort that fires at the next output boundary — returns `interrupting:true` meaning armed, not stopped; optional `force:true` ⇒ abort now), `kill_instance`, `respawn_instance`.
- **Session renewal / prune:** `renew_session` (`{sessionId?, summary?, directive?, followUp?}`) — an agent renews its OWN session (sheds context about landed jobs — dead weight taxing every future turn — at a lifecycle seam, not because context is "full"). Caller identity comes from `?caller=<instanceId>` (the stable instanceId, resolved to the caller's sessionId at the MCP boundary — so it always targets the calling session, works only for a code-conductor-managed instance, and **stays valid across repeated renewal**); it hands off a self-authored `summary` (a three-section template: live work roster, completed work index with pointers, user context) and code-conductor drives a **server-managed `/clear`** at the caller's next `turn_end`, rotating the CLI's context in place (**same OS process/pid**, old jsonl preserved) and reseeding the cleared session with the summary plus a **server-generated mechanical state block** as its first user turn. **The session's `sessionId` does not change** — only the CLI's internal backing id rotates, and the rotation is recorded as a `renew` segment in the session's lineage (see [architecture.md](architecture.md)), so every id a conductor, a kanban card or a wiki page holds stays valid. `summary()` reports `rotationReason`/`lastRotatedAt`/`segmentCount` so a conductor can still tell a freshly-renewed worker from a stalled one. The caller's durable transcript-keyed markers (`temp`, `conducted`, custom title, recorded mode, backend) are carried onto the rotated backing id, and the abandoned pre-clear session is **auto-archived** (its jsonl stays resumable but moves to the archived section), so a later resume/`spawn_instance({resume})` of the renewed session keeps its temp/conducted/title state. The state block (built at reseed time, not arm time, so it reflects current — not stale — state) enumerates the live instances the caller spawned (`InstanceManager.liveOwnedBy`, via the same `callerInstanceId` ownership tracking the sub-agent panel uses) and the caller's own owned wake targets (spawn or dispatch, whether or not one is armed right now) — a safety net so a worker a degraded summary omitted is never orphaned: the mechanical list wins for **existence**, the self-authored summary wins for **intent**. The bare form is deferred to the caller's `turn_end` (not fired inline) so the tool call's own turn finishes first, and returns `{ok:true, willClearAtTurnEnd:true}`. **A conductor can also REQUEST a renewal** — `renew_session({sessionId, directive?, followUp?})` prompts that worker to renew itself and returns immediately (the request's own turn wakes the caller) (`{requested:true, …}`). The worker authors its own summary via its ordinary self-call, so the conductor never writes another session's working memory: `directive` is a PRE-directive (what to be sure to capture), `followUp` a POST-directive (its next job, fenced into the reseed under its own marker, so one call replaces renew-then-send_prompt). The request lives exactly one turn and **cannot be forced**: a worker that ends its turn without calling `renew_session` has DECLINED — it may be mid-rebase or holding state only it can land — and that expiry is reported as a note prefixed into the conductor's wake stub. Mixing the two forms' arguments (a `summary` with a `sessionId`, a `directive` without one, or targeting yourself) soft-refuses `INVALID_RENEW_FORM`; a target that is not free — mid-turn, or idle but owing a re-invocation turn, running subagents, or overage-parked — soft-refuses `SESSION_BUSY`, because a request needs a turn of its own. The decline note reaches the conductor that asked and no other, exactly once. Because it declares a `sessionId` it is a governable tool: a playbook stage may deny the request, while the bare form and the worker's own self-call are never gated. Empty summary soft-refuses `INVALID_SUMMARY`; a renewal armed while a prune is rotating the same session soft-refuses `SESSION_ROTATING` (and vice versa — the two mechanisms are mutually exclusive, because a prune makes `prompt()` 409 and the reseed is a `prompt()`). The clear is deferred further past an overage-queued turn or live subagents so queued/background work is never stranded by the rotation. Mechanism in `src/sessionRenew.ts` (`SessionRenewController`, keyed by the stable instanceId; no side-structure migration needed since the idle-wake graph and overage timers are instanceId-keyed too). A default-on conductor convention, `context-renewal` (`conventions/conductor/context-renewal.md`), teaches when to call it. **`prune_session`** (`{sessionId, keepLatestTurns?, pruneThinking?, inputMode?}`) is the other half of that convention and the MCP face of the Prune feature above: it rewrites the target worker's transcript with old tool outputs, oversized tool inputs and thinking replaced by size stubs, then respawns that worker against the pruned copy — no LLM pass, no summary, no turn spent, and the worker comes back **idle** with nothing seeded. Handler defaults (the schema's `default` is documentation only): `keepLatestTurns: 1`, `pruneThinking: true`, `inputMode: 'truncate'`. `keepLatestTurns: 0` prunes every turn including the newest; a value larger than the session has clamps to "prune nothing". Returns `{ok:true, sessionId, keptTurns, prunedTurns, saved:{thinking,toolInputs,toolOutputs}}` — the SAME public `sessionId` it was given (only the backing id rotates), and deliberately **no** `oldSessionId`/`newSessionId`, which are internal backing ids. `keptTurns`/`prunedTurns` are what make a clamped `keepLatestTurns` legible. Soft refusals: `SESSION_UNKNOWN` / `SESSION_NOT_LIVE` (strict-live, like every worker-addressing tool), `SESSION_BUSY` mid-turn (routing to `interrupt_turn`), `SESSION_ROTATING` when a renewal or another prune already holds the target, and `INVALID_PRUNE_TARGET` when the `sessionId` is the caller's own (a prune respawns its target, so it would kill the calling process mid-call — `renew_session({summary})` is the self-directed form). Because it declares a `sessionId` it is prefix-resolvable and playbook-governable like the rest. Renew vs prune: renew at a **job seam**, when a summary is all that needs to survive; prune **inside** a job, when the worker must keep its recent working state and only its older payloads are dead weight.
- **Wake on turn end is a property of ownership.** A conductor OWNS a target if it spawned it (`callerInstanceId`) or has ever dispatched to it — `send_prompt`, `approve_plan`, `reject_plan`, `answer_question`, and the targeted `renew_session` each record the edge (from `?caller=` on the MCP URL) **before** the send. Arming happens in `Instance._setStatus`'s into-`turn` branch, so every transition into a turn re-arms one wake per live owner: prompted and **unprompted** turns alike, which is what covers an auto-approved plan rolling into implementation with no conductor call behind it. There is no `subscribe` parameter, no result field, and no opt-out; `idleTimeoutSeconds` (whole seconds, `minimum:1`, floored at both ends against `ORCH_SUBSCRIBE_TIMEOUT_MS` via `DEFAULT_SUBSCRIBE_TIMEOUT_SECONDS`) only shortens the heartbeat window. A failed ownership record never fails the send. One armed wake per owner→target pair, so a mid-turn steer on top of a dispatch still delivers exactly ONE wake. Cleared by `turn_end` / the idle task-drain settle / rotation completion (all of which deliver), by `kill_instance` (which delivers nothing), and by `interrupt_turn({force:true})`, which clears the INTERRUPTER's own entry **before** the abort's own `turn_end` so that turn wakes it not at all — the conductor caused it. Every OTHER owner is still woken there and told the turn was **interrupted**, not finished (a fourth wake-stub variant, never folded — see [protocol.md](protocol.md#mcp-tool-protocol)); silencing an owner that did not ask for the abort would strand a wait nothing else can end, and a target can have several owners. The UI's stop button goes through the same `Instance.interrupt` chokepoint, so it produces the same interrupted stub — with no interrupter, every owner gets it. A SOFT `interrupt_turn` deliberately leaves it armed: its boundary wait is unbounded, so the continuing heartbeat is the escalation signal.
- **Plan handling (Conduct-mode verbs):** `approve_plan` (`{sessionId, feedback?}` — flips to bypassPermissions + sends canonical approval prompt), `reject_plan` (`{sessionId, feedback?}` — stays in plan mode, asks for refinement). Both share the same approval/rejection text as the UI's Approve & Implement / Reject buttons via `src/planApproval.ts`. `approve_plan`/`reject_plan` record ownership like every turn-starting call (see above).
- **Question handling:** `answer_question` (`{sessionId, answers}`) — structured answer to a worker's `AskUserQuestion`, mirroring the UI question card. `answers` aligns by index to the worker's pending questions (re-derived from the ring, same source as `get_recent_messages`); each entry is `{option}` / `{options:[…]}` / `{text}` / `{}` with an optional `note`. Delivers text **byte-identical** to a UI submit — both call the DOM-free formatter in `public/userQuestionAnswers.js`. Soft-refuses `{ok:false, code}` with `NO_PENDING_QUESTION` / `ANSWER_COUNT_MISMATCH` / `INVALID_OPTION` / `NOT_MULTISELECT` / `EMPTY_ANSWER`. Records ownership like every turn-starting call (see above).
- **Playbooks:** `list_playbooks`, `describe_playbook` (`{id}` — **text-rendered** on success; its `PLAYBOOK_UNKNOWN` refusal stays JSON), `playbook_state` (`{sessionId?}` — omit it for every run at once). All three are read-only and never create the ledger they read. `spawn_instance` gains `playbook`/`stage`/`provenance` and `send_prompt` gains `stage`/`provenance`; under `enforce` a run-root `spawn_instance` is refused unless it names `playbook` + `stage` — but a `spawn_instance({resume})` of a playbook-tracked session is not a run root and inherits both from the session record. `list_sessions` rows carry `playbook`/`stage` (`null` when the session is not playbook-tracked). See [protocol.md → Playbooks](protocol.md#playbooks).
- **Worktrees:** `create_worktree` (`{project, baseWorktree?, name?}` — see Feature branches above), `delete_worktree` (soft-refuses `{ok:false, reason, code:'WORKTREE_ATTACHED'|'WORKTREE_DIRTY'|'WORKTREE_HAS_DEPENDENTS'}` unless `force:true`), `sync_worktree` (`{project, worktree}`; `action: already-in-sync|fast-forwarded|rebased|commit-required|rebase-conflict` — the last two are `ok:true` and carry a rendered `rebasePrompt`; it never prompts a worker), `merge_worktree` (`{project, worktree}`; fast-forwards the worktree's own branch onto the new merge commit; refusals carry a `code`: `WORKTREE_BEHIND`/`BASE_BRANCH_MISMATCH`/`PARENT_MID_MERGE`/`PARENT_DIRTY`/`PARENT_STATUS_UNKNOWN`/`WORKTREE_DIRTY`/`WORKTREE_STATUS_UNKNOWN`/`NOTHING_TO_MERGE`/`MERGE_FAILED`/`SYSTEM_UNREACHABLE` — `WORKTREE_DIRTY` here is the worktree's own tree, not the parent's, and is overridable via `allowDirty:true`). `sync_worktree`, `merge_worktree`, and `delete_worktree` all refuse `WORKTREE_HAS_DEPENDENTS` (with `dependents[]`) — see Feature branches above.

### Plugins
- **What a plugin is** — any project (in-root, or an **adopted** out-of-root repo) with a `conductor.plugin.json` at its root (schema: [docs/plugins.md](plugins.md)). Each capability is one manifest key past the identity block — `KNOWN_TOP_KEYS` (`src/plugins/manifest.ts`) minus `id`/`name`/`version`/`pluginApi`, so a key added there is a capability unless it joins the identity block: a supervised backend process, an embedded frontend, MCP tools forwarded through the conductor's MCP server, **conventions** (entries joining the Conventions catalog as `<plugin-id>/<slug>`, each `project`- or `conductor`-scoped — see **Convention scope** below — and carrying a CLAUDE.md fragment and/or a one-time scaffold directive), **roles** (named model-bindings joining the role list as `<plugin-id>/<slug>`, resolvable by `spawn_instance`, user-rebindable in Settings → Models → Roles — the manifest binding is the default; a user override takes precedence at spawn), and **Claude Code skills** (a `claudePlugin` root contributed as a session-local `--plugin-dir` at every claude launch — interactive sessions and MCP-spawned workers alike). The contribution-only kinds need **no backend** — a manifest declaring no `backend` (`hasBackend`, `src/plugins/row.ts`) validates, enables, and never starts a process. Discovery scans the projects root at boot and on **↻ Rescan**; duplicate ids resolve first-alphabetical-project-wins (the rest show `conflict`).
- **Conventions & scaffolds** — an enabled plugin's `conventions` join the new-project dialog + `list_project_conventions` (namespaced `<plugin-id>/<slug>`). A convention carries a CLAUDE.md **fragment** (`file`, written into the project's regenerated `CONVENTIONS.md` at creation — regeneration drops the slug's text and names it in the file once the plugin is disabled/uninstalled, and it returns verbatim on re-enable; see the **Project** convention bullet above and [architecture.md](architecture.md#component-layout) for the full behavior) and/or a **scaffold** facet (`scaffold:{text|file}`, a one-time setup directive, **plugin-only**); at least one of the two is required. A convention flagged `hasScaffold` carries its scaffold invisibly in the dialog (no tag); when picked at creation its directive is composed (in selection order across all picked scaffold-bearing conventions) into one framed block **returned** by `create_project`/`POST /api/projects` under a `scaffold` field — nothing persisted, no spawn coupling. The conductor folds it into the first worker's brief; the UI displays it read-only in the create confirmation (v1). A **scaffold-only** convention contributes nothing to `CONVENTIONS.md` but still emits its directive. Only enabled+`ok` plugins contribute; a stale/missing fragment or scaffold `file` makes the plugin `invalid` at load. Since fragment and scaffold now live on one entry, author a scaffold-bearing convention to **degrade gracefully** if the scaffold step wasn't run (e.g. "if a project-local harness wrapper exists, use it; otherwise see the shared harness to create one"). Updating a plugin's checkout (rescan, restart, an active-version switch, or Plugin Library **Update**) now reaches every referencing project's `CONVENTIONS.md` on that same request — no orchestrator restart needed (see limitations in [plugins.md](plugins.md#rest--apiplugins)).
- **Convention scope** — every plugin convention declares a required `scope`. **`project`** and **`conductor`** are accepted today; `workspace` is **planned** and rejected at manifest load with a "not yet supported" error. A **`conductor`-scope** convention joins the Conductor-conventions catalog above (Settings → Conventions → Conductor) as its own checkbox, namespaced `<plugin-id>/<slug>`; it is **on by default while the plugin is enabled** (composed into the conductor's system prompt), unless the user has explicitly unchecked it (a remembered off-switch). Unlike a project convention it leaves no tracked in-tree artefact, so disabling the plugin (or unchecking its convention) simply drops it from the next conductor spawn's composed prompt — there is no marker keeping it named. The scaffold facet has no scope of its own — it's inherently project-scoped (it runs at project creation); a scaffold facet on a `conductor`-scope entry is simply never read (nothing outside project creation consumes it). ⚠️ A **`conductor`-scope** convention edits the orchestrator's **own** rules (the conductor role-prompt conventions that govern how it delegates/reviews/merges across all projects) — a powerful, trust-loaded capability (consistent with "plugins are trusted code", but far beyond a per-project convention); it requires the same explicit user opt-in as any other conductor convention, precisely because of that trust jump.
- **Trust stance (loud)** — plugins are **trusted own code**. Their frontends are same-origin iframes: plugin JS can call every conductor API the UI can. Enabling a plugin is equivalent to running its code with your conductor's privileges.
- **App switcher** — the sidebar `CodeConductor` title becomes a dropdown once an enabled plugin contributes a frontend (zero plugins ⇒ plain `<h1>`, no visual change). Selecting a plugin navigates to `#plugin/<id>/`; selecting Conductor deterministically closes the plugin view and restores the active session anchor (never `history.back()` — a deep link has no usable back entry). Rendered by `public/appSwitcher.js` from `GET /api/plugins`.
- **Plugin view** — `#plugin/<id>/<subpath>` shows the plugin's frontend in a full-page iframe (`public/pluginView.js`, src `/plugins/<id>/<subpath>` through the reverse proxy). Switching to an enabled-but-stopped plugin **auto-starts it behind a "Starting …" overlay** (REST status→start before the iframe loads, a bounded readiness window (`READY_TIMEOUT_MS`, `src/plugins/supervisor.ts`)); a start failure shows the error + crash tail with a **Retry** button instead of raw proxy JSON in the frame. Entering a plugin costs exactly **one** history entry (the bridge patches `pushState`→`replaceState` inside the iframe), so hardware **Back always lands on the conductor**; Escape works too. The sidebar stays live (`/ws` events keep flowing) while a plugin is open, and **any sidebar navigation** (selecting a session, opening commits/review/settings) closes the plugin view and returns to the conductor. Leaving the hash space blanks the iframe (frees memory). Limitation: multi-page (non-SPA) plugins still pollute joint history.
- **Settings → Plugins** — management group (`public/pluginManager.js`): per-plugin state badge (`discovered / disabled / enabled / stopped / starting / ready / crashed / failed / invalid / conflict / incompatible`), contribution badges (`N project conventions`, `N roles`, `Project scaffold: N` with a per-scaffold name/description preview), immediate Enable/Disable/Start/Stop buttons, crash-output expander, ↻ Rescan, and an **active version** dropdown (main + the project's worktrees). A ready row shows `running <version> @ <sha7>`, ` · update available` when stale, + port. A **backendless (contributions-only)** enabled plugin shows state `enabled` and only a Disable button (no Start/Stop/version — it has no process).
- **Restart on stale code** — a running plugin whose active checkout's HEAD has moved past the sha it was started at (a commit landed while it was running) is flagged `stale` and gets a **Restart** button next to Stop (stop + start in place, `POST /api/plugins/:id/restart`, 409 if not running). No button while stopped, backendless, or already at the started-at sha; a non-git checkout is never stale. Plugin Library **Update** now does this restart for you (see below) — the manual Restart button stays for a plugin whose code moved by some other means (e.g. a hand-run `git pull`).
- **Plugin Library** — below the installed-plugins list, a catalog of *installable* plugins (git repo URLs) with an **Install** button that clones the repo into the projects root (`GET`/`POST /api/plugins/library[...]`, `src/plugins/library.ts`). Install clones then **enables the freshly-discovered plugin by default** (so its conventions go active immediately); enabling is start-neutral (backends start lazily on first use), so nothing launches at install time, and an invalid/conflicting manifest is left disabled. Once cloned, the project surfaces in the list above through the normal discovery/rescan flow, same as any other plugin project. A set of built-in library entries is always present (see `src/plugins/library.ts`), even with no library dir — overlaid by drop-in manifests dropped into `<orchStoreRoot()>/plugins/library/*.json` (one JSON object per file: `{id, name, description?, repo, postClone?, postPull?}`; a dropped file whose `id` matches a built-in overrides it; malformed/incomplete files are skipped with a warning, never fatal). An entry already cloned (its derived target directory exists) shows "installed as `<name>`"; an **Update** button only appears when the checkout is actually **behind its origin** — `list()` runs a bounded (8s), best-effort `git fetch` per installed entry before comparing (reusing `getProjectUpstreamStatus`, `src/worktrees.ts`), so a fetch timeout/no-remote/detached-HEAD/non-repo just hides Update rather than crashing the list; an up-to-date entry shows "installed as `<name>` · up to date" instead. The target project name is derived from the repo URL's last path segment (`.git` suffix stripped); only `http:`/`https:`/`git:` repo URL schemes are accepted. A failed/timed-out clone shows the error + clone-output tail (reusing the crash-tail `<details>` styling) and cleans up any partial directory so the same install can be retried.
- **Plugin Library — live install/update output** — Install/Update stream their progress as NDJSON (`src/plugins/api.ts`'s `streamLibraryAction`), so the clicked row shows its button disabled + relabeled (`Installing…`/`Updating…`) and a small live output box (`.pll-live`) filling in with clone/pull/hook stdout+stderr as it runs, instead of only a result appearing after the fact. On failure the row's live output stays visible and the button re-enables; on success the whole library list re-renders (dropping the live box, re-evaluating Update availability).
- **Plugin Library — postClone/postPull + Update** — an entry may declare `postClone`/`postPull` shell commands (run via `bash -lc`, cwd = the project directory, e.g. `code-playwright`'s `bash install.sh`) that install the plugin's own dependencies. `postClone` runs once, right after a successful install (clone + rescan); **Update** (when shown — see above) runs `git pull --ff-only` → rescan → `postPull` → **auto-restarts the plugin's own backend if it's currently running** (a stopped plugin is left stopped — it'll pick up the pulled code lazily on its next start) → regenerates every project referencing one of its conventions. **If a backend is actually running and `postPull` fails, the auto-restart is skipped entirely rather than attempted** (checked in that order — a plugin with nothing running reports the same "nothing to restart" either way, never a skip) — a broken `postPull` leaves the checkout half-built, and restarting into it would trade a healthy backend serving old code for a crash-looping one serving no code at all; the running backend is left exactly as it was, still serving the pre-update code, until the user fixes the dependency and retries Update (or trusts the checkout enough to hit **Restart** by hand). A failed `git clone`/`git pull` is a hard failure (error + tail shown, and a failed clone is rolled back); a failed `postClone`/`postPull`/auto-restart, by contrast, is a **soft warning** — the clone/pull already succeeded and the project is already discoverable, so the entry still shows as installed, just with a warning + output tail (a failed post-hook wins the status line over a failed or skipped restart, since it's the likelier root cause of both, and the message is extended to say the backend was left on the old code). The documented way to retry a failed `postClone` is hitting **Update** (which reruns `postPull` — `code-playwright` sets both to the identical command); a failed (or skipped) auto-restart can be retried with the manual **Restart** button. Running a library entry's declared command is a trusted-code-execution surface (bounded timeout, output always surfaced), consistent with the plugin system's overall "plugins are trusted own code" stance.
- **Lifecycle & lazy start** — enabling records the plugin. Any discovered plugin project (enabled or not, valid or not) with no workspace is auto-assigned to the **CC-Dev** workspace on every rescan/boot — enable, install, and manual rescan all trigger this via the same discovery pass, and a project already assigned elsewhere is never moved. The conductor's own project gets the same CC-Dev placement via a one-time boot seed, since it isn't a plugin. Enabled-but-stopped costs zero RAM: the first proxy request or MCP tool call starts the child and waits through the readiness window (`READY_TIMEOUT_MS` in `src/plugins/supervisor.ts`). Children are detached process groups that **survive conductor restarts** (adopted on boot when still alive+answering). Health is passive (exit events, proxy errors, on-demand probes) — on Android, Doze may kill a child at any time; the next request 503s with the crash tail, then lazy-restarts after a short backoff. a crash-count threshold within a rolling window ⇒ `failed` (see `src/plugins/registry.ts`; manual Start/Enable to recover).
- **Worktree-version activation** — the version dropdown switches which checkout the child runs from (`main` or any of the project's worktrees, resolved via the worktree store). The manifest is re-read from the active checkout on every start and must keep the same id (else 400, previous state kept). Caveat: worktrees don't share `node_modules` — a missing-deps start failure surfaces in the crash tail; the per-project `post-worktree-create.sh` hook can `npm install` automatically.
- **Plugin MCP tools** — manifest-declared tools appear inside the existing conductor MCP server as `<plugin-id>__<tool>` (client-visible `mcp__code-conductor__<plugin-id>__<tool>`). Visibility: **globally visible** — every enabled plugin's tools are offered to the conductor UI and to workers in **every** project (the manifest `mcp.scope` field is accepted for compatibility with shipped manifests but dropped at load — nothing reads it). A disabled plugin's tools are simply unknown. Calls lazy-start the plugin and forward over HTTP with a per-manifest timeout. Note: workers snapshot the tool list at spawn — mid-session enable/disable reaches only new sessions.

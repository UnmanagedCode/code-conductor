## Features

### Projects & workspaces
- **Project list** — STORE-DERIVED: the sidebar shows one row per record under `<store>/projects/`, and nothing else. A directory under `<projectsRoot>/` is not a project until it is registered, which is what lets the root hold container directories with projects nested inside them at any depth. A record cc cannot parse still lists, with an empty path and a `degraded` reason — invisible would also mean undeletable. `+ New project` creates a dir, `git init`s it, seeds `CLAUDE.md` containing exactly `@CONVENTIONS.md` — the import of the regenerated in-project conventions file that carries both workspace and project conventions (see **Conventions** below), written whether or not any project convention was picked — then commits both files, so the project is worktree-ready with no first commit needed. The commit uses the repo's configured `user.name`/`user.email`, substituting `code-conductor <code-conductor@invalid>` per field only where one is unset (`-c` on that one command; nothing is written to any git config). A global `core.excludesFile` cannot drop a scaffolded file from it (creation force-adds exactly what it wrote). A commit that cannot be made — a refusing hook, a broken signing key, or a git that resolves the new directory to some other repository — is a `console.warn` and leaves the project created with an unborn HEAD; creation never fails over it, and never commits into a repo it did not just create. Nothing has to be filtered out of the list: a worktree checkout, a container directory and cc's own dotfolders all lack records. The list also carries every project placed on a **system** (see **Projects on a system** below).
- **Delete project** — `×` per row opens the confirm dialog (`public/deleteProjectDialog.js`): a typed-name confirm plus an **off-by-default** "also delete the project directory" checkbox, naming the literal path it would remove. **DELETE MEANS DEREGISTER**: the record goes and the tree stays unless that box is ticked, and the box is **absent** for a project on a system — cc removes its record of a tree on another machine, never the tree (`deleteDirectory:true` there is refused **400**). One behaviour for every project, whichever way it was registered.
  - The cascade kills instances, then removes every worktree **with the ordinary guards** — a worktree that is dirty, dirty-unknown or depended-on **refuses the whole delete 409**, and nothing is force-removed under the user. A checkout that is not there, or whose parent is no longer a repo, has no uncommitted work to lose: its registration is dropped rather than refused, so a project whose tree vanished out-of-band is still deletable.
  - cc's own area for the project always goes: `<store>/projects/<name>/` and `<projectsRoot>/.worktrees/<name>/`. Session jsonls are left intact, but WHERE differs: a local project's stay at `<configDir>/projects/<encoded>/` and remain resumable by the standalone CLI, while a system-placed project's stay under that target's own cc-owned transcript root (`<store>/claude-config/<dirName>/.claude/projects/`), which the standalone CLI does not read — re-registering the project at the same placement is what reaches them again. Response: `{ok, project, killedInstances, system, remoteId, path, directoryDeleted}`.
- **Adopted projects** — a directory that already exists anywhere on disk becomes a project — a git repo or not — without being copied or moved. Sidebar ≡ → **+ Add project**, MCP `adopt_project({name, path, system?, remoteId?})`, or `POST /api/projects/external`. **Nesting under the projects root is legal**: a container directory there can hold projects at any depth, and only the ones adopted are projects.
  - **Layout** — the record at `<store>/projects/<name>/project.json` carries `location: {kind:'local', path}` and IS the registration. Nothing else is written outside the store.
  - **The Adopt dialog** (`public/adoptProjectDialog.js`) — opened from the sidebar ≡ overflow panel. **Name** + **System** + **Directory**, plus a list of suggested directories from `GET /api/projects/suggestions`. The list is an **input helper for the Directory field**: clicking a row fills Directory (and Name, from `suggestedName`), and Submit always POSTs whatever is in the field — so adopting a path from anywhere on disk is the *same* action, typed rather than clicked, not a second flow.
    - **Where the tree lives** — the **System** picker offers the built-in **This machine** (the default) plus every registry row with a provider command, and choosing one reveals an optional **Remote** (the target's name; blank for the provider's default), exactly as `+ New project` does. Directory then means a path on that machine, so **changing the machine empties Directory** — a path on one machine is not a path on another, whether it was typed or clicked out of the list — and the suggestion list is **hidden** with its note retargeted to *Type an absolute path on remote 'r' of system 's' — cc cannot list directories there*, because the scan is of cc's own disk. A **relative path on a system is refused in the dialog**, before any request; a relative path with no system is left to the server, so a local adopt surfaces the server's own refusals, and a local adopt posts only `{name, path}`. If the registry cannot be read the dialog **says so** (*Could not read the systems registry (HTTP 503) — only this machine is offered*) and still offers this machine — a registry that answers with only the local row says nothing, so "cc could not ask" and "nothing is registered" are distinguishable.
    - **What the scan offers** (`src/projectSuggestions.ts`): unregistered directories under the projects root, `SUGGEST_MAX_DEPTH` levels deep, `.git`-bearing ones ranked first then `relPath` ascending. Five rules, each derived from a refusal `adopt_project` would otherwise answer: **dot-prefixed directories are skipped** (which is what keeps the store, `.worktrees`, `.plugins` and `.conduct` out — there is no second exclusion list); a **registered project is skipped AND not descended into**; the walk **stops descending at a `.git`-bearing directory** (every descendant is `TARGET_INSIDE_REPO`); **symlinked entries are neither offered nor followed**; and breadth is bounded by `SUGGEST_MAX_DIRS`, with `truncated` and `unreadable` surfaced in the dialog's scan note so an absent directory is not read as "cc looked and it is not adoptable". No `git` is run — a `.git` stat answers both the ranking and the stop-descend rule.
    - **A stale record** (`PROJECT_EXISTS_STALE`) swaps the dialog to a second pane naming the path the record still points at and the three `discards` counts, with **Relocate** / **Replace** re-sending the same target as `onStaleRecord`. A `PROJECT_PLACEMENT_IN_USE` refusal of a Relocate is rendered **on that pane**, so Replace stays one click away.
    - **Refusal wording** — every `reason` is shown to the user and a bare `code` never is. Two are reworded, because the server's remedy clause is written for an API caller: `TRANSCRIPT_DIR_COLLISION`'s "Pick another name." becomes "Pick a different directory…" (the transcript directory is keyed on the cwd, which the project name never enters, so renaming cannot help on the adopt path), and `PROJECT_PLACEMENT_IN_USE`'s "pass `onStaleRecord:'replace'`" becomes "choose Replace below". Each replacement is keyed on a byte-exact tail of the server's sentence and **replaces** that clause rather than stacking a second remedy; a sentence that no longer matches renders verbatim.
  - **A corrupt record does not strand its directory.** A `project.json` that cannot be parsed lists as a degraded row with an empty `path` — which names no directory, so it suppresses nothing in the scan and nothing in the transcript-key guard (`registeredPlaces` skips it for the same reason). Its tree is therefore **offered as a candidate, and adopting it under a free name succeeds**: that is the recovery, not a hazard. The degraded row stays listed and stays deletable (`getProjectForDelete` tolerates a record it cannot read), and re-using the corrupt *name* is refused `PROJECT_EXISTS` naming that repair.
  - **Paths are REALPATHS.** `resolveProjectDir` / `getProject` (`src/projects.ts`) hand back the target's realpath, never a symlink, and `list_projects` / `GET /api/projects` report that. Load-bearing: the Claude CLI encodes its `<configDir>/projects/<encoded-cwd>/` session dir from `getcwd()` (always the realpath) and walks `CLAUDE.md` upward along the realpath, with no env lever — a logical-path project would strand every resume. `<configDir>` is `~/.claude` for a local place and the target's own cc-owned config directory for a remote one; the cwd half is what this bullet is about, and it is the same either way.
  - **Refusals** (returned as `{ok:false, code, reason}`, never an error): `INVALID_NAME` (bad charset, or dot-leading — reserved for orchestrator-managed projects, which is what stops an adopted project shadowing `.conduct`), `INVALID_TARGET_PATH` (not a non-empty absolute path), `TARGET_NOT_FOUND`, `TARGET_NOT_A_DIRECTORY`, `TARGET_ALREADY_MANAGED` (already registered under another name, or the target CONTAINS the projects root), `TARGET_IS_CC_STATE` (inside `<store>`, `<projectsRoot>/.worktrees/` or `<projectsRoot>/.plugins/`), `TARGET_INSIDE_REPO` (a *subdirectory* of a git repository — `reason` names the toplevel it found), `TARGET_NO_WORK_TREE` (a bare repository, or a repo's own `.git`), `PROJECT_EXISTS` (the name is held by a project whose path still resolves), **`PROJECT_EXISTS_STALE`** (the name is held by a record whose path no longer exists — carries `heldPath` and `discards:{attachments,debug,worktrees}`; re-call with `onStaleRecord:'relocate'` to repoint that record and keep its stored state, or `'replace'` to discard the state and register afresh; a `relocate` of a project **on a system** is itself refused `PROJECT_PLACEMENT_IN_USE` while it has registered worktrees — a remote worktree derives its path from its parent's and its checkout does not move, so the two would diverge permanently), **`PROJECT_EXISTS_UNRESOLVABLE`** (the name is held and cc could not ask whether it still resolves, so it cannot tell a moved project from a machine that is merely down — relocation is not offered), `INVALID_STALE_ACTION`, **`TRANSCRIPT_DIR_COLLISION`** (the transcript directory the project would use is already held — see **Two places cannot share one transcript directory** below; `reason` names the holder), `SYSTEM_UNREACHABLE` (the named system could not be resolved, or stopped answering mid-probe — this also carries `SYSTEM_NO_REMOTES` / `REMOTE_NOT_FOUND`), `INVALID_REMOTE_ID` (unusable, or given without a `system`). Every check runs before the record is written, so a refused adopt leaves nothing behind.
  - **cc writes into the adopted directory, at adopt time.** `<target>/CONVENTIONS.md` is created/overwritten with the composed document (app-owned, no sentinel), and `<target>/CLAUDE.md` gains an `@CONVENTIONS.md` line — prepended, every existing byte kept below it; already present ⇒ no write at all. That is the only channel the workspace conventions have, so it is unconditional and not skippable; **in a git target both land as uncommitted changes in the user's repo.** Recomposition is a pure function of the selections, so repeat sweeps are byte-identical and a git target is dirtied exactly once.
  - **Worktrees live in cc's own area** — `<projectsRoot>/.worktrees/<project>/<key>`, wherever the project's tree is: cc owns that directory, and the user's parent directory is not cc's to scatter checkouts in. They never surface as projects — nothing without a record does.
  - **A vanished target still LISTS** — resolution is a record read, so a project whose tree was unmounted, moved or deleted keeps its row (its git facts go unknown) and stays deletable. Re-adopting the name at the new path answers `PROJECT_EXISTS_STALE` with the two repairs.
- **Projects on a system** — a project's tree, git repo and shell commands can live on a registered **system** (Settings → Systems) instead of on the machine cc runs on. A third placement: neither in-root nor adopted.
  - **A system is an endpoint; a TARGET is what it serves.** One registered system can serve many targets — one `docker exec` provider talks to the daemon on behalf of every container — so ten containers are one Settings row and one provider process, not ten of each. Which target a project is on is chosen **per project**, by its `remoteId`, and all three of `(system, remoteId, path)` together identify a tree: the same path on two targets of one system is two different projects. **Absence of `remoteId` means the provider's own default target**, exactly as absence of `system` means cc's own machine.
  - **Creating one** — `+ New project` offers a **System** picker (the built-in **This machine**, the default, plus every user row that has a provider command — a row with none is skipped, since a project on it could never be opened) and, when one is chosen, the absolute **path on that system** plus an optional **Remote** (the target's name — a container name, a hostname, a VM id; left blank for the provider's default). The `mkdir`, `git init` and seed files all happen there; under the projects root there is no tree and no directory — only the `<store>/projects/<name>/` record, which IS the registration, exactly as for a local project. Adopting an existing tree on a system is the same **System** + **Remote** pair in the Adopt dialog (≡ → **+ Add project**), `adopt_project({name, path, system, remoteId})`, or `POST /api/projects/external` — every check (realpath, directory, enclosing-repo + work-tree) runs on that target.
  - **Changing the target** — `set_project_remote({project, remoteId})` / `PUT /api/projects/:name/remote`, or the **Change target** dialog behind a remote project's **system pill** in the sidebar (the pill reads `<system>/<target>`; it is a control only when the system is reachable, since the change verifies the new target there before persisting). `remoteId:null` (or `""`) clears it back to the provider's default; **omitting the field is refused**, not read as a clear. It is **refused 409 `PROJECT_PLACEMENT_IN_USE`** while the project has live sessions or registered worktrees, and the refusal **names whichever of the two is blocking** (the parts are `Boolean`-filtered, so a project blocked only by worktrees is not told about sessions) while the 409 BODY always carries both `instances` and `worktrees` arrays — kill the sessions and delete the worktrees first; nothing is discarded for you. A permitted change leaves no cc-owned copy of the old target behind — there is none to leave, so the clobber a stale local root once made possible is unreachable rather than cleaned up.
  - **`remoteId` is not a slug** — container names, hostnames and VM ids legitimately carry `_` and `.`. It must be non-empty after trimming, at most `REMOTE_ID_MAX` characters (`src/projects.ts`), and free of whitespace and control characters. A `remoteId` with no `system` is a 400: cc's own machine is one machine.
  - **Layout** — the record IS the registration: `<store>/projects/<name>/project.json` carries `location: {kind:'remote', system, remoteId, path}`. No directory. Names stay globally unique, and the same path on two different targets is two different projects.
  - **Worktrees** — created **on the system**, at that system's `worktreesDir` when Settings → Systems sets one, else `<dirname(project path)>/.worktrees/<project>/<key>`: cc owns no area on another machine, so the default sits beside the tree that is already there. Same `<root>/<project>/<key>` shape as the local layout — no per-kind exception.
  - **What works** — worker sessions (below), the project list and its git facts, worktrees, diff, status, merge, sync, the **in-tree** `post-worktree-create.sh` hook, conventions materialisation, and every `project_*` tool.
  - **What does not** — `project_bash` runs in a plain login shell there (claude's own restored shell bundle is a file on cc's machine). A **store-sourced** `post-worktree-create.sh` is skipped with `STORE_HOOK_LOCAL_ONLY` in its own report — it lives under cc's store, and putting a cc-owned file on the system is a later phase; the in-tree hook works. Plugin **backends** and repo-tracked **`claudePlugin` dirs** stay local-only — see [plugins.md](plugins.md).
- **Worker sessions on a system** — spawning works exactly as on a local project; what changes is where the worker's tools land. The `claude` CLI always runs on cc's machine (a system cannot be assumed to host node or Claude credentials), so cc puts it inside a **chroot onto a union filesystem** whose root is the system's, and redirects `Bash` to run there.
  - **Where the worker works** — the CLI's working directory **is the project's own path on its system**. There is no cc-owned local session root any more, nothing is pulled ahead of a spawn, and a file has ONE spelling whichever tool names it. Its CLI is pointed at that remote's own config directory (below), so the transcript directory it derives from that cwd cannot be another machine's. What makes the cwd itself possible is the **FUSE-union chroot** ([architecture.md](architecture.md)), which is **mandatory** for a worker on a system — a host that cannot mount it refuses the spawn rather than running the worker somewhere wrong: the filesystem decides which bytes appear at a path, so `Read`/`Write`/`Edit` need no translation — they are hooked only to REFUSE a path the union does not serve to that session, and never to gate one (a read on a remote project raises no permission card, exactly as locally).
  - **Each remote gets its own CLI config directory.** The Claude CLI names its transcript directory `<configDir>/projects/<encodeCwd(cwd)>`, and a remote-backed worker's cwd is the remote's own path spelling — so `/root/app3` on two boxes would be one directory. cc gives every `(system, remoteId)` a config directory of its own at `<store>/claude-config/<dirName>/.claude/` and launches the worker with `CLAUDE_CONFIG_DIR` pointing at it, so the root differs per machine. `encodeCwd` is unchanged; only the root it joins to moved. **A local project is untouched** — same directory as before, byte for byte.
    - The directory is a **symlink farm** over the host's real config dir: every top-level entry is linked, so settings, plugins, skills and history stay shared and are edited in one place. These are not linked — `projects/` (the isolation itself), `.claude.json` (its lock is not realpath-resolved, so sharing it loses writes, and its `projects` map is cwd-keyed and would leak allowed tools and trust acceptances between remotes), `.credentials.json` (reached through `CLAUDE_SECURESTORAGE_CONFIG_DIR` instead) and `backups/` (its contents are `.claude.json` backups and nothing else, so sharing it lets one config's churn evict another's last backup, and makes the CLI's missing-config recovery offer a foreign config for restore). The farm is rebuilt before every spawn, so an entry the CLI adds in a later version starts being shared; a real file cc did not create, at a name cc links, is left alone and reported once.
    - **Plan mode** writes to the worker's own `<configDir>/plans`, which is a link to the host's `~/.claude/plans` — so plan files still accumulate in one place, and a worker cannot name another remote's config directory through a file tool.
  - **Two places cannot share one transcript directory.** Creating or adopting a project, or creating a worktree, whose **transcript directory** is already held is refused **409 `TRANSCRIPT_DIR_COLLISION`**, naming the holder and saying whether the two are literally one directory or merely encode alike (`_` and `.` both become `-`). The comparison is on the whole directory, so what it now refuses is what genuinely IS one directory: **two places on one target** at one path, and **two local places** whose cwds encode alike. Two systems at one absolute path, two targets of one system, and a remote plus a local project at one path are all registrable. A session that ran on a system is still **locatable by `sessionId` alone**, and its transcript is READ from cc's own disk, so an unreachable system refuses a spawn but never a read.
  - **How wide the remote tier is, is the provider's to say.** A provider may advertise a **mirror root** and an **exclude list** per target (`describeRemote`, [systems-protocol.md](systems-protocol.md)). Advertise nothing — the default, and every provider that predates the frame — and the answer is the **narrowest** one: the project's own path. Advertise a root **above** the project and that wider slice is served from the system too, so a worker can reach a file outside the project tree at its real path. The advertisement is read **once, at create, and pinned for the session**. A provider that answers differently on a later connection generation makes the next relaunch refuse **501 `MIRROR_ADVERTISEMENT_CHANGED`**, naming both geometries: a session cannot continue at a shape it did not start under, and there is no local image left to rebuild at a new one. Refused at spawn: **501 `MIRROR_ROOT_EXCLUDES_PROJECT`**, **501 `MIRROR_EXCLUDE_COVERS_PROJECT`**, **502 `MIRROR_ADVERTISEMENT_INVALID`**. An exclude *outside* the mirror root is inert and reported on the session's event stream, never a refusal.
  - **`Bash` runs on the system** — **one fresh shell per command**, exactly as locally: each local `Bash` call gets a brand-new shell and the CLI resets the working directory to the project root (measured on CLI 2.1.258), and a redirected one behaves the same way. So nothing carries between two commands — not `cd`, not `export`, not a shell function, and not between agents in either direction. **A command that ends somewhere else is told so**, on stderr after its output: cc names where it ended and where the next command will start, because a `cd` that silently vanished is worse than one that is announced. Commands that did not move the working directory are told nothing, matching a local session's silence. **Output streams as it arrives**, not at exit: a long build or test run is visible while it is still running, and a backgrounded command's output accumulates in its task file as it goes rather than appearing at exit. stdout and stderr stay on their own descriptors, and the exit code is still the command's own. A command that dies without finishing still delivers what it printed first. **Commands run concurrently** — nothing takes a turn, so two agents' commands, or a session's own, overlap freely. **A command's own `timeout` does not cut it short**, exactly as locally, where a foreground Bash past its `timeout` is handed to you as a background task and keeps running — a redirected one is handed over the same way. That it then **keeps running on the system** follows from cc never being told to stop it, and has not been observed directly — treat it as the expected behaviour rather than a verified one. cc is not even told the number and needs it for nothing. What does bound it is cc's per-command ceiling, set just over the built-in Bash tool's **documented** maximum so it never cuts short a command that tool would still be waiting for — a `timeout` above that documented maximum is untested territory, and `ORCH_SHELL_COMMAND_TIMEOUT_MS` is the knob that raises cc's ceiling back above it.
    - **Output is fenced at 8 MiB per command.** Past it the command is killed and the call fails, naming the limit — cc accumulates a command's output in its own memory while it runs, and a truncated success would be read as the command's real output.
    - **Interrupting cancels that call and nothing else.** A call cancelled before it crosses never runs on the system at all; one already running is stopped there, through its own command's kill signal — so a concurrent command is untouched. Ending the session stops every command it still has running, rather than leaving them to finish on a machine nobody is reading.
    - **A backgrounded job returns immediately and outlives its command, as it does locally**, and the command still reports its own exit code and its own output. Every shape behaves the same way — `cmd &`, `cmd & disown`, `setsid cmd &`, and `nohup cmd &` **with or without** an output redirect — so there is no form to prefer and nothing to work around. (`nohup` alone diverts a TTY, not a pipe, so the redirect is the half that could matter — and here it does not.) **Measured on cc's reference provider** — same-host and across a real container boundary, in both capability configurations; a third-party provider is not covered by that measurement. Before the fix a job holding the command's stdout open kept the provider from ever reporting the command's exit, and a command that exited 0 reached the worker as a failure with an empty stdout, minutes late; cc now settles a redirected command on **its own framing sentinel**, which is where the output ends by construction.
  - **`Glob` and `Grep` are unavailable — removed from the registry AND refused by name**, and the second guard is not a leftover: a marked CLI's `Grep` spawns an **unmarked** `rg`, which the union routes as a stranger, so it would search the wrong side and return silently wrong results rather than failing. A search also cannot be redirected the way `Bash` can — a tool result can be annotated but never replaced. Re-enabling them needs mark inheritance, which is measured closed. The refusal names `find`/`grep` through `Bash`, which runs on the system. The cost is coverage confidence, not correctness.
  - **The worker is told**, in two sentences at the top of the project's `CONVENTIONS.md`: where the tree is, that `Bash` runs there, and that **the same path names the file for every tool** — the CLI is chrooted at the system path, so there is no second, local spelling of it. It deliberately makes no claim about *where* such a path can appear: both earlier wordings of this sentence made one and both were falsified, one by telling the worker to read at a local path and never at the system path — which would now forbid the only path that works. It says nothing about shells or where a command starts: that is delivered at the point of use, by the notice on the one command whose `cd` was discarded.
  - **Refused before it starts** — **501 `REDIRECT_HOOKS_DISABLED`** when any scanned settings file sets `"disableAllHooks": true`. That switch turns the whole redirect off: the worker's commands would run on the orchestrator's machine while every result claimed the system, and no edit would reach it — and because it leaves `permissions.*` working, nothing else would fail loudly. **501 `BASH_RULES_NOT_ENFORCEABLE`** when a `Bash(…)` pattern rule appears in `permissions.deny`/`ask`. Both scan the same files: the project's own `.claude/settings*.json` **read through its `System` handle** (they live on the system; there is no local copy), `~/.claude/settings.json`, and `/etc/claude-code/managed-settings.json`. Redirection rewrites every command into one forwarder invocation, so the CLI — which matches rules against the rewritten command — could no longer tell two commands apart and the rule would apply to nothing. cc does not reimplement the matcher; it names the rules and their files and declines. **501 `WORKER_SESSIONS_NEED_A_SHELL`** when cc cannot run a command on the system at all. **501 `FUSE_LAUNCHER_UNRESOLVED`** when the `claude` CLI does not resolve to an absolute path on cc's own machine — that path is the union's marking event and the CLI's only host pin, so a session started without one would mark no caller and pin no launcher; the message names `CLAUDE_BIN` as it was set and the repair. (A session whose launcher runs the CLI **inside cc's own process** has no chroot and no marking event, and is exempt.) **501 `FUSE_BACKEND_UNRESOLVED`** when the session's **backend** launch command — the template's first token — does not resolve on cc's own PATH; the message names the backend, the token it tried and the template. It is refused **for attribution, not for pin correctness**: that command runs unmarked inside the chroot and needs no host pin, but an unresolvable one fails the launch inside `setpriv`, deep in the chroot, naming nothing. Same in-process exemption. Three more come from the mirror advertisement — **501 `MIRROR_ROOT_EXCLUDES_PROJECT`**, **501 `MIRROR_EXCLUDE_COVERS_PROJECT`**, **502 `MIRROR_ADVERTISEMENT_INVALID`** — described under **How wide the remote tier is** above, plus **501 `MIRROR_ADVERTISEMENT_CHANGED`** on a relaunch after the provider moved it. Two more are asked **LIVE at every launch**, because a machine that stopped after cc connected is invisible to every memoised answer — and for a union-mounted worker "discovered at first use" means inside its own chroot, with every project path answering -EIO and nothing there to say why: **502 `FUSE_REMOTE_UNREACHABLE`** (the system did not answer a live check; it names the remote, the system and the far side's own reason) and **501 `FUSE_MIRROR_ROOT_ABSENT`** (the system is up and the advertised mirror root does not exist on it — every file tool in the session would be refused as outside it). Both run before the mount is prepared, so a refused spawn creates nothing. All of these refuse the SESSION and nothing else: the project keeps its row and every `project_*` tool still works, because none of them consults the mirror.
  - **When the project cannot be resolved** — an unregistered system, one with no provider command, one that is down, or a record naming a system with no `systemPath`: the project **keeps its row** in every listing, carrying `systemUnreachable` with the reason; its git facts are absent rather than invented. The sidebar row shows a red **system pill** with the refusal in its tooltip and hides the controls that would fail; delete stays, and works — unregistering never reaches the system, at any layer, so a project on a system that is down (or one whose record is malformed) is never stranded holding its system row at 409. Its worktree **registrations still list** — they are cc's own records and need no system — with their divergence unknown rather than invented. Addressed-by-name calls refuse: `SYSTEM_NOT_REGISTERED` (501), `SYSTEM_NO_PROVIDER` (501), `SYSTEM_UNREACHABLE` (502), **`SYSTEM_NO_REMOTES`** (501 — the record names a target but the provider does not serve named targets; drop the target or upgrade the provider) and **`REMOTE_NOT_FOUND`** (502 — it does serve targets, but not this one: the container is gone, or the name is a typo). The two new codes are raised at creation and at every resolution, so a bad target is refused before anything is written and again on every later use. A system that dies MID-operation refuses the same way rather than reporting a git answer, and `merge_worktree` adds `mayHaveCompleted` when the transport dropped after `git merge` was issued — cc cannot know whether it landed.
- **Workspaces** — `≡` hamburger menu hosts `+ New workspace`; nest projects under collapsible `<details>` headers, one workspace per project, empty workspaces persist. Edit (rename / re-pick members / delete) via the ✎ button on each header. Unassigned projects list below the last workspace, as their own section opened by the same dashed rule that opens each workspace; their names start at the workspace labels' x, with the `≡` commit-history button in the caret's column. Workspaces default-collapsed; expand state persists in `localStorage` (`code-conductor:workspaces-expanded`). Stored server-side at `<store>/projects/<name>/project.json`; the workspace set is the union of `<store>/workspaces.json` and any referenced names. Workspace names use the same `^[a-zA-Z0-9._-]+$` charset as project names, capped at 40 chars and barred from starting with `.` (`^[a-zA-Z0-9_-][a-zA-Z0-9._-]{0,39}$`), so a name stays safe as a path segment.
- **Resizable sidebar** — desktop grid layout only (>720px). A drag handle on `#sidebar`'s right edge (`#sidebar-resize-handle`) resizes the column live via the `--sidebar-width` CSS variable (default `280px`), clamped to 220–560px. Persisted in `localStorage` (`code-conductor:sidebar-width`). Hidden below the 720px breakpoint, where the sidebar is a fixed-width slide-in drawer instead.
- **Git status pill** —
  - **Project rows**: amber `↑N ↓M` against the currently-checked-out branch's *configured upstream* (e.g. `origin/<branch>`), using cached refs only (no `git fetch`). No pill when in sync / detached / upstream-less.
  - **Worktree rows**: same shape but compares the worktree branch to its captured *parent base branch* (may be a local branch, not a remote). `↑N` = ahead and FF-able, `↓M` = behind and FF-able, `↑N ↓M` = diverged → rebase needed before merge.

### Worktrees
- **Isolated environments** — "Run in isolated git worktree" checkbox in the new-instance dialog runs `git worktree add <projectsRoot>/.worktrees/<project>/<short-id> -b code-conductor/<short-id> <currentSha>` and spawns the agent with `cwd` set to the worktree. ONE layout for every local project, wherever its tree lives; a project on a system puts its worktrees there instead — see **Projects on a system** above.) The orchestrator captures `{baseBranch, baseSha, branch}` at creation so you can spawn off any branch and land back later. Worktrees survive instance death — re-spawn into the same worktree from the sidebar. The checkbox is disabled with the reason in its hint when the project is not a git repo **or** is a repo with no commits yet (`unbornHead`); the sidebar flags the same state with a `no commits` pill on the project row.
- **Named worktrees** — MCP `create_worktree` / `spawn_instance({createWorktree:true})` accept `name`, slugified (lowercase, non-alphanumerics → `-`, trimmed, capped at `SLUG_MAX_LEN` in `src/worktrees.ts`) into `code-conductor/<slug>` in place of the random 6-hex id. **The store key, the `worktreeName` and the directory basename are ONE string** — the slug — so nothing parses a name out of a path and nothing aliases one spelling to another. A name with no usable characters is refused **400**; a slug whose branch `code-conductor/<slug>` already exists is refused **409**; so is one whose working directory is already held by another place, on any system (**`TRANSCRIPT_DIR_COLLISION`**), checked before any git state is touched — a SEPARATE 409 from the branch pre-check below, on a different subject. That branch-ref check covers both of ITS collision cases — a still-registered worktree (whose branch git won't let you delete while it is checked out) and a worktree that was deleted but left its branch behind — and its value is the clean 409 in place of the 500 `git worktree add` would otherwise raise. Worth setting for a worktree others will be based on, whose branch is read in `git log` long after it was created. There is one spelling per worktree, so every worktree-addressing input takes the slug exactly as it is reported (see [protocol.md → Input params](protocol.md#mcp-tool-protocol)). No GUI affordance — the browser checkbox still creates hash-named worktrees.
- **Two-step rebase-back**:
  - **Sync** — already in sync → no-op; purely behind & clean → server-side `git merge --ff-only <baseBranch>`; diverged & clean → orchestrator attempts `git rebase --rebase-merges <baseBranch>` directly (`rebased` on success) and on conflict aborts cleanly and returns `rebase-conflict`; behind-but-dirty → `commit-required`. **Sync never prompts an agent.** Those last two are `ok:true` results carrying `branch`/`baseBranch`/`baseSha`/`ahead`/`behind` plus a rendered `rebasePrompt` — two briefs (commit-then-rebase, or rebase-by-hand from a clean tree), both telling the agent to run the same `--rebase-merges` command, to consult the user via `AskUserQuestion` on non-trivial conflicts, and to reply `REBASE_DONE`. Neither brief claims an earlier rebase attempt: a dispatch can arrive after the worktree's state has moved, so the conflict brief asserts only the standing invariant (the orchestrator aborts a failed rebase, never leaves one half-applied) and tells the agent to verify with `git status` — and to say so if the branch turns out to need nothing. Dispatch is the caller's own explicit step: the conductor `send_prompt`s the text to whichever worker should do the work; the GUI confirms, naming the session, then `POST /api/instances/:id/rebase-prompt`. **`--rebase-merges` is load-bearing** on every path: a branch that other worktrees merged into carries their merge commits, and a bare `git rebase` flattens them silently, looking like a clean sync.
  - **Merge** — `git merge --no-ff --no-edit <worktreeBranch>` on the parent. Always produces a merge commit (default msg `Merge branch 'code-conductor/<id>'`) so each contribution stays visible in `git log --graph` and is revertible as one commit. Refuses inline (not as a 500) if the worktree is behind the parent, the parent is on a different branch than `baseBranch`, or the parent tree is dirty. On success, also fast-forwards the worktree's own branch up to the new merge commit (best-effort — reported as `worktreeFastForwarded: true/false`) so a kept worktree lands at `ahead:0/behind:0` instead of looking one commit behind.
- **Delete** — refused if there's a live instance, uncommitted work, or another worktree based on this one, with a `force=1` override.
- **Feature branches (a worktree based on another worktree)** — `create_worktree` / `spawn_instance({createWorktree:true})` accept `baseWorktree: "<worktree name>"`. The new worktree takes `baseBranch`/`baseSha` from **that worktree's HEAD** and its `parentPath` points at that worktree's checkout, so it syncs against and merges into the base worktree instead of the project root. That yields nested history — `main ← merge ← merge ← … ← commits`, one level per link in the chain — lets a multi-stage feature be tested integrated without landing partial work on `main`, and gives a whole feature one reviewable diff.
  - **"Feature" is a position in the graph, not a type.** A worktree others are based on is a feature; a worktree with a `baseWorktree` is a task. The only stored field is `baseWorktree` (`WorktreeMeta`, `src/worktrees.ts`) — absent means based on the project root. `parentProject` stays the **root project name** either way. There are no `*_feature` tools: the existing sync/merge/delete tools do the work.
  - **Chains nest to any depth.** A `baseWorktree` may itself have a `baseWorktree`. Cycles are impossible by construction rather than by check: `baseWorktree` has one write site (`createWorktree`, at creation, naming a record that already exists), so creation order is a topological order and there is no re-parenting API. The `WORKTREE_HAS_DEPENDENTS` *predicate* stays direct-only and is depth-independent — a grandchild cannot exist without its parent record, so the direct child always blocks first — while the *list* it hands back walks the subtree (below). The cost of depth is the freeze: a non-leaf can neither sync nor merge for the union of its descendants' lifetimes.
  - **`WORKTREE_HAS_DEPENDENTS`** — `sync_worktree`, `merge_worktree`, and `delete_worktree` all refuse, listing the blocking worktree names in `reason` and in `dependents[]`, while any worktree record descends from this one. The list is **transitive and deepest-first** — the order they must be deleted in — so the first refusal names the real blocker rather than a child whose own delete then refuses. Every sync path rewrites this branch, which is the base the children were created from; a delete removes that branch outright. The predicate is over **worktree records, not live instances**: killing a child's worker is not enough, the worktree must be deleted. A surviving child whose base was rewritten or deleted under it is genuinely broken, so this is deliberate. The refusal is unconditional on ahead/behind, and on `merge_worktree` it is checked **before** `WORKTREE_BEHIND` — merging needs a prior sync that would also refuse, so this names the real blocker on the first call.
  - **`force` overrides it on delete, and strands the subtree.** `delete_worktree({force:true})` / `?force=1` deletes that worktree's branch anyway, so each surviving **direct child**'s `baseBranch` ref disappears and its next sync fails loudly with "base branch may have been deleted or renamed". Anything deeper keeps an intact base ref but is rootless — its chain no longer reaches the project. Legitimate when abandoning a whole feature including its children; otherwise delete the subtree first. (The project-delete cascade sweeps with `force`, so it is unaffected.)
  - **It applies to the worktree being synced/merged/deleted, never to the one being merged INTO.** Merging task `A` into feature `F` succeeds while `F` still has task `B` based on it: a `--no-ff` merge onto `F` appends to `F`'s history rather than rewriting it. (Were it otherwise, no feature with two children could ever take a merge.) A task's own delete is likewise unaffected by having a base.
  - **Two disciplines, both valid — pick per feature; nothing here prescribes one.** *Serialized*: land child → delete child worktree → sync feature → spawn next child → … → sync → merge feature. The feature tracks `main` continuously. *Concurrent*: several children at once; the feature's base is frozen for that window (its sync is refused), so all `main`-integration risk lands at the end.
  - **Known shortcoming: a task's merge sha is ephemeral.** Each sync of a base rewrites that base's history, so a merge commit into it is renewed every time. Only the **root-most** worktree's landing commit on `main` is durable — don't cite an intermediate merge sha as a stable reference.
  - **Every non-leaf worktree is a merge target, so it must be kept clean.** `PARENT_DIRTY` is evaluated against it and has **no override** (`allowDirty` covers only the *merging* worktree's own tree), so untracked build artifacts there — e.g. from `post-worktree-create.sh` — will refuse every task merge into it.
  - A derived worktree's `post-worktree-create.sh` is resolved from **its base's checkout** (in-tree lookup uses `parentPath`), not the project root — same repo, and a base that edited the hook correctly passes the new one down. `CC_PARENT_PATH` likewise points at the base's checkout.
  - `list_projects` and `list_worktrees` both show the relation as `base <branch>@<sha>` and mark a derived row `← <baseWorktree>` — its own direct base, so a chain is read by joining rows. There is no GUI tree view — the sidebar renders every worktree as a flat sibling row.
- **Post-worktree-create hook** — a `post-worktree-create.sh` script (need not be committed — read from disk, not the new worktree) is resolved from two locations in priority order: **in-tree** `<parent>/.code-conductor/post-worktree-create.sh` first, else the **central store** `<root>/.code-conductor/projects/<name>/post-worktree-create.sh`. When found, the orchestrator runs it automatically with `cwd` in the new worktree, after the worktree directory, branch, and metadata are written. Use case: symlink `node_modules`, copy `.env`, run `npm ci`, etc. The script receives env vars `CC_WORKTREE_PATH`, `CC_PROJECT_NAME`, `CC_BRANCH`, `CC_BASE_BRANCH`, `CC_PARENT_PATH`. Non-fatal: a failure warns but does not roll back the worktree. Output is capped to a tail bound (`HOOK_OUTPUT_CAP`); timeout via `ORCH_POST_WORKTREE_TIMEOUT_MS` (see `src/worktrees.ts`). Kill-switch: `ORCH_DISABLE_POST_WORKTREE_HOOK=1`. Result is reported in the spawn/worktree-create response as `postWorktreeCreate: { ran, source, exitCode, durationMs, output, truncated?, timedOut? }` (`source` is `'in-tree'` or `'store'`). The spawn dialog re-opens briefly with a one-line summary (expandable output) when the hook ran.

### Diff / review & commit history
- **Worktree diff/review** — `±` button on every worktree row opens a full-page, mobile-friendly diff browser (`#review-view`, `public/review.js`). Fetches a per-file **summary** (no hunks, never truncated — a `--numstat`/`--name-status` pass) from `GET /api/projects/:name/worktrees/:wt/diff` (`<baseBranch>...HEAD`) and renders collapsible `<details>` per file (status badge, `±` counts). A file's hunks are fetched lazily via `?path=<file>` only when its card is expanded, and cached on the card so collapsing/re-expanding doesn't refetch; an expanded card shows a brief loading state, then hunks reusing `.diff-line.add/.del/.ctx` with `overflow-x:auto` for horizontal scroll. Failure states per file: a retryable `.review-file-error`, an `.review-file-note` for a binary file (no fetch at all) or an oversized file (`adds+dels > FILE_DIFF_LINE_GUARD`, hunks never fetched), and a truncation note if that one file's raw diff still exceeds `DIFF_BYTE_CAP` (both constants in `src/gitDiff.ts`). Because the summary has no size cap, a change touching any number of files always lists every one, with exact totals.
- **Commit history** — `≡` button on every git-repo project row opens a full-page scrollable commit list (`#commits-view`, `public/commits.js`) of the project's **current branch (HEAD)**: short sha, subject, author, relative date, newest first — and **topologically ordered** (`--topo-order`), which the rail below depends on: a parent never precedes its child, so no lane is ever routed at an already-drawn commit. Backed by the commits endpoint (bounded limit, default in `src/worktrees.ts`; header shows `(showing latest N)` when truncated). Tapping a commit opens the **same diff renderer** showing just that commit's change (`GET /api/projects/:name/commits/:sha/diff`, via `git show`); the diff layers over the list and `← Back` returns to it. Merge commits (parents.length ≥ 2) show the **first-parent aggregate** — the full diff the merged branch brought onto mainline (`git show --first-parent`), not git's default combined/conflict-only diff — and every file in that aggregate is listed regardless of the change's total size. A **branch/merge graph rail** (git-log --graph style) is drawn to the **left** of each row: colored lanes, a dot per commit, diagonals where branches fork and merges converge. Topology is computed client-side in `computeGraph()` (`public/commits.js`) from each commit's `parents` (SHAs from `%P`); lanes use stable column indices so pass-through lines stay aligned. Each rail is a fixed-height SVG "node band" (dot + diagonals) plus full-height CSS filler lines, so it aligns with variable-height (wrapping) rows without measurement. Parents older than the cap / on unfetched branches simply trail off the bottom; a lane aimed at a commit already drawn ABOVE it terminates instead (it could never converge). Every row is badged ahead/already-merged from its **own** `ahead` flag (never from its position — the ahead set is not a contiguous prefix; see [protocol.md](protocol.md)). A divider row labelled `↓ already in <base>`, bound to the section below it, sits above the first already-merged commit — but **only when every row below it is also already merged**, since that is what its label claims. Where the ahead rows are interleaved (a branch that merged its base back in), the badges carry the answer alone and no divider is drawn. A soft lane cap (`MAX_LANES`, `public/commits.js`); extras clamp to the last column, logged to console. The **same view opens on a worktree row's `≡`**, addressed as the pair `(project, worktree)` — the sidebar hands both to `onShowCommits`, exactly as the `±` beside it hands both to `onReviewWorktree`, and every URL the view builds (list, commit diff, working-tree diff) hangs off the worktree-scoped prefix. That pair is what makes the view work for a project **on a system**: the worktree's tree sits beside its parent's on that machine, so nothing under cc's projects root names it. The header titles the worktree, not the parent.

### Sessions & instances
- **Unified view** — Sessions list per project (and per worktree) shows live + historical. Header: `Sessions (N) · K live · last <ago>`. Click to focus live instance, or resume stopped one (`POST /api/instances` with `--resume <sid>`). Synthetic `(new session)` row for spawned-but-no-jsonl-yet instances. Rows bucket into up to three sections: the normal list, then a dim `— temp —` separator, then a dim `— conducted —` separator (each section only renders when non-empty).
- **Conducted sessions** — a session spawned via the MCP `spawn_instance` tool (orchestrator-driven) rather than the browser/HTTP path is marked **conducted** (a worker an orchestrator conducts; the orchestrator itself is the `.conduct` session). Orthogonal to temp: unlike temp (in-memory, wiped on exit) the conducted marker is **durable** — persisted to `<store>/conducted-sessions.json` (a `{sessions:[sid,…]}` set, written on turn-end via the same path as last-prompt/permission-mode metadata) so it survives exit, restart, and `--resume` (a UI-resumed conducted session re-acquires the marker from the sidecar). Set **only** in the MCP `spawn_instance` handler — plain UI spawns stay non-conducted. Grouping precedence: a conducted session renders under `— conducted —`; a conducted **and** temp session renders under `— conducted —` but keeps the warm temp preview colour (`.session-row.temp`); a temp-but-not-conducted session stays under `— temp —`. Pure conducted rows get a cool preview tint (`.session-row.conducted:not(.temp)`). It's a grouping, never a filter — conducted sessions stay fully visible in `list_sessions`, the HTTP session APIs, and the sidebar. The marker is cleaned up alongside the session-title sidecar only on session delete (Settings → Archived); it survives temp-exit archiving and the boot sweep, staying meaningful on the archived row.
- **Live owner + awaiting-user (server-side, no UI yet)** — every live row reports `ownerSessionId`: the sessionId of the conductor at the root of a live worker's spawn chain (null for a hand-spawned session and for anything not live; never on a disk row), and every live and disk row reports `awaitingUser` (`question` / `plan`) + `awaitingUserSource` (`tool` / `text`) while the session's last ask has had no real user message since. Derived from the session's own transcript, so it holds across a restart or resume; never set on a conducted worker. Exposed on `GET /api/instances`, `GET /api/projects/:name/sessions`, `list_sessions` and `describe_session`. Detail: [architecture.md](architecture.md) → "Ownership and awaitingUser".
- **Unread indicator** — small accent pill next to a row when its instance finishes a turn while you're viewing a different session (per-instance, persisted in `localStorage` key `code-conductor:unread`).
- **Archive session (the `×` action)** — the hover-revealed `×` on a session row **archives** it (never deletes): single confirm, `POST …/sessions/:sid/archive`; on 409 the client auto-retries with `?force=1` (stops the live instance) without a second prompt. Archived sessions keep their jsonl (still resumable) + title + conducted markers and **disappear from the sidebar entirely** — they're managed only from **⚙ Settings → Archived**. There is no longer an inline `— archived —` sidebar section, and sessions are never deleted from the sidebar.
- **Archived page (Settings → Archived)** — lists every archived session grouped by owning project (`GET /api/archived`). Each project group is a `<details>` **collapsed by default**; expanding reveals its archived sessions (title/first-prompt/sid + worktree tag + last-active). Per session: **Restore** (`POST …/restore` un-archives it, then resumes/spawns it and navigates straight to it, closing Settings — restoring alone doesn't create a live instance, so the client drives `resumeSession` itself via the `onSessionRestored` callback) and **Delete** (confirm → `DELETE …/sessions/:sid`, the single permanent jsonl-removal path; cannot be undone). The `.conduct` (orchestrator) project's group is always pinned first and rendered as `🎼 Conductor` instead of its raw folder name — sorting/labeling happens client-side in `renderArchived()`.
- **Session summary** — `⋮` menu's `📝 Summarize` opens a modal dialog that generates and displays an AI-written summary of the session via a one-shot `-p --output-format=json` call using the **Fast capability tier**'s bound model/backend, launched through that backend's template — the same `resolveBackendLaunch()` seam `project_bash`'s shell-env bundle uses (see `src/summarize.ts` and [models.md](models.md)). Four options, **Title** shown leftmost: **Title** (a single line in the form `{Project}: <title>`, the title part ≤60 chars, naming the session's *current end goal* — not a recap of what happened, the objective the most recent turns are working toward; the project prefix is the instruction's own output format, not string concatenation). The project name comes primarily from the **conversation itself** — the projects it spawns workers into, the paths/repos it discusses — because a conductor session's own checkout is the hidden `.conduct` project, never the project it's actually orchestrating; the checkout-derived project name (worktree-aware, so a worktree checkout still resolves to its root project) is passed in only as a labelled hint the model may use when the conversation is ambiguous, and is dropped entirely rather than passed through when it would resolve to `.conduct`. If no project can be identified from either source, the model omits the prefix and outputs a bare title. **Short** (~40 content words, plain prose gist), **Medium** (~150 words, scannable recap with bullets/tables), **Long** (~400 words, thorough with `##` headings and structured tables). All four are generated, cached, and rendered identically (same markdown pipeline, same stale badge, same `↺ Regenerate`); the default tier on open is still **Medium**. Title adds one extra affordance: an **✏️ Use as session title** button (shown only when Title is selected and has a cached value) that PUTs the generated text through the same `/api/sessions/:sid/title` path as **Rename** below, sharing its client-side apply logic. The dialog also shows the **cost of the last generation** (`Cost: $0.00xx`, from the POST response's `costUsd`, itself the CLI's `total_cost_usd` — `null`/hidden for a non-Claude backend, same policy as the cost dashboard) — this is **ephemeral**: it clears on open and on every tier switch, is never persisted, and is absent from the GET response. Summaries are rendered as full markdown (headings, tables, code) via the same `renderMarkdownInto` pipeline as assistant messages. A **stale indicator** (`⚠ Session has grown since this summary`) appears when the session has received more turns since the last generation; regeneration is always user-initiated. Stored in `<store>/session-summaries.json` keyed by `sessionId` — `{ short?, medium?, long?, title? }`, each a `{ summary, generatedAt, messageCount }` record (the key IS the tier; cost is never stored); auto-removed when the session jsonl is deleted. That store is cc-owned rather than filename-keyed, so it needs no public→backing resolution; the transcript reads behind the generation do. `sessionId` is stable across `--resume`, renewal and prune, so summaries simply persist.
- **Rename session** — `⋮` menu's `✏️ Rename` opens a prompt to set a custom human-readable label (≤100 chars, empty clears) that overrides the first-prompt preview in the sidebar and prepends an italic chip to the active header. Stored in `<store>/session-titles.json` keyed by the **transcript** id (the session's current backing id — what the sidebar's bulk title load matches by filename, and what `Instance._hydrateTitle` reads), so the REST route resolves the public id a client sends before writing. A session can also name itself via the `set_session_title` MCP tool, which writes through the same `applySessionTitle` (`src/sessionTitles.ts`). Auto-cleaned only when the session jsonl is deleted (Settings → Archived); survives a temp session's exit, since that archives rather than deletes. Survives rewind, `--resume`, renewal and prune — a renewal carries the title onto the rotated id; fork starts un-titled.
- **Change model** — `⋮` menu's `🧠 Change model` (directly below Rename) opens a capability-tier picker (Fast / Balanced / Powerful / Frontier) using the same catalog/source of truth as the spawn dialog (`Settings → Models`). Selecting a tier sends only the **tier name** over WS — the server resolves that row's **current** `{backend, model}` binding and switches the **live** session's model via a `control_request` (`subtype:set_model`) — no restart, no history loss, and no risk of a stale client cache pinning an old model. **The tier's default effort is not applied** — a live switch changes the model alone; move the level with the sibling **Change effort** item below. A switch posts a `Model changed: <from> → <to>` notice in the transcript and blanks the ctx chip to `ctx —` (see the combined chip bullet below) — **re-selecting the tier the session is already on does neither**. The server decides that on the canonical model ids, so a tier whose model carries a catalog launch tag is still recognised as a non-change even though the server resolves the bare version id. The picker highlights the tier the running session is on with `.qs-selected` (display-only, from the client's tier cache). **A session on a non-Claude backend can't switch model live** (the endpoint is fixed at launch): every tier is disabled with a "kill and respawn on that tier" note, and switching a Claude session *to* a tier on another backend is likewise blocked — as is substitution↔substitution (server-enforced too — `409 BACKEND_LOCKED`).
- **Change effort** — `⋮` menu's `⚡ Change effort` (directly below Change model) opens a picker over the level catalog (`EFFORT_LEVELS`, `src/effortLevels.ts`, ordered low → high; the client renders the `efforts` key of `/api/settings/models`, never a literal). Picking a level repoints the **live** session — no restart. There is no `set_effort` control_request, so the server sends `/effort <level>` on the session's stdin and the CLI runs it as a **local slash command**: no model turn, zero tokens, a `$0.00` turn footer. The exchange therefore **shows in the transcript** as a user bubble plus the CLI's own `Set effort level to …` confirmation — deliberately, since the CLI persists that line in the session jsonl and rewind/fork indices count it. **Idle-only**, like 🪒 Prune: mid-turn the item is greyed (`Effort can only be changed between turns`) and the server refuses it `409` — mid-turn the CLI would fold the line into the running turn's input instead of running it. The picker highlights the current level with `.qs-selected`. **No backend is refused** (unlike Change model): nothing here repoints an endpoint. The new level is what every later relaunch that reuses the live value comes back at — per-path table in [models.md](models.md#default-effort).
- **Rewind & fork** — every user message bubble has `↶` (rewind in place, same `sessionId`) and `⑂` (fork to a new `sessionId`) on hover. Both atomically rewrite the jsonl, preserve the dropped prompt in the composer, and 409 during a running turn. Bubbles anchor on the **server-stamped `userIndex`** riding on each outer `user_echo` (the absolute Nth-pure-user-prompt ordinal) — never a client-side bubble count, which would drift once the capped ring / tail-only snapshot starts the view mid-history. An echo without a stamp (rare orphan) renders without the buttons. A fork of a **temp** session is itself temp — the new `sessionId` is marked at spawn and archived on its own exit; the source is untouched and stays temp.
  - Rewinding **to the first user message** is special-cased: prefix is empty, so the orchestrator deletes the jsonl entirely and respawns with `--session-id <sid>` (not `--resume`, which the CLI rejects on zero-line files).

- **Prune** — `⋮` menu's `🪒 Prune` shrinks a session's context **deterministically and at zero token cost**: no LLM pass, no `/compact`. It rewrites a *copy* of the jsonl under a fresh **backing** id, replacing fat block content with size stubs, archives the original (still resumable), and respawns the **same instance** against the pruned file. The session's public `sessionId` does not move, so every reference to it stays valid. The session comes back **idle** — unlike `renew_session`, nothing is seeded as a first turn. Idle-only (the button is disabled mid-turn; the endpoint 409s).
  - **Controls.** A slider over turn boundaries (`cutTurnIndex`, the same pure-user-prompt index space rewind/fork anchor on, so the cut can never land between a `tool_use` and its `tool_result`); its range is `0…turnCount`, so a full prune (newest turn included) is reachable, but the slider's DEFAULT is `turnCount-1` — shedding the newest turn is a deliberate drag to the far right. Plus two tickboxes: **prune all thinking blocks** (global, independent of the slider — thinking staleness is categorical, not temporal) and **minimal tool inputs** (squeeze any string value over 80 chars to a size marker; the default truncate mode keeps the first 500 chars, so a value under ~519 chars shrinks not at all — minimal always saves at least as much). A session with one turn is prunable (only `turnCount === 0` is refused).
  - **What it does in the pruned region.** Tool outputs → `[pruned: 12.4 KB]`. Tool input string values → truncated or squeezed; **path keys (`file_path`/`notebook_path`) and the input's key set are never altered** (see architecture.md → Prune for why this is load-bearing). Thinking text → `[pruned: thinking]`, signature retained, exempt on an assistant entry holding an unresolved `tool_use`. `text` blocks are never touched. A stub that would be *larger* than what it replaces is skipped, so pruning can never inflate the context.
  - **Exempt tools** (`isPruneExemptTool`, sessionPrune.ts) — a `tool_use` **and the `tool_result` answering it** are copied verbatim in every mode, at any cut, for: **`AskUserQuestion`** (the question card is rebuilt from `input.questions` on replay and the answer is recovered by string-matching the question text + option labels against the following user echo — squeezing either strands the human with an unreadable question and no answer on the card) and **core conductor MCP calls**, i.e. `mcp__code-conductor__<tool>` (the orchestration record: what was spawned, approved, merged, filed). Exempt by *namespace*, so a core tool added later is exempt by default. Three things stay prunable: **`mcp__code-conductor__project_read`**, **`mcp__code-conductor__project_bash`** and **`mcp__code-conductor__system_bash`** (bulk file/command output — exactly what Prune exists to shed; a hardcoded denylist, not user-configurable), **plugin-namespaced** tools (`mcp__code-conductor__<plugin>__<tool>` — `code-kanban__*`, `code-hub__*`, and any third-party id such as `acme-tools__*`; what discriminates them is the *further* `__` after the prefix, not the first-party `code-*` naming habit, so matching the prefix alone is not enough), and any foreign MCP server. An *orphaned* `tool_result` (no `tool_use` in context ⇒ no name) stays prunable. Thinking on an assistant entry that carries an exempt `tool_use` is unaffected — it follows the normal thinking rules.
  - **Never deletes an entry or a block** — only block content is replaced. That is what keeps the `parentUuid` chain and the `tool_use`/`tool_result` pairing invariant intact with no relinking.
  - **Read-before-edit re-arms.** A pruned Read/Write result drops the CLI's cached file-state entry, so the model must re-Read before editing that file. At a full cut (`cutTurnIndex === turnCount`, or `prune_session({keepLatestTurns: 0})`) that includes a file the worker read moments ago, so it owes a re-Read before its very next edit. Deliberate: the guard exists to guarantee current file content is in context, and pruning is what removes it. Costs one refused Edit per file, self-corrected by a Read.
  - **Sidechains are untouched** and stay readable — sub-agent transcripts are copied to the new `sessionId` alongside the jsonl.
  - **Fails safe.** A throw partway through (the cut is out of range, the copy fails) respawns the instance against the ORIGINAL, unpruned session rather than leaving it with a dead subprocess — the original jsonl is intact by construction. A prompt arriving while a rewrite is in flight is refused with 409 rather than racing the transform — for prune and rewind that spans the whole kill→respawn, for fork (which never kills the source subprocess) it spans the jsonl read, after which a prompt can no longer affect the copy.
  - **Savings estimate** is a `chars/4` heuristic computed over **in-context entries only**: sidechain entries and the disk-only `toolUseResult` sidecar are excluded (counting them would report a large saving while the model's real context barely moves). **Exempt tools contribute zero savings** but stay in the denominator — they remain in the model's context. The `~X% of conversation tokens` denominator counts every in-context entry kind including **`attachment` entries** (CLAUDE.md / nested-memory / file injections) — Prune never touches them, but they are in the model's context, and omitting them would over-report the percentage saved. The dialog shows a per-category breakdown (thinking / tool inputs / tool outputs) recomputed client-side from one analysis call; the preview and the transform share one code path, and a test asserts they agree exactly for every slider/tickbox combination.
  - **Known degradations.** A pruned `Write`'s `input.content` becomes the harness's cached content for that path, so a later on-disk change diffs against the stub in the watched-file attachment. Pruned `Edit` `old_string`/`new_string` shorten the tool-diff rendering (truncate mode keeps the first 500 chars). The ctx chip reads `ctx —` until the first live turn — the jsonl's newest `usage` still reports the pre-prune size, and a known-wrong number is worse than none.
  - **Also reachable from a conductor** — `prune_session` ([MCP interface](#mcp-interface)), which spells the cut relatively (`keepLatestTurns`) rather than as this dialog's absolute `cutTurnIndex`.
- **Remote worker refusals you can see (FUSE-union chroot).** Spawning a worker on a non-local project mounts a union filesystem and chroots the CLI into it. Four things surface to the user:
  - **`FUSE_UNAVAILABLE`** — a `501` on the spawn naming the FIRST missing dependency and the package that supplies it (`/dev/fuse`; passwordless `sudo -n`, which is cc's **whole** sudoers requirement — nothing rides through sudo, so a plain `NOPASSWD:` rule with no `SETENV:` tag launches a worker; one of `unshare`/`stat`/`rm`/`mount`/`umount`/`nsenter`/`chroot`/`setpriv`/`fusermount3`; `fusectl` in `/proc/filesystems`; `gcc`; or libfuse3 headers). Refused **before** anything is created: no run directory, no mount, no daemon. cc never installs anything.
  - **A file-tool refusal naming its class.** `Read`/`Write`/`Edit`/`NotebookEdit` on a remote-backed worker are decided from the session's tier table (never by probing the filesystem), and a path the union does not serve to that session is DENIED with a sentence rather than left to answer `-ENOENT` — a model that reads a refusal as file-not-found concludes the file is absent instead of using the channel that works. Four classes, four wordings, and which one a worker gets is the whole information:
    - **excluded** — the system advertises a prefix as excluded from file mirroring. Names the prefix, and points at **Bash**, which execs on the system under no such restriction (`cat` / `sed -i` / `>`).
    - **outside the mirror root** — the path is outside the boundary the system advertises. Names the root, and points at Bash.
    - **a bind mount** (`/proc`, `/sys`, `/dev`) — those are the **orchestrator's own**, bind-mounted in so the CLI works, so a file tool there would answer about the orchestrator's kernel. Points at Bash, which answers the same question about the right one.
    - **host-pinned** (and the session's own hidden scaffolding) — the path is pinned to the **orchestrator's** machine so the local CLI can run. Points at Bash and, uniquely, names **which machine Bash answers from**: the same path exists on both, so a shell on the system returns the system's own file there — the right answer for a question about the system, and explicitly not the orchestrator's copy that was refused. Without that qualifier "use Bash" would send the worker to a real file it would mistake for cc's.

    Every one of them states outright that this is cc refusing to carry the file and **not** the file being absent.
  - **Two MORE refusals, about a specific file rather than about a prefix.** These are per-path and STATEFUL — a path acquires one only by failing during this session — and they are asked only after the four above have already ALLOWED the path, so the count of tier wordings stays four. Both keep the same discipline (cc named as the actor, the act named as a refusal, the file named, an explicit *not the file being absent*, and Bash named with the machine it answers from):
    - **diverged** — an earlier write to that exact file was written locally but could **not** be landed on the system, so this session's copy and the system's have parted. Names the recorded cause, refuses every file tool **except `Read`** — the local copy is intact and still readable, and that is the recovery channel the sentence points at — and tells the worker to inspect the system's own copy with `cat` and land the change with `sed -i` or a `>` redirect **on that machine**. Sticky for the session's life, with one exception: if a later write to that same file **does** land on the system, the divergence is over and the refusal stops — that is the only thing that clears it. It also arrives **as a note on the tool result** when the failure lands after the tool already returned success, which is the only way a post-return failure reaches the worker in band.
    - **over cap** — the file is larger than the system protocol carries per file (`MAX_FILE_BYTES`, 32 MiB). Names the **size and the cap**, refuses `Read` as well (cc never materialised it, so there is nothing to serve), and names the channel that works: a **range** read through Bash — `sed -n`, `head`, `tail` — on the system. Refused before a byte moves.
  - **What a worker can still read on the orchestrator, and one accepted leak.** A short declared list stays reachable to file tools because Bash — which execs on the system — cannot see it at all, so denying it would make it unreachable through every channel at once: this project's **attachments** dir, this session's **own** tmp dir, each enabled **plugin's root** (its skills instruct the model to read files under it), **its own remote's `<configDir>/plans`**, where plan mode's `Write` lands, and **`~/.claude/plans`**, where a plan file forwarded from another session lives. Everything else under its own config dir is denied — including its own `projects/` — and so is **every other remote's config directory**, which holds those remotes' transcripts and settings. Everything else under `~/.claude` is denied too, including `~/.claude/projects` — every local session's transcripts. **The accepted residual:** `~/.claude/plans` accumulates other sessions' plan files and cannot be narrowed to "its own" ahead of the write, because the CLI chooses the filename. It is allowed anyway — denying it breaks plan mode outright for every remote-backed worker — and it belongs beside the standing limit that **a chroot is not a security boundary**.
  - **A path nobody pinned is ABSENT to the CLI inside the chroot, not quietly the orchestrator's** — at the default mirror root, which is the project's own path. The union serves the system's tree at the project's own path, the orchestrator's own files at a declared set of pinned prefixes, and **nothing at all** anywhere else — so the CLI reaching an unpinned path gets `-ENOENT` rather than the orchestrator's copy. That is deliberate: one path answering from whichever machine happened to have it is the confusion this whole arrangement removes. **Bash is the channel** — it execs on the system and reaches the system's whole filesystem. Anything the CLI itself genuinely needs is pinned; if something is missing, the session's `events.log` in its run directory names the exact path, and the store-wide `systems/fuse/events.log` keeps it after the session is gone — with the array in `tierTable.ts` to add it to.
  - **The sandbox is the CLI's, not every process in the chroot's.** The shells, hooks and helper subprocesses the CLI spawns — and, before the CLI exists at all, the launch chain that starts it: the chroot'd shell, the privilege-dropper, and the backend launch command a non-Claude backend puts in front of the CLI — are separate processes that were never going to be served the system's files, so **the union subtracts nothing from the orchestrator's own filesystem for them**: wherever the orchestrator has something, they get it — its real contents, its real mode, its real write surface — and they get it at **every** mirror root, not just the default one. That is what lets a shell load its libraries and `rg` run without cc having to pin every tool on the machine. The **system's tree stays closed to them** for reads and writes alike: the remote tier is simply absent from their view of the table, so no such process can name it. The only thing added for them is entry to the CLI's own working directory — each component made traversable, by the orchestrator's own directory where it has one and by an empty traverse-only node where it does not — so a spawn can `cd` there and start at all, and so can the launch chain itself. **A backend launcher's own files are the orchestrator's**, therefore: it reads its configuration and writes its state on the machine it was installed on, and anything it hands the CLI through a file has to sit somewhere both see the same bytes — `$HOME`, the projects root, or another host-pinned prefix. Two consequences worth stating: such a process reaches whatever its uid could already write on the orchestrator at any path cc did not pin (every one is logged by path), and cc's own run directory — which holds the mirror and the control socket — stays hidden from it, because that is the one place the system's bytes live on this machine.
  - **ONLY THE FIRST OF THOSE IS THE DEFAULT MIRROR ROOT'S; THE SECOND HOLDS AT EVERY ROOT.** Where a provider advertises a mirror root **above** the project, the wider slice is remote-tier — so for **the CLI** there is no "nobody pinned it" tier left at all, and the first bullet reads differently: it is served the **system's** answer at an unpinned path rather than `-ENOENT`. For **everything else in the chroot nothing changes**, and that is deliberate: the remote tier is struck from their view whatever its extent, so a wider advertised root cannot take away a single byte of the orchestrator's filesystem from a shell or a helper. A helper that needs a host library cc did not pin still gets it, and the session's `events.log` still records the path — as a `served`/`unmarked-host-served` row, which carries **no pin suggestion**: `pinSuggestionFor` fills those columns only for the marked CLI's own `deny`/`unpinned-fail-closed` rows, because a path that was served needs no repair. The row is still the instrument — it names the path, and the pin list is derived from it by hand. Nothing about the **system's tree** differs between the configurations either: it is closed to every process but the CLI in both. *(Both halves are load-bearing: a wide root that did NOT strike the remote tier from their view would take the orchestrator's filesystem away from helpers, and under one where the mirror root is a strict ancestor of the project path it would also make the working directory unenterable, so every `Bash` call in the session would fail with no output.)*
  - **The wedged-mount report** — where teardown cannot finish, the session's event stream carries a `system`/`stderr` line naming the terminal state, the surviving mountpoints, the daemon pid and the connection minor; the same line goes to the orchestrator log, and the on-disk record is kept so the next boot re-reports it. A wedge is never silent — and a session whose worker, daemon or mount-namespace anchor is still alive **is** a wedge, so cc never discards the record that names a process it left running.
- **Crash recovery** — subprocess death → `crashed`; Resume respawns with `--resume <sid>`, preserving the in-memory event ring + conversation.
- **Session anchor** — `#session=<sid>` URL hash; on reload, auto-resumes by locating the jsonl on disk (worktree-aware) via `GET /api/sessions/:sid/locate`. `--resume` spawn costs zero API tokens until the next prompt. Stale anchors are silently cleared.

### Spawn options
- **Mode** — `plan` (read-only, propose then `ExitPlanMode`), `ask` (every destructive tool gates through Allow/Deny card), `code` (full power, CLI's `bypassPermissions`). CLI's `default` / `acceptEdits` are not exposed: in `stream-json --print` (no SDK `canUseTool` callback) they auto-deny tool calls and the only recovery is forcing the model to regenerate the entire tool input.
- **Effort** — `low` / `medium` / `high` / `xhigh` / `max` (`EFFORT_LEVELS`, `src/effortLevels.ts`). **A separate axis from the tier/model binding** — how hard it reasons, not which model. The dialog's Effort select opens on `Default (<level>)`, which sends no `effort` and lets the server resolve the selected **tier's** default (set per row in Settings → Models; the Conduct button resolves the **Conductor role's** instead). Picking a level overrides it for that one spawn. A **resume** names no tier/role, so a sidebar/anchor resume falls back to `DEFAULT_EFFORT` (`high`), while a respawn or a post-restart resume keeps the level the session was already running at. Precedence + per-path table: [models.md](models.md#default-effort). A running session's level can be moved without a restart — see **Change effort** above.
- **Thinking** — `adaptive` (default) / `enabled` / `disabled`.
- **Model** — pick a capability tier (Fast / Balanced / Powerful / Frontier; a tier hidden if disabled in Settings → Models). There is no empty option — the dialog renders one card per tier and pre-selects the **default spawn tier** (Settings → Models); the dialog POSTs only the tier name — no `model`/`backend` — and the server resolves it against that row's **current** binding. Each tier binds to a **backend + model**; the backend is a row in the user-managed **backend registry** (`claude` runs the CLI directly, any other row wraps it via a command template — Settings → Backends). A tier on a non-Claude backend resolves straight to its model id (no version choice) and its declared native context window drives both the context-usage bar and the cc-managed `CLAUDE_CODE_AUTO_COMPACT_WINDOW` + `CLAUDE_CODE_MAX_CONTEXT_TOKENS` at spawn. Every model — Claude or not — has exactly one native window, so there is no window picker. MCP `spawn_instance` also accepts a **role** name — built-in, user-custom, or plugin-owned (`<plugin-id>/<slug>`) — a legacy family alias (`opus`/`sonnet`/`haiku`/`fable`, → that family's default version), or a full Claude model id; **omitting `model` on a fresh spawn resolves the default spawn tier's binding** — this tool has no `tier`/`role` argument, so that is always the row it lands on, whereas `POST /api/instances` applies the same never-the-account-default rule but prefers a named `role`, then a named `tier` ([models.md](models.md#same-row)). A resume with no `model` recovers the model **and backend** it last ran. Full contract — registry, custom models, tier/role binding + dead-binding revert, context-window policy: [models.md](models.md).
- **Temp session** — archives on exit (jsonl kept and stays resumable, sibling `subagents/` dir deleted), drops itself from the sidebar's Sessions list on exit/crash (no ghost row to clean up by hand — it surfaces under Archived instead), and skips `last-prompt`/`permission-mode` metadata appends during the run; mode defaults to `code`; header shows a `TEMP` pill.
- **Debug mode** — mirrors raw CLI traffic (`claude-stdin.jsonl`, `claude-stdout.jsonl`, `claude-stderr.log`, `meta.json`) to `<store>/projects/<p>/[worktrees/<wt>/]debug/<instance-id>/`. Append-mode, survives session end. Header shows a `DEBUG` pill. Spawn calls that omit `debug` fall back to the persisted **debug-by-default** setting (Settings → Models → Debug capture fieldset, `spawn.debugByDefault` in `settings.json`); an explicit `debug` on the spawn call always wins. The New Session dialog's checkbox is pre-checked from this default when it opens, and always sends its literal checked state (never omitted) so unchecking it reliably opts a single session out even when the default is on.

### Live conversation
- **Tail-first load + scroll-up history** — subscribing renders the ring tail (around `ORCH_SNAPSHOT_TAIL` events, default in `src/instances.ts` — quiescent-aligned: whole blocks, resolved tools; the quiescent snap can land the served count either shorter or longer than that count, and a backstop serves the nearest quiescent cut rather than an empty tail). When older history exists, a tappable `⋯ earlier messages` sentinel sits above the oldest content and scrolling near the top auto-fetches the previous page (`GET /api/instances/:id/lineage-events` at the page size `public/lazyHistory.js` requests, clamped by `clampLimit` in `src/eventArchive.ts`; flipping the sentinel to `loading earlier…`). A tail that already holds the ring's whole content asks once silently whether earlier contexts exist, so no sentinel flashes for a session that has none. If the rendered tail is shorter than the scroll viewport, the controller **auto-fills**: it keeps paging earlier chunks in (same path) until a scrollbar exists or history is exhausted, so the sentinel is never the only thing on screen — it stops on the no-more-history terminal case, on a fetch error (no hot-loop; sentinel stays tappable), and while the container has no layout (background tab). Pages render through the standard block pipeline on a detached node and splice in above with the viewport preserved; a turn split across page seams **merges back into one assistant bubble** (the batch's trailing open bubble concatenates into the chunk below), and sub-agent (Task) groups always travel whole with their nested panel — live children of a not-yet-loaded Task head are parked and adopted into the panel once its page loads. Events evicted from the in-memory ring are reconstructed from the session jsonl. Caveats: the task panel and usage chip rebuild from the tail only, and a single turn longer than the ring cap pages back with a gap (never duplicated content) ONLY when the archive replay can't correlate the ring head's own content back into the evicted history (no `(kind, msgId, blockIdx)`/`toolUseId` match) — a completed turn's content is otherwise stitched exactly, no gap. When a gap is marked, it renders as a `── ⋯ earlier messages unavailable ──` divider at the exact seam; only whole blocks are ever missing, and a genuinely interrupted tool renders `· incomplete` rather than a stuck spinner. **Earlier contexts:** scroll-up continues past the start of the current context into every earlier one of the session (each renew — `renew_session` or a typed `/clear` — and each prune started one), down to the first, each separated by a `── context renewed ──` divider — live across a renew too, with no gap for the pre-renew messages the ring evicted. A **pruned original is never shown**: its pruned copy (which holds the same turns with tool output stubbed) stands in for it, so nothing appears twice. A context whose transcript was **deleted** (Settings → Archived → Delete) or has gone missing shows one `earlier messages unavailable` divider in its place and scrolling carries on into the contexts before it. Bubbles from an earlier context carry **no ↶ rewind / ⑂ fork** — those act on the current context's transcript only; a renew strips them from every earlier bubble on screen the moment it happens.
- **Text** — streams as text-node deltas; on `text_end` re-renders through `public/markdown.js` (headings, lists, code, **bold**, *italic*, links, autolinked bare `http(s)://…` URLs, `![alt](src)` images; ordered lists keep their start number — `3.` renders as 3, not 1). Link schemes restricted to `http(s)/relative/fragment/mailto`; image `src` to `http(s)/file://`/absolute path; no `innerHTML`; raw HTML in source rendered as literal text.
- **User messages** — rendered through the same `public/markdown.js` pipeline as assistant text (same safety guarantees: no `innerHTML`, raw HTML/tag-like text such as `<pasted_content>` shown literally). Single newlines are kept as line breaks (`.block.text` sets `white-space: pre-wrap`). Headings render at body size with no underline, so a pasted markdown brief doesn't tower over the rest of the bubble. Hovering a bubble reveals a `raw`/`md` toggle (switches between the rendered view and the literal source, monospace) and a `copy` button that always copies the exact source text regardless of which view is showing (after the `<transcribed>` marker strip). Wake-callback, skill-load and renew-seed bubbles' expanded bodies (see below) get the same rendered body, `raw`/`md` toggle and `copy`, built lazily on first expand. **Known limitation:** a forwarded worker payload truncated mid-way inside an open code fence renders its tail (the truncation marker, the footer, the guiding instruction) inside that code block — still fully visible, monospace; use `raw` to read it as plain text.
- **Renewal reseed** — the first user turn of a session a `renew_session` rotated renders as a collapsed `♻️ Context renewed — handoff summary` bubble (dashed border, matching the wake-callback bubble). Expanding it shows the handoff summary split into one labelled section per heading the summary template asks for, falling back to a single "Handoff summary" section when the summary doesn't match it, then the conductor's follow-up directive (targeted-renewal form only) and the mechanical state block as literal monospace text (never markdown, so a `worktree=…` line can't mangle into emphasis). Same `raw`/`md` toggle and `copy` of the exact seed text as the wake and skill bubbles (see User messages, above); recognised live and on reload/history paging alike, since detection reads the seed's own fixed wording rather than a wire marker.
- **Text-to-speech (read aloud)** — the inverse of voice dictation: finalized assistant text blocks get a trailing `🔊` button (tap to hear it), and a global **auto-speak** toggle reads each reply as it lands. Local server-side Piper — no network, no API key. Synthesis is **streamed per sentence**: `POST /api/tts` returns a sequence of `[4-byte LE length][WAV]` frames (one per sentence) flushed as Piper yields them; the client (`public/tts.js`) decodes each with the Web Audio API and schedules them back-to-back, so the first sentence starts playing (~0.3s) while the rest synthesize. The 🔊 button appears once Piper is installed (`GET /api/tts/status` gates it; Settings → Voice → Speech installs/flips it at runtime). Auto-speak only fires after the user has interacted at least once (browsers block audio without a prior gesture); a 🔊 tap always works. Sub-agent text isn't auto-spoken.
- **Thinking** — collapsible block; redacted thinking renders as a non-expandable `thinking (redacted)` line (no disclosure caret). Opus 4.7 emits only a `signature_delta`; Opus 4.8 streams empty `thinking_delta`s (`""`) — the parser drops the empties so both collapse to the same redacted line. When the CLI streamed a token estimate for the block, the line reads `thinking (redacted, ~N tokens)` and keeps the count when you switch sessions or refresh; it falls back to the bare label after an action that reloads the session (resume, restart, and the rest — [docs/protocol.md](protocol.md) → `thinking_tokens` lists them), since the estimate is never persisted. Blocks with visible thinking text finalize to `thinking (N chars)` instead.
- **Tool use** — collapsed by default with smart one-line summary (`🔧 Bash · ls -la · done`). Edit/Write/NotebookEdit render as syntax-coloured unified diffs (green/red gutters, ±counts, sticky file-path); Write shows a numbered preview. Other tools: raw-JSON input in its own collapsed `↪ tool_input` block.
- **Action groups** — a contiguous run of non-prose blocks (tool calls, tool results, thinking) between two assistant text blocks is wrapped in one collapsible `<details>` (`.action-group`) headed by a tally: `7 actions · Bash ×3, Read ×2, thinking, Edit · 1 error` — count, distinct labels in first-appearance order (at most four, then `+N more`), and a trailing error clause counting every tool result in the group that came back as an error (including an orphan result whose `tool_use` is not in view). The run still accumulating during a live turn stays **expanded** so it can be watched, and folds the moment the run ends: prose, a user action, the turn's end, an interrupt, or the process exiting (`system/exit`, which every subprocess death emits). Historical pages arrive folded. **Toggling a group by hand sticks** — a group the user opened or closed is never auto-collapsed again. A sub-agent's own machinery groups the same way inside its nested panel (its failures are tallied by its own header, not the outer one), and a run-ender folds those nested groups too — a sub-agent gets no turn end of its own. A run cut in half by a lazy-history page seam merges back into one group with one header — unless a run boundary the live view honours (a turn-end line, an interrupt note) sits between the halves, in which case they stay two.
- **Skill loading** — a `Skill` tool call's SKILL.md content, which the CLI injects back as a plain (large) user message, renders as a dedicated collapsed `📘 Loading skill: <name>` bubble instead of a giant plain-text bubble; expanding it renders the content as markdown, built on first expand, with the `raw`/`md` toggle and a `copy` of the exact injected text (see User messages, above). Works live and on session reload for top-level `Skill` calls; a `Skill` invoked inside a sub-agent `Task` folds on session reload only — no live content injection was observed to follow a sub-agent turn (n=1, in a capture since deleted; see `docs/protocol.md`), so there is nothing to fold until the session is replayed from its jsonl. Server-side correlation with the originating `Skill` tool_use (not just the CLI's injected-message flag, which it also reuses for unrelated compaction/hook text) — see `docs/protocol.md`.
- **Tool result** — truncated at 4 KB with "show full". `image` content blocks (e.g. `Read` on a `.png`/`.jpg`) render as inline `<img>` thumbnails alongside the text — base64 sources become `data:` URLs, `url` sources only pass through for `http(s)`/`file://`, `image/svg+xml` is refused (XSS). Auto-expanded when an image is present. Tap any conversation image to open it full-size in an in-page lightbox (`public/lightbox.js`) — works for `data:`/`file://` sources that Chrome on Android refuses to open as a top-level navigation. Opens fit-to-screen; tap the image to toggle 1:1 full native resolution (backdrop scrolls to pan), tap again to fit; tap backdrop or press Esc to close.
- **Sub-agent drill-down** — `Agent` tool calls nest a mini-conversation (dashed border, `↳ sub-agent` summary) inside the parent tool block, routed by `parentToolUseId`. The block exposes **four independently collapsible surfaces**, each its own `<details>`: the balloon (`.block.tool`), `tool_args` (`.block.tool-args`), the sub-agent's turn transcript (`.sub-conversation`) and `tool_result` (`.block.tool-result`). The balloon is **collapsed by default** — it no longer pops open when the sub-agent's first event arrives — while the turn transcript is open by default, so expanding the balloon shows the transcript. Every one of the four **survives later streamed sub-agent events**: once toggled by hand a surface keeps that state for the rest of the session. The state lives on each node's `open` attribute, is per-block, and is **not persisted across a page reload** (the conversation is rebuilt from the snapshot).

  - **Cache-miss detection** is **cross-turn**, so it catches *partial* (minority) evictions the old stateless rule missed. Captured live in `src/instances.ts`, it compares this turn's **first**-request `cache_read` (`read_N`, pre-tool-call) against the **previous** turn's **last**-request full prefix (`P = cache_read + cache_creation`, the fully-accumulated cacheable prefix — cache_read accumulates across a turn's tool-call iterations, so the first request is used for read_N and the last for P). A miss is flagged when `read_N < P − tolerance` (`tolerance = max(1024, 1% of P)`): this turn served less of the prefix than was demonstrably cached last turn ⇒ an eviction, full or partial. A warm continuation reads exactly `P` (drop 0) and is never flagged. **Turn 1** (no prior `P`) and the turn after a **compaction / model switch / rewind** fall back to the old stateless `creation > read` rule, which still flags a genuinely cold prefix (cold start, expiry, resume, cold rewind). **Guards:** compaction (`system`/`compacting`), model switch (`_trackModel`), and rewind/respawn (`_wipeForResume`) legitimately shrink the prefix, so each sets a `_prefixBaselineInvalid` flag consumed on the next turn's first request — the cross-turn rule is skipped there and `P` is re-established fresh, preventing false positives. **Known limitation:** a miss on a request *after* the first (e.g. a turn outliving the ~1h cache TTL) isn't caught — detection is first-request-only. The verdict + evidence persist on each row (`cache_miss`, `first_req_cache_read`, `first_req_cache_creation`, and `first_req_evicted` = the `P − read_N` estimate on the cross-turn path), and the dashboard's **Cache misses** column counts the flag. On every detected miss an informational in-session notice appears in that session's conversation (a `SystemBlock`, same surface as the overage/rate-limit notice, no action): the cross-turn path shows `♻ ~<evicted> tokens evicted (<read> served of <P> cached).`, the fallback path `♻ <creation> tokens written to cache, <read> served.`. Both conjuncts are needed: in-control alone is not enough, since a worker that had already gone idle is not stopped at all and queues like any other in-flow session. Which case a given session lands in follows from its position in the tree and what it was doing when the window tripped, not from its backend; what root-scoping fixes is membership. Only a whole root tree that touches no monitored domain is exempt. **Trip detection is scoped differently — per session, by its own backend:** a non-Claude session's own `rate_limit_event` reports its own endpoint's window, so it never trips the monitored flow even when its tree is in-flow. This is backend-scoped by *usage-window domain* (`src/usageWindowDomains.ts`), where `claude` maps to the monitored `anthropic` domain and every other backend to its own unmonitored one — not hardcoded per provider, so monitoring another backend's window is a one-line addition.
      - **Global stop-and-queue lockout** — under `Stop & resume`, while the window is active **every** session queues its sends, not just the one stopped mid-turn: an idle/existing chat and a **brand-new chat started during the window** both queue (each queued-only session **arms its resume deadline immediately**, since there's no mid-turn→idle transition to arm on). Typing does **not** resume a session inside the still-throttled window: each message is **queued** and delivered as **one combined prompt** (reset text + numbered list + all queued attachments) when the deadline fires. This is a **hard lockout — no override, no early-resume button** (resume happens only on the deadline; internally `fireNow()` stays as the sweep/test seam). **Safety rail:** global queueing engages only when there's a valid *future* reset time with an armed clear timer — a missing/past reset means sends flow normally (never a permanent lockout). Plain `Stop` never queues (no flush path). **One session does not queue:** a worker the stop left **un-armed** (its conductor is the sole driver) *refuses* sends instead — the MCP tools soft-refuse `OVERAGE_STOPPED_UNARMED`, the WS path fails the send, its composer **disables Send** rather than relabelling it, and its banner reads "Stopped for account overage — your conductor resumes this worker. Messages can't be queued here." Queueing it would strand the text: the queue flushes only on a resume deadline it deliberately does not have. A **queued-only** session (idle/new, never stopped mid-work) resumes with a **softened preamble** ("Delivering the messages you queued while paused") instead of "continue where you left off". The auto-resume badge (header chip + sidebar) appends `· N queued`. Queued messages + every resume-preamble selector are persisted in the resume manifest so a restart doesn't drop them (all three states — stopped mid-work, idle-parked, queued-only — are carried; losing one resumes the session on a preamble that is false for it).

A **third direction** covers the action itself: an Apply that moves the action **off** `Stop & resume` (to `Stop` *or* `Off`) clears every pending resumption mark fleet-wide — across all projects — right then: the auto-resume badge and deadline drop, and any messages queued behind the lockout are **dropped**, each session logging one `⚠ Auto-resume skipped: overage handling changed — N queued message(s) dropped` line. - **Two-tier interrupt** — ⏸ Interrupt is a **deferred** stop by default: it **arms** an abort that fires at the next output boundary — when nothing is mid-stream and every dispatched tool has returned its result — so the block being written and any finished tool work are preserved, and the model is never asked to acknowledge anything (no extra round-trip). Armed with nothing in flight, it fires at once. Repeating ⏸ while armed does nothing. An unanswered ask-mode permission card never holds the stop up (the tool has not started) and flips to **✗ denied** once the abort lands, rather than waiting out the hook timeout. While armed, the header status chip reads **stopping…** and the bottom turn-indicator label switches to **Stopping…** with an inline **⏹ Interrupt now** button — the explicit escalation to an **immediate** abort that severs the turn and discards in-progress work. The split is driven by a transient `interrupting` flag on the `status`/`snapshot` WS frames; it auto-clears when the turn ends. Either tier leaves the CLI's `[Request interrupted by user]` marker line, which renders as the **⏸ Turn interrupted** system annotation rather than a user bubble, and is never counted as a real user prompt (so rewind/fork indices stay correct) — live it is dropped while the post-abort drain window (below) is open, which the abort itself opens, so it typically surfaces on replay/resume where that turn's `drain_abort` line is not there to say the same thing. Omitting `force` (WS `interrupt`, MCP `interrupt_turn`) is always the deferred tier.
  - **Post-abort drain window** — after an abort the CLI's internal stdin queue is not cleared: any messages written mid-turn (a prompt sent while busy) remain queued, and the CLI will dequeue them and start spurious new turns. The orchestrator opens a **drain window** (`POST_ABORT_DRAIN_WINDOW_MS`, default 3 s) after every abort — forced, or an armed ⏸ firing. The moment a spurious turn announces itself (via `system/init` on the event channel, ~39 ms after the abort and ~3.7 s before the first API round-trip), the orchestrator fires an immediate `control_request interrupt` to sever it — each spurious drain resets the window deadline (sliding window) so a queue of N messages is fully drained. Each drained turn shows a `drain_abort` system annotation ("⏹ Drained queued turn after interrupt") in the conversation. The window closes automatically when it elapses with no new turn-start. Calling `prompt()` (any explicit new-turn path) closes the window immediately so intentional follow-up prompts are never intercepted. A safety cap `POST_ABORT_DRAIN_MAX` (`src/instances.ts`) bounds the number of drains per window.

Shown/enabled whenever the rest of the ⋮ menu is (a live instance with a `sessionId`); the label swaps to reflect the action you'd take next, same convention as the Interrupt/Terminate item above it. - **Resume after restart** — when the `⟲` button is pressed **while live instances exist**, a dialog offers **Resume after restart** / **Restart only** / Cancel (no live instances ⇒ immediate hard restart, as before). ### Conduct mode
- **`🎼 Conduct` button** at the top of the sidebar (`+ New project`, `+ Add project` and `+ New workspace` are in the `≡` burger menu beside it). Tap → no dialog: immediately ensures the `.conduct` project exists, then spawns a **temp** Claude session there in code mode (bypassPermissions), sending `role:'conductor'` and no `model`/`backend`/`effort` — the server resolves the **Conductor role**'s current binding (Settings → Models → Roles) and its default effort, falling back to the default spawn tier if the role's binding has gone dead. Failures (ensure or spawn) surface via `alert()`.
- **`.conduct` project** lazy-created on first Conduct-button tap (`POST /api/projects/.conduct/ensure`). Lives at `<projectsRoot>/.conduct/`, holding two app-owned files: a generated `CONVENTIONS.md` — the conductor's role prompt, composed from the always-on core (`conventions/conductor/core.md`) + enabled toggleable conventions (`conventions/conductor/*.md`) + custom conventions, rewritten before **every** conductor spawn/resume (see **Settings → Conventions → Conductor** above) — and a `CLAUDE.md` carrying an `@CONVENTIONS.md` import line, created if absent and otherwise left with every existing user line intact. Delivery is the messages stream rather than an appended system prompt because a translation proxy in front of a non-Anthropic backend can drop the CLI's extra `system` block. Workspace conventions reach the conductor through this same file: `materializeCurrentConduct()` prepends the composed workspace text above the role doc. The dir is filtered out of `listProjects()` by the existing dot-prefix rule, so it never appears in the sidebar; the sidebar synthesises a `🎼 Conduct` row only while a live conductor instance exists. Reserved name: `POST /api/projects {name:".conduct"}`, `DELETE /api/projects/.conduct`, and `PUT /api/projects/.conduct/workspace` all return 400.
- **Workflow** (full details in the composed conductor role prompt — source: `conventions/conductor/core.md` + `conventions/conductor/*.md`): conductor uses MCP to `spawn_instance({mode:'plan', worktree:true})`, reviews via `get_recent_messages` / `project_diff`, lands via `approve_plan` → `sync_worktree({project, worktree})` → `merge_worktree({project, worktree})` → `kill_instance` + `delete_worktree`.
- **Playbooks** — declarative, enforceable workflow graphs, so a conductor's flow is checked by the server instead of only described in its prompt. A playbook is a graph of **stages** a worker is bound to; illegal moves are refused at the MCP boundary and every legal one is appended to a ledger, which makes the current state inspectable and the history backtrackable. Four ship in-repo (`playbooks/*.json`): `solo` (one worker plans, implements and refines; separate reviewers), `relay` (a planner that can never implement, handing off to a fresh implementer), `forge` (relay plus two mandatory critic passes over the plan — a rival plan, then a defect audit — that an implementer cannot be spawned ahead of) and `freeform` (the unconstrained escape hatch — a fan-out, a one-off command, or a worker that lands code). **Author your own** as a JSON file under `<projectsRoot>/.code-conductor/playbooks/` — it is picked up without a restart, and `list_playbooks`' `errors` tells you why one failed to load. Enabled **plugins** can ship playbooks too, listed as `<plugin-id>/<slug>` with a `plugin` field; disabling the plugin leaves its bound workers refused (the reason names the plugin) until it is re-enabled, which restores them untouched — see [plugins.md](plugins.md). Enforcement is per conductor session, starting at the **Playbook enforcement** level set in **Settings → Conventions → Conductor** (beside the Preferred-playbook picker; **`enforce` out of the box**, applied to the next conductor spawned). **⋮ → Enforce Playbooks** (below Prune, shown for `.conduct` sessions only) overrides that level **for the current session only** — it never changes the setting — toggling between the two levels — on refuses illegal moves; off allows the call but records the refusal in the ledger **and** drops an amber ⚠ warning bubble into the conductor's own transcript naming the tool, the refusal code, the reason, and the target worker when the refused call named one, so a would-be refusal is visible as it happens instead of only in the ledger. Under `enforce`, a spawn that starts a new run must name a `playbook` and a `stage`; the refusal names every playbook and where each can be entered (under `warn` the same spawn is warned about and proceeds untracked). Conductor-facing surface: `list_playbooks`, `describe_playbook`, `playbook_state` (which reports where a run is and what each next move would do). Contract, refusal codes and known limitations: [protocol.md → Playbooks](protocol.md#playbooks); internals: [architecture.md → Playbooks](architecture.md#playbooks).
- **Awaiting-wake dot** — a session's sidebar status dot renders **accent** (`.dot.idle.awaiting`, `public/styles.css`) while it is idle *and* an armed wake on a session it owns is pending, with the tooltip `idle — waiting on a worker`. Armed-wake-pending is wider than "its worker is mid-turn": the wake is held — and the dot stays lit — through a deferred `turn_end` (live subagent / unconsumed task notification, target already idle) and a dropped idle-drain settle, which is precisely when a conductor most needs not to read as done. It is the only thing on the row distinguishing "idle because I am waiting on a worker" from "idle because I am done". Fed by the `awaitingWake` field on the instance summary (`public/sidebar.js` → `instanceAwaitingWake`), which is CALLER-side. It stays lit across a heartbeat, because a heartbeat reports without consuming the wake — a conductor whose worker is hung no longer reads as finished.
- **Sub-agent panel** — while viewing a conductor session, a **Sub-agents** strip appears above the task panel listing every worker spawned by that conductor via `spawn_instance`. Each card shows a label (custom title → first-prompt preview → `project · id8`) plus a live status marker keyed off `displayStatus` (not raw `status`): `○` spawning, `●` idle, `▶` turn or idle-with-an-active-background-Agent-task ("running" — a worker whose turn ended but still has a backgrounded subagent working shows the same `▶` as an actively-turning one, not the idle `●`), `✓` exited, `✗` crashed. ### MCP interface
Mounted at `POST /mcp` (Streamable HTTP, JSON-RPC 2.0); tools exposed as `mcp__code-conductor__*`. Auto-registered on every spawn via `--mcp-config` (opt out with `ORCH_DISABLE_MCP_AUTOREGISTER=1`). No auth — localhost-only.

**Contract conventions (clean, no legacy aliases).** The worker handle is always `sessionId` (stable across respawn / `--resume` / restart, **and** across a `renew_session` or a prune — it is a permanent public id, never the CLI's rotating one); the per-process `instanceId` is internal and **never** appears on, nor is accepted by, the conductor-facing surface (a legacy `{id}` hard-fails; the REST/browser path keeps `id`). Every worker-addressing tool accepts three forms — the public id, an unambiguous **prefix** of it, or **any** of the session's backing/segment ids (permanently, so ids already written into wiki pages and old cards keep resolving) — resolved at the MCP boundary; exact matches always win, an ambiguous prefix soft-refuses `{ok:false, code:'SESSION_AMBIGUOUS', matches:[…]}` (see [protocol.md → MCP tool protocol](protocol.md#mcp-tool-protocol)). **`describe_session` is the one scoped exception to the third form**: it takes the handle (or a prefix of it) only, and a backing/segment id soft-refuses `SESSION_NOT_A_HANDLE` naming the handle that owns it, so a conductor never holds a `~/.claude` UUID — see [protocol.md → Public vs backing id](protocol.md#mcp-tool-protocol). Worktree is always `worktree`, and takes the one registered name. Worker resolution is **strict-live + soft-erroring** — `{ok:false, code:'SESSION_NOT_LIVE'|'SESSION_UNKNOWN', reason}`, and **never** brings a worker back: reviving a stopped session is `spawn_instance({resume})`, an explicit call, never a side effect of addressing one — except for the three call sites that read a session's bytes rather than drive it (`get_transcript`, `get_recent_messages`, `send_prompt`'s `forward` source), which fall back to the on-disk transcript so a retired worker stays readable and forwardable. `describe_session` is a further exception in the same direction, and not a fourth byte-reader: it describes a **retired** session from its on-disk session **row** rather than refusing `SESSION_NOT_LIVE`. The row is the one the session scan already builds (`listSessionsForCwdWithCounts`), so it does touch the transcript — a head read for the first prompt, a tail read for last-activity — but it serves that row and never the session's **content**, and it never resolves through `getInstOrDisk`, which is the line the three byte-readers sit on. It falls back to `SESSION_NOT_LIVE` only when the orchestrator still holds the session in memory but nothing on disk describes it. Inputs are schema-validated (unknown properties rejected); text-payload tools (`project_read`, `project_diff` diff mode, `project_bash`, `system_bash`, `get_recent_messages`) append raw un-escaped body blocks after the `content[0]` metadata; the five recon read tools and `describe_playbook` instead return a plain-text rendering as their whole result (no JSON); `ok:false`+`code` for soft refusals, prose+`statusCode` for errors. Full wire contract: [protocol.md → MCP tool protocol](protocol.md#mcp-tool-protocol).

- **Read:**
  - `list_projects`, `list_worktrees` — **text-rendered**, no JSON (see [protocol.md → Rendered read results](protocol.md#rendered-read-results)). `list_projects` counts a project's live workers (`live N`) but does not name them — that is `list_sessions`' job; every row has the same shape whatever kind of project it is — the listed `path` is the tree's real path, and the only extra line a row can carry about itself is `! unreadable project record`.
  - `list_workspaces` — bare listing.
  - `list_sessions` — **text-rendered**; the single session-listing entrypoint (live workers *and* resumable stopped sessions). Args `project?` (omit = everything; **covers the project's worktrees**, validated — an unknown name soft-refuses `PROJECT_UNKNOWN`), `worktree?` (narrows; requires `project`, else soft-refuses `PROJECT_REQUIRED`), `includeArchived?` (default false). Output groups by directory — each project's main checkout first, then its worktrees — with a per-group `live N · inactive N · archived N` header carrying the branch. A worktree group also shows `↑N ↓N vs base` (commits vs the base branch it merges into); a main checkout shows no divergence — its equivalent is vs the remote upstream, a different question, reported by `list_projects` instead. Live rows lead their group marked `LIVE`, carrying displayStatus and activeAgentTasks; inactive rows are one line each (sessionId, last-activity, playbook/stage, flags, title), newest first. Archived collapses to a per-group `+N archived` line unless `includeArchived:true`. The `resumes-hot` flag marks a session whose resume comes up in `bypassPermissions`. `owner <sessionId>` (live workers) and `awaiting-user <kind>` / `awaiting-user-via <source>` (live and inactive rows) flag the root conductor and an unanswered ask; archived rows are not derived here.
  - `describe_session` — **text-rendered**; one session's row addressed by its handle, live or retired, plus the project and worktree that own it. A live session renders the same `LIVE` worker block `list_sessions` prints; a retired one renders the same single session line, which carries no mode/effort/model because there is no process to read them off; its `awaiting-user` flag is derived even when the session is archived. `sessionId` takes the **handle only** — a backing/segment id soft-refuses `SESSION_NOT_A_HANDLE` naming the handle that owns it — and `SESSION_UNLOCATABLE` says the transcript exists but no registered project or worktree owns its directory.

A live worker that renewed reads its current context only: evicted pre-renew events surface as one `history_gap` at the front of a walk from `fromSeq: 0` (or of a default call that reaches that far), never on an incremental poll.

Tool inputs come back as a per-argument descriptor (pointers verbatim, oversized arguments marked) unless `includeToolCalls:true`.

It is phrased conditionally on the loss, because the flag fans out to every convention scope and can fire where this scope lost nothing: whatever *is* missing from the listing cannot appear in the line-1 `CONVENTIONS.md` marker of a project created from it, and no regeneration adds it back.

- **Shell** (read-only inspection only): `project_bash` — run a shell command inside a project/worktree cwd, in the exact shell environment claude's own built-in Bash tool uses (the `rg`/`find`/`grep` shims and shell functions/aliases from a captured shell snapshot, generated once per (`claude` version, shell) via a throwaway one-shot `-p` run — spawned through the **Fast capability tier**'s bound backend (Settings → Models) — plain `claude -p` on the identity `claude` row, or that row's command template followed by the claude args (the built-in `ollama` row happens to end in `--`, but a template need not — e.g. `ollama launch claude --model <tag> --yes -- -p ...`) — honoring that tier's model either way (no Anthropic default fallback) — cached under `<store>/shell-env/` as `bundle-<version>-<bash|zsh>.sh` (the cache key is the real `claude --version`, independent of the Fast tier's backend), and memoized in-memory for the life of the daemon process — at most one `claude --version` spawn per restart; see `src/claudeShellEnv.ts` + the shared `resolveBackendLaunch()` in `src/claudeLauncher.ts`). The bundle records which shell (bash or zsh) actually produced it, and `project_bash` spawns that same shell to source it — a zsh-flavored capture (e.g. oh-my-zsh completion internals) is only ever re-sourced by zsh, never by bash. Mirrors `project`/`worktree` for cwd scoping plus the meaningful subset of the built-in Bash tool's schema: `command` (required), `description` (shown in the transcript bubble in place of the command; never read server-side), `timeout` (ms; the default is in the `project_bash` schema, the clamp is `clampBashTimeoutMs`). **multi-block** — metadata `{project, worktree, cwd, exitCode, durationMs, truncated?, timedOut?, descendantsMaySurvive?, error?}` + a raw body block carrying the combined stdout+stderr output in arrival order; a non-zero `exitCode` is a normal result, not a tool error; `truncated:true` means retained output was capped at the bash output cap (`BASH_OUTPUT_CAP`) but the command still ran to completion (drain-and-discard, not kill-on-cap); on `timeout` (the only hard kill) the whole process group is killed, `exitCode` is `null`, `timedOut:true`. Replaces the former `grep`/`glob` tools — use `rg`/`grep`/`find` through this tool for search.
- **Shell on a system** (read-only inspection only): `system_bash` — run a shell command on a REGISTERED SYSTEM addressed directly, with **no project in play**, so a box can be inspected before anything is placed on it. Args `system` (a system registry id — `local` refuses `SYSTEM_IS_LOCAL` (400), since that is cc's own machine and the caller has its own Bash tool for it), `remoteId?` (one of that system's named targets; omit, `null` or `""` all mean the provider's own default target), `command` (required), `cwd?` (absolute path on that system; omit or `null` for `/`), `description?` (shown in the transcript bubble in place of the command; never read server-side — the same property `project_bash` takes) and `timeout?` (ms; the default is in the `system_bash` schema, the clamp is `clampBashTimeoutMs`). That `/` default is the one path [systems-protocol.md](systems-protocol.md) §7 requires every conforming provider to accept; a relative `cwd` refuses `CWD_NOT_ABSOLUTE` (400) before the system is resolved. There is no `list_systems`: `list_projects` names a project's placement (`system <id>` / `remoteId <target>`) only when it is on a **non-local** system — `local` and a null `remoteId` are the deviation defaults and print nothing — so nothing lists a system with nothing on it, the case this tool exists for. The command runs in a **plain login shell** on that system — the captured `claude` shell-env bundle is a file on cc's own machine and is never sourced here. Resolution is `systemById`, so the same named refusals a project on that system would get reach the caller unflattened: `SYSTEM_NOT_REGISTERED` (501), `SYSTEM_NO_PROVIDER` (501), `SYSTEM_UNREACHABLE` (502), plus `SYSTEM_NO_REMOTES` (501) and `REMOTE_NOT_FOUND` (502) when a `remoteId` is named. **multi-block** — metadata `{system, remoteId, cwd, exitCode, durationMs, truncated?, timedOut?, descendantsMaySurvive?, error?}` + a raw body block carrying the combined stdout+stderr output in arrival order; the truncation, timeout and `descendantsMaySurvive` semantics are `project_bash`'s, computed by the one shared helper.

Twin of `PUT /api/projects/:name/remote` — both call the one helper, so both inherit the same guard.
- **Workspaces:** `create_workspace` (`{name}` — register), `delete_workspace` (`{name}` — removes registry entry + clears member assignments), `rename_workspace` (`{oldName, newName}` — atomic), `set_project_workspace` (`{project, workspace}` — assign or clear with `null`/`""`; refuses `.conduct`; auto-registers a new workspace name).
- **Spawn/drive:** `spawn_instance` (`createWorktree:true` makes a fresh worktree off HEAD; `worktree:"<name>"` attaches to an existing one — the old `worktree: boolean|string` overload is gone. MCP-path spawns are always `temp` (archived on subprocess exit — transcript retained and resumable, just out of the default session list) with **no MCP knob for it**; mode still stays `plan` — `InstanceManager.create()` is policy-light and never couples temp to mode, so conducted workers plan before acting; an explicit `mode` still wins. The UI's temp⇒`bypassPermissions` shortcut lives only at the `POST /api/instances` route, not in `create()`; the UI temp checkbox and `POST /api/instances/:id/promote` remain the human's affordances), `send_prompt` (`{sessionId, …}`; a mid-turn send to a worker whose model declares **no mid-turn steering** stops that turn at a block boundary — finished text and completed tool work are kept — and arrives as a fresh turn instead, told that its turn was cut off; same tool, same result shape. `approve_plan` / `reject_plan` / `answer_question` and the web UI's composer and card surfaces take the same route, and no result field says which one ran; [protocol.md](protocol.md#subprocess-protocol)'s `user` row is the authoritative routed-site list; **you are woken when its turn ends** — see below; optional `forward:{sessionId}` injects another worker's recent output into the prompt server-side — the same default `get_recent_messages` selection, framed as context-only, with the conductor's own `text` placed last; an empty/tool-only source soft-refuses `NOTHING_TO_FORWARD` before any prompt is sent), `set_idle_timeout` (`{sessionId, timeoutSeconds}`; adjusts the HEARTBEAT window on one owned session and re-arms a running heartbeat — `armed:true` means the target was mid-turn — with the default as its ceiling, so it can only shorten. The wake itself needs no tool: when an owned target hits `turn_end` the orchestrator injects a stub user prompt into the *owner* via `Instance.prompt()`, naming the worker by sessionId; **folded wake** — on an ordinary `turn_end` delivered to an already-idle caller the stub **folds the worker's recent output inline** (the SAME content a default `get_recent_messages({sessionId})` call returns — bonded prose + plan/questions — via the shared `buildRecentMessages` builder + `flattenPayload`), so the conductor needs no follow-up call; the folded stub is tagged with a `[[cc:wake-callback]]` marker (`public/wakeCallback.js`) that the conductor UI renders as a **collapsible wake-callback bubble** (worker id + a one-line summary always visible — "finished its turn" for this folded variant; the other variants say plainly that it did NOT finish — with the folded payload collapsed by default; expanding it renders the payload, whose first line (the compact-JSON metadata block of the `get_recent_messages` result) shows as a muted monospace line and never as markdown, with the rest rendered as markdown and its framing lines as plain paragraphs — `raw`/`md` toggle and a `copy` yielding the exact folded payload including the metadata line, never the summary) with an orchestrator badge (🔔) marking it as system-injected; caller identity is read from `?caller=<caller sessionId>` baked into the per-worker MCP URL at spawn time (after the sessionId is minted); **carve-outs** — the heartbeat stub, the mid-turn-deferred stub and the force-abort **interrupted** stub all keep a plain "call `get_recent_messages` to inspect" pointer (no fold), while still being tagged with the marker (via `markPlainStub`, body-less) so they render as the **same wake bubble** — badge + summary line only, no expandable body or caret. On the interrupted one the carve-out is deliberate rather than incidental: a force-abort's output is PARTIAL, and the body separator is the client's "this is the finished result" signal, so folding it would invite the conductor to act on exactly what the abort was meant to stop it acting on. It reaches every owner except whoever called for the abort (that one is silenced), and the UI's stop button — same `Instance.interrupt` chokepoint — has no interrupter, so there every owner gets it; the idle-wake graph is keyed internally by the stable instanceId (the `?caller=` sessionId is translated at the dispatch boundary); the heartbeat repeats every window with a clearly-labelled "did NOT finish" stub while the target is mid-turn — **without consuming the pending turn-end wake** — so a hung worker is never misread as finished, and keeps saying so for as long as it can still finish. It does NOT ping forever: a target that is gone for good (subprocess dead with no prune/rewind/respawn reviving it) gets one final ping and then the heartbeat retires, because no `turn_end` can follow and an unbounded series would be a false report rather than a warning. Silence after a "did NOT finish" ping therefore means the worker died, not that the wake was lost; a conductor whose own model declares **no mid-turn steering** (Settings → Models) never receives a wake into its running turn — the wake is **held** and delivered at that conductor's own next `turn_end`, folded, or marked "no longer idle" if the worker has since started another turn), `set_mode`, `interrupt_turn` (default arms a deferred abort that fires at the next output boundary — returns `interrupting:true` meaning armed, not stopped; optional `force:true` ⇒ abort now), `kill_instance`.
- **Self-title:** `set_session_title` (`{title}` — names the CALLING session: the target is always the `?caller=` identity, and there is no `sessionId` argument, so passing one is refused as an unexpected argument. `title` must contain a non-whitespace character and is capped at `MAX_TITLE_LEN` by the schema's `maxLength` (refused, not truncated); clearing stays a UI-only action. Writes the same custom title as **Rename session**, so it shows in the sidebar, the header chip and `list_sessions`/`describe_session`, and survives restart, resume and renewal. Returns `{sessionId, title}`; no caller identity throws `caller identity missing`.) The always-on conductor core tells a conductor to name itself once its task is clear.
- **Session renewal / prune:** `renew_session` (`{sessionId?, summary?, directive?, followUp?}`) — an agent renews its OWN session (sheds context about landed jobs — dead weight taxing every future turn — at a lifecycle seam, not because context is "full"). Caller identity comes from `?caller=<instanceId>` (the stable instanceId, resolved to the caller's sessionId at the MCP boundary — so it always targets the calling session, works only for a code-conductor-managed instance, and **stays valid across repeated renewal**); it hands off a self-authored `summary`, structured under the exact `## <heading>` titles `RENEW_SUMMARY_SECTIONS` (`public/renewSeed.js`) names, and code-conductor drives a **server-managed `/clear`** at the caller's next `turn_end`, rotating the CLI's context in place (**same OS process/pid**, old jsonl preserved) and reseeding the cleared session with the summary plus a **server-generated mechanical state block** as its first user turn (the web UI renders that reseed as the renewal-reseed bubble — see User messages, above). **The session's `sessionId` does not change** — only the CLI's internal backing id rotates, and the rotation is recorded as a `renew` segment in the session's lineage (see [architecture.md](architecture.md)), so every id a conductor, a kanban card or a wiki page holds stays valid. `summary()` reports `rotationReason`/`lastRotatedAt`/`segmentCount` so a conductor can still tell a freshly-renewed worker from a stalled one. The caller's durable transcript-keyed markers (`temp`, `conducted`, custom title, recorded mode, backend) are carried onto the rotated backing id, and the abandoned pre-clear session is **auto-archived** (its jsonl stays resumable but moves to the archived section), so a later resume/`spawn_instance({resume})` of the renewed session keeps its temp/conducted/title state. The state block (built at reseed time, not arm time, so it reflects current — not stale — state) enumerates the live instances the caller spawned (`InstanceManager.liveOwnedBy`, via the same `callerInstanceId` ownership tracking the sub-agent panel uses) and the caller's own owned wake targets (spawn or dispatch, whether or not one is armed right now) — a safety net so a worker a degraded summary omitted is never orphaned: the mechanical list wins for **existence**, the self-authored summary wins for **intent**. The bare form is deferred to the caller's `turn_end` (not fired inline) so the tool call's own turn finishes first, and returns `{ok:true, willClearAtTurnEnd:true}`. **A conductor can also REQUEST a renewal** — `renew_session({sessionId, directive?, followUp?})` prompts that worker to renew itself and returns immediately (the request's own turn wakes the caller) (`{requested:true, …}`). The worker authors its own summary via its ordinary self-call, so the conductor never writes another session's working memory: `directive` is a PRE-directive (what to be sure to capture), `followUp` a POST-directive (its next job, fenced into the reseed under its own marker, so one call replaces renew-then-send_prompt). The request lives exactly one turn and **cannot be forced**: a worker that ends its turn without calling `renew_session` has DECLINED — it may be mid-rebase or holding state only it can land — and that expiry is reported as a note prefixed into the conductor's wake stub. Mixing the two forms' arguments (a `summary` with a `sessionId`, a `directive` without one, or targeting yourself) soft-refuses `INVALID_RENEW_FORM`; a target that is not free — mid-turn, or idle but owing a re-invocation turn, running subagents, or overage-parked — soft-refuses `SESSION_BUSY`, because a request needs a turn of its own. The decline note reaches the conductor that asked and no other, exactly once. Because it declares a `sessionId` it is a governable tool: a playbook stage may deny the request, while the bare form and the worker's own self-call are never gated. Empty summary soft-refuses `INVALID_SUMMARY`; a renewal armed while a prune is rotating the same session soft-refuses `SESSION_ROTATING` (and vice versa — the two mechanisms are mutually exclusive, because a prune makes `prompt()` 409 and the reseed is a `prompt()`). The clear is deferred further past an overage-queued turn or live subagents so queued/background work is never stranded by the rotation. Mechanism in `src/sessionRenew.ts` (`SessionRenewController`, keyed by the stable instanceId; no side-structure migration needed since the idle-wake graph and overage timers are instanceId-keyed too). A default-on conductor convention, `context-renewal` (`conventions/conductor/context-renewal.md`), teaches when to call it. **`prune_session`** (`{sessionId, keepLatestTurns?, pruneThinking?, inputMode?}`) is the other half of that convention and the MCP face of the Prune feature above: it rewrites the target worker's transcript with old tool outputs, oversized tool inputs and thinking replaced by size stubs, then respawns that worker against the pruned copy — no LLM pass, no summary, no turn spent, and the worker comes back **idle** with nothing seeded. Handler defaults (the schema's `default` is documentation only): `keepLatestTurns: 1`, `pruneThinking: true`, `inputMode: 'truncate'`. `keepLatestTurns: 0` prunes every turn including the newest; a value larger than the session has clamps to "prune nothing". Returns `{ok:true, sessionId, keptTurns, prunedTurns, saved:{thinking,toolInputs,toolOutputs}}` — the SAME public `sessionId` it was given (only the backing id rotates), and deliberately **no** `oldSessionId`/`newSessionId`, which are internal backing ids. `keptTurns`/`prunedTurns` are what make a clamped `keepLatestTurns` legible. Soft refusals: `SESSION_UNKNOWN` / `SESSION_NOT_LIVE` (strict-live, like every worker-addressing tool), `SESSION_BUSY` mid-turn (routing to `interrupt_turn`), `SESSION_ROTATING` when a renewal or another prune already holds the target, and `INVALID_PRUNE_TARGET` when the `sessionId` is the caller's own (a prune respawns its target, so it would kill the calling process mid-call — `renew_session({summary})` is the self-directed form). Because it declares a `sessionId` it is prefix-resolvable and playbook-governable like the rest. Renew vs prune: renew at a **job seam**, when a summary is all that needs to survive; prune **inside** a job, when the worker must keep its recent working state and only its older payloads are dead weight.
- **Wake on turn end is a property of ownership.** A conductor OWNS a target if it spawned it (`callerInstanceId`) or has ever dispatched to it — `send_prompt`, `approve_plan`, `reject_plan`, `answer_question`, and the targeted `renew_session` each record the edge (from `?caller=` on the MCP URL) **before** the send. Arming happens in `Instance._setStatus`'s into-`turn` branch, so every transition into a turn re-arms one wake per live owner: prompted and **unprompted** turns alike, which is what covers an auto-approved plan rolling into implementation with no conductor call behind it. There is no `subscribe` parameter, no result field, and no opt-out; `idleTimeoutSeconds` (whole seconds, `minimum:1`, floored at both ends against `ORCH_SUBSCRIBE_TIMEOUT_MS` via `DEFAULT_SUBSCRIBE_TIMEOUT_SECONDS`) only shortens the heartbeat window. A failed ownership record never fails the send. One armed wake per owner→target pair, so a mid-turn steer on top of a dispatch still delivers exactly ONE wake. Cleared by `turn_end` / the idle task-drain settle / rotation completion (all of which deliver), by `kill_instance` (which delivers nothing), and by `interrupt_turn({force:true})`, which clears the INTERRUPTER's own entry **before** the abort's own `turn_end` so that turn wakes it not at all — the conductor caused it. Every OTHER owner is still woken there and told the turn was **interrupted**, not finished (a fourth wake-stub variant, never folded — see [protocol.md](protocol.md#mcp-tool-protocol)); silencing an owner that did not ask for the abort would strand a wait nothing else can end, and a target can have several owners. The UI's stop button goes through the same `Instance.interrupt` chokepoint, so it produces the same interrupted stub — with no interrupter, every owner gets it. A SOFT `interrupt_turn` deliberately leaves it armed: its boundary wait is unbounded, so the continuing heartbeat is the escalation signal.

Soft-refuses `{ok:false, code}` with `NO_PENDING_QUESTION` / `ANSWER_COUNT_MISMATCH` / `INVALID_OPTION` / `NOT_MULTISELECT` / `EMPTY_ANSWER`. All three are read-only and never create the ledger they read. `spawn_instance` gains `playbook`/`stage`/`provenance` and `send_prompt` gains `stage`/`provenance`; under `enforce` a run-root `spawn_instance` is refused unless it names `playbook` + `stage` — but a `spawn_instance({resume})` of a playbook-tracked session is not a run root and inherits both from the session record. `list_sessions` rows carry `playbook`/`stage` (`null` when the session is not playbook-tracked). ### Plugins
- **What a plugin is** — any project (in-root, or an **adopted** out-of-root directory) with a `conductor.plugin.json` at its root (schema: [docs/plugins.md](plugins.md)). Each capability is one manifest key past the identity block — `KNOWN_TOP_KEYS` (`src/plugins/manifest.ts`) minus `id`/`name`/`version`/`pluginApi`, so a key added there is a capability unless it joins the identity block: a supervised backend process, an embedded frontend, MCP tools forwarded through the conductor's MCP server, **conventions** (entries joining the Conventions catalog as `<plugin-id>/<slug>`, each `project`- or `conductor`-scoped — see **Convention scope** below — and carrying a CLAUDE.md fragment and/or a one-time scaffold directive), **roles** (named model-bindings joining the role list as `<plugin-id>/<slug>`, resolvable by `spawn_instance`, user-rebindable in Settings → Models → Roles — the manifest binding is the default; a user override takes precedence at spawn), and **Claude Code skills** (a `claudePlugin` root contributed as a session-local `--plugin-dir` at every claude launch — interactive sessions and MCP-spawned workers alike). The contribution-only kinds need **no backend** — a manifest declaring no `backend` (`hasBackend`, `src/plugins/row.ts`) validates, enables, and never starts a process. Discovery scans the projects root at boot and on **↻ Rescan**; duplicate ids resolve first-alphabetical-project-wins (the rest show `conflict`).
- **Conventions & scaffolds** — an enabled plugin's `conventions` join the new-project dialog + `list_project_conventions` (namespaced `<plugin-id>/<slug>`). A convention carries a CLAUDE.md **fragment** (`file`, written into the project's regenerated `CONVENTIONS.md` at creation — regeneration drops the slug's text and names it in the file once the plugin is disabled/uninstalled, and it returns verbatim on re-enable; see the **Project** convention bullet above and [architecture.md](architecture.md#component-layout) for the full behavior) and/or a **scaffold** facet (`scaffold:{text|file}`, a one-time setup directive, **plugin-only**); at least one of the two is required. A convention flagged `hasScaffold` carries its scaffold invisibly in the dialog (no tag); when picked at creation its directive is composed (in selection order across all picked scaffold-bearing conventions) into one framed block **returned** by `create_project`/`POST /api/projects` under a `scaffold` field — nothing persisted, no spawn coupling. The conductor folds it into the first worker's brief; the UI displays it read-only in the create confirmation (v1). A **scaffold-only** convention contributes nothing to `CONVENTIONS.md` but still emits its directive. Only enabled+`ok` plugins contribute; a stale/missing fragment or scaffold `file` makes the plugin `invalid` at load. Since fragment and scaffold now live on one entry, author a scaffold-bearing convention to **degrade gracefully** if the scaffold step wasn't run (e.g. "if a project-local harness wrapper exists, use it; otherwise see the shared harness to create one"). Updating a plugin's checkout (rescan, restart, an active-version switch, or Plugin Library **Update**) now reaches every referencing project's `CONVENTIONS.md` on that same request — no orchestrator restart needed (see limitations in [plugins.md](plugins.md#rest--apiplugins)).
- **Convention scope** — every plugin convention declares a required `scope`. **`project`** and **`conductor`** are accepted today; `workspace` is **planned** and rejected at manifest load with a "not yet supported" error. A **`conductor`-scope** convention joins the Conductor-conventions catalog above (Settings → Conventions → Conductor) as its own checkbox, namespaced `<plugin-id>/<slug>`; it is **on by default while the plugin is enabled** (composed into the conductor's system prompt), unless the user has explicitly unchecked it (a remembered off-switch). Unlike a project convention it leaves no tracked in-tree artefact, so disabling the plugin (or unchecking its convention) simply drops it from the next conductor spawn's composed prompt — there is no marker keeping it named. The scaffold facet has no scope of its own — it's inherently project-scoped (it runs at project creation); a scaffold facet on a `conductor`-scope entry is simply never read (nothing outside project creation consumes it). ⚠️ A **`conductor`-scope** convention edits the orchestrator's **own** rules (the conductor role-prompt conventions that govern how it delegates/reviews/merges across all projects) — a powerful, trust-loaded capability (consistent with "plugins are trusted code", but far beyond a per-project convention); it requires the same explicit user opt-in as any other conductor convention, precisely because of that trust jump.
- **Trust stance (loud)** — plugins are **trusted own code**. Their frontends are same-origin iframes: plugin JS can call every conductor API the UI can. Enabling a plugin is equivalent to running its code with your conductor's privileges.
- **App switcher** — the sidebar `CodeConductor` title becomes a dropdown once an enabled plugin contributes a frontend (zero plugins ⇒ plain `<h1>`, no visual change). Selecting a plugin navigates to `#plugin/<id>/`; selecting Conductor deterministically closes the plugin view and restores the active session anchor (never `history.back()` — a deep link has no usable back entry). Rendered by `public/appSwitcher.js` from `GET /api/plugins`.
- **Plugin view** — `#plugin/<id>/<subpath>` shows the plugin's frontend in a full-page iframe (`public/pluginView.js`, src `/plugins/<id>/<subpath>` through the reverse proxy). Switching to an enabled-but-stopped plugin **auto-starts it behind a "Starting …" overlay** (REST status→start before the iframe loads, a bounded readiness window (`READY_TIMEOUT_MS`, `src/plugins/supervisor.ts`)); a start failure shows the error + crash tail with a **Retry** button instead of raw proxy JSON in the frame. Entering a plugin costs exactly **one** history entry (the bridge patches `pushState`→`replaceState` inside the iframe), so hardware **Back always lands on the conductor**; Escape works too. The sidebar stays live (`/ws` events keep flowing) while a plugin is open, and **any sidebar navigation** (selecting a session, opening commits/review/settings) closes the plugin view and returns to the conductor. Leaving the hash space blanks the iframe (frees memory). Limitation: multi-page (non-SPA) plugins still pollute joint history.
- **Settings → Plugins** — management group (`public/pluginManager.js`): per-plugin state badge (`discovered / disabled / enabled / stopped / starting / ready / crashed / failed / invalid / conflict / incompatible`), contribution badges (`N project conventions`, `N roles`, `N playbooks`, `Project scaffold: N` with a per-scaffold name/description preview), immediate Enable/Disable/Start/Stop buttons, crash-output expander, ↻ Rescan, and an **active version** dropdown (main + the project's worktrees). A ready row shows `running <version> @ <sha7>`, ` · update available` when stale, + port. A **backendless (contributions-only)** enabled plugin shows state `enabled` and only a Disable button (no Start/Stop/version — it has no process).
- **Restart on stale code** — a running plugin whose active checkout's HEAD has moved past the sha it was started at (a commit landed while it was running) is flagged `stale` and gets a **Restart** button next to Stop (stop + start in place, `POST /api/plugins/:id/restart`, 409 if not running). No button while stopped, backendless, or already at the started-at sha; a non-git checkout is never stale. Plugin Library **Update** now does this restart for you (see below) — the manual Restart button stays for a plugin whose code moved by some other means (e.g. a hand-run `git pull`).
- **Plugin Library** — below the installed-plugins list, a catalog of *installable* plugins (git repo URLs) with an **Install** button that clones the repo into the projects root (`GET`/`POST /api/plugins/library[...]`, `src/plugins/library.ts`). Install clones then **enables the freshly-discovered plugin by default** (so its conventions go active immediately); enabling is start-neutral (backends start lazily on first use), so nothing launches at install time, and an invalid/conflicting manifest is left disabled. Once cloned, the project surfaces in the list above through the normal discovery/rescan flow, same as any other plugin project. A set of built-in library entries is present even with no library dir (hidden when `settings.json` sets `plugins.builtinLibrary: false`) — overlaid by drop-in manifests dropped into `<orchStoreRoot()>/plugins/library/*.json` and any configured `plugins.libraryDirs` (one JSON object per file: `{id, name, description?, repo, postClone?, postPull?}`; a later layer's entry with the same `id` overrides; malformed/incomplete files, and files whose `repo` is refused, are skipped with the reason in the Library status line, never fatal). **Local / offline catalogs** — a `repo` may be a `file:///` URL or a `catalog:<path>` relative to its JSON, naming a bare repo or a git bundle, so a mounted volume of mirrored repos installs and updates with no network; rules in [plugins.md](plugins.md#local--offline-catalogs). An entry whose derived project name is registered as a project (the record, not a directory on disk) shows "installed as `<name>`"; an **Update** button only appears when the checkout is actually **behind its origin** — `list()` runs a bounded (8s), best-effort `git fetch` per installed entry before comparing (reusing `getProjectUpstreamStatus`, `src/worktrees.ts`), so a fetch timeout/no-remote/detached-HEAD/non-repo just hides Update rather than crashing the list; an up-to-date entry shows "installed as `<name>` · up to date" instead. The target project name is derived from the resolved clone URL's last path segment (`.git` or `.bundle` suffix stripped); `repo` is always a URL — `http:`/`https:`/`git:`/`file:`/`catalog:`; a bare path is refused with a message naming both local forms. A failed/timed-out clone shows the error + clone-output tail (reusing the crash-tail `<details>` styling) and cleans up any partial directory so the same install can be retried.
- **Plugin Library — live install/update output** — Install/Update stream their progress as NDJSON (`src/plugins/api.ts`'s `streamLibraryAction`), so the clicked row shows its button disabled + relabeled (`Installing…`/`Updating…`) and a small live output box (`.pll-live`) filling in with clone/pull/hook stdout+stderr as it runs, instead of only a result appearing after the fact. On failure the row's live output stays visible and the button re-enables; on success the whole library list re-renders (dropping the live box, re-evaluating Update availability).
- **Plugin Library — postClone/postPull + Update** — an entry may declare `postClone`/`postPull` shell commands (run via `bash -lc`, cwd = the project directory, e.g. `code-playwright`'s `bash install.sh`) that install the plugin's own dependencies. `postClone` runs once, right after a successful install (clone + rescan); **Update** (when shown — see above) runs `git pull --ff-only` → rescan → `postPull` → **auto-restarts the plugin's own backend if it's currently running** (a stopped plugin is left stopped — it'll pick up the pulled code lazily on its next start) → regenerates every project referencing one of its conventions. **If a backend is actually running and `postPull` fails, the auto-restart is skipped entirely rather than attempted** (checked in that order — a plugin with nothing running reports the same "nothing to restart" either way, never a skip) — a broken `postPull` leaves the checkout half-built, and restarting into it would trade a healthy backend serving old code for a crash-looping one serving no code at all; the running backend is left exactly as it was, still serving the pre-update code, until the user fixes the dependency and retries Update (or trusts the checkout enough to hit **Restart** by hand). A failed `git clone`/`git pull` is a hard failure (error + tail shown, and a failed clone is rolled back); a failed `postClone`/`postPull`/auto-restart, by contrast, is a **soft warning** — the clone/pull already succeeded and the project is already discoverable, so the entry still shows as installed, just with a warning + output tail (a failed post-hook wins the status line over a failed or skipped restart, since it's the likelier root cause of both, and the message is extended to say the backend was left on the old code). The documented way to retry a failed `postClone` is hitting **Update** (which reruns `postPull` — `code-playwright` sets both to the identical command); a failed (or skipped) auto-restart can be retried with the manual **Restart** button. Running a library entry's declared command is a trusted-code-execution surface (bounded timeout, output always surfaced), consistent with the plugin system's overall "plugins are trusted own code" stance.
- **Lifecycle & lazy start** — enabling records the plugin. Any discovered plugin project (enabled or not, valid or not) with no workspace is auto-assigned to the **CC-Dev** workspace on every rescan/boot — enable, install, and manual rescan all trigger this via the same discovery pass, and a project already assigned elsewhere is never moved. The conductor's own project gets the same CC-Dev placement via a one-time boot seed, since it isn't a plugin. Enabled-but-stopped costs zero RAM: the first proxy request or MCP tool call starts the child and waits through the readiness window (`READY_TIMEOUT_MS` in `src/plugins/supervisor.ts`). Children are detached process groups that **survive conductor restarts** (adopted on boot when still alive+answering). Health is passive (exit events, proxy errors, on-demand probes) — on Android, Doze may kill a child at any time; the next request 503s with the crash tail, then lazy-restarts after a short backoff. a crash-count threshold within a rolling window ⇒ `failed` (see `src/plugins/registry.ts`; manual Start/Enable to recover).
- **Worktree-version activation** — the version dropdown switches which checkout the child runs from (`main` or any of the project's worktrees, resolved via the worktree store). The manifest is re-read from the active checkout on every start and must keep the same id (else 400, previous state kept). Caveat: worktrees don't share `node_modules` — a missing-deps start failure surfaces in the crash tail; the per-project `post-worktree-create.sh` hook can `npm install` automatically.
- **Plugin MCP tools** — manifest-declared tools appear inside the existing conductor MCP server as `<plugin-id>__<tool>` (client-visible `mcp__code-conductor__<plugin-id>__<tool>`). Visibility: **globally visible** — every enabled plugin's tools are offered to the conductor UI and to workers in **every** project (the manifest `mcp.scope` field is accepted for compatibility with shipped manifests but dropped at load — nothing reads it). A disabled plugin's tools are simply unknown. Calls lazy-start the plugin and forward over HTTP with a per-manifest timeout. Note: workers snapshot the tool list at spawn — mid-session enable/disable reaches only new sessions.

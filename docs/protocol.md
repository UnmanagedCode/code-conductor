> This file is the protocol between cc and the **Claude CLI / its own clients** — the subprocess stream, the WebSocket messages, the REST and MCP surface. The protocol between cc and a **System provider** (the NDJSON stdio contract for running commands and reading/writing files on another machine) is its own document: [systems-protocol.md](systems-protocol.md).

## Subprocess protocol
```bash
claude -p \
  --input-format=stream-json --output-format=stream-json \
  --verbose --include-partial-messages --include-hook-events \
  --exclude-dynamic-system-prompt-sections \
  --allow-dangerously-skip-permissions \
  --permission-prompt-tool stdio \
  --permission-mode <plan|bypassPermissions> --effort <effort> --thinking <thinking> \
  --settings '{"hooks":{"PreToolUse":[…]}}' \
  --mcp-config '{"mcpServers":{"code-conductor":{"type":"http","url":"http://127.0.0.1:<port>/mcp"}}}' \
  [--plugin-dir <root> …] \
  [--model <name>] \
  --session-id <fresh-uuid> | --resume <existing-uuid>
```

The `--mcp-config` line is omitted when `ORCH_DISABLE_MCP_AUTOREGISTER=1` (no MCP toolbelt auto-registered into the spawned process).

`--plugin-dir` is **repeatable, one per enabled cc plugin** whose manifest declares `claudePlugin` (session-local Claude Code plugin roots — skills et al.). `<root>` is the resolved+validated abs dir (a dir directly containing `.claude-plugin/plugin.json`); a plugin whose target lacks that file is warned + dropped. Absent when no enabled plugin ships one. See [plugins.md](plugins.md#manifest--conductorpluginjson-at-the-plugin-project-root) → `claudePlugin`.

**Substitution backends (the launch template).** Spawning is backend-agnostic: `Instance.spawn` computes only the command + argv prefix from the session's **backend record**, then appends the **same** claude args (including `--model <model>`) for every backend. A backend's `template` is the command that replaces `claude`, with `{model}` substituted in (blank template ⇒ run `claude` directly); `resolveBackendLaunch` in `src/claudeLauncher.ts` is the single substitution point, and the backend's configured `env` pairs ride along with it. Backends are user-managed data — see [models.md](models.md). For the built-in `ollama` row the template is `ollama launch claude --model {model} --yes --`, so the full argv is `ollama launch claude --model <tag> --yes -- <all the args above, including --model <tag>>`. `ollama launch` sets the Anthropic-compatible endpoint + auth internally and re-injects `--model` into the child; the forwarded `--model <tag>` is a matching **no-op duplicate** (verified harmless). `--yes` bypasses the interactive agent-capability confirmation (which would fail a piped spawn). Everything after `--` (stream-json stdin/stdout, `--mcp-config`, `--settings` hook, `--session-id`) is forwarded unchanged — the worker registers, streams, and drives MCP + hooks exactly like a bare-`claude` spawn. Any non-blank template refuses to launch without a resolved model (`422 BACKEND_MODEL_MISSING` at create time, and the same refusal inside `resolveBackendLaunch`) — **unconditional on the template shape**, so a template that never names `{model}` is no exception: the model still rides in the forwarded claude args and drives the context-window env below. A backend id that isn't in the registry is likewise refused `422 BACKEND_GONE` rather than falling back to `claude` (see [models.md](models.md#missing-backends-are-refused-never-downgraded)). There is **no** reachability preflight: a bad backend or model fails at spawn and surfaces as `launch_failed`. For a spawn on any **non-`claude`** backend, both `CLAUDE_CODE_AUTO_COMPACT_WINDOW` and `CLAUDE_CODE_MAX_CONTEXT_TOKENS` are set on the child env to the session's resolved `contextWindowTokens` (raw tokens; resolved once at create by `resolveContextWindowTokens` in `src/appSettings.ts`, which matches the custom-model row or curated catalog on the **exact** model id); unset when the window is unknown. These two are **cc-managed** — implicit to every substitution backend, never applied to plain `claude`, never exposed in the Backends UI, and applied *after* the backend's own `env` so they win over a same-named pair. Both are needed: the CLI clamps the effective compact trigger to `Math.min(modelWindow, AUTO_COMPACT_WINDOW)`, and its internal per-model table defaults any unrecognized model (every non-Claude id) to a 200k assumed window, which silently caps `AUTO_COMPACT_WINDOW` back down — `MAX_CONTEXT_TOKENS` overrides that assumed window directly for non-Claude models, so the CLI actually auto-compacts at the real limit instead of ~200k. The `.conduct` orchestrator's opt-in compact-window override still wins when both apply (it only overrides `AUTO_COMPACT_WINDOW`, which remains the binding minimum).

**Interactive tools under CLI ≥ 2.1.x — `--permission-prompt-tool stdio`.** Headless stream-json (`-p`) sessions are non-interactive (`isNonInteractiveSession=true`); the CLI serves a coordinator/agent tool profile and **strips the interactive plan/question tools** unless the client presents as a permission consumer. Passing **`--permission-prompt-tool stdio`** does exactly that: the CLI routes those tools' permission prompts to us as `can_use_tool` control_requests over the stream-json channel (verified: it re-adds the three tools to `system/init` `tools[]` and they become callable). It is **additive** to `--allow-dangerously-skip-permissions` (normal tools stay auto-allowed and never reach `can_use_tool`; only the interactive tools do). Kill-switch: `ORCH_DISABLE_STDIO_PERMISSIONS=1` reverts to the fail-closed behavior (tools stripped).

The orchestrator answers `can_use_tool` in `Instance._handleStdoutLine`: for `ExitPlanMode`/`EnterPlanMode`/`AskUserQuestion` it replies `control_response {behavior:"deny", message:<AWAITING_INPUT_MESSAGE>}`; any other tool (rare) is allowed. The deny releases the tool call — the `plan_request`/`user_question` card is emitted from the tool-use, so the drive-forward path needs nothing more from it — but it **does not reliably end the turn**: the model gets an `is_error` tool_result (tagged `yielded` — see UI event kinds) and wraps up only if the CLI has nothing queued behind it. A message already sitting in the CLI's stdin (typically a wake callback from a finished worker) is injected right after the deny and the **same turn keeps running**. So the reply is still fire-and-forget rather than held open — holding it for an *in-turn* answer would suppress `turn_end` entirely and deadlock a conductor's wake — but `turn_end` may be arbitrarily far off, and every answer path (`approve_plan`/`reject_plan`/`answer_question` and the UI cards alike) therefore sends **unconditionally**, picking up `MID_TURN_NOTE` when it lands mid-turn — or, on a model declaring `midTurnSteering:false`, parking behind a block-edge stop and picking up `POST_STOP_STEER_NOTE` instead (routed-site inventory in the `user` row below; the result shape does not say which route ran). `approve_plan`/`reject_plan` are unchanged (setMode + approval prompt); `answer_question` delivers the worker a structured AskUserQuestion answer that is **byte-identical** to a UI question-card submit — both call the one DOM-free formatter in `public/userQuestionAnswers.js` (re-exported by `public/blocks.js`, imported server-side by `src/mcp/handlers.ts`). The flag alone exposes and makes the tools callable — **no `initialize`/`supportedDialogKinds` handshake is sent** (probe-verified unnecessary), and the CLI never issues `request_user_dialog` in this configuration (permission flows via `can_use_tool`).

`--allow-dangerously-skip-permissions` is **always** passed at spawn — even for `plan`-mode instances — because without it the CLI rejects any later runtime `set_permission_mode bypassPermissions` (i.e. the plan-approve flow). The flag only *permits* the switch; it doesn't activate bypass on its own.

**`agent_id` is NOT read.** The CLI puts it on a **subagent's** `PreToolUse` payload and omits it on the main agent's, and cc used it to pick which of a session's per-agent shells a redirected `Bash` ran in. There are no such shells — one `exec` per command, so no command's state reaches any later command and there is nothing to keep apart — and the field went with them, off the envelope type, off the forwarder argv and off the `bash-forward` body. `tests/systems-cli-contract.real.test.mjs` still pins the payload shape, as a fact about the CLI rather than something cc depends on.

**Two-tier interrupt.** Both tiers send the same `control_request` `subtype:interrupt`; they differ in **when**. FORCED (`force:true`) sends it immediately (discards in-progress work). SOFT (default) **arms** it: `interrupting:true` broadcasts at once, nothing is written to the CLI, and the abort fires at the first **quiescent point** — no outer text/thinking/tool_use block mid-stream (each opened block has had its `content_block_stop`) and every outer `tool_use` has received its top-level `tool_result`. Armed in a gap ⇒ fires synchronously inside the `interrupt()` call. No steering message is injected on either tier, so a soft stop costs no extra model round-trip. The SOFT tier is reused verbatim by the no-mid-turn-steering delivery path above (`await inst.interrupt()`, no arguments): because the fire predicate holds while any outer `tool_use` lacks its `tool_result`, the stop never leaves a dangling `tool_use` and the next turn's request is well-formed.

The fire predicate (`Instance._atInterruptBoundary`) is `pendingTools.size === 0 && (openBlocks.size === 0 || boundarySeq > armSeq)`. Tool spans are strict — only a matching `tool_result` or a turn boundary discharges one. Display blocks have **two** discharge paths: their own close event, and **progression** — the appearance of a different `${msgId}:${blockIdx}` key, which marks the previous block stale and bumps `QuiescenceScan.boundarySeq`. Progression exists because a substitution gateway can withhold a close entirely (a `content_block_start` with no `content_block.type`, or a `type` of `"output_text"`: the block opens on its first `text_delta` and its `content_block_stop` emits nothing), which pre-fix latched the arm for the whole turn and cleared it silently at `turn_end`. `interrupt()` snapshots `boundarySeq` into `_interruptArmSeq` at arm time, so the second clause reads "a boundary has been crossed **since you armed**" — the retiring event is the same event that opens the next block, so an empty-state reading can never see it. On a well-formed stream the close is its own event, so this reduces to today's behaviour exactly; on a withheld-close stream the abort lands **one block late** instead of never. Progression reads only events carrying BOTH a `msgId` and a numeric `blockIdx`: `system`, `tool_result` and a bare `assistant_message` name no block and retire nothing.

Residuals the soft tier still cannot discharge: **R1** an arm in the turn's FINAL block on such a gateway, **R2** a gateway that frames the whole turn as one block, **D** a proxy that renames tool ids between the streamed block and the `tool_result`, and a genuinely wedged tool. R1/R2 still reach idle at `turn_end`, so the automatic callers get their stop either way; D and a wedged tool are covered by the deadline backstop below.

The predicate is one `QuiescenceScan` (`src/parser.ts`, the same class the snapshot/paging snap uses) fed from `Instance._emitUi`, evaluated in `_maybeFireArmedInterrupt` after the event reaches subscribers. The two consumers ask different questions of it — paging asks "is state empty AT index i", the abort asks "has a boundary been crossed since the arm" — so progression MARKS a stale block rather than deleting it: a never-closed block is unfinished permanently, and paging must keep counting it or a cut would end a page on a dangling block. Quiescent cut indices are therefore identical by construction. Consequences of that scan: sub-agent events (`parent_tool_use_id != null`) are ignored, and a backgrounded Agent/Bash whose `tool_result` already resolved (`isAsync`) does not hold the fire. A genuinely wedged tool is what FORCED is for. No timer and no max-defer knob on the MANUAL doors (⏸ / `interrupt_turn`) — a human and a conductor both already have ⏹. The three AUTOMATIC callers (`_directOverageStop`, `_guardOverageTurnStart`, `drainToManifest`) pass an opt-in `{ deadlineMs }` (`softInterruptDeadlineMs()`, default 120 s, env seam `ORCH_SOFT_INTERRUPT_DEADLINE_MS`): on expiry the arm escalates to FORCED and emits a `system`/`stderr` line naming the held block keys and unreturned `toolUseId`s. It fires only for a turn that never ends — R1/R2 end by themselves — and never after `_interruptFired` (an ACKed-but-not-honoured stop is a different defect). The fire gates on `_interruptArmed`, **not** on the `interrupting` flag the WS frames carry. `_interruptFired` suppresses any further `control_request` from the moment one goes out, and exactly two things clear it: a rejection, and the exit from `turn`. An **ACK is not one of them** — the flag stays true for the rest of a turn whose stop landed, which is what lets the deadline above tell an undelivered stop from an ACKed-but-unhonoured one. Not one per arm, though: repeated soft is a no-op and a FORCED escalation while armed sets the flag so no second fire lands at the boundary, but either tier rolls it back when its own `control_request` rejects, so an arm that survives a failed escalation goes on to fire at the next boundary. All three flags clear on any exit from `turn` in `_setStatus` — which runs *before* `turn_end` is emitted, so a turn that ends first sends nothing and no arm leaks into the next turn. A fire also opens the drain window (below). A failed/timed-out `control_request` on the SOFT fire emits a `system`/`stderr` line and clears **all three** flags — the abort never landed, so the same turn stays re-armable by a second soft call. The FORCED tier's rule is narrower: it clears `_interruptFired` on **every** rejection mode (timeout included) and emits nothing, and it leaves `interrupting`/`_interruptArmed` untouched because it never set them — a bare force leaves both `false`, an escalation leaves both `true` and therefore keeps the ⏹ lever on screen. `_turnForceAborted` alone keeps its `timedOut`-keyed pessimism: on an unknown outcome both of its readers prefer assuming the abort landed — the wake report (`Instance.turnForceAborted` below) and `resumeRestart`'s drain-escalation loop, which skips a second force for an instance already forced once — while `_interruptFired` prefers letting another stop through. Both tiers gated by `if (status !== 'turn') return`.

The CLI then writes its own `[Request interrupted by user]` / `[Request interrupted by user for tool use]` line as a plain `type:"user"` message. `isInterruptMarkerContent` (`src/parser.ts`) recognizes it (anchored, lone text block) and it is filtered at the same three sites as `SOFT_INTERRUPT_MARKER` (`parser._handleUser`, `transcript.replayPersistedLine`, `transcript.isPureUserPromptLine`), so live and on replay it renders as a bare `system`/`soft_interrupted` annotation, never a user bubble, and never shifts `_userEchoCount`/the rewind-fork index. While a drain window is open the annotation is dropped entirely (`_handleStdoutLine`) — that turn already annotates as `drain_abort`. Nothing persists a prompt index, so old sessions simply stop counting the marker; there is no migration.

`system`/`soft_interrupted` also has a **server-side** emitter: `InstanceManager._guardOverageTurnStart` emits it with `data.text` (the overage lockout reason) before stopping a turn that started during the pause, which `public/blocks.js` renders as `⏸ Turn interrupted: <text>`. The parser-generated one stays payload-free, so the CLI's own marker for that same abort produces a second, bare `⏸ Turn interrupted` line right after it — accepted, not suppressed.

`SOFT_INTERRUPT_MARKER` is **read-only**: nothing writes it any more. The two sites that did — the resume-restart drain and the overage conductor stop, via `Instance.windDown()` — are plain aborts now (a steer a model may silently drop cannot be load-bearing), and `windDown` is deleted. Historical jsonls still carry the marker, so its VALUE must not change and every recognition site stays live.

**Managed `/clear` (session renewal).** `Instance.clearContext()` writes a `type:'user'` message whose sole content is the text `/clear` on the same stdin path a normal prompt uses (via `_sendRaw`, but bypassing `prompt()`'s user_echo + overage-queue intercept — it is a server-internal control send). The CLI rotates its sessionId to a fresh UUID **in place** — same OS process/pid, old `<sid>.jsonl` preserved, a new `<newId>.jsonl` created — and emits a `system/init` carrying the new `session_id` (which `Instance`'s system/init handler folds into `this.backingSessionId` — **not** `this.sessionId`, which is pinned for the session's life; it also appends a `renew` segment to the session's lineage row, see [architecture.md](architecture.md)) plus a `result` (turn_end). On rotation the controller carries the caller's durable sessionId-keyed markers (`temp`/`conducted`/title) onto the new id and **archives** the abandoned old id (via `Instance.carryMarkersAcrossRenewal` — see architecture.md), so the preserved old `<sid>.jsonl` surfaces in the archived section rather than as a stale live row. Driven by `SessionRenewController` off the `renew_session` MCP tool — see [MCP tool protocol](#mcp-tool-protocol) and [architecture.md](architecture.md).

**Post-abort drain window.** The CLI's stdin queue is not cleared by an abort. Any `user` message written before it (a prompt sent mid-turn) remains queued; after the abort the CLI dequeues them and starts a spurious new turn for each. After every abort — forced, or an armed soft one firing — the orchestrator opens a drain window (`POST_ABORT_DRAIN_WINDOW_MS`, default 3 s) and watches for `system/init` events on the event channel (`Instance._openDrainWindow`). The `system/init` event arrives ~39 ms after the abort and ~3.7 s before any API round-trip, so the drain fires an immediate `control_request subtype:interrupt` to sever the spurious turn at zero token cost. Each drain resets the window deadline (sliding window). Calling `prompt()` closes the window so intentional follow-up prompts proceed normally — **before and after** its own send: the prompt's `user_echo` is itself a quiescence reset, so a stop armed earlier in that turn fires right there and opens a window that would otherwise sever the turn this prompt is starting. The drain emits a `system/drain_abort` event (kind `'system'`, subtype `'drain_abort'`, data `{count}`) visible in the conversation as "⏹ Drained queued turn after interrupt".

**UI event kinds (`ev.kind`)** — each carries `parentToolUseId` (or `null`); non-null routes into a nested sub-Conversation.

- `message_start` — one per agent-loop LLM call. **Live shape** `{msgId, usage, model}`; `usage` is that single call's prompt size (`input_tokens + cache_read_input_tokens + cache_creation_input_tokens`) and is the only **live-frame** feed for the ctx readout apart from `context_usage` below (`turn_end.usage` is a per-turn SUM across every call in the turn — using it is the `ctx 743%` bug; see `public/usage.js`). `usage` may be **`null`**: the parser drops any block whose `input_tokens + cache_read_input_tokens + cache_creation_input_tokens` is 0, because some substitution backends' gateways report an all-zero block on every `message_start` and put the real numbers only on the final `result` and in the jsonl — latched verbatim that renders a false `ctx 0% · 0/200k`. The **event still fires** (it also carries the turn-boundary model reading and the idle→turn flip for a turn we didn't initiate), and both latches (`Instance._lastContextUsage`, `UsageTracker.lastUsage`) skip a null block, so a good reading — including the replayed jsonl seed below — survives. A present-but-zero-sum block additionally **arms the `context_usage` fallback** for that message (next bullet), so the reading arrives from `message_delta.usage` instead of staying unknown; a usage-bearing block **disarms** it. `loadPersistedTranscript` (`src/transcript.ts`) floors the replay path over the same three fields. An **absent** `usage` still suppresses the event entirely (fixture accommodation) and leaves the arming flag untouched. **Replay shape** `{msgId, usage, replayed: true}`, emitted once by `loadHistory` from the newest non-`<synthetic>` assistant line's `message.usage` so a resumed session's ctx chip is populated before its first live turn (the jsonl carries no `message_start`; it also carries no `type:"result"` line, so the summed value is structurally unreachable from replay). The replayed one is **seq-less and never retained** — `EventLog.push` declines it, so it reaches the live feed only and never appears in a snapshot `events[]`. That keeps it off the ring head (where it could fake a `history_gap` at the archive seam) and out of `ring.nextSeq` (which `idleSubscriptions.ts` arms on). `model` is deliberately **omitted** on the replay shape so `UsageTracker` keeps falling back to the instance's tagged model for the window denominator — the jsonl reports the model bare (`glm-5.2`, not `glm-5.2:cloud`). `conversation.apply` has no `message_start` case in either shape.
- `context_usage` `{msgId, usage}` — the **fallback** ctx reading, emitted from `stream_event`/`message_delta` (event-level `usage`, not `delta.usage`) and **only** while armed by that message's zero-sum `message_start` (previous bullet). Same three-field floor: an absent or all-zero-sum block emits nothing. The parser stays armed across a message's deltas, so **last non-zero wins** at the latch. Both latches read it exactly as they read a usage-bearing `message_start` — one whole `usage` object, no per-field merge — and `public/wsRouter.js` refreshes the header chip on it. Deliberately **not** a second `message_start` shape: that would feed the delta's cache numbers into `Instance`'s cross-turn cache-miss bookkeeping and fake an eviction on the following turn. Carries **no `model`**, so the window denominator keeps resolving from the instance's tagged model. **Seq-less and never retained** (`EventLog.push` declines it) — a re-subscribing client is seeded from the snapshot's `lastContextUsage` field, and on such a backend every in-tail `message_start` carries `usage: null` and so cannot clobber that seed. `conversation.apply` has no case for it. Arming resets on `Parser.reset()` (reached from `_wipeForResume`), and a fork/resume starts a new `Parser`.

**`system` sub-mechanisms:**

- `thinking_tokens` — `data:{estimated_tokens, estimated_tokens_delta}`, a live-only last-value-wins counter driving the thinking-block summary, emitted by the Claude CLI as a per-token progress estimate (one per `thinking_delta` token). Observed on `claude-opus-4-8`, `claude-sonnet-5`, `claude-fable-5` (all with redacted thinking — no content deltas) and `claude-haiku-4-5` (alongside **plaintext** deltas), so it is a progress signal, **not** a redaction marker; `claude-sonnet-4-6` and `claude-opus-4-7` were observed emitting none. Whether workers on a non-Claude backend emit it is unverified (no capture on disk). Both streams flood live per-token, but the ring keeps `thinking_tokens` out entirely and coalesces `thinking_delta` — and, identically, `text_delta` — to one slot per `(msgId, blockIdx)` block, so folded/counter frames arrive **seq-less** on the live feed (the client renders seq-less events unconditionally). Persistence of the count across a re-subscribe depends on the block shape:
  - **Open block** — latest count held as O(1) server state (`inst.liveThinkingTokens`), re-attached to a fresh subscriber's snapshot (see the `snapshot` row above).
  - **Closed block with text** — nothing to carry; the coalesced `thinking_delta` replays and the summary finalizes to `thinking (N chars)`.
  - **Closed redacted block** — no text replays, so the final estimate is stamped onto the retained `thinking_redacted` slot as `estimatedTokens`.
  - **Known limitation** — ring-resident only. Paths that rebuild from jsonl (resume, respawn, rewind, server-restart manifest restore, paging above `trimmedBefore`) show the bare `thinking (redacted)`: the CLI persists no counter frames to its session jsonl.
- `auto_resume` — `data:{count}`; marks the overage resume firing ("Window reset — delivered N queued").
- `auto_resume_skipped` — `data:{reason}`; fires ONLY for the genuine "session no longer running" case — a missing/past `resetsAt` no longer dead-ends; it schedules a usage recheck instead (see the usage-verified fire in architecture.md).
- `cache_miss` — `data:{cacheRead, cacheCreation}`, plus `prevPrefix` + `evicted` on the cross-turn path; an informational once-per-turn notice fired on a detected cache miss (rendered as a `SystemBlock`, no action). Detection is **cross-turn**: a miss when this turn's first-request `cache_read` (`read_N`) is below the previous turn's last-request prefix `P` (`cache_read + cache_creation`), i.e. `read_N < P − tolerance` (tolerance defined in the cache-miss detector, `src/instances.ts`) — catches full AND partial evictions. Turn 1 (no prior `P`) and the turn after a compaction (`system`/`compacting`), model switch (`_trackModel`), or rewind/respawn (`_wipeForResume`) — each sets `_prefixBaselineInvalid`, consumed next turn — fall back to the stateless `creation > read` rule (still flags cold start / expiry / resume / cold rewind). Not flagged: warm continuations (read == `P`) or content-addressed hits. A mid-turn eviction (past the first request) is not caught (first-request-only).
- `model_changed` — `data:{from, to}`, both canonical model ids (the `claude` catalog's launch tag included, e.g. `claude-sonnet-4-6[1m]`). Announces a mid-session model switch. **Two emit sites, one helper:** `Instance._announceModelSwitch` (`src/instances.ts`), called from `_trackModel`'s real-switch branch (the CLI switched interactively — `system/init` or `message_start` starts reporting a different id) and from `setModel` (the UI **Change model** picker, reached over the WS `model` frame). A session on a substitution backend reaches neither: `_trackModel` returns early for it and `setModel` refuses `409 BACKEND_LOCKED`. Re-selecting the running tier emits nothing — the guard compares CANONICAL forms, so a bare id that canonicalizes to the running tagged model is a non-change. `_trackModel`'s silent-adopt branch (a resume whose model could not be recovered) also emits nothing: that is discovery, not a switch. Notices form a **contiguous chain** — each `from` is the model the previous notice's `to` left the session on — because `setModel` reads `from` AFTER its control round-trip, inside which a CLI-reported switch can land and be announced by `_trackModel` first; reading it before would skip a step or repeat one.
  - **Both context-usage latches drop on it** — `Instance._lastContextUsage` (server, in the helper) and `UsageTracker.lastUsage` (client, in `public/usage.js`'s `apply`). A switch moves the window denominator without changing what the reading measured, so a retained reading would render the old model's used tokens against the new model's window; the chip reads `ctx —` until the next usage-bearing `message_start`/`context_usage`. The client drop is `lastUsage = null` only — never `reset()`, which would also blank the `cum.*` session totals a switch does not invalidate. `_trackModel` runs BEFORE the per-event `_emitUi` in `_handleStdoutLine`'s loop, so a switch frame that also carries usage re-latches its own reading in the same line and no `ctx —` flash is rendered; the emitted order is `model_changed` then `message_start`, and the client applies them in that order too.
  - **Retained** (unlike `context_usage`): `EventLog.push` accepts it, so it carries a `_seq`, survives a re-subscribe as a transcript notice, and advances `ring.nextSeq` — which is what lets a `setModel`-originated one freeze out a pending idle-drain settle (bounded in [architecture.md](architecture.md) → the idle task-drain settle). `public/wsRouter.js` refreshes the header chip on it.
- `playbook_warn` — `data:{tool, code, reason, sessionId?}`; the only UI signal for a **warn-mode** playbook refusal, emitted by `src/mcp/playbookGate.ts` on the **calling conductor's** instance (it made the call; `sessionId` — the refused call's target worker — is absent when the call named none, e.g. `spawn_instance`). Emitted strictly **after** the ledger `refusal` append, and only under `warn` — under `enforce` the refusal goes back to the caller, which needs no bubble. **UI-only** — `_emitUi` reaches the event ring and the WebSocket feed, never the CLI's stdin, so the conductor agent still sees the call succeed and enforcement semantics are unchanged. Ring-resident (survives a re-subscribe, lost on restart or eviction); the ledger row is the durable record. Rendered as an amber `SystemBlock` (`.block.system.warn`).
- `launch_failed` — `data:{code, signal, stderr}`; fires when a subprocess on a **substitution backend** (any backend but the identity `claude` row) terminates on its own (nonzero/signalled exit, not a commanded kill) — emitted right after the bare `exit` event. **Where the reason lives depends on the sub-case:**
  - **The wrapper ran and died** (daemon down, cloud-auth 401): `stderr` is the captured stderr, so the real reason is visible instead of an unexplained exit.
  - **The wrapper NEVER STARTED** (wrapper binary missing): no process ever wrote anything, so `stderr` is `null` and `code` is `-2`; the reason (`spawn <cmd> ENOENT`) is on the **preceding `spawn_error` event's `message`**. A failed spawn emits no `exit` at the OS level — this pair exists at all because `Instance` latches its terminal path on `'close'` as well (see [architecture.md](architecture.md) → Instance lifecycle → terminal latch).

  This is the only failure signal for a bad backend, since there is no spawn-time preflight. Never emitted for the `claude` backend or clean/commanded exits. **Known gap — no frontend consumer:** it reaches WS subscribers and the event ring, but is absent from `SHOWN_SYSTEM_SUBTYPES` (`public/blocks.js`), so nothing renders it; what a user actually sees on either sub-case is the co-emitted `exit` and `spawn_error` rows.

**`turn_end` additional fields:** carries `cacheMiss` (bool) + `firstReqCacheRead`/`firstReqCacheCreation` (the deciding first-request usage) + `firstReqEvicted` (`P − read_N` on the cross-turn path, else 0), persisted to `costs.jsonl` as `cache_miss`/`first_req_cache_read`/`first_req_cache_creation`/`first_req_evicted`. It also carries `durationMs` (turn walltime incl. tool exec, from the SDK result's `duration_ms` — genuinely per-turn), `durationApiMs` (the SDK's raw `duration_api_ms`, a cumulative session total kept for reference), and `durationApiMsDelta` (the per-turn LLM/inference time, derived as a delta against the prior turn — mirrors `cost`/`costDelta`). `duration_ms` is persisted as `duration_ms`; `durationApiMsDelta` is persisted as `duration_api_ms` (so aggregates sum true per-turn LLM time). Both are null on legacy rows written before capture; rows written before the delta fix carry the old cumulative `duration_api_ms` and are left as-is. `costs.jsonl` rows additionally carry `parentSessionId` — the spawning conductor's current sessionId, resolved from the worker's ephemeral `callerInstanceId` when the `turn_end` is observed, not when the (queued) write runs (null for UI/HTTP-created sessions) — which drives the per-session worker-tree rollup.

See the `EventLog` retention note in [architecture.md](architecture.md).

**Skill-load correlation (`attachSkillLoad`, `src/parser.ts`).** A `Skill` tool call's SKILL.md content is injected back by the CLI as a separate `user` message. The parser tags the resulting `user_echo` with `skillLoad: {skill}` only when it can correlate that message with a queue of pending `{toolUseId, skill}` entries (`pendingSkillLoads`) pushed when a `Skill` tool_use is seen; an uncorrelated injection renders as an ordinary `user_echo`.

*Two surfaces, two marker names, two correlation strengths* — normalized in one place (`skillInjectionMarker`), because the replay path testing the stdout field name is exactly what shipped the "skill bubble only renders live" bug:

| surface | "CLI-injected" marker | identity link | correlation |
|---|---|---|---|
| stream-json **stdout** envelope | `isSynthetic: true` (CLI builds it as `isMeta \|\| isVisibleInTranscriptOnly`) | none — never carries `sourceToolUseID` | FIFO order (the CLI's synchronous `tool_use` → `tool_result` → injection ordering) |
| persisted **jsonl** line | `isMeta: true` (also `isVisibleInTranscriptOnly` for compaction lines) | `sourceToolUseID` — the id of the originating `Skill` tool_use | exact id match only |

Match order in `attachSkillLoad(events, sourceLine, pendingSkillLoads)`: (1) `sourceToolUseID` names a pending entry → splice it out (consuming it) and tag; (2) `sourceToolUseID` names nothing pending → the entry is gone or was never made (expired by an intervening real turn, dropped by an erroring `tool_result`, or its `Skill` tool_use sits outside the replayed range — every `sourceToolUseID` line in the persisted corpus names a `Skill` tool_use, so this is never "an injection for a different tool"), claim nothing and consume nothing; (3) jsonl-marked with **no** `sourceToolUseID` → a compaction continuation or hook feedback, never a skill load (no FIFO fallback on this surface — every real jsonl skill injection carries the id, so a fallback could only mis-stamp); (4) stdout-marked → FIFO `shift`; (5) unmarked → a real user turn, expire the queue.

**`_handleAssistant` is the single registration point** for pending entries on the live path. Measured over the 11 stdout captures on disk (12,226 lines, 6 model ids): 353 `tool_use` ids appeared on both the `assistant` envelope and the streaming frames — envelope first in **353/353** — and **0** appeared on the streaming frames alone. **Nothing arrives streaming-only**, so registering at the envelope loses nothing; registering in the `content_block_stop` branch as well would only double-register, because the envelope lands first and the entry is still pending when the stop frame arrives, and the duplicate goes on to mislabel the next injection. A trimmed live capture of one such turn is committed as `tests/fixtures/scenario-live-skill-load.json`.

**Sub-agent `tool_use`s are deliberately not registered live.** The CLI forwards sub-agent turns as envelopes tagged with `parent_tool_use_id` and no `stream_event` frames. No injection was ever observed to follow one: the *one* captured sub-agent `Skill` call ran `tool_use` → `tool_result` → `system` with no injection. ⚠️ That is **n=1 and rests on a capture since deleted** — it is no longer re-derivable from anything on disk, unlike every other number on this page, and no surviving capture contains a sub-agent turn at all, so nothing corroborates it either way. An entry registered for a sub-agent could never be consumed by its own injection, and — its `tool_result` not being an error, so the error-drop never fires — would sit at the queue head and claim the next *top-level* injection. Not registering is therefore the conservative reading: it forgoes folding we have no evidence is possible rather than risking a mislabel. A sub-agent `Skill` still folds on **replay**, where the persisted jsonl does record the injection (`loadSubAgentTranscript`, pinned against `tests/fixtures/real-skill-load-subagent.jsonl`).

`src/transcript.ts`'s replay path threads the same queue (alongside the existing `blockCursor`) through `replayPersistedLine`, for both `loadPersistedTranscript` and `loadSubAgentTranscript`, so live and replayed sessions tag identically. Replay always parses a session's jsonl in one complete pass from line 0 (never a partial/windowed range), and the queue is a fresh local array per call, so a `Skill` tool_use and its content injection are always correlated within the same pass regardless of how the resulting events are later paged.

Where only FIFO order is available, an entry could be orphaned (skill errored, or its turn was interrupted before the injection arrived) and survive to mislabel a later, unrelated injected message, so entries are bounded (`expireSkillLoads`): an erroring `tool_result` for its `toolUseId` drops it immediately, and any genuine (unmarked) `user_echo` — a real prompt, including the `queued_command` replay branch and `Instance.prompt()`'s direct live emission — clears the whole queue, since the synchronous ordering guarantee is broken once a new real turn begins. The id-matching surface is not exposed to that risk.

The client (`public/conversation.js` `_renderUserEcho`) renders a `skillLoad`-tagged echo as a collapsed `<details class="block skill">` — summary names the invoked skill, body holds the raw SKILL.md text — instead of the plain-text bubble a normal echo gets.

**Agent-tool (subagent) task events.** The CLI emits `system` events with these subtypes:

| Subtype | Payload | Notes |
|---|---|---|
| `task_started` | `{task_id, tool_use_id, description, subagent_type, task_type, prompt}` | fired the instant an `Agent` tool_use dispatches (foreground or backgrounded) |
| `task_progress` | `{task_id, tool_use_id, usage:{total_tokens,tool_uses,duration_ms}, last_tool_name}` | periodic ticks while it runs |
| `task_updated` | `{task_id, patch:{status, end_time}}` | on a state transition; `status` one of `completed\|failed\|cancelled\|error` for a terminal one |
| `task_notification` | `{task_id, tool_use_id, status, output_file, summary, usage}` | the human/model-facing "it's done" ping — the same event a `<task-notification>` block wraps when injected back into a worker's own conversation |

None carry `parent_tool_use_id`, so they land as top-level `system` events like `turn_end`. `shouldRenderSystem` (`public/blocks.js`) hides `task_progress`/`task_started`/`task_updated` from the chat feed (`task_notification` falls through the same allow-list to hidden-by-default). That re-injected `<task-notification>` block is itself persisted as a `type:"user"` jsonl line — `isTaskNotificationContent` (`src/parser.ts`) recognizes it by tag shape and it's filtered at the same three sites as `SOFT_INTERRUPT_MARKER` (`parser._handleUser`, `transcript.isPureUserPromptLine`, `transcript.replayPersistedLine`), so it never becomes a `user_echo` or shifts a rewind/fork index. Server-side, `Instance` tracks in-flight ones in `_activeAgentTasks` (see `displayStatus` below). Task events fire for more than explicit `run_in_background` calls: background is the Agent tool's default, and long-running foreground Bash gets promoted to a task (every promoted Bash observed ran ≥3.5 s — a full test run always does; a foreground Bash exceeding its `timeout` is promoted too, its tool_result resolving early with "Command running in background with ID: …"). `task_started.task_type` discriminates the kinds: `local_agent` (Agent-tool subagents) vs `local_bash` (backgrounded/promoted Bash). Only non-`local_bash` tasks enter `_activeAgentTasks` — a promoted long-lived command (a started server) never emits a terminal task event, so counting it would pin `displayStatus:'running'` and defer the idle wake and session renewal indefinitely, leaving only a repeating heartbeat. Delivery has two shapes: a **slow** task's tool_result resolves immediately with an "Async agent launched" ack (`isAsync:true`), so `turn_end` can fire while `task_updated` is still pending; a **fast/blocking** task holds the tool_result open and delivers the full output right after its mid-turn `task_notification`, always before `turn_end`.

**Overage queue intercept (`Instance.prompt`).** A **non-internal** `prompt()` is **queued** (`{text, attachments, ts}` onto `_overageQueue`), emits `overage_message_queued`, and returns **before** `user_prompt` — so it neither resumes the session nor cancels the pending resume — when **either** intercept path fires:

| Path | Condition |
|---|---|
| (a) per-session | the session was stopped mid-turn and is armed: `autoStoppedForOverage && autoResumeAt` |
| (b) global gate | the GLOBAL gate is active: `inst._overageGate() → {active, resetsAt}`, where `active` is true iff `_overageActive && _overageResumeMode` (i.e. `stop-resume`, not plain `stop`) **and** `_overageResetsAt` is a valid **FUTURE** epoch-secs instant **and** `_inUsageWindowFlow(inst)` — the ROOT-scoped usage-window predicate (`src/usageWindowDomains.ts`), so a session whose whole root tree touches no monitored domain reports `active:false` and its sends flow normally, while a **non-Claude worker under a Claude conductor is in-flow**: it queues and shows the overage badge like any Claude sibling in that position. The one exception needs **both** conjuncts: a worker that was **mid-turn when the window tripped** **and** whose conductor is in control is stopped **un-armed**, and an un-armed session *refuses* instead of queueing (`OVERAGE_STOPPED_UNARMED` on the MCP surface, below). In-control alone is not enough — Pass 3 visits only mid-turn instances, so a worker that had already gone idle is never stopped or marked and queues like any other in-flow session |
| internal carve-out | every `internal:true` prompt **falls through** and bypasses both intercept paths — the idle-wake stub, the renewal reseed, and the auto-resume's own send (which first clears the flags via `cancel`) |

That future-`resetsAt` check is the **safety rail**: a queued send bypasses the manual-resume clear, so a missing/past/NaN reset must mean `active:false` (sends flow normally) or every session would lock out permanently. Path (b) makes it a **global lockout**: idle/existing and brand-new sessions queue too. A queued-only session (no `autoResumeAt` yet) emits an internal **`overage_queued`** (`{resetsAt}`) that the manager (`_armResumeNow`) turns into an immediate resume deadline via the controller — it can't wait for a mid-turn→idle transition. `_armResumeNow` has a second caller for the same reason: `_directOverageStop` on an already-idle session, which is never prompted and so never transitions at all. The one choke point covers the WS `prompt`, MCP `send_prompt`, and any REST path. On fire, `OverageResumeController.run` delivers all queued messages as **one combined** `prompt({internal:true})` (preamble + numbered list + concatenated attachments); an empty queue is the unchanged single resume. The preamble is **three-way**, selected by `overageResumeKind(inst)`: stopped mid-work (`_overageWasStopped`) → "…continue where you left off"; idle-parked (`_overageWasIdleParked`, the stop found it idle) → "You were idle when the overage stop fired…"; neither → the softened queued-only "Delivering the messages you queued while paused". `summary().queuedCount` carries the depth; `summary().overageActive` + `overageResetsAt` (read from the gate) let the client paint the paused state before the first message is typed. `_clearOverage` (window reset) clears `_overageResumeMode` and emits a fresh `status` for every instance so paused banners drop everywhere.

**`summary().displayStatus` / `activeAgentTasks`.** Additive, display-only fields alongside `status` — `activeAgentTasks` is the count of in-flight Agent-tool tasks (`_activeAgentTasks`, keyed by `task_id`; `task_type:'local_bash'` tasks are excluded at `task_started`, unknown `task_type`s counted); `displayStatus` is `'running'` when `status === 'idle'` and `activeAgentTasks > 0`, else identical to `status`. Never repurposes the `status` enum itself, so nothing that gates on the literal 5 `status` values (composer, kill/resume buttons) is affected. `IdleSubscriptionHub.onTurnEnd` **does** read the count (via `Instance.activeAgentTaskCount`): a `turn_end` while `activeAgentTasks > 0` **defers** the idle wake until the follow-up `turn_end` after the last subagent finishes. It **also** defers on `Instance.taskNotificationPending` — set when a `task_notification` fires *mid-turn*, cleared by any top-level `tool_result` that follows it within the turn (the task's own sync-delivered result, or the outer tool round-trip the CLI attaches queued notifications to). Still set at `turn_end` therefore means the notification is genuinely queued and an unprompted **re-invocation turn** will deliver it; the wake waits for that turn's `turn_end`. A notification consumed in-turn wakes at the same `turn_end` — parked (AskUserQuestion/ExitPlanMode) or not. So the dispatch-and-wake callback fires only when the worker AND its subagents are done and no re-invocation turn is owed (a never-finishing subagent — or a CLI that never flushes its queue — shows up as a repeating heartbeat instead). Every summary-based surface carries the fields — `GET /api/instances` plus every MCP tool that returns a worker summary through `toConductorView()` (`src/mcp/handlers.ts`). `displayStatus:'running'` (not just raw `idle`) means "still busy"; `status:'idle'` alone doesn't prove a backgrounded subagent has finished.

**`GET /api/instances/:id/events` paging mechanics.** Backward pages are **quiescent-aligned**: the page start snaps to the nearest quiescent point (no open block, every `tool_use` resolved; outer `user_echo`/`turn_end` reset the scan), so each page holds only whole blocks and complete tool round-trips; sub-agent group integrity pulls a child's Task head (and thus the whole group) into the page, or pushes the page start past any child with no head at or before it in the loaded array. Quiescent points are dense, so pages stay ~`limit`-sized. Backward pages are never empty while `hasMore` is true: a window whose only servable cut would be its own `end` (the whole tentative window fell inside a forbidden component anchored by a headless group) is instead served from that window's own pre-snap start, down-snapped to the nearest quiescent cut — so a sub-agent child with no reachable head may ride along on a page and park client-side rather than the page coming back empty. `hasMore: false` remains the only end-of-history signal, never `events: []`. The `nextBefore` cursor jumps the numeric gap between the two seq spaces. Evicted/archived events get their own dense `_seq` space strictly below `trimmedBefore`, cut so ring + archive never overlap — at the ring head's stamped `userIndex` when it's an outer echo (turn boundary), or content-correlated into the archive by `(kind, msgId, blockIdx)`/a `tool_result`'s `toolUseId` when it's mid-turn, falling back to the echo ordinal only when no correlator resolves (full correlator mechanics in [architecture.md](architecture.md) → `eventArchive.ts`) — a mid-turn head with no correlator hit ⇒ gap, never duplication — marked with a seq-less synthetic `{kind:'history_gap'}` event placed at the archive/ring **seam** — the last event of a page whose window *ends* on that boundary, or spliced at the seam's own offset **inside** the served slice when the window *straddles* it (one page, `[…, 12, <GAP>, 13, …]`) — so in the reassembled stream it always sits between the last archive event and the first ring-side one. **At least one** marker per backward walk: pages tile unconditionally (every window is served, none skipped), so some page always ends on the seam or straddles it. Not exactly one — a page whose snapped start lands exactly *on* the seam splices at offset 0 while the page below it splices at its own end, yielding `[…, 12, <GAP>][<GAP>, 13, …]`. That server-side double is known, narrow and deliberately not closed; the client collapses it at render time — `_renderHistoryGap` in `public/conversation.js` skips the append when the root's last element is already a gap divider, and `spliceBatchAbove` in `public/lazyHistory.js` drops a batch's trailing gap divider when the chunk below it begins with one (paged batches render into their own detached root, so the append-side check cannot see across a page seam) — so a doubled marker surfaces as **one** "earlier messages unavailable" divider. The dedupe is adjacency-scoped: markers separated by real content are distinct seams and both render. A page serving entirely **above** the seam with `hasMore:false` — only reachable via forward `after=` paging, where no further page follows — appends the marker after whatever it serves instead, so the eviction is never left unmarked). Synthetic `{kind:'task_completion', tasks}` events (no `_seq`) are spliced in after the completing `TaskUpdate` of any task batch below the tail, so lazily-loaded history shows the finished-task bubble. Full mechanics in [architecture.md](architecture.md) → `eventArchive.ts` / `taskReconstruct.ts`.

**Paging across a live rotation** (a managed renew or a typed `/clear` — the instance, its ring and its `_seq`/`userIndex` counters keep running while the backing jsonl changes):

- **The archive is the current segment's jsonl only.** Which segment owns which ring seq range is `EventLog.seams` (`src/instances.ts`); `currentSegmentScope` (`src/eventArchive.ts`) reads it.
- **Ring head predates the current segment** (`trimmedBefore` below the last seam's `startSeq`) ⇒ no archive is loaded: the ring is the whole servable history and `hasMore` is never optimistic.
- **Ring head inside the current segment** ⇒ the echo cut is **calibrated by content**, because the CLI writes a varying number of replay-only records (the `<local-command-caveat>` and `<command-name>/clear` lines, which replay as outer echoes) at the head of a post-`/clear` jsonl. When no ring turn correlates into the file, nothing is served from it and the seam marker lands directly before the ring head.
- **Floor marker.** Evicted events of *earlier* segments are never read and are marked by one `{kind:'history_gap'}` **before the first event this pager can serve** — the current file's first event, or the ring head when no archive is loaded. It is only ever spliced at offset 0:
  - backward: the first event of the terminal page (`hasMore:false`);
  - forward: only when the requested window reaches the evicted seqs — `after < 0` (MCP `fromSeq: 0`), or, with no archive loaded, `after + 1` below the ring head's `_seq`. An incremental poll from `nextFrom` or from `trimmedBefore` never carries it;
  - never appended by the terminal-forward backstop above, which still applies only to the no-`sessionId` marker.
- **Both markers on one page** — `[<GAP floor>, archive…, <GAP seam>, ring…]` — only when a page starts at the floor and also contains the seam: two distinct losses with real content between them. When the cut is 0 they are adjacent and one marker covers both.
- The seam-marker rules above (at least one per backward walk, the known double) are unchanged.
- **Live `get_transcript` shares this pager** (`source:'ring'`): a call without `fromSeq` is the newest backward page and carries the floor marker only when that page reaches the floor; older segments are never read.
- **The lineage route composes this pager per segment** ([Lineage scrollback](#lineage-scrollback)) and passes `markFloor: false` only when it serves what the floor stands for (the ring-head view or an older step) or marks it itself (a `top` gap). The seam marker is never suppressed.

### Lineage scrollback

`GET /api/instances/:id/lineage-events` (`pageLineageEvents`, `src/lineagePager.ts`) owns the cross-segment walk only; every page comes from a single-segment pager MCP also reads through.

**Sources, newest first** — per request, the lineage row's full chain (`chainFor`, tombstones included) is read, then the ring is captured in one tick. `H` = the segment owning the ring head (`segmentOfSeq(seams, trimmedBefore)`; the backing id before the first seam); `current` = the last seam's segment.

| Source | `segment` cursor | Served by | Floor marker (`markFloor`) |
|---|---|---|---|
| **live** | `null` | `pageInstanceEvents(inst)` — exactly `/events`' pager — then `insertRingSeamDividers` | only when nothing older is walked (no view, no step, no `top` gap) |
| **view** of `H` | `H` (only when `H !== current` and `trimmedBefore > 0`) | `pageInstanceEvents(segmentRingView(…))` — `H`'s file cut at the ring head as it stood before the rotation that superseded it; cursor ≤ `trimmedBefore` | only when there is no step and no `top` gap |
| **disk** step | the step's id | `loadStampedTranscript` + `pageStampedTranscript` (the two halves of MCP's `pagePersistedEvents`); a tombstoned step or missing file serves one `[{kind:'history_gap'}]` page | never |

- **Which older segments** (`lineageSteps(chain, H)`): walk the chain from `H` toward `initial`. An entry whose immediate successor (tombstones included) is a `prune` is that prune's original — skipped, never read. Every other boundary is a renew and gets one `segment_seam`, plus one `history_gap` when the skipped run just above it contained a tombstone. `top` = one `history_gap` above everything when the walk ends on a skipped run containing a tombstone, or the chain's oldest entry is not `initial` (an entry missing outright rather than tombstoned). An `H` absent from the chain walks nothing.
- **Marker placement.** Markers go at the start of the newer source's terminal page, top → bottom, so each is served once per walk. When a terminal page has no events and no markers, the next source is served in the same request; a response is empty only when history is exhausted.
- **Continuation.** live → the view (cursor `min(before, trimmedBefore)`, no marker) when viewable, else the first step; view → the first step; step `j` → step `j+1`; the last source → `top`, then `hasMore: false`.
- **The view's one value beyond the seams:** its `_userEchoCount` is the echo counter at seam `k+1` — the `userIndex` of the first outer `user_echo` at or after that seam in the captured ring, else the live counter. The archive cut reads it only for an initial (`startSeq 0`) segment.
- **Dividers inside the live ring**: `insertRingSeamDividers` draws one before each later seam's rotation init whose `startSeq > trimmedBefore`; a seam exactly at the floor is drawn by the walk's own marker instead, so no response carries both. The client additionally collapses a same-label divider repeated across responses, keeping the upper one.
- **Inherited cursor hazard**: a ring trim past the client's oldest rendered seq between two requests mixes the live and file seq spaces, exactly as it does for `/events`.

**`postWorktreeCreate` result field** — present on `POST /api/instances` responses and MCP `create_worktree` / `spawn_instance({createWorktree:true})` results when a worktree was created. Shape: `{ ran: boolean, source?: 'in-tree'|'store'|null, exitCode: number|null, durationMs: number, output: string, truncated?: true, timedOut?: true, descendantsMaySurvive?: true, skipped?: 'disabled'|'STORE_HOOK_LOCAL_ONLY', error?: true }`. `ran:false` means no hook script existed, or a hook was found and deliberately not run — `skipped` says which: `'disabled'` for the kill-switch `ORCH_DISABLE_POST_WORKTREE_HOOK=1` (which returns before hook detection, so it carries **no `source`**), and **`'STORE_HOOK_LOCAL_ONLY'`** — the one skip that does carry `source:'store'` — for a store-sourced script on a non-`local` system (the script lives under cc's own store, so running it there would hand the remote shell a path that exists only on cc's machine; shipping the body across needs a cc-owned location on the system, which is a later phase). An **in-tree** hook is unaffected on any system — it is already there. When `ran:true`, `exitCode` is the script's exit code (0 = success; non-zero = failure, but worktree creation still succeeded). `output` is capped to a tail bound (`HOOK_OUTPUT_CAP`; `truncated:true` when the raw output exceeded the cap); timeout `ORCH_POST_WORKTREE_TIMEOUT_MS` (default in `src/worktrees.ts`) — `timedOut:true` when the script was killed at the timeout, `exitCode` is null in that case, and `descendantsMaySurvive:true` alongside it means the project's system could signal only the direct child (its provider does not advertise `processGroupSignal`), so whatever the script started may still be running — the timed-out-`npm ci` case. Absent, never `false`, whenever the process group was reached. The hook is non-fatal: a failure or timeout never rolls back the worktree.

**`<store>/pending-resume.json` entry schema** (one per carried-over session, written by `drainToManifest`, consumed by `restoreFromResumeManifest`): `project`, `sessionId` (the cross-restart identity + `--resume` key), `cwd`, `mode`, `effort`, `thinking`, `model` (the concrete id for every backend — a Claude version id OR another backend's model id, byte-exact), `contextWindowTokens` (the session's last known capacity in raw tokens, or `null`; a **fallback only** — used if the model's custom-model row was deleted before the restart, since live registry resolution wins whenever it succeeds), `backend` (a registry id — belt-and-braces alongside the durable `session-backends.json` sidecar; a resume whose recorded backend has since been REMOVED from the registry is refused `422 BACKEND_GONE` rather than silently falling back to `claude` with a foreign model id), `worktreeName`, `temp`, `conducted`, `debug`, `title`, `firstPrompt`, `autoApprovePlan`, `group` (`conductor`/`worker`/`other`), `wasBusy` (re-prompt gate), `workers` (conductor entries only). Pending **overage auto-resume** state — persisted so a resume that was armed in memory survives the restart: `overageResumeAt` (fire deadline, epoch secs = window reset + buffer; `null`/absent ⇒ no pending resume), `overageStopped` (stop-resume intent boolean), `overageWasStopped` and `overageIdleParked` (the two positive resume-preamble selectors — stopped mid-work vs. the stop found the session idle; both false ⇒ queued-only), `overageResetsAt` (window reset, epoch secs), `overageQueue` (messages queued during the wait window — `[{text, attachments, ts}]`, restored onto `_overageQueue` so they still flush with the resume). On boot, an entry with `overageStopped` + finite `overageResumeAt` **and** a live `models.onOverage` of `stop-resume` re-arms the wall-clock sweep after the session is live + idle — the policy outranks the persisted mark, so under `stop`/`none` the entry restores as an ordinary session instead (`RESUME_TEXT` iff `wasBusy`, no deadline, no badge) and its `overageQueue` is dropped; a deadline already past fires on the first sweep tick, carrying whichever preamble the restored selectors resolve to (`overageResumeKind`) — not `AUTO_RESUME_TEXT` unconditionally, since the restore sets `overageIdleParked` before re-arming (and the `RESUME_TEXT` re-prompt is suppressed for it).

## MCP tool protocol

Mounted at `POST /mcp` (Streamable HTTP, JSON-RPC 2.0). Tools are listed in [features.md → MCP interface](features.md#mcp-interface). This section specifies the wire contract — a **clean break** with no backwards-compatibility aliases.

**Input params.** The worker handle is always `sessionId` (the stable session id; the per-process `instanceId` is internal and never accepted — a legacy `{id}` arg hard-fails as unknown). Every worker-addressing tool takes `{sessionId}` — the class is exactly the tools whose `inputSchema` declares it, the same predicate `governableToolNames()` computes the governable set from, and deliberately not re-listed here (see [Playbooks](#playbooks)). `renew_session` is the one where it is **optional**, and that is the whole distinction (with it: ask that worker to renew itself; without it: renew your own session). `merge_worktree` and `sync_worktree` are **not** in that list — they address a worktree, not a worker: `{project, worktree, allowDirty?}` and `{project, worktree}`. `spawn_instance`'s `resume` already takes a sessionId. Worktree is always `worktree` (never `worktreeName`), and there is **ONE spelling per worktree**: the store key, the `worktreeName` and the directory basename are one string — the slug or the 6-hex id. Every worktree-addressing input — MCP args and the REST `:wt` path segment alike — takes that string exactly, and anything else is a **404**; nothing parses a name out of a path and nothing aliases one spelling to another. `spawn_instance` takes `createWorktree:true` (fresh worktree off HEAD) and/or `worktree:"<name>"` (attach existing) — the old `worktree: boolean|string` overload is removed. `create_worktree` and `spawn_instance` both also take `baseWorktree` (base the new worktree on another worktree of the project — see [Feature branches](features.md#worktrees)) and `name` (slugified into the new worktree's branch + dir); on `spawn_instance` both require `createWorktree:true` and are refused **400** otherwise rather than ignored — `name` names the worktree, never the session. `createWorktree:true` alongside `resume` is likewise refused **400 `RESUME_TAKES_NO_WORKTREE`** (`_doCreateResolved`, `src/instances.ts`), before the worktree is created: a new worktree is a new cwd, and the transcript dir is keyed on that path, so it can hold none of the resumed session's history. An explicit `worktree:"<name>"` alongside `resume` skips the project/worktree recovery below, so it is checked rather than trusted: a name that is not where `findSessionLocation` places the session is refused **400 `RESUME_WORKTREE_MISMATCH`**, naming where it actually ran. Comparison is on the resolved record's `worktreeName`; naming the session's own worktree stays legal, and a session that cannot be placed is left to the pre-flight. `spawn_instance` and `send_prompt` additionally take the playbook-policy arguments in [Playbooks](#playbooks). `send_prompt` also takes `forward:{sessionId}` (see `send_prompt({forward})` below) — the one **nested** worker handle on this surface, since every other worker reference above is a top-level `sessionId`.

**Prefix resolution (MCP boundary).** Before strict-live resolution, the MCP dispatch layer (`src/mcp/server.ts`) resolves the incoming `sessionId` arg of any tool that declares one through `InstanceManager.resolveSessionRef` — so a caller may pass an **unambiguous prefix** (e.g. first 8 chars) in place of the full UUID. It is the single, uniform chokepoint (covers `describe_session` too, and `send_prompt`'s nested `forward.sessionId`) and is **non-destructive**: an exact full-id match always wins (even if it is also a prefix of another id) and passes through unchanged; a prefix that matches exactly one id is rewritten to that full id; no match is left untouched (so the strict-live paths below still produce `SESSION_NOT_LIVE`/`SESSION_UNKNOWN`/on-disk lookups). A prefix that matches **more than one** id (or a prefix shorter than `SESSION_PREFIX_MIN` (see `src/instances.ts`) that matches any) soft-refuses `{ok:false, code:'SESSION_AMBIGUOUS', sessionId, reason, matches:[<public ids>]}` (`isError:false`) — the ids **whole**, never sliced: a public id is 8 chars only until a mint-time collision extends it (`PUBLIC_ID_LEN_EXTENDED`, `src/sessionLineage.ts`), and two extended ids share their first 8, so truncating would print the same candidate twice. The resolution **universe** is, for every in-memory instance (live **and** exited in `byId`), its **public id plus every backing id it has run under** — broader than live-only, so a prefix unique among live workers but shared with an exited in-memory session is ambiguous rather than mis-resolved; historical disk-only sessions are out of scope (address them by their full id — and on `describe_session` that means the full **handle**, since a full backing/segment id soft-refuses `SESSION_NOT_A_HANDLE` there; see [Public vs backing id](#mcp-tool-protocol) below). Resolution at **those three** sites is entirely in-memory, so it stays synchronous. **`resume`** (spawn_instance) is the fourth site: same chokepoint, same decision, but **async** and over a wider universe — `InstanceManager.resolveResumeRef` overlays the **lineage store** (`src/sessionLineage.ts`) onto `byId` and decides the **union** in one pass, at a cost of one JSON read per `spawn_instance({resume})`. It has to be wider: the ordinary resume target is not in `byId` at all — a conductor worker is temp, so its exit evicts it, and `src/resumeRestart.ts` skips `group:'worker'` on boot, so after an orchestrator restart a conducted worker is never re-entered. Deciding the union (rather than consulting the store only on a memory miss) is what makes a prefix unique in memory but shared with a cold session `SESSION_AMBIGUOUS` instead of a confident wrong answer. It also differs in what it **rewrites**. It answers TWO ids: the public id (which the policy gate needs — its projection is keyed by it) travels beside the argument as `resumeHandle`, while `args.resume` is rewritten **only for a prefix**. An exact **segment** id is left verbatim, because `resolveBacking` returns a named segment as itself and `current` only for a public id — so normalising a segment to its handle would silently redirect the resume to the session's newest transcript. A prefix names no particular segment, so the handle is the only reading available (and `create()` cannot resolve a prefix itself).

**Public vs backing id.** A session has one **public id**, fixed for life: the first 8 hex chars of its first CLI `session_id`, minted through a collision-checked store (`src/sessionLineage.ts`). That is the only id that crosses an API / MCP / WS / UI boundary, and it is what `sessionId` means everywhere on this surface. The CLI's own `session_id` **rotates** on every managed `/clear` and on every prune; that rotating value is the **backing id**, confined to process launch (`--session-id`/`--resume`) and transcript resolution (the `${backingId}.jsonl` transcript, the subagent dir). It reaches no caller: it is absent from `Instance.summary()` and from `CONDUCTOR_VIEW_KEYS`, and that absence is the enforcement. A session with **no lineage row** — anything pre-dating the store, or never rotated and never minted — has public id == backing id; that is the store's base case, not a legacy branch, so there is no migration and no backfill.

Three input forms are accepted, all resolving to the same session: (1) the public id; (2) an unambiguous **prefix** of it; (3) **any full backing/segment id, permanently** — not transitionally. Form 3 is a **guarantee**, so the full UUIDs already written into wiki pages, resume manifests and old kanban cards keep resolving; do not "clean it up". Naming a segment directly opens **that** segment rather than redirecting to the newest, so an archived transcript stays individually addressable.

**One scoped exception: `describe_session`.** Form 3 stands **as a resolution guarantee** — it is not repealed, and it still holds for internal callers and for every other `sessionId` argument on the surface. `describe_session` is a conductor-facing *inspector* whose contract is deliberately narrower: it takes the **handle only**, and a backing/segment id soft-refuses `{ok:false, code:'SESSION_NOT_A_HANDLE', handle, reason}` naming the handle that owns it (the refusal echoes that handle, never the id passed in, so the tool emits no backing id at all). The principle is about what the **conductor sees and uses**: it must never hold a `~/.claude` UUID. Read a scoped narrowing here, not an inconsistency to tidy away. The check is **`publicIdFor(input) !== input`** (`src/sessionLineage.ts`) and must **never** be a length or shape test: a session with no lineage row has public id == backing id (the base case above), so a full 36-char UUID may be the only handle it has — `publicIdFor` accepts it, and refuses only an id the store knows to be *someone else's* segment. The refusal cannot fire for a session still in `byId`, because [prefix resolution](#mcp-tool-protocol) at the dispatch chokepoint rewrites an exact segment match to that session's public id before the handler runs; it fires for segment ids whose session is no longer in memory.

| Input | Verdict |
|---|---|
| Exact match on a public id, or on any segment id | **Resolves** (exact always wins, even when it is also a prefix of something else) |
| Prefix shared by two segments of the **same** session | **Resolves** — the answer set is of sessions, not of candidate strings |
| Prefix spanning a session's public id and one of its own segments | **Resolves** |
| A session's public id that is also a prefix of a **different** session's segment | **Resolves to the exact match** (public ids are claimed before segments) |
| Prefix shared by two **different** sessions (by public id or by segment) | **`SESSION_AMBIGUOUS`** — the input genuinely names two sessions |
| No match | `null` — the strict-live / disk-probe paths below still run |

`matches` on a `SESSION_AMBIGUOUS` refusal carries **public ids only**.

**Worker resolution (strict-live for addressing, disk-backed for reads).** `sessionId` (post prefix-resolution) resolves to its single *running* (proc-attached) instance. If the session is known but has no running process → `{ok:false, code:'SESSION_NOT_LIVE', sessionId, reason}` (resume via `spawn_instance({resume:sessionId})`); if no such session anywhere → `{ok:false, code:'SESSION_UNKNOWN', sessionId, reason}`. Both are normal results (`isError:false`), matching the soft-refusal convention. The resolver **never auto-respawns** — a dead session is a refusal, not a resurrection.

Every tool that **addresses** a worker (drives it, changes it, reaps it) resolves this way. The exception is the three call sites that need a session's **bytes** rather than its subprocess — `get_transcript`, `get_recent_messages`, and `send_prompt`'s `forward` **source**, which performs the same read — and they resolve through the sibling `getInstOrDisk`: live instance → **on-disk transcript** → refusal. So a retired worker stays readable and forwardable without being resurrected; see [Disk-backed reads](#disk-backed-reads-ring-first-fallback-on-demand) for the mechanics and the two refusals that survive it. `kill_instance` is live-only (it cannot reap an already-exited non-temp instance by sessionId — accepted under strict-live). `forward.sessionId` resolves **independently** of the target `sessionId`, with its own `FORWARD_SESSION_NOT_LIVE`/`FORWARD_SESSION_UNKNOWN` codes (see `send_prompt({forward})` below) — so a two-session call always says which side to fix.

**Resume pre-flight (`spawn_instance({resume})`).** Before constructing an Instance or spawning `claude --resume`, `InstanceManager._doCreate` verifies the resume id has a **resumable conversation** at the resolved cwd (`hasResumableConversation` in `src/transcript.ts`: the `${sessionId}.jsonl` exists **and** holds ≥1 `user`/`assistant` record — mirroring the CLI's own "No conversation found" criterion, so a marker-only crash stub of `last-prompt`/`permission-mode` lines does **not** qualify). If it doesn't, `spawn_instance` soft-refuses `{ok:false, code:'SESSION_UNKNOWN', sessionId, reason}` (`isError:false`) instead of spawning a subprocess that would exit 1 and crash-loop. The `reason` names **the cwd it probed** (carried off the thrown error as a `cwd` property) — a refusal that omitted it read as a bad id when the real fault was the wrong place — while `sessionId` echoes **the caller's own input, untouched** — a prefix the transport already resolved to the handle, or an exact id verbatim, which for a named segment is a segment id rather than the handle. That is an echo, not a leak (the caller already held it); what the refusal never surfaces is the backing id `create()` has internally rebound `resume` to by that point, which for a handle or a prefix would be an id the caller never had. On a project on a **system** the resolved cwd is the project's own path there, so there is one candidate and no scan — and the probe resolves that cwd against **that remote's own transcript root** (`transcriptRoot`, `src/projects.ts`), so two boxes at one absolute path are probed separately rather than answering for each other. This guards the case a caller pins `project`+`worktree` (which bypasses the `findSessionLocation` "project required" net — a net that catches a session on a **system** too: its transcript is located from the project's path on that machine, which is where the CLI ran, so the bare `{resume}` form recovers project and worktree there as well) with a mistyped/bogus resume id. Because the refusal fires before any Instance is registered in `byId`, the refusal is **idempotent**: repeating the same `spawn_instance({resume})` returns `SESSION_UNKNOWN` again, with no phantom crashed instance for the retry to resolve through.

**Resume liveness guard + reclaim (`spawn_instance({resume})`, and every other resume).** The pre-flight above sits beside a liveness guard: `_doCreate` refuses **409** when `InstanceManager.isSessionLive(publicId)` — the same authority governance reads, **not** `liveForSession`. Two consequences on this surface. (1) A resume issued **during a relaunch window** — a prune's kill→relaunch (`rotationPending`), a rewind's or a respawn's (`_relaunching`) — now 409s instead of starting a second `claude --resume` on one transcript; a `proc`-only guard read those as gone. (2) A resume over a **settled** in-memory instance for that session **retires** it (`InstanceManager.remove`) rather than registering a second one, so at most one `byId` entry ever answers to a public sessionId — but only on the way to **success**: the retire is the last statement before registration, so a resume refused by any check above it (`SESSION_UNKNOWN` pre-flight, `BACKEND_GONE`, an invalid `mode`/`thinking`/`effort`, a worktree or mirror-geometry refusal) leaves the session's existing instance exactly as it found it. The refusals that fire from `launch()` are **below** it and so do not get that protection — `MIRROR_ADVERTISEMENT_CHANGED`, `FUSE_REMOTE_UNREACHABLE`, `FUSE_MIRROR_ROOT_ABSENT` (see the REST table above): those land after the retire and after the replacement registers. Known and deliberately unfixed; rationale in [architecture.md → Instance lifecycle](architecture.md#instance-lifecycle). (3) While a resume is in flight for a session, `POST /api/instances/:id/respawn` on one of that session's instances refuses **409** — the two would otherwise race over the same Instance. `isSessionLive` is a `.some()` over **every** instance answering to the session, not `anyForSession`'s first match — an exited instance ordered ahead of a live one used to shadow it, which is what made `playbook_state`'s `live:` field untrustworthy. Mechanics and invariants: [architecture.md → Instance lifecycle](architecture.md#instance-lifecycle).

**Emitted handles.** Returns never carry an `instanceId`: `toConductorView()` projects every summary through an **explicit allowlist** (`CONDUCTOR_VIEW_KEYS`, `src/mcp/handlers.ts`) before it reaches any conductor-facing return — every `toConductorView()` call site in `src/mcp/handlers.ts`, including `list_sessions`, which then renders it as text — and inline returns emit `sessionId` instead of `id`. What it withholds is the **complement**: every key `summary()` emits (`src/instances.ts`) that the list does not name — pinned as a set by `tests/mcp-conductor-view.test.mjs`, so a field added to `summary()` reaches no conductor until someone names it in `CONDUCTOR_VIEW_KEYS`. Today that is the per-process handles `id` + `callerInstanceId`, `debugDir` (the `debug` boolean is the signal), the UI-only `autoApprovePlan`, `playbookEnforcement` (the gate reads the CALLING conductor's level and never its target's, so a worker's copy is the inert default), and `interrupting` / `overageStoppedUnarmed`, each of which the caller either already knows or is told where it would act (the `OVERAGE_STOPPED_UNARMED` refusal). `backingSessionId` is withheld one level earlier — `summary()` never emits it at all — and that absence is what keeps a rotating id off this surface. It publishes `lastRotatedAt` / `rotationReason` / `segmentCount`: pinning the public id makes a rotation invisible, which removes the only tell a conductor had that one happened, so a renewed or pruned worker would otherwise be indistinguishable from one that had gone quiet. Deliberately rotation-generic rather than `lastRenewedAt` — prune rotates too. It publishes `ownerSessionId` / `awaitingUser` / `awaitingUserSource` — what a conductor-first view groups and sorts by: `ownerSessionId` is the public sessionId of the root of a **live** conducted worker's spawn chain (`null` on a hand-spawned session, on a conducted one spawned with no `?caller=`, and on any dead instance); `awaitingUser` (`'question'` \| `'plan'` \| `null`) is the sticky ask with no real user message since, and `awaitingUserSource` (`'tool'` \| `'text'` \| `null`, null iff `awaitingUser` is) says whether an `AskUserQuestion`/`ExitPlanMode` or a turn-end text ask set it. Always null on a conducted worker. Semantics, classifier and limits: [architecture.md](architecture.md) → "Ownership and awaitingUser". `list_sessions` alone adds the keys in `LIST_ONLY_KEYS` (`src/mcp/handlers.ts`), attached on top of the projection by `listSessions`'s own `view()` closure rather than supplied by `summary()`: `awaitingWake` comes from `InstanceManager.list()` (`src/instances.ts`) — **caller-side**: true while an ARMED WAKE on a session this instance owns is pending, so it is what distinguishes "idle because I am waiting" from "idle because I am done". Armed-wake-pending, **not** "a session it owns is mid-turn": the two diverge in the states the wake is deliberately held through — a deferred `turn_end` (a live subagent or an unconsumed task notification, with the target already back to `idle`) and a dropped idle-drain settle. It also stays true across a heartbeat, which reports without consuming. `playbook`/`stage` come from the read-only playbook projection. The `list_sessions` description in `src/mcp/tools.ts` is the authoritative key list for the worker summary, and the same test pins it against the allowlist — so an allowlisted key that nobody documented fails too. `?caller=<instanceId>` on the per-worker MCP URL is the caller's own **stable instanceId** (baked into `--mcp-config` at spawn). It is the instanceId — NOT the sessionId — deliberately, though no longer for the original reason: a baked public sessionId would in fact stay valid now that rotation cannot move it. What the instanceId buys is that it identifies the **process**, which is what a caller-addressed tool acts on, and it needs no store read to resolve. (`spawn_instance({resume})` mints a new instanceId for the same session, so the instanceId is stable on the process axis and the sessionId on the session axis; `?caller=` wants the former.) The `/mcp` boundary (`src/mcp/server.ts`) resolves the handle to the caller's **current** sessionId per request via `InstanceManager.callerSessionId(handle)` (`byId.get(handle)?.sessionId`), so every downstream handler still receives a live sessionId as `callerId` — valid across any number of rotations, with no event or re-registration. A handle naming no live instance yields `callerId=null` (the same "no caller" path as an absent param). The instanceId never leaves the server as an identity: the two sites that surface the caller (the `renew_session` return, the plugin `caller.sessionId` envelope) emit the resolved sessionId. For `spawn_instance` the resolved caller instance is stored as `callerInstanceId` (internal/REST only). Internally the idle-wake graph (`_idleSubscribers`, plus the ownership edges behind it) and overage timers (`_autoResumeTimers`) are keyed by the **stable instanceId**; sessionId is translated to instanceId at the dispatch boundary (`noteDispatch`/`setIdleTimeout`) and back for delivery — so an in-place `/clear` rotation needs no re-keying.

**Session renewal (`renew_session`).** TWO FORMS, one tool; a call that mixes their arguments is refused `INVALID_RENEW_FORM`. **Bare** (`{summary}`): renew the CALLER, resolved from `?caller=<instanceId>` (a missing/unresolvable caller throws). A session can renew **repeatedly** — the handle resolves per request, and the sessionId it resolves to is pinned, so it is the same value before and after every rotation. It arms a managed `/clear` on the caller (see [Subprocess protocol → Managed `/clear`](#subprocess-protocol)); `SessionRenewController` is keyed by the caller's `instanceId` because that is the handle its `?caller=` URL carries, and the idle-wake graph and overage timers are instanceId-keyed for the same reason — so the rotation strands nothing and needs no migration. **Targeted** (`{sessionId, directive?, followUp?}`): *request* that worker renew itself. The server prompts it (a normal, non-`internal` prompt carrying `directive` — what to be sure to capture — plus the summary template), records the caller's ownership before prompting — unconditionally, since a request whose outcome the conductor never hears is useless — and returns immediately with bare data (`{requested:true, sessionId, note}`, no `ok`). **The target must be FREE:** a request needs a turn of its own, so a target that is mid-turn — or idle but owing a re-invocation turn, or with live subagents, or with its sends parked in the overage queue (`renewalDeferredBy`, the same predicate `SessionRenewController` defers the `/clear` on) — soft-refuses `SESSION_BUSY`, carrying `status` plus `busy` naming which of those it is. Registering against a turn the worker did not open for it would expire the request as a decline the worker never saw and spend the conductor's armed wake on unrelated work; an overage-parked prompt would open no turn at all, so the conductor would be told a healthy worker "did NOT finish" on every heartbeat instead. **The worker's own bare self-call is the only channel a summary is ever authored on, and the conductor cannot force it:** the request is held for exactly ONE turn — the worker's own `renew_session({summary})` consumes it (folding `followUp` into the reseed under its own fence, distinct from the summary section), and the worker's `turn_end` expires it. That expiry **is** the decline, recorded server-side at the moment it happens and reported on the wake of the conductor that ASKED — the note is keyed to that requester, so a second conductor watching the same worker is never told about a request it did not make, and the note dies with the wait it was recorded for (delivered once, or dropped on a silent disarm/purge/a dead caller) rather than surfacing on a later, unrelated wake. A request deliberately opens **no** rotation window, so a decline rides the worker's ordinary, undeferred `turn_end`. `renew_session` declares a `sessionId`, so it is **governable** like any other targeted tool and a stage may deny it (see [Playbooks](#playbooks)); the bare form names no worker, so it is never subject to a stage's policy, and neither is the worker's own self-call (policy applies to conductor callers only). **Interlock:** soft-refuses `{ok:false, code:'SESSION_ROTATING'}` when a prune is already rotating the subject (or a rewind/fork holds `_mutating`), because a prune makes `prompt()` 409 and the renewal's reseed **is** a `prompt()` — interleaving them would clear the context and then lose the summary. On the targeted form the same check reads the TARGET and also refuses while it has a renewal already pending (`renewalPending`), so a request can never clobber one. Re-arming a renewal over its own pending one stays idempotent. The reseeded prompt also carries a server-generated mechanical state block — see [features.md → Session renewal](features.md#mcp-interface) and [architecture.md](architecture.md).

**Idle wake-stub text (`IdleSubscriptionHub.deliver`).** Four variants, injected as an `internal:true` `user_echo` into the caller. **All four carry the `[[cc:wake-callback]]` marker** (defined in `public/wakeCallback.js`, imported by both `src/idleSubscriptions.ts` and `public/conversation.js`), so all four render as the wake-callback UI bubble with an orchestrator badge (🔔); only **Folded** additionally carries the `[[cc:wake-body]]` separator + payload. The markers survive persist/replay in the CLI jsonl and are stripped from display, not from the prompt the model reads. A declined `renew_session` request prefixes a one-sentence note into the **summary** of whichever variant is delivered (`buildWakeStub`'s `note`, `_plainStub`'s `note` — wording in `declineNote`, `src/idleSubscriptions.ts`), so it lands in the always-visible line; it is not a fifth variant. The presence of `[[cc:wake-body]]` is the "is it folded" signal — the client renders a collapsible `<details>` when a body is present, else a body-less summary line (no caret).
- **Folded** (real `turn_end` delivered to an already-idle caller): `[[cc:wake-callback]]<summary>[[cc:wake-body]]<payload>` (via `buildWakeStub`). The summary names the worker + says it finished; `<payload>` is `flattenPayload(meta, bodies)` — the compact-JSON metadata block + each raw body block joined by blank lines, i.e. **byte-identical to the content a default `get_recent_messages({sessionId})` call returns** (via the shared `buildRecentMessages` builder in `handlers.ts`, so the fold never drifts from the tool). `send_prompt({forward})` (below) renders a **third**, separate view over the same underlying selection (`selectRecentMessages`) — deliberately **not** byte-identical to this fold, since it is worker-facing rather than conductor-facing: no `sessionId`/`msgId`/char-count telemetry, bare `--- message i/n ---` boundaries, and the guiding text placed last inside a fixed frame.
- **Plain** (`turn_end` but caller was **mid-turn** at delivery, so the send is deferred to when it goes idle): `[[cc:wake-callback]]` + the unchanged `Worker \`<sid>\` finished its turn. Call get_recent_messages(...) to inspect the result.` pointer (via `markPlainStub`, body-less) — decided synchronously at delivery time, so the deferral keeps the plain stub even though the caller is idle by the time it actually fires.
- **Timeout** (heartbeat): `[[cc:wake-callback]]` + the unchanged `... did NOT finish — timed out after <duration> ...` pointer, where `<duration>` is `humanizeDuration(window)` (`src/duration.ts` — compact `30m` / `1m30s` / `<1s`, never ms) (via `markPlainStub`, body-less). Repeats every window while the target is mid-turn and consumes nothing, so a **Folded**, **Plain** or **Interrupted** variant still follows at the real `turn_end`.
- **Interrupted** (the `turn_end` a FORCE-abort produced — `Instance.turnForceAborted`, set at the one chokepoint both doors go through, so the MCP `interrupt_turn({force:true})` and the UI's stop button behave identically; **every** consuming path reports it — `turn_end`, the idle task-drain settle, and rotation completion alike, since which one resolves an abort's wake is an accident of what the worker was doing. A consuming path only READS the flag (`_abortQualifier`); it neither consumes nor clears it, so `turnForceAborted` legitimately stays true after a wake is delivered, until the next turn start. Adding a consuming path means adding the read and nothing else — clearing has its own home, [architecture.md](architecture.md#component-layout)): `[[cc:wake-callback]]` + a `... was INTERRUPTED — ... did NOT finish and whatever it produced is PARTIAL ...` pointer (via `markPlainStub`, body-less). **Deliberately never folded**, even to an idle recipient: the presence of `[[cc:wake-body]]` is the client's "this is the finished result" signal, so folding partial aborted output in would invite the conductor to act on exactly what the abort was meant to stop it acting on. Delivered to every owner EXCEPT the one that called for the abort, whose own entry was silently disarmed first (`disarmSilently`, caller-scoped) — a target can have several owners, and telling the others a killed turn "finished" is the misreport this variant exists to prevent, while silencing them would strand a wait nothing else can end. The UI door has no interrupter, so there every owner takes this path.
All four keep `internal:true` semantics (bypass the overage queue intercept, never cancel a pending auto-resume) — including **Interrupted**, which is the abort path, i.e. exactly where not cancelling a pending auto-resume matters.

**Held wakes and stopped turns (models that can't take a mid-turn injection).** Two extra rules, both keyed on `Instance.acceptsMidTurnSteering` / `steerPending` (see [models.md](models.md#mid-turn-steering-capability)):
- **Recipient side.** A wake for a conductor that is mid-turn on such a model is **held** in `IdleSubscriptionHub._deferredWakes` (keyed by caller instanceId) and delivered at that conductor's own next `turn_end` — never a block-edge stop: an idle report is not urgent, and aborting a conductor would sever its in-flight orchestration. Held-then-delivered means the recipient is idle at delivery, so it gets the **Folded** variant — unless the turn it reports was force-aborted, in which case **Interrupted**, which is never folded regardless of recipient state. It re-defers once more while a steer is parked on the recipient (`steerPending`), and flushes on the `system`/`steer_settled` event when a steer drains with no turn to end (failed or overage-queued delivery) — the strand a `turn_end`-only trigger would leave. A held wake whose **worker went busy again** is delivered with the plain stub plus a leading "no longer idle" note rather than dropped or folded.
- **Target side.** `steerPending` joins `activeAgentTaskCount` / `taskNotificationPending` / `rotationPending` in `_onTurnEnd`'s defer gate: the `turn_end` an armed block-edge stop produces means the worker was **cut off** to deliver a steer, not that it finished, so the wake stays armed for the steered turn's real `turn_end`.

**Input validation (`validateArgs`).** Beyond type/enum/required, the server enforces the declared `pattern`, `minLength`/`maxLength`, `minimum`/`maximum`, and array `items.type`. **Unknown properties are rejected** (not silently dropped): `unexpected argument '<k>' — not a recognized parameter for <tool>. Allowed: <keys>`. Validation failures return `isError:true` with the message as a single text block. Schemas also declare `default`s mirroring handler defaults (documentation; handlers still apply them).

<a name="mcp-result-format"></a>
**Result format.** `content[0]` is a **compact** JSON block (no pretty-print) for every tool except the six that render plain text instead (see [Rendered read results](#rendered-read-results)). Pure-metadata tools emit just that one block. **Text-payload tools** append separate raw, **un-escaped** text blocks in `content[1..]`:

| Tool | content[0] metadata | content[1..] bodies |
|---|---|---|
| `project_read` | `{path, size, truncated, encoding, lineCount, lineCountExact, startLine?, endLine?}` | one block: utf8 file text, or base64 (binary) |
| `project_diff` (diff mode) | `{project, worktree, baseRef, head:<sha>, contextLines, offset, truncated, nextOffset, totalLines, totalBytes, hasUncommittedChanges, untracked, ahead, includedFiles?, omittedFiles?}` | one block: raw unified diff, always including a `@@@ uncommitted working tree changes (git diff HEAD) @@@`-separated section when uncommitted changes exist (empty string when no diff and no uncommitted changes) |
| `project_diff` (summary mode) | single JSON block `{project, worktree, baseRef, head:<sha>, summary:true, ahead, totals, files[], uncommitted:{totals, files, untracked}}`. When the uncommitted diff could not be READ, `uncommitted` is `{unknown:true, reason}` instead — absent counts, never zeroed ones, since a zero here reads as "nothing will land if you merge right now". The committed half throws on the same failure. | — |
| `get_recent_messages` | `{sessionId, messages:[{index, msgId, hasToolUse, textChars, textTruncated, hasPlan?, planPath?, questionCount?, blocks?}], source:"ring"\|"disk", omittedToolOnly, retained:{firstSeq,lastSeq,trimmed}, hint?}` | one body block **per message**, block k+1 ↔ messages[k]: prose plus a `--- plan ---`/`--- questions ---` fenced section when the turn produced one (the plan header is `--- plan · saved to <path> ---` when the message carries a `planPath`; a message whose plan is a path with no readable text is that header alone) (order-faithful to when those blocks occurred — never empty for a plan/question-only turn) — UNLESS >1 message is returned, in which case every body is prefixed with `--- message i/N · msgId · textChars chars ---` |

<a name="rendered-read-results"></a>
**Unanswerable reads.** A git command that did not answer is never rendered as a positive fact about the tree: `project_status` prints `DIRTY (unknown — git status did not answer)` instead of `DIRTY (0)`, `project_diff`'s summary carries `uncommitted:{unknown, reason}` instead of zeroed totals, and the commit-log payload carries `hasUncommitted: undefined` + `uncommittedUnknown:true` instead of `false` (and refuses **502** on a `git log` that did not answer, which it tells apart from a legitimately empty history via `hasUnbornHead`). Every one of those is a command that **RAN and answered non-zero**, and the realistic trigger is `runGit`'s own 16 MB output fence — which fires on exactly the tree least safe to describe as clean. A command that **never ran or never answered** takes a different route out: `runGit` throws a system refusal (502 `GIT_DID_NOT_RUN` / 504 `GIT_TIMED_OUT`), so none of these degraded renderings appear for it — the read fails by name instead.

**Rendered read results.** Six tools — the five recon read tools (`list_projects`, `list_worktrees`, `list_sessions`, `describe_session`, `project_status`) plus `describe_playbook` — return a **plain-text rendering as their entire result**: one `content[0]` text block, no metadata block, **no JSON at all** (a `JSON.parse` of it throws). `describe_playbook` is text on its **success path only**; its `PLAYBOOK_UNKNOWN` refusal is a JSON `{ok:false, code}` like every other soft refusal, so branch on `code` before reading the text. Handlers opt in via `textResult(text)` (`src/mcp/content.ts`) — Symbol-tagged like `textPayload` rather than sniffing `typeof result === 'string'`, which would reshape any plugin returning a string through the bridge's `result` passthrough. Transport branch in `src/mcp/server.ts`; renderers in `src/mcp/readRenderers.ts` over the primitives in `src/mcp/textRender.ts`.

There is **no structured channel** beside the text — no MCP `structuredContent`, no `outputSchema` — so the text is the whole contract: **every fact a conductor acts on is in it.** Two ways a field gets there: rendered unconditionally, or declared in a `DeviantSpec[]` with a default and surfaced only when the value leaves it (`overageActive`, `archived`, `isGitRepo:false`, `unbornHead:true`, `degraded` on a `list_projects` block — `! unreadable project record <reason>`, the one thing a project row says about ITSELF, since every kind of project renders alike — `system`/`remoteId` on a `list_projects` block, which default to `local`/`null` and so print only for a project whose record names another system, and `remoteId` only for one that also names a target on it, `systemUnreachable` — `! system unreachable <reason>`, which leads the block because it is why the git facts under it are absent rather than measured, `dirtyTruncated`, …), which keeps the common case short without hiding live state.

Fields deliberately **dropped** rather than hidden — not rendered and not reachable anywhere, each because it is redundant on screen or not actionable: `list_projects` `worktrees[].parentProject`/`.parentPath` (identical to the project header above them; `list_worktrees` renders `parentProject` in its own header, and drops `parentPath` for a different reason — it is not row-invariant once a worktree can be based on another, and is derivable either way: the project path for a root-based worktree, the base worktree's own `worktreePath` line for a derived one) and `worktrees[].sessions.{archivedCount,lastActivity}` (`list_sessions({project, worktree})` has it); `sessions.handCount` and `worktrees[].sessions.handCount` (a sidebar filter input; `list_sessions` carries each row's `conducted`); `list_sessions` `pid`, `createdAt`, `contextWindowTokens`, and on an inactive row every runtime field plus `size`; and `firstPrompt` wherever a `title` exists. A session's recorded `mode` is not a field either — the one off-process mode fact is the `resumes-hot` DEVIANT flag. Full rationale in the header comment of `src/mcp/readRenderers.ts`.

**The recon split.** `list_projects` answers "what projects/worktrees exist and what is their git state"; `list_sessions` is the complete answer to "what sessions exist, live or resumable, and where". So `list_projects` prints `live N` as a **count only** — the payload carries no sessionIds at all (`liveCount`, from `InstanceManager.liveCountForProject`). That count and the live/inactive split in `list_sessions` both read one predicate, `isDeadStatus` (`src/instances.ts`), so the two tools cannot report a different fleet; `tests/mcp-instance-exits.test.mjs` pins the agreement — including for a **non-temp exited instance**, which `byId` retains indefinitely (respawn resumes it) and which must therefore count as dead, not live. The REST `GET /api/projects` keeps its own `sessionIds` array (`src/routes.ts`) — the sidebar consumes it, and it is a separate contract.

Two session counts on a `list_projects` block mean different things and are *both* intended to: `live N` counts in-memory workers, while `sessions N` counts non-archived transcript files on disk (`summarizeSessions`, `src/projects.ts`) — exactly what `list_sessions({project, worktree})` would list, which is why it keeps that name. A worktree with no worker can therefore read `sessions 2`. The MCP handler and the REST route pass that helper **different arguments on purpose**: REST passes `instances.tempSessionIdsForPlace(...)` so the GUI can render live temp sessions as their own nodes, while MCP passes nothing — excluding them would show `sessions 0` on a worktree with two running workers. So the same worktree legitimately shows a lower count in the GUI than in the MCP text.

`list_sessions` groups by the directory the sessions live in — each project's **main checkout first**, then its worktrees. The main checkout is the one group that always exists, so the top of the output stays put as worktrees come and go. Within a group, live workers lead (marked `LIVE`): `byId` rows failing `isDeadStatus`. Inactive rows are that group's persisted sessions with no process, read from `listSessionsForCwd` (`src/projects.ts`) — the same function behind `GET /projects/:name/sessions`, so there is one definition of "which sessions exist and which are archived", not two. The live sessionIds are passed as `excludeSessionIds`, so live and inactive are disjoint and a dead-but-retained `byId` instance reappears as an inactive row off its own transcript. An inactive row is a `SessionRow`: it has no `status`/`effort`/`model`, so it renders as ONE table line (`sessionId  lastActivity  playbook/stage  flags  title`) rather than a worker block padded with `—`; the two shapes are unmistakable at a glance. Its flags column carries `awaiting-user <kind>,awaiting-user-via <source>` when the transcript ends on an unanswered ask; a live block's `flags` line carries `owner <sessionId>` and the same pair. **Archived** sessions are counted in every group header and collapse to a `+N archived` line; `includeArchived:true` lists them inline. They stay off the default listing because archiving is the deliberate act of taking a session off the list — but the count is always visible, so an archived session is never silently invisible. Each group header carries its branch. A **worktree** group also carries its divergence, rendered `↑N ↓N vs base` — commits vs the base branch it will merge back into (`getWorktreeMergeStatus`, the same helper `list_projects` uses), which is what decides whether resuming into it lands somewhere useful. A **main checkout** group carries no divergence: its equivalent number would be vs the remote upstream, a different question that renders `? ?` on any project without one, and it cost three git subprocesses per project to say nothing. The `vs base` label is load-bearing — it is what makes the main checkout's silence read as "a different question was asked" rather than "not computed". `list_projects` still reports upstream status for a project.

**Cost.** `list_sessions` is disk- and git-bound. Measured 2026-08-09, **before** the lineage bulk load and per-row lineage projection landed (2026-08-12) — so read the figures below as the comparative ratio they were taken for, not as today's absolute ms. On a 24-project install with 6 worktrees (31 candidate cwds, 25 non-empty), old and new **interleaved in one process** (median of 21 — measuring them in separate runs drifts by 2× on filesystem-cache state alone, so interleaving is the only comparison worth quoting): **~76 ms filtered to one project / ~353 ms unfiltered**, against **~33 ms / ~258 ms** for the same scan without the grouping headers. The added cost is git: one call per rendered group header, on top of the one `git worktree list` per project the scan already did. The filtered ratio is the worse one (~2.3× vs ~1.4×) because with only a handful of cwds the git calls dominate. Per cwd the disk work is one `readdir`, one `stat` per transcript, one bulk read per store `listSessionsForCwdWithCounts` loads up front (`src/projects.ts` — every sidecar it reads **plus** the session lineage; one each per cwd, never per session) and a `readFirstPrompt` open per LISTED transcript — **not an exhaustive list**: the memoized 64 KB tail read behind `lastActivity` is per listed transcript too, and is described where `lastActivity` is, below. Three things keep it from compounding: `listSessionsForCwdWithCounts` returns the rows and the archived count from **one** walk — pairing `listSessionsForCwd` with `summarizeSessions` instead costs a second `readdir`, a second `stat` of every transcript and a second archived-set load for a number the first walk already has; archived rows are counted before the `includeArchived` filter but their first prompt is read only when they are actually listed, so a project where archived outnumbers active 25:1 pays no per-transcript cost for its `+N archived` line; and a wholly empty group is dropped before its git call in an unfiltered listing. `includeArchived:true` opts back into the full per-transcript read (~404 ms unfiltered). The `project` filter narrows the scan *before* it happens (only that project's cwds are visited), so passing it is the mitigation; the tool description says so. There is no cache — a stale session list would be worse than a slow one.

`list_sessions` takes an optional `project` filter — which now covers **the project AND its worktrees**; reaching a worktree's sessions no longer requires naming it — plus an optional `worktree` to narrow to one (without `project` it soft-refuses `{ok:false, code:'PROJECT_REQUIRED'}`), and `includeArchived`. Groups sort by project, then main-checkout-before-worktrees, then worktree name. Live rows within a group sort by project, worktree name, `createdAt`, `sessionId` (`compareInstanceRows`, `src/mcp/handlers.ts`); inactive rows sort by `lastActivity` descending instead — a stopped session has no `createdAt` on this surface, so recency comes off its transcript. **Not the transcript's mtime**: the CLI appends untimestamped bookkeeping records (`last-prompt`, `mode`, `ai-title`) as its process exits, so a mass subprocess exit stamps every live session's file within the same millisecond, hours or days after those sessions actually stopped. `lastActivity` is the ISO `timestamp` on the LAST timestamped record INSIDE the jsonl (last in file order, not newest by value — they differ only where interleaved sidechain records land a few ms out of order), read from a bounded 64 KB tail and memoized per file (`src/sessionActivity.ts`); it falls back to mtime only when the tail holds no timestamped record. Unsorted `byId` Map order was creation order: deterministic between calls, but it interleaves projects and does not survive a restart. The filter is **validated** via `getProject`, the same check every project-addressing tool uses: an unknown name (or `''`, which fails the name regex) soft-refuses `{ok:false, code:'PROJECT_UNKNOWN'}` rather than rendering as an empty fleet — one of two cases where this tool returns JSON instead of text. `.conduct` is legal by NAME rather than by a directory probe (the dir is created lazily at first conductor spawn), and the **unfiltered** scope appends it too — `listProjects` skips dotdirs, so without that a conductor hunting its own prior session to resume would see every project's stopped sessions and none of its own. A *valid* project with nothing in it still renders normally, and the heading echoes the filter (`SESSIONS (live 0 · inactive 0 · archived 0)  project foo`) so that emptiness is not read as an idle fleet.

`list_sessions` and `describe_session`'s **live** branch are the two of the five whose payload keys are a runtime-enumerable, code-owned list (`CONDUCTOR_VIEW_KEYS` + `LIST_ONLY_KEYS`, `src/mcp/handlers.ts`) — the same list, since both project through the one `conductorRowView` — so they are bound to their rendering directly: `tests/mcp-text-render.test.mjs` → *"list_sessions renders every allowlisted field"* feeds a unique sentinel per key and requires each to appear, with a small, non-empty, explicitly-named exempt set for the drops above. It is fail-by-default — a new allowlist key must be rendered or classified. The doc-drift gate in `tests/mcp-conductor-view.test.mjs` binds the allowlist to the tool *description* only; both are needed, since a field can pass that gate and still never be emitted. The sentinel fill runs through `renderSession`'s live branch as well as `renderSessions`, so a new allowlist key must be rendered on **both** surfaces or classified. `describe_session`'s **retired** branch is a `SessionRow` instead, so it falls in with the erased-type tools below. The other three tools' payload shapes are TypeScript types erased at runtime, so the same technique does not apply to them; their renderings are pinned by exact-output tests instead, which catch a field that stops rendering but not one added upstream and never rendered.

Handles stay full-length (sessionIds, absolute paths, branch names, `project_status`'s HEAD sha); a `baseSha` is shortened to 12 as informational context.

**`get_recent_messages` default-call bonding.** `count` defaults to 1 and is clamped to a bounded range (see the `get_recent_messages` schema). On the **default** call only (`count` omitted — not `count:1`), when the last message is plain prose the selection is bonded back to the turn's plan/questions message and spans from it through the end of that turn — so a split turn whose trailing prose spans two or more messages surfaces the plan/question together with all of it, without the caller needing an explicit `count`. A message counts as plan-bearing for this purpose when it has plan text **or** a `planPath`, so a plan that is only a path still bonds its trailing prose. The walk-back is **scoped to the current turn** (via the ring's `turn_end` seqs — a plan from an earlier turn is never pulled in), and a message that already carries its own plan/questions is returned alone. Any explicit `count` is literal (`slice(-count)`), bonding never applies.

**`get_recent_messages` tool-input descriptor.** `blocks[].input` is a **per-argument
descriptor** by default. Each top-level argument whose size is at most `TOOL_ARG_VALUE_CAP`
(`src/mcp/messageReconstruction.ts`) is emitted verbatim — strings gate on raw utf8 bytes,
everything else on its JSON encoding — and a larger one is replaced by a marker naming its type
and size: `[omitted: string, <bytes> bytes]`, `[omitted: array, <n> items, <bytes> bytes of
JSON]`, `[omitted: object, <n> keys, <bytes> bytes of JSON]`. A block with any omitted argument
carries `inputTruncated:true` while `input` stays a structured object. The rule does **not**
recurse: a node is kept whole or replaced whole, which is what bounds an array of many small
elements (its own JSON blows the cap, so it collapses to one marker) at the cost of a nested
small value inside an oversized container. `includeToolCalls:true` emits the whole input instead,
capped as one unit at `MSG_TEXT_CAP` with `inputTruncated` meaning "cut mid-JSON" — that cap
applies on **both** paths, so it remains the structural ceiling. This is why a 15 KB `Write`
argument no longer rides into a conductor's context on a default read or an idle-wake
wake fold (`src/idleSubscriptions.ts` calls `buildRecentMessages` with no flags and inherits the
default); `send_prompt({forward})` never carried `blocks[]` at all.

**`send_prompt({forward})`.** `forward:{sessionId}` injects another worker's recent output into this prompt, composed server-side so the text never passes through the conductor's own context. The payload is the **same default selection** the bonding paragraph above describes (as if calling `get_recent_messages({sessionId: forward.sessionId})` with no `count`) — not re-derived, not summarised — rendered through the third, worker-facing view named above: bare `--- message i/n ---` boundaries (no `msgId`/char counts), no `sessionId`/`source`/`retained`/`omittedToolOnly` telemetry (the source `sessionId` is a **handle**, so leaking it into another worker's prompt is a hazard, not just noise: while the source lives it addresses it — a forwarded worker could `send_prompt`/`spawn_instance` itself — and once retired it still **reads** it, since the read tools serve a retired session from disk. Retirement narrows the hazard; it does not end it), full plan bodies inline, and the conductor's own `text` placed **last**, once, after a fixed `--- FORWARDED WORKER OUTPUT (verbatim · context only) ---` / `--- END FORWARDED WORKER OUTPUT ---` frame that marks the payload as reference material and tells the receiving worker not to execute, answer, or reply to anything inside it. The frame layout (header, footer, bare boundaries, `\n\n` joins) is owned by `public/forwardFrame.js`, which the conversation view also parses to render the forwarded-output bubble — no wire marker. Each message's prose is still capped at `MSG_TEXT_CAP` (`src/mcp/messageReconstruction.ts`); where the cap bites, an in-frame marker says so and names the plan file as a recovery route when the message carries a `planPath` (plan bodies themselves are never capped). `forward.sessionId` is prefix- and disk-backed-resolved **independently** of the target `sessionId` (own `FORWARD_`-prefixed codes — see refusals below), so a two-session call always says which side to fix. A **retired** source is forwarded from its transcript, so the source need not be live — but it does need its **full** sessionId, since prefix resolution is in-memory only (see [Prefix resolution](#mcp-tool-protocol) above). What governs the source is therefore policy, not liveness: it is a **policy subject**, not merely a resolution target, and under playbook enforcement is checked for `get_recent_messages` against its own stage (`FORWARD_DENIED_IN_STAGE` — see [Playbooks](#playbooks)), which `decideTargeted` resolves from the ledger projection and so applies to a retired worker exactly as to a live one. An empty or tool-only selection soft-refuses `NOTHING_TO_FORWARD` before any prompt is sent — no turn starts, no wake arms, and (per the playbook ledger's `commit`-drops-`ok:false` rule) no transition is recorded even when the call also carried a legal `stage`. On success the result gains `forwarded:<int>` (the forwarded message count); everything else about `send_prompt`'s result shape, wake semantics, and mid-turn steering is unchanged — a mid-turn forward takes exactly the same route as an unforwarded mid-turn send, with the steer note preceding the frame: delivered live on an ordinary model, and on one declaring `midTurnSteering:false` routed through the block-edge stop with `POST_STOP_STEER_NOTE` instead (the deferred branch keys on the composed text, so the frame rides along either way).

**Annotations.** `tools/list` entries carry `annotations`: `readOnlyHint` (all `list_*`, `describe_*`, `project_read`, `project_status`, `get_*`), `destructiveHint` (`kill_instance`, `delete_worktree`, `merge_worktree`, `prune_session`), `idempotentHint` (`set_mode`, `set_project_workspace`, `set_project_remote`, `set_idle_timeout`, `set_session_title`, `create_workspace`, `delete_workspace`, `rename_workspace`, `kill_instance`).

**`ok` / refusals.** `ok` is reserved for **soft refusals** only. Acknowledgement tools (`kill_instance`, `set_idle_timeout`, `set_session_title`, `approve_plan`/`reject_plan`, `answer_question` success, the workspace tools, `set_project_workspace`, `set_project_remote`, `delete_worktree` success) return bare data with **no `ok`** — `send_prompt` left this list once `forward` gave it a refusal path: an ordinary send (forwarded or not) still returns bare data, but a refused `forward` returns `{ok:false, code, reason}` like any other soft refusal. Expected business refusals return `{ok:false, reason, code}` and are **not thrown**, with stable codes: `WORKTREE_ATTACHED`, `WORKTREE_DIRTY`, `WORKTREE_DIRTY_UNKNOWN`, `WORKTREE_HAS_DEPENDENTS` (`delete_worktree` — `WORKTREE_DIRTY_UNKNOWN` is a dirty check that **ran and failed**. A failed check must never read as a passed one: falling through to `git worktree remove --force` deletes a worktree whose dirtiness was never measured. `force:true` overrides both. A check that **never ran or never answered** does not produce this code: the precheck's `worktreeDirtyLines` is unguarded, so `runGit`'s throw escapes the soft-refusal vocabulary as 502 `GIT_DID_NOT_RUN` / 504 `GIT_TIMED_OUT`, and `force:true` does not override it — measured, the forced path fails 504 at `git worktree remove --force` too); `SESSION_NOT_LIVE` / `SESSION_UNKNOWN` (every worker-**addressing** tool, from strict-live resolution — **not** the read tools, which serve a retired session from disk; on those two `SESSION_NOT_LIVE` carries its second meaning instead: the transcript exists, under some transcript root cc knows about, but sits in an encoded-cwd directory no registered project or worktree owns, so it cannot be read — re-register that worktree); `SESSION_UNKNOWN` also from **`spawn_instance({resume})`** when the resume id has no resumable conversation on disk (resume pre-flight above); `SESSION_AMBIGUOUS` (any worker-addressing tool, when a sessionId **prefix** matches >1 in-memory session or is shorter than `SESSION_PREFIX_MIN`; carries `matches:[<8-char ids>]`; on `send_prompt` the ambiguous side can be either the target `sessionId` or `forward.sessionId`, and `reason` names which); `NOTHING_TO_FORWARD`, `FORWARD_SESSION_NOT_LIVE`, `FORWARD_SESSION_UNKNOWN` (`send_prompt({forward})` — the forward source resolves independently of the target. `FORWARD_SESSION_NOT_LIVE` narrowed when forward gained its disk path: a non-live source is ordinarily forwarded from its transcript, so this now means the transcript could not be **reached** (the orphaned-transcript case above), not merely that the process is gone — a retired source with a readable transcript forwards, and one with nothing readable refuses `NOTHING_TO_FORWARD`; these carry `forwardSessionId`, never a bare `sessionId`, whenever a source id was resolvable — the malformed-argument case of `FORWARD_SESSION_UNKNOWN` (`forward` carried no usable `sessionId`) carries neither, since there is no id to name — see `send_prompt({forward})` above); a **fourth** `FORWARD_` code comes from the playbook gate rather than the handler — `FORWARD_DENIED_IN_STAGE`, when the source's stage denies the read (see [Playbooks](#playbooks)); `NO_PENDING_QUESTION`, `ANSWER_COUNT_MISMATCH`, `INVALID_OPTION`, `NOT_MULTISELECT`, `EMPTY_ANSWER` (`answer_question`); `OVERAGE_STOPPED_UNARMED` (`send_prompt`, `approve_plan`, `reject_plan`, `answer_question` — the target is a worker the overage auto-stop left **un-armed**, so its conductor is the sole driver and a send to it can be neither delivered (the account is still throttled) nor queued (the queue flushes only on a resume deadline it deliberately does not have). Shape `{ok:false, code, sessionId, reason}`; lifts by itself when the window resets, since the predicate `Instance.overageSendRefused` gates on the live overage window. The **WS** `prompt` frame diverges deliberately: it keeps `Instance.prompt`'s throw, surfacing as `ack ok:false` and a failed send in the composer, which is the right shape for a human — see [architecture.md](architecture.md) → overage); `WORKTREE_BEHIND`, `BASE_BRANCH_MISMATCH`, `PARENT_MID_MERGE`, `PARENT_DIRTY`, `PARENT_STATUS_UNKNOWN`, `WORKTREE_DIRTY`, `WORKTREE_STATUS_UNKNOWN`, `NOTHING_TO_MERGE`, `MERGE_FAILED`, `SYSTEM_UNREACHABLE` (`merge_worktree`. `SYSTEM_UNREACHABLE` covers the System failing at any point, not only at entry — the WHOLE body is converted, because a transport failure mid-merge otherwise arrived as a git-shaped answer and was reported as `MERGE_FAILED` carrying a transport cause. It carries **`mayHaveCompleted: true`** when the transport dropped *after* `git merge` was issued: the orphaned merge was observed completing on the far side after cc had already reported failure, so `git merge` is **not** individually atomic and a refusal implying "nothing happened" would be wrong — check the parent before retrying. `PARENT_MID_MERGE` is the state that leaves behind (`MERGE_HEAD` set), reported separately because `PARENT_DIRTY`'s repair — commit or stash — does not apply to it. `PARENT_STATUS_UNKNOWN` and `WORKTREE_STATUS_UNKNOWN` are a `git status` that did not answer, on the parent and on the worktree's own tree: an unread tree is neither clean nor dirty, and the guard refuses instead of skipping itself. `allowDirty:true` overrides the worktree one, as it does `WORKTREE_DIRTY`. All returned rather than thrown, because every blocker here is a code the caller renders and a throw would surface as a 500 with nothing to act on — same `WORKTREE_DIRTY` meaning as `delete_worktree`'s (the worktree's own tree, not `PARENT_DIRTY`'s parent repo), overridable here via `allowDirty:true`); `WORKTREE_HAS_DEPENDENTS` (`sync_worktree`, `merge_worktree`, **and** `delete_worktree`; carries `dependents:[<worktree names>]`, and on `delete_worktree` is overridable via `force:true` — see [Feature branches](features.md#worktrees)); `INVALID_SUMMARY` (`renew_session`, empty summary); `INVALID_RENEW_FORM` (`renew_session`, any illegal combination of its two forms' arguments — `summary` with a `sessionId`, `directive`/`followUp` without one, or a `sessionId` naming the caller itself; `reason` names which); `SESSION_BUSY` (`renew_session` targeted form, when the target is not free; carries `status` + `busy`); `INVALID_PRUNE_TARGET` (`prune_session`, when the `sessionId` names the caller itself — a prune respawns its target, so self-pruning would kill the calling process mid-call; `reason` routes to `renew_session`); `SESSION_BUSY` also from `prune_session` when the target is mid-turn (`reason` names `interrupt_turn`); `SESSION_ROTATING` (`renew_session`, when a prune or another mutation already holds the caller — or, on the targeted form, the target — and `prune_session`, when any rotation already holds its target — see [Session renewal](#mcp-tool-protocol); the REST prune path raises the same code as a 409, though the REST error handler forwards only the status and message). The only constant `ok:true` is `merge_worktree`/`sync_worktree` success (shape shared with the REST land endpoints).

**Errors.** True faults are caught and returned `isError:true` as a prose block — `<message> (HTTP <statusCode>)` when the handler set a `statusCode` — followed by a structured `{error, code, statusCode}` block. `code` derives from `statusCode` (`400→BAD_REQUEST`, `404→NOT_FOUND`, `409→CONFLICT`, `500→INTERNAL`). Example sources: `project_read` 404, invalid `baseRef` 400. (`describe_session` is not one — every way it can fail to answer is a soft refusal.)

**Conventions listings carry their own incompleteness.** `list_project_conventions` and `list_conductor_conventions` return **`{conventions:[…], incomplete?:string}`** — an object, not the bare array. `incomplete` is **present only when the convention catalog is degraded** (`CatalogList.degraded` — an `extraProvider` throw, a transient plugin **placement** failure, or a latched **discovery scan** that could not reach an enabled plugin's project; see [architecture.md](architecture.md#component-layout) → `src/fragmentCatalog.ts` and [plugins.md](plugins.md) → *Discovery rules*), so its **presence is the signal** and a healthy result is exactly the old array under one key. It carries a **prose sentence, one per surface**, and neither names the missing slug or plugin — the flag carries no cause and the failed plugin's declared slugs are not on the channel these handlers read. The object shape is required, not cosmetic: `degraded` is the array's own property, which neither `.map()` nor the dispatcher's `JSON.stringify(result)` carries. The project-scope sentence names the **committed** consequence, phrased conditionally on the loss because the flag fans out to every scope and can fire where nothing was lost: whatever is missing from the listing cannot appear in the line-1 `CONVENTIONS.md` marker of a project created from it, and no later regeneration adds it back. The conductor-scope one names the contrast — nothing there is committed, since the role doc is recomposed from the catalog on every spawn. `create_project` is not refused during a degrade; **on success only** it logs one server-side `createProject:` line naming the project, and that line — not the listing sentence — is where the lost **`scaffold`** directive is reported: a scaffold-bearing convention that dropped out of the listing cannot be picked, so no directive is emitted for it and nothing reissues one. The REST twins `GET /api/settings/conventions/{project,conductor}` deliberately do **not** carry the flag.

**Disk-backed reads (ring-first, fallback-on-demand).** "Disk-backed" covers two distinct cases, and both apply to `get_transcript` and `get_recent_messages`:

1. **A live instance whose ring evicted the range** — the in-memory event ring is a fixed-cap (`DEFAULT_RING_CAP`, `src/instances.ts`) drop-oldest cache, and eviction is **invisible** to these tools (per-tool mechanics below).
2. **A retired session with no instance at all** — killing a temp worker *archives* its session (`Instance._archiveTempSession`) and drops it from `byId`, but **retains the `.jsonl`**, so the whole read is served from the transcript with no ring involved. `getInstOrDisk` (`src/mcp/handlers.ts`) finds it via the instance record if one survives, else by probing registered projects/worktrees (`findSessionLocation`). `source` reports `"disk"` on both tools, `get_transcript` reports `status:"exited"` (a session with no process is accurately dead; no `"not-live"` member was invented), and `trimmedBefore` is `0` / `retained` is `{firstSeq:0, lastSeq:-1, trimmed:false}` — honest, since nothing is retained in memory. Two consequences worth planning around: a retired session needs its **full** sessionId (the prefix universe at [Prefix resolution](#mcp-tool-protocol) is in-memory only), and a retired page carries only the event kinds the CLI **persisted**: no `turn_end`, no status/system events, nothing stream-only. That is also why turn bonding on the disk side partitions turns at outer `user_echo` events rather than `turn_end` — the same partition, from the boundary that *is* persisted (`src/transcript.ts`). A conductor must not poll a retired session for a completion event; `hasMore:false` is the end of it. If the transcript exists but sits under an encoded-cwd directory no registered project or worktree owns, it cannot be read at all (`encodeCwd` is one-way, so the directory name cannot be reversed into a `cwd`) and both tools refuse `SESSION_NOT_LIVE` naming that cause — deliberately not `SESSION_UNKNOWN`, so *retired* stays distinguishable from *never existed*. That scan (`findOrphanedTranscript`) sweeps the local transcript root **and every registered remote's**, because there is no single root any more; left local-only it would answer `SESSION_UNKNOWN` for every remote session where this more informative refusal is owed. It is also what an **upgraded** install's stranded pre-per-remote-config-dir transcripts land on: the place IS registered, its root moved, so the refusal names the cause slightly imprecisely and is still the more useful of the two. A retired session on a project on a **system** is NOT that case: `findSessionLocation` derives the cwd from the project's registered path, so the read is served from cc's own disk and **needs no data from the box** — an unreachable system does not refuse a read, only a spawn. It is not free of the box either: locating the session walks each project's worktree store through its system, so a **wedged** provider stalls the read rather than refusing it and a **down** one changes which worktree places exist — see `findSessionLocation` (`src/projects.ts`) for that contract.

Per-tool mechanics:
- `get_transcript({sessionId, fromSeq, limit})` pages via `pageInstanceEvents` — or, for a retired session, `pagePersistedEvents` (both `src/eventArchive.ts`, sharing one windowing core) — and is always **single-segment**: an older segment id of a live session answers with the live pager, and only the web UI walks earlier segments ([Lineage scrollback](#lineage-scrollback)). It translates at the boundary since the two surfaces deliberately differ: `fromSeq` is **inclusive** (events with `_seq >= fromSeq`, oldest-first — `fromSeq: 0` reaches the very first event), unlike the REST `after=` cursor above, which stays exclusive. Served from the ring; when the requested range dips below `trimmedBefore` (an evicted range) the on-disk session transcript is loaded and reconciled with the ring by `_seq` at a turn-aligned seam (no gap/dup). The response adds `{source, hasMore, nextFrom}` — `source` is `"ring"` vs `"disk"`, mirroring `get_recent_messages`, and tells a conductor it is reading history rather than a live stream; poll again with `fromSeq = nextFrom` (always the last served `_seq + 1`, so a caught-up re-poll returns nothing rather than re-serving the boundary event). `limit` is bounded with a fixed default. Replaces the old `truncated` field. Caveat: a single turn larger than the ring cap leaves a mid-turn `_seq` gap (covered by `get_recent_messages`) — but neither reasoning nor prose length triggers it any more, since the ring coalesces the per-token `thinking_delta`/`thinking_tokens`/`text_delta` floods to `O(blocks)` (see the `EventLog` retention note in [architecture.md](architecture.md), and the `thinking_tokens` entry above for provenance); only a turn with thousands of tool round-trips can still reach it. **Cursor consequence of that coalescing:** an open block occupies ONE slot whose `_seq` is stamped at its first fragment while its text keeps growing in place, and `nextFrom` is always the last served `_seq + 1` — so once served, an in-flight block is never re-served and incremental polling does **not** show it grow. Use `get_recent_messages` for in-flight prose (it reconstructs by `blockIdx` off the live ring, so it re-reads the growing slot on every call). Re-serving the slot at its unchanged `_seq` is deliberately NOT done: the client dedups by `_seq` (`public/conversation.js`) and would silently drop it.
- `get_recent_messages` is ring-first; only when the retained tail can't satisfy the requested recent **text** messages (and the ring was trimmed) does it read the on-disk transcript and merge by `msgId` (ring entry wins; bounded by `DISK_REPLAY_TAIL_CAP` (`src/mcp/messageReconstruction.ts`)). `source` reports `"ring"` vs `"disk"`. A genuinely missing transcript degrades to ring-only + a `hint`; never crashes — note that an exited **temp** session is not that case, since its jsonl is retained rather than deleted. On a **defaulted** call (no `count` passed) the ring must satisfy `n+1` text messages, not `n`, since the default path may bond in one preceding plan/question message (see below) — this raises the bar for staying ring-only before falling back to disk.

Note: the REST endpoints above keep their own `worktreeName` field — they are a separate contract from the MCP tools and were not renamed.

## Playbooks

A **playbook** is a JSON graph of **stages** a worker is bound to. The conductor declares its intent on the calls that create or move workers; the server verifies the move against the graph and appends it to a ledger. Definitions: built-ins in `playbooks/*.json`, user overlay in `<store>/playbooks/*.json`, and enabled plugins' `playbooks` (ids `<plugin-id>/<slug>` — manifest schema, freshness and disable semantics in [plugins.md](plugins.md)). Schema, validator and the policy decision live in `src/playbooks.ts`; the conductor reads a graph via `describe_playbook` — it is deliberately **not** restated in prose here or in any prompt.

**Scope.** Policy applies only when the caller resolves to the conductor (`isConductorInstance`, `src/conduct.ts`) — worker-side calls keep their existing recursion rules. Within that, a tool is **governable** iff its `inputSchema` declares a `sessionId` (plus `spawn_instance`, governed by the stage being *entered*). A tool declaring no `sessionId` names no worker for a policy to be read from, so it can never appear in a stage's `tools` map and is ungoverned; that gap is accepted. The membership of that class is computed from `buildTools()` by `governableToolNames()` and is deliberately not enumerated anywhere — a hand-maintained copy would drift.

**Subjects.** A governed call is checked once per worker it names, each against the tool describing what is done to *that* worker. `send_prompt`'s target is checked for `send_prompt` (plus its move); its `forward.sessionId` **source** is checked for **`get_recent_messages`** — the read a forward actually performs (`selectRecentMessages`, `src/mcp/handlers.ts`) — and for permission only: no move, no `needs`, no `pin`, since `stage`/`provenance` on that call belong to the target. So `forward` is **not** an exception to the governable-set rule above: it is an existing governable tool evaluated against a second subject, and a stage's `tools` map still names only tools that take a `sessionId`. The subject list matches, one for one, the places `dispatch()` prefix-resolves a handle it will then **check** (`sessionId`, each `provenance` value, `forward.sessionId`) — kept identical deliberately, since a handle policy cannot see is a handle policy cannot govern. The fourth resolution site, `spawn_instance`'s `resume`, is not a subject: `decideSpawn` reads it to find that worker's **existing** binding, not to check a second worker.

**New tool arguments.**

| Tool | Argument | Meaning |
|---|---|---|
| `spawn_instance` | `playbook` | Required on a **run root** (a spawn with no `provenance`); inherited from the `provenance` ancestors otherwise, and a conflicting value is `PLAYBOOK_MISMATCH`. |
| `spawn_instance` | `stage` | The stage to enter. It must declare `spawn_instance` (else `STAGE_NOT_SPAWNABLE`) — that tool is the one that **fails closed**, and a `"*"` wildcard confers no spawnability. |
| `spawn_instance` | `provenance` | `{"<stage>": "<sessionId>"}` — the workers satisfying the entered stage's `needs`. |
| `spawn_instance` | `resume` | Not a policy argument, but it **decides which rules apply**: resuming a playbook-tracked session inherits its recorded `playbook`+`stage` and is not a run root. See [Resuming a playbook-tracked worker](#resuming-a-playbook-tracked-worker). |
| `send_prompt` | `stage` | **Always** carried. Equal to the worker's current stage ⇒ a **self-edge**: always legal and never subject to the destination's `needs`, and ledgered as a `from===to` transition **iff the playbook declares that self-loop** (which is how a review/refine round becomes countable). Different ⇒ a transition checked against the edge set. |
| `send_prompt` | `provenance` | Satisfies the **destination** stage's `needs`, since a stage's entry conditions apply however it is entered. |
| `send_prompt` | `forward.sessionId` | The forward **source** — a second policy subject, checked for `get_recent_messages` against its own current stage (`FORWARD_DENIED_IN_STAGE`). Permission only; never checked for run membership — see Known limitations. |

**Optional `description`.** Every **stage** and every **transition** accepts an optional `description` string: conductor-facing intent — the conductor's *move* at that stage and what it expects back. Never a restatement of `tools`/`needs`/the graph, which are enforced and already returned by `describe_playbook`. Rejected at load (`readDescription`, `src/playbooks.ts`) if present and not a non-empty string; **no length limit** — the gate is editorial. Present iff authored: an unauthored description makes `describe_playbook` emit **no line at all** for it (no label, no `—`), so absence is legible in the text rather than signalled by an empty value. Authored text is rendered **verbatim** under a `description` label, indented one level deeper than the stage's own fields — never reflowed or truncated. The label and indent mark where the rendering ends and the author's text begins; they cannot disambiguate prose that is itself indented into a field column, which is contained editorially by the "never a restatement of the graph" rule above, not by the renderer. `list_playbooks` and the composed prompt's playbook listing (`playbookListing`, `src/conductorConventions.ts`) carry the **top-level** playbook description only. A transition `description` is reserved for the rare edge whose move is not already implied by the destination stage's `description` + `needs`. The built-ins are the templates to copy: **every** stage carries one, **no** transition does (pinned by `tests/playbook-schema.test.mjs`).

**The preferred-playbook convention.** Settings → Conventions → Conductor selects a **preferred playbook**, stored **globally** as the `defaultPlaybook` sibling key in `<store>/conventions/conductor.json` (the conductor is a singleton, and `composeCurrentConduct()` takes no instance argument — it runs before the instance exists). The selection is **tri-state** (`DefaultPlaybookSelection`, `src/conductorConventions.ts`), because never having chosen is not the same as having chosen nothing: **unset** — the key's *absence*, the only representation of that state — resolves to `DEFAULT_PLAYBOOK_ID` (`src/playbooks.ts`); `{"mode":"none"}` is the explicit opt-out that injects nothing; `{"mode":"playbook","id"}` names one. `resolveDefaultPlaybookId()` is the single home of the fallback. Only the **write** is validated against the loaded definitions: a stored id that stops resolving (a disabled plugin's playbook, a deleted overlay file) is **retained**, renders nothing meanwhile, is reported as `defaultPlaybookMissing` in the Settings payload, and applies again once it loads. Migration 0028 converts the older `<id>|null` shape, mapping a legacy `null` to **unset** (nobody who predates the tri-state chose the opt-out). At compose time its definition is **rendered** into the role prompt by `renderPlaybookConvention` (`src/playbookConvention.ts`): a `## Preferred playbook — \`<id>\`` header, one bullet per stage carrying `**<stage>**` + `(many workers)` when `workers:"many"` + the authored `description` **verbatim**, and a closing transition list with `via = on ?? send_prompt`. **Generated, never hand-authored** — that is what makes drift from the enforced graph impossible.

**What the section carries is decided by one rule: push into the system prompt exactly the facts with no channel that fires on its own; leave in the payload every fact a refusal or a pre-resolved field volunteers unasked.** So rendered: the stage `description` (nothing volunteers it, and it is needed to compose a brief *before* any call — a bad brief yields a soft review, never a refusal), `workers:"many"` (no refusal until `STAGE_AT_CAPACITY` has already fired, and it shapes a fan-out decision made before any call), and the transitions (a shape error is expensive and non-local, unlike a refused call). Deliberately **not** rendered: the `tools` policy (`TOOL_DENIED_IN_STAGE` ships it with `legalMoves`), `needs` (`NEEDS_UNSATISFIED` names what to pass), spawnability (`STAGE_NOT_SPAWNABLE`, plus `list_playbooks`' `spawnableStages` and the `spawnable yes|no` `describe_playbook` renders per stage), `entryStages` (a spawn is gated by `isSpawnable`, not by entry-stage membership), and the top-level description + a `describe_playbook` pointer (the available-playbooks listing sits directly above in the same prompt and carries both — an **order the composed-prompt test pins**). Each omitted fact arrives at point of use and cannot go stale under a live worker, which a spawn-time snapshot can: definitions are not pinned to a run (see Known limitations). Absent on the explicit `none`, when the selected id no longer resolves, or when the `playbooks` convention is off (the section rides that toggle, like the available-playbooks listing). **Freshness:** every input to this section is read **per compose** — the built-in `playbooks/*.json` definitions (through `fragmentCatalog`'s `seedExt: '.json'` catalog, whose seed bodies are never memoised), the user overlay at `<store>/playbooks/*.json`, and the selection itself. An edit to any of them reaches the next conductor spawned, with **no orchestrator restart**, exactly like a `conventions/*.md` edit. The exception is a **plugin** playbook: its body is held on the plugin's manifest, read at manifest load, so an edit reaches the section only after that manifest is re-read — see the freshness bullet under `playbooks` in [plugins.md](plugins.md).

#### Resuming a playbook-tracked worker

**A resume is not a stage entry.** `spawn_instance({resume})` where the resumed sessionId is in the ledger's projection inherits that session's recorded `playbook` + `stage` (`decideResume`, `src/playbooks.ts`) — alongside the project + worktree already recovered from the session record — so the **bare** `spawn_instance({resume:sessionId})` the `SESSION_NOT_LIVE` refusal names is sufficient, and needs neither argument. The worker is coming back to where it already is, so the entered-stage checks do not run: no `isSpawnable` (forced rather than chosen — it would refuse a worker that transitioned into a transition-only stage and then died), no `needs`, no capacity count. **`pin` is the one that splits.** Its **spawn-shape** keys — `createWorktree`, `baseWorktree`, `name`, `model` (`SPAWN_SHAPE_PINS`, `src/playbooks.ts`) — are dropped, because each describes how to *create* a process and a resume's subject already exists; injecting `createWorktree` is what hands a resumed session a fresh worktree, at a cwd that by construction holds none of its history. Every **other** pinned key still applies, filled or `ARG_PIN_CONFLICT`-refused exactly as on a spawn. That half is load-bearing, not tidiness: with no pinned `mode` and none supplied, `_doCreateResolved` falls back to `effectiveResumeMode(null)` = `DEFAULT_RESUME_MODE`, i.e. **`bypassPermissions`** (`src/sessionModes.ts`) — so skipping it would widen an adopted session inside a stage that asked for something narrower. The set enumerates what to **strip**, so a newly pinned key stays enforced by default. The same rule applies to an **adopted** resume (one the ledger holds nothing for, declaring `playbook` + `stage`), so there is one rule rather than two. `patchedArgs` is the caller's **own args object** whenever the policy remainder is empty, which is the common case.

A supplied binding is therefore **checked, not applied** — match-or-refuse, the same rule and the same `PLAYBOOK_MISMATCH` code a non-root spawn uses for an inherited playbook. `playbook` and `stage` are compared **independently** (a matching playbook with a differing stage is still a conflict) and the refusal prints **both** the recorded pair and the supplied one, so one round-trip is enough to retry legally. A `provenance` map alongside a tracked resume is likewise `PLAYBOOK_MISMATCH`: a resume enters no stage, so it satisfies no `needs`.

Commits a **`resume`** ledger event (never a second `spawn` — that would reset `stageHistory` and empty `provenance`; see [architecture.md](architecture.md)). Two cases still refuse: a resume of a session the ledger holds **nothing** for is `PLAYBOOK_UNKNOWN` and must name `playbook` + `stage` like any run root (its reason names that case specifically), and a session whose recorded playbook is **no longer loaded** is `PLAYBOOK_UNKNOWN` for the same definition-drift reason a targeted call is. A recorded *stage* that no longer exists is not checked here (nothing on this path reads it); the next `send_prompt` reports `STAGE_UNKNOWN`.

`provenance` values are sessionIds and get the same **prefix resolution** as a top-level `sessionId` (schema-driven, so any tool declaring `provenance` is covered); an ambiguous one soft-refuses `SESSION_AMBIGUOUS` naming the `provenance.<stage>` entry.

**The policy step in `tools/call`.** One checkpoint in `dispatch()` (`src/mcp/server.ts`), **after** `validateArgs` and after every prefix-resolution pass, **before** `tool.handler`. Refusals use the established soft shape — `{ok:false, code, reason, legalMoves, playbookEnforcement:"enforce"}`, `isError:false`, never thrown — because there is no server→client notification channel, so a conductor's tool list is fetched once and a denied tool cannot be hidden; every refusal therefore carries the way forward. Codes: `PLAYBOOK_UNKNOWN`, `STAGE_UNKNOWN`, `STAGE_NOT_SPAWNABLE`, `TRANSITION_ILLEGAL`, `NEEDS_UNSATISFIED`, `NEEDS_WORKER_GONE`, `ARG_PIN_CONFLICT`, `TOOL_DENIED_IN_STAGE`, `STAGE_AT_CAPACITY`, `PLAYBOOK_MISMATCH`, `FORWARD_DENIED_IN_STAGE`. `STAGE_AT_CAPACITY`'s `reason` names the blocking sessionId and a working recovery (`kill_instance({sessionId})` for a worker that is actually still running, or a `workers:"many"` playbook). Capacity counts **live processes** (`InstanceManager.isSessionLive`, see [architecture.md](architecture.md#playbooks)), not a ledger-side flag, so a slot held by a session the orchestrator no longer knows about (e.g. after a host reboot) reads free on the very next check — it can never wedge a run permanently, and there is no boot-time repair step for it to wait on.

Because a `spawn` ledger event needs the new worker's sessionId — which does not exist until the handler has run — the checkpoint is **check-before / commit-after**: one call decides, a second records. A handler that throws never reaches the commit, and one that soft-refuses is filtered inside it; either way the move did not happen, so the ledger must not claim it did. The commit reads the sessionId off the **result**, not the arguments, and re-checks it there: a `spawn` move whose result names a session the projection **already holds** is appended as a **`resume`** instead (`commitMove`, `src/mcp/playbookGate.ts`), decided **inside** the serialized append chain so two concurrent commits on one sessionId cannot both read "unbound" — the decision layer was handed an id it could not place, and folding a spawn would reset that worker's `stage`, `stageHistory` and `provenance`. A committed `transition` row — a real move or a declared self-loop — carries `forwardSessionId` (the forward source's sessionId, resolved at the transport's prefix chokepoint like every other worker handle) whenever the `send_prompt` call carried `forward`; the key is absent otherwise, and it reaches callers through `playbook_state`'s `history`.

**Read tools.** `list_playbooks` (ids, names, descriptions, entry + spawnable stages, `plugin` naming the owner on a plugin-contributed playbook, plus `errors` for definitions rejected at load — JSON, because `errors` is structured data), `describe_playbook({id})` (the full graph, as **plain text** — see [Rendered read results](#rendered-read-results)), `playbook_state({sessionId?})` (the run graph, legal next moves, and the run's ledger history; for a worker whose playbook is no longer loaded, `playbookMissing: "<id>"` plus a `reason` naming the cause — for a plugin playbook, the owning plugin and where to look to tell the possible causes apart — `list_playbooks` → `errors`, or the plugin's Settings → Plugins row when its manifest is invalid as a whole; a conductor at `enforce` gets the targeted call refused `PLAYBOOK_UNKNOWN` with the same cause instead, since the call names that worker). All three are read-only in the strong sense: on an install with no ledger they answer with empty state and **create no file**. The REST routes ([REST — `/api/playbooks`](#rest--apiplaybooks)) serve the same payload builders as the first two (`playbookSummary` / `playbookDetail`, `src/playbooks.ts`).

`describe_playbook`'s layout is owned by `renderPlaybook` (`src/mcp/readRenderers.ts`). The worked example is the synthetic `GRAPH` in `tests/mcp-text-render.test.mjs`, whose expected rendering is asserted line by line and exercises every layout feature at once — a multi-member `needs.position` join, `tools (none)`, a `"*"` policy entry, edge-label padding, and verbatim indented description prose. Read it there rather than from a pasted sample: a renderer change fails that test, so it cannot drift the way a hand-pasted rendering of a hand-editable built-in silently did.

`playbook_state`'s `nextMoves` is answered by dry-running the same `decide()` that enforces, once per outgoing edge, so what it advertises and what the gate permits cannot diverge. Each move is evaluated as the **bare call**, with no `provenance` supplied, so an edge into a stage declaring `needs` reads `ok:false`/`NEEDS_UNSATISFIED` even when a satisfying worker exists — that is "pass the argument", not "impossible", and the `reason` names what to pass. `playbook_state` declares a `sessionId`, so it is governable like any other targeted tool and a stage may deny it; the no-argument form names no worker, so it is never subject to a stage's policy and remains available.

**Enforcement level.** `playbookEnforcement: "warn" | "enforce"`, per conductor session. The level a new session **starts at** is the persisted `defaultPlaybookEnforcement` (Settings → Conductor conventions, same store and endpoint block as the preferred playbook above), falling back to `DEFAULT_PLAYBOOK_ENFORCEMENT` (`src/playbooks.ts`) — **`enforce`** — when nothing is persisted, so a fresh install refuses illegal moves until someone selects `warn`. `Manager._doCreate` reads it live, so a change lands on the next conductor spawn without a server restart and leaves running sessions alone. `warn` records the refusal, pushes a `system`/`playbook_warn` event to the **calling conductor's** event stream (below), and allows the call; `enforce` returns the refusal to the caller instead. **Neither level is inert** — both decide, patch args and write to the ledger, so every conductor session materialises it. An explicit value at create on `POST /api/instances` **wins over** the persisted default (the restart path carries a session its own recorded level, and inheriting a since-changed default would silently up/downgrade it). Flipped at runtime over the WebSocket (above) — a session-only override that never writes the persisted default — and carried across a graceful restart. A `pending-resume.json` from a build that still had the retired `off` level is normalized on read — to `warn`, always, regardless of the current shipped default — since resurrecting an unenforced session as enforced would be a silent upgrade (`normalizePlaybookEnforcement`). The **runtime authority is the instance field**; the ledger's `enforcement` events are the audit trail, written by the gate watching the manager's `status` stream so whichever surface flips the toggle is recorded without knowing the ledger exists.

**Known limitations.**
- **Definition edits drift under live workers.** Definitions are deliberately not pinned to a run — no snapshot, no hash on the `spawn` event, and a load is never refused for invalidating a live run. A worker whose stage vanished under it gets `STAGE_UNKNOWN`, whose text says the definition changed rather than blaming the call. The same holds when a **plugin** providing the playbook is disabled or removed: the worker's governed calls (under `enforce`) and its resume are refused `PLAYBOOK_UNKNOWN` with a reason naming the plugin and pointing at `list_playbooks` → `errors` to tell a disabled plugin (re-enable restores it) from an unavailable plugin host or an invalid body, and at the plugin's Settings → Plugins row for a manifest invalid as a whole (still enabled, re-enable refused until fixed) (`missingPlaybookCause`, `src/playbooks.ts`); the ledger binding is untouched, so re-enabling restores governance on the same session.
- **A worker spawned illegally under `warn` stays untracked.** The refusal is recorded but the call proceeds, and no binding is written — so flipping to `enforce` mid-run governs new spawns while that worker stays ungoverned (no subject in the projection). A *legal* `warn` spawn is bound normally and becomes governable on the flip.
- **A forward source is checked for permission, never for run membership.** A stage may forbid its worker's output being read out (`"get_recent_messages": "deny"`), and that denial covers `send_prompt({forward})` as well as a direct read. It is not scoped to a run: a conductor may forward from any tracked worker whose stage permits the read, including one in another run or another project. Deliberate — `freeform` declares no `needs`, so each of its workers is its own run root, and a same-run rule would refuse the fan-out-and-synthesise pattern that stage invites, recoverable only by declaring `provenance` at spawn time and never retroactively.

### REST — `/api/playbooks`

Read + validate only, served by `buildPlaybookApi` (`src/playbookApi.ts`, mounted at `/api/playbooks` from `src/routes.ts`). There is **no write or delete route**: an authoring plugin writes the user-overlay file itself — see [plugins.md → Authoring playbooks from a plugin](plugins.md#authoring-playbooks-from-a-plugin). Ledger state is read only through the playbook gate (`tests/playbook-ledger-chokepoint.test.mjs`).

Shape conventions (all three routes):
- An optional key (`description` on a stage or a transition) is **absent** when unauthored — never `null` or `""`.
- The order of `playbooks` is not part of the contract.
- `takenIds.*`, `pinArgs` and `governableTools` are sorted ascending.

**`GET /api/playbooks`** → 200

```json
{
  "playbooks": [{ "id": "relay", "name": "…", "description": "…", "source": "builtin", "editable": false,
                  "entryStages": ["plan"], "spawnableStages": ["plan", "implement"] }],
  "errors": [{ "id": "broken", "message": "…" }],
  "governableTools": [{ "name": "send_prompt", "pinArgs": ["model", "text"] }],
  "takenIds": { "builtin": ["…"], "user": ["…"], "reserved": ["custom"] }
}
```

| Field | Meaning |
|---|---|
| `source` | `"builtin"` \| `"user"` \| `"plugin:<plugin-id>"` (`playbookSource`) — of the definition that **won**: a valid overlay file with a built-in's id overrides it and reports `"user"`; an invalid one leaves the built-in loaded (`"builtin"`) with its reasons in `errors` under that id. |
| `editable` | `true` iff `source === "user"`. |
| `entryStages` / `spawnableStages` | As `list_playbooks`; spawnable = `isSpawnable` (a `"*"` entry confers nothing). |
| `errors` | Exactly `list_playbooks`' `errors`. Ids: a bare slug, `<plugin-id>/<slug>`, or `plugins` when the plugin host is unavailable. |
| `governableTools` | One entry per `governableToolNames` (`governableToolCatalog`). `pinArgs` = the tool's `inputSchema` properties minus `PIN_FORBIDDEN_KEYS` — exactly the argument names the validator accepts inside `{pin:{…}}`. A pin on `"*"` is always refused. |
| `takenIds.builtin` | `SEED_PLAYBOOK_IDS`. Writing one **overrides** the shipped definition — legal; warn, don't block. |
| `takenIds.user` | Every `<id>.json` in the overlay (`userPlaybookIds`), **loaded or not** — an invalid file is absent from `playbooks` but its id is taken. |
| `takenIds.reserved` | `RESERVED_OVERLAY_ID` — the loader **silently skips** that file (it is the catalog's store file). Refuse these ids. |

Plugin ids are never in `takenIds`: they contain `/`, which an overlay id cannot. The editor catalog rides on the list rather than a route of its own because any literal `/api/playbooks/<word>` path would collide with a playbook of that id.

**`GET /api/playbooks/:id`** → 200. Plugin ids resolve both raw (`/api/playbooks/acme/release`) and encoded (`/api/playbooks/acme%2Frelease`).

```json
{
  "id": "acme/release", "name": "…", "description": "…", "source": "plugin:acme", "editable": false,
  "entryStages": ["plan"],
  "stages": { "plan": { "needs": [{ "stage": "research", "position": ["research"], "liveness": "live" }],
                        "workers": "one", "tools": { "spawn_instance": { "pin": { "model": "acme/captain" } } },
                        "spawnable": true, "description": "…" } },
  "transitions": [{ "from": "plan", "to": "ship", "via": "send_prompt", "description": "…" }],
  "liveWorkers": 0
}
```

- The graph is **post-validation** (`playbookDetail`, the payload `describe_playbook` renders): defaults applied (`needs[].position` → `[stage]`, `liveness` → `"live"`, `workers` → `"one"`); `tools` holds only the declared entries.
- `via` = the declared `on`, else `"send_prompt"`. Lossless: the validator refuses `on: "send_prompt"`, so `via: "send_prompt"` always means no `on`.
- `spawnable` = `isSpawnable(stage)`.
- `liveWorkers` = the length of the gate's `readLiveWorkers(id)` — workers bound to this id in its projection for which `isLive` holds — for warning about [definition drift](#playbooks) before an edit. `null` = unknown: no gate wired, or the projection read failed (logged with `console.warn`, still 200 — the same degrade as `GET /api/instances`' bindings).
- **404** `{error: "no playbook '<id>'", code: "PLAYBOOK_UNKNOWN"}` — an unknown id, an unknown plugin slug, or an overlay file that failed validation (its reasons are in the list's `errors`).

**`POST /api/playbooks/validate`** → 200. The body is the draft definition itself — the JSON that would be written to `<id>.json`. Never writes.

```json
{ "ok": false, "errors": [
  { "message": "stage 'plan': …", "stage": "plan", "transition": null },
  { "message": "transition plan->ship: …", "stage": null, "transition": { "from": "plan", "to": "ship" } },
  { "message": "name is required and must be a non-empty string", "stage": null, "transition": null }
] }
```

- Valid → exactly `{ok: true}`.
- `message` = `validatePlaybook(draft, draft.id, <tool index>)`'s errors, in emission order — the validator is the only rule set. The expected id is the draft's **own** `id`, so the filename-match check never fires; a missing or non-string id is reported once, as `invalid id '…'`.
- `stage` / `transition` come from `locateValidationError` (`src/playbooks.ts`), matched against the draft's **actual** stage names and edges (so `plan` never captures `plan-b`'s messages):
  - `stage` — a message starting `stage '<name>'` followed by `:` or a space. When several names match (`a` and `a' b` both head `stage 'a' b': …`), the **longest** wins.
  - `transition` — a message starting `transition <from>-><to>:`, or exactly `duplicate transition <from>-><to>`. When that text is printed by more than one distinct declared edge (`a`→`->b` and `a->`→`b`), `transition` is `null`.
  - both `null` — a playbook-level message, or a transition message not attributed to a declared edge (e.g. `transition from names unknown stage …`).
- No per-field path: the message text names the field.
- A request whose `Content-Type` is not `application/json` → **400** `{error, code: "BODY_NOT_JSON"}`, never validated.
- A non-object JSON body (e.g. `[]`) → `ok:false` with the validator's `must be a JSON object` error. An `application/json` body that does not parse → 400 from `express.json`.
- No collision check — apply `takenIds` client-side.

## The FUSE-union daemon's policy event log

A **file format with real readers**, which is why it is here and not only in [architecture.md](architecture.md): the real gate's `R4` filters it, `runTeardown` harvests it, and an operator (or a Claude session) derives the pin list from it. `docs/architecture.md` → "The FUSE-union chroot" carries the *why*; this is the contract.

**Two artifacts, one row shape plus provenance.**

| | path | row |
|---|---|---|
| per session | `<rundir>/events.log`, written by the daemon (`CC_UNION_EVENTS`, `policy_event` in `policy.h`) | `<kind>\t<op>\t<path>\t<reason>\t<pid>\t<tgid>\t<comm>\t<cmdline>` |
| store-wide | `orchStoreRoot()/systems/fuse/events.log` (`fuseEventStore()`), appended by `runTeardown` immediately before the run directory is reclaimed | `<iso8601>\t<instanceId>\t<kind>\t<op>\t<path>\t<pid>\t<tgid>\t<comm>\t<cmdline>\t<suggested list>\t<suggested entry>` |

**A `#` HEADER LINE IS WRITTEN ONCE**, when the daemon opens the session log (`main()`), naming the columns and the sampling caveat. **It contains tabs**, so a parser that only tests for N non-empty fields will read it as a row: `parsePolicyEvents` (`session.ts`) and the real gate's `eventsOf` both skip lines beginning with `#`.

- **Deduped on `(path, reason, tgid)`**, never on the op and never on the kind, in the daemon and in the harvest — the two keys are the same by design, or the artifacts stop being comparable. **The tgid is load-bearing**: without it the first caller to reach a path wins the row and every later one is silently dropped, so the identity columns would answer *who asked* with *whoever happened to be first*. The kind is left out because it is a **function of the reason** (set-compared against both C sources in both directions by `tests/fuse-union-policy.test.mjs`), so on any emission the daemon can produce the two keys partition identically and that choice is **unobservable**. **What that costs, named:** a defect emitting one reason under *both* kinds would collapse to a single row rather than showing two — acceptable only because the one-kind-per-reason property is checked at the **call sites**, where it is decidable, and never inferred from a row count here.
- **The last two store columns are for `deny`/`unpinned-fail-closed` rows only** and are empty otherwise: a pin does not fix an `unmarked-host-served` row, whose path already came from the host. `suggestPin` (`src/systems/fuse/tierTable.ts`) is the mapping.
- **PATHS ONLY, never content.** A credential path may appear in either; a credential never does.
- **Append-only, never rotated.** The store-wide file is the only record that outlives a session.
- **Unstable by design**, like the rest of cc's surface: `enum ev_kind` and the reason set change with their callers.

### The identity columns

`pid` is the **calling thread** (`fuse_get_context()->pid`, measured to be a TID); `tgid` is its thread group — the id the mark, the resolution cache and the dedupe key are all on, and the id `CC_FUSE_TRACE` rows can be joined on. Both are logged because neither substitutes for the other. `comm` and `cmdline` are read from the **tgid**.

**IDENTITY IS SAMPLED AT POLICY TIME**, after the decision and after the dedupe — so the two /proc reads it costs, `comm` and `cmdline`, are paid once per **distinct row** rather than once per op. The `tgid` read is **not**: the dedupe key needs it, so it happens on every call — the same read `mark_of` and `policy_project_route` already make. Identity can never change an answer. `exec(2)` replaces `comm`, `cmdline` and `exe` while leaving pid, tgid and start time untouched, so **no validation can make the sample authoritative for the op that triggered it**: a row may name what the process *became*. The header line says so in the file.

**ESCAPING — `policy_escape` in `policy.h`, applied to `path`, `comm` and `cmdline`.** `op` and `reason` are C string literals and need none. A `/proc/<pid>/cmdline` is NUL-separated and a `bash -c` argv carries the whole script, newlines included, so an unescaped row is unparsable — which is what the escaping exists to prevent.

| input byte | output |
|---|---|
| `\` | `\\` — **handled first**, or the round trip collapses |
| `\t` `\n` `\r` | `\t` `\n` `\r` (two chars each) |
| `0x00` | `\0` — **and this is the argv separator** |
| other `< 0x20`, `0x7f` | `\xHH`, lowercase hex |
| `0x80`–`0xff` | verbatim (a UTF-8 path stays readable and still cannot break the parse) |
| everything else | verbatim |

`decodeEventField` (`src/systems/fuse/session.ts`) is the **only** inverse; `parsePolicyEvents` splits a decoded `cmdline` on `U+0000` into `argv`. The two implementations are cross-checked against real daemon output by `tests/fuse-union-policy.test.mjs`'s `argv-vectors` round trip.

**RECORDED ABSENCES.** The escaper never emits `\` followed by `!`, so `\!` is an unforgeable sentinel namespace. A missing identity is one of these, never a value:

| sentinel | meaning |
|---|---|
| `\!gone` | the `/proc` entry was not there — the process exited between the op and the sample |
| `\!unreadable` | it was there and could not be read (`EACCES`, `EPERM`, a racing reap) |
| `\!empty` | the read succeeded and returned zero bytes (a kernel thread, or a zombie) |
| `\!truncated` | a **suffix** on an otherwise-valid encoded field that hit the cap |

**`cmdline` IS CAPPED BY `POLICY_CMDLINE_MAX` (`policy.h`, 4096) — the BUFFER, so the field carries at most 4095 bytes.** A cmdline can reach `ARG_MAX`; a log row cannot. The reader takes `n - 1` so the result is also a C string; a read that fills the buffer gets the `\!truncated` suffix and keeps the bytes it did read, so a reader gets *argv-so-far, truncated* rather than a short argv it would read as complete. Round-trip is exact **up to 4095 bytes**, and truncation is never silent.

**A CMDLINE OF EXACTLY 4095 BYTES IS MARKED TRUNCATED EVEN WHEN IT IS COMPLETE**, and there is no way to tell the two apart: "the read filled the buffer" is the only signal `read(2)` gives, and the alternative — a 4096-byte read to disambiguate — would only move the same ambiguity one byte along. The marker therefore means *at least this much, possibly more*, never *exactly this much was lost*.

**READERS MUST READ THE FILE AS BYTES.** `0x80-0xff` passes through verbatim, so the log is not necessarily valid UTF-8 — a latin-1 filename or a binary argument puts a lone high byte in it, and a `utf8` read replaces it with U+FFFD before any column is formed. `parsePolicyEvents` documents `latin1` as its input contract, and `harvestEvents`, `Instance._awaitFuseMount` and the real gate all read that way; the store is appended as a `Buffer` for the same reason.

**EXACTLY TWO KINDS, and `R4`'s whole filter is `kind === 'deny'`** — a third would silently fall out of it and stop being checked at all. `enum ev_kind { EV_DENY = 0, EV_SERVED }`, rendered by `ev_kind_name`:

- `deny` — the op was **refused**; the caller has a negative errno.
- `served` — the op **succeeded**, but not the way the tier table said.

**EVERY REASON, WITH ITS KIND.** Derived from every `policy_event(` call site in `union.c` and `policy.h` and set-compared **in both directions** by `tests/fuse-union-policy.test.mjs`, so a new reason with no classification is a test failure rather than an unclassified row.

| reason | kind | emitted where, and what the caller got |
|---|---|---|
| `unpinned-fail-closed` | `deny` | `route()`'s fall-through, `-ENOENT`. **The MARKED CLI's alone** — an unmarked caller at `fail` is substituted to `host` before the switch |
| `unmarked-project-denied` | `deny` | `policy_project_route`'s mark check, `-ENOENT`. **UNREACHABLE, AND THE ROW IS KEPT ANYWAY.** An unmarked caller resolves in `VIEW_HOST`, where `tier_of` skips every `project` pin — so no unmarked resolution can produce `T_PROJECT` and `route()` cannot dispatch one to that function. The check is retained as defence in depth on the only path that sends a control frame, and this row is what an operator would see if a later edit ever reopened the route. The live mechanism is the view, where the invariant is structural |
| `control-unavailable` | `deny` | cc could not be reached, `-EIO` |
| `remote-absent` | `deny` | the remote does not have it, `-ENOENT` |
| `control-refused` | `deny` | cc would not carry it, `-EACCES` |
| `not-reconcilable` | `deny` | outside `DIRTY`'s domain (`mknod`, `link`, `chown`, a directory rename), `-EOPNOTSUPP` |
| `xdev-rename` | `deny` | the two routed ends are on different backing stores, `-EXDEV` |
| `dirty-push-refused` | `deny` | the reconcile could not land; the op returns cc's errno |
| `dirty-remove-refused` | `deny` | as above, for a removal |
| `self-recursion` | `served` | the daemon's own thread group at a project path — served from `policy_host_fd`, **returns 0**. A liveness precondition, not a routing policy |
| `pinned-children-truncated` | `served` | a `readdir` past `MAX_PINNED_CHILDREN`; the listing **succeeds** with a name dropped |
| `unmarked-host-served` | `served` | an unmarked caller was routed to the host at an unpinned path. Fires on the **substitution**, whatever the host read then does — the host's own ENOENT is not a policy event and `route()` cannot know it. ~20 per shell startup. **It is also the row a `project`- or `synth`-tier path writes**, because both re-resolve in `VIEW_HOST` and land on this same rule rather than on a substitution of their own |

**TWO REASONS ARE RETIRED, and the deletions are the point rather than an omission.** `unmarked-project-host-served` existed because the `project` tier had a substitution rule of its own, gated on a host-existence probe; `cwd-traversal-served` recorded a grant by the cwd-chain exemption. Both mechanisms are gone — a project-tier path re-resolves in `VIEW_HOST` and writes `unmarked-host-served`, and a cwd component is answered by the orchestrator's own directory (same row) or by the overlay node (no row, because nothing was substituted). The set is derived from every `policy_event(` call site and compared **both ways** against `EVENT_KINDS` in `tests/fuse-union-policy.test.mjs`, so re-adding either reason means re-adding a mechanism.

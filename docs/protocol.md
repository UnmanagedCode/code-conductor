## Subprocess protocol
```bash
claude -p \
  --input-format=stream-json --output-format=stream-json \
  --verbose --include-partial-messages --include-hook-events \
  --allow-dangerously-skip-permissions \
  --permission-prompt-tool stdio \
  --permission-mode <plan|bypassPermissions> --effort <effort> --thinking <thinking> \
  --settings '{"hooks":{"PreToolUse":[…]}}' \
  --mcp-config '{"mcpServers":{"code-conductor":{"type":"http","url":"http://127.0.0.1:<port>/mcp"}}}' \
  [--plugin-dir <root> …] \
  [--model <name>] \
  --session-id <fresh-uuid> | --resume <existing-uuid>
```

The `--mcp-config` line is omitted when `ORCH_DISABLE_MCP_AUTOREGISTER=1` (no MCP toolbelt auto-registered into the spawned process).

`--plugin-dir` is **repeatable, one per enabled cc plugin** whose manifest declares `claudePlugin` (session-local Claude Code plugin roots — skills et al.). `<root>` is the resolved+validated abs dir (a dir directly containing `.claude-plugin/plugin.json`); a plugin whose target lacks that file is warned + dropped. Absent when no enabled plugin ships one. See [plugins.md](plugins.md#manifest--conductorpluginjson-at-the-plugin-project-root) → `claudePlugin`.

**Substitution backends (the launch template).** Spawning is backend-agnostic: `Instance.spawn` computes only the command + argv prefix from the session's **backend record**, then appends the **same** claude args (including `--model <model>`) for every backend. A backend's `template` is the command that replaces `claude`, with `{model}` substituted in (blank template ⇒ run `claude` directly); `resolveBackendLaunch` in `src/claudeLauncher.ts` is the single substitution point, and the backend's configured `env` pairs ride along with it. Backends are user-managed data — see [models.md](models.md). For the built-in `ollama` row the template is `ollama launch claude --model {model} --yes --`, so the full argv is `ollama launch claude --model <tag> --yes -- <all the args above, including --model <tag>>`. `ollama launch` sets the Anthropic-compatible endpoint + auth internally and re-injects `--model` into the child; the forwarded `--model <tag>` is a matching **no-op duplicate** (verified harmless). `--yes` bypasses the interactive agent-capability confirmation (which would fail a piped spawn). Everything after `--` (stream-json stdin/stdout, `--mcp-config`, `--settings` hook, `--session-id`) is forwarded unchanged — the worker registers, streams, and drives MCP + hooks exactly like a bare-`claude` spawn. Any non-blank template refuses to launch without a resolved model (`422 BACKEND_MODEL_MISSING` at create time, and the same refusal inside `resolveBackendLaunch`) — **unconditional on the template shape**, so a template that never names `{model}` is no exception: the model still rides in the forwarded claude args and drives the context-window env below. A backend id that isn't in the registry is likewise refused `422 BACKEND_GONE` rather than falling back to `claude` (see [models.md](models.md#missing-backends-are-refused-never-downgraded)). There is **no** reachability preflight: a bad backend or model fails at spawn and surfaces as `launch_failed`. For a spawn on any **non-`claude`** backend, both `CLAUDE_CODE_AUTO_COMPACT_WINDOW` and `CLAUDE_CODE_MAX_CONTEXT_TOKENS` are set on the child env to the session's resolved `contextWindowTokens` (raw tokens; resolved once at create by `resolveContextWindowTokens` in `src/appSettings.ts`, which matches the custom-model row or curated catalog on the **exact** model id); unset when the window is unknown. These two are **cc-managed** — implicit to every substitution backend, never applied to plain `claude`, never exposed in the Backends UI, and applied *after* the backend's own `env` so they win over a same-named pair. Both are needed: the CLI clamps the effective compact trigger to `Math.min(modelWindow, AUTO_COMPACT_WINDOW)`, and its internal per-model table defaults any unrecognized model (every non-Claude id) to a 200k assumed window, which silently caps `AUTO_COMPACT_WINDOW` back down — `MAX_CONTEXT_TOKENS` overrides that assumed window directly for non-Claude models, so the CLI actually auto-compacts at the real limit instead of ~200k. The `.conduct` orchestrator's opt-in compact-window override still wins when both apply (it only overrides `AUTO_COMPACT_WINDOW`, which remains the binding minimum).

**Interactive tools under CLI ≥ 2.1.x — `--permission-prompt-tool stdio`.** Headless stream-json (`-p`) sessions are non-interactive (`isNonInteractiveSession=true`); the CLI serves a coordinator/agent tool profile and **strips the interactive plan/question tools** unless the client presents as a permission consumer. Passing **`--permission-prompt-tool stdio`** does exactly that: the CLI routes those tools' permission prompts to us as `can_use_tool` control_requests over the stream-json channel (verified: it re-adds the three tools to `system/init` `tools[]` and they become callable). It is **additive** to `--allow-dangerously-skip-permissions` (normal tools stay auto-allowed and never reach `can_use_tool`; only the interactive tools do). Kill-switch: `ORCH_DISABLE_STDIO_PERMISSIONS=1` reverts to the fail-closed behavior (tools stripped).

The orchestrator answers `can_use_tool` in `Instance._handleStdoutLine`: for `ExitPlanMode`/`EnterPlanMode`/`AskUserQuestion` it replies `control_response {behavior:"deny", message:<AWAITING_INPUT_MESSAGE>}`; any other tool (rare) is allowed. The deny releases the tool call — the `plan_request`/`user_question` card is emitted from the tool-use, so the drive-forward path needs nothing more from it — but it **does not reliably end the turn**: the model gets an `is_error` tool_result and wraps up only if the CLI has nothing queued behind it. A message already sitting in the CLI's stdin (typically a wake callback from a finished worker) is injected right after the deny and the **same turn keeps running**. So the reply is still fire-and-forget rather than held open — holding it for an *in-turn* answer would suppress `turn_end` entirely and deadlock a conductor's `subscribe_to_idle` — but `turn_end` may be arbitrarily far off, and every answer path (`approve_plan`/`reject_plan`/`answer_question` and the UI cards alike) therefore sends **unconditionally**, picking up `MID_TURN_NOTE` when it lands mid-turn. `approve_plan`/`reject_plan` are unchanged (setMode + approval prompt); `answer_question` delivers the worker a structured AskUserQuestion answer that is **byte-identical** to a UI question-card submit — both call the one DOM-free formatter in `public/userQuestionAnswers.js` (re-exported by `public/blocks.js`, imported server-side by `src/mcp/handlers.ts`). The flag alone exposes and makes the tools callable — **no `initialize`/`supportedDialogKinds` handshake is sent** (probe-verified unnecessary), and the CLI never issues `request_user_dialog` in this configuration (permission flows via `can_use_tool`).

`--allow-dangerously-skip-permissions` is **always** passed at spawn — even for `plan`-mode instances — because without it the CLI rejects any later runtime `set_permission_mode bypassPermissions` (i.e. the plan-approve flow). The flag only *permits* the switch; it doesn't activate bypass on its own.

One `PreToolUse` hook via inline `--settings` JSON (the old static `command` deny on **AskUserQuestion|ExitPlanMode** is **removed** — those tools are now gated at the `can_use_tool` layer, see above):
1. **Edit|Write|NotebookEdit|Bash** — `http` hook → `POST /api/instances/<id>/hook-callback`, a CLI-side hook timeout (`HOOK_HTTP_TIMEOUT_S`); the orchestrator holds the ask-mode response open for a window deliberately under it (`HOOK_PENDING_TIMEOUT_MS`). `ask` is orchestrator-tracked only and maps to `bypassPermissions` at the CLI level; the hook callback inspects orchestrator-side mode to gate.

**Inbound** (orchestrator → CLI stdin):

| Type | Payload | Notes |
|---|---|---|
| `user` | text or `[{type:"text", text:"..."}, …]` blocks; attachments use `` Attached file: `<rel-path>` `` | A `user` written while a turn is running is **delivered mid-turn and interleaved into the live turn** (steering) — not queued until `turn_end`; the CLI persists it as a `type:"attachment"` `queued_command` line (array `prompt`), not a `type:"user"` line. |
| `control_request` | `set_permission_mode` / `set_model` / `interrupt` | |
| `control_response` | our reply to the CLI's `can_use_tool` | |

**Two-tier interrupt.** SOFT (default) injects a hidden steering `user` message suffixed with `[[cc:soft-interrupt]]` (`SOFT_INTERRUPT_MARKER`) telling the model to stop all work and end its turn after one brief acknowledgement line — graceful wind-down, partial work preserved (a fully silent reply would make the CLI inject a "no visible output" follow-up that re-engages the model). At send time, `Instance.interrupt()` also emits a live `system`/`soft_interrupted` event with `data.text` set to the steer text — not a `user_echo`, so it never shifts `_userEchoCount`/the rewind-fork index. The marker itself is filtered everywhere it could surface (`parser._handleUser`, `transcript.replayPersistedLine`, `transcript.isPureUserPromptLine`) so on JSONL replay it never renders a user bubble, produces the same bare `soft_interrupted` annotation (no `data.text`) instead, and never shifts the rewind/fork index. FORCED (`force:true`) is the unchanged hard `control_request` `subtype:interrupt` abort (discards partial work). Both gated by `if (status !== 'turn') return`.

**Managed `/clear` (session renewal).** `Instance.clearContext()` writes a `type:'user'` message whose sole content is the text `/clear` on the same stdin path a normal prompt uses (via `_sendRaw`, but bypassing `prompt()`'s user_echo + overage-queue intercept — it is a server-internal control send). The CLI rotates its sessionId to a fresh UUID **in place** — same OS process/pid, old `<sid>.jsonl` preserved, a new `<newId>.jsonl` created — and emits a `system/init` carrying the new `session_id` (which `Instance`'s system/init handler folds into `this.sessionId`) plus a `result` (turn_end). On rotation the controller carries the caller's durable sessionId-keyed markers (`temp`/`conducted`/title) onto the new id and **archives** the abandoned old id (via `Instance.carryMarkersAcrossRenewal` — see architecture.md), so the preserved old `<sid>.jsonl` surfaces in the archived section rather than as a stale live row. Driven by `SessionRenewController` off the `renew_session` MCP tool — see [MCP tool protocol](#mcp-tool-protocol) and [architecture.md](architecture.md).

**Post-hard-abort drain window.** The CLI's stdin queue is not cleared by a hard abort. Any `user` message written before the abort (the soft-interrupt steer, or prompts sent mid-turn) remains queued; after the abort the CLI dequeues them and starts a spurious new turn for each. After every hard abort the orchestrator opens a drain window (`POST_ABORT_DRAIN_WINDOW_MS`, default 3 s) and watches for `system/init` events on the event channel (`Instance._openDrainWindow`). The `system/init` event arrives ~39 ms after the abort and ~3.7 s before any API round-trip, so the drain fires an immediate `control_request subtype:interrupt` to sever the spurious turn at zero token cost. Each drain resets the window deadline (sliding window). Calling `prompt()` closes the window so intentional follow-up prompts proceed normally. The drain emits a `system/drain_abort` event (kind `'system'`, subtype `'drain_abort'`, data `{count}`) visible in the conversation as "⏹ Drained queued turn after interrupt".

| Type | Payload / key fields | Notes |
|---|---|---|
| `system` | `subtype:"init"` bundled with the first turn's response (not at startup): `session_id`, `model`, `tools`, `permissionMode` | other subtypes carry their own data |
| `stream_event` | live SSE deltas | primary feed |
| `assistant` | reconciled message content | one multi-block envelope per message on older CLIs; the async-worker CLI finalizes **each content block as its own single-block envelope** (all sharing `message.id`) and persists that one-block-per-line shape to the session jsonl |
| `user` | `tool_result` blocks | |
| `result` | turn-end: `duration_ms`, `usage`, `total_cost_usd`, `stop_reason`, `is_error` | |
| `hook_event` | | |
| `control_response` | | |
| `control_request` | `can_use_tool` — the CLI asking permission for an interactive tool | we `deny` the three gated tools (see above) |

Notes on `assistant` envelope handling that don't table cleanly: `buildMessageFromRing` merges all envelopes of a `msgId` (the UI ignores outer-turn envelopes either way); disk replay threads a per-file `blockCursor` so a fragmented message's blocks get distinct `blockIdx` values matching the live stream indices. Tools dispatch per-block, so a `tool_result` `user` line can land *between* two envelopes of the same `msgId`. Sub-agent (Task/Agent) turns arrive as finals-only `assistant`/`user` envelopes tagged `parent_tool_use_id` — their partial `stream_event` frames are never emitted (every CLI `stream_event` hardcodes `parent_tool_use_id:null`; the forwarding knob `forwardSubagentText` is SDK-only, no CLI flag).

**Server → client:**
| `t` | Fields |
|---|---|
| `snapshot` | `id`, `status`, `mode`, `sessionId`, `project`, `autoApprovePlan`, `interrupting`, `events[]` (ring **tail** only — target ≤ `ORCH_SNAPSHOT_TAIL` (default in `src/instances.ts`); the window start is snapped to a **quiescent point** — no open text/thinking/tool block, every `tool_use` resolved by its `tool_result` — so the tail holds only whole blocks and complete tool round-trips; quiescent points are dense, so the snap normally moves a few events (worst case, one giant non-quiescent span, is the whole ring); sub-agent group integrity additionally pulls an in-tail child's Task head — and thus the whole group — into the tail, or, for a child with no head at or before it in the ring, pushes the tail start past that child), `tailStartSeq` (`_seq` of first tail event; `>0` ⇒ older history exists — page it via `GET /api/instances/:id/events?before=<seq>`), `trimmedBefore` (first `_seq` still in the in-memory ring), `tasksAtTailStart` (the in-flight task batch reconstructed as of `tailStartSeq`, so the client task panel shows a batch whose `TaskCreate` fell below the tail — the client seeds its `TaskTracker` with it before replaying the tail; `[]` when no batch is open; recovered from the retained ring, or — when the create was evicted entirely below the ring — from the jsonl archive), `lastContextUsage` (the last observed `message_start.usage` object, or `null` before the first one — the client seeds its `UsageTracker` with it **before** replaying the tail, so an in-tail `message_start` still wins. Needed because only `message_start` feeds the ctx readout and the quiescent snap can leave every one of them below the window: a turn whose final text block outruns the tail has no quiescent cut except past the whole block, so the tail collapses to a few events and a re-subscribing client would rebuild an empty tracker (`ctx —`). Held as O(1) server state, last-value-wins; deliberately **survives `turn_end`** — between turns is exactly when a reload would otherwise lose the readout. Its only reset is `_wipeForResume` (rewind/respawn), so a `reset_snapshot` omits it and a rewound session correctly starts blank; a fork or a resume-after-restart needs no reset because each builds a new Instance that starts it `null` (and a fork leaves the parent's value alone — that session continues). In all three cases the value is then **re-seeded from the replayed jsonl** — `loadHistory` emits the replay-path `message_start` described below, so a resumed/respawned/rewound session is populated before its first live turn instead of reading `ctx —`. A **field**, not an appended event like `thinking_tokens` below — the snapshot appends no synthetic `message_start` to `events[]`, and the replay-path one is never retained, so `events[]` holds only genuine ones), `droppedText?` (present **once** on a fork's first snapshot — server consumes it, so a later re-subscribe omits it — ⇒ client prefills the composer). When a thinking block is still streaming, a trailing **seq-less** `system/thinking_tokens` (`data:{estimated_tokens}`) is appended to `events[]` so a client joining mid-thinking shows the current count immediately (the coalesced ring slot already carries the partial thinking text); absent once the block closes — a closed redacted block instead carries its count on `thinking_redacted.estimatedTokens` (see the `thinking_tokens` entry below) |
| `reset_snapshot` | Same shape minus the tail metadata (`events: []`); sent after rewind so subscribers clear DOM first. Carries `droppedText` ⇒ the client prefills the composer with the dropped prompt (same inline mechanism as `snapshot`'s fork prefill) |
| `event` | `id`, `ev` (monotonic `_seq` for idempotent merge) |
| `status` | `id`, `status` (`spawning|idle|turn|exited|crashed`), `sessionId`, `mode`, `autoApprovePlan`, `interrupting` (transient — `true` while a soft interrupt winds a turn down; auto-clears on exit from `turn`). Does **not** carry `displayStatus`/`activeAgentTasks` (see below) — those ride the accompanying `instances` broadcast + REST refetch instead |
| `ack` | `reqId`, `ok`, `error?` |

**UI event kinds (`ev.kind`)** — each carries `parentToolUseId` (or `null`); non-null routes into a nested sub-Conversation.

- `message_start` — one per agent-loop LLM call. **Live shape** `{msgId, usage, model}`; `usage` is that single call's prompt size (`input_tokens + cache_read_input_tokens + cache_creation_input_tokens`) and is the **only** feed for the ctx readout (`turn_end.usage` is a per-turn SUM across every call in the turn — using it is the `ctx 743%` bug; see `public/usage.js`). **Replay shape** `{msgId, usage, replayed: true}`, emitted once by `loadHistory` from the newest non-`<synthetic>` assistant line's `message.usage` so a resumed session's ctx chip is populated before its first live turn (the jsonl carries no `message_start`; it also carries no `type:"result"` line, so the summed value is structurally unreachable from replay). The replayed one is **seq-less and never retained** — `EventLog.push` declines it, so it reaches the live feed only and never appears in a snapshot `events[]`. That keeps it off the ring head (where it could fake a `history_gap` at the archive seam) and out of `ring.nextSeq` (which `idleSubscriptions.ts` arms on). `model` is deliberately **omitted** on the replay shape so `UsageTracker` keeps falling back to the instance's tagged model for the window denominator — the jsonl reports the model bare (`glm-5.2`, not `glm-5.2:cloud`). `conversation.apply` has no `message_start` case in either shape.
- `text_delta` / `text_end` — streaming text deltas.
- `thinking_start` / `thinking_delta` / `thinking_end` / `thinking_redacted` — thinking-block lifecycle; `redacted` renders as a non-expandable `thinking (redacted)` line. `thinking_redacted` carries optional `estimatedTokens` (number) — the final `thinking_tokens` estimate, stamped at emit by `Instance._emitUi`; present only when counter frames ran during the block, and renders as `thinking (redacted, ~N tokens)`.
- `tool_use_start` / `tool_input_delta` / `tool_use` — tool-call lifecycle.
- `tool_result` — tool-result block.
- `user_echo` — outer user-prompt echo. Carries `userIndex` (absolute 0-based ordinal among pure user-prompt jsonl lines; the rewind/fork anchor, immune to ring trimming); optionally `skillLoad: {skill}` (see Skill-load correlation below).
- `system` — subtypes incl. `init`, `history_replayed`, plus `thinking_tokens`, `cache_miss`, `auto_resume`, `auto_resume_skipped`, `launch_failed` (sub-mechanisms below).
- `hook` — hook lifecycle.
- `turn_end` — turn boundary; carries timing + cache-miss fields (below).
- `assistant_message` — reconciled assistant message.
- `control_response` — the CLI's ACK to a conductor `control_request` (`set_permission_mode` / `set_model` / `interrupt`), resolved against the pending-request map; hidden from UI.
- `user_question` — `toolUseId`, `questions[]`.
- `plan_request` — `toolUseId`, `plan`, `planPath`, optional `autoApproved`.
- `permission_request` — `toolUseId`, `toolName`, `toolInput`.
- `permission_resolved` — `toolUseId`, `allow`.
- `overage_message_queued` — `data:{text, attachmentCount, ts, queuedCount}`; rendered as a muted ghost bubble; **no** `user_echo`/turn is sent.
- `raw` — passthrough.

**`system` sub-mechanisms:**

- `thinking_tokens` — `data:{estimated_tokens, estimated_tokens_delta}`, a live-only last-value-wins counter driving the thinking-block summary, emitted by the Claude CLI as a per-token progress estimate (one per `thinking_delta` token). Observed on `claude-opus-4-8`, `claude-sonnet-5`, `claude-fable-5` (all with redacted thinking — no content deltas) and `claude-haiku-4-5` (alongside **plaintext** deltas), so it is a progress signal, **not** a redaction marker; `claude-sonnet-4-6` and `claude-opus-4-7` were observed emitting none. Whether workers on a non-Claude backend emit it is unverified (no capture on disk). Both streams flood live per-token, but the ring keeps `thinking_tokens` out entirely and coalesces `thinking_delta` to one slot per block, so folded/counter frames arrive **seq-less** on the live feed (the client renders seq-less events unconditionally). Persistence of the count across a re-subscribe depends on the block shape:
  - **Open block** — latest count held as O(1) server state (`inst.liveThinkingTokens`), re-attached to a fresh subscriber's snapshot (see the `snapshot` row above).
  - **Closed block with text** — nothing to carry; the coalesced `thinking_delta` replays and the summary finalizes to `thinking (N chars)`.
  - **Closed redacted block** — no text replays, so the final estimate is stamped onto the retained `thinking_redacted` slot as `estimatedTokens`.
  - **Known limitation** — ring-resident only. Paths that rebuild from jsonl (resume, respawn, rewind, server-restart manifest restore, paging above `trimmedBefore`) show the bare `thinking (redacted)`: the CLI persists no counter frames to its session jsonl.
- `auto_resume` — `data:{count}`; marks the overage resume firing ("Window reset — delivered N queued").
- `auto_resume_skipped` — `data:{reason}`; fires ONLY for the genuine "session no longer running" case — a missing/past `resetsAt` no longer dead-ends; it schedules a usage recheck instead (see the usage-verified fire in architecture.md).
- `cache_miss` — `data:{cacheRead, cacheCreation}`, plus `prevPrefix` + `evicted` on the cross-turn path; an informational once-per-turn notice fired on a detected cache miss (rendered as a `SystemBlock`, no action). Detection is **cross-turn**: a miss when this turn's first-request `cache_read` (`read_N`) is below the previous turn's last-request prefix `P` (`cache_read + cache_creation`), i.e. `read_N < P − tolerance` (tolerance defined in the cache-miss detector, `src/instances.ts`) — catches full AND partial evictions. Turn 1 (no prior `P`) and the turn after a compaction (`system`/`compacting`), model switch (`_trackModel`), or rewind/respawn (`_wipeForResume`) — each sets `_prefixBaselineInvalid`, consumed next turn — fall back to the stateless `creation > read` rule (still flags cold start / expiry / resume / cold rewind). Not flagged: warm continuations (read == `P`) or content-addressed hits. A mid-turn eviction (past the first request) is not caught (first-request-only).
- `launch_failed` — `data:{code, signal, stderr}`; fires when a subprocess on a **substitution backend** (any backend but the identity `claude` row) crashes on its own (nonzero/signalled exit, not a commanded kill) — emitted right after the bare `exit` event, carrying captured stderr so the real reason (wrapper binary missing, daemon down, cloud-auth 401, etc.) is visible instead of an unexplained exit. This is the only failure signal for a bad backend, since there is no spawn-time preflight. Never emitted for the `claude` backend or clean/commanded exits.

**`turn_end` additional fields:** carries `cacheMiss` (bool) + `firstReqCacheRead`/`firstReqCacheCreation` (the deciding first-request usage) + `firstReqEvicted` (`P − read_N` on the cross-turn path, else 0), persisted to `costs.jsonl` as `cache_miss`/`first_req_cache_read`/`first_req_cache_creation`/`first_req_evicted`. It also carries `durationMs` (turn walltime incl. tool exec, from the SDK result's `duration_ms` — genuinely per-turn), `durationApiMs` (the SDK's raw `duration_api_ms`, a cumulative session total kept for reference), and `durationApiMsDelta` (the per-turn LLM/inference time, derived as a delta against the prior turn — mirrors `cost`/`costDelta`). `duration_ms` is persisted as `duration_ms`; `durationApiMsDelta` is persisted as `duration_api_ms` (so aggregates sum true per-turn LLM time). Both are null on legacy rows written before capture; rows written before the delta fix carry the old cumulative `duration_api_ms` and are left as-is. `costs.jsonl` rows additionally carry `parentSessionId` — the spawning conductor's current sessionId, resolved from the worker's ephemeral `callerInstanceId` when the `turn_end` is observed, not when the (queued) write runs (null for UI/HTTP-created sessions) — which drives the per-session worker-tree rollup.

See the `EventLog` retention note in [architecture.md](architecture.md).

**Skill-load correlation (`attachSkillLoad`, `src/parser.ts`).** A `Skill` tool call's SKILL.md content is injected back by the CLI as a separate `user` message. The parser tags the resulting `user_echo` with `skillLoad: {skill}` only when it can correlate that message with a queue of pending `{toolUseId, skill}` entries (`pendingSkillLoads`) pushed when a `Skill` tool_use is seen; an uncorrelated injection renders as an ordinary `user_echo`.

*Two surfaces, two marker names, two correlation strengths* — normalized in one place (`skillInjectionMarker`), because the replay path testing the stdout field name is exactly what shipped the "skill bubble only renders live" bug:

| surface | "CLI-injected" marker | identity link | correlation |
|---|---|---|---|
| stream-json **stdout** envelope | `isSynthetic: true` (CLI builds it as `isMeta \|\| isVisibleInTranscriptOnly`) | none — never carries `sourceToolUseID` | FIFO order (the CLI's synchronous `tool_use` → `tool_result` → injection ordering) |
| persisted **jsonl** line | `isMeta: true` (also `isVisibleInTranscriptOnly` for compaction lines) | `sourceToolUseID` — the id of the originating `Skill` tool_use | exact id match only |

Match order in `attachSkillLoad(events, sourceLine, pendingSkillLoads)`: (1) `sourceToolUseID` names a pending entry → splice it out (consuming it) and tag; (2) `sourceToolUseID` names nothing pending → the entry is gone or was never made (expired by an intervening real turn, dropped by an erroring `tool_result`, or its `Skill` tool_use sits outside the replayed range — every `sourceToolUseID` line in the persisted corpus names a `Skill` tool_use, so this is never "an injection for a different tool"), claim nothing and consume nothing; (3) jsonl-marked with **no** `sourceToolUseID` → a compaction continuation or hook feedback, never a skill load (no FIFO fallback on this surface — every real jsonl skill injection carries the id, so a fallback could only mis-stamp); (4) stdout-marked → FIFO `shift`; (5) unmarked → a real user turn, expire the queue.

**`_handleAssistant` is the single registration point** for pending entries on the live path. Measured over the 11 stdout captures on disk (12,226 lines, 6 model ids): 353 `tool_use` ids appeared on both the `assistant` envelope and the streaming frames — envelope first in **353/353** — and **0** appeared on the streaming frames alone. **Nothing arrives streaming-only**, so registering at the envelope loses nothing; registering in the `content_block_stop` branch as well would only double-register, because the envelope lands first and the entry is still pending when the stop frame arrives, and the duplicate goes on to mislabel the next injection. A trimmed live capture of one such turn is committed as `tests/fixtures/scenario-live-skill-load.json`.

**Sub-agent `tool_use`s are deliberately not registered live.** The CLI forwards sub-agent turns as envelopes tagged with `parent_tool_use_id` and no `stream_event` frames. No injection was ever observed to follow one: the *one* captured sub-agent `Skill` call ran `tool_use` → `tool_result` → `system` with no injection. ⚠️ That is **n=1 and rests on a capture since deleted** — it is no longer re-derivable from anything on disk, unlike every other number on this page, and no surviving capture contains a sub-agent turn at all, so nothing corroborates it either way. An entry registered for a sub-agent could never be consumed by its own injection, and — its `tool_result` not being an error, so the error-drop never fires — would sit at the queue head and claim the next *top-level* injection. Not registering is therefore the conservative reading: it forgoes folding we have no evidence is possible rather than risking a mislabel. A sub-agent `Skill` still folds on **replay**, where the persisted jsonl does record the injection (`loadSubAgentTranscript`, pinned against `tests/fixtures/real-skill-load-subagent.jsonl`).

`src/transcript.ts`'s replay path threads the same queue (alongside the existing `blockCursor`) through `replayPersistedLine`, for both `loadPersistedTranscript` and `loadSubAgentTranscript`, so live and replayed sessions tag identically. Replay always parses a session's jsonl in one complete pass from line 0 (never a partial/windowed range), and the queue is a fresh local array per call, so a `Skill` tool_use and its content injection are always correlated within the same pass regardless of how the resulting events are later paged.

Where only FIFO order is available, an entry could be orphaned (skill errored, or its turn was interrupted before the injection arrived) and survive to mislabel a later, unrelated injected message, so entries are bounded (`expireSkillLoads`): an erroring `tool_result` for its `toolUseId` drops it immediately, and any genuine (unmarked) `user_echo` — a real prompt, including the `queued_command` replay branch and `Instance.prompt()`/`windDown()`'s direct live emissions — clears the whole queue, since the synchronous ordering guarantee is broken once a new real turn begins. The id-matching surface is not exposed to that risk.

The client (`public/conversation.js` `_renderUserEcho`) renders a `skillLoad`-tagged echo as a collapsed `<details class="block skill">` — summary names the invoked skill, body holds the raw SKILL.md text — instead of the plain-text bubble a normal echo gets.

**Agent-tool (subagent) task events.** The CLI emits `system` events with these subtypes:

| Subtype | Payload | Notes |
|---|---|---|
| `task_started` | `{task_id, tool_use_id, description, subagent_type, task_type, prompt}` | fired the instant an `Agent` tool_use dispatches (foreground or backgrounded) |
| `task_progress` | `{task_id, tool_use_id, usage:{total_tokens,tool_uses,duration_ms}, last_tool_name}` | periodic ticks while it runs |
| `task_updated` | `{task_id, patch:{status, end_time}}` | on a state transition; `status` one of `completed\|failed\|cancelled\|error` for a terminal one |
| `task_notification` | `{task_id, tool_use_id, status, output_file, summary, usage}` | the human/model-facing "it's done" ping — the same event a `<task-notification>` block wraps when injected back into a worker's own conversation |

None carry `parent_tool_use_id`, so they land as top-level `system` events like `turn_end`. `shouldRenderSystem` (`public/blocks.js`) hides `task_progress`/`task_started`/`task_updated` from the chat feed (`task_notification` falls through the same allow-list to hidden-by-default). That re-injected `<task-notification>` block is itself persisted as a `type:"user"` jsonl line — `isTaskNotificationContent` (`src/parser.ts`) recognizes it by tag shape and it's filtered at the same three sites as `SOFT_INTERRUPT_MARKER` (`parser._handleUser`, `transcript.isPureUserPromptLine`, `transcript.replayPersistedLine`), so it never becomes a `user_echo` or shifts a rewind/fork index. Server-side, `Instance` tracks in-flight ones in `_activeAgentTasks` (see `displayStatus` below). Task events fire for more than explicit `run_in_background` calls: background is the Agent tool's default, and long-running foreground Bash gets promoted to a task (every promoted Bash observed ran ≥3.5 s — a full test run always does; a foreground Bash exceeding its `timeout` is promoted too, its tool_result resolving early with "Command running in background with ID: …"). `task_started.task_type` discriminates the kinds: `local_agent` (Agent-tool subagents) vs `local_bash` (backgrounded/promoted Bash). Only non-`local_bash` tasks enter `_activeAgentTasks` — a promoted long-lived command (a started server) never emits a terminal task event, so counting it would pin `displayStatus:'running'` and defer the idle wake and session renewal until their watchdogs. Delivery has two shapes: a **slow** task's tool_result resolves immediately with an "Async agent launched" ack (`isAsync:true`), so `turn_end` can fire while `task_updated` is still pending; a **fast/blocking** task holds the tool_result open and delivers the full output right after its mid-turn `task_notification`, always before `turn_end`.

**Overage queue intercept (`Instance.prompt`).** A **non-internal** `prompt()` is **queued** (`{text, attachments, ts}` onto `_overageQueue`), emits `overage_message_queued`, and returns **before** `user_prompt` — so it neither resumes the session nor cancels the pending resume — when **either** intercept path fires:

| Path | Condition |
|---|---|
| (a) per-session | the session was stopped mid-turn and is armed: `autoStoppedForOverage && autoResumeAt` |
| (b) global gate | the GLOBAL gate is active: `inst._overageGate() → {active, resetsAt}`, where `active` is true iff `_overageActive && _overageResumeMode` (i.e. `stop-resume`, not plain `stop`) **and** `_overageResetsAt` is a valid **FUTURE** epoch-secs instant |
| internal carve-out | `internal:true` prompts (idle-wake stub, conductor steer, and the auto-resume's own send — which first clears the flags via `cancel`) **fall through** and bypass both intercept paths |

That future-`resetsAt` check is the **safety rail**: a queued send bypasses the manual-resume clear, so a missing/past/NaN reset must mean `active:false` (sends flow normally) or every session would lock out permanently. Path (b) makes it a **global lockout**: idle/existing and brand-new sessions queue too. A queued-only session (no `autoResumeAt` yet) emits an internal **`overage_queued`** (`{resetsAt}`) that the manager (`_armQueuedOnly`) turns into an immediate resume deadline via the controller — it can't wait for a mid-turn→idle transition. The one choke point covers the WS `prompt`, MCP `send_prompt`, and any REST path. On fire, `OverageResumeController.run` delivers all queued messages as **one combined** `prompt({internal:true})` (preamble + numbered list + concatenated attachments); an empty queue is the unchanged single resume. The preamble is softened for a **queued-only** session (`_overageWasStopped === false`) — "Delivering the messages you queued while paused" vs. "…continue where you left off" for one stopped mid-work. `summary().queuedCount` carries the depth; `summary().overageActive` + `overageResetsAt` (read from the gate) let the client paint the paused state before the first message is typed. `_clearOverage` (window reset) clears `_overageResumeMode` and emits a fresh `status` for every instance so paused banners drop everywhere.

**`summary().displayStatus` / `activeAgentTasks`.** Additive, display-only fields alongside `status` — `activeAgentTasks` is the count of in-flight Agent-tool tasks (`_activeAgentTasks`, keyed by `task_id`; `task_type:'local_bash'` tasks are excluded at `task_started`, unknown `task_type`s counted); `displayStatus` is `'running'` when `status === 'idle'` and `activeAgentTasks > 0`, else identical to `status`. Never repurposes the `status` enum itself, so nothing that gates on the literal 5 `status` values (composer, kill/resume buttons) is affected. `IdleSubscriptionHub.onTurnEnd` **does** read the count (via `Instance.activeAgentTaskCount`): a `turn_end` while `activeAgentTasks > 0` **defers** the idle wake until the follow-up `turn_end` after the last subagent finishes. It **also** defers on `Instance.taskNotificationPending` — set when a `task_notification` fires *mid-turn*, cleared by any top-level `tool_result` that follows it within the turn (the task's own sync-delivered result, or the outer tool round-trip the CLI attaches queued notifications to). Still set at `turn_end` therefore means the notification is genuinely queued and an unprompted **re-invocation turn** will deliver it; the wake waits for that turn's `turn_end`. A notification consumed in-turn wakes at the same `turn_end` — parked (AskUserQuestion/ExitPlanMode) or not. So the dispatch-and-wake callback fires only when the worker AND its subagents are done and no re-invocation turn is owed (a never-finishing subagent — or a CLI that never flushes its queue — falls back to the subscription watchdog). Every summary-based surface carries the fields: `GET /api/instances`, `list_instances`, `wait_for_idle`, `respawn_instance`, `promote_session`. `displayStatus:'running'` (not just raw `idle`) means "still busy"; `status:'idle'` alone doesn't prove a backgrounded subagent has finished.

**`GET /api/instances/:id/events` paging mechanics.** Backward pages are **quiescent-aligned**: the page start snaps to the nearest quiescent point (no open block, every `tool_use` resolved; outer `user_echo`/`turn_end` reset the scan), so each page holds only whole blocks and complete tool round-trips; sub-agent group integrity pulls a child's Task head (and thus the whole group) into the page, or pushes the page start past any child with no head at or before it in the loaded array. Quiescent points are dense, so pages stay ~`limit`-sized. The `nextBefore` cursor jumps the numeric gap between the two seq spaces. Evicted/archived events get their own dense `_seq` space strictly below `trimmedBefore`, cut at the ring head's stamped `userIndex` (turn boundary) so ring + archive never overlap (the echo ordinal is the only cross-space correlator; a mid-turn ring head ⇒ gap, never duplication — marked with a seq-less synthetic `{kind:'history_gap'}` event spliced before the first ring-side event). Synthetic `{kind:'task_completion', tasks}` events (no `_seq`) are spliced in after the completing `TaskUpdate` of any task batch below the tail, so lazily-loaded history shows the finished-task bubble. Full mechanics in [architecture.md](architecture.md) → `eventArchive.ts` / `taskReconstruct.ts`.

**`postWorktreeCreate` result field** — present on `POST /api/instances` responses and MCP `create_worktree` / `spawn_instance({createWorktree:true})` results when a worktree was created. Shape: `{ ran: boolean, exitCode: number|null, durationMs: number, output: string, truncated?: true, timedOut?: true, skipped?: 'disabled', error?: true }`. `ran:false` means no hook script existed (or the kill-switch `ORCH_DISABLE_POST_WORKTREE_HOOK=1` was set — in that case `skipped:'disabled'`). ## MCP tool protocol

Mounted at `POST /mcp` (Streamable HTTP, JSON-RPC 2.0). Tools are listed in [features.md → MCP interface](features.md#mcp-interface). This section specifies the wire contract — a **clean break** with no backwards-compatibility aliases.

**Input params.** The worker handle is always `sessionId` (the stable session id; the per-process `instanceId` is internal and never accepted — a legacy `{id}` arg hard-fails as unknown). Every worker-addressing tool takes `{sessionId}`: `get_transcript`, `send_prompt`, `wait_for_idle`, `set_mode`, `approve_plan`, `reject_plan`, `answer_question`, `interrupt_turn`, `kill_instance`, `respawn_instance`, `promote_session`, `sync_worktree`, `merge_worktree` ({sessionId} form; the `{project, worktree}` form is unchanged), `get_recent_messages`, `subscribe_to_idle`, `unsubscribe_from_idle`. `spawn_instance`'s `resume` already takes a sessionId. Worktree is always `worktree` (never `worktreeName`). `spawn_instance` takes `createWorktree:true` (fresh worktree off HEAD) and/or `worktree:"<name>"` (attach existing) — the old `worktree: boolean|string` overload is removed.

**Prefix resolution (MCP boundary).** Before strict-live resolution, the MCP dispatch layer (`src/mcp/server.ts`) resolves the incoming `sessionId` arg of any tool that declares one through `InstanceManager.resolveSessionRef` — so a caller may pass an **unambiguous prefix** (e.g. first 8 chars) in place of the full UUID. It is the single, uniform chokepoint (covers `respawn_instance`/`locate_session` too) and is **non-destructive**: an exact full-id match always wins (even if it is also a prefix of another id) and passes through unchanged; a prefix that matches exactly one id is rewritten to that full id; no match is left untouched (so the strict-live paths below still produce `SESSION_NOT_LIVE`/`SESSION_UNKNOWN`/on-disk lookups). A prefix that matches **more than one** id (or a prefix shorter than `SESSION_PREFIX_MIN` (see `src/instances.ts`) that matches any) soft-refuses `{ok:false, code:'SESSION_AMBIGUOUS', sessionId, reason, matches:[<8-char ids>]}` (`isError:false`). The resolution **universe is the distinct sessionIds across all in-memory instances** (live **and** exited in `byId`) — broader than live-only, so a prefix unique among live workers but shared with an exited in-memory session is ambiguous rather than mis-resolved; historical disk-only sessions are out of scope (address them by full id). The canonical stored/persisted sessionId is unchanged (full UUID everywhere): `--session-id`/`--resume`, the `${sessionId}.jsonl` transcript, the subagent dir, and the `?caller=` URL all stay full ids. `resume` (spawn_instance) is **not** prefix-resolved.

**Worker resolution (strict-live, soft-erroring).** `sessionId` (post prefix-resolution) resolves to its single *running* (proc-attached) instance. If the session is known but has no running process → `{ok:false, code:'SESSION_NOT_LIVE', sessionId, reason}` (resume via `spawn_instance({resume:sessionId})`); if no such session anywhere → `{ok:false, code:'SESSION_UNKNOWN', sessionId, reason}`. Both are normal results (`isError:false`), matching the soft-refusal convention. The resolver **never auto-respawns** and never special-cases reads. `respawn_instance` is the exception — it targets a non-live, still-in-`byId` instance by sessionId (and 409s if actually running). `kill_instance` is now live-only (it cannot reap an already-exited non-temp instance by sessionId — accepted under strict-live).

**Resume pre-flight (`spawn_instance({resume})`).** Before constructing an Instance or spawning `claude --resume`, `InstanceManager._doCreate` verifies the resume id has a **resumable conversation** at the resolved cwd (`hasResumableConversation` in `src/transcript.ts`: the `${sessionId}.jsonl` exists **and** holds ≥1 `user`/`assistant` record — mirroring the CLI's own "No conversation found" criterion, so a marker-only crash stub of `last-prompt`/`permission-mode` lines does **not** qualify). If it doesn't, `spawn_instance` soft-refuses `{ok:false, code:'SESSION_UNKNOWN', sessionId, reason}` (`isError:false`) instead of spawning a subprocess that would exit 1 and crash-loop. This guards the case a caller pins `project`+`worktree` (which bypasses the `findSessionLocation` "project required" net) with a mistyped/bogus resume id. Because the refusal fires before any Instance is registered in `byId`, a follow-up `respawn_instance` on the same bogus id then returns `SESSION_NOT_LIVE` (no phantom crashed instance to respawn).

**Emitted handles.** Returns never carry an `instanceId`: `toConductorView()` projects every summary through an **explicit allowlist** (`CONDUCTOR_VIEW_KEYS`, `src/mcp/handlers.ts`) before it reaches `spawn_instance` / `respawn_instance` / `list_instances` / `wait_for_idle` / `promote_session`, and inline returns emit `sessionId` instead of `id`. The allowlist withholds `id` + `callerInstanceId` (per-process handles) and `debugDir` / `autoApprovePlan` / `interrupting`; `list_instances` alone adds `hasIdleSubscriber`, which `InstanceManager.list()` supplies rather than `summary()`. The `list_instances` description in `src/mcp/tools.ts` is the authoritative key list and is pinned against the code by `tests/mcp-conductor-view.test.mjs` — a field added to `summary()` is NOT published until it is added here deliberately. `?caller=<instanceId>` on the per-worker MCP URL is the caller's own **stable instanceId** (baked into `--mcp-config` at spawn). It is the instanceId — NOT the sessionId — deliberately: the URL is frozen in the subprocess config for the process lifetime, but a `/clear` rotates the sessionId in place, so a baked sessionId would go stale after the first renewal. The `/mcp` boundary (`src/mcp/server.ts`) resolves the handle to the caller's **current** sessionId per request via `InstanceManager.callerSessionId(handle)` (`byId.get(handle)?.sessionId`), so every downstream handler still receives a live sessionId as `callerId` — valid across any number of rotations, with no event or re-registration. A handle naming no live instance yields `callerId=null` (the same "no caller" path as an absent param). The instanceId never leaves the server as an identity: the two sites that surface the caller (the `renew_session` return, the plugin `caller.sessionId` envelope) emit the resolved sessionId. For `spawn_instance` the resolved caller instance is stored as `callerInstanceId` (internal/REST only). Internally the idle-subscription graph (`_idleSubscribers`) and overage timers (`_autoResumeTimers`) are keyed by the **stable instanceId**; sessionId is translated to instanceId at the register boundary (`subscribe`/`unsubscribe`) and back for delivery — so an in-place `/clear` rotation needs no re-keying.

**Caller-addressed tools.** `renew_session` takes **no** target sessionId — it acts solely on the caller, resolved from `?caller=<instanceId>` (a missing/unresolvable caller throws). Because the handle is the stable instanceId (resolved to the current sessionId at the boundary, above), a session can call `renew_session` **repeatedly** — the caller stays resolvable across each `/clear` rotation. It arms a managed `/clear` on the caller (see [Subprocess protocol → Managed `/clear`](#subprocess-protocol)); because the `/clear` rotates the caller's sessionId, `SessionRenewController` is keyed by the caller's stable `instanceId`. The other internal side structures (idle-subscription graph, overage timers) are likewise instanceId-keyed, so the rotation strands nothing and needs no migration. The reseeded prompt also carries a server-generated mechanical state block — see [features.md → Session renewal](features.md#mcp-interface) and [architecture.md](architecture.md).

**Idle wake-stub text (`IdleSubscriptionHub.deliver`).** Three variants, injected as an `internal:true` `user_echo` into the caller. **All three carry the `[[cc:wake-callback]]` marker** (defined in `public/wakeCallback.js`, imported by both `src/idleSubscriptions.ts` and `public/conversation.js`), so all three render as the wake-callback UI bubble with an orchestrator badge (🔔); only **Folded** additionally carries the `[[cc:wake-body]]` separator + payload. The markers survive persist/replay in the CLI jsonl and are stripped from display, not from the prompt the model reads. The presence of `[[cc:wake-body]]` is the "is it folded" signal — the client renders a collapsible `<details>` when a body is present, else a body-less summary line (no caret).
- **Folded** (real `turn_end` delivered to an already-idle caller): `[[cc:wake-callback]]<summary>[[cc:wake-body]]<payload>` (via `buildWakeStub`). The summary names the worker + says it finished; `<payload>` is `flattenPayload(meta, bodies)` — the compact-JSON metadata block + each raw body block joined by blank lines, i.e. **byte-identical to the content a default `get_recent_messages({sessionId})` call returns** (via the shared `buildRecentMessages` builder in `handlers.ts`, so the fold never drifts from the tool).
- **Plain** (`turn_end` but caller was **mid-turn** at delivery, so the send is deferred to when it goes idle): `[[cc:wake-callback]]` + the unchanged `Worker \`<sid>\` finished its turn. Call get_recent_messages(...) to inspect the result.` pointer (via `markPlainStub`, body-less) — decided synchronously at delivery time, so the deferral keeps the plain stub even though the caller is idle by the time it actually fires.
- **Timeout** (watchdog): `[[cc:wake-callback]]` + the unchanged `... did NOT finish — timed out after <ms>ms ...` pointer (via `markPlainStub`, body-less).
All three keep `internal:true` semantics (bypass the overage queue intercept, never cancel a pending auto-resume).

**Input validation (`validateArgs`).** Beyond type/enum/required, the server enforces the declared `pattern`, `minLength`/`maxLength`, `minimum`/`maximum`, and array `items.type`. **Unknown properties are rejected** (not silently dropped): `unexpected argument '<k>' — not a recognized parameter for <tool>. Allowed: <keys>`. Validation failures return `isError:true` with the message as a single text block. Schemas also declare `default`s mirroring handler defaults (documentation; handlers still apply them).

<a name="mcp-result-format"></a>
**Result format.** `content[0]` is always a **compact** JSON block (no pretty-print). Pure-metadata tools emit just that one block. **Text-payload tools** append separate raw, **un-escaped** text blocks in `content[1..]`:

| Tool | content[0] metadata | content[1..] bodies |
|---|---|---|
| `project_read` | `{path, size, truncated, encoding, lineCount, lineCountExact, startLine?, endLine?}` | one block: utf8 file text, or base64 (binary) |
| `project_diff` (diff mode) | `{project, worktree, baseRef, head:<sha>, contextLines, offset, truncated, nextOffset, totalLines, totalBytes, hasUncommittedChanges, untracked, ahead, includedFiles?, omittedFiles?}` | one block: raw unified diff, always including a `@@@ uncommitted working tree changes (git diff HEAD) @@@`-separated section when uncommitted changes exist (empty string when no diff and no uncommitted changes) |
| `project_diff` (summary mode) | single JSON block `{project, worktree, baseRef, head:<sha>, summary:true, ahead, totals, files[], uncommitted:{totals, files, untracked}}` | — |
| `get_recent_messages` | `{sessionId, messages:[{index, msgId, hasToolUse, textChars, textTruncated, hasPlan?, questionCount?, blocks?}], source:"ring"\|"disk", omittedToolOnly, retained:{firstSeq,lastSeq,trimmed}, hint?}` | one body block **per message**, block k+1 ↔ messages[k]: prose plus a `--- plan ---`/`--- questions ---` fenced section when the turn produced one (order-faithful to when those blocks occurred — never empty for a plan/question-only turn) — UNLESS >1 message is returned, in which case every body is prefixed with `--- message i/N · msgId · textChars chars ---` |

**`get_recent_messages` default-call bonding.** `count` defaults to 1 and is clamped to a bounded range (see the `get_recent_messages` schema). On the **default** call only (`count` omitted — not `count:1`), when the last message is plain prose the selection is bonded back to the turn's plan/questions message and spans from it through the end of that turn — so a split turn whose trailing prose spans two or more messages surfaces the plan/question together with all of it, without the caller needing an explicit `count`. The walk-back is **scoped to the current turn** (via the ring's `turn_end` seqs — a plan from an earlier turn is never pulled in), and a message that already carries its own plan/questions is returned alone. Any explicit `count` is literal (`slice(-count)`), bonding never applies.

**Annotations.** `tools/list` entries carry `annotations`: `readOnlyHint` (all `list_*`, `project_read`, `project_status`, `get_*`, `locate_session`), `destructiveHint` (`kill_instance`, `delete_worktree`, `merge_worktree`), `idempotentHint` (`set_mode`, `set_project_workspace`, `unsubscribe_from_idle`, `create_workspace`, `delete_workspace`, `rename_workspace`, `kill_instance`).

**`ok` / refusals.** `ok` is reserved for **soft refusals** only. Acknowledgement tools (`send_prompt`, `kill_instance`, `subscribe_to_idle`/`unsubscribe_from_idle`, `approve_plan`/`reject_plan`, `answer_question` success, the workspace tools, `set_project_workspace`, `delete_worktree` success) return bare data with **no `ok`**. Expected business refusals return `{ok:false, reason, code}` and are **not thrown**, with stable codes: `WORKTREE_ATTACHED`, `WORKTREE_DIRTY` (`delete_worktree`); `SESSION_NOT_LIVE` / `SESSION_UNKNOWN` (`sync_worktree` and every worker-addressing tool, from strict-live resolution); `SESSION_UNKNOWN` also from **`spawn_instance({resume})`** when the resume id has no resumable conversation on disk (resume pre-flight above); `SESSION_AMBIGUOUS` (any worker-addressing tool, when a sessionId **prefix** matches >1 in-memory session or is shorter than `SESSION_PREFIX_MIN`; carries `matches:[<8-char ids>]`); `NO_PENDING_QUESTION`, `ANSWER_COUNT_MISMATCH`, `INVALID_OPTION`, `NOT_MULTISELECT`, `EMPTY_ANSWER` (`answer_question`); `WORKTREE_BEHIND`, `BASE_BRANCH_MISMATCH`, `PARENT_DIRTY`, `WORKTREE_DIRTY`, `NOTHING_TO_MERGE`, `MERGE_FAILED` (`merge_worktree` — same `WORKTREE_DIRTY` meaning as `delete_worktree`'s (the worktree's own tree, not `PARENT_DIRTY`'s parent repo), overridable here via `allowDirty:true`); `INVALID_SUMMARY` (`renew_session`, empty summary). The only constant `ok:true` is `merge_worktree`/`sync_worktree` success (shape shared with the REST land endpoints).

**Errors.** True faults are caught and returned `isError:true` as a prose block — `<message> (HTTP <statusCode>)` when the handler set a `statusCode` — followed by a structured `{error, code, statusCode}` block. `code` derives from `statusCode` (`400→BAD_REQUEST`, `404→NOT_FOUND`, `409→CONFLICT`, `500→INTERNAL`). Example sources: `locate_session`/`project_read` 404, invalid `baseRef`/`promote_session` non-temp 400.

**Disk-backed reads (ring-first, fallback-on-demand).** The in-memory event ring is a fixed-cap (`DEFAULT_RING_CAP`, `src/instances.ts`) drop-oldest cache, but ring eviction is **invisible** to these two tools:
- `get_transcript({sessionId, fromSeq, limit})` pages via `pageInstanceEvents` (`src/eventArchive.ts`), translating at the boundary since the two surfaces deliberately differ: `fromSeq` is **inclusive** (events with `_seq >= fromSeq`, oldest-first — `fromSeq: 0` reaches the very first event), unlike the REST `after=` cursor above, which stays exclusive. Served from the ring; when the requested range dips below `trimmedBefore` (an evicted range) the on-disk session transcript is loaded and reconciled with the ring by `_seq` at a turn-aligned seam (no gap/dup). The response adds `{hasMore, nextFrom}` — poll again with `fromSeq = nextFrom` (always the last served `_seq + 1`, so a caught-up re-poll returns nothing rather than re-serving the boundary event). `limit` is bounded with a fixed default. Replaces the old `truncated` field. Caveat: a single turn larger than the ring cap leaves a mid-turn `_seq` gap (covered by `get_recent_messages`) — but reasoning length no longer triggers it, since the ring coalesces the CLI's per-token `thinking_delta`/`thinking_tokens` flood to `O(blocks)` (see the `EventLog` retention note in [architecture.md](architecture.md), and the `thinking_tokens` entry above for provenance); only a turn with thousands of tool round-trips can still reach it.
- `get_recent_messages` is ring-first; only when the retained tail can't satisfy the requested recent **text** messages (and the ring was trimmed) does it read the on-disk transcript and merge by `msgId` (ring entry wins; bounded by `DISK_REPLAY_TAIL_CAP` (`src/mcp/messageReconstruction.ts`)). `source` reports `"ring"` vs `"disk"`. A missing transcript (exited temp session) degrades to ring-only + a `hint`; never crashes. On a **defaulted** call (no `count` passed) the ring must satisfy `n+1` text messages, not `n`, since the default path may bond in one preceding plan/question message (see below) — this raises the bar for staying ring-only before falling back to disk.

Note: the REST endpoints above keep their own `worktreeName` field — they are a separate contract from the MCP tools and were not renamed.

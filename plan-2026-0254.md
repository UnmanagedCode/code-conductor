# Plan — card 2026-0254: commits tree ordering, phantom lanes, ahead divider

Base: `main@e7ed1182`, branch `code-conductor/commits-tree-0254`.

## Context

The commits view (`#commits`, `public/commits.js`) draws a git-log-style lane rail to the
left of each commit row. `computeGraph` documents one precondition — *index 0 = newest/tip,
and a parent never precedes its child* — and the server that feeds it violates it.

`getProjectCommits` (`src/worktrees.ts`) runs `git log --max-count=N --pretty=…` with **no
ordering flag**, so rows arrive in git's default committer-date priority-queue order. When
`syncWorktree` rebases, every replayed commit gets one committer second, the sort key goes
constant, and the emitted order degenerates. The rail then routes lanes at commits that were
already drawn above, so those lanes never converge and run off the bottom of the list —
phantom lines, inflated lane counts, and branch points attached to the wrong row. Because the
view renders **author** dates while the server orders by **committer** date, the dates also
read as zig-zag.

**Measured on this repo, right now** (read-only, `git log --max-count=200 --pretty='%H %P'`,
checking every in-window parent's index against its child's):

| ordering | topology violations in the last 200 commits of `main` |
|---|---|
| default (no flag) | **10** |
| `--topo-order` | **0** |

First violation: child `486f10bd` at index 54 has parent `b9703d81` at index 50. This is not
theoretical and it is not worktree-specific — it is `main`.

Separately, `.ahead-divider` (`public/styles.css`) carries `border-bottom` and
`text-align: center`, and its label `in <base>` names no direction — so a divider that is
meant to open the "already merged" section below it reads as closing the ahead band above it.

Cost of the flag, measured on this repo (2322 commits, no commit-graph file, 5 runs each of
the real production argv with `--max-count=101`): **~10 ms without, ~5 ms with**. Noise-level;
no performance objection.

## Judgements on the acceptance list

Three corrections, stated with evidence rather than planned around.

**A. AC-2's fixture must contain a merge. A linear chain cannot diverge, and a linear fixture
is a silent false green.** `git log` seeds its queue with HEAD and pops the newest committer
date. With a linear history the queue never holds more than one candidate, so lying about
dates changes nothing and the topology invariant holds *vacuously* on today's broken code —
the test would pass before the fix and the whole AC would be satisfied by a test that measures
nothing. Divergence requires ≥2 concurrent queue entries, i.e. a branch that is merged back.
The fixture in step 1 below is built for exactly that, and step 1 carries a **non-vacuity
control** that fails loudly if the fixture ever stops diverging.

**B. AC-4 undersells the `seen` guard. It is not only truncation hardening — it is the exact
defence against the backward edge the ordering bug produces.** Traced by hand through
`computeGraph` over the fixture topology (derivation in step 3): fed the *date*-ordered array,
the final row's `lanesAfter` is `[null, <sha of A>]` — a live lane aimed at a commit rendered
three rows earlier, which is the phantom line. Fed the *topo*-ordered array, the same commits
converge cleanly and the final row is `[null, null]`. The guard is what makes the second
outcome hold even if a future caller hands `computeGraph` an unordered list. Keep the AC's
code; do not repeat its framing in the comment.

**C. AC-3's `maxCols === 2` does not discriminate on a small fixture — keep it, but do not
claim it pins the ordering fix.** `activeLanes` never shrinks in *length* (freed slots become
`null` and stay in the array), and `maxCols` is computed from `lanesBefore.length` /
`lanesAfter.length`. On the 5-commit fixture it is 2 under **both** orderings; the "4 lanes"
in the card's measurement come from a 100-commit window accumulating many stale lanes. The
assertion that actually discriminates is the branch-point row (`rows[4].lanesBefore` deep-equal
`[A, A]`, `rows[4].col === 0`) plus "no live lane in the last row". Both are in the plan.
`maxCols === 2` stays as a cheap shape pin against a phantom third column.

**D. Do NOT add the per-commit server-side `ahead` boolean.** Recommended exclusion, with the
reasoning:

- The prefix property is **provable in one direction**: the ahead set is closed upward toward
  HEAD. If `X` is ahead (reachable from HEAD, not from base) and `Y` is a child of `X`
  reachable from HEAD, then `Y` cannot be reachable from base — if it were, its parent `X`
  would be too, contradicting `X` ahead. So no non-ahead commit can sit *below* an ahead
  commit on any single line of history.
- Measured across the 8 most recent merges on this repo (treating each merge `M` as HEAD and
  `M^1` as base, listing `git log --topo-order`): **8/8 `PREFIX_OK`** — under `--topo-order`
  git emits the whole merged-in line before returning to the first-parent line, so the ahead
  set lands as a contiguous prefix in every real case here.
- The counterexample is only reachable when two *unrelated* lines interleave, which
  `--topo-order` is specifically designed to avoid, and no such case exists in this repo.
- Against that: a third git subprocess per request, a new protocol field with a new doc
  clause, and `CONVENTIONS.md`'s explicit YAGNI rule ("build only what a current, concrete
  requirement needs"). Adding it now is speculative hardening for a case nobody can produce.

Consequence: AC-7 covers only the ordering guarantee, and the index-based partition at
`renderCommitList` stays. Record the upward-closure argument in the comment there so the next
reader does not have to re-derive it.

### Step 4 — the `seen` guard

**File: `public/commits.js`, in `computeGraph`.** Add `const seen = new Set();` beside
`activeLanes`, and:

```js
    // Route parents out of `col`. A parent ALREADY emitted above this row can never
    // be reached by continuing downward, so a lane aimed at it would run to the
    // bottom of the list without converging — a phantom line. Terminate it here. A
    // parent merely ABSENT from the list (older than the cap) is not in `seen`, so
    // its lane still trails off the bottom, which is the honest "history continues"
    // signal.
    if (parents.length === 0) {
      activeLanes[col] = null; // root: lane terminates
    } else {
      activeLanes[col] = seen.has(parents[0]) ? null : parents[0];
      for (let j = 1; j < parents.length; j++) {
        const pj = parents[j];
        if (seen.has(pj)) continue;
        if (activeLanes.indexOf(pj) === -1) activeLanes[firstFreeColumn()] = pj;
        // else: a lane already targets pj — the merge converges into it later.
      }
    }
    seen.add(sha);
```

`seen.add(sha)` goes after the parent routing and before `lanesAfter` is snapshotted. (Placing
it earlier is equivalent — a commit is never its own parent — but "everything above this row"
is the invariant worth reading off the code.)

Also refresh the block comment above `computeGraph`: the "index 0 = newest/tip" precondition is
now **guaranteed** by `--topo-order` in `getProjectCommits` (name it), and the trail-off
sentence should say explicitly that it applies to parents *absent* from the list, not to
parents already drawn.

**Verifiable:** 3b green; 3a and 3c still green; the 4 existing `laneEmanates` tests untouched.

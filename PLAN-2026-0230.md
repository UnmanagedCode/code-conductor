# PLAN 2026-0230 — Soft interrupt appears to be a no-op against a non-Claude-backend worker

Epic `generic-backends` · branch `code-conductor/interrupt-nonclaude` · base `main` @ `fdbb8862`

## Context

A conductor on the `claude` backend soft-interrupted a worker on a non-Claude backend. The UI
showed the arm (the ⏹ *Interrupt now* affordance is gated on `inst.status === 'turn' &&
inst.interrupting`, `public/header.js:567,573`, so the owner's read of the tell is sound) and the
worker's turn ran on to completion. No error, no annotation.

**The defect is one missing discharge path, not a design problem.** Today's soft tier already
implements the right model: it lets the open block finish and fires the moment it ends. The bug is
that a block has exactly **one** way to be retired — its own close event — and on off-spec gateway
framing that event never arrives. There is no second path. The fix is to add one.

### The suspected mechanism is refuted: there is no per-backend adapter

`resolveBackendLaunch` (`src/claudeLauncher.ts:67`) shows every backend runs the **same** `claude`
CLI — an empty template runs it directly, a template wraps it (`ollama launch claude --model
{model} --yes --`). `Instance.spawn` appends an identical argv for all of them
(`src/instances.ts:1710-1839`), and `_controlRequest` writes to that same CLI's stdin. Every
`CLAUDE_BACKEND_ID` reference in the tree was enumerated: none is in `interrupt`,
`_maybeFireArmedInterrupt`, `_controlRequest`, or `_openDrainWindow`. The interrupt path is
backend-uniform, and the **forced** tier works on these sessions — it has no quiescence gate. There
is no missing translation layer, because there is no adapter layer.

### The real defect: one discharge path, and off-spec framing withholds it

`_maybeFireArmedInterrupt` (`src/instances.ts:2817-2820`) defers while `!this._quiescence.empty`.
`QuiescenceScan` (`src/parser.ts:996`) clears `openBlocks` only on the matching
`text_end`/`thinking_end`/`tool_use`, and `pendingTools` only on a `tool_result` whose `toolUseId`
matches. No timer, no escalation. Any withheld close latches the arm for the rest of the turn,
after which `_setStatus('idle')` clears all three flags *before* `turn_end` is emitted
(`src/instances.ts:1235-1239`, `2087`) — silently, with no annotation.

Three latch classes, each confirmed by feeding the real `Parser`:

| # | Trigger | Result |
|---|---|---|
| B | `content_block_start` omits `content_block.type` | `text_delta` opens the block; `content_block_stop` falls through all three branches (`src/parser.ts:354-372`) and emits nothing → `openBlocks` holds `msg:0:text` for the turn |
| C | `content_block.type` is `"output_text"` (or any non-`"text"` string) | identical latch |
| D | proxy renames tool ids between the streamed block and the `tool_result` | `pendingTools` never drains |

Note for the fix's shape: on B and C the block is opened by the **`text_delta`**, not by
`content_block_start` — so the added signal must be expressed in UiEvent terms, not raw-frame
terms. Separately, `message_start` with no `usage` block emits no UiEvent at all
(`src/parser.ts:271`, `if (!usage) return []`), so that event cannot be relied on as a signal; the
msgId still rides on every subsequent content event.

### Why this is the sharp end

Since `91dbc1e` (card 2026-0183) every automatic stop is this same soft abort, and none has an
escalation path:

- `drainToManifest` step 3 (`src/resumeRestart.ts:165-171`) is a `while (timedOut)` loop that logs
  a warning and **waits forever**; it never forces.
- `_directOverageStop` and `_guardOverageTurnStart` both do `inst.interrupt().catch(() => {})`.
  Fire-and-forget; nothing observes failure.

The documented non-Claude overage **exemption is not this bug**: it is deliberate and root-tree
scoped (`src/usageWindowDomains.ts`, `_routeOverageStop`, card 2026-0212), and a non-Claude worker
under a Claude conductor is explicitly *in* the flow. Membership was fixed; the *effectiveness* of
the stop it issues was never checked.

**Card 2026-0207 is a sibling.** It needs a control-request timeout to latch `_interruptFired`;
here the request is never sent, so `_interruptFired` stays `false` and `_interruptArmed` stays
`true`. Different flag, same missing property: an arm with no bounded terminal outcome.

## The fix: one added discharge path, in the shared rule

**A stale open block is retired by the appearance of a different `(msgId, blockIdx)` key**, in
addition to its own close event and the existing turn boundary. That is the renderer's own keying
and the owner's original observation, expressed in UiEvent terms.

Tool spans are **unchanged and strict**: discharged only by a matching `tool_result` or a turn
boundary. No progression on tool spans (see *Declined* below), so a new block key retires the
display block while a live tool call still holds.

**One extra piece the abort needs, and it is not part of the rule.** The event that retires a
stale block is the same event that *opens* the next one, so on a stream whose closes never arrive
`openBlocks.empty` would never read true and nothing would fire. The abort therefore needs an
arm-relative signal: `QuiescenceScan` counts retirements (`boundarySeq`), `Instance` records that
count when the arm is placed, and the fire predicate becomes

```
pendingTools.size === 0 && (openBlocks.size === 0 || boundarySeq > armSeq)
```

— "nothing executing, and either nothing streaming or a block boundary has been crossed since you
armed." On a well-formed stream the close creates a real gap, so this reduces to today's
behaviour exactly. This is arm bookkeeping alongside `_interruptArmed`, not a second rule.

### Measured (real `Parser`, production semantics — the arm is cleared before `turn_end`)

```
--- well-formed streams: behaviour PRESERVED ---
OK   arm mid-text ⇒ fires at its close                        lag 1 event
OK   arm mid-thinking ⇒ fires at its close                    lag 1 event
OK   arm at a gap ⇒ fires at once                             lag 0
--- latch classes: now fire at the NEXT block start ---
OK   [B] type absent, 2nd block follows                       lag 3 events (one block)
OK   [C] type "output_text", 2nd block follows                lag 3 events (one block)
OK   [C+] unclosed, new MESSAGE follows                        lag 3 events (one block)
OK   [C/thinking] unclosed thinking, next block               lag 2 events
--- RESIDUALS: no next block key AND no close ---
OK   [R1] arm in the FINAL block of the turn                  NEVER
OK   [R2] gateway emits ONE block for the whole turn          NEVER
--- tool spans STRICT: must HOLD ---
OK   [S1] tool dispatched, no result                          NEVER
OK   [S2] 2 tools/1 msg, first resolved                       NEVER
OK   [S3] tool + later text, same msg                         NEVER
OK   [S5] tool in flight + msgId-less system events           NEVER
OK   [S6] NEW msgId while a tool is genuinely open            NEVER
OK   [S7] its tool_result lands ⇒ fires at next boundary      lag 1 event
OK   [S8] NEW BLOCK KEY while a tool is in flight             NEVER
OK   [D] tool_result id renamed by a proxy                    NEVER (→ backstop)
--- REAL capture trace-quiescent-boundary.jsonl (arm at event 28) ---
   today=48   repaired=48   IDENTICAL — no regression
```

**Lag: one block.** On B/C/C+ the abort lands at the start of the block after the one that was
streaming when the arm was placed — not never.

**Interleaving premise, measured not reasoned.** Can a different block key appear while the
previous block is genuinely still streaming? On the only live `stream_event` capture committed
in-tree (`trace-quiescent-boundary.jsonl`, 56 parser events, 6 distinct block keys):
**0 interleaved-while-open events.** Blocks are strictly sequential, including the four
consecutive tool blocks. **This is n = 1 turn** — the repo holds no live-frame capture from a
substitution gateway, so for those the premise rests on the Anthropic streaming contract plus this
one Claude turn. That limit is real; what bounds the damage is that a false retire here costs a
render artifact the client already draws as `· incomplete`, not lost work.

### Residuals — the predicate is still forgeable, and here is exactly how

Under this design something *can* still latch the abort, and it must be said plainly rather than
softened:

- **R1** — the arm lands in the **final** block of a turn on a B/C gateway: no next block key, no
  close. Never fires; resolves only at `turn_end`.
- **R2** — a gateway that emits **one** block for the whole turn: same.
- **D** — renamed tool ids: `pendingTools` never drains. Unchanged by this fix.
- A genuinely wedged tool — by design, unchanged.

R1/R2 mean the abort's *own* signal is still withholdable. What they do **not** mean is that the
stop fails: in both, the turn ends on its own, and `turn_end` reaches `idle` — which is precisely
what the automatic callers need. So they are cosmetic for the drain and the overage stop (the
session does go idle) and a mild annoyance for a human wanting to cut a long monologue early.

### Declined, and why: progression applied to *tool spans*

Recorded here as a deliberate contrast with what is being built, because the two look similar and
only one is safe.

**Corpus.** 1,288 real session jsonls under `~/.claude/projects`, backend-attributed via
`<store>/session-backends.json`: **68,431 outer tool spans**, 5,615 turns, across the identity
backend and **six** substitution backends / thirteen backend-model pairs (`ollama`×4,
`openrouter`, `openrouter-pim`, `codex`×3, `opencode`×3). Sub-agent lines excluded, mirroring the
scan's own filter.

- **A msgId change does occur with a span open**: 85 events (53 on a substitution backend). Split
  by whether the span ever resolves: **85 dangling** (no `tool_result` anywhere), **0
  late-resolving**. So "a step change cannot occur while a span is *live*" survives 68,431 spans
  with zero counterexamples — but it is jsonl, not live stdout, and a span live at session end is
  indistinguishable from one that never ran, so this is strong evidence, not proof.
- **Class D is unattested**: **0 orphan `tool_result` ids** across all 68,431 spans. Every result's
  id matches a `tool_use` id, on every gateway — including where ids are foreign-shaped
  (`tests/fixtures/real-skill-load-parent.jsonl`, a `gpt-5.6-sol` capture, round-trips
  `call_F8awQmxYJ4V21fFu7iUUnM2v` on both sides). Only 10 dangling `tool_use`s exist at all, 9 on
  the identity backend, all consistent with interrupted turns.

So tool-span progression would buy a class no gateway in a 68,000-span corpus exhibits, at the
cost of the one failure that deletes live work. Declined. Class D routes to the backstop. If it is
ever seen in the wild, re-run the orphan-`tool_result` scan rather than re-deriving it.

## Where the added path lives: **in** `QuiescenceScan` — the earlier two-scan split is superseded

I previously argued for a separate abort-only scan on the grounds that the abort wants a different
*rule* from the paging snap. Under this framing that is wrong, and I withdraw it: the model is
already right and only the signal is incomplete, so this is a repair to the shared rule and
forking it would leave the paging consumer holding the unrepaired half. One owner,
`QuiescenceScan`.

**But paging does not actually benefit, and the "same defect from the other end" hypothesis is
measurably false.** Quiescent indices, today vs repaired:

```
MALFORMED (block 0 never closes): events=16
   today    (2): [0,1]      repaired (2): [0,1]      IDENTICAL
WELL-FORMED:                      events=21
   today   (11): [0,1,4,5,8,9,12,13,16,17,20]
   repaired(11): [0,1,4,5,8,9,12,13,16,17,20]        IDENTICAL
```

Bit-identical on both. The reason is the two consumers ask different *questions*, not different
rules: paging asks "is state empty **at index i**", evaluated before applying event `i` — and the
retiring event is the same event that opens the next block, so no new empty index appears. The
abort asks "has a boundary been crossed **since I armed**", which is why it needs `boundarySeq`.

> **CORRECTION (found during implementation, 2026-08-26).** The *measurement* above is right and
> the *generalisation* from it is wrong. "The retiring event is the same event that opens the next
> block, so no new empty index appears" misses the case where that **successor block itself
> closes**: state then reaches empty where it never would have, and paging gains a cut. Measured on
> an array these two did not cover — unclosed text `m1:0`, then a thinking block `m1:1` that opens
> and closes normally, then `m1:2` — a delete-based retire yields `[0,1,2,6]` against the base's
> `[0,1,2]`. That extra cut is not a bonus: index 6 would end the preceding page **on** the
> never-closed block, which is exactly what the snap exists to prevent.
>
> The retire therefore **MARKS the stale block rather than deleting it**: it stays in `openBlocks`,
> `empty` keeps its original meaning, and paging is identical **by construction** on every stream
> rather than on the arrays that happened to be measured. This is the semantically correct answer,
> not a compatibility shim — a block that never closes is unfinished permanently, so a consumer
> that must render whole blocks is right to keep counting it. What progression publishes is
> `boundarySeq`, which is all the abort ever needed. Pinned by
> `tests/quiescent-paging.test.mjs` → the three `2026-0230:` cases, the third being the
> stale-then-normally-closing array.

Consequence: the repair is **safe** for paging (provably unchanged, so no paging test can regress)
and the paging consumer is not fixed by it. A snap can still fail to find a cut on a malformed
stream and fall back to the raw start (`quiesceStart`'s `best !== -1 ? best : start`), with
`finalizeDanglingBlocks()` rendering `· incomplete` — the pre-existing degradation, untouched.
**Do not** extend the repair to give paging cuts inside never-closed blocks: that is what the snap
exists to prevent, and it is a separate card if it is wanted at all.

## Changes

### 1. `src/parser.ts` — `QuiescenceScan`, repaired

- `openBlocks` becomes `Map<key, {owner: "msgId:blockIdx", stale}>` so a stale entry can be
  recognised — and, per the correction above, so it can be MARKED rather than deleted.
- Add `boundarySeq`, incremented on every retirement (its own close, a progression mark, or a
  turn-boundary clear over blocks not already marked).
- **The added path:** on an event carrying **both** a `msgId` and a numeric `blockIdx`, retire
  (mark) every open block whose key differs. Comment at the source that this reads only from events that
  *have* a block key — an `msgId`-less or `blockIdx`-less event (`system`, `tool_result`, a bare
  `assistant_message`) names no block and must retire nothing — and cite the evidence: a candidate
  that read this from any event fired at **index 35** of `trace-quiescent-boundary.jsonl` while
  Bash `3iXWNctP` ran until **index 47**.
- `pendingTools` untouched.
- Header comment: both consumers, their two different questions, the measured
  paging-identical result, and the declined tool-span progression with its corpus numbers.

### 2. `src/instances.ts` — arm-relative bookkeeping

- `interrupt()` soft branch: record `this._interruptArmSeq = this._quiescence.boundarySeq`
  alongside `_interruptArmed`; clear it wherever those flags clear (`_setStatus`, `~1620`, `~3327`).
- `_maybeFireArmedInterrupt` (`~2820`): gate on the Measured section's own predicate —
  `pendingTools.size === 0 && (openBlocks.size === 0 || boundarySeq > armSeq)` — extracted as
  `_atInterruptBoundary()`, with `_blockedOnPermission()` still overriding it.

  > **CORRECTION (found during implementation, 2026-08-26).** The line this section originally
  > carried —
  > `if (!this._quiescence.empty && this._quiescence.boundarySeq <= this._interruptArmSeq && !this._blockedOnPermission()) return;`

- No new scan, no second `_emitUi` feed.

### 3. `src/instances.ts` + `src/resumeRestart.ts` — bounded terminal outcome (backstop)

Still required — an arm with no bounded terminal outcome is the underlying defect either way.

**Expected firing rate: exceptional, not load-bearing.** The residuals that survive change 1 are
R1/R2 (where the turn ends by itself and the session reaches idle anyway), class D (unattested in a
68,000-span corpus), and a genuinely wedged tool. So the backstop fires only when the turn *never
ends* — which is the case that has no other remedy. **The working assumption therefore stands and
needs no fresh product call:** bound the three automatic callers only, escalate to force plus
annotation on expiry, manual ⏸ unbounded.

- `_directOverageStop`, `_guardOverageTurnStart`, `drainToManifest` pass an opt-in `{ deadlineMs }`
  to `interrupt()`. Manual ⏸ / `interrupt_turn` keep today's unbounded semantics — human and
  conductor both already have ⏹, and `protocol.md`'s "no timer, no max-defer knob" rationale
  stands for the tier it describes.
- On expiry: escalate to the forced abort and emit a `system`/`stderr` annotation naming *why* the
  boundary was never reached (the held block keys and `toolUseId`s), so the next report is a
  one-line diagnosis. Deadline via a module constant with an `ORCH_*` env seam, following
  `ORCH_OVERAGE_RESUME_BUFFER_MS` (`src/instances.ts:4579`), so tests never sleep out a real clock.
- `drainToManifest`'s `while (timedOut)` loop keeps waiting, but each re-arm now escalates rather
  than only warning.

## Post-review addenda (implementation + review, 2026-08-26)

**Which S-case pins tool-span strictness: S8, not S1.** Mutation-proving showed that a
progression-clears-`pendingTools` mutant *survives* S1 — S1's tool block was already closed by
`tool_use` before the arm, so `openBlocks` is empty when its next block key arrives and the mark
loop is a no-op there. S8 is the only case whose mark loop runs with a span open, so its
`pendingTools.size === 1` assertion is the actual killer. Both tests now state which invariant
they pin separately: S1 = "an unreturned span holds the arm across events that name no new block";
S8 = "progression never discharges a span". S8 must not be weakened.

**The arm-time snapshot has its own pin now.** `_interruptArmSeq = this._quiescence.boundarySeq`
survived mutation to `= 0` against every other test in this card's suite, because all of them arm
while `boundarySeq` is still 0 — where the two are indistinguishable. It was killed only by
pre-existing general soft-interrupt tests that happen to arm after a prior retirement, i.e. by
accident. `tests/interrupt-nonclaude.test.mjs` → *arm-time snapshot: crossings BEFORE the arm do
not count toward it* now creates the missing condition directly (retire a block, then arm mid-way
through a later one) and asserts the abort holds until the next retirement. Under `= 0` it fails
behaviourally — the abort fires synchronously inside `interrupt()`, cutting the block that is
streaming.

**The drain's grace-loop force path is tested.** `tests/resume-restart-drain-backstop.test.mjs`
covers both fuses: the soft deadline shorter than the grace window, the grace window shorter than
the deadline (`graceMs: 100` vs `10000`), the don't-escalate side of each, and the equal-fuse case
proving `turnForceAborted` keeps the two paths from double-forcing one straggler.

**WAIVED, deliberately kept: `_interruptArmSeq = 0` in `_clearInterruptArm()`.** Mutation showed
the line is redundant — the field is read only while `_interruptArmed` is true, and arming always
re-snapshots it first — and it is kept anyway, with no test. That equivalence rests on a
call-chain reading (one reader, one caller, one gate), and a call-chain reading enumerates the
callers that exist *today*, not the reachable set. "The arm's fields are cleared as one unit" is
the property a future reader will rely on when adding a second reader. Leave the line; if
`_clearInterruptArm` is edited, it stays.


## Round-2 review addenda (2026-08-26)

**Deleted as vacuous: `'drain grace loop: a straggler that discharges within the grace window is
never escalated'`.** Measured to pass both unmutated and with the grace loop's `status !== 'turn'`
guard removed, at file and whole-suite scope. Its staging discharged the arm in ~0 ms against a
3000 ms grace window, so the instance was idle before the loop's first tick returned, `timedOut`
was `false`, the `while (timedOut)` body never ran, and no force could land either way —
`turnForceAborted === false` was settled by test timing, not by the loop withholding anything. Not
repairable: see the next note.

**Pinned this round: the deadline's `_interruptFired` conjunct.** Dropping it from
`_armInterruptDeadline`'s guard SURVIVED the entire suite (3302 tests, 0 failures) — nothing
reached the window `_interruptArmed && _interruptFired && status === 'turn'`. The round-1
"discharges normally" case does not: it is already idle when its deadline comes due, so the guard
returns on the `_interruptArmed` conjunct and `_interruptFired` never decides anything.
`tests/resume-restart-drain-backstop.test.mjs` → *deadline: a stop that has already FIRED is not

the deadline (`delay_ms` on that turn) so the deadline genuinely fires inside the window. Without
the conjunct the deadline escalates on top of a stop that already landed: a second
`control_request`, a forced abort of a turn that was winding down cleanly, and a diagnostic naming
a boundary that was in fact reached.

**MEASURED-REDUNDANT BUT RETAINED: the grace loop's `inst.status !== 'turn'` guard**
(`src/resumeRestart.ts`, step 3's escalation). Proven untestable: `interrupt({force:true})` returns
